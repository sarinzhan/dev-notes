## TL;DR
A Spring Data repository is an interface; Spring generates the implementation (`SimpleJpaRepository` over an `EntityManager`) at startup. The hierarchy is `Repository` → `CrudRepository` → `PagingAndSortingRepository` → `JpaRepository`. Queries come from method names, `@Query` (JPQL or native), the Criteria API, Specifications or QueryDSL. Updates and deletes written as queries need `@Modifying`.

## Key points

### Repository interfaces
- `Repository<T, ID>` is a **marker interface**: it only tells Spring Data that subtypes are repositories to be scanned and proxied. It is annotated `@Indexed`, so every sub-interface is recorded in the component index (`spring-context-indexer`) and found by scanning without classpath walks.
- `CrudRepository` adds `save`, `saveAll`, `findById`, `existsById`, `findAll`, `count`, `deleteById`, `delete`.
- `ListCrudRepository` (Spring Data 3.0) returns `List` instead of `Iterable`.
- `PagingAndSortingRepository` adds `findAll(Pageable)` and `findAll(Sort)`. Since Spring Data 3.0 it no longer extends `CrudRepository`; combine them yourself or use `JpaRepository`.
- `JpaRepository` = `ListCrudRepository` + `ListPagingAndSortingRepository` + JPA extras: `flush()`, `saveAndFlush()`, `deleteAllInBatch()`, `getReferenceById()` (a lazy proxy without a `SELECT`).
- `@NoRepositoryBean` on an intermediate interface (for example a `BaseRepository<T, ID>` with shared methods) stops Spring from creating a bean for it.
- `save()` calls `persist()` when the entity is new (`id == null`, or `@Version` is null, or `Persistable.isNew()`), otherwise `merge()`. `merge()` on an entity with a manually assigned id issues an extra `SELECT`.

### Ways to write a query
| Way | How | When |
|---|---|---|
| Method name | `findByStatusAndCreatedAtAfter(...)` parsed by `PartTreeJpaQuery` | simple filters; long names become unreadable |
| JPQL / HQL `@Query` | entity and field names, not tables; `:named` or `?1` params | most custom reads; goes through the persistence context |
| Native `@Query(nativeQuery = true)` | plain SQL; result mapped to entity, interface projection or `Tuple` | DB-specific SQL (`jsonb`, CTEs, `FOR UPDATE SKIP LOCKED`) |
| Criteria API | `CriteriaBuilder` → `CriteriaQuery<T>` → `Root<T>` → `Predicate` | dynamic filters; verbose, type-safe with the generated metamodel |
| `JpaSpecificationExecutor` | `Specification<T>` = reusable lambda over Criteria | composable dynamic filters in repositories |
| QueryDSL | generated `Q` classes, `BooleanBuilder`, `Predicate`, `QuerydslPredicateExecutor<T>` | the same as Criteria but readable |
| Custom implementation | `OrderRepositoryCustom` + `OrderRepositoryImpl` (suffix `Impl`), injected `EntityManager` | anything else |

- A native query bypasses JPQL parsing but still returns managed entities when it maps to an entity. What it does **not** do is trigger an automatic flush of the pending changes in the persistence context before it runs (Hibernate flushes only when the native query is known to touch the affected tables; set the query spaces or call `flush()`), see [[jpa-persistence-context-and-entity-lifecycle]].
- Criteria API concepts: `CriteriaBuilder` (factory for queries and predicates, from `EntityManager`), `CriteriaQuery<T>` (the query, typed by result), `Root<T>` (the entity in `FROM`), `Predicate` (the `WHERE` condition).
- QueryDSL concepts: `BooleanBuilder` (the predicate builder, plain `new`, no `EntityManager` needed), `QOrder`/Q-classes (generated by an annotation processor at build time, one per entity), `Predicate`, `QuerydslPredicateExecutor<T>` mixed into the repository. On Hibernate 6 / Jakarta use the `querydsl-jpa` artifact with the `jakarta` classifier.

### `@Modifying`
- A JPQL/native `UPDATE` or `DELETE` in `@Query` must be annotated `@Modifying`, so Spring Data calls `executeUpdate()` and returns the affected row count (`int`/`void`) instead of trying to build a result set. The method also needs a transaction: `@Transactional` on it or on the caller (see [[spring-transactional]]).
- Bulk JPQL updates skip the persistence context: entities already loaded keep stale values. `@Modifying(clearAutomatically = true, flushAutomatically = true)` flushes pending changes first and clears the context after.

### Paging and projections
- `Page<T>` runs a second `count` query; `Slice<T>` fetches `size + 1` rows and skips the count; prefer `Slice` for infinite scroll.
- Interface or record projections (`select new com.x.OrderView(o.id, o.total)`) avoid loading entities you will not change; combine with `@Transactional(readOnly = true)`.

## Example
```java
public interface OrderRepository extends JpaRepository<Order, Long>, JpaSpecificationExecutor<Order> {

    List<Order> findByCustomerIdAndStatus(Long customerId, OrderStatus status);

    @Query("select o from Order o join fetch o.lines where o.id = :id")
    Optional<Order> findWithLines(@Param("id") Long id);

    @Modifying(clearAutomatically = true)
    @Transactional
    @Query("update Order o set o.status = 'EXPIRED' where o.status = 'NEW' and o.createdAt < :before")
    int expireOlderThan(@Param("before") Instant before);

    @Query(value = """
            select * from orders
            where status = 'NEW'
            order by created_at
            limit :n for update skip locked
            """, nativeQuery = true)
    List<Order> lockNextBatch(@Param("n") int n);
}
```

## Pitfalls
- A `@Query` with a typo in an entity field fails at **startup** (good); a native query with a typo fails at **runtime** on the first call (test it).
- Derived query names are validated at startup too; a property that does not exist aborts context creation with `PropertyReferenceException`.
- `findAll()` on a large table without `Pageable` loads everything into the persistence context.
- `deleteById` first does `findById` and then `remove` (two statements, cascades apply); `deleteAllInBatch` is a single JPQL delete without cascades.
- Repository methods are transactional by default (`SimpleJpaRepository` is `@Transactional(readOnly = true)` with write methods overriding), but a custom `@Query` read inside a service without a transaction runs on its own and cannot lazy-load afterwards; see [[spring-transactional]] and [[jpa-n-plus-one]].
- Locking annotations on repository methods: [[jpa-locking]].
