## TL;DR
Three columns that every schema gets and most get wrong at least once. **Time**: store instants as `timestamptz` (UTC on the wire, converted on display), store calendar facts (a birthday, a tariff start date in the operator's local calendar) as `date` or `timestamp` plus a time zone name, never as `timestamp` without zone for instants. **Money**: `numeric(19,4)` or minor units in `bigint`, with the currency next to it; `BigDecimal` in Java, never `double`. **Identifiers**: a `bigint` identity or sequence for internal keys, UUID v7 when ids are generated outside the database or exposed publicly, UUID v4 only when unpredictability matters more than index locality.

## Key points

### Time
| Postgres type | Stores | Use |
|---|---|---|
| `timestamptz` | an instant (microseconds since epoch, normalized to UTC); the session `TimeZone` only affects display and parsing | `created_at`, `expires_at`, event times, anything that happened |
| `timestamp` (without time zone) | a wall-clock reading with no zone; `2026-10-27 09:00` is ambiguous | avoid for instants; acceptable for "local time rule" data paired with a zone column |
| `date` | a calendar day | birthdays, billing periods, partition keys |
| `interval` | a duration with months/days/seconds parts | rarely in columns; fine in queries |
| `tstzrange` | an interval of instants | validity periods, with an exclusion constraint against overlaps |

- `timestamptz` does not store the zone; it stores UTC. If the user's zone matters (show the activation in Bishkek time, run the job at 09:00 local), store the IANA zone name (`Asia/Bishkek`) in its own column; offsets like `+06:00` drift with DST rules and politics.
- Java mapping: `Instant` or `OffsetDateTime` ↔ `timestamptz`; `LocalDate` ↔ `date`; `LocalDateTime` ↔ `timestamp`; `ZonedDateTime` is a `timestamptz` plus a separate zone column. Hibernate 6 maps `Instant` to `timestamptz` by default (`hibernate.timezone.default_storage = NORMALIZE_UTC`); run the JVM in UTC (`-Duser.timezone=UTC`) and the JDBC session in UTC so no layer silently converts.
- Compare and compute in UTC; render in the user's zone at the edge. `date_trunc('day', created_at AT TIME ZONE 'Asia/Bishkek')` for "per local day" reports.
- `created_at` is not unique and pod clocks differ ([[time-and-clocks]]): order and paginate by `(created_at, id)`.
- `now()` is the transaction start time, `clock_timestamp()` the wall clock; in a long transaction they differ.

### Money
- Floating point cannot represent 0.1 exactly; `0.1 + 0.2 != 0.3` and sums of thousands of rows drift ([[numbers-bits-and-floating-point]]). Never `double`/`float`/`real`/`double precision` for amounts.
- Two correct representations:
  - `numeric(19, 4)` (arbitrary precision, exact) with `BigDecimal` in Java and `RoundingMode.HALF_EVEN` (banker's rounding) or whatever the regulation prescribes at the point of rounding. Four decimals allow intermediate precision; the currency's exponent (2 for KGS/USD, 0 for JPY, 3 for KWD) decides the final rounding.
  - **Minor units** in `bigint` (`amount_minor = 12550` for 125.50) with `long` in Java: fastest, no rounding surprises in storage, conversion only at the boundary. Standard in card processing and ISO 8583 messages ([[emv-card-processing]]).
- Always store the **currency** (`char(3)` ISO 4217) next to the amount; a value object `Money(amount, currency)` in the domain refuses to add KGS to USD ([[value-objects-and-entities]]). Exchange rates are `numeric(19, 8)` or more with the rate's timestamp.
- Compute in `BigDecimal` with `MathContext.DECIMAL128`, round once at the end. Ledger tables are append-only: insert postings and derive the balance ([[design-payment-processing]]).

### Identifiers
| Generator | Size | Ordered | Generated by | Use |
|---|---|---|---|---|
| `bigint GENERATED ALWAYS AS IDENTITY` / sequence | 8 bytes | yes | database | internal primary keys, FK columns, best index locality; `serial` is the legacy form |
| UUID v4 (random) | 16 bytes | no | anyone | unpredictable public ids, tokens; random inserts scatter across the B-tree and bloat it |
| UUID v7 (RFC 9562, 2024) | 16 bytes | yes (millisecond timestamp prefix + random) | anyone | ids generated by clients or before the insert (outbox, sagas, idempotency), merged across shards; nearly the locality of a sequence |
| ULID / KSUID / Snowflake | 16 / 20 / 8 bytes | yes | application | same role as v7; Snowflake needs a worker id |
- Exposing `bigint` ids publicly leaks volume (order 1 000 001 today, 1 000 500 tomorrow) and invites enumeration; expose a UUID or an opaque public id and keep the `bigint` internal, or use UUID v7 for both.
- Sequences have gaps (rollbacks, caching, crashes); never rely on them being contiguous.
- Postgres 17 has no built-in `uuidv7()` (it arrives in 18); generate v7 in Java (`java.util.UUID` has no v7 factory; use a small library) or the `pg_uuidv7` extension. Store as the native `uuid` type, never `varchar(36)`.
- Natural keys (MSISDN, ICCID, email) are unique constraints, not primary keys: they change or get reassigned. Surrogate id plus `UNIQUE` on the natural key.
- Partition keys and v7 ordering: [[postgres-partitioning]]; random keys vs B-trees: [[database-indexes]].

## Example
```sql
-- V9__payments.sql
CREATE TABLE payment (
    id              uuid        PRIMARY KEY,            -- UUID v7 from the application
    order_id        bigint      NOT NULL REFERENCES esim_order(id),
    amount_minor    bigint      NOT NULL CHECK (amount_minor > 0),
    currency        char(3)     NOT NULL CHECK (currency ~ '^[A-Z]{3}$'),
    fx_rate         numeric(19, 8),
    created_at      timestamptz NOT NULL DEFAULT now(),
    captured_at     timestamptz,
    customer_tz     text        NOT NULL DEFAULT 'Asia/Bishkek',
    UNIQUE (order_id, currency)
);
```
```java
public record Money(long minor, Currency currency) {
    public BigDecimal major() {
        return BigDecimal.valueOf(minor, currency.getDefaultFractionDigits());
    }
    public Money plus(Money other) {
        if (!currency.equals(other.currency)) throw new IllegalArgumentException("currency mismatch");
        return new Money(Math.addExact(minor, other.minor), currency);
    }
    public static Money of(BigDecimal major, Currency currency) {
        return new Money(major.setScale(currency.getDefaultFractionDigits(), RoundingMode.HALF_EVEN)
                              .movePointRight(currency.getDefaultFractionDigits()).longValueExact(), currency);
    }
}

@Entity class Payment {
    @Id UUID id = UuidV7.generate();                 // time-ordered, generated before insert
    long amountMinor; String currency;
    Instant createdAt = Instant.now();               // timestamptz
    String customerTz;                               // IANA name, for display and local-day reports
}
```

## Pitfalls
- `timestamp` without zone plus a JVM in `Asia/Bishkek` and a database in UTC: every value shifts six hours on the way in or out, found months later in a report.
- `double` for money "because it is just a prototype": the prototype ships, and reconciliation differs by one tyiyn per thousand rows.
- UUID v4 primary keys on a 100-million-row table: random inserts touch random leaf pages, cache hit ratio drops, index bloat doubles ([[postgres-vacuum-and-bloat]]).
- `varchar` for UUIDs: 37 bytes instead of 16 and string comparison instead of integer comparison in every index.
