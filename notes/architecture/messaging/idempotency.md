## TL;DR
An operation is idempotent when applying it twice has the same effect as once. Every at-least-once channel ([[spring-kafka-consumer|Kafka]], HTTP retries, the [[outbox-pattern]]) delivers duplicates sooner or later, so the receiving side must either be naturally idempotent or deduplicate by a key. The dedup record and the business effect must commit in the **same transaction**.

## Key points

### Natural idempotency vs deduplication
- Natural: `UPDATE sim SET status = 'ACTIVE' WHERE iccid = ?`, `INSERT ... ON CONFLICT DO NOTHING`, "set balance to X". Repeating is harmless, no bookkeeping.
- Not natural: `balance = balance - 100`, "send SMS", "charge card", "append row". Needs a key and a dedup store.
- Prefer rewriting the operation to be natural (absolute state instead of deltas) before adding a dedup table.

### Idempotency keys
- A unique id generated by the **producer of the request**: event `id` from the outbox row, `Idempotency-Key` header from the client, transaction reference in payments.
- Store the key with the result. A repeat with the same key returns the stored result instead of re-executing; a repeat with the same key but different payload is a client bug (return 422).
- Keys need a TTL (24 h is the Stripe convention) or a purge job; a Redis `SET key value NX EX 86400` works when losing the key on Redis restart is acceptable ([[redis-data-structures]]), Postgres when it is not.

### Idempotent Kafka consumer
- Table `processed_events(event_id uuid primary key, processed_at timestamptz)`.
- In one transaction: insert the key, do the business write, commit. If the insert fails with a unique violation, the event was already handled: acknowledge and skip.
- Why not check first, then process? Two consumers (after a rebalance) read the same record, both see "not processed", both execute. The unique constraint is the only race-free check.
- Why same transaction? If the key commits and the business write fails, the event is lost forever; if the business write commits and the key does not, the next delivery double-applies.

### Kafka exactly-once and why the consumer still needs this
- Idempotent producer (`enable.idempotence=true`, default since Kafka 3.0): the broker dedups producer retries using a producer id + sequence number. Covers only "the send was retried", not "the application called send twice".
- Transactions (`transactional.id`, `isolation.level=read_committed`): atomic consume-transform-produce **inside Kafka**. They do not cover a Postgres write, an HTTP call or an SMS. The moment a side effect leaves Kafka, you are back to at-least-once plus dedup.
- Offset commit and DB commit are separate systems; a crash between them re-delivers ([[kafka-consumer]]).

### Idempotent HTTP APIs
- `GET`, `PUT`, `DELETE` are idempotent by the HTTP contract; `POST` and `PATCH` are not ([[rest-and-http]]).
- `PUT /sims/{iccid}/profile` with the full state is idempotent by design; `POST /payments` needs `Idempotency-Key`.
- Server flow: look up the key; if found and finished, replay stored status + body; if found and in progress, return 409; else insert the key, process, store the response.

### Retries and timeouts in payments
- A timeout is the ambiguous case: the charge may or may not have happened. Never retry a charge without the same idempotency key; without one you must query the status first.
- Card processing uses the same idea: STAN/RRN and the reversal/advice flow exist because the terminal cannot know whether the host saw the request ([[emv-card-processing]]).
- Combine: bounded retries with backoff, a stable key across retries, and a reconciliation job for what is still unknown after the retry budget.

## Example
```java
@Component
@RequiredArgsConstructor
public class ActivationListener {
    private final JdbcTemplate jdbc;
    private final SimService sim;

    @KafkaListener(topics = "esim.activation", groupId = "provisioning")
    @Transactional
    public void on(ActivationRequested evt, Acknowledgment ack) {
        int inserted = jdbc.update(
            "INSERT INTO processed_events(event_id) VALUES (?) ON CONFLICT DO NOTHING",
            evt.id());
        if (inserted == 0) {           // duplicate delivery
            ack.acknowledge();
            return;
        }
        sim.activate(evt.iccid());     // same transaction as the key
        ack.acknowledge();             // after commit the offset moves; a crash before it just re-delivers
    }
}
```
`ON CONFLICT DO NOTHING` avoids the exception-driven control flow and does not mark the transaction for rollback the way a caught `DataIntegrityViolationException` would in JPA ([[spring-transactional]]).

## Pitfalls
- Checking "already processed?" and then doing the work in separate transactions reopens the race. Insert the key in the same transaction.
- Under READ COMMITTED a concurrent duplicate blocks on the unique index until the first commits, then fails or returns 0 rows; see [[postgres-isolation-levels]].
- Deduplicating in memory (a `Set` in the consumer) is lost on restart and not shared between instances.
- Using the Kafka offset or partition as the key: it changes on re-partitioning and on replay from a backup.
- Idempotent does not mean "safe to retry forever"; a poison message still needs a dead letter topic ([[spring-kafka-consumer]]).
- Related: [[saga]] compensations must be idempotent too; see [[circuit-breaker]] for when to stop retrying.
