## Кратко
Собеседование по проектированию систем — это структурированный разговор: уточнить требования, оценить нагрузку, определить API и модель данных, нарисовать общие блоки, а затем подробно разобрать две-три сложные части. Блоки всегда из одного и того же каталога — балансировщик нагрузки, сервисы без состояния, кеш, база данных с репликами и шардами, очередь сообщений, CDN, ограничитель частоты запросов, — а умение состоит в том, чтобы выбрать, какой компромисс (согласованность, задержка, стоимость, сложность) покупает каждый блок. Горстку чисел нужно знать наизусть, чтобы оценки были обоснованными.

## Основное

### Схема (45 минут)
1. **Требования** (5 мин): функциональные («отправить пользователю push/SMS/email»), нефункциональные (масштаб, задержка, надёжность хранения, согласованность), вне рамок. Спросить про соотношение чтения и записи и про пик против среднего.
2. **Оценки** (5 мин): DAU → QPS → хранилище/трафик, пик = 2–5× среднего.
3. **API** (5 мин): несколько REST-эндпоинтов или топиков Kafka ([[rest-and-http]], [[openapi-swagger]]). Ключи идемпотентности для записи.
4. **Модель данных** (5 мин): основные сущности и хранилище для каждой ([[database-fundamentals]], [[normalization-and-denormalization]]).
5. **Общая архитектура** (10 мин): клиент → LB → сервисы → кеш/БД/очередь. Пусть будет скучно.
6. **Глубокий разбор** (15 мин): любимое узкое место интервьюера: горячая партиция, retry, exactly-once, failover.

### Строительные блоки
- **Балансировщик нагрузки (load balancer)**: L4 (TCP) или L7 (HTTP, маршрутизация по пути). Алгоритмы: round-robin, наименьшее число соединений (least connections), консистентное хеширование (consistent hashing) для привязанной маршрутизации. Проверки здоровья (health checks) убирают плохие экземпляры. За ним [[api-gateway-and-service-discovery|API-шлюз]] выполняет аутентификацию и ограничение частоты.
- **Сервисы без состояния**: на машине нет сессии, поэтому любая реплика обрабатывает любой запрос, а масштабирование — это «добавить pod-ов» ([[kubernetes-basics]]). Состояние уходит в БД, кеш или токен ([[jwt-authentication]]).
- **Кеш** (Redis, [[redis-data-structures]]): *cache-aside* (приложение читает кеш, при промахе читает БД и пишет в кеш), *write-through* (пишем в кеш и БД вместе), *write-behind* (пишем в кеш, сбрасываем позже, рискованно). **TTL** ставить всегда; для данных, чувствительных к корректности, инвалидировать при записи. Проблемы: лавина промахов (cache stampede — много промахов одновременно → блокировка или объединение запросов), горячие ключи, устаревшие чтения. [[spring-cache-abstraction]] на стороне приложения, [[hibernate-caching]] внутри ORM.
- **CDN**: статика и кешируемые ответы отдаются с edge-узлов (PoP); заголовки `Cache-Control` определяют, что можно кешировать.
- **База данных**: один primary для записи, **реплики чтения (read replicas)** для чтения (асинхронная репликация → отставание реплики → проблемы с чтением своих записей). **Шардирование/партиционирование** — когда один узел не справляется с записью или объёмом данных: хеш-шардирование (равномерно, без range-сканов), шардирование по диапазонам (range-сканы, горячие диапазоны), справочник (directory). Цена — join-ы и транзакции между шардами. Postgres: сначала декларативное партиционирование, Citus/шардирование потом ([[postgres-indexes]], [[postgres-isolation-levels]]).
- **Очередь сообщений / лог** ([[kafka-architecture]], [[rabbitmq-basics]]): развязывает producer-ов и consumer-ов, поглощает всплески, даёт retry и рассылку (fan-out). В паре с [[outbox-pattern]] для атомарной публикации и с [[idempotency]] на стороне consumer-а, потому что доставка at-least-once.
- **Ограничение частоты запросов (rate limiting)**: token bucket (всплески допустимы), leaky bucket (ровный поток), счётчики фиксированного/скользящего окна. Счётчики храним в Redis; возвращаем `429` + `Retry-After`.
- **Устойчивость**: таймауты, retry с задержкой (backoff), [[circuit-breaker]], переборки (bulkheads); долгие многошаговые процессы — как [[saga]] или [[temporal-concepts|Temporal workflow]].
- **Наблюдаемость**: метрики, логи, трейсы ([[distributed-tracing]], [[logging-stacks]]).

### CAP и PACELC простыми словами
- Во время сетевого **разделения (partition)** распределённое хранилище должно выбрать: продолжать отвечать, возможно, устаревшими данными (**AP**), или отказывать/блокироваться, чтобы оставаться **согласованным** (**CP**). «CA» — это один узел.
- **PACELC** добавляет обычный случай: *else* (разделения нет) — выбор между **задержкой** и **согласованностью**. Синхронная репликация = согласованно, но медленнее; асинхронная = быстро, но с устаревшими данными. Postgres с синхронными репликами: PC/EC; Cassandra с настройкой кворума: PA/EL.
- Уровни согласованности: **строгая / линеаризуемая (linearizable)** (чтение видит последнюю запись), **последовательная (sequential)**, **причинная (causal)**, **чтение своих записей (read-your-writes)**, **монотонное чтение (monotonic reads)**, **в конечном счёте (eventual)** (сходится «когда-нибудь»). Выбирается под сценарий: баланс должен быть строгим; история уведомлений может быть согласована в конечном счёте.

### Числа, которые нужно знать
| Операция | Задержка |
|---|---|
| Кеш L1 / неверное предсказание ветвления | ~1 нс |
| Чтение из основной памяти | ~100 нс |
| Redis GET в том же ДЦ | ~0.2–0.5 мс |
| Случайное чтение с SSD | ~100 мкс; последовательное 1 GB/с+ |
| Точечное чтение по индексу в Postgres | ~1 мс |
| Round trip внутри ДЦ | ~0.5 мс |
| Round trip Бишкек ↔ Франкфурт | ~70–90 мс |
| Kafka produce (acks=all, 3 брокера) | ~2–10 мс |

- В сутках ~86 400 с ≈ 10⁵ с. 10 M запросов в день ≈ 115 QPS; 1 B в день ≈ 11 600 QPS. Пик ×3.
- Один primary Postgres на хорошем железе: тысячи простых записей/с, десятки тысяч чтений по индексу/с. Один брокер Kafka: десятки MB/с на набор партиций с комфортом.
- Хранилище: запись 1 KB × 10 M в день ≈ 10 GB в день ≈ 3.6 TB в год.

## Пример
«Спроектируйте сервис уведомлений» (push, SMS, email) для телеком-приложения: 5 M абонентов, 20 M уведомлений в день (пик 1 000/с), провайдеры на каждый канал с разными SLA, без дубликатов.

```yaml
# API
POST /v1/notifications
  Idempotency-Key: <uuid>            # дедупликация повторов клиента
  body: { userId, template, params, channels: [PUSH, SMS], priority }
  -> 202 { notificationId }
GET  /v1/notifications/{id}          # статус по каждому каналу

# Поток
api -> postgres (notification row + outbox) --relay--> kafka topic notifications.requested (key = userId)
router consumer: resolves user prefs/quiet hours -> fans out to notifications.push / .sms / .email
per-channel workers (separate consumer groups, own concurrency, own circuit breaker per provider)
  - provider call with timeout 3s, retry 3x exponential+jitter on 5xx/timeouts
  - on permanent failure or exhausted retries -> notifications.sms.dlq + status FAILED
  - delivery status written back (processed_events table keyed by notificationId+channel for idempotency)
  - providers' delivery receipts (webhooks) -> notifications.receipts -> status DELIVERED
redis: rate limit per user (no more than N SMS/hour), provider quota counters, template cache (TTL 10 min)
```

Почему так: Kafka с ключом `userId` сохраняет порядок уведомлений одного пользователя и позволяет worker-ам каналов масштабироваться независимо; outbox делает «строка сохранена» и «событие опубликовано» атомарными; `Idempotency-Key` плюс таблица `processed_events` гарантируют одну SMS на запрос, даже когда повторяет клиент API или consumer; DLQ не даёт «ядовитому» сообщению (poison message) заблокировать партицию; breaker на каждого провайдера не даёт сбою SMS повлиять на push.

## Подводные камни
- Рисовать блоки раньше QPS: «нам нужно шардирование» для 50 записей/с — классический провал. Один Postgres с репликами покрывает большинство задач размера собеседования.
- Забыть про режимы отказа: что, если очередь лежит, провайдер тормозит, consumer падает после отправки, но до commit (→ дубликат → идемпотентность).
- Кеш без TTL и стратегии инвалидации; отставание реплик игнорируется в сценариях «прочитать после записи».
- Заявлять сквозной «exactly-once» через внешнего SMS-провайдера; честно: at-least-once плюс дедупликация.
