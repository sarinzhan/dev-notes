## Кратко
Сокращатель ссылок — разминочная задача: крошечный путь записи (сохранить `code → long URL`) и огромный путь чтения (редирект). Интересные решения: как генерировать короткие, уникальные и неугадываемые коды без центрального узкого места, как сделать так, чтобы редирект попадал в кеш, а не в базу данных, и как считать клики, не добавляя запись в путь чтения. Числа стоит назвать сразу: чтений в 100 раз больше, чем записей (100:1), поэтому это задача про [[caching]] и [[cdn]] с изюминкой в генерации ключей.

## Основное

### Требования и оценки
- Функциональные: создать короткую ссылку (по желанию — свой псевдоним и срок действия), редирект, базовая аналитика (клики по дням), удаление.
- Нефункциональные: задержка редиректа < 50 мс на edge, доступность чтения 99.99%, коды не последовательные (без перебора), ссылки живут годами.
- Числа: 10 M новых ссылок в месяц ≈ 4 записи/с; 100:1 → 400 редиректов/с в среднем, 4 000/с в пике. Строка ≈ 200 B → 2 GB в месяц — пустяк. За пять лет: 600 M ссылок; 7-символьный код в base62 даёт 62⁷ ≈ 3.5 × 10¹² значений — достаточно.

### API
```
POST /v1/links            { url, alias?, expiresAt? }   -> 201 { code, shortUrl }
GET  /{code}              -> 302 Location: <url>  (301 if you want browsers to cache, see trade-offs)
GET  /v1/links/{code}     -> { url, createdAt, clicks }
DELETE /v1/links/{code}
```
- `POST` с `Idempotency-Key` или уникальным ограничением `(owner, url)`, чтобы повторное создание возвращало тот же код ([[idempotency]]).
- Проверять целевой адрес: белый список схем, никаких приватных диапазонов IP (SSRF через редирект), ограничение длины ([[owasp-top-10-for-backend]]).

### Модель данных
- `link(code text PK, url text, owner_id, created_at, expires_at, deleted boolean)`; индекс по `(owner_id, created_at)`.
- `click_daily(code, day, count)` или сырые `click(code, ts, referer, ua_hash)` с партиционированием по дням для аналитики ([[postgres-partitioning]]).
- Postgres хватает на 600 M строк; KV-хранилище (DynamoDB/Cassandra) — если нужна запись в нескольких регионах ([[storage-choices]]).

### Общая архитектура
```
browser ──GET /abc1234──▶ CDN / edge (cached 302 for hot codes)
                              │ miss
                              ▼
                      LB ──▶ redirect service (stateless) ──▶ Redis (code → url, TTL)
                                                                  │ miss
                                                                  ▼
                                                               Postgres (read replica)
                              │ async: click event ──▶ Kafka ──▶ analytics aggregator
create: API ──▶ key generator ──▶ Postgres primary ──▶ (warm Redis)
```

### Подробно: генерация ключей
| Способ | Как | Плюсы | Минусы |
|---|---|---|---|
| Хеш URL | base62(md5/sha256(url))[0:7] | тот же URL → тот же код, координатор не нужен | коллизии нужно проверять и разрешать; два пользователя, сократившие один URL, делят код и аналитику |
| Последовательность в БД + base62 | `nextval()` → кодирование | уникален по построению, плотный | последовательный = перебираемый; один primary для id |
| Заранее сгенерированный пул ключей | сервис генерации ключей (Key Generation Service) заполняет таблицу случайными неиспользованными кодами; API берёт один через `FOR UPDATE SKIP LOCKED` | случайный, нет проверки коллизий во время запроса, масштабируется горизонтально | ещё один сервис, ключи нужно атомарно помечать использованными |
| Случайный + повтор | сгенерировать 7 случайных символов base62, `INSERT ... ON CONFLICT DO NOTHING`, повторить при конфликте | проще всего, координатор не нужен | вероятность коллизии растёт со степенью заполнения (всё ещё крошечная при 600 M / 3.5 T) |
| Id в стиле Snowflake | время + узел + последовательность, затем base62 | уникален между узлами, примерно упорядочен | 11 символов, раскрывает время ([[time-money-and-ids]]) |

- Безопасный ответ на собеседовании: случайный 7-символьный base62 с повтором через `ON CONFLICT`; упомянуть пул ключей как масштабируемую версию, а последовательность — как вариант, которого стоит избегать для публичных ссылок.
- Пользовательские псевдонимы делят то же пространство имён: зарезервировать префикс или отдельную проверку уникальности; запретить зарезервированные слова (`api`, `admin`).

### Подробно: путь чтения
- Cache-aside в Redis с ключом по коду и долгим TTL; рабочий набор перекошен (несколько процентов ссылок собирают большинство кликов), поэтому доля попаданий выше 95% реалистична ([[caching]]).
- Негативное кеширование неизвестных кодов (короткий TTL) не даёт ботам сканировать базу данных; [[bloom-filters-and-probabilistic|фильтр Блума]] существующих кодов в каждом экземпляре делает то же самое дешевле.
- `302` или `301`: `301` позволяет браузерам и CDN кешировать редирект, что снижает нагрузку, но теряет подсчёт кликов и делает изменение URL «залипающим» в браузерах; `302` (или `307`) оставляет каждый клик видимым. По умолчанию `302`, `301` — для неизменяемых публичных ссылок с `Cache-Control` ([[http-caching]]).
- Подсчёт кликов по принципу «отправил и забыл»: публикуем `{code, ts, referer}` в Kafka, агрегируем по дням в consumer-е; никогда не делаем `UPDATE link SET clicks = clicks + 1` на горячем пути ([[async-processing-and-event-driven-scaling]]).

### Компромиссы
- Postgres или KV: Postgres выигрывает простотой, пользовательскими псевдонимами и списками по владельцу; KV выигрывает для multi-region active/active, где глобального ограничения уникальности нет ([[multi-region-basics]]).
- Истечение срока: лениво (проверять `expires_at` при чтении, вычищать ночной задачей) — достаточно; TTL на ключе в Redis повторяет это.
- Точность аналитики против стоимости: точные счётчики через Kafka и дневные агрегаты; приблизительное число уникальных посетителей — через HyperLogLog в Redis.

## Пример
Случайный код с повтором при конфликте и редирект через cache-aside:

```java
private static final String ALPHABET = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz";

public String create(String url) {
    for (int attempt = 0; attempt < 5; attempt++) {
        String code = randomCode(7);
        int inserted = jdbc.update("""
            INSERT INTO link (code, url, created_at) VALUES (?, ?, now())
            ON CONFLICT (code) DO NOTHING""", code, url);
        if (inserted == 1) return code;
    }
    throw new IllegalStateException("could not allocate a code");
}

public Optional<String> resolve(String code) {
    String cached = redis.opsForValue().get("l:" + code);
    if (cached != null) return cached.isEmpty() ? Optional.empty() : Optional.of(cached);
    Optional<String> url = jdbc.query("SELECT url FROM link WHERE code = ? AND NOT deleted AND (expires_at IS NULL OR expires_at > now())",
            rs -> rs.next() ? Optional.of(rs.getString(1)) : Optional.empty(), code);
    redis.opsForValue().set("l:" + code, url.orElse(""), url.isPresent() ? Duration.ofDays(7) : Duration.ofMinutes(5));
    return url;
}
```

`randomCode` берёт символы из `ALPHABET` через `SecureRandom`; значение «пустая строка» — маркер негативного кеша.

## Подводные камни
- На собеседовании спрашивают: «почему не md5?» — коллизии и общие коды; «почему не автоинкремент?» — перебор и единственный источник id; «а если Redis умрёт?» — база данных всё равно отвечает, а всплеск при холодном кеше гасится объединением запросов (request coalescing) ([[distributed-cache-coherence]]).
- «Как удалить ссылку, закешированную в CDN и в браузерах?» `301` отозвать нельзя; поэтому по умолчанию `302`, а TTL кеша на edge короткий.
- Злоупотребление открытым редиректом: сокращатели — инструмент фишинга; проверять целевые адреса, добавить проверку safe-browsing, дать возможность пожаловаться.
- Синхронный подсчёт кликов превращает нагрузку 4 000 чтений/с в 4 000 записей/с на primary.
- Связанные заметки: [[system-design-basics]], [[load-balancing]], [[hash-tables]] — почему 7 случайных символов достаточно.
