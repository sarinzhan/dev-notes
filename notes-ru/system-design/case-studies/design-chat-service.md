## Кратко
Чат-сервис держит открытыми миллионы долгоживущих соединений, за несколько сотен миллисекунд доставляет сообщение от отправителя на каждое онлайн-устройство каждого получателя, надёжно сохраняет его для тех, кто офлайн, и показывает всем один и тот же порядок сообщений. Архитектура: парк WebSocket-шлюзов (gateway), по возможности без состояния; реестр сессий, который знает, к какому шлюзу подключён каждый пользователь; сервис сообщений, который сначала сохраняет и только потом рассылает (fan-out); слой pub/sub или Kafka между шлюзами; и wide-column или партиционированное хранилище с ключом по беседе. Самое сложное — порядок и состояние доставки между устройствами и при переподключениях. Варианты транспорта — в [[websockets-sse-and-long-polling]]; push для офлайн-пользователей — в [[notifications-and-push]].

## Основное

### Требования и оценки
- Функциональные: личные и групповые чаты (до 500 участников), текст и медиа, отметки о доставке и прочтении (receipts), присутствие (онлайн / был в сети), история с пагинацией, несколько устройств.
- Нефункциональные: сквозная задержка < 300 мс для онлайн-пользователей, ни одного потерянного сообщения, согласованный порядок внутри беседы, доступность 99.95%.
- Числа: 10 M DAU, 40 сообщений на пользователя в день → 400 M/день ≈ 4 600/с в среднем, 15 000/с в пике. Сообщение ≈ 300 B → 120 GB/день текста; медиа — в объектном хранилище ([[file-and-blob-storage]]). Одновременных соединений: 2 M; при ~50 k соединений на узел шлюза (ограничение по памяти, простаивающие сокеты дёшевы с NIO/виртуальными потоками) нужно 40–60 шлюзов.

### API
```
WebSocket wss://chat.example.com/ws   (auth via JWT in the first frame or a short-lived ticket)
  client → server:  { type: SEND, clientMsgId, conversationId, body }
  server → client:  { type: ACK, clientMsgId, messageId, seq }
                    { type: MESSAGE, conversationId, messageId, seq, senderId, body, sentAt }
                    { type: RECEIPT, conversationId, messageId, userId, state: DELIVERED|READ }
REST:
  GET  /v1/conversations/{id}/messages?beforeSeq=&limit=50
  POST /v1/conversations            { memberIds }
  POST /v1/media/upload-url         -> presigned URL
```
- `clientMsgId` — ключ идемпотентности для повторов после переподключения ([[idempotency]]).

### Модель данных
- `message(conversation_id, seq, message_id, sender_id, body, sent_at)` — ключ партиции `conversation_id`, кластеризация по `seq` по убыванию; Cassandra/ScyllaDB подходят под такой паттерн «много записей, читаем свежее»; Postgres, партиционированный по хешу беседы, справляется до десятков тысяч записей в секунду ([[column-and-wide-column-stores]], [[storage-choices]]).
- `conversation(id, type, created_at)`, `membership(user_id, conversation_id, last_read_seq)` — запросы идут в обе стороны, поэтому храним дважды или индексируем по обоим полям.
- `session(user_id, device_id, gateway_id, connected_at)` в Redis с TTL, который обновляется heartbeat-ами ([[redis-data-structures]]).
- `presence(user_id) → last_seen` в Redis.

### Общая архитектура
```
mobile/web ──WebSocket──▶ LB (L4, sticky by connection) ──▶ gateway nodes (N)
                                                                 │ register session in Redis
                                                                 ▼
                                                      message service ──▶ message store (by conversation)
                                                                 │ assign seq, persist, ack sender
                                                                 ▼
                                   fan-out: for each member → lookup gateway in session registry
                                            online  → publish to gateway's channel (Redis pub/sub or Kafka topic per gateway)
                                            offline → push notification + unread counter
```

### Подробно: порядок и состояние доставки
- **Последовательность на беседу**: сервис сообщений в момент сохранения присваивает монотонно растущий `seq` в пределах беседы (Redis `INCR conv:{id}:seq` или счётчик в строке через `UPDATE ... RETURNING`). Клиенты сортируют по `seq`, а не по клиентским временным меткам, которые расходятся из-за часов устройств ([[time-and-clocks]]). В групповых чатах все отправки одной беседы идут через одну партицию (ключ Kafka = `conversationId`), поэтому присвоение сериализовано ([[kafka-architecture]]).
- **Сохранить до рассылки**: отправитель получает `ACK` только после подтверждения от хранилища; сбой рассылки тогда означает retry, а не потерю ([[async-processing-and-event-driven-scaling]]).
- **Обнаружение пропусков на клиенте**: каждое устройство помнит последний `seq` по каждой беседе; при переподключении запрашивает `?afterSeq=` и сливает результат. Сообщения через сокет могут потеряться во время переподключения, поэтому сокет — это оптимизация, а источник истины — хранилище.
- **Отметки (receipts)**: DELIVERED ставится, когда устройство получателя подтверждает фрейм; READ — по явному событию. Храним `last_delivered_seq` / `last_read_seq` на участника, а не на сообщение: O(участников), и «прочитано до seq 120» сжимает сотни событий. Отметки рассылаем только отправителю и с ограничением частоты (одна в секунду на беседу).
- **Несколько устройств**: рассылка идёт на все сессии пользователя; другие устройства отправителя тоже получают сообщение.
- **Отказ шлюза**: LB держит привязку (sticky) только в рамках соединения; когда шлюз падает, клиенты переподключаются к любому другому узлу, заново регистрируются и догоняют по `seq`. Сессии в Redis истекают по TTL ([[leases-heartbeats-and-health]]).
- **Присутствие**: heartbeat каждые 30 с обновляет `last_seen`; «онлайн» = был виден в течение 60 с. Рассылка статусов присутствия — самая большая скрытая нагрузка (каждое изменение статуса каждому контакту): её группируют в пачки и отправляют только контактам с открытым экраном беседы.

### Компромиссы
| Решение | Выбрано | Альтернатива | Почему |
|---|---|---|---|
| Транспорт | WebSocket | long polling / SSE | двунаправленный, одно соединение на устройство; SSE — для лент только на чтение |
| Шина между шлюзами | Redis pub/sub на шлюз | Kafka на шлюз | pub/sub работает по принципу «отправил и забыл» и быстр; надёжность уже гарантирует хранилище |
| Источник последовательности | счётчик на беседу | глобальный Snowflake id | пользователи видят строгий порядок в беседе; глобальный порядок не нужен |
| Хранилище | wide-column по беседе | Postgres | объём записи и паттерн «последние N по беседе»; Postgres подходит ниже ~10 k записей/с |
| Рассылка в группы | при записи (на каждого участника) | при чтении | группы ≤ 500 держат усиление записи (write amplification) в рамках; каналы со 100 k участников переходят на рассылку при чтении ([[design-news-feed]]) |

## Пример
Сохранение с последовательностью на беседу и подтверждение отправителю, идемпотентно по `clientMsgId`:

```java
@Transactional
public Ack send(SendCommand cmd) {
    Optional<Message> dup = messages.findByClientMsgId(cmd.senderId(), cmd.clientMsgId());
    if (dup.isPresent()) return Ack.of(dup.get());                     // повтор после переподключения

    long seq = jdbc.queryForObject("""
        UPDATE conversation SET last_seq = last_seq + 1
        WHERE id = ? RETURNING last_seq""", Long.class, cmd.conversationId());  // блокировка строки сериализует писателей

    Message m = Message.create(cmd, seq);
    messages.save(m);
    outbox.publish(new MessageStored(m.conversationId(), m.id(), seq));  // рассылка после commit
    return Ack.of(m);
}
```

Consumer рассылки читает `MessageStored`, находит в Redis сессии каждого участника и публикует фрейм в каналы шлюзов; участники без сессий получают push-уведомление.

## Подводные камни
- На собеседовании спрашивают: «двое пишут в группу одновременно — кто первый?» Тот, кто первым получил номер последовательности; решает хранилище, а не шлюз. «А если шлюз упал после ACK?» Сообщение сохранено; получатели догонят по `seq`.
- Рассылка до сохранения: при падении сообщение теряется, хотя часть получателей уже его видела.
- Строки отметок на каждое сообщение раздувают хранилище и трафик; вместо них — водяные знаки (watermarks) на участника.
- Обновления присутствия, рассылаемые всем контактам на каждый heartbeat, съедают больше трафика, чем сами сообщения.
- Связанные заметки: [[load-balancing]] — про sticky L4 и плавное отключение соединений (connection draining), [[design-notification-service]] — про офлайн-путь, [[consistency-models]] — почему «одинаковый порядок для всех» — это последовательная согласованность (sequential consistency) в пределах беседы.
