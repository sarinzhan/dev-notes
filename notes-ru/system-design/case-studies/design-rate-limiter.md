## Кратко
Ограничитель частоты запросов (rate limiter) для каждого запроса решает, превысил ли клиент свою квоту (например, 100 запросов в минуту на API-ключ), и отвечает гораздо быстрее миллисекунды, согласованно на всех репликах сервиса. Архитектура: общее хранилище счётчиков (Redis) с атомарной проверкой и инкрементом (Lua-скрипт), алгоритм, выбранный под нужное поведение при всплесках, и слой middleware на шлюзе или в каждом сервисе, который возвращает `429` с `Retry-After`. Самое сложное — сделать это атомарно, экономно по памяти и решить, что происходит, когда хранилище счётчиков недоступно. Сами алгоритмы (token bucket, leaky bucket, фиксированное/скользящее окно) описаны в [[rate-limiting]]; эта заметка — про систему вокруг них.

## Основное

### Требования и оценки
- Функциональные: ограничение по API-ключу, id пользователя или IP; несколько правил на маршрут (в секунду и в день); оставшаяся квота в заголовках; правила меняются без повторного deploy.
- Нефункциональные: задержка решения < 1 мс p99 сверху к запросу; корректность на N репликах (никаких лимитов на отдельный pod); явно заявленная политика fail-open или fail-closed; память ограничена числом активных клиентов.
- Числа: 10 000 запросов/с на весь парк, 200 k разных клиентов в час. Журнал скользящего окна (sliding window log) хранит по записи на запрос: 100 запросов/мин × 200 k клиентов ≈ 20 M записей — слишком много; счётчик скользящего окна (sliding window counter) хранит два целых на пару клиент–окно ≈ несколько MB. Redis выполняет 100 k+ простых операций/с на одном узле, так что хватит одного экземпляра; кластер — ради доступности.

### API
```
# применяется как middleware, клиенты его не вызывают; ответы содержат:
HTTP 429 Too Many Requests
Retry-After: 12
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1730000012

# плоскость управления (control plane)
PUT /v1/limits/{ruleId}   { key: "api_key", route: "/v1/sms/**", limit: 100, window: "1m", burst: 20 }
```

### Модель данных
- Redis: один ключ на `(rule, client, window)`: `rl:sms:key123:1730000000` → счётчик, с TTL = 2 × окно. Token bucket хранит `(tokens, lastRefillMs)` в hash.
- Правила — в Postgres, рассылаются в каждый сервис через обновление конфигурации или pub/sub; кешируются в памяти и перезагружаются каждые 30 с ([[caching]]).
- Память: ключи истекают по TTL, поэтому объём пропорционален активным клиентам, а не всем клиентам ([[redis-data-structures]]).

### Общая архитектура
```
client ──▶ API gateway / each service pod
               │ middleware: identify client (API key, JWT sub, IP)
               │ match rules for route
               ▼
         Redis (Lua: check + increment atomically) ──▶ allow / deny + remaining
               │
         rules cache ◀── control plane (Postgres) ── admin API
```
- Где работает: на [[api-gateway-and-service-discovery|шлюзе]] — для грубых глобальных лимитов (дёшево, в одном месте), внутри сервисов — для бизнес-лимитов («не больше 5 SMS в час на абонента»), которым нужен доменный контекст ([[load-balancing]] здесь не помогает: каждая реплика должна видеть один и тот же счётчик).

### Подробно: атомарный счётчик скользящего окна в Redis
- Фиксированное окно (`INCR` + `EXPIRE`) пропускает 2× лимит на границе окна. Журнал скользящего окна (`ZADD` + `ZREMRANGEBYSCORE` + `ZCARD`) точен, но требует O(лимит) памяти на клиента. **Счётчик скользящего окна** даёт приближение: `count = current_window + previous_window × (1 − elapsed_fraction)`; два целых, погрешность в пределах нескольких процентов — обычный выбор в продакшене.
- Атомарность: `GET`/сравнение/`INCR` из приложения создают гонку между репликами; Lua-скрипт выполняется на сервере как единое целое. `MULTI/EXEC` недостаточно, потому что решение зависит от прочитанного значения.
- Часы: используй Redis `TIME` внутри скрипта или передавай время приложения; разные часы на разных pod-ах сдвигают окна ([[time-and-clocks]]).
- Token bucket на Lua: прочитать `tokens` и `ts`, добавить `rate × (now − ts)` с ограничением сверху `burst`, если `tokens ≥ 1` — вычесть и пропустить, сохранить оба значения; один round trip, допускает всплески до `burst`, а затем ровный `rate`.
- Политика при сбое: Redis недоступен → **fail-open** для обычных API (доступность важнее строгости, логируем и алертим), **fail-closed** для дорогих или уязвимых к злоупотреблениям эндпоинтов (SMS, OTP, логин). Добавь крошечный запасной ограничитель в памяти каждого pod-а, чтобы fail-open не означал «без ограничений».
- Горячие клиенты: один ключ на клиента, поэтому трафик одного клиента попадает на один шард Redis; это нормально, потому что один клиент всё равно не может превысить возможности одного узла. Для глобальных лимитов на весь парк счётчик шардируют (`key:{0..9}`) и суммируют или мирятся с небольшим перебором.

### Компромиссы
| Вариант | Когда выбирать | Цена |
|---|---|---|
| Token bucket | API, где короткие всплески допустимы (мобильное приложение просыпается) | два поля на ключ, чуть больше логики в скрипте |
| Счётчик скользящего окна | строгие SLA «N в минуту» с провайдерами | приближение на границе |
| Журнал скользящего окна | точный аудит каждого запроса (биллинг) | память O(лимит) на клиента |
| Только локально в памяти | один экземпляр или защитные лимиты на pod | не общий, лимит умножается на число pod-ов |
| Шлюз или сервис | глобальная защита или бизнес-правила | шлюз не видит доменных ключей |

## Пример
Счётчик скользящего окна в виде Lua-скрипта, вызываемого через `EVALSHA` из Spring Data Redis:

```lua
-- KEYS[1] = префикс (rl:sms:key123), ARGV[1] = лимит, ARGV[2] = window_ms, ARGV[3] = now_ms
local limit, win, now = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
local cur_win  = math.floor(now / win)
local cur_key  = KEYS[1] .. ':' .. cur_win
local prev_key = KEYS[1] .. ':' .. (cur_win - 1)
local cur  = tonumber(redis.call('GET', cur_key) or '0')
local prev = tonumber(redis.call('GET', prev_key) or '0')
local elapsed = (now % win) / win
local estimate = prev * (1 - elapsed) + cur
if estimate + 1 > limit then
  local retry_ms = math.floor(win - (now % win))
  return {0, 0, retry_ms}                      -- отказ, остаток, повторить через
end
redis.call('INCR', cur_key)
redis.call('PEXPIRE', cur_key, win * 2)
return {1, math.floor(limit - estimate - 1), 0}
```

```java
Long[] r = (Long[]) redis.execute(script, List.of("rl:sms:" + apiKey), "100", "60000", String.valueOf(clock.millis()));
if (r[0] == 0) throw new TooManyRequestsException(Duration.ofMillis(r[2]));
response.setHeader("X-RateLimit-Remaining", r[1].toString());
```

## Подводные камни
- На собеседовании спрашивают: «две реплики проверяют одновременно — могут пройти обе?» Нет, если скрипт на стороне сервера; да, если из приложения `GET`, а потом `INCR`.
- «Redis упал» — назови политику и локальный запасной вариант; «без ограничений» и «всем 429» — оба неправильные ответы.
- «Откуда берётся всплеск 2× на границах окна?» Из фиксированных окон; покажи формулу скользящего счётчика.
- Ограничение по IP за прокси ограничивает сам прокси; `X-Forwarded-For` можно доверять только от известных узлов ([[reverse-proxy-nginx-basics]]).
