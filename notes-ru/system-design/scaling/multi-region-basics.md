## Кратко
Второй регион даёт две вещи: переживание отказа целого дата-центра и меньшую задержку для пользователей, далёких от первого региона. **Active/passive** держит тёплую копию и переключается на неё при сбое; это просто, а проблема данных сводится к «односторонней репликации плюс несколько секунд возможной потери». **Active/active** принимает запись в нескольких регионах; везде быстро, но каждый конфликт записи, каждая проверка уникальности и каждый вопрос «какое значение последнее» превращается в задачу распределённых систем. Большинству компаний, включая телеком-операторов, обслуживающих одну страну, нужен active/passive плюс CDN, а не active/active. Регулирование (резидентность данных) может навязать выбор раньше, чем задержка.

## Основное

### Зачем вообще несколько регионов
- **Доступность**: отказы AZ обрабатываются внутри региона; на случай сбоя всего региона (питание, сеть, плоскость управления облака) нужен второй регион. Измеряется через RTO (время восстановления) и RPO (данные, которые можно потерять).
- **Задержка**: round trip между континентами — 100–300 мс ([[latency-numbers]]); страница с тремя последовательными вызовами в далёкий регион ощущается сломанной. Статика сначала уходит в [[cdn]]; региональные вычисления нужны только для динамических, персонализированных данных.
- **Резидентность**: GDPR, местные правила для телекома или банков могут требовать, чтобы данные абонентов оставались в стране. Тогда разделение на регионы следует закону, а не карте трафика.

### Топологии
| | Active/passive | Active/active (с разделением) | Active/active (общие данные) |
|---|---|---|---|
| Запись | один регион | каждый регион владеет подмножеством пользователей/арендаторов | любой регион, любая строка |
| Данные | асинхронная репликация primary → standby | primary на каждую партицию, перекрёстная репликация для DR | multi-leader или консенсус между регионами |
| Переключение | смена DNS/LB + повышение standby, минуты | перенаправить партицию, минуты | автоматически, секунды |
| Конфликты | нет | нет (запись разделена) | есть: LWW, CRDT или слияние в приложении |
| Задержка записи | далёкие пользователи платят за round trip | локальная | локальная или +1 RTT при синхронном консенсусе |
| Сложность | низкая | средняя | высокая |

- Active/active с разделением («домашний регион» для каждого пользователя, как у телеком-оператора с одной страной на регион) даёт большую часть выгоды без всякой обработки конфликтов; это шардирование на уровне регионов ([[sharding-strategies]]).
- Active/active с общими данными требует репликации [[multi-leader-and-leaderless]] или глобально согласованного хранилища (Spanner, CockroachDB, YugabyteDB), которое платит межрегиональным round trip за каждый commit ([[raft-explained]], [[quorums-and-leader-election]]).

### Всё решает слой данных
- Postgres между регионами: асинхронная потоковая репликация на standby в регионе B ([[postgres-replication-and-failover]]). RPO = отставание репликации в момент сбоя (обычно меньше секунды, больше при всплесках). Синхронная репликация между регионами заставляет каждый commit ждать далёкий регион: при 10 мс — нормально, при 100 мс — больно.
- Kafka: топики реплицируют MirrorMaker 2 или cluster linking; offset-ы в каждом кластере свои, поэтому consumer-ы должны уметь продолжать по временной метке или через идемпотентную повторную обработку ([[idempotency]]).
- Redis: межрегиональные кеши обычно независимы в каждом регионе; кеш — это кеш и никогда не источник истины ([[caching]]).
- Объектное хранилище реплицируется асинхронно из bucket-а в bucket ([[file-and-blob-storage]]).

### Управление трафиком
- Глобальная балансировка на уровне DNS (записи по задержке или геолокации, с проверками здоровья, низким TTL) или anycast ([[load-balancing]], [[dns-resolution]]). Из-за TTL в DNS и клиентских кешей переключение становится видно всем только через минуты; standby нужно проектировать так, чтобы он спокойно принимал ранний трафик.
- Регион должен быть самодостаточным: запрос, попавший в регион B, не должен на горячем пути вызывать сервисы в регионе A, иначе выигрыш в задержке исчезает, а домены отказа сливаются.

### Механика переключения (active/passive)
1. Обнаружить: проверки здоровья снаружи обоих регионов, а не изнутри падающего ([[failure-modes-and-timeouts]], [[leases-heartbeats-and-health]]).
2. Оградить (fence): убедиться, что старый primary не может принимать запись (остановить его, отозвать учётные данные или использовать fencing token), чтобы избежать split brain ([[distributed-locks-and-fencing]]).
3. Повысить standby, перенаправить приложение (обнаружение по роли, а не по именам хостов).
4. Переключить трафик (DNS/LB), затем воспроизвести или сверить всё, что было в процессе.
5. Отрепетировать: непроверенное переключение — это план, а не возможность. Учения (game days) раз в квартал.

### Ракурсы на собеседовании
- «Active/active или active/passive?» Пользователи в одной стране с правилами хранения данных внутри страны: active/passive на второй площадке в той же стране; глобальные пользователи с записью на пользователя: active/active с разделением.
- «Домашний регион пользователя лежит, а он пишет?» Отклонить для этой партиции (CP) или принять в DR-регионе и сверить позже (AP); скажи, что выбираешь и почему ([[cap-and-pacelc]], [[consistency-models]]).
- «Какие RPO/RTO можешь обещать?» RPO = отставание репликации, RTO = обнаружение + повышение + распространение DNS: секунды / 5–15 минут.

## Пример
Postgres в двух регионах со standby внутри страны: асинхронно ради пропускной способности, но с алертами на отставание; приложение находит primary по роли через Patroni/HAProxy, а не по хосту:

```yaml
# primary в регионе A
postgresql.conf:
  wal_level: replica
  max_wal_senders: 10
  synchronous_commit: "on"            # локальная надёжность; standby асинхронный
  synchronous_standby_names: ""      # без синхронного ожидания другого региона

# standby в регионе B (потоковая репликация из replication slot)
primary_conninfo: "host=pg-a.internal port=5432 user=replicator application_name=standby_b"
primary_slot_name: "standby_b"

# алерт: отставание больше 30 с или slot неактивен → вызов дежурного, потому что RPO уже не «секунды»
# promql (postgres_exporter)
# pg_replication_lag_seconds{application_name="standby_b"} > 30
# pg_replication_slots_active{slot_name="standby_b"} == 0
```

JDBC URL приложения перечисляет оба эндпоинта HAProxy с `targetServerType=primary`, поэтому после повышения оно переподключается к тому узлу, который объявляет себя primary, без изменения конфигурации.

## Подводные камни
- Синхронная репликация между регионами «ради нулевого RPO» без измерения задержки записи, которую она добавляет каждой транзакции.
- Переключение, которое повышает standby, пока старый primary ещё обслуживает запись: два primary, разошедшиеся данные и мучительное ручное слияние.
- Сервисы в регионе B, которые всё ещё смотрят на Redis, Kafka или config server в регионе A; сбой роняет оба региона.
- Считать резидентность обеспеченной размещением в регионе, хотя резервные копии, логи с MSISDN или стек наблюдаемости отправляют данные куда-то ещё ([[observability-three-pillars]]).
- Связанные заметки: [[horizontal-vs-vertical-scaling]], [[leader-follower-replication]], [[time-and-clocks]] — почему «последняя запись» неоднозначна между регионами.
