## Кратко
Большинство сервисов нагружены в основном чтением (от 10:1 до 100:1), поэтому самый дешёвый шаг масштабирования — отправлять чтения куда-то кроме primary: на реплику, в кеш или в специально построенную модель чтения. «Облегчённый CQRS (CQRS-lite)» означает раздельные **пути кода** для чтения и записи (запросы возвращают DTO прямо из SQL или проекции, команды проходят через доменную модель) без полной архитектуры на event sourcing. Цена всегда одна: сторона чтения может отставать, поэтому каждый сценарий «прочитать после записи» нужно выявить и направить к свежему источнику. Полный CQRS с раздельными хранилищами описан в [[cqrs]].

## Основное

### Три уровня разделения
| Уровень | Источник чтения | Источник записи | Устаревание | Когда |
|---|---|---|---|---|
| Уровень кода | та же БД, другой путь кода (JDBC-проекции) | доменная модель + JPA | нет | всегда стоит делать; дёшево |
| Уровень реплик | потоковая реплика Postgres | primary | отставание репликации (мс–с) | пропускная способность чтения превышает один узел |
| Уровень моделей | денормализованная модель чтения (таблица, Redis, Elasticsearch) | primary, события через outbox | отставание асинхронной проекции | чтениям нужна другая форма или хранилище |

### Уровень кода: отдельный путь запросов
- Команды загружают агрегаты, проверяют инварианты, сохраняют ([[aggregates-and-invariants]]). Запросам не нужны сущности: проекция `JdbcClient`/`JdbcTemplate` в record обходит persistence context, ленивую загрузку и N+1 ([[jpa-n-plus-one]], [[jpa-persistence-context-and-entity-lifecycle]]).
- DTO для чтения имеют форму экрана (одна строка на элемент списка с присоединёнными колонками), а не домена.
- `@Transactional(readOnly = true)` на стороне запросов позволяет Hibernate пропустить проверку изменений (dirty checking), а маршрутизирующему data source — выбрать реплику.

### Уровень реплик: маршрутизация чтений
- Варианты маршрутизации: в приложении (`AbstractRoutingDataSource`, см. [[database-scaling-path]]), в драйвере (`targetServerType=preferSecondary` в URL PgJDBC с несколькими хостами) или через прокси (пары PgBouncer, pgpool, HAProxy с проверками здоровья).
- Оговорки по согласованности:
  - **Чтение своих записей (read-your-writes)**: после `POST /orders` клиент вызывает `GET /orders/{id}` и получает 404 от отстающей реплики. Исправления: в течение N секунд после записи этого пользователя направлять его чтения на primary (привязка по сессии), или ждать, пока реплика пройдёт LSN записи (`pg_last_wal_replay_lsn() >= <lsn>`), или возвращать созданный ресурс в ответе на POST, чтобы немедленный GET не был нужен.
  - **Монотонное чтение (monotonic reads)**: два последовательных чтения с двух реплик с разным отставанием могут показать, как значение исчезает. Привязать сессию к одной реплике.
  - Оба случая — частные проявления [[consistency-models]]; эксплуатационная сторона (мониторинг отставания, переключение) — в [[read-replicas-and-stale-reads]] и [[postgres-replication-and-failover]].

### Уровень моделей: проекции
- Сторона записи испускает события через [[outbox-pattern]]; проектор потребляет их и поддерживает таблицу чтения (`order_summary`), hash в Redis или документ в Elasticsearch ([[search-and-indexing-services]]).
- Проекции — это идемпотентные upsert-ы с ключом по id агрегата и версии события, поэтому повторная доставка из Kafka безвредна ([[idempotency]]).
- Пересборка — это функция: очистить проекцию и проиграть топик заново (или пересканировать исходную таблицу). Закладывать это нужно с первого дня.
- Здесь заканчивается облегчённый CQRS и начинаются [[cqrs]] / [[event-sourcing]]: как только сама модель записи хранится в виде событий, replay и проекции становятся основным механизмом.

### Как выбирать
- Начинать с уровня кода; он ничего не стоит и убирает большую часть медлительности, вызванной ORM.
- Переходить на уровень реплик, когда CPU или ввод-вывод primary занят в основном `SELECT`-ами, а пути «прочитать после записи» известны и их немного.
- Переходить на уровень моделей, когда форма чтения сильно отличается (поиск, ленты, дашборды) или когда чтения должны переживать медленный primary.

### Ракурсы на собеседовании
- «Как избежать устаревших чтений после записи?» Primary для того же пользователя на несколько секунд, ожидание LSN или возврат полного ресурса из вызова записи.
- «Это CQRS?» Раздельные пути — да, раздельные модели — по желанию, event sourcing — нет. Скажи это явно; интервьюерам нравится это различие.
- «Как держать проекцию в синхронизации?» Outbox → Kafka → идемпотентный upsert; мониторить отставание каждого проектора; пересобирать через replay.

## Пример
Проекция истории заказов, питаемая из Kafka и идемпотентная благодаря колонке версии:

```sql
CREATE TABLE order_summary (
    order_id     uuid PRIMARY KEY,
    msisdn       text NOT NULL,
    status       text NOT NULL,
    iccid        text,
    updated_at   timestamptz NOT NULL,
    version      bigint NOT NULL          -- порядковый номер события внутри агрегата
);
CREATE INDEX order_summary_msisdn_idx ON order_summary (msisdn, updated_at DESC);

-- upsert проектора: игнорировать события не по порядку и дубликаты
INSERT INTO order_summary (order_id, msisdn, status, iccid, updated_at, version)
VALUES (:orderId, :msisdn, :status, :iccid, :occurredAt, :version)
ON CONFLICT (order_id) DO UPDATE
SET status = EXCLUDED.status,
    iccid = COALESCE(EXCLUDED.iccid, order_summary.iccid),
    updated_at = EXCLUDED.updated_at,
    version = EXCLUDED.version
WHERE order_summary.version < EXCLUDED.version;
```

Условие `WHERE version <` делает upsert безопасным при доставке at-least-once и rebalance партиций; сторона запросов читает `order_summary` одним сканированием индекса вместо join-а заказов, профилей и SIM.

## Подводные камни
- Направлять каждый `GET` на реплики, не перечислив экраны «прочитать после записи»; в баг-репортах пишут «мой заказ на секунду исчез».
- Реплика используется для чтения внутри транзакции записи: чтение устарело, а запись на нём основана. Чтения, от которых зависят решения, оставляй на primary ([[transactions-acid-and-isolation]]).
- Проекция без проверки версии или id события: повторная доставка откатывает статус назад.
- Забыть, что реплику могут повысить при переключении; пул «только для чтения» нужно перенаправить или использовать маршрутизацию по роли (а не по хосту).
- Связанные заметки: [[caching]] — другой путь разгрузки чтения, [[event-driven-architecture]] — сторона интеграции.
