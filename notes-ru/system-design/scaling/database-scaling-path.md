## Кратко
Реляционную базу данных масштабируют в фиксированном порядке и останавливаются на первом сработавшем шаге: исправить запросы и индексы, нарастить машину, добавить реплики чтения, поставить кеш перед базой, партиционировать большие таблицы и только потом шардировать запись по узлам. Каждый шаг примерно в десять раз дешевле следующего по инженерным усилиям, и каждый более поздний шаг добавляет постоянную эксплуатационную цену (отставание, инвалидация, запросы между шардами). На собеседовании сказать «шардировать» при 500 записях/с — классическая ошибка; один хорошо настроенный primary Postgres обслуживает большинство задач вплоть до десятков тысяч QPS.

## Основное

### Лестница
| Шаг | Решает | Цена | Прирост мощности |
|---|---|---|---|
| 1. Запросы и индексы | медленные чтения, конкуренция за блокировки | время разработчиков | 10–1000× на плохих запросах |
| 2. Вертикальное масштабирование | CPU, RAM под буферный кеш, IOPS | деньги, перезапуск | до самого большого инстанса |
| 3. Пул соединений (PgBouncer) | слишком много соединений, переключения контекста | ещё один компонент | стабильная пропускная способность при множестве клиентов |
| 4. Реплики чтения | пропускная способность чтения, изоляция отчётов | отставание репликации, устаревшие чтения | чтения масштабируются линейно |
| 5. Кеширование | повторные чтения горячих данных | инвалидация, память | 10–100× для горячих ключей |
| 6. Партиционирование | огромные таблицы, сроки хранения, время vacuum | ограничения планировщика | управляемость, а не сырая пропускная способность |
| 7. Шардирование | пропускная способность записи, данные больше одного узла | join-ы/транзакции между шардами, перебалансировка | линейно по числу шардов |

### Шаг 1: сначала посмотреть на запросы
- `pg_stat_statements` ранжирует запросы по суммарному времени; три верхних обычно дают большую часть нагрузки. Исправить N+1 из ORM ([[jpa-n-plus-one]]), добавить составные и частичные индексы ([[postgres-indexes]], [[database-indexes]]), читать планы через [[explain-analyze]].
- Избыток индексов — тоже проблема масштабирования: каждый индекс замедляет запись и раздувает работу vacuum ([[postgres-vacuum-and-bloat]]).
- Таймауты на выражения и блокировки не дают одному плохому запросу уронить primary ([[postgres-performance-checklist]], [[postgres-locks]]).

### Шаги 2–3: машина побольше и пулер
- Postgres работает по модели «процесс на соединение»; тысячи простаивающих соединений тратят RAM и CPU. PgBouncer в режиме транзакций мультиплексирует множество соединений приложения на несколько десятков серверных ([[hikaricp-pool-sizing]], [[sockets-and-connection-pooling]]).
- Буферный кеш такого размера, чтобы рабочий набор помещался в RAM, превращает случайные чтения с диска в чтения из памяти; часто это и есть вся история «масштабирования».

### Шаг 4: реплики чтения
- Потоковая репликация (streaming replication) передаёт WAL на реплики ([[postgres-replication-and-failover]]); чтения направляются на реплики, запись — на primary ([[read-write-splitting-and-cqrs-lite]]).
- Цена — отставание. Сценарии «прочитать после записи» («создать заказ, перейти на страницу заказа») должны читать с primary или ждать, пока реплика дойдёт до LSN записи ([[read-replicas-and-stale-reads]], [[leader-follower-replication]]).
- Реплики не помогают нагрузкам с преобладанием записи: каждая запись всё равно применяется на каждой реплике.

### Шаг 5: кеш
- Cache-aside с Redis перед самыми горячими чтениями; стратегии, TTL и защита от лавины промахов — в [[caching]]. Кеш скрывает нагрузку чтения, но делает корректность твоей проблемой.

### Шаг 6: партиционирование (один узел)
- Декларативное партиционирование делит одну логическую таблицу на дочерние по диапазону (время), списку (регион) или хешу ([[postgres-partitioning]]). Плюсы: отсечение партиций (partition pruning) по ключу, удаление старых данных через `DETACH`, меньшие индексы и более быстрый vacuum на каждую партицию.
- Это по-прежнему один узел и один primary; партиционирование даёт управляемость больших таблиц, а не мощность записи.

### Шаг 7: шардирование (много узлов)
- Каждый шард владеет непересекающимся подмножеством строк, выбранным по ключу шардирования (id арендатора, id пользователя). Стратегии и работа с горячими партициями: [[sharding-strategies]], [[consistent-hashing]].
- Цена, которая никуда не уходит: запросы и транзакции между шардами ([[cross-shard-queries-and-transactions]]), уникальные ограничения только в пределах шарда, перешардирование, когда шард заполнился, и слой маршрутизации (Citus, прокси в стиле Vitess или само приложение).
- Альтернатива до шардирования: перенести таблицу с интенсивной записью в хранилище, созданное для этого (Kafka для событий, wide-column хранилище для временных рядов) ([[storage-choices]], [[column-and-wide-column-stores]]).

### Числа для оценок
- Один primary на хорошем инстансе: десятки тысяч чтений по индексу/с, несколько тысяч транзакционных записей/с; с `synchronous_commit = off` для некритичных данных — больше.
- Отставание репликации: единицы миллисекунд в здоровой LAN, секунды при сильных всплесках записи или долгих запросах на реплике.
- Размер таблицы, при котором партиционирование начинает окупаться: сотни миллионов строк или когда удаление по сроку хранения измеряется часами.

## Пример
Маршрутизация через `AbstractRoutingDataSource`, чтобы транзакции только на чтение шли на реплику, а страница заказа eSIM читала только что созданный заказ с primary:

```java
public class ReplicaRoutingDataSource extends AbstractRoutingDataSource {
    @Override
    protected Object determineCurrentLookupKey() {
        boolean readOnly = TransactionSynchronizationManager.isCurrentTransactionReadOnly();
        return readOnly ? "replica" : "primary";
    }
}

@Service
@RequiredArgsConstructor
public class OrderQueryService {
    private final OrderRepository orders;

    @Transactional(readOnly = true)            // направляется на реплику
    public Page<OrderView> history(String msisdn, Pageable page) {
        return orders.findByMsisdn(msisdn, page).map(OrderView::from);
    }

    @Transactional                             // primary: только что созданный заказ должен быть виден
    public OrderView justCreated(UUID orderId) {
        return OrderView.from(orders.findById(orderId).orElseThrow());
    }
}
```

Обёртка `LazyConnectionDataSourceProxy` обязательна, чтобы выбор источника происходил после того, как Spring выставил флаг read-only, а не в момент открытия транзакции ([[spring-transactional]]).

## Подводные камни
- Добавлять реплики чтения, когда проблема в записи или конкуренции за блокировки; primary всё равно остаётся узким местом.
- Кешировать до индексирования: кеш скрывает плохой запрос до первого холодного старта или шторма вытеснения ключей.
- Шардировать по ключу, которого нет в основных запросах (по `order_id`, когда каждый экран фильтрует по `user_id`), — каждый запрос превращается в scatter-gather.
- Долгая аналитика на primary; отчёты нужно перенести на реплику или в отдельное хранилище ([[sql-vs-nosql-choosing]]).
- Связанные заметки: [[horizontal-vs-vertical-scaling]], [[back-of-envelope-estimation]], [[transactions-acid-and-isolation]].
