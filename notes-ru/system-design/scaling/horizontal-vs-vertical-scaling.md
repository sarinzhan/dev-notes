## Кратко
Вертикальное масштабирование — это машина побольше: просто, без изменений кода, но есть потолок, кривая цены, загибающаяся вверх, и одна машина, которая может отказать. Горизонтальное масштабирование — это больше машин за [[load-balancing|балансировщиком нагрузки]]: в теории без границ, дешевле на единицу мощности, устойчиво к отказам, но только если сервис **без состояния (stateless)**, чтобы любая реплика могла обслужить любой запрос. Настоящая работа при «масштабировании вширь» — вынести состояние (сессии, загрузки, кеши, блокировки, задачи по расписанию) из процесса в общую инфраструктуру.

## Основное

### Сравнение двух направлений
| | Вертикальное (scale up) | Горизонтальное (scale out) |
|---|---|---|
| Как | больше CPU / RAM / более быстрый диск на одном узле | больше реплик того же узла |
| Изменения кода | никаких | сервис должен быть без состояния; общее состояние вынесено наружу |
| Предел | самый большой инстанс, который можно купить | накладные расходы на координацию, узким местом становится общая БД |
| Доступность | единая точка отказа, перезапуск = простой | N-1 реплик продолжают работать; поэтапный deploy (rolling) |
| Кривая стоимости | сверхлинейная на верхнем краю | примерно линейная, плюс LB и оркестрация |
| Типичное первое применение | базы данных, Redis, брокеры Kafka (с состоянием) | API-сервисы, worker-ы, consumer-ы |

- Честный первый шаг почти всегда — вертикальный для базы данных и горизонтальный для уровня приложения. Postgres масштабируется вверх очень далеко (десятки ядер, сотни GB RAM, NVMe), прежде чем реплики чтения или шардирование становятся оправданы ([[database-scaling-path]]).
- Горизонтальное масштабирование компонентов с состоянием — другая задача: репликация и партиционирование ([[leader-follower-replication]], [[sharding-strategies]]), а не «добавить pod».

### Что делает сервис stateless
- Никакие данные запроса не переживают в процессе между запросами: никаких синглтонов `HashMap<SessionId, …>`, никаких счётчиков rate limit в памяти, никаких множеств «уже видели».
- Любую реплику можно убить в любой момент без потери работы: запросы в обработке быстро падают, а клиент или очередь повторяют их ([[idempotency]]).
- Deployment-ы взаимозаменяемы: конфигурация через окружение и config server, а не через файлы, отредактированные на машине ([[spring-boot-properties-and-profiles]]).

### Вынос сессий наружу
- Классические веб-приложения на Java держали `HttpSession` в контейнере сервлетов, поэтому второму экземпляру нужны были привязанные сессии (sticky sessions) или репликация сессий. Оба варианта хрупкие: sticky sessions ломаются при уменьшении числа экземпляров (scale-in), репликация «болтлива».
- Варианты сегодня:
  - **Токены без состояния**: подписанный [[jwt-authentication|JWT]] несёт идентичность; сервер проверяет подпись и ничего не хранит. Для logout и отзыва нужны короткий TTL и чёрный список (denylist).
  - **Общее хранилище сессий**: Spring Session с Redis хранит сессию по id; cookie содержит только id ([[redis-data-structures]]). Любая реплика может её загрузить.
- Всё остальное, что раньше жило «в приложении», выносится так же: загруженные файлы — в объектное хранилище ([[file-and-blob-storage]]), кеши — в Redis ([[caching]]), блокировки — в базу данных или сервис координации ([[distributed-locks-and-fencing]]), задачи по расписанию — на единственного лидера или в очередь ([[background-jobs-and-schedulers]]).

### Масштабирование уровня приложения на практике
- За LB реплики регистрируются через service discovery ([[api-gateway-and-service-discovery]]); Kubernetes делает это через `Service` и масштабирует через HPA по CPU или пользовательской метрике вроде lag очереди ([[kubernetes-basics]]).
- Сервисы «поток на запрос» ограничены произведением потоков на задержку; закон Литтла: concurrency = throughput × latency ([[amdahls-law-and-parallel-speedup]]). Снизить задержку нижестоящих систем часто дешевле, чем добавлять реплики, а [[virtual-threads]] убирают потолок по потокам для сервисов, упирающихся в ввод-вывод.
- Каждая реплика открывает свой пул к БД. 20 реплик × 10 соединений = 200 серверных соединений; размер пулов выбирают с учётом суммы или добавляют PgBouncer ([[hikaricp-pool-sizing]]).
- Consumer-ы масштабируются горизонтально только до числа партиций Kafka ([[kafka-consumer]]); реплики сверх числа партиций простаивают.

### Ракурсы на собеседовании
- «Твой сервис тормозит в пик, что будешь делать?» Сначала измерить (куда уходит время: CPU, БД, внешний вызов?). Если упирается в CPU и без состояния — масштабировать вширь. Если упирается в БД — масштабирование уровня приложения сделает хуже, потому что больше реплик — это больше соединений, долбящих тот же primary.
- «Почему просто не масштабировать вертикально?» Потолок, кривая стоимости, простой при изменении размера, единая точка отказа; но для компонента с состоянием ниже его потолка это правильный ответ.
- «Что ломается при переходе от одного экземпляра к двум?» Кеши в памяти расходятся, задачи `@Scheduled` выполняются дважды, локально загруженные файлы исчезают, rate limit-ы считаются на экземпляр, сессии теряются на другом экземпляре.

## Пример
Spring Session на Redis превращает сервис на сессиях в сервис без состояния, не трогая контроллеры:

```yaml
# application.yml
spring:
  session:
    store-type: redis
    timeout: 30m
  data:
    redis:
      host: redis
      port: 6379
server:
  servlet:
    session:
      cookie:
        http-only: true
        secure: true
        same-site: lax
```

```java
@Configuration
@EnableRedisHttpSession
public class SessionConfig {
    // cookie хранит только id сессии; атрибуты лежат в Redis в виде hash,
    // поэтому запрос может попасть на любую реплику за балансировщиком нагрузки
}
```

С этим `kubectl scale deployment api --replicas=6` — безопасная операция: LB распределяет трафик, каждый pod загружает сессию из Redis, а перезапуск pod-а никого не разлогинивает.

## Подводные камни
- «Stateless»-сервисы, которые всё ещё используют `@Scheduled` без распределённой блокировки (ShedLock, advisory lock в БД), выполняют задачу по разу на каждой реплике; заметка про outbox relay показывает способ сделать это безопасно через `SKIP LOCKED` ([[outbox-pattern]]).
- Локальный кеш внутри процесса (Caffeine) на N репликах даёт N разных представлений данных; допустимо для справочных данных с TTL, неправильно для всего, что пользователи могут редактировать ([[distributed-cache-coherence]]).
- Масштабировать уровень приложения вширь раньше, чем база данных выдержит нагрузку: первый симптом — исчерпание пула и `too many connections`.
- Sticky sessions прячут проблему до первого scale-in или deploy.
- Связанные заметки: [[load-balancing]], [[database-scaling-path]], [[read-write-splitting-and-cqrs-lite]].
