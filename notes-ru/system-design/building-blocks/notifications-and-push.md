## Кратко
Подсистема уведомлений превращает одно доменное событие («пополнение прошло успешно», «eSIM активирована») в ноль или больше доставок по каналам с очень разными провайдерами и гарантиями: push (APNs/FCM, «отправил и забыл» на токен устройства), SMS (шлюз с жёстким ограничением частоты и оплатой за сообщение), email (SMTP или API с отказами доставки (bounces)), in-app (собственное хранилище и WebSocket). Строительный блок — это **конвейер (pipeline)**: принять и сохранить, определить получателей и их настройки, разослать по каналам, доставить через адаптер провайдера с retry и circuit breaker, записать статус по квитанциям провайдера и дедуплицировать на каждой границе retry, чтобы пользователь никогда не получил одно и то же SMS дважды. Полный разбор кейса — в [[design-notification-service]]; эта заметка — о переиспользуемом блоке и решениях внутри него.

## Основное

### Этапы конвейера
| Этап | Ответственность | Хранилище / инструмент |
|---|---|---|
| Приём | проверить, сохранить с `Idempotency-Key`, вернуть `202` | Postgres + [[outbox-pattern]] |
| Разрешение | получатели (один пользователь, сегмент, тема), настройки, тихие часы, отписки, локаль, токены устройств | Postgres + кэш Redis ([[caching]]) |
| Рендеринг | шаблон + параметры → контент для канала (заголовок push, текст SMS ≤ 160 символов, HTML письма) | хранилище шаблонов, с кэшем |
| Fan-out | одно сообщение на пару (получатель, канал) в топики по каналам | Kafka с ключом по получателю ([[message-queues-and-streams]]) |
| Доставка | адаптер провайдера: таймаут, retry, [[circuit-breaker]], [[rate-limiting]] на провайдера | воркеры по каналам |
| Отслеживание | квитанции провайдера (вебхуки) → DELIVERED / FAILED / BOUNCED, очистка токенов | топик квитанций, таблица статусов |
| Наблюдение | доля успеха по каналу, задержка, lag очереди, структура ошибок провайдера | [[grafana-dashboards-and-red-use]] |

### Варианты fan-out
- **Fan-out при записи (fan-out on write)** (материализовать по сообщению на получателя в момент отправки) — для адресных уведомлений и небольших сегментов: просто, retry по каждому получателю, статус по каждой доставке. Сегмент в 5 M пользователей — это 5 M сообщений; для Kafka нормально, но притормаживай производителя, чтобы не завалить провайдера.
- **Fan-out при чтении (fan-out on read)** — для in-app лент с широковещательным контентом: кампания хранится один раз, каждый клиент запрашивает «кампании, подходящие мне, с момента моего последнего чтения». Тот же компромисс, что в [[design-news-feed]].
- **Подписки на темы** у push-провайдера (FCM topics) переносят широковещательный fan-out на провайдера; теряется статус по каждому устройству.
- Порядок для получателя важен («активировано» раньше «деактивировано»): используй id получателя как ключ везде, чтобы одна партиция упорядочивала сообщения одного пользователя.

### Каналы и их особенности
| Канал | Контракт провайдера | Сигнал об ошибке | Частота / стоимость | На что обратить внимание |
|---|---|---|---|---|
| Push (APNs/FCM) | HTTP/2 API, токен устройства | сразу 4xx (недействительный токен), позже «unregistered» | высокая пропускная способность, бесплатно | токены истекают: удаляй при `Unregistered`; collapse keys, чтобы заменять устаревшие уведомления |
| SMS | HTTP-шлюз или SMPP | синхронный приём, асинхронный вебхук DLR | 100–1 000 сообщений/с по договору, оплата за сообщение | длина в GSM-7 и UCS-2, правила sender id, без retry при «неверном номере», тихие часы по закону |
| Email | SMTP или API | отказы и жалобы через вебхук, спустя часы | дёшево, ограничено репутацией | список подавления для hard bounces, DKIM/SPF, ссылка отписки |
| In-app | твоя БД + [[websockets-sse-and-long-polling|WebSocket/SSE]] | нет | бесплатно | состояние прочитано/не прочитано, счётчики на значках |
| Вебхук партнёрам | HTTP POST на их URL | 5xx / таймаут | их лимиты | подпись, retry с backoff, [[dead-letter-queues-and-retries|DLQ]] |

**Воркер** для каждого канала со своей consumer group, пулом потоков, breaker и лимитером не даёт сбою SMS затронуть push ([[async-processing-and-event-driven-scaling]]).

### Retry, дедупликация и порядок
- Доставка везде at-least-once (повторная доставка Kafka, падение воркера после того, как провайдер принял сообщение, retry API со стороны клиента). Дедуплицируй через **уникальное ограничение** на `(notification_id, channel)` в таблице `delivery`, запись в которую делается до вызова провайдера, и через собственный ключ идемпотентности провайдера, если он есть (FCM и большинство SMS API принимают клиентский id сообщения).
- Классифицируй ошибки провайдера: **повторяемые** (таймаут, 5xx, 429 → backoff с джиттером, максимум N, затем DLQ) и **постоянные** (недействительный токен, номер не обслуживается, пользователь отписался → сразу FAILED, исправлять данные). Retry постоянной ошибки — самая частая растрата ресурсов в таких системах ([[error-handling-strategies]]).
- Retry должны учитывать **срок действия**: OTP, повторённый через 40 минут, вреден; каждое сообщение несёт `ttl`, после которого воркер отбрасывает его со статусом EXPIRED.
- Квитанции приходят не по порядку и с дубликатами: обновляй статус с семантикой «только вперёд» (`ACCEPTED → SENT → DELIVERED`, никогда назад) и идемпотентными upsert ([[idempotency]]).

### Настройки, требования регуляторов, троттлинг
- Настройки по каналу и категории (транзакционные и маркетинговые), **тихие часы** в часовом поясе пользователя (для транзакционных — отложить, не отбрасывать; для маркетинговых — отбросить), отписка, которая проверяется при разрешении получателей *и* при доставке (она может измениться, пока сообщение лежит в очереди).
- Ограничения частоты на пользователя («максимум 3 маркетинговых push в день») — скользящее окно в Redis; лимиты провайдера — token bucket, общий для всех воркеров ([[rate-limiting]]).
- Приоритет: OTP и оповещения безопасности обходят ограничения и идут в отдельный высокоприоритетный топик с зарезервированной ёмкостью воркеров; маркетинг разбирается с той скоростью, что остаётся.
- Аудит: храни, что и кому отправлено, с хэшем отрендеренного контента — для поддержки и регуляторов; срок хранения по каналу (SMS 90 дней, email дольше) ([[requirements-and-constraints]]).

### Напоминание о размерах
Для 10 M пользователей и 12 M уведомлений/день пик конвейера — около 1 K сообщений/с, а реальное ограничение — 100 сообщений/с у SMS-провайдера; задача очереди — поглотить разницу, задача лимитера — защитить договор ([[back-of-envelope-estimation]]).

## Пример
Воркер доставки SMS: дедупликация через уникальную строку, вызов провайдера с таймаутом и breaker, классификация ошибок, срок действия и обновление статуса только вперёд.

```java
@Component
public class SmsDeliveryWorker {
    private final DeliveryRepository deliveries; private final SmsGatewayClient gateway;
    private final RedisTokenBucket providerLimit; private final CircuitBreaker breaker;

    public SmsDeliveryWorker(DeliveryRepository d, SmsGatewayClient g, RedisTokenBucket l, CircuitBreakerRegistry reg) {
        this.deliveries = d; this.gateway = g; this.providerLimit = l; this.breaker = reg.circuitBreaker("sms-gateway");
    }

    @KafkaListener(topics = "notifications.sms", groupId = "sms-worker")
    public void onMessage(SmsMessage msg, Acknowledgment ack) {
        if (Instant.now().isAfter(msg.expiresAt())) {                         // OTP не должны приходить с опозданием
            deliveries.markExpired(msg.notificationId(), "SMS");
            ack.acknowledge(); return;
        }
        // 1. Дедупликация между повторными доставками: уникальный (notification_id, channel). Строка уже есть = уже обработано.
        if (!deliveries.insertIfAbsent(msg.notificationId(), "SMS", msg.phone())) { ack.acknowledge(); return; }

        // 2. Лимит провайдера: ждать, а не отбрасывать. Пауза здесь создаёт обратное давление на партицию.
        var decision = providerLimit.tryConsume("rl:provider:sms-gw", 100, 100.0, 1);
        while (!decision.allowed()) {
            LockSupport.parkNanos(Duration.ofMillis(Math.max(100, decision.retryAfterSec() * 1000)).toNanos());
            decision = providerLimit.tryConsume("rl:provider:sms-gw", 100, 100.0, 1);
        }

        try {
            // 3. Вызов провайдера за breaker с таймаутом 3 с; наш notificationId — ключ идемпотентности у провайдера.
            var result = breaker.executeSupplier(() -> gateway.send(msg.phone(), msg.text(), msg.notificationId().toString()));
            deliveries.advance(msg.notificationId(), "SMS", DeliveryStatus.SENT, result.providerRef());
            ack.acknowledge();
        } catch (SmsGatewayException e) {
            if (e.isPermanent()) {                                             // неверный номер, отписка, чёрный список
                deliveries.advance(msg.notificationId(), "SMS", DeliveryStatus.FAILED, e.code());
                ack.acknowledge();
            } else {
                deliveries.deleteAttempt(msg.notificationId(), "SMS");       // чтобы retry прошёл дедупликацию
                throw e;                                                       // повторяемая: error handler контейнера → retry-топик → DLQ
            }
        } catch (CallNotPermittedException open) {
            deliveries.deleteAttempt(msg.notificationId(), "SMS");
            throw open;                                                        // breaker открыт: отступаем через уровень retry
        }
    }
}

// Вебхук квитанций от шлюза, идемпотентный и только вперёд:
// UPDATE delivery SET status = 'DELIVERED', delivered_at = :t WHERE provider_ref = :ref AND status IN ('SENT');
```

Error handler контейнера (`DefaultErrorHandler` с `DeadLetterPublishingRecoverer`) направляет повторяемые сбои в `notifications.sms.retry.1m`, а после последнего уровня — в `notifications.sms.dlq` ([[spring-kafka-consumer]], [[dead-letter-queues-and-retries]]).

## Подводные камни
- Дедупликация только в памяти или только по offset Kafka: повторный deploy или rebalance переобрабатывает пачку, и пользователь получает два SMS; гарантия — это уникальная строка.
- Синхронный вызов провайдера внутри API-запроса: API наследует задержки и сбои шлюза ([[api-design-for-system-design]]).
- Одна consumer group на все каналы: медленный SMS-шлюз тормозит push; нужны отдельные топики, группы и пулы.
- Игнорирование обратной связи провайдера: незарегистрированные токены и hard bounces накапливаются, расходы растут, репутация email падает; обрабатывай квитанции и чисти данные.
- Тихие часы и отписка проверяются только при приёме: маркетинговый push, поставленный в очередь в 21:55, доставляется в 23:10; перепроверяй при доставке.
- Связанные заметки: [[design-notification-service]] — сквозной дизайн и ёмкость; [[outbox-pattern]] — атомарная публикация на этапе приёма.
