## Кратко
Выбирай хранилище по **паттерну доступа (access pattern)** (как данные пишутся, как читаются, как растут), а не по форме данных или моде. Реляционная база покрывает большинство сервисов: транзакции, join, вторичные индексы, зрелые инструменты. Специализированные хранилища оправданы, когда доминирует один паттерн и RDBMS за него расплачивается: key-value хранилище — для поиска по id быстрее миллисекунды, wide-column — для данных с преобладанием записи и упорядоченных по времени при десятках тысяч записей в секунду, блоб-хранилище — для больших неизменяемых файлов, поисковый движок — для полнотекстовых и фасетных запросов, база временных рядов — для метрик. Ответ по умолчанию на собеседовании — «Postgres плюс X для того единственного паттерна, которому это нужно»; дерево решений SQL/NoSQL — в [[sql-vs-nosql-choosing]].

## Основное

### Каталог
| Хранилище | Модель данных | Сильно в | Слабо в | Примеры |
|---|---|---|---|---|
| Реляционное | таблицы, строки, FK, SQL | транзакции, join, произвольные запросы, ограничения, индексы | горизонтальное масштабирование записи, очень широкие/разреженные строки | Postgres, MySQL |
| Key-value | ключ → непрозрачное значение / структуры | поиск за 0,2–1 мс, счётчики, TTL, 100 K+ операций/с на узел | запросы по чему-либо, кроме ключа | Redis, DynamoDB (отчасти и документное) |
| Документное | ключ → дерево JSON, вторичные индексы | гибкая схема, чтение агрегата целиком, вложенные данные | транзакции на несколько документов, join, аналитика | MongoDB, Couchbase; Postgres JSONB покрывает многое |
| Wide-column | ключ партиции → отсортированные строки → колонки | преобладание записи, упорядоченность по времени, линейное масштабирование, несколько ЦОД | произвольные запросы, join, строгая согласованность, транзакции | Cassandra, ScyllaDB, HBase |
| Блоб / объектное | бакет + ключ → байты + метаданные | огромные неизменяемые файлы, дёшево за GB, доступ по HTTP, origin для CDN | листинг, изменение, задержка для маленьких объектов | S3, MinIO, GCS |
| Поисковое | инвертированный индекс по документам | полнотекстовый поиск, релевантность, фасеты, нечёткий поиск, агрегации | роль источника истины, транзакции, задержка записи | Elasticsearch, OpenSearch |
| Временные ряды | (метрика, теги, время) → значение, со сжатием | высокая скорость приёма, прореживание (downsampling), запросы по диапазону времени | реляционные join, обновления | Prometheus/Mimir, TimescaleDB, ClickHouse |
| Графовое | узлы, рёбра, обходы | связи через несколько переходов (мошеннические кольца, соцсети) | массовая аналитика, простой CRUD | Neo4j |
| Колоночное / OLAP | колонки, сжатие, сканирования | аналитика по миллиардам строк, агрегаты | точечные чтения, обновления | ClickHouse, BigQuery |
| Лог / поток | партиции только на дозапись | события, replay, развязка | запросы | Kafka ([[message-queues-and-streams]]) |

### Вопросы, которые определяют хранилище
1. **Как читаются данные?** Только по первичному ключу → KV или документное. По многим атрибутам с join → реляционное. По тексту → поисковое. По диапазону времени для сущности → wide-column или временные ряды. Через несколько переходов → графовое.
2. **Как пишутся данные?** Тысячи записей/с с транзакциями → primary в Postgres (5–10 K/с). Десятки тысяч/с, в основном дозапись, без транзакций между строками → wide-column или лог. Большие файлы → блоб.
3. **Какая нужна согласованность?** Деньги и складские остатки → ACID в одном хранилище ([[transactions-acid-and-isolation]]). Ленты, история, аналитика → согласованности в конечном счёте достаточно ([[consistency-models]]).
4. **Размер и рост?** Меньше нескольких TB → один Postgres с [[postgres-partitioning|партиционированием]] и репликами. Десятки TB горячих данных → хранилище с нативным шардированием или [[sharding-strategies|шардирование]].
5. **Кто его эксплуатирует?** Каждое новое хранилище — новая зона дежурств: бэкапы, обновления, переключение при отказе. Сначала управляемые сервисы или расширения Postgres (JSONB, полнотекстовый поиск, TimescaleDB) ([[postgres-jsonb-and-full-text]]).

### Polyglot на практике: одна система, несколько хранилищ
Сервис уведомлений ([[design-notification-service]]): Postgres для уведомлений, настроек и outbox (транзакции, запросы по статусу); Redis для лимитов, ключей дедупликации и кэша настроек; Kafka как конвейер; S3 для вложений и логов провайдеров; опционально Elasticsearch для текстового поиска операторами; Mimir для метрик. Каждое хранилище держит один вид данных, и **реляционное хранилище — источник истины**; остальные производные и восстанавливаемые ([[search-and-indexing-services]], [[caching]]).

### Последствия для моделирования
- Wide-column и документные хранилища — **query-first**: таблица/коллекция проектируется под запрос (денормализация, дублирование), join, которые спасут потом, не будет ([[column-and-wide-column-stores]], [[mongodb-basics]], [[normalization-and-denormalization]]).
- Реляционное остаётся **data-first**: нормализуй, индексируй под запросы, денормализуй только измеренные горячие пути ([[data-modeling-for-services]], [[postgres-indexes]]).
- Блоб-хранилище — **write-once**: версионирование и правила жизненного цикла заменяют обновления; метаданные в Postgres, байты в бакете ([[file-and-blob-storage]]).

### Грубые ориентиры по ёмкости
| Хранилище (один узел хорошего размера) | Чтения | Записи | Данные |
|---|---|---|---|
| Postgres 17 | 20–50 K точечных чтений/с | 5–10 K транзакций/с | до нескольких TB без проблем |
| Redis | 100 K+ операций/с | столько же | ограничено RAM, десятки GB |
| Узел Cassandra | ~10 K/с | ~10–20 K/с | 1–2 TB на узел, масштабируется линейно |
| Узел Elasticsearch | 1–5 K запросов/с | 5–20 K документов/с пачками | сотни GB на узел |
| Бакет в стиле S3 | фактически без ограничений, 3 500 PUT / 5 500 GET на префикс в секунду | | PB |

Используй их вместе с [[back-of-envelope-estimation]], чтобы понять, хватит ли одного Postgres (обычно хватает).

## Пример
Схема и размещение для домена уведомлений с обоснованиями в комментариях: единственное место, где был бы оправдан wide-column (попытки доставки при очень большом объёме), остаётся в партиционированном Postgres, пока цифры не потребуют иного.

```sql
-- Postgres: источник истины, транзакционные записи, запросы по статусу, outbox в той же транзакции.
CREATE TABLE notification (
    id             uuid PRIMARY KEY,
    subscriber_id  bigint      NOT NULL,
    template       text        NOT NULL,
    params         jsonb       NOT NULL,                       -- гибкие данные под шаблон; документная БД не нужна
    priority       smallint    NOT NULL DEFAULT 1,
    status         text        NOT NULL DEFAULT 'ACCEPTED',
    created_at     timestamptz NOT NULL DEFAULT now()
) PARTITION BY RANGE (created_at);                             -- дневные партиции, удаляются через 90 дней
CREATE INDEX ON notification (subscriber_id, created_at DESC); -- страница истории абонента (keyset-пагинация)

-- Попытки доставки: 18 M строк/день, только дозапись, читаются по id уведомления или для дашбордов эксплуатации.
-- Postgres легко справляется с ~200 вставок/с; в тот день, когда второй провайдер поднимет это до 20 K/с,
-- эта таблица станет кандидатом на Cassandra/ClickHouse (ключ партиции = notification_id, кластеризация = attempted_at).
CREATE TABLE delivery_attempt (
    notification_id uuid        NOT NULL,
    channel         text        NOT NULL,
    attempt_no      smallint    NOT NULL,
    provider        text        NOT NULL,
    result          text        NOT NULL,
    provider_ref    text,
    attempted_at    timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (notification_id, channel, attempt_no)
) PARTITION BY RANGE (attempted_at);

-- Вложения: байты в объектном хранилище, здесь только ссылка.
CREATE TABLE attachment (
    id              uuid PRIMARY KEY,
    notification_id uuid NOT NULL REFERENCES notification(id),
    object_key      text NOT NULL,                             -- s3://notif-attachments/2026/10/27/<uuid>.pdf
    size_bytes      bigint NOT NULL,
    content_type    text NOT NULL
);

-- Redis (не SQL, указан для полноты размещения): token bucket rl:api:<client>, dedup:<idempotencyKey> с TTL 24 ч,
-- кэш prefs:v1:<subscriberId> с TTL 10 мин.  Elasticsearch (опционально): поиск операторами по
-- тексту уведомлений и ошибкам провайдеров, наполняется через CDC из outbox.
```

## Подводные камни
- Выбрать NoSQL «ради масштаба» при 100 записях/с, а потом заново строить join и транзакции в коде приложения.
- Redis как основное хранилище без персистентности и репликации: перезапуск теряет данные ([[redis-patterns-and-persistence]]).
- Хранение файлов в колонках `bytea`: бэкапы, репликация и vacuum замедляются; паттерн — блоб-хранилище плюс ссылка ([[postgres-vacuum-and-bloat]]).
- Elasticsearch как источник истины: это индекс; при отказе узла он теряет записи так, как база данных не теряет, и переиндексация из источника истины должна оставаться возможной.
- Много хранилищ без владельца: каждому нужны бэкапы, окна обновлений и мониторинг; эксплуатационные расходы платятся каждый месяц ([[requirements-and-constraints]]).
- Связанные заметки: [[sql-vs-nosql-choosing]] — дерево решений; [[database-scaling-path]] — как далеко заходит один Postgres, прежде чем понадобится что-то из этого.
