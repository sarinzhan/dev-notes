## Кратко
У работы, которой не место внутри запроса, есть три дома. **Планировщик (scheduler)** (cron, `@Scheduled`, Kubernetes CronJob) запускает что-то в определённое время: ночные отчёты, ротацию партиций, очистку outbox. **Очередь с воркерами** выполняет что-то в ближайшее время и надёжно в ответ на событие: отправить это SMS, сжать это изображение, повторять, пока не получится. **Движок workflow (workflow engine)** (Temporal или оркестратор саг) выполняет многошаговый долгий процесс с состоянием, таймерами, retry для каждого шага и компенсацией: провижининг этой eSIM, подключение этого абонента в течение трёх дней. Выбор определяется длительностью, количеством шагов и тем, что должно пережить падение. Общая проблема всех трёх — **двойной запуск**: на нескольких pod, после падения, после повторного deploy; решение — блокировка или аренда (lease) плюс идемпотентные шаги.

## Основное

### Три модели
| | Планировщик (cron) | Очередь + воркеры | Движок workflow |
|---|---|---|---|
| Триггер | время | событие / сообщение | событие или API, дальше собственные часы |
| Длительность | секунды–минуты, ограничена | одна единица работы, секунды | от минут до месяцев |
| Состояние между шагами | нет (вычисляется заново из БД) | на сообщение | долговечное, в движке (история событий) |
| Retry | следующий запуск или собственный цикл | повторная доставка, backoff, DLQ ([[dead-letter-queues-and-retries]]) | политика на каждую activity, таймеры переживают перезапуски |
| Безопасность при нескольких экземплярах | нужна блокировка (ShedLock, `pg_advisory_lock` в БД, выбор лидера) | партиции / visibility timeout | очереди задач движка |
| Наблюдаемость | логи, метрика последнего запуска | lag, размер DLQ | история и UI для каждого workflow |
| Примеры | удаление партиций, отчёт, сверка, обновление токенов | отправка SMS, миниатюры, веерная рассылка вебхуков | провижининг eSIM, выполнение заказа, платёж с 3-DS, подключение абонента |

### Планировщики
- `@Scheduled(cron = "0 5 2 * * *")` в Spring — самый простой вариант; при двух pod задача выполнится дважды. Варианты: ShedLock (строка-блокировка в Postgres с арендой), `SELECT pg_try_advisory_lock(hashtext('nightly-report'))` или запуск задачи как Kubernetes **CronJob** с `concurrencyPolicy: Forbid` в отдельном pod, чтобы deployment API оставался без состояния ([[kubernetes-basics]], [[horizontal-vs-vertical-scaling]]).
- Делай каждую плановую задачу **идемпотентной и возобновляемой**: её запустят дважды (истечение блокировки, ручной перезапуск) и убьют на полпути (deploy). Обрабатывай пачками с водяным знаком (watermark) (`WHERE created_at > :last_processed`) и фиксируй водяной знак вместе с пачкой.
- Джиттер и разнесение: 50 сервисов с `0 0 * * *` одновременно бьют по базе в полночь. Сдвигай минуты или выводи расписание из хэша имени задачи.
- Пропущенные запуски: cron не наверстывает их после простоя; если задачу пропускать нельзя (биллинг), записывай «последний успешный запуск» и пусть задача сама вычисляет, что просрочено.
- Часовые пояса и переход на летнее время (DST): планируй в UTC, если бизнес-требование не задано в местном времени («отправить в 09:00 по Бишкеку»), и явно указывай, какое время имеется в виду ([[time-and-clocks]]).

### Очереди и воркеры
- Каждая единица работы — сообщение; воркеры масштабируются горизонтально по партициям или как конкурирующие потребители (competing consumers) ([[message-queues-and-streams]], [[async-processing-and-event-driven-scaling]]).
- Отложенные задачи («повторить через 10 мин», «напомнить через 24 ч»): встроены в RabbitMQ (delayed exchange), SQS (delay seconds, максимум 15 мин), неудобны в Kafka (retry-топики с consumer, который ставит паузу до наступления срока); для долгих задержек честным и простым решением будет таблица задач со сроком в БД, которую опрашивает планировщик (`SELECT ... WHERE run_at <= now() FOR UPDATE SKIP LOCKED`) ([[postgres-locks]]).
- Приоритет: отдельные очереди на каждый приоритет с отдельными пулами воркеров; одна очередь с приоритетами под нагрузкой морит голодом низкоприоритетные задачи.
- Задаче, которая вызывает внешнего провайдера, нужны таймаут, ограниченное число retry, [[circuit-breaker]] и [[rate-limiting|ограничение частоты]]; иначе пул воркеров превращается в генератор шторма повторов (retry storm).

### Движки workflow
- Когда в процессе **много шагов с состоянием, ожиданиями и компенсацией**, самописное «задача + колонка статуса + cron, который перезапускает застрявшие строки» разрастается в неподдерживаемый конечный автомат. Temporal даёт долговечное выполнение (durable execution): после любого падения код workflow воспроизводится (replay) по его истории событий; `sleep(3 days)` переживает повторный deploy; у каждой activity своя политика retry и таймаут ([[temporal-concepts]], [[workflow-engines-vs-sagas]]).
- Цена: кластер, который нужно эксплуатировать (или управляемый сервис), детерминированный код workflow, версионирование работающих workflow. Окупается примерно начиная с «три шага, две внешние системы, нужно переживать перезапуски» ([[design-esim-provisioning]], [[esim-provisioning-platform]]).
- **Сага** на событиях ([[saga]]) решает ту же задачу без движка, но размазывает логику процесса по потребителям; подходит для 2–3 шагов, дальше её трудно увидеть целиком и отлаживать.

### Как выбирать на собеседовании
- «Удалять истёкшие сессии каждую ночь» → cron с блокировкой.
- «Отправить SMS с OTP, который пользователь только что запросил» → очередь, p95 до 5 с, retry, DLQ.
- «После оплаты активировать eSIM, дождаться, пока устройство скачает профиль (до 24 ч), затем уведомить, иначе откатить списание» → движок workflow.
- «Через неделю повторно отправить письмо со счётом, если он не оплачен» → таблица задач со сроком или таймер workflow; не cron, который каждый час сканирует все счета.

## Пример
Таблица задач со сроком в Postgres и воркер, который забирает пачку через `SKIP LOCKED`: безопасно при любом количестве pod, поддерживает произвольные задержки и не требует дополнительной инфраструктуры. Используется в сервисе уведомлений для «повторной доставки вебхуков провайдера с backoff»; тяжёлые многошаговые процессы уходят в Temporal.

```sql
CREATE TABLE job (
    id          bigserial PRIMARY KEY,
    type        text        NOT NULL,                  -- 'webhook.deliver', 'invoice.remind'
    payload     jsonb       NOT NULL,
    run_at      timestamptz NOT NULL,
    attempts    int         NOT NULL DEFAULT 0,
    max_attempts int        NOT NULL DEFAULT 8,
    locked_until timestamptz,                           -- аренда, переживает падение воркера
    status      text        NOT NULL DEFAULT 'PENDING'  -- PENDING | DONE | FAILED
);
CREATE INDEX job_due_idx ON job (run_at) WHERE status = 'PENDING';   -- частичный: только «горячее» множество
```

```java
@Component
public class JobWorker {
    private final JdbcClient db; private final Map<String, JobHandler> handlers;
    public JobWorker(JdbcClient db, List<JobHandler> hs) {
        this.db = db; this.handlers = hs.stream().collect(toMap(JobHandler::type, h -> h));
    }

    @Scheduled(fixedDelay = 1000)                       // опрашивает каждый pod; SKIP LOCKED делает это безопасным
    public void runBatch() {
        List<Job> batch = db.sql("""
                UPDATE job SET locked_until = now() + interval '2 minutes', attempts = attempts + 1
                WHERE id IN (
                    SELECT id FROM job
                    WHERE status = 'PENDING' AND run_at <= now()
                      AND (locked_until IS NULL OR locked_until < now())
                    ORDER BY run_at
                    FOR UPDATE SKIP LOCKED
                    LIMIT 50)
                RETURNING id, type, payload, attempts, max_attempts
                """).query(Job.class).list();
        for (Job job : batch) execute(job);
    }

    private void execute(Job job) {
        try {
            handlers.get(job.type()).handle(job.payload());                      // должен быть идемпотентным
            db.sql("UPDATE job SET status = 'DONE', locked_until = NULL WHERE id = :id").param("id", job.id()).update();
        } catch (Exception e) {
            if (job.attempts() >= job.maxAttempts()) {
                db.sql("UPDATE job SET status = 'FAILED', locked_until = NULL WHERE id = :id").param("id", job.id()).update();
                return;                                                          // алерт по количеству FAILED
            }
            long backoffSec = (long) Math.min(3600, Math.pow(2, job.attempts()) * 30) + ThreadLocalRandom.current().nextLong(0, 30);
            db.sql("UPDATE job SET run_at = now() + make_interval(secs => :s), locked_until = NULL WHERE id = :id")
              .param("s", backoffSec).param("id", job.id()).update();
        }
    }
}
```

Аренда (`locked_until`) покрывает случай, когда воркер умирает посреди задачи: через две минуты её подхватывает другой pod, поэтому обработчик должен выдерживать повторное выполнение ([[idempotency]]).

## Подводные камни
- `@Scheduled` в реплицированном сервисе без блокировки: каждый отчёт генерируется N раз, каждое напоминание отправляется N раз.
- Задачи, которые держат открытой транзакцию БД во время вызова внешнего API: пул соединений иссякает, и задержка API становится задержкой пула ([[hikaricp-pool-sizing]]).
- Бесконечный retry с фиксированной задержкой: тысячи задач долбят упавшего провайдера каждые 30 с; используй экспоненциальный backoff с джиттером и потолком, затем помечай как ошибку и поднимай алерт.
- Случайно написанный движок workflow: признаки — колонки `status`, cron-уборщики «застрявших задач» и ручные перезапуски; переноси процесс в Temporal, пока он не разросся ([[workflow-engines-vs-sagas]]).
- Планирование по часам приложения с учётом часовых поясов и перехода на летнее время: задача на 02:30 раз в год пропадает или выполняется дважды.
- Связанные заметки: [[temporal-concepts]] — долговечное выполнение; [[outbox-pattern]] — задача-ретранслятор, которую большинство сервисов запускает первой.
