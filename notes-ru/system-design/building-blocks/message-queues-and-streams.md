## Кратко
Очередь или лог между двумя компонентами дают четыре вещи: **развязку (decoupling)** (производитель не знает о потребителе и не ждёт его), **буферизацию** (всплеск в 10 K/с поглощается и разбирается в темпе потребителя), **надёжность** (сообщение переживает падение потребителя и обрабатывается повторно) и **веерную рассылку (fan-out)** (несколько потребителей получают одно и то же событие). Две модели различаются тем, кому принадлежит сообщение: **очередь** (RabbitMQ, SQS, ActiveMQ) отдаёт каждое сообщение одному потребителю и удаляет его по ack; **лог** (Kafka, Pulsar, Kinesis) хранит упорядоченную запись, которую можно перечитать, по каждой партиции, а потребители сами отслеживают свой offset. Выбирай по вопросам ниже; внутреннее устройство — в [[kafka-architecture]], [[rabbitmq-basics]] и [[activemq-basics]].

## Основное

### Очередь или лог
| | Очередь (RabbitMQ, SQS) | Лог (Kafka) |
|---|---|---|
| Доставка | push одному потребителю, ack удаляет | потребители забирают (pull) и делают commit offset; сообщение хранится до истечения retention |
| Порядок | в пределах очереди, теряется при конкурирующих потребителях и requeue | строгий в пределах партиции (по ключу) |
| Повторное чтение (replay) | нет (после ack сообщения нет) | да: сбросить offset и переобработать день |
| Fan-out | exchange → несколько очередей (копии) | несколько consumer group читают одни и те же партиции |
| Возможности на уровне сообщения | приоритет, TTL, отложенная доставка, routing keys, ack/nack для каждого сообщения, встроенная DLQ | ничего из этого нативно нет; retry и DLQ — топики, которые строишь сам ([[dead-letter-queues-and-retries]]) |
| Пропускная способность на узел | десятки тысяч сообщений/с | от сотен тысяч до миллионов сообщений/с, последовательный диск |
| Параллелизм потребителей | любое число потребителей на одну очередь | ≤ числа партиций на группу; для масштабирования добавляй партиции |
| Обратное давление | управление потоком на стороне брокера, prefetch | потребитель забирает так быстро, как может; сигнал — lag ([[backpressure-and-flow-control]]) |
| Лучше всего подходит для | очереди задач, работа в стиле RPC, маршрутизация, задержки | потоки событий, аудит, CDC, несколько независимых потребителей, replay |

### Когда что использовать
- **Распределение задач** («отправить это SMS», «сгенерировать этот PDF»), приоритет или задержка для отдельного сообщения, много маленьких очередей с разными потребителями: очередь. RabbitMQ на своих серверах; SQS, если вы на AWS и время на эксплуатацию важно (управляемый, at-least-once, хранение 14 дней, FIFO-очереди с меньшей пропускной способностью).
- **Шина событий (event backbone)** (один факт потребляют биллинг, аналитика, уведомления, поисковый индексатор), порядок по сущности, replay для нового потребителя или исправления бага, большой объём: Kafka. Сюда относятся и eSIM-платформа, и сервис уведомлений ([[esim-provisioning-platform]], [[design-notification-service]]).
- **Оба** — частый вариант: Kafka для событий, очередь или движок workflow для retry отдельных задач ([[background-jobs-and-schedulers]], [[workflow-engines-vs-sagas]]).
- Вообще не очередь: запрос, которому ответ нужен сейчас (логин, проверка баланса), остаётся синхронным ([[service-communication-sync-vs-async]]).

### Гарантии, которые нужно спроектировать, а не предполагать
- Доставка в любой практической конфигурации — **at-least-once**; потребители обязаны быть идемпотентными ([[delivery-guarantees]], [[exactly-once-myth]], [[idempotency]]).
- Публикация атомарна с записью в БД только через [[outbox-pattern]]; `save(); send();` теряет события или порождает фантомные.
- Порядок соблюдается по ключу в пределах партиции и только пока эту партицию обрабатывает один потребитель; retry-топик ломает порядок для повторяемого ключа ([[dead-letter-queues-and-retries]]).
- Изменениям схемы нужно правило совместимости, иначе старый потребитель падает на новом поле ([[message-schema-evolution]]).

### Расчёт размеров лога
- Партиции: `max(target throughput / per-consumer throughput, number of consumers you want)`, с округлением вверх и запасом на рост. 12 партиций позволяют работать 12 воркерам; при 13 воркерах один простаивает.
- Выбор ключа определяет горячие партиции: `userId` равномерно распределяется по миллионам пользователей; `tenantId` с одним огромным тенантом — нет (в [[sharding-strategies]] тот же урок).
- Retention — это бюджет диска: `msg/s × size × replication × seconds` ([[back-of-envelope-estimation]]); 7 дней — частое значение по умолчанию, дольше для фактов, которые нужно перечитывать, compacted-топики для «последнего состояния по ключу».
- Consumer lag — метрика отставания; алерт ставь на рост lag, а не на его абсолютное значение ([[slo-sli-and-alerting]]).

### Тезисы для собеседования
- «Почему не вызвать сервис напрямую?» Связанность и доступность: доступность синхронной цепочки — произведение доступностей всех звеньев; с очередью производитель работает, даже когда потребитель лежит.
- «А если брокер упал?» Outbox хранит события в Postgres, и ретранслятор догоняет; API всё равно возвращает `202`.
- «А что с ядовитым сообщением (poison message)?» Повторить N раз с backoff, затем DLQ с ошибкой, алерт и инструмент для replay.
- «Как масштабировать потребителей?» Добавлять экземпляры до числа партиций; дальше — больше партиций или второй этап с другим ключом.

## Пример
Раскладка топиков и конфигурация потребителя для конвейера уведомлений: топик событий с ключом по абоненту, рабочие топики по каналам, retry- и DLQ-топики и потребитель Spring Kafka, настроенный на at-least-once с ручными commit.

```yaml
# топики (создаются скриптом оператора или Terraform; Kafka 4.x, KRaft)
topics:
  - name: notifications.requested          # каждое принятое уведомление, от ретранслятора outbox
    partitions: 24
    replication: 3
    config: { retention.ms: 604800000, min.insync.replicas: 2 }        # 7 дней
  - name: notifications.sms                # работа по каналу, тот же ключ (subscriberId) сохраняет порядок для пользователя
    partitions: 12
    replication: 3
  - name: notifications.sms.retry.1m       # уровни retry с растущей задержкой, consumer ставит паузу до наступления срока
    partitions: 12
    replication: 3
  - name: notifications.sms.dlq
    partitions: 3
    replication: 3
    config: { retention.ms: 2592000000 }                                # 30 дней, replay вручную
  - name: subscriber.preferences           # compacted: последние настройки абонента для прогрева кэша
    partitions: 12
    replication: 3
    config: { cleanup.policy: compact }

# application.yml для sms-worker
spring:
  kafka:
    bootstrap-servers: kafka-0:9092,kafka-1:9092,kafka-2:9092
    consumer:
      group-id: sms-worker
      enable-auto-commit: false              # commit после успешного вызова провайдера (at-least-once)
      auto-offset-reset: earliest
      max-poll-records: 50
      properties:
        max.poll.interval.ms: 300000         # 50 записей × 3 с таймаута провайдера × retry должны уложиться сюда
        isolation.level: read_committed
    listener:
      ack-mode: manual_immediate
      concurrency: 12                        # = числу партиций; больше потоков будут простаивать
    producer:
      acks: all
      properties:
        enable.idempotence: true
        linger.ms: 5
```

Почему здесь подошла бы и очередь: задержка и приоритет для отдельного сообщения («HIGH раньше LOW») нативно есть в RabbitMQ и неудобны в Kafka; Kafka выбрана ради replay, общей шины событий и порядка по абоненту. Подробности — в [[kafka-consumer]], [[kafka-producer]] и [[spring-kafka-consumer]].

## Подводные камни
- Использовать Kafka как очередь задач, рассчитывая на ack для каждого сообщения: одно медленное сообщение блокирует свою партицию; выноси медленную работу в пул воркеров с собственным уровнем retry или используй очередь.
- Слишком мало партиций «для начала»: перепартиционирование меняет соответствие ключ → партиция и ломает порядок на время перехода; закладывай с запасом сразу (партиции дешёвые, пока их не тысячи).
- Consumer group с `concurrency` больше числа партиций или два сервиса с одним group id из-за копипасты: половина сообщений уходит не в тот сервис.
- Бесконечные retry при «временной» ошибке, которая на самом деле постоянная (неверный номер телефона): сообщение крутится вечно, а DLQ остаётся пустой. Классифицируй ошибки ([[error-handling-strategies]]).
- Забыть, что брокер — инфраструктура с состоянием: диск, репликация, rebalance, обновления. SQS или управляемая Kafka снимают большую часть этого с небольшой команды ([[requirements-and-constraints]]).
- Связанные заметки: [[event-driven-architecture]] — архитектурный стиль поверх; [[async-processing-and-event-driven-scaling]] — масштабирование потребителей.
