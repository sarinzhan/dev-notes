## Кратко
ICMP — управляющий канал и канал ошибок IP: маршрутизаторы и хосты сообщают через него «недоступно», «TTL истёк» или «слишком большой, нужна фрагментация». У него нет портов, и он не несёт данных приложения. `ping` отправляет ICMP Echo Request и замеряет время до Echo Reply; `traceroute` отправляет пробы с TTL 1, 2, 3… и перечисляет маршрутизаторы, которые отвечают Time Exceeded. Блокировка всего ICMP выглядит как усиление защиты, но ломает определение MTU пути и усложняет диагностику аварий; фильтруй по типам.

## Основное
### Основы ICMP
- Передаётся прямо в IP (номер протокола 1; для ICMPv6 next header 58). У каждого сообщения есть **тип**, **код** и контрольная сумма; сообщения об ошибках включают IP-заголовок и первые 8 байт пакета, который их вызвал, чтобы отправитель мог сопоставить ошибку с сокетом (в этих 8 байтах лежат порты TCP/UDP).
- Ошибки ICMP никогда не отправляются в ответ на другие ошибки ICMP, на широковещательные пакеты и на фрагменты кроме первого, чтобы не было лавин.
- Маршрутизаторы ограничивают частоту генерации ICMP в своём control plane, поэтому ответы от маршрутизаторов медленнее и менее надёжны, чем пересылаемый трафик.

| Тип / код | Название | Кто и когда отправляет |
|---|---|---|
| 0 | Echo Reply | ответ на ping |
| 8 | Echo Request | ping |
| 3 / 0 | Net Unreachable | у маршрутизатора нет маршрута |
| 3 / 1 | Host Unreachable | последний маршрутизатор не смог сделать ARP для хоста |
| 3 / 3 | Port Unreachable | хост получил UDP на закрытый порт (TCP вместо этого отвечает RST) |
| 3 / 4 | Fragmentation Needed | пакет больше MTU при установленном DF; несёт MTU следующего хопа |
| 3 / 13 | Administratively Prohibited | файрвол отклонил (вместо молчаливого отбрасывания) |
| 5 | Redirect | «используй лучший шлюз в своей подсети»; серверы обычно игнорируют |
| 11 / 0 | Time Exceeded | TTL дошёл до 0 в пути |

- В IPv6 ICMPv6 обязателен: Packet Too Big (тип 2) заменяет фрагментацию на маршрутизаторах, а Neighbor Discovery заменяет ARP ([[arp]]).

### ping
- Отправляет Echo Request с идентификатором и порядковым номером; измеряет RTT каждого ответа и сообщает о потерях. Linux отправляет один запрос в секунду; `-c` — количество, `-i` — интервал, `-s` — размер нагрузки, `-M do` — установить DF (проверка MTU; см. [[ip-packet-structure]]).
- `ttl=` в ответе — оставшийся TTL при получении: 64 − хопы для Linux-цели.
- Что доказывает успешный ping: L3-путь в обе стороны и ядро хоста живы. Он не доказывает, что порт открыт, приложение здорово или файрвол пропускает TCP. Что доказывает неудачный ping: мало, ведь ICMP часто фильтруется (облачные security groups по умолчанию его блокируют).
- Для проверки сервисов используй пробы L4/L7: `nc -zv host 5432`, `curl` на health-эндпоинт или `InetAddress.isReachable` в Java, который пробует ICMP, только если у процесса есть привилегия, а иначе откатывается на TCP-соединение к порту 7.

### traceroute
- Отправляет пробу с TTL 1. Первый маршрутизатор уменьшает его до 0, отбрасывает пробу и возвращает Time Exceeded со своего адреса: хоп 1 найден. Затем TTL 2, 3, … пока не ответит назначение.
- Тип пробы: `traceroute` в Linux по умолчанию использует UDP на порты 33434+ (назначение отвечает Port Unreachable); `-I` использует ICMP echo (так делает `tracert` в Windows); `-T -p 443` использует TCP SYN и проходит через файрволы, которые пропускают только порт сервиса.
- Три пробы на хоп, поэтому в строке три RTT. `* * *` означает, что ответа за тайм-аут нет: маршрутизатор не отправляет Time Exceeded или ограничивает его частоту. Если следующие хопы отвечают, путь в порядке.
- RTT на среднем хопе включает медленную генерацию ICMP этим маршрутизатором; хоп с высокой задержкой, за которым идут хопы с низкой, — не узкое место. Настоящий рост задержки сохраняется до конца.
- Обратный путь может отличаться от прямого, а балансировка ECMP может отправить каждую пробу по своему маршруту; `mtr` и `tracepath` (который ещё сообщает MTU пути) дают более устойчивую картину.
- Коммутаторы и устройства L2 никогда не появляются: они не трогают TTL ([[host-to-host-communication]]).

```anim
traceroute-ttl
```

### Почему блокировка всего ICMP вредит
- **Ломается PMTUD**: TCP ставит DF и полагается на Fragmentation Needed, чтобы узнать, что у туннеля или VPN MTU меньше. Если файрвол его отбрасывает, большие сегменты молча исчезают. Симптом: TCP-рукопожатие и маленькие запросы работают, а большие ответы или TLS-рукопожатия с длинными цепочками сертификатов зависают. Это «чёрная дыра PMTUD» ([[mss-mtu-pmtud]]).
- Теряются сообщения о недоступности, поэтому клиенты ждут тайм-аутов, а не падают быстро.
- Пропадает диагностика: ни ping, ни traceroute во время аварии.
- Разумная политика: пропускать Echo Request/Reply (с ограничением частоты), Destination Unreachable (особенно код 4), Time Exceeded, а в IPv6 — Packet Too Big и Neighbor Discovery. Отбрасывать Redirect и устаревшие типы.

## Пример
Быстрая проверка снизу вверх с хоста приложения до базы данных, которая «отваливается по тайм-ауту»:
```bash
$ ping -c 3 -W 1 10.0.2.15
PING 10.0.2.15 (10.0.2.15) 56(84) bytes of data.
64 bytes from 10.0.2.15: icmp_seq=1 ttl=63 time=0.52 ms   # ttl 63: между нами один маршрутизатор
64 bytes from 10.0.2.15: icmp_seq=2 ttl=63 time=0.48 ms
64 bytes from 10.0.2.15: icmp_seq=3 ttl=63 time=0.50 ms
--- 10.0.2.15 ping statistics ---
3 packets transmitted, 3 received, 0% packet loss, time 2003ms

# L3 в порядке; трассируем настоящий порт сервиса TCP-пробами
$ sudo traceroute -n -T -p 5432 10.0.2.15
 1  10.0.1.1   0.41 ms  0.37 ms  0.35 ms
 2  * * *
 3  * * *
# маршрутизатор отвечает, но дальше него на 5432 ничего не проходит: файрвол отбрасывает SYN к порту БД
$ tracepath -n 10.0.2.15    # ещё печатает pmtu вдоль пути
```

## Подводные камни
- Делать вывод «сервер лежит» из неудачного ping. Многие хосты и любая облачная security group по умолчанию отбрасывают ICMP; проверяй настоящий порт.
- Считать `* * *` в середине трассы потерей пакетов. Проблему означают только звёздочки, идущие до самого конца, или потери, которые в `mtr` сохраняются до последнего хопа.
- Блокировать ICMP тип 3 код 4 (или ICMPv6 тип 2) на файрволе или security group перед VPN, overlay-сетью или кластером Kubernetes ([[docker-networking]]).
- Пинговать в цикле из мониторинга с `-i 0.01`: маршрутизаторы понижают приоритет ICMP, и ты измеряешь их CPU, а не сеть.
- Связанные заметки: [[network-routing]] — пути, которые показывает traceroute, [[network-debugging-toolkit]] — следующие инструменты после ping, [[ip-packet-structure]] — поля TTL и DF.
