## Кратко
Каждый хост и маршрутизатор выбирает следующий хоп для каждого пакета по таблице маршрутизации: списку префиксов, каждый из которых указывает на интерфейс и, возможно, шлюз. Побеждает самый специфичный совпавший префикс (longest-prefix match), а `0.0.0.0/0`, маршрут по умолчанию, ловит всё остальное. Маршрутизация идёт от хопа к хопу: каждый маршрутизатор знает только следующий шаг, а не весь путь. Пакет с частного адреса попадает в интернет только потому, что какой-то маршрутизатор по пути выполняет NAT; ответ находит дорогу обратно через таблицу трансляций этого маршрутизатора.

## Основное
### Таблица маршрутизации
- Каждая запись: префикс назначения, `dev` (исходящий интерфейс), необязательный `via` (шлюз следующего хопа), `src` (предпочтительный адрес источника), `metric` (решает при равенстве), `proto` (кто установил: kernel, dhcp, static, bgp).
- **Подключённые маршруты** (connected routes) появляются автоматически при назначении адреса: `10.0.1.10/24` на `eth0` устанавливает `10.0.1.0/24 dev eth0 scope link`. Шлюза нет: до назначений в этой сети добираются напрямую через [[arp]].
- **Маршрут по умолчанию** `default via 10.0.1.1`: всё, что не совпало с другими записями, уходит на этот шлюз. У типичного сервера ровно один подключённый маршрут и один маршрут по умолчанию.
- Хост без подходящего маршрута падает сразу (`Network is unreachable`); хост, чей маршрут указывает на мёртвый шлюз, падает медленно (ARP для шлюза не удаётся, затем `No route to host` или тайм-аут подключения).
- В Linux несколько таблиц и правила политик (`ip rule`) для маршрутизации по источнику; их используют VPN-клиенты, CNI в Kubernetes и хосты с несколькими сетями. `ip route get` показывает итоговое решение с учётом всего этого.

### Longest-prefix match
- Среди всех записей, содержащих адрес назначения, побеждает запись с самой длинной маской; только при равенстве решает метрика.
- При записях `0.0.0.0/0 via 10.0.1.1`, `10.0.0.0/8 via 10.0.1.254` (VPN) и `10.0.1.0/24 dev eth0` назначение `10.0.1.20` совпадает со всеми тремя и использует `/24` (напрямую); `10.8.3.4` использует `/8` (VPN); `8.8.8.8` — маршрут по умолчанию.
- Поэтому VPN, который добавляет `10.0.0.0/8`, может перехватить трафик сети Docker в `10.x`, если маршрут Docker менее специфичен, и поэтому пересекающиеся подсети вызывают проблемы вида «с ноутбука работает, из контейнера — нет» ([[ip-addressing-and-nat]]).

### Пересылка от хопа к хопу
- На каждом маршрутизаторе: снять кадр, найти IP назначения, уменьшить TTL, сделать ARP для следующего хопа, отправить новый кадр ([[host-to-host-communication]]). IP источника и назначения не меняются, если не настроен NAT.
- Маршрутизаторы узнают маршруты статически или через протоколы маршрутизации: OSPF/IS-IS внутри одной организации, BGP между организациями (интернет — это примерно 1 миллион BGP-префиксов, сшитых автономными системами).
- Обратный трафик маршрутизируется независимо и может пойти другим путём (асимметричная маршрутизация). Тогда stateful-файрволы и NAT, стоящие только на одном из путей, отбрасывают ответы.

### Разбор примера: через две подсети
Две подсети соединены маршрутизатором R (`eth0 10.0.1.1`, `eth1 10.0.2.1`). Хост приложения A `10.0.1.10/24`, база данных B `10.0.2.15/24`.
1. A подключается к `10.0.2.15:5432`. Таблица на A: `10.0.1.0/24 dev eth0` не совпадает; `default via 10.0.1.1` совпадает. Следующий хоп — R.
2. A делает ARP для `10.0.1.1` и отправляет кадр на MAC R с IP назначения `10.0.2.15`.
3. Таблица R: совпадает `10.0.2.0/24 dev eth1` (подключённая). R уменьшает TTL, делает ARP для `10.0.2.15` на `eth1` и пересылает пакет.
4. B отвечает на `10.0.1.10`; его собственный маршрут по умолчанию отправляет ответ через `10.0.2.1`; R доставляет его на `eth0`.
5. Если бы у B был неверный шлюз, SYN от A дошёл бы, а SYN-ACK от B ушёл бы в никуда: со стороны A это выглядит как тайм-аут подключения, хотя `tcpdump` на B показывает приходящий SYN.

### Частные IP и NAT на выходе: Wi-Fi в самолёте
- Ноутбук пассажира подключается к Wi-Fi в салоне и получает по DHCP `10.20.0.57/22` со шлюзом `10.20.0.1` (бортовой сервер). Сотни других ноутбуков в самолёте делят тот же частный диапазон, как и тысячи других самолётов; частные адреса не уникальны и никогда не маршрутизируются в интернете.
- Ноутбук → `10.20.0.1`: у бортового маршрутизатора маршрут по умолчанию через спутниковый канал, и он выполняет **SNAT**: источник `10.20.0.57:51000` превращается в его собственный адрес, например `100.72.4.9:23011`, а соответствие записывается в таблицу NAT.
- Наземная станция провайдера может сделать NAT ещё раз (carrier-grade NAT) в публичный IP `198.51.100.20:40500`. Веб-сервер видит только этот адрес, общий для многих самолётов.
- Ответ приходит на `198.51.100.20:40500`; каждый NAT смотрит в свою таблицу и шаг за шагом переписывает назначение обратно, и ноутбук получает пакет, адресованный `10.20.0.57:51000`.
- Последствия: никто из интернета не может открыть соединение к ноутбуку (отображения нет, пока он сам не заговорит первым); простаивающие соединения умирают, когда истекает запись NAT; один публичный IP представляет многих пользователей, поэтому ограничения частоты и баны по IP бьют по всем в самолёте. Подробности NAT: [[ip-addressing-and-nat]].

## Пример
Чтение и проверка маршрутов на Linux-хосте или внутри контейнера:
```bash
$ ip route
default via 10.0.1.1 dev eth0 proto dhcp src 10.0.1.10 metric 100
10.0.0.0/8 via 10.0.1.254 dev eth0 proto static           # шлюз корпоративного VPN
10.0.1.0/24 dev eth0 proto kernel scope link src 10.0.1.10
172.18.0.0/16 dev br-3f2a proto kernel scope link src 172.18.0.1   # сеть Docker

# какая запись побеждает для назначения (после правил политик и longest-prefix match)
$ ip route get 10.0.1.20
10.0.1.20 dev eth0 src 10.0.1.10 uid 1000
$ ip route get 10.8.3.4
10.8.3.4 via 10.0.1.254 dev eth0 src 10.0.1.10 uid 1000
$ ip route get 8.8.8.8
8.8.8.8 via 10.0.1.1 dev eth0 src 10.0.1.10 uid 1000

# добавить более специфичный маршрут к сети партнёра, затем удалить его
$ sudo ip route add 192.0.2.0/24 via 10.0.1.254 dev eth0
$ sudo ip route del 192.0.2.0/24
```

## Подводные камни
- Пересекающиеся диапазоны: сеть Compose или CIDR подов Kubernetes в том же префиксе `10.x` или `172.x`, что и офисный VPN, делают часть внутренних хостов недоступными; более специфичный маршрут тихо побеждает.
- Два маршрута по умолчанию (Wi-Fi и Ethernet или VPN, добавляющий свой) с похожими метриками: трафик прыгает между интерфейсами, а долгоживущие соединения сбрасываются.
- Асимметричная маршрутизация через stateful-файрвол: файрвол видит только SYN-ACK (или только SYN) и отбрасывает их как невалидные.
- Отладка одним `ping`; сначала используй `ip route get`, чтобы увидеть, какой путь ядро реально выберет, затем [[icmp-ping-traceroute]], чтобы увидеть, где он обрывается.
- Связанные заметки: [[ip-packet-structure]] — TTL, [[docker-networking]] — как Docker добавляет маршруты и правила NAT, [[linux-networking]] — полный путь пакета через netfilter.
