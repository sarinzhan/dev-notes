## Кратко
IPv4-пакет — это заголовок длиной 20–60 байт плюс полезная нагрузка, всего до 65 535 байт, хотя на практике размер ограничен MTU канала (1500 в Ethernet). Заголовок несёт адреса источника и назначения, TTL, который останавливает петли маршрутизации, номер протокола, говорящий, что внутри (TCP, UDP, ICMP), и поля для фрагментации. Фрагментация позволяет маршрутизатору разбить пакет, слишком большой для следующего канала, но она медленная и хрупкая, поэтому современные стеки ставят бит Don't Fragment и вместо этого определяют MTU пути. IPv6 упрощает заголовок до фиксированных 40 байт и полностью убирает фрагментацию с маршрутизаторов.

## Основное
### Поля заголовка IPv4
| Поле | Размер | Что делает |
|---|---|---|
| Version | 4 бита | `4` |
| IHL | 4 бита | длина заголовка в 32-битных словах: от 5 (20 байт) до 15 (60 байт); больше 5 означает наличие опций |
| DSCP / ECN | 6 + 2 бита | раньше «Type of Service». DSCP помечает классы приоритета (VoIP получает EF = 46); ECN позволяет маршрутизаторам сигнализировать о перегрузке без отбрасывания |
| Total length | 16 бит | заголовок + нагрузка в байтах, максимум 65 535 |
| Identification | 16 бит | одинаковое значение у всех фрагментов одного исходного пакета |
| Flags | 3 бита | зарезервирован, **DF** (Don't Fragment), **MF** (More Fragments) |
| Fragment offset | 13 бит | с какого места начинаются данные этого фрагмента, в единицах по 8 байт |
| TTL | 8 бит | уменьшается каждым маршрутизатором; при 0 пакет отбрасывается и обратно отправляется ICMP Time Exceeded ([[icmp-ping-traceroute]]). Linux начинает с 64, Windows — со 128 |
| Protocol | 8 бит | 1 ICMP, 6 TCP, 17 UDP, 47 GRE, 50 ESP (IPsec) |
| Header checksum | 16 бит | покрывает только заголовок; пересчитывается на каждом хопе, потому что меняется TTL |
| Source / destination | 32 + 32 бита | IP-адреса; переписываются только NAT ([[ip-addressing-and-nat]]) |
| Options | 0–40 байт | запись маршрута, временные метки; используются редко, файрволы их часто отбрасывают |

- В заголовке нет портов. Они в заголовке TCP/UDP внутри нагрузки ([[tcp-segment-structure]], [[udp-in-depth]]); маршрутизатор, который читает порты (L4-балансировщик, NAT, файрвол), заглядывает дальше IP.
- Контрольная сумма не защищает нагрузку; у TCP и UDP свои контрольные суммы, а у Ethernet — CRC на каждый кадр.
- TTL — это счётчик хопов, а не время. Его настоящая задача — убивать пакеты, попавшие в петлю маршрутизации; traceroute использует его, чтобы узнать путь.

### Фрагментация
- У каждого канала есть MTU — самый большой IP-пакет, который он может передать (1500 в Ethernet, часто 1450 или меньше внутри туннелей VXLAN или VPN, 9001 с jumbo-кадрами в AWS).
- Если пакет больше MTU следующего канала и DF сброшен, маршрутизатор его разбивает: каждый фрагмент получает копию заголовка с тем же Identification, своё смещение и MF = 1, кроме последнего. Собирает пакет только получатель.
- Пример: 4000-байтный пакет (3980 байт данных) через MTU 1500 превращается во фрагменты по 1480 + 1480 + 1020 байт данных со смещениями 0, 185, 370.
- Почему её все избегают: потеря одного фрагмента — потеря всего пакета; сборка стоит памяти на получателе (и была классической целью DoS); фрагменты после первого не несут портов, поэтому файрволы, NAT и балансировщики не могут их классифицировать.
- Если DF установлен, а пакет слишком велик, маршрутизатор его отбрасывает и возвращает ICMP «Fragmentation Needed» (тип 3, код 4) с MTU следующего хопа. TCP использует это для определения MTU пути (path MTU discovery) и уменьшает размер сегмента ([[mss-mtu-pmtud]]). Linux по умолчанию ставит DF на TCP.
- Где фрагментация всё ещё кусается — это UDP: большой DNS-ответ или крупная датаграмма syslog/StatsD с нагрузкой больше 1472 байт (1500 − 20 IP − 8 UDP) фрагментируется или отбрасывается.

### Отличия IPv6
- Фиксированный заголовок 40 байт: version, traffic class, flow label, payload length, next header, hop limit, 128-битные адреса источника и назначения.
- Нет контрольной суммы заголовка (L2 и L4 уже проверяют), нет полей фрагментации в базовом заголовке, опции вынесены в цепочку заголовков расширения (`next header`).
- Маршрутизаторы никогда не фрагментируют. Отправитель обязан определять MTU пути; слишком большой пакет вызывает ICMPv6 «Packet Too Big». Минимальный MTU, который должен поддерживать любой канал IPv6, — 1280.
- Hop limit — это переименованный TTL. Flow label позволяет маршрутизаторам держать один поток на одном пути, не читая заголовки L4.

## Пример
Как увидеть поля заголовка и управлять фрагментацией из командной строки:
```bash
# подробный захват показывает TTL, id, флаги, общую длину и протокол каждого пакета
$ sudo tcpdump -nn -v -i eth0 icmp -c 2
IP (tos 0x0, ttl 64, id 40211, offset 0, flags [DF], proto ICMP (1), length 84)
    10.0.1.10 > 10.0.1.20: ICMP echo request, id 7, seq 1, length 64
IP (tos 0x0, ttl 64, id 5512, offset 0, flags [none], proto ICMP (1), length 84)
    10.0.1.20 > 10.0.1.10: ICMP echo reply, id 7, seq 1, length 64

# 1472 байта нагрузки + 8 ICMP + 20 IP = 1500: помещается с установленным DF
$ ping -c 1 -M do -s 1472 10.0.1.20
1480 bytes from 10.0.1.20: icmp_seq=1 ttl=64 time=0.41 ms
# на байт больше с DF: отказ локально вместо фрагментации
$ ping -c 1 -M do -s 1473 10.0.1.20
ping: local error: message too long, mtu=1500
# без DF ядро фрагментирует пакет; захват показывает две части с одинаковым id
$ ping -c 1 -M dont -s 3000 10.0.1.20
$ sudo tcpdump -nn -v -i eth0 'ip[6:2] & 0x3fff != 0'   # только фрагменты (MF установлен или offset > 0)
```

## Подводные камни
- Блокировать весь ICMP на файрволе. «Fragmentation Needed» не доходит, пакеты с DF молча исчезают, а соединения зависают после рукопожатия, когда отправляется первый полноразмерный сегмент ([[mss-mtu-pmtud]]).
- Несовпадение MTU в overlay-сетях: overlay в Docker Swarm, VXLAN в Kubernetes или VPN добавляют 50+ байт инкапсуляции. Если внутренний MTU всё ещё 1500, большие ответы зависают, а маленькие запросы проходят ([[docker-networking]]).
- Читать TTL в захвате как расстояние, не зная начального значения: TTL 57 при получении от Linux-хоста означает около 7 хопов, от Windows было бы 128 − 57.
- Считать, что UDP-датаграммы до 64 КБ — это нормально. Они фрагментируются, и потеря одного фрагмента теряет всё сообщение; держи нагрузку UDP меньше примерно 1200 байт, когда трафик идёт через интернет.
