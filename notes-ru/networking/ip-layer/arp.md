## Кратко
Чтобы отправить IP-пакет в канал Ethernet или Wi-Fi, отправителю нужен MAC-адрес следующего хопа. Его находит ARP: широковещательный запрос «у кого 10.0.1.20?» и unicast-ответ «10.0.1.20 находится по адресу bb:bb:…», который какое-то время хранится в таблице соседей ядра. Для назначения вне подсети хост делает ARP для шлюза по умолчанию, а не для удалённого IP. В ARP нет аутентификации, поэтому любой в том же сегменте L2 может соврать (отравление ARP, ARP poisoning). В IPv6 ARP заменён на Neighbor Discovery поверх ICMPv6.

## Основное
### Запрос и ответ
- **Запрос**: Ethernet-назначение `ff:ff:ff:ff:ff:ff` (широковещательный адрес), EtherType `0x0806`, тело «у кого *целевой IP*, ответь *IP отправителя* / *MAC отправителя*». Коммутатор рассылает его во все порты VLAN.
- **Ответ**: unicast обратно на MAC запросившего: «*целевой IP* находится по адресу *целевой MAC*». Все остальные хосты запрос отбрасывают.
- Целевой хост узнаёт соответствие запросившего из самого запроса, поэтому для обратного пути второй ARP не нужен.
- ARP живёт между L2 и L3: он передаётся прямо в Ethernet-кадрах, а не внутри IP. Он работает только в пределах одного широковещательного домена; маршрутизаторы его не пересылают.

### Кеш ARP (таблица соседей)
- Linux хранит записи в состояниях: `REACHABLE` (недавно подтверждена), `STALE` (ещё используется, перепроверяется при следующей отправке), `DELAY`/`PROBE` (идёт проверка), `FAILED` (ответа нет), `PERMANENT` (статическая).
- Запись остаётся `REACHABLE` примерно 15–45 секунд (случайное значение от `base_reachable_time`), затем становится `STALE`; TCP-трафик, на который приходят ACK, подтверждает её без новых ARP-запросов.
- Пока ARP не разрешён, ядро держит в очереди несколько пакетов для этого соседа; если ARP не удался, отправитель получает `EHOSTUNREACH` («No route to host») примерно через три секунды, даже в той же подсети.
- Большие плоские сети или узлы Kubernetes с тысячами подов могут переполнить таблицу (`neighbour table overflow` в `dmesg`); увеличь `net.ipv4.neigh.default.gc_thresh1/2/3`.

### Почему ARP делается для шлюза, а не для удалённого хоста
- MAC-адреса имеют смысл только в пределах одного канала. Веб-сервер в другой стране не находится в твоей LAN, поэтому на ARP для его IP никто бы не ответил.
- Ядро ищет маршрут ([[network-routing]]): `8.8.8.8 via 10.0.1.1`. Оно узнаёт MAC адреса `10.0.1.1` и отправляет туда кадр с IP назначения `8.8.8.8`. Затем маршрутизатор делает ARP на своём исходящем канале для своего следующего хопа ([[host-to-host-communication]]).
- Следствие: на хосте, который общается только с удалёнными сервисами, в кеше ARP есть лишь шлюз (и, может быть, DNS-сервер в LAN).

### Gratuitous ARP
- Непрошеное объявление собственного соответствия, отправленное как широковещательный запрос или ответ, где IP отправителя = целевой IP.
- Применение: поиск дублей IP при загрузке (если кто-то ответил, адрес занят); обновление кешей у всех после замены сетевой карты; **failover** виртуального IP. keepalived/VRRP, Pacemaker, Patroni с VIP и пары балансировщиков без облака переносят IP на резервную машину и рассылают gratuitous ARP, чтобы трафик переключился за миллисекунды.
- В публичных облаках это не работает: AWS, GCP и Azure игнорируют ARP-объявления гостевых машин, поэтому failover VIP идёт через API провайдера (переназначение Elastic IP или дополнительного IP).

### Отравление ARP (spoofing)
- Атакующий в том же сегменте L2 отправляет поддельные ответы, например «IP шлюза находится по моему MAC». Хосты принимают непрошеные ответы и обновляют кеш, поэтому трафик идёт через атакующего: это man in the middle, который может читать, менять или отбрасывать его.
- Защита: dynamic ARP inspection и DHCP snooping на управляемых коммутаторах, port security, статические записи ARP для критичных соседей, разбиение сети на маленькие VLAN и прежде всего шифрование всего на L7, чтобы MITM видел только TLS ([[tls-handshake-and-certificates]], [[mtls-and-service-to-service-auth]]).

### IPv6: Neighbor Discovery
- NDP делает работу ARP через ICMPv6: Neighbor Solicitation (отправляется на multicast-адрес solicited-node, а не широковещательно) и Neighbor Advertisement. Он также отвечает за обнаружение маршрутизаторов и автоконфигурацию адресов (SLAAC).
- Проблема доверия та же; RA guard и SEND существуют, но внедряются редко.

## Пример
Просмотр и проверка ARP на Linux-хосте:
```bash
# таблица соседей: шлюз и один локальный сосед
$ ip neigh show dev eth0
10.0.1.1 lladdr 52:54:00:00:01:01 REACHABLE
10.0.1.20 lladdr bb:bb:bb:00:00:14 STALE

# смотрим ARP в проводе, принудительно запуская новый поиск
$ sudo ip neigh flush dev eth0 to 10.0.1.20
$ sudo tcpdump -nn -e -i eth0 arp &
$ ping -c 1 10.0.1.20
aa:aa:aa:00:00:0a > ff:ff:ff:ff:ff:ff, ethertype ARP (0x0806), length 42:
  Request who-has 10.0.1.20 tell 10.0.1.10, length 28
bb:bb:bb:00:00:14 > aa:aa:aa:00:00:0a, ethertype ARP (0x0806), length 60:
  Reply 10.0.1.20 is-at bb:bb:bb:00:00:14, length 46

# проверка дубля IP перед назначением (код выхода 1 = кто-то ответил)
$ sudo arping -D -I eth0 -c 2 10.0.1.50
# объявить всем соседям переехавший VIP (то, что делает keepalived при failover)
$ sudo arping -U -I eth0 -c 3 10.0.1.100
```

## Подводные камни
- Сервер заменили новым с тем же IP, и часть клиентов минуту не может до него достучаться: в их кешах всё ещё старый MAC. Отправляй gratuitous ARP при старте (`arping -U`) или жди истечения записей.
- Два хоста с одним IP: соединения работают, потом рвутся, потом снова работают, потому что кеш ARP переключается между двумя MAC. Делай `arping -D` перед назначением статических адресов.
- `No route to host` для локального адреса — обычно неудавшийся ARP (хост выключен, неверный VLAN, файрвол хоста отбрасывает ARP), а не проблема маршрутизации.
- Доверять общей сети L2 (офисный Wi-Fi, плоский VLAN в дата-центре), потому что «она внутренняя». Для ARP-спуфинга нужен лишь ноутбук в этом сегменте.
