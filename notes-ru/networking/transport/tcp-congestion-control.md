## Кратко
Управление потоком защищает получателя; управление перегрузкой (congestion control) защищает **сеть**. Отправитель держит второе окно — **окно перегрузки** (congestion window, `cwnd`), которое никто не объявляет: отправитель выводит его из ACK и потерь. Байты в полёте ограничены `min(cwnd, rwnd)`. Новое соединение начинает с `cwnd` = 10 сегментов и удваивает его каждый RTT (**медленный старт**, slow start), пока не достигнет `ssthresh` или не потеряет пакет; затем окно растёт примерно на один сегмент за RTT (**избегание перегрузки**, congestion avoidance) и урезается при потере. Linux по умолчанию использует CUBIC, BBR — опция. Следствие для бэкендов: новые или простаивавшие соединения медленные, поэтому важно переиспользование.

## Основное
### Два окна
| | Управление потоком | Управление перегрузкой |
|---|---|---|
| Защищает | буфер получателя | роутеры и каналы между ними |
| Окно | `rwnd`, объявляется в каждом ACK ([[tcp-flow-control]]) | `cwnd`, хранится у отправителя и никому не сообщается |
| Сжимается, когда | приложение медленно читает | потери, ECN-метки, рост задержки (BBR) |
- Эффективное окно = `min(cwnd, rwnd)`. Пропускная способность ≈ `окно / RTT`.
- Оба считаются в байтах, а рассуждают о них обычно в сегментах размером MSS ([[mss-mtu-pmtud]]).

### Медленный старт
- Начальное окно (`initcwnd`) — **10 сегментов** (~14,6 КБ) начиная с RFC 6928 и Linux 2.6.39; до этого было 2–4.
- Каждый ACK увеличивает `cwnd` на один сегмент, поэтому окно **удваивается каждый RTT**: 10, 20, 40, 80…
- Медленный старт заканчивается, когда `cwnd` достигает **порога медленного старта** (slow start threshold, `ssthresh`, изначально очень большой), или при первой потере.
- Цена: при RTT 80 мс разгон окна с 14,6 КБ до 1 МБ занимает около 6 RTT ≈ 0,5 с. Ответу в 300 КБ на холодном соединении нужно ~5 кругов на любом канале; отсюда тёплые пулы и мультиплексирование в HTTP/2 ([[connection-establishment-cost]]).

### Избегание перегрузки (AIMD)
- Выше `ssthresh` окно `cwnd` растёт примерно на **один MSS за RTT**: аддитивный рост.
- При потере `cwnd` урезается: **мультипликативное уменьшение** (Reno делит пополам, CUBIC умножает на 0,7). AIMD заставляет конкурирующие потоки сходиться к справедливой доле.

### Обнаружение потерь и восстановление
- **Быстрая повторная передача** (fast retransmit): три дублирующих ACK для одного и того же номера последовательности значат, что один сегмент пропал, а следующие дошли. Отправитель повторяет его сразу, не дожидаясь таймера.
- **Быстрое восстановление** (fast recovery): после fast retransmit `ssthresh = cwnd / 2` (Reno), и `cwnd` продолжает с `ssthresh`, а не с 1. SACK точно сообщает отправителю, каких диапазонов не хватает.
- **Тайм-аут повторной передачи** (RTO): ACK нет совсем (в Linux минимум 200 мс, удваивается при каждой попытке). Это считается серьёзным: `ssthresh = cwnd / 2`, `cwnd` = 1 сегмент, снова медленный старт.
- **ECN**: вместо отбрасывания роутер помечает пакеты «congestion experienced»; получатель возвращает метку, и отправитель уменьшает `cwnd` без потерь и повторных передач. Нужна поддержка на обоих концах и на пути (`net.ipv4.tcp_ecn`).

### Алгоритмы
| Алгоритм | Сигнал | Заметки |
|---|---|---|
| Reno / NewReno | потери | классический AIMD, делит пополам при потере; плох на каналах с большим BDP |
| CUBIC | потери | по умолчанию в Linux с 2.6.19; окно — кубическая функция времени с последней потери: быстро возвращается, выходит на плато около прежнего максимума, затем зондирует выше |
| BBR (v1, v3) | измеренная пропускная способность и минимальный RTT | моделирует узкое место, а не ждёт потерь; намного лучше на каналах с потерями или длинных путях; может быть несправедлив к потокам CUBIC |
- Управление перегрузкой — решение **только отправителя**: сервер выбирает алгоритм для своих отдач, клиент — для своих. `sysctl net.ipv4.tcp_congestion_control`; BBR лучше всего работает с qdisc `fq`.

### Медленный старт после простоя
- Если соединение простаивает дольше одного RTO, Linux сбрасывает `cwnd` до начального окна (`net.ipv4.tcp_slow_start_after_idle = 1` по умолчанию), так как его оценка могла устареть.
- Поэтому соединение из пула, которое используется раз в несколько секунд, снова платит за медленный старт на каждом всплеске. Для чувствительного к задержкам внутреннего трафика в стабильной сети значение `0` сохраняет окно. Keep-alive и пулы ([[sockets-and-connection-pooling]], [[hikaricp-pool-sizing]]) в любом случае экономят рукопожатие.
- Linux кэширует `ssthresh` для каждого адресата, поэтому новое соединение с хостом, где недавно были потери, может выйти из медленного старта раньше.

## Пример
Просмотр и настройка управления перегрузкой на Linux-хосте.
```bash
# какой алгоритм используется и какие доступны
sysctl net.ipv4.tcp_congestion_control net.ipv4.tcp_available_congestion_control
# состояние соединения: cwnd, ssthresh, rtt, повторные передачи
ss -ti dst :5432
#   cubic wscale:7,7 rto:204 rtt:1.2/0.4 mss:1448 cwnd:10 ssthresh:7 retrans:0/3 ...

# сохранять cwnd на простаивающих соединениях из пула (чувствительный к задержкам внутренний трафик)
sysctl -w net.ipv4.tcp_slow_start_after_idle=0

# переключиться на BBR с qdisc fq (ядро 4.9+)
sysctl -w net.core.default_qdisc=fq
sysctl -w net.ipv4.tcp_congestion_control=bbr

# увеличенное начальное окно для одного маршрута (по умолчанию 10)
ip route change default via 10.0.0.1 dev eth0 initcwnd 20 initrwnd 20
```
В контейнере эти sysctl в основном относятся к сетевому пространству имён (network namespace), и их можно задать в спецификации pod или Compose ([[docker-networking]]).

## Подводные камни
- Медленные короткие ответы на холодных соединениях — это медленный старт, а не медленная сеть: считай круги (round trips), а не байты.
- Повторные передачи выглядят как случайные всплески задержки от 200 мс (RTO). Следи за `retrans` в `ss -ti` и `TcpRetransSegs` в `nstat` ([[network-debugging-toolkit]]).
- BBR на общем канале может душить соседние потоки CUBIC; проверь, прежде чем раскатывать на весь парк.
- Потери пакетов из-за перегруженного UDP-потока или крошечного буфера роутера урезают окно у каждого TCP-потока, а не у одного ([[udp-in-depth]]).
- Связанное: [[head-of-line-blocking]] — что потери делают с мультиплексированными потоками, [[tcp-vs-udp]] — общая картина.
