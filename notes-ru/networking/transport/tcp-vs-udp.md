## Кратко
TCP даёт соединение и упорядоченный надёжный поток байтов: рукопожатие, номера последовательности, подтверждения, повторную передачу, управление потоком (окно получателя) и управление перегрузкой (отправитель замедляется при потерях). UDP даёт независимые датаграммы с портом и контрольной суммой — и ничего больше. Почти всё, что пишет бэкенд-разработчик, едет поверх TCP (HTTP/1.1, HTTP/2, gRPC, Postgres, Kafka). UDP появляется в DNS, метриках, видео и HTTP/3 (QUIC), где приложение готово реализовать собственную надёжность или отбрасывать опоздавшие данные.

## Основное
### Сравнение
| Аспект | TCP | UDP |
|---|---|---|
| Соединение | да, тройное рукопожатие перед данными ([[tcp-handshake-and-connection-states]]) | нет; первый пакет уже с данными |
| Единица | поток байтов, нарезаемый ядром на сегменты | датаграмма, один `send()` = один пакет (до ~64 КБ, на практике держи меньше MTU ~1400 Б) |
| Порядок | гарантирован номерами последовательности | нет; пакеты могут прийти в другом порядке |
| Надёжность | ACK, повторная передача по таймауту или по тройному дублирующему ACK | нет; потери — проблема приложения |
| Управление потоком | получатель объявляет окно ([[tcp-flow-control]]) | нет |
| Управление перегрузкой | отправитель подстраивается под потери и задержку ([[tcp-congestion-control]]) | нет; некорректно ведущий себя UDP-отправитель может забить канал |
| Заголовок | 20–60 байт ([[tcp-segment-structure]]) | 8 байт ([[udp-in-depth]]) |
| Блокировка начала очереди (head-of-line blocking) | да: потерянный сегмент останавливает всё, что за ним | нет |
| Broadcast / multicast | нет | да |
| Типичное применение | HTTP, TLS, протоколы БД, Kafka, SSH | DNS, DHCP, NTP, StatsD, syslog, VoIP, игры, QUIC |

### Порты
| Диапазон | Название | Примечания |
|---|---|---|
| 0–1023 | общеизвестные (well-known) | для привязки нужен root или `CAP_NET_BIND_SERVICE`; 22, 53, 80, 443 |
| 1024–49151 | зарегистрированные (registered) | 5432 Postgres, 6379 Redis, 9092 Kafka, 8080 Tomcat, 4317/4318 OTLP |
| 32768–60999 | эфемерные (ephemeral, Linux) | выделяются исходящим соединениям; исчерпание — в [[tcp-handshake-and-connection-states]] |

- Сокет идентифицируется кортежем `(protocol, local ip, local port, remote ip, remote port)`, поэтому один серверный порт обслуживает тысячи клиентов; пространства портов TCP и UDP независимы.
- `bind()` на `127.0.0.1:8080` принимает только локальные соединения; на `0.0.0.0:8080` — с любого интерфейса. В Spring Boot это `server.address`. Внутри контейнера `127.0.0.1` — собственный loopback контейнера, поэтому сервис, привязанный к нему, недоступен с хоста и из других контейнеров: причина номер один для «порт открыт, но connection refused» ([[docker-networking]]).
- `SO_REUSEADDR` позволяет перезапущенному серверу привязаться, пока старые соединения находятся в `TIME_WAIT` (JVM по умолчанию ставит его на серверных сокетах).

### TCP: плюсы и минусы
- **Плюсы**: надёжная упорядоченная доставка; повторную передачу, управление потоком и перегрузкой берёт на себя ядро; проходит через любой файрвол и NAT; универсальные инструменты.
- **Минусы**: один RTT рукопожатия до данных, плюс TLS; пулы платят его один раз ([[connection-establishment-cost]], [[sockets-and-connection-pooling]]); новое соединение стартует медленно; Nagle и отложенный ACK могут добавлять задержки по 40 мс ([[nagle-and-delayed-ack]]); потерянный сегмент останавливает всё, что за ним ([[head-of-line-blocking]]); состояние соединения в ядре (буферы, очереди, `TIME_WAIT`) ограничивает, сколько клиентов держит одна машина.

### UDP: плюсы и минусы
- **Плюсы**: нет рукопожатия, 8-байтный заголовок, stateless-сервер, нет блокировки начала очереди, multicast; приложение само решает, что делать с потерями.
- **Минусы**: потери, перестановки и дубликаты — твоя проблема; нет управления перегрузкой; подделываемый адрес источника позволяет атаки с усилением; файрволы и NAT часто блокируют UDP или быстро забывают трансляции. Выбирай его, когда данные устаревают, опоздав (медиа, состояние игры, метрики), когда рукопожатие дороже нагрузки (DNS, NTP, [[dns-resolution]]) или когда строишь собственный транспорт (QUIC) — подробности в [[udp-in-depth]].

### Надёжность — не то же самое, что «нет потерь данных в приложении»
- TCP гарантирует доставку в буфер ядра собеседника, а не обработку приложением; падение после ACK теряет данные. Подтверждения на уровне приложения (Kafka `acks=all`, HTTP 2xx, идемпотентные retry) всё равно нужны ([[delivery-guarantees]], [[idempotency]]).
- В TCP нет границ сообщений: `read()` может вернуть половину сообщения или два сообщения. Каждый протокол поверх TCP определяет кадрирование (framing): HTTP `Content-Length`/chunked, кадры Kafka с префиксом длины, тип сообщения + длина в Postgres. В UDP каждая датаграмма — это сообщение, но её можно потерять или получить дважды.

### Вопросы в стиле собеседования
- «Как TCP обнаруживает потери?» По таймауту повторной передачи или по трём дублирующим ACK (fast retransmit); SACK позволяет повторить только недостающие диапазоны.
- «Управление потоком против управления перегрузкой?» Управление потоком защищает получателя, управление перегрузкой — сеть; отправитель использует меньшее из двух окон.
- «Бывает ли UDP надёжным?» Только если приложение делает его таким, как QUIC.

## Пример
Отправка одной и той же крошечной полезной нагрузки обоими способами из Java: поток, в который пишешь, против пакетов, которые отправляешь. StatsD — канонический случай «UDP подойдёт»: потеря 0,1% инкрементов счётчика допустима, блокировка потока обработки запроса при сбое метрик — нет.
```java
// TCP: подключиться один раз (рукопожатие), затем писать в поток; кадрирование — твоя забота
try (var socket = new Socket("metrics.internal", 9000);
     var out = new DataOutputStream(socket.getOutputStream())) {
    socket.setTcpNoDelay(true);               // избежать задержек Nagle на мелких записях
    byte[] msg = "esim.activations:1|c".getBytes(StandardCharsets.UTF_8);
    out.writeInt(msg.length);                  // префикс длины = граница сообщения
    out.write(msg);
    out.flush();
}

// UDP: соединения нет; каждая отправка — одна датаграмма, может потеряться или прийти не по порядку, никогда не блокируется на мёртвом собеседнике
try (var channel = DatagramChannel.open()) {
    var target = new InetSocketAddress("statsd.internal", 8125);
    var buf = ByteBuffer.wrap("esim.activations:1|c".getBytes(StandardCharsets.UTF_8));
    channel.send(buf, target);                 // отправил и забыл; счётчик StatsD может позволить себе потери
}
```

## Подводные камни
- Предположение, что один `write()` по TCP превращается в один `read()` на другой стороне. Это не так; реализуй кадрирование или используй протокол, в котором оно есть.
- Долгоживущие простаивающие TCP-соединения молча умирают на NAT-шлюзах и файрволах (обычно после 5–60 минут тишины). Включай keep-alive или ping на уровне приложения ([[tcp-handshake-and-connection-states]]).
- UDP-датаграммы больше MTU пути фрагментируются, и потеря одного фрагмента теряет всю датаграмму ([[mss-mtu-pmtud]]).
- Слишком маленькие буферы на каналах с высокой задержкой ограничивают пропускную способность TCP величиной `window / RTT`; приёмные буферы UDP переполняются молча (`UdpRcvbufErrors` в `nstat`).
- Связанные заметки: [[osi-and-tcp-ip-models]] — где находится транспортный уровень, [[building-tcp-udp-servers]] — минимальные серверы обоих видов, [[socket-management]] — как сервер обслуживает тысячи таких сокетов.
