## Кратко
Управление потоком (flow control) не даёт быстрому отправителю завалить медленного получателя. Каждый TCP-сегмент несёт **окно приёма** (receive window, `rwnd`) получателя: сколько ещё байт он может сейчас принять в буфер. Отправитель держит в полёте не больше этого числа неподтверждённых байт и сдвигает окно вперёд по мере прихода ACK. Когда принимающее приложение перестаёт вызывать `read()`, его буфер приёма сокета заполняется, объявленное окно падает до **нуля**, и отправитель останавливается и шлёт пробы окна, пока окно не откроется. Так медленный потребитель создаёт обратное давление (back-pressure) на быстрого производителя без единой строки кода в приложении.

## Основное
### Скользящее окно
- Поток байтов отправителя делится на четыре области: **отправлено и подтверждено** (можно освободить), **отправлено, но не подтверждено** (в полёте), **не отправлено, но разрешено** (доступное окно) и **пока не разрешено** (за пределами окна).
- Доступное окно = `rwnd − байты в полёте` (а на деле `min(rwnd, cwnd) − в полёте`, см. [[tcp-congestion-control]]).
- Каждый ACK делает две вещи: сдвигает левый край (байты подтверждены) и заново объявляет окно, что сдвигает правый край. Если приложение читает медленно, левый край двигается, а правый нет: окно **сжимается**.
- Поле окна находится в заголовке TCP ([[tcp-segment-structure]]) и видно как `win` в выводе [[tcpdump]].

### Масштабирование окна
- Поле заголовка 16-битное, поэтому окно ограничено 65 535 байтами: на пути со 100 мс это ≈ 5 Мбит/с, каким бы быстрым ни был канал.
- **Опция масштабирования окна** (window scale, RFC 7323) согласуется только в SYN и SYN-ACK: каждая сторона объявляет величину сдвига (0–14), и настоящее окно равно `field << shift`, до примерно 1 ГБ. Если промежуточное устройство вырезает опцию из рукопожатия, соединение навсегда застревает на 64 КБ.

### Произведение пропускной способности на задержку
- Чтобы канал был загружен, окно должно покрывать все байты, которые помещаются «в трубу»: **BDP = пропускная способность × RTT**. 1 Гбит/с × 50 мс = 6,25 МБ. При меньшем окне пропускная способность = `окно / RTT`.
- Внутри дата-центра (RTT ~0,2 мс) хватает маленьких буферов; репликации между регионами нужны окна в несколько мегабайт ([[latency-numbers]]).

### Окно и буфер приёма сокета
- Объявленное окно — это свободное место в **буфере приёма** соединения в ядре ([[socket-management]]). Его занимают байты, которые ядро подтвердило, а приложение ещё не прочитало (`Recv-Q` в `ss`).
- Linux **автоматически подстраивает** (autotuning) буфер между минимумом и максимумом `net.ipv4.tcp_rmem` (`4096 131072 6291456` по умолчанию в свежих ядрах) по измеренному RTT и скорости чтения. Часть буфера резервируется под накладные расходы ядра (`tcp_adv_win_scale`), поэтому окно меньше буфера.
- Явная установка `SO_RCVBUF` (в Java `setReceiveBufferSize`) **отключает автоподстройку** для этого сокета и ограничивает масштаб окна, выбранный при рукопожатии.

### Нулевое окно и пробы
- Когда буфер полон, получатель объявляет `win 0`. Отправитель останавливается и запускает **persist-таймер**, посылая **пробы окна** (window probe) с экспоненциальной задержкой, чтобы потерянное обновление окна не привело к взаимной блокировке соединения.
- Когда приложение читает, получатель отправляет **обновление окна** (window update). Чтобы избежать *синдрома глупого окна* (silly window syndrome: объявлять окно по нескольку байт и получать крошечные сегменты), получатель ждёт, пока освободится хотя бы один MSS или половина буфера ([[mss-mtu-pmtud]]); сторону отправителя описывает [[nagle-and-delayed-ack]].
- Нулевое окно — не ошибка: соединение может так висеть часами. Закончить это могут только тайм-ауты приложения, поэтому ставь тайм-ауты чтения на клиентах и `statement_timeout` в базе ([[failure-modes-and-timeouts]]).

### Обратное давление от начала до конца
- Медленный потребитель заполняет свой буфер приёма → нулевое окно → заполняется **буфер отправки** отправителя → `write()` у отправителя блокируется (или возвращает `EAGAIN` на неблокирующем сокете) → поток-производитель останавливается. Эта цепочка и есть встроенное в TCP [[backpressure-and-flow-control|обратное давление]].
- Конкретный случай: JDBC-клиент потоково читает большой результат запроса и медленно обрабатывает строки. Как только его окно закрывается, backend-процесс Postgres блокируется в `send()`, удерживая свой снимок (snapshot) и блокировки. `pg_stat_activity` показывает его с `wait_event = ClientWrite` ([[network-access-to-databases]]).
- То же самое происходит с HTTP-ответами, которые стримятся медленным мобильным клиентам.

## Пример
Потоковое чтение большого результата из Postgres: TCP даёт обратное давление, и heap не растёт, но запрос остаётся открытым, пока идёт обработка.
```java
@Transactional(readOnly = true)                       // pgJDBC стримит только внутри транзакции
public void exportActivations(PrintWriter out) {
    jdbcTemplate.setFetchSize(1_000);                  // читать пачками, а не весь результат в heap (отдельный бин JdbcTemplate)
    jdbcTemplate.query("""
            SELECT iccid, msisdn, activated_at
            FROM esim_activation
            WHERE activated_at >= now() - interval '30 days'
            """,
        rs -> {
            // если это медленно (например, запись в медленного HTTP-клиента), буфер приёма сокета заполняется,
            // rwnd падает до 0, и backend Postgres блокируется в send(): wait_event = ClientWrite
            out.println(rs.getString("iccid") + ";" + rs.getString("msisdn"));
        });
}
```
Проверить вживую можно через `ss -tmi dst :5432`: растущий `Recv-Q` на клиенте и полный `Send-Q` на хосте базы значат, что узкое место — читатель.

## Подводные камни
- Жёстко заданные `SO_RCVBUF`/`SO_SNDBUF` «для производительности» обычно делают хуже: они отключают автоподстройку. Вместо этого подними максимум `net.ipv4.tcp_rmem`/`tcp_wmem` (и `net.core.rmem_max`), когда каналы с большим BDP действительно недогружены.
- Долгие потоковые запросы с медленным потребителем держат открытым снимок Postgres и блокируют vacuum ([[postgres-vacuum-and-bloat]]). Для выгрузок буферизуй в файл или используй keyset-пагинацию.
- Пропускная способность, застрявшая на ~64 КБ за RTT, значит, что промежуточное устройство вырезало масштабирование окна.
- Связанное: [[tcp-congestion-control]] — окно на стороне отправителя, [[tcp-vs-udp]] — общая картина, [[sockets-and-connection-pooling]] — поведение буферов у соединений из пула.
