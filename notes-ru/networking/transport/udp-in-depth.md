## Кратко
UDP добавляет поверх IP ровно две вещи: порты (чтобы ядро могло отдать пакет нужному сокету) и необязательную контрольную сумму. Заголовок — 8 байт; нет соединения, порядка, повторной передачи, управления потоком и перегрузкой. Каждый `sendto()` — одна датаграмма, и каждый `recvfrom()` возвращает ровно одну датаграмму, поэтому границы сообщений сохраняются, чего TCP не делает. Этот минимализм делает UDP быстрым, stateless и дешёвым в обслуживании, но он же позволяет легко подделывать адрес и использовать UDP для атак с усилением (amplification).

## Основное
### Заголовок датаграммы
| Поле | Бит | Значение |
|---|---|---|
| Порт источника | 16 | порт отправителя, куда идут ответы; поверх IPv4 может быть 0, если ответ не нужен |
| Порт назначения | 16 | какой сокет получателя получает датаграмму |
| Длина | 16 | заголовок + полезная нагрузка в байтах, минимум 8; ограничивает нагрузку 65 507 байтами поверх IPv4 (65 535 − 8 − 20) |
| Контрольная сумма | 16 | покрывает псевдозаголовок (IP источника/назначения, протокол, длину), заголовок и нагрузку; необязательна поверх IPv4 (0 = не вычислялась), обязательна поверх IPv6; неверная сумма означает молчаливое отбрасывание |

- Адреса несёт IP-заголовок ([[ip-packet-structure]]); UDP добавляет только порты. Пара «IP + порт» на обоих концах позволяет многим приложениям делить один хост: ядро **демультиплексирует** каждую пришедшую датаграмму по порту назначения (а для подключённых сокетов — ещё и по источнику).

### Что даёт UDP и чего не даёт
- **Границы сообщений**: отправил 3 датаграммы по 100 байт — прочитал 3 датаграммы по 100 байт (если все дошли). Буфер меньше датаграммы обрезает её; остаток теряется.
- **Нет соединения**: один сокет обслуживает всех клиентов. Сервер вызывает `recvfrom()`, узнаёт адрес собеседника из результата и отвечает через `sendto()`. Нет `listen()`, нет `accept()`, нет состояния на клиента в ядре ([[building-tcp-udp-servers]]).
- **Нет порядка, гарантии доставки и подавления дубликатов**: датаграммы могут прийти с опозданием, в другом порядке, дважды или не прийти вовсе.
- **Нет управления потоком**: если приложение читает медленнее, чем приходят датаграммы, приёмный буфер сокета заполняется, и ядро отбрасывает новые (`UdpRcvbufErrors` в `nstat`).
- **Нет управления перегрузкой**: UDP-отправитель продолжает слать на полной скорости по перегруженному каналу. Протоколы поверх UDP (QUIC, WebRTC) обязаны реализовать своё.
- **Подключённый UDP**: вызов `connect()` на UDP-сокете только фиксирует собеседника по умолчанию. Пакеты не отправляются, но ядро отфильтровывает датаграммы от других источников и сообщает об ICMP «port unreachable» как `ECONNREFUSED` при следующем вызове ([[icmp-ping-traceroute]]).

### Плюсы и минусы
| Плюсы | Минусы |
|---|---|
| нет рукопожатия: первый пакет уже несёт данные | потери, перестановки и дубликаты — проблема приложения |
| 8-байтный заголовок, малая цена пакета по CPU и памяти | нет управления потоком и перегрузкой; легко перегрузить получателя или сеть |
| stateless-сервер обслуживает миллионы клиентов на одном сокете | NAT-трансляции для UDP быстро истекают (часто через 30–120 с простоя), поэтому долгоживущим потокам нужны keep-alive-пакеты |
| нет блокировки начала очереди ([[head-of-line-blocking]]) | многие корпоративные файрволы блокируют UDP, кроме DNS; QUIC откатывается на TCP |
| broadcast и multicast | адрес источника тривиально подделать: никакое рукопожатие не доказывает, кто отправитель |

### Где используется UDP
- **DNS**: запрос и ответ помещаются каждый в одну датаграмму ([[dns-resolution]]). Большие ответы выставляют бит TC (truncated), и клиент повторяет запрос по TCP.
- **QUIC / HTTP/3**: надёжность, порядок в пределах потока, управление перегрузкой и TLS 1.3, заново построенные в пространстве пользователя ([[http-1-1-vs-2-vs-3]]).
- **Медиа в реальном времени, VoIP** (RTP, WebRTC), игры: опоздавший кадр бесполезен, его повторная передача лишь добавляет задержку.
- **Метрики и логи**: StatsD (порт 8125), syslog. Потерять 0,1% инкрементов счётчика допустимо; заблокировать поток обработки запроса на мёртвом сервере метрик — нет ([[otel-metric-types]]).
- DHCP, NTP, WireGuard, оверлеи VXLAN в контейнерных сетях ([[docker-networking]]).

### Подделка адреса и усиление
- Раз рукопожатия нет, атакующий может поставить **IP жертвы** в поле источника. Все ответы уходят жертве.
- **Усиление** (amplification): выбирается сервис, ответ которого намного больше запроса. DNS-запросы `ANY` (до ~50×), NTP `monlist` (~500×) и открытый в интернет memcached по UDP (до ~50 000×) превращали небольшие ботнеты в терабитные флуды.
- Защита: провайдеры отбрасывают пакеты, чей источник не может быть из их сети (ingress filtering, BCP 38); серверы ограничивают частоту ответов (DNS RRL) и никогда не открывают memcached/Redis в интернет. QUIC запрещает серверу отправлять больше 3× полученных байт, пока адрес клиента не подтверждён.
- TCP неуязвим именно к этому трюку: на поддельный SYN уходит SYN-ACK примерно того же размера, и данные не идут, пока настоящий клиент не завершит рукопожатие.

## Пример
DNS-запрос на проводе (по одной датаграмме в каждую сторону, без рукопожатия) и счётчики отбрасываний, которые стоит проверить, когда UDP-сервис «теряет» данные.
```bash
$ sudo tcpdump -ni any -c 2 udp port 53
IP 10.0.0.5.53412 > 10.0.0.2.53: 4660+ A? example.com. (29)
IP 10.0.0.2.53 > 10.0.0.5.53412: 4660 1/0/0 A 93.184.215.14 (45)
# UDP-заголовок запроса, 8 байт: d0a4 0035 0025 xxxx
#   d0a4 = порт источника 53412, 0035 = порт назначения 53, 0025 = длина 37 (8 заголовок + 29 DNS), затем контрольная сумма

$ nstat -az | grep -E 'UdpInDatagrams|UdpRcvbufErrors|UdpInErrors'
UdpInDatagrams     1823344    0.0
UdpRcvbufErrors       5121    0.0   # приёмный буфер полон: приложение читало слишком медленно
UdpInErrors           5121    0.0
```

## Подводные камни
- Отправка датаграмм больше MTU пути: IP их фрагментирует, и потеря любого фрагмента теряет всю датаграмму. Держи полезную нагрузку в районе 1200–1400 байт ([[mss-mtu-pmtud]]).
- Маленький `SO_RCVBUF` на нагруженном приёмнике StatsD или syslog молча отбрасывает всплески. Увеличь его (и `net.core.rmem_max`) и следи за `UdpRcvbufErrors`.
- Считать «нет ошибки от `send()`» доставкой. Это значит лишь, что датаграмма дошла до локального ядра.
- В Docker `-p 8125:8125` пробрасывает только TCP. Для UDP нужно `-p 8125:8125/udp`.
- Связанные заметки: [[tcp-vs-udp]] — сравнение бок о бок, [[socket-management]] — как ядро ставит датаграммы в очередь сокета.
