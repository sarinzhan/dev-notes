## Кратко
HTTP/1.1 отправляет по одному запросу за раз в одном TCP-соединении, поэтому клиенты открывают много соединений и всё равно стоят в очереди. HTTP/2 сохраняет ту же семантику, но упаковывает всё в бинарные кадры и мультиплексирует много потоков (streams) в одном TCP-соединении со сжатием заголовков; его оставшаяся проблема — блокировка начала очереди (head-of-line blocking) на уровне TCP, когда один потерянный пакет останавливает все потоки. HTTP/3 переносит всё это на QUIC (UDP), где потоки независимы, рукопожатие объединено с TLS 1.3, а соединения переживают смену IP. Для Java-бэкенда: HTTP/2 — то, что требует gRPC и на чём по умолчанию говорит JDK `HttpClient`; HTTP/3 важен в основном на границе (CDN, браузер) и редко — между сервисами.

## Основное
### Сравнение
| | HTTP/1.1 (1997) | HTTP/2 (2015) | HTTP/3 (2022) |
|---|---|---|---|
| Транспорт | TCP | TCP (на практике с TLS) | QUIC поверх UDP, TLS 1.3 встроен |
| Формат | текст | бинарные кадры | бинарные кадры (потоки QUIC) |
| Запросов на соединение | 1 за раз (pipelining не используется) | много потоков, мультиплексированы | много потоков, независимы |
| Блокировка начала очереди | на уровне HTTP: медленный ответ блокирует следующий | на уровне TCP: потерянный пакет блокирует все потоки | нет между потоками |
| Сжатие заголовков | нет (повтор cookies в каждом запросе) | HPACK | QPACK |
| Рукопожатие до первого байта | TCP 1 RTT + TLS 1 RTT | так же | всего 1 RTT, 0-RTT при возобновлении |
| Server push | нет | да (устарел, удалён из браузеров) | да (не используется) |
| Приоритизация | клиент открывает 6 соединений и надеется | приоритеты/зависимости потоков | более простая схема приоритетов |
| Миграция соединения | нет | нет | да (connection ID, переживает переход Wi-Fi → 4G) |
| Совместимость с промежуточным оборудованием | поддерживается везде | нужен TLS (браузеры отказываются от h2c) | UDP/443 блокируется некоторыми корпоративными файрволами; откат на h2 |

### HTTP/2 подробно
- Одно TCP-соединение на источник; **потоки** несут пары запрос/ответ, каждый разбит на **кадры** (`HEADERS`, `DATA`, `SETTINGS`, `PING`, `RST_STREAM`, `GOAWAY`, `WINDOW_UPDATE`). Кадры разных потоков перемежаются.
- Окна **управления потоком** на поток и на соединение поверх окна TCP; медленный потребитель одного потока не останавливает остальные, пока не исчерпано окно соединения (для больших полезных нагрузок настраивай `initialWindowSize` в gRPC/Netty).
- **HPACK**: статическая таблица частых заголовков плюс динамическая таблица на соединение; второй запрос с тем же `authorization: Bearer ...` стоит несколько байт. Поэтому раздутые cookies на h2 вредят гораздо меньше.
- Согласование: расширение **ALPN** в рукопожатии TLS (`h2`) или `Upgrade: h2c` в открытом виде (используется gRPC внутри кластера, когда TLS делает mesh). Браузеры говорят на h2 только поверх TLS.
- `GOAWAY` — это graceful shutdown: сервер говорит «никаких новых потоков после id N», клиенты завершают текущие и переподключаются. Корректная обработка важна для rolling deployment ([[kubernetes-basics]]).
- Семантика не изменилась: методы, коды статуса, заголовки. Псевдозаголовки `:method`, `:path`, `:authority`, `:scheme` заменяют строку запроса; имена заголовков — в нижнем регистре.

### HTTP/3 и QUIC
- QUIC — транспорт в пространстве пользователя: надёжность, управление перегрузкой и потоки реализованы поверх UDP, поэтому он поставляется вместе с приложением (браузер, граница CDN), а не ждёт обновлений ядра.
- TLS 1.3 — часть рукопожатия, а не слой поверх: 1 RTT для нового соединения, 0-RTT для возобновлённого (допускает повтор, поэтому только для идемпотентных запросов).
- Восстановление после потерь на уровне потока: потерянный пакет задерживает только тот поток, чьи данные он нёс.
- Обнаружение: сервер объявляет `Alt-Svc: h3=":443"`; в следующий раз клиент пробует UDP и откатывается на TCP, если тот заблокирован. DNS-записи `HTTPS` могут объявить это раньше.
- Статус в Java: в JDK `HttpClient` нет HTTP/3 по состоянию на Java 25; в Netty есть инкубаторный модуль QUIC; на практике h3 завершается на nginx/Caddy/Envoy или CDN ([[cdn]]), а твой сервис видит h2 или h1.1.

### Что это значит для бэкенд-сервиса
- Балансировщики часто говорят с клиентами на h2, а с upstream — на h1.1; проверь, не понижается ли версия у твоего gRPC-трафика ([[load-balancers-l4-vs-l7]]).
- С HTTP/2 «размер пула соединений» значит меньше (одно соединение несёт 100+ параллельных потоков, `SETTINGS_MAX_CONCURRENT_STREAMS`), но одно соединение означает одно окно TCP и одно ядро CPU на сервере для этого клиента; gRPC-клиенты к нагруженному сервису иногда намеренно открывают несколько каналов ([[grpc-and-protobuf]]).
- h2 на одном соединении делает неэффективной клиентскую балансировку через DNS round-robin: все потоки идут на тот один IP, к которому открыто соединение ([[dns-resolution]]).
- Spring Boot: `server.http2.enabled=true` работает с Tomcat (нужен TLS или h2c), Jetty, Undertow и Netty (WebFlux); `RestClient` в Spring поверх клиента JDK использует h2, если сервер его предлагает ([[rest-clients]]).

- Мог бы QUIC нести протоколы баз данных? Он убрал бы блокировку начала очереди между параллельными запросами и позволил бы миграцию соединения, но драйверы баз мало мультиплексируют (одна транзакция на соединение), большая часть трафика остаётся внутри дата-центра с крошечными потерями, а пользовательский стек QUIC стоит CPU. Поэтому базы остаются на TCP; выигрыш был бы в основном для клиентов в мобильных сетях с потерями ([[head-of-line-blocking]], [[database-wire-protocols]]).

## Пример
Проверка того, что сервер реально согласует. Вывод показывает версию протокола, результат ALPN и объявлен ли h3.
```bash
$ curl -sI --http2 https://api.beeline.kg/actuator/health -w '\nprotocol=%{http_version}\n'
HTTP/2 200
content-type: application/vnd.spring-boot.actuator.v3+json
alt-svc: h3=":443"; ma=86400          # сервер принял бы HTTP/3 на UDP 443
protocol=2

$ curl -sI --http3-only https://api.beeline.kg/actuator/health -w 'protocol=%{http_version}\n'
protocol=3                           # работает только с curl, собранным с библиотекой QUIC

$ openssl s_client -connect api.beeline.kg:443 -alpn h2,http/1.1 </dev/null 2>/dev/null | grep ALPN
ALPN protocol: h2
```
Включение h2 в Spring Boot за TLS:
```yaml
server:
  http2:
    enabled: true
  ssl:
    bundle: server            # SSL bundles в Spring Boot 3.1+
```

## Подводные камни
- Включение h2 не делает медленный бэкенд быстрее; оно убирает очередь на уровне соединения у клиента, и больше ничего.
- Одно h2-соединение к одному upstream прибивает весь трафик к одному поду за L4-балансировщиком; для gRPC используй L7-балансировщик или балансировку на стороне клиента.
- Корпоративный файрвол, блокирующий UDP/443, молча понижает h3 до h2; ожидай этого отката и не отлаживай «медленный» путь как баг.
- Данные 0-RTT в HTTP/3 (и early data в TLS 1.3) можно воспроизвести повторно; серверы должны отклонять неидемпотентные запросы в early data.
- Имена заголовков в h2/h3 — в нижнем регистре; код, делающий `headers.get("X-Request-ID")` с регистрозависимой map, ломается, когда прокси повышает версию.
- Связанные заметки: [[tcp-vs-udp]] — почему QUIC понадобился UDP, [[tls-handshake-and-certificates]] — ALPN и рукопожатие TLS 1.3, на котором он едет.
