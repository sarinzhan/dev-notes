## Кратко
HTTP — протокол запрос/ответ без состояния поверх надёжного потока байтов: стартовая строка, заголовки, пустая строка, необязательное тело. Метод говорит, чего ты хочешь, заголовки — как это интерпретировать, код статуса — что произошло. Именно безопасные и идемпотентные методы делают возможными retry, кеширование и прокси; всё остальное — соглашения. Эта заметка — о самом протоколе; соглашения REST, дизайн URL, этикет кодов статуса и CORS в Spring живут в [[rest-and-http]] и здесь не повторяются.

## Основное
### Анатомия сообщения
```
POST /api/v1/esims/8999600000000000001/activations HTTP/1.1      <- строка запроса
Host: api.beeline.kg                                              <- обязателен в 1.1, выбирает виртуальный хост
Content-Type: application/json
Content-Length: 27
Idempotency-Key: 0b1f0a3e-...                                     <- свой заголовок, через дефис, регистр не важен
                                                                  <- пустая строка завершает заголовки
{"channel":"MY_BEELINE_APP"}                                      <- тело, ровно Content-Length байт
```
- Заголовки нечувствительны к регистру, значения — текст, дубликаты склеиваются через запятую (кроме `Set-Cookie`). HTTP/2 переводит их в нижний регистр и хранит как бинарные поля, поэтому `X-Request-ID` и `x-request-id` нужно обрабатывать одинаково.
- Длина тела задаётся через `Content-Length`, через `Transfer-Encoding: chunked` (поток кусков с префиксом длины, последний кусок `0`) или закрытием соединения (только 1.0). Несовпадение длины и фактических байтов — классическая причина «зависаний» и request smuggling.
- Запрос без тела (GET, DELETE) формально может его нести; серверы в основном его игнорируют.

### Методы: суть в безопасности и идемпотентности
- **Безопасные** (safe: GET, HEAD, OPTIONS): изменение состояния не предполагается; кеши и краулеры могут вызывать их свободно.
- **Идемпотентные** (idempotent: GET, HEAD, PUT, DELETE, OPTIONS): N одинаковых запросов дают тот же эффект, что и один. Клиент, прокси или балансировщик могут повторить их после таймаута, ни у кого не спрашивая. POST и PATCH по определению не идемпотентны; повторяй их только с ключом идемпотентности ([[idempotency]]).
- `HEAD` возвращает заголовки GET без тела (дешёвая проверка существования/размера); `OPTIONS` перечисляет разрешённые методы и несёт CORS preflight ([[cookies-sessions-and-cors]]).

### Классы статусов и те, что важны для retry
| Класс | Значение | Повторять? |
|---|---|---|
| 1xx | информационные (`100 Continue`, `101 Switching Protocols` для WebSocket) | неприменимо |
| 2xx | успех; `202 Accepted` = работа поставлена в очередь, опроси позже | нет |
| 3xx | редирект; `304 Not Modified` — это попадание в кеш ([[http-caching]]) | следовать, но не для POST, кроме 307/308 |
| 4xx | ошибка клиента; повторять стоит только `408`, `425`, `429` (с backoff) | в основном нет |
| 5xx | ошибка сервера; `502/503/504` на шлюзе обычно временные | да, с backoff и бюджетом, только для идемпотентных запросов |

### Заголовки, которые нужно знать по имени
| Заголовок | Направление | Назначение |
|---|---|---|
| `Host` | запрос | выбор виртуального хоста; обязателен в HTTP/1.1 |
| `Content-Type` / `Accept` | оба / запрос | медиатип тела / согласование содержимого |
| `Content-Length`, `Transfer-Encoding` | оба | кадрирование |
| `Connection: keep-alive` / `close` | оба | в 1.1 по умолчанию keep-alive; `close` принудительно закрывает |
| `Authorization: Bearer ...` | запрос | учётные данные ([[authentication-vs-authorization]]) |
| `Cache-Control`, `ETag`, `If-None-Match` | оба | кеширование ([[http-caching]]) |
| `Location` | ответ | где находится созданный ресурс или цель редиректа |
| `Retry-After` | ответ | с 429/503, секунды или дата |
| `X-Forwarded-For`, `X-Forwarded-Proto`, `Forwarded` | запрос | исходные IP/схема клиента, добавляются прокси ([[reverse-proxy-nginx-basics]]) |
| `traceparent` | запрос | W3C trace context ([[distributed-tracing]]) |

### Постоянные соединения и pipelining
- HTTP/1.0 закрывал соединение после каждого ответа. HTTP/1.1 по умолчанию держит его открытым (keep-alive); один запрос за раз на соединение, поэтому клиенты открывают несколько (браузеры: 6 на хост). Pipelining (отправка следующего запроса до ответа на предыдущий) есть в спецификации, но отключён везде, потому что ответы должны возвращаться по порядку.
- Мультиплексирование в одном соединении — то, что добавляет HTTP/2 ([[http-1-1-vs-2-vs-3]]). Лимиты keep-alive на стороне сервера в Spring Boot/Tomcat: `server.tomcat.keep-alive-timeout`, `server.tomcat.max-keep-alive-requests`.

### Отсутствие состояния
- Протокол не несёт памяти между запросами; каждый запрос должен быть самодостаточным. Состояние сессии надстраивается через cookies ([[cookies-sessions-and-cors]]) или токены ([[jwt-authentication]]). Именно поэтому HTTP-сервисы масштабируются горизонтально за балансировщиком.

## Пример
Наблюдение за «сырым» протоколом через `curl -v` к Spring Boot сервису — самый быстрый способ увидеть заголовки, которые прячет браузер.
```bash
$ curl -sv -X POST https://api.beeline.kg/api/v1/esims/8999600000000000001/activations \
     -H 'Content-Type: application/json' -H 'Idempotency-Key: 0b1f0a3e-7c1e-4d1a-9f0a-1a2b3c4d5e6f' \
     -d '{"channel":"MY_BEELINE_APP"}'
> POST /api/v1/esims/8999600000000000001/activations HTTP/2
> Host: api.beeline.kg
> user-agent: curl/8.6.0
> accept: */*
> content-type: application/json
> idempotency-key: 0b1f0a3e-7c1e-4d1a-9f0a-1a2b3c4d5e6f
> content-length: 28
>
< HTTP/2 202
< content-type: application/json
< location: /api/v1/esims/8999600000000000001/activations/7f3c
< retry-after: 2
< x-request-id: 4a8d0d6e
<
{"status":"PENDING","activationId":"7f3c"}
```
`202 + Location + Retry-After` — стандартная форма для «принято, опрашивай здесь»; тот же запрос с тем же `Idempotency-Key` должен вернуть тот же `activationId`, а не запустить второй процесс.

## Подводные камни
- Возврат `200` с ошибкой внутри тела; клиенты, прокси и мониторинг ориентируются на коды статуса.
- Повтор POST по таймауту, потому что «сервер, наверное, лежал»: запрос мог быть обработан. Таймауты неоднозначны; вслепую повторять безопасно только идемпотентные запросы.
- Забытый `Host` при ручной работе с HTTP (`nc`, сырые сокеты): серверы HTTP/1.1 отвечают `400`.
- Отсутствующий или неверный `Content-Length` заставляет собеседника ждать новых байтов до таймаута чтения; chunked-кодирование без завершающего куска `0` делает то же самое.
- Заголовки сами по себе не являются безопасным каналом для секретов; они защищены только внутри TLS ([[tls-handshake-and-certificates]]) и попадают в журналы прокси, если их не вычищать.
- Связанные заметки: [[rest-and-http]] — дизайн API поверх всего этого, [[spring-mvc-request-lifecycle]] — как Spring разбирает запрос.
