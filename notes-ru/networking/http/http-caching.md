## Кратко
HTTP-кеширование управляется сервером через заголовки ответа: `Cache-Control` говорит, кто может хранить ответ и как долго, `ETag`/`Last-Modified` позволяют клиенту дёшево перепроверить актуальность условным запросом, который возвращает `304 Not Modified`, а `Vary` говорит, какие заголовки запроса меняют ответ. Браузеры, обратные прокси и CDN следуют одним и тем же правилам, поэтому один правильный набор заголовков заставляет работать каждый слой; один ошибочный `Cache-Control: public` на эндпоинте с данными конкретного пользователя приводит к утечке через общий кеш. Стратегии кеширования на стороне приложения (cache-aside, write-through, инвалидация) — отдельная тема, она в [[caching]].

## Основное
### Свежесть: `Cache-Control`
| Директива | Значение |
|---|---|
| `max-age=N` | свежий N секунд с момента ответа; отдавать, не обращаясь к источнику (origin) |
| `s-maxage=N` | то же, но только для общих кешей (CDN, прокси); там переопределяет `max-age` |
| `no-cache` | можно хранить, но перед каждым использованием нужно перепроверить (название вводит в заблуждение) |
| `no-store` | никогда нигде не хранить: токены, персональные данные, страницы оплаты |
| `private` | хранить может только браузер конечного пользователя; общие кеши — нет |
| `public` | общие кеши могут хранить даже ответы с `Authorization` |
| `must-revalidate` | после устаревания не отдавать устаревшую копию ни во время перепроверки, ни при ошибке |
| `stale-while-revalidate=N` | отдавать устаревшую копию N с, пока в фоне загружается свежая |
| `stale-if-error=N` | отдавать устаревшую копию, если источник возвращает 5xx; дешёвая устойчивость на CDN |
| `immutable` | никогда не перепроверять в пределах `max-age`; для ресурсов с хешем содержимого в имени (`app.3f9c1a.js`) |

- Эвристическое кеширование: без `Cache-Control` и `Expires` кеши могут угадать время жизни по `Last-Modified` (обычно 10% от возраста). Всегда отправляй явную политику в API, обычно `no-store` или `private, max-age=0`.
- `Expires` — форма HTTP/1.0 с абсолютной датой; когда есть оба, побеждает `Cache-Control`.
- По умолчанию кешируются только безопасные методы; ответ на `POST` кешируется только с явными заголовками и на практике почти никогда.

### Валидация: условные запросы
- **`ETag`**: непрозрачный идентификатор версии, сильный (`"3f9c1a"`) или слабый (`W/"3f9c1a"`, семантически равен, байты могут отличаться). Клиент отправляет его обратно в `If-None-Match`; сервер отвечает `304` без тела, если ничего не изменилось. Дёшево вычисляется из `updated_at`, столбца версии или хеша тела.
- **`Last-Modified`** + `If-Modified-Since`: точность в одну секунду, нормально для файлов, слабо для строк, обновляемых несколько раз в секунду.
- Те же валидаторы защищают запись: `If-Match: "3f9c1a"` в PUT/PATCH даёт оптимистичную конкурентность поверх HTTP и возвращает `412 Precondition Failed`, если кто-то другой изменил ресурс раньше ([[jpa-locking]] делает то же самое на уровне базы данных).
- `304` всё равно стоит round trip; выигрыш — в трафике и работе сервера, а не в задержке. Round trip убирает именно `max-age`.

### `Vary` и ключи кеша
- Кеш строит ключ записи из метода + URL. Если ответ зависит от заголовка запроса, об этом нужно сказать: `Vary: Accept-Encoding` (gzip против identity), `Vary: Accept-Language`, `Vary: Origin` для ответов CORS ([[cookies-sessions-and-cors]]).
- `Vary: Authorization` или `Vary: Cookie` фактически делают ответ некешируемым в общих кешах, что для персонализированных данных обычно правильно; предпочитай `private`.
- `Vary: *` означает «никогда не отдавать из кеша».

### Где находятся кеши
1. Кеш браузера (на пользователя): достаточно `private`.
2. Обратный прокси / `proxy_cache` в nginx ([[reverse-proxy-nginx-basics]]): учитывает `s-maxage`, может добавить `stale-while-revalidate`.
3. Граница CDN ([[cdn]]): те же правила плюс API для сброса (purge) и подписанные URL; правильное место для `public, s-maxage=3600` на данных вроде каталога.
4. Кеш ответов в API-шлюзе: обычно настраивается по маршруту, игнорирует заголовки; опасен для всего, что зависит от пользователя.

### Сторона Spring
- `ResponseEntity.ok().cacheControl(CacheControl.maxAge(10, MINUTES).cachePublic()).eTag(version).body(dto)`.
- `WebRequest.checkNotModified(etag)` в контроллере возвращает `true` и сам готовит `304`, когда совпадает `If-None-Match`, так что сериализацию можно пропустить.
- `ShallowEtagHeaderFilter` хеширует тело каждого ответа, чтобы получить ETag: экономит трафик, но не CPU и не работу базы данных. Нормально для маленьких API, неправильно для больших или потоковых ответов.
- Статические ресурсы: `spring.web.resources.cache.cachecontrol.max-age=365d` плюс имена файлов с хешем содержимого через resource chain.

## Пример
Эндпоинт каталога тарифов: публичные данные, меняются несколько раз в день, читаются при каждом запуске приложения. Можно безопасно кешировать на CDN 10 минут, а затем перепроверять по ETag.
```java
@GetMapping("/api/v1/tariffs")
public ResponseEntity<List<TariffDto>> tariffs(WebRequest request) {
    CatalogVersion v = catalog.currentVersion();            // один дешёвый запрос: max(updated_at)
    String etag = "\"" + v.hash() + "\"";
    if (request.checkNotModified(etag)) {
        return null;                                         // Spring пишет 304 + ETag, без тела
    }
    return ResponseEntity.ok()
            .eTag(etag)
            .cacheControl(CacheControl.maxAge(10, TimeUnit.MINUTES)
                    .cachePublic()
                    .staleWhileRevalidate(60, TimeUnit.SECONDS))
            .header(HttpHeaders.VARY, "Accept-Language")
            .body(catalog.list(request.getLocale()));
}
```
Как это выглядит в сети при втором вызове:
```bash
$ curl -sI https://api.beeline.kg/api/v1/tariffs -H 'If-None-Match: "9c4e12"' -H 'Accept-Language: ru'
HTTP/2 304
etag: "9c4e12"
cache-control: max-age=600, public, stale-while-revalidate=60
vary: Accept-Language
age: 143                       # ответ отдал CDN; прошло 143 с из окна в 600 с
```
Эндпоинт для конкретного абонента, например `/api/v1/subscribers/{msisdn}/balance`, получает противоположную политику: `Cache-Control: no-store` и без ETag, чтобы ничто между приложением и сервисом не хранило копию.

## Подводные камни
- `public` на ответе, зависящем от `Authorization`: CDN отдаёт данные пользователя A пользователю B. Для всего, что за аутентификацией, по умолчанию используй `private` или `no-store`.
- Забытый `Vary: Accept-Encoding` на кеширующем прокси: клиент, не умеющий распаковывать gzip, получает сжатое тело.
- ETag, вычисленный из сериализованного тела через `ShallowEtagHeaderFilter`, всё равно выполняет полный запрос и сериализацию; используй столбец версии.
- `no-cache`, понятый как «не кешировать»: он кеширует и перепроверяет. Для секретов нужен `no-store`.
- Длинный `max-age` на ресурсах без хеша в имени или на меняющемся JSON: единственные решения — версионирование URL или сброс CDN, и оба стоит заложить в дизайн заранее.
