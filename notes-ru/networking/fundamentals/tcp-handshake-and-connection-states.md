## Кратко
TCP-соединение открывается последовательностью SYN, SYN-ACK, ACK (один round trip) и закрывается парой FIN/ACK в каждом направлении. Сторона, которая закрывает первой, держит четвёрку адресов в `TIME_WAIT` 60 секунд в Linux, поэтому клиенту, открывающему новое соединение на каждый запрос, не хватает портов. Keep-alive-пробы обнаруживают мёртвых собеседников на простаивающих соединениях; без них полуоткрытое соединение (одна сторона упала, другая всё ещё считает себя подключённой) может подвесить поток, пока запись наконец не провалится. `ss -tan` показывает все эти состояния, и это первое, что стоит запустить, когда «соединения копятся».

## Основное
### Открытие: тройное рукопожатие
1. Клиент отправляет `SYN` со случайным начальным номером последовательности (ISN) и опциями: MSS, масштаб окна, SACK permitted, временные метки.
2. Сервер отвечает `SYN-ACK`: свой ISN и подтверждение ISN клиента + 1. Соединение находится в **очереди SYN** сервера (`SYN_RECV`).
3. Клиент отправляет `ACK`; соединение переходит в **очередь accept** (`ESTABLISHED`), пока приложение не вызовет `accept()`.
- Данные могут идти только после шага 3 (кроме TCP Fast Open, который включают редко). Цена: один RTT. TLS добавляет ещё один ([[tls-handshake-and-certificates]]).
- Если очередь accept заполнена (`somaxconn`, `server.tomcat.accept-count` в Tomcat), ядро отбрасывает ACK или SYN; клиенты видят таймауты, а не отказы. Следи за `ListenOverflows` в `nstat`.
- **SYN flood**: атакующий шлёт SYN без ACK, заполняя очередь SYN. Linux отвечает SYN cookies, когда очередь заполнена (`net.ipv4.tcp_syncookies=1`).

### Закрытие: четырёхстороннее рукопожатие
1. Активно закрывающая сторона отправляет `FIN` → `FIN_WAIT_1`.
2. Пассивная сторона отвечает ACK → активная сторона в `FIN_WAIT_2`, пассивная — в `CLOSE_WAIT`, пока её приложение не вызовет `close()`.
3. Пассивная сторона отправляет свой `FIN` → `LAST_ACK`.
4. Активно закрывающая сторона отвечает ACK и переходит в `TIME_WAIT` на 2×MSL (60 с в Linux), затем в `CLOSED`.
- `TIME_WAIT` существует для того, чтобы запоздавшие сегменты старого соединения нельзя было принять за новое соединение с той же четвёркой адресов, и чтобы последний ACK можно было отправить повторно, если он потерялся.
- `RST` — резкая альтернатива: отправляется, когда на порту никто не слушает («connection refused»), когда приходят данные для закрытого сокета или когда `SO_LINGER` равен нулю. У отправителя RST нет `TIME_WAIT`.

### Состояния, которые встречаются в продакшене
| Состояние в `ss` | Значение | Если их много, это значит |
|---|---|---|
| `LISTEN` | серверный сокет ждёт | норма |
| `SYN-SENT` | клиент отправил SYN, ответа пока нет | файрвол отбрасывает, хост лежит, неверный маршрут |
| `SYN-RECV` | сервер получил SYN, ждёт ACK | SYN flood, или ACK клиента отбрасывается |
| `ESTAB` | данные могут идти | норма; считай их для подбора размеров пулов |
| `CLOSE-WAIT` | собеседник закрыл, **наше приложение не вызвало close()** | утечка соединений в твоём коде (тело ответа не закрыто, пул не получает соединения обратно) |
| `FIN-WAIT-2` | мы закрыли, ждём FIN собеседника | приложение собеседника медленно закрывает; ограничено `tcp_fin_timeout` |
| `TIME-WAIT` | мы закрыли первыми, защитные 60 с | клиент без пула соединений или прокси, закрывающий соединение к upstream на каждый запрос |

### Keep-alive и полуоткрытые соединения
- **Полуоткрытое** (half-open): одна сторона исчезла (пропало питание, под убит, истекла запись NAT), не отправив FIN или RST. Другая сторона ничего не знает, пока не запишет данные и запись не останется неподтверждённой (тогда по умолчанию она повторяет передачу ~15 минут, прежде чем сдаться, `tcp_retries2`). Читатель, заблокированный в `read()`, может ждать вечно.
- **TCP keep-alive** (`SO_KEEPALIVE`): после `tcp_keepalive_time` простоя (по умолчанию 7200 с, слишком долго) отправлять пробы каждые `tcp_keepalive_intvl`, сдаться после `tcp_keepalive_probes`. Для соединений с БД из пула и долгоживущих связей Kafka/gRPC ставь десятки секунд. В HikariCP есть `keepaliveTime`, в JDBC-драйвере Postgres — `tcpKeepAlive=true` ([[hikaricp-pool-sizing]]).
- **HTTP keep-alive** — другое: переиспользование одного TCP-соединения для нескольких запросов ([[http-fundamentals]]). gRPC и HTTP/2 добавляют собственные кадры `PING`.
- Единственная настоящая защита — таймаут на каждом блокирующем сетевом вызове ([[failure-modes-and-timeouts]]): таймаут подключения, таймаут чтения, а для пулов — валидация/максимальное время жизни.

### Эфемерные порты и исчерпание из-за `TIME_WAIT`
- Клиентское соединение берёт порт из эфемерного диапазона (`net.ipv4.ip_local_port_range`, ~28k портов по умолчанию, 32768–60999). Каждая четвёрка в `TIME_WAIT` удерживает свой порт для того же назначения 60 с, поэтому ~470 новых соединений в секунду к одному upstream — потолок без переиспользования.
- Решения по порядку: пул соединений / keep-alive ([[sockets-and-connection-pooling]]), `net.ipv4.tcp_tw_reuse=1` (безопасно для исходящих соединений), расширение диапазона портов. `tcp_tw_recycle` удалён в Linux 4.12; не ищи его.

## Пример
Диагностика утечки в клиенте на Spring Boot. Растущий `CLOSE-WAIT` на нашей стороне в сторону upstream — всегда наш баг: собеседник закрыл, а мы — нет.
```bash
$ ss -tan state close-wait '( dport = :443 )' | head
Recv-Q Send-Q Local Address:Port   Peer Address:Port
     1      0 10.20.5.2:41722      52.18.7.90:443
     1      0 10.20.5.2:41730      52.18.7.90:443
...
$ ss -tan state close-wait | wc -l
812                                   # растёт ~1/с: один утёкший сокет на вызов

$ ss -tan | awk 'NR>1 {print $1}' | sort | uniq -c
   812 CLOSE-WAIT
    42 ESTAB
    10 LISTEN
   318 TIME-WAIT                      # отдельная проблема: короткоживущие исходящие соединения
```
Типичная причина в Java: чтение `HttpResponse<InputStream>` или потокового тела `RestClient` без закрытия, либо перехват исключения до того, как тело прочитано, так что соединение из пула никогда не возвращается. Каждый такой сокет остаётся в `CLOSE-WAIT` до завершения JVM.

## Подводные камни
- Длительность `TIME_WAIT` в Linux не настраивается (она зафиксирована на 60 с); настоящее решение — переиспользование соединений.
- Балансировщик или NAT с idle timeout короче времени простоя в твоём пуле даёт «connection reset by peer» на первом запросе после затишья. Ставь `maxLifetime`/`idleTimeout` пула ниже таймаута инфраструктуры (AWS NLB: 350 с; многие файрволы: 300 с).
- `SO_LINGER=0`, чтобы «избежать TIME_WAIT», отправляет RST и может выбросить неотправленные данные у собеседника; собеседник видит «connection reset» вместо чистого закрытия.
- Сеть контейнеров добавляет слой NAT (`docker-proxy` или DNAT в iptables); полуоткрытое соединение к перезапущенному контейнеру обнаруживается только при следующей записи ([[docker-fundamentals]]).
- Связанные заметки: [[tcp-vs-udp]] — зачем вообще нужно рукопожатие, [[linux-networking]] — набор инструментов `ss`/`tcpdump` вокруг него.
