## Кратко
Любому сообщению между двумя машинами нужны три адреса: MAC-адрес, чтобы пересечь один канал, IP-адрес, чтобы пересечь сети, и порт, чтобы попасть в нужный процесс. Если IP назначения в твоей подсети, хост отправляет кадр прямо ему; иначе он отправляет кадр на MAC шлюза по умолчанию (default gateway), а IP-заголовок по-прежнему указывает конечное назначение. Коммутаторы пересылают кадры по MAC и никогда не трогают IP; маршрутизаторы снимают кадр, уменьшают TTL, выбирают следующий хоп и собирают новый кадр. IP-адреса и порты остаются теми же от начала до конца (если их не переписывает NAT); MAC-адреса меняются на каждом маршрутизаторе.

## Основное
### Клиент-сервер в одном абзаце
- **Сервер** — процесс, который владеет слушающим сокетом на известных IP и порту и ждёт; **клиент** — процесс, который открывает к нему соединение с эфемерного порта. Твой Spring Boot сервис — сервер для своих HTTP-клиентов и клиент для Postgres, Kafka и каждого REST API, который он вызывает ([[sockets-and-connection-pooling]]).
- Такое разделение нужно, чтобы дорогая или общая работа (данные, бизнес-правила) жила в одном месте, а много тонких клиентов её переиспользовали. Цена — каждый вызов теперь пересекает сеть с задержками, потерями и частичными отказами ([[failure-modes-and-timeouts]]).

### Три адреса — три задачи
| Адрес | Уровень | Область действия | Кто назначает | Пример |
|---|---|---|---|---|
| MAC | L2 | один канал / широковещательный домен | зашит в сетевую карту (или генерируется для виртуальных NIC) | `02:42:ac:11:00:02` |
| IP | L3 | весь интернет (или частная сеть) | DHCP, статическая настройка, облако, Docker | `10.0.1.10` |
| Порт | L4 | один хост | ОС (эфемерный) или приложение (`bind`) | `51514 → 443` |

- Аналогия, которая работает: IP — это здание, порт — квартира, MAC — адрес на конверте курьера только для текущего участка пути.
- Почему не маршрутизировать по MAC? MAC-адреса плоские и не несут информации о местоположении, поэтому маршрутизатору понадобилась бы запись для каждого устройства на планете. IP-адреса иерархичны: один маршрут для `10.0.2.0/24` покрывает 254 хоста ([[ip-addressing-and-nat]]).

### Та же подсеть или через шлюз
- Отправитель сравнивает IP назначения со своим адресом и маской (на практике ядро смотрит в таблицу маршрутизации; см. [[network-routing]]).
- **Та же подсеть**: узнать MAC назначения через [[arp]] и отправить кадр напрямую. Максимум один хоп через коммутатор.
- **Другая подсеть**: узнать MAC **шлюза** и отправить кадр туда. В IP-заголовке по-прежнему настоящее назначение. Шлюз на своей стороне повторяет то же решение.
- Хост с неверной маской ошибается в этом решении: пытается делать ARP для удалённого хоста (ответа нет) или отправляет локальный трафик через маршрутизатор.

### Коммутатор и маршрутизатор
| | Коммутатор (switch) | Маршрутизатор (router) |
|---|---|---|
| Уровень | L2 | L3 |
| Смотрит на | MAC назначения | IP назначения |
| Таблица | MAC-таблица, изучается по MAC источника входящих кадров | таблица маршрутизации, задаётся вручную или изучается через OSPF/BGP |
| Неизвестное назначение | рассылает во все порты | отбрасывает (или отправляет по маршруту по умолчанию) |
| Меняет пакет | ничего | новый заголовок L2, TTL − 1, контрольная сумма IP; NAT, если настроен |
| Граница | один широковещательный домен | разделяет широковещательные домены |

- «Коммутатор третьего уровня» (L3 switch) — коммутатор с аппаратной маршрутизацией; между VLAN он ведёт себя как маршрутизатор.
- Bridge в Docker (`docker0`) — программный коммутатор; маршрутизатором для своих контейнеров служит сам хост ([[docker-networking]]).

### Что происходит на каждом хопе
1. **Отправитель**: приложение пишет в сокет; ядро добавляет TCP-заголовок (порты), IP-заголовок (IP, TTL 64) и Ethernet-заголовок (свой MAC → MAC следующего хопа). Устройство этих заголовков: [[ip-packet-structure]], [[tcp-segment-structure]].
2. **Коммутатор**: запоминает MAC источника на входящем порту, пересылает кадр в порт для MAC назначения. Больше ничего не меняется.
3. **Маршрутизатор**: принимает кадр, потому что MAC назначения — его собственный, снимает Ethernet-заголовок, ищет IP назначения, уменьшает TTL (при 0 отбрасывает и шлёт ICMP Time Exceeded; см. [[icmp-ping-traceroute]]), делает ARP для следующего хопа и собирает новый кадр.
4. **Получатель**: сетевая карта принимает кадр для своего MAC, ядро проверяет, что IP локальный, читает поле протокола (6 = TCP, 17 = UDP) и доставляет данные в сокет, совпадающий по четырём полям (4-tuple).

## Пример
Как MAC меняется, а IP остаётся на хосте, который обращается к внешнему API. Запусти два захвата одновременно: один на хосте приложения, другой на маршрутизаторе или NAT-хосте (или на bridge Docker-хоста).
```bash
# на хосте приложения: MAC назначения — шлюза, IP назначения — удалённого API
$ ip route get 93.184.216.34
93.184.216.34 via 10.0.1.1 dev eth0 src 10.0.1.10 uid 1000
$ ip neigh show 10.0.1.1
10.0.1.1 dev eth0 lladdr 52:54:00:00:01:01 REACHABLE
$ sudo tcpdump -nn -e -v -i eth0 host 93.184.216.34 -c 1
aa:aa:aa:00:00:0a > 52:54:00:00:01:01, ethertype IPv4, length 74:
  (ttl 64, id 0, proto TCP (6)) 10.0.1.10.51514 > 93.184.216.34.443: Flags [S]

# на маршрутизаторе, внешняя сторона: новые MAC, TTL 63, и здесь NAT ещё переписал источник
$ sudo tcpdump -nn -e -v -i wan0 host 93.184.216.34 -c 1
52:54:00:00:02:01 > 00:1c:73:aa:10:01, ethertype IPv4, length 74:
  (ttl 63, id 0, proto TCP (6)) 198.51.100.7.40122 > 93.184.216.34.443: Flags [S]
```

## Подводные камни
- Ожидать, что `ping` до IP в той же подсети зависит от шлюза. Если ARP не работает (неверный VLAN, файрвол на хосте), локальный трафик не проходит, даже когда шлюз в порядке.
- Забывать, что коммутатор рассылает кадры для неизвестных MAC во все порты: захват на любом порту показывает часть чужого трафика, пока MAC-таблица не обучится.
- Считать MAC-адреса в захвате настоящими конечными точками. На маршрутизируемом пути это соседи на одном канале; конечные точки — в IP-заголовке.
- Считать IP источника адресом клиента. Любой NAT или L7-прокси на пути его заменяет ([[ip-addressing-and-nat]], [[reverse-proxy-nginx-basics]]).
- Связанные заметки: [[osi-and-tcp-ip-models]] — словарь уровней, [[network-routing]] — как выбирается следующий хоп, [[tcpdump]] — чтение захватов.
