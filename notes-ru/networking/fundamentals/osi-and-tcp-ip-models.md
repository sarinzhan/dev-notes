## Кратко
Модель OSI — это семиуровневый учебный словарь; модель TCP/IP — четырёхуровневый стек, который реально работает. Для бэкенд-разработчика полезно такое соответствие: HTTP/gRPC/DNS — прикладные протоколы, TLS находится между ними и TCP, TCP/UDP дают порты и (TCP) надёжность, IP маршрутизирует пакеты между сетями, Ethernet/Wi-Fi передают кадры в пределах одного канала. Любая фраза «уровень N» на собеседовании (балансировщик L4 или L7, коммутатор L3, сеть L2) относится к нумерации OSI, поэтому номера стоит выучить, хотя OSI никто не реализует.

## Основное
### Две модели рядом
| OSI | TCP/IP | Что передаётся | Адресация | Реальные примеры |
|---|---|---|---|---|
| 7 Прикладной | Прикладной | сообщение | URL, имя хоста | HTTP, gRPC, DNS, SMTP, протокол Kafka, сетевой протокол Postgres |
| 6 Представления | Прикладной | сообщение | — | шифрование TLS (часто относят сюда), кодирование JSON/Protobuf, gzip |
| 5 Сеансовый | Прикладной | сообщение | — | возобновление сессии TLS, потоки HTTP/2, соединение WebSocket |
| 4 Транспортный | Транспортный | сегмент / датаграмма | порт | TCP, UDP, QUIC |
| 3 Сетевой | Межсетевой (Internet) | пакет | IP-адрес | IPv4, IPv6, ICMP, маршрутизаторы |
| 2 Канальный | Канальный (Link) | кадр | MAC-адрес | Ethernet, Wi-Fi, ARP, коммутаторы, VLAN |
| 1 Физический | Канальный (Link) | биты | — | кабели, радио, оптоволокно |

- Уровни 5–7 OSI схлопываются в один прикладной уровень TCP/IP; на практике всё, что выше TCP, все называют «L7».
- **Инкапсуляция**: каждый уровень оборачивает вышележащий своим заголовком. HTTP-запрос превращается в `Ethernet[ IP[ TCP[ TLS[ HTTP ] ] ] ]`. При приёме происходит обратное; поэтому захват пакетов показывает вложенные заголовки ([[network-debugging-toolkit]]).
- Уровень общается с одноимённым уровнем на другом хосте через нижележащие уровни и знает только интерфейс уровня непосредственно под собой. Поэтому под HTTP можно заменить TCP на QUIC ([[http-1-1-vs-2-vs-3]]), не меняя приложение.

### Какой уровень я отлаживаю?
- **L2**: неверный VLAN, устаревший кеш ARP после переезда сервера, несовпадение MTU. Симптомы: хост недоступен в той же подсети, большие пакеты исчезают.
- **L3**: нет маршрута, неверный шлюз, файрвол отбрасывает ICMP, проблемы с NAT ([[ip-addressing-and-nat]]). Симптомы: `ping` не проходит, `traceroute` обрывается.
- **L4**: порт закрыт, SYN отброшен файрволом, сброс соединения, исчерпаны эфемерные порты ([[tcp-handshake-and-connection-states]]). Симптомы: «connection refused» против «timeout».
- **L5–6**: сбой рукопожатия TLS, сертификат не доверенный, неверный SNI ([[tls-handshake-and-certificates]]).
- **L7**: 4xx/5xx, неверный заголовок `Host`, CORS, медленный upstream ([[http-fundamentals]]).
- Движение снизу вверх с одним инструментом на уровень — самая быстрая диагностика; сторона Linux этого обхода описана в [[linux-networking]].

### Где находится типичная инфраструктура
| Устройство / компонент | На каком уровне работает | Почему это важно |
|---|---|---|
| Коммутатор (switch) | L2 (MAC) | Не может маршрутизировать между подсетями |
| Маршрутизатор, CNI в Kubernetes, VPN | L3 (IP) | Решает, куда следующий хоп; здесь живёт NAT |
| Балансировщик L4, `iptables`, kube-proxy | L4 (IP + порт) | Перенаправляет TCP-потоки, не читая HTTP ([[load-balancers-l4-vs-l7]]) |
| nginx, Envoy, API-шлюз, CDN | L7 (HTTP) | Может маршрутизировать по пути/заголовку, завершать TLS, кешировать ([[reverse-proxy-nginx-basics]], [[cdn]]) |
| Sidecar сервис-меша | L4 + L7 | mTLS и retry на каждый запрос ([[mtls-and-service-to-service-auth]]) |

### Вопросы в стиле собеседования
- «В чём разница между TCP и IP?» IP доставляет пакеты от хоста к хосту без гарантий; TCP поверх него доставляет упорядоченный поток байтов от процесса к процессу с помощью портов ([[tcp-vs-udp]]).
- «Где место TLS?» Между транспортным и прикладным уровнями; пуристы OSI говорят — уровень представления/сеансовый. Практический ответ: он оборачивает поток байтов TCP, и приложение разницы не видит.
- «Зачем мы до сих пор упоминаем OSI?» Ради словаря. «Маршрутизация L7» и «L4-прокси» имеют смысл только через нумерацию OSI.

## Пример
Один запрос от Spring Boot сервиса к Postgres, уровень за уровнем, как он выглядит в захвате. Флаг `-e` печатает адреса канального уровня, поэтому каждая строка показывает сразу все четыре уровня TCP/IP:
```bash
sudo tcpdump -nn -e -i eth0 port 5432 -c 3
# L2 MAC источника -> MAC назначения      L3 IP источника -> IP назначения        L4 флаги/порты TCP
02:42:ac:11:00:02 > 02:42:ac:11:00:03, ethertype IPv4 (0x0800), length 74:
  10.20.5.2.52914 > 10.20.5.10.5432: Flags [S], seq 1831221184, win 64240, options [mss 1460,...]
02:42:ac:11:00:03 > 02:42:ac:11:00:02, ethertype IPv4 (0x0800), length 74:
  10.20.5.10.5432 > 10.20.5.2.52914: Flags [S.], seq 2993241, ack 1831221185, win 65160, ...
02:42:ac:11:00:02 > 02:42:ac:11:00:03, ethertype IPv4 (0x0800), length 66:
  10.20.5.2.52914 > 10.20.5.10.5432: Flags [.], ack 1, win 502, ...
# После этого полезная нагрузка L7 (Postgres StartupMessage, затем SSLRequest) идёт внутри TCP.
```
Как читать: MAC-адреса — это интерфейсы bridge в Docker (L2), `10.20.5.2 -> 10.20.5.10` — маршрутизация (L3), `52914 -> 5432` — эфемерный и серверный порты (L4), а `[S]`, `[S.]`, `[.]` — тройное рукопожатие (three-way handshake).

## Подводные камни
- Считать OSI описанием устройства ядра. В Linux есть сокеты, TCP/UDP, IP, netfilter и драйверы; кода «сеансового уровня» там нет нигде.
- Говорить «балансировщик L7», когда продукт только перенаправляет TCP (многие облачные «сетевые» балансировщики — L4). От этой разницы зависит, будут ли маршрутизация по пути, canary по заголовкам и завершение TLS.
- Забывать, что NAT и файрволы переписывают или отбрасывают пакеты на L3/L4 ещё до того, как запустится твой HTTP-код; `504` от шлюза часто означает отброшенный SYN двумя уровнями ниже.
- Думать, что HTTP/3 «заменяет TCP на UDP»; QUIC заново реализует надёжность поверх UDP, а разбиение на уровни сохраняется.
- Связанные заметки: [[tcp-vs-udp]] — транспортный уровень подробно, [[linux-networking]] — путь пакета через ядро.
