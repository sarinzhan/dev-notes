## Кратко
TCP даёт соединение и упорядоченный надёжный поток байтов: рукопожатие, номера последовательности, подтверждения, повторную передачу, управление потоком (окно получателя) и управление перегрузкой (отправитель замедляется при потерях). UDP даёт независимые датаграммы с портом и контрольной суммой — и ничего больше. Почти всё, что пишет бэкенд-разработчик, едет поверх TCP (HTTP/1.1, HTTP/2, gRPC, Postgres, Kafka). UDP появляется в DNS, метриках, видео и HTTP/3 (QUIC), где приложение готово реализовать собственную надёжность или отбрасывать опоздавшие данные.

## Основное
### Сравнение
| Аспект | TCP | UDP |
|---|---|---|
| Соединение | да, тройное рукопожатие перед данными ([[tcp-handshake-and-connection-states]]) | нет; первый пакет уже с данными |
| Единица | поток байтов, нарезаемый ядром на сегменты | датаграмма, один `send()` = один пакет (до ~64 КБ, на практике держи меньше MTU ~1400 Б) |
| Порядок | гарантирован номерами последовательности | нет; пакеты могут прийти в другом порядке |
| Надёжность | ACK, повторная передача по таймауту или по тройному дублирующему ACK | нет; потери — проблема приложения |
| Управление потоком | получатель объявляет окно (`win` в захватах) | нет |
| Управление перегрузкой | slow start, congestion avoidance, CUBIC по умолчанию в Linux, BBR опционально | нет; некорректно ведущий себя UDP-отправитель может забить канал |
| Заголовок | 20–60 байт | 8 байт |
| Блокировка начала очереди (head-of-line blocking) | да: потерянный сегмент останавливает всё, что за ним | нет |
| Broadcast / multicast | нет | да |
| Типичное применение | HTTP, TLS, протоколы БД, Kafka, SSH | DNS, DHCP, NTP, StatsD, syslog, VoIP, игры, QUIC |

### Почему TCP иногда кажется медленным
- **Цена рукопожатия**: один RTT до первого байта плюс 1 RTT на TLS 1.3. Пулы соединений существуют, чтобы заплатить её один раз ([[sockets-and-connection-pooling]]).
- **Медленный старт** (slow start): новое соединение начинает с маленького окна перегрузки (10 сегментов в Linux) и удваивает его каждый RTT; короткоживущее соединение никогда не выходит на полную пропускную способность. Ещё один довод за keep-alive.
- **Nagle + отложенный ACK**: алгоритм Нейгла буферизует мелкие записи, пока предыдущая не подтверждена; получатель откладывает ACK до 40 мс. Вместе это даёт протоколам запрос/ответ с мелкими сообщениями задержки по 40 мс. Большинство клиентов ставят `TCP_NODELAY` (Netty и HTTP-клиент JDK так делают).
- **Блокировка начала очереди**: HTTP/2 мультиплексирует потоки в одном TCP-соединении, поэтому один потерянный пакет останавливает все потоки; QUIC решает это, помещая потоки внутрь UDP ([[http-1-1-vs-2-vs-3]]).

### Когда UDP — правильный выбор
- Данные устаревают, как только опоздали: живое аудио/видео, состояние игры, отсчёты метрик. Повторно передавать кадр двухсекундной давности бесполезно.
- Крошечный запрос/ответ, где рукопожатие стоило бы дороже полезной нагрузки: DNS ([[dns-resolution]]), NTP.
- Нужна собственная схема надёжности: QUIC, WireGuard, RTP. Это много работы; делай так, только когда семантика TCP тебе не подходит.
- Нужен multicast или broadcast (обнаружение сервисов в LAN, DHCP).

### Надёжность — не то же самое, что «нет потерь данных в приложении»
- TCP гарантирует доставку в буфер ядра собеседника, а не то, что приложение прочитало и обработало данные. Если сервер падает после ACK, данные пропали. Подтверждения на уровне приложения (Kafka `acks=all`, HTTP 2xx, идемпотентные retry) всё равно нужны ([[delivery-guarantees]], [[idempotency]]).
- В TCP нет границ сообщений: `read()` может вернуть половину сообщения или два сообщения. Каждый протокол поверх TCP определяет кадрирование (framing): HTTP `Content-Length`/chunked, кадры Kafka с префиксом длины, тип сообщения + длина в Postgres. В UDP каждая датаграмма — это сообщение, но её можно потерять или получить дважды.

### Вопросы в стиле собеседования
- «Как TCP обнаруживает потери?» По таймауту повторной передачи (RTO, вычисляется из замеров RTT) или по трём дублирующим ACK для одного номера последовательности (fast retransmit). Современные стеки также используют SACK, чтобы повторно передавать только недостающие диапазоны.
- «Управление потоком против управления перегрузкой?» Управление потоком защищает получателя (окно объявляет получатель). Управление перегрузкой защищает сеть (окно отправитель выводит из потерь и задержек). Эффективное окно — минимум из двух.
- «Бывает ли UDP надёжным?» Только если приложение делает его таким. QUIC надёжен, упорядочен в пределах потока, зашифрован и работает поверх UDP.

## Пример
Отправка одной и той же крошечной полезной нагрузки обоими способами из Java показывает разницу на уровне API: поток, в который пишешь, против пакетов, которые отправляешь.
```java
// TCP: подключиться один раз (рукопожатие), затем писать в поток; кадрирование — твоя забота
try (var socket = new Socket("metrics.internal", 9000);
     var out = new DataOutputStream(socket.getOutputStream())) {
    socket.setTcpNoDelay(true);               // избежать задержек Nagle на мелких записях
    byte[] msg = "esim.activations:1|c".getBytes(StandardCharsets.UTF_8);
    out.writeInt(msg.length);                  // префикс длины = граница сообщения
    out.write(msg);
    out.flush();
}

// UDP: соединения нет; каждая отправка — одна датаграмма, может потеряться или прийти не по порядку, никогда не блокируется на мёртвом собеседнике
try (var channel = DatagramChannel.open()) {
    var target = new InetSocketAddress("statsd.internal", 8125);
    var buf = ByteBuffer.wrap("esim.activations:1|c".getBytes(StandardCharsets.UTF_8));
    channel.send(buf, target);                 // отправил и забыл; счётчик StatsD может позволить себе потери
}
```
Случай StatsD — каноническое решение «UDP подойдёт»: потеря 0,1% инкрементов счётчика допустима, а сбой метрик никогда не должен блокировать поток обработки запроса.

## Подводные камни
- Предположение, что один `write()` по TCP превращается в один `read()` на другой стороне. Это не так; реализуй кадрирование или используй протокол, в котором оно есть.
- Долгоживущие простаивающие TCP-соединения молча умирают на NAT-шлюзах и файрволах (обычно после 5–60 минут тишины). Включай keep-alive или ping на уровне приложения ([[tcp-handshake-and-connection-states]]).
- UDP-датаграммы больше MTU пути фрагментируются на уровне IP, и потеря одного фрагмента теряет всю датаграмму; держи полезную нагрузку меньше ~1400 байт.
- Слишком маленькие `SO_RCVBUF`/`SO_SNDBUF` на каналах с высокой задержкой ограничивают пропускную способность величиной `window / RTT`; Linux автоматически настраивает буферы TCP, но приёмные буферы UDP переполняются молча (`UdpInErrors` в `nstat`).
- Связанные заметки: [[osi-and-tcp-ip-models]] — где находится транспортный уровень, [[socket-management]] — как сервер обслуживает тысячи таких сокетов.
