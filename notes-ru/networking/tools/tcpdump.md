## Кратко
`tcpdump` печатает или сохраняет в файл `.pcap` пакеты, проходящие через интерфейс, отфильтрованные в ядре BPF-выражением вроде `host 10.20.5.10 and tcp port 5432`. Он отвечает на вопросы, на которые не отвечают журналы: ушёл ли SYN, вернулось ли что-нибудь, кто прислал RST, какой DNS-сервер спросили и что он ответил. Захватывай с `-nn` и узким фильтром, для всего длиннее нескольких строк пиши в файл через `-w` и открывай файл в Wireshark. В контейнерах запускай его внутри сетевого пространства имён контейнера, а не гадай с хоста.

## Основное
### Форма команды
`tcpdump [options] [filter]`, запуск от root (или с `CAP_NET_RAW`).
| Опция | Значение |
|---|---|
| `-i eth0` / `-i any` | интерфейс; `any` захватывает все (Linux-заголовок «cooked», без MAC-адресов) |
| `-nn` | без DNS-запросов для адресов и без имён для портов; быстрее и однозначно |
| `-c 50` | остановиться после 50 пакетов |
| `-v`, `-vv` | больше деталей заголовка: TTL, IP ID, общая длина, контрольные суммы |
| `-e` | показать заголовок канального уровня (MAC), нужно для отладки ARP на реальной сетевой карте |
| `-A` / `-X` | полезная нагрузка как ASCII / как hex + ASCII; читаемо только для текстовых протоколов |
| `-w file.pcap` / `-r file.pcap` | записать сырые пакеты / прочитать их обратно (фильтры работают и с `-r`) |
| `-C 100 -W 5` | новый файл каждые 100 МБ, хранить 5: кольцевой буфер для долгих захватов |
| `-U`, `-l` | сбрасывать каждый пакет (при `-w -` в конвейер) / построчная буферизация текстового вывода (в конвейер с `grep`) |

### Примитивы BPF-фильтров
- Адреса: `host 10.0.0.5`, `src host ...`, `dst host ...`, `net 10.20.0.0/16`.
- Порты и протоколы: `port 443`, `tcp port 5432`, `udp port 53`, `portrange 8000-8100`, `icmp`, `arp`, `ip6`.
- Комбинируются через `and`, `or`, `not` и скобки; весь фильтр бери в кавычки, чтобы shell его не трогал.
- Флаги TCP: `'tcp[tcpflags] & tcp-syn != 0'` (любой SYN), `'tcp[tcpflags] & (tcp-syn|tcp-ack) == tcp-syn'` (только попытки нового соединения), `'tcp[tcpflags] & tcp-rst != 0'` (сбросы).
- Типы ICMP: `'icmp[icmptype] == icmp-echo'`, `'icmp[icmptype] == icmp-unreach'` (ищи «frag needed» при отладке [[mss-mtu-pmtud]]).
- Фильтр компилируется в BPF и выполняется в ядре, поэтому неподходящие пакеты никогда не попадают в пространство пользователя.

### Чтение вывода TCP
Каждая строка: время, `IP src.port > dst.port`, `Flags [..]`, номера sequence/ack, окно, опции, длина полезной нагрузки.
- Флаги: `[S]` SYN, `[S.]` SYN-ACK, `[.]` ACK, `[P.]` данные с PSH, `[F.]` FIN, `[R]` / `[R.]` сброс.
- Рукопожатие — это `[S]`, `[S.]`, `[.]` ([[tcp-handshake-and-connection-states]]); опции SYN показывают MSS, масштаб окна и SACK, которые предлагает клиент ([[tcp-segment-structure]], [[tcp-flow-control]]).
- После рукопожатия tcpdump показывает относительные номера (`seq 1:518`, `ack 1`); `-S` печатает абсолютные.
- Шаблоны: SYN повторяется через 1 с, 2 с, 4 с без ответа = порт фильтруется; на `[S]` приходит `[R.]` = никто не слушает; `win 0` от получателя = он не читает ([[tcp-flow-control]]); один и тот же `seq` отправлен дважды = повторная передача (retransmission) ([[tcp-congestion-control]]).

### Чтение вывода UDP, ICMP и ARP
- DNS-запрос: `10.20.6.10.48211 > 10.20.0.2.53: 31837+ A? api.example.com. (33)`: id 31837, `+` = желательна рекурсия, тип записи, имя, длина полезной нагрузки. Ответ несёт тот же id, `1/0/0` (answers/authority/additional) и записи ([[dns-resolution]], [[udp-in-depth]]).
- `ICMP echo request` / `echo reply` с `id` и `seq`; `ICMP time exceeded in-transit` — это то, что собирает traceroute ([[icmp-ping-traceroute]]).
- `ARP, Request who-has 10.20.6.1 tell 10.20.6.10` и `Reply 10.20.6.1 is-at 52:54:00:..`; запросы без ответа означают, что сосед выключен или находится в другом L2-сегменте ([[arp]], [[host-to-host-communication]]).

### Wireshark
- Захвати с `-w`, скопируй файл, открой локально: следуй за TCP-потоками, декодируй HTTP/2, Postgres и Kafka, фильтруй через `tcp.analysis.retransmission` или `dns.flags.rcode != 0`.
- Живой удалённый захват без файла: `ssh host 'sudo tcpdump -i eth0 -U -w - port 8080' | wireshark -k -i -`.
- Полезная нагрузка TLS остаётся зашифрованной, если не передать файл журнала ключей (`SSLKEYLOGFILE`) ([[tls-handshake-and-certificates]]).

### Контейнеры
- С хоста `-i docker0` или `-i br-<id>` показывает трафик между контейнерами на этом мосту, а `veth` на стороне хоста — трафик одного контейнера ([[docker-networking]]).
- Внутри пространства имён контейнера с tcpdump хоста: `nsenter -t <pid> -n tcpdump -i eth0 ...`; образу приложения инструменты не нужны.
- Или sidecar, разделяющий пространство имён: `docker run --rm --net container:api nicolaka/netshoot tcpdump ...`; в Kubernetes — `kubectl debug` ([[network-debugging-toolkit]]).

## Пример
Почему API получает тайм-аут от Postgres? Захват внутри контейнера API, затем чтение рукопожатия и DNS-запроса.
```bash
PID=$(docker inspect -f '{{.State.Pid}}' esim-api)
sudo nsenter -t "$PID" -n tcpdump -i eth0 -nn -c 20 'tcp port 5432 or udp port 53'

# запрос имени "postgres" ушёл во встроенный DNS на lo, поэтому на eth0 видна только TCP-часть
# 09:14:02.103 IP 172.18.0.5.51514 > 172.18.0.3.5432: Flags [S], seq 3913254091, win 64240, options [mss 1460,sackOK,TS val 1022 ecr 0,nop,wscale 7], length 0
# 09:14:02.103 IP 172.18.0.3.5432 > 172.18.0.5.51514: Flags [S.], seq 1783392040, ack 3913254092, win 65160, options [mss 1460,sackOK,TS val 877 ecr 1022,nop,wscale 7], length 0
# 09:14:02.103 IP 172.18.0.5.51514 > 172.18.0.3.5432: Flags [.], ack 1, win 502, length 0
# 09:14:02.104 IP 172.18.0.5.51514 > 172.18.0.3.5432: Flags [P.], seq 1:9, ack 1, win 502, length 8      # SSLRequest
# 09:14:02.104 IP 172.18.0.3.5432 > 172.18.0.5.51514: Flags [P.], seq 1:2, ack 9, win 509, length 1      # 'S': TLS принят

# DNS на стороне хоста: запрос и ответ с общим id 31837
sudo tcpdump -i any -nn -c 2 'udp port 53'
# IP 10.20.6.10.48211 > 10.20.0.2.53: 31837+ A? billing.internal. (34)
# IP 10.20.0.2.53 > 10.20.6.10.48211: 31837 1/0/0 A 10.20.7.15 (50)

# Только попытки соединений и сбросы, сохранение для Wireshark, ротация 5 x 100 МБ
sudo tcpdump -i eth0 -nn -C 100 -W 5 -w /tmp/pg.pcap \
  'tcp port 5432 and (tcp[tcpflags] & (tcp-syn|tcp-rst) != 0)'
tcpdump -nn -r /tmp/pg.pcap0 'tcp[tcpflags] & tcp-rst != 0' | head
```

## Подводные камни
- Забытый `-nn`: tcpdump делает обратный DNS-запрос для каждого адреса, тормозит, теряет пакеты, а его собственные DNS-запросы попадают в захват.
- Захват не на том интерфейсе: трафик на `localhost` идёт через `lo`, встроенный DNS контейнера — через его собственный `lo`, трафик моста — через `docker0`/`br-*`; `-i any` на хосте не видит loopback-интерфейсы других сетевых пространств имён.
- Ошибки контрольных сумм с `-vv` на исходящих пакетах — обычно checksum offload: сетевая карта заполняет их уже после захвата.
- «packets dropped by kernel» в конце означает, что фильтр слишком широкий или вывод слишком медленный; сузь фильтр и пиши через `-w`.
- Захваты содержат учётные данные, токены и персональные данные в текстовых протоколах; держи их короткими, отфильтрованными и удаляй после использования.
- Связанные заметки: [[network-debugging-toolkit]] — пошаговый сценарий вокруг этого инструмента, [[linux-networking]] — интерфейсы и пространства имён, [[osi-and-tcp-ip-models]] — заголовки, которые ты читаешь.
