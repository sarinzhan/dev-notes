## Кратко
**Алгоритм Нейгла** (Nagle's algorithm, на стороне отправителя) придерживает маленькую запись, пока предыдущие данные ещё не подтверждены, чтобы «болтливое» приложение не засыпало сеть крошечными пакетами. **Отложенный ACK** (delayed ACK, на стороне получателя) придерживает подтверждение до 40 мс в Linux (200 мс в Windows) в надежде отправить его вместе с ответом. По отдельности оба разумны; вместе они на один период таймера взаимно блокируются на шаблоне **запись–запись–чтение** (write-write-read): отправитель ждёт ACK, прежде чем отправить второй маленький кусок, получатель ждёт этот кусок, прежде чем ответить, и поэтому держит ACK, пока не сработает таймер. Решение — `TCP_NODELAY`, который чувствительные к задержке программы (Netty, gRPC, драйвер PostgreSQL JDBC, клиенты Kafka, curl, nginx) включают по умолчанию, плюс запись каждого сообщения одним вызовом.

## Основное
### Алгоритм Нейгла (RFC 896, 1984)
- Правило: если в полёте есть неподтверждённые данные, новый сегмент меньше одного MSS не отправляется; он буферизуется, пока не придёт ACK или не накопится достаточно данных на полный сегмент ([[mss-mtu-pmtud]]).
- Цель: терминал, отправляющий по одному нажатию клавиши в пакете, платит 40 байт заголовков IP и TCP за 1 байт данных. Нейгл объединяет эти байты в один пакет за круговую задержку (round trip).
- Следствие: одновременно в полёте не больше одного маленького сегмента. На канале с RTT 50 мс поток маленьких записей уходит не чаще раза в 50 мс.
- Первая маленькая запись на простаивающем соединении не задерживается; ждёт только маленькая запись, идущая за неподтверждёнными данными.

### Отложенный ACK (RFC 1122)
- Получатель не подтверждает каждый сегмент сразу. Он ждёт второго полноразмерного сегмента, исходящих данных, к которым можно прицепить ACK, или таймера. RFC 1122 ограничивает задержку 500 мс; Linux использует минимум 40 мс (адаптивно до 200 мс), Windows — 200 мс по умолчанию.
- Цель: вдвое сократить число пакетов с одним только ACK и дать протоколам «запрос–ответ» отправлять ACK внутри ответа.
- Linux начинает каждое соединение в **режиме quickack** (сразу подтверждает первые сегменты, чтобы помочь медленному старту) и переходит в отложенный режим, когда трафик выглядит интерактивным.

### Задержка на запись–запись–чтение
1. Клиент записывает маленький заголовок запроса. В полёте ничего нет, поэтому Нейгл сразу его отправляет.
2. Клиент записывает маленькое тело. Заголовок ещё не подтверждён, поэтому Нейгл придерживает тело.
3. Сервер получает заголовок, не может ответить без тела, отправлять ему нечего, поэтому отложенный ACK придерживает ACK.
4. Через 40 мс срабатывает таймер ACK на сервере. ACK освобождает тело, сервер отвечает.
- Итог: запрос, занимающий 0,3 мс в локальной сети, длится 40,3 мс. Под нагрузкой это видно как p50, похожий на фиксированное число (40 мс, 200 мс) и не зависящий ни от размера данных, ни от CPU сервера, — это и выдаёт проблему.
- То же происходит с любым протоколом, который отправляет сообщение двумя вызовами `write()`: заголовок и тело HTTP, префикс длины и кадр, TLS-запись, разбитая на несколько записей.

### TCP_NODELAY и связанные опции
| Опция | Сторона | Эффект |
|---|---|---|
| `TCP_NODELAY` | отправитель | отключает Нейгла; каждый `write()` уходит, как только позволяет окно |
| `TCP_QUICKACK` | получатель (Linux) | подтверждать сразу; не «липкая», ядро может вернуться в отложенный режим, поэтому её ставят заново после каждого чтения |
| `TCP_CORK` | отправитель (Linux) | противоположность NODELAY: держать все неполные сегменты, пока опцию не снимут (или 200 мс); используется, чтобы приклеить заголовок к телу из `sendfile()` |
| `TCP_NOPUSH` | отправитель (BSD/macOS) | BSD-аналог `TCP_CORK` |

- Кто ставит `TCP_NODELAY` по умолчанию: Netty (а значит, Reactor Netty, WebFlux, gRPC Java), коннекторы Tomcat, драйвер PostgreSQL JDBC (`tcpNoDelay=true`), MySQL Connector/J, сокеты producer, consumer и брокера Kafka, curl (с 2016 года), nginx на keep-alive соединениях (`tcp_nodelay on`). Обычный `java.net.Socket` оставляет Нейгла включённым, поэтому на «сырых» сокетах ставь опцию сам.
- В Java: `socket.setTcpNoDelay(true)` или `StandardSocketOptions.TCP_NODELAY`; `jdk.net.ExtendedSocketOptions.TCP_QUICKACK` есть с Java 10 в Linux; epoll-транспорт Netty даёт `EpollChannelOption.TCP_CORK` и `TCP_QUICKACK`.
- NODELAY перекладывает группировку на тебя: собирай всё сообщение в буфере и записывай одним вызовом (`BufferedOutputStream` со сбросом на каждое сообщение, один `writeAndFlush` в Netty на ответ). Иначе задержка в 40 мс меняется на множество крошечных пакетов.

## Пример
Клиент самописного бинарного протокола на «сыром» сокете, сделанный правильно:
```java
import java.io.BufferedOutputStream;
import java.io.DataInputStream;
import java.io.DataOutputStream;
import java.net.InetSocketAddress;
import java.net.Socket;
import java.nio.charset.StandardCharsets;

public final class LedgerClient implements AutoCloseable {
    private final Socket socket = new Socket();
    private final DataOutputStream out;
    private final DataInputStream in;

    public LedgerClient(String host, int port) throws Exception {
        socket.setTcpNoDelay(true);                       // без Нейгла: группируем сами
        socket.connect(new InetSocketAddress(host, port), 2_000);
        socket.setSoTimeout(5_000);
        out = new DataOutputStream(new BufferedOutputStream(socket.getOutputStream(), 8192));
        in = new DataInputStream(socket.getInputStream());
    }

    public long balance(String msisdn) throws Exception {
        byte[] body = msisdn.getBytes(StandardCharsets.UTF_8);
        out.writeInt(body.length);   // префикс длины и тело попадают в один буфер...
        out.write(body);
        out.flush();                 // ...и уходят одним write(), одним сегментом
        return in.readLong();
    }

    @Override public void close() throws Exception { socket.close(); }
}
```

## Подводные камни
- Стабильный «пол» задержки в 40 мс или 200 мс на маленьких запросах — это Нейгл плюс отложенный ACK, пока не доказано обратное. Проверь через `ss -ti` или захват [[tcpdump]]: ищи разрыв ~40 мс перед вторым сегментом с данными.
- Включить `TCP_NODELAY` и при этом писать ответ по полю (небуферизованный `OutputStream`, `write()` на каждую строку заголовка) — значит засыпать сеть крошечными пакетами и поднять нагрузку на CPU; всегда сочетай его с буферизацией.
- `TCP_QUICKACK`, поставленный один раз, в Linux не постоянен; код, который ставит его только после `connect()`, снова видит задержку.
- `TCP_CORK` без снятия оставляет последний неполный сегмент ждать потолка в 200 мс.
- Связанное: [[socket-management]] — буферы отправки и нарезка на сегменты; [[tcp-flow-control]] и [[tcp-congestion-control]] — другие механизмы, решающие, когда байты уходят; [[connection-establishment-cost]] — задержка до первого байта.
