## Кратко
Новое соединение стоит нескольких круговых задержек (RTT) до первого полезного байта: 1 RTT на TCP-рукопожатие, плюс 2 RTT на рукопожатие TLS 1.2 или 1 RTT на TLS 1.3, и затем сам запрос. На межрегиональном канале с RTT 60 мс это 180–240 мс чистого ожидания, а свежее соединение затем начинает с **медленного старта** (slow start), так что большому ответу нужно ещё несколько круговых задержек. Решение — заплатить один раз и переиспользовать: **пулы соединений** и **keep-alive**. Остальное срезают протокольные приёмы: возобновление сессии TLS, **0-RTT** в TLS 1.3, **TCP Fast Open** (данные в SYN, на практике редко применим) и **QUIC**, который объединяет транспорт и TLS в 1 RTT, а при возобновлении — 0.

## Основное
### Считаем круговые задержки
| Вариант | RTT до отправки запроса | Время до первого байта ответа |
|---|---|---|
| Чистый TCP | 1 | 2 RTT |
| TCP + TLS 1.2 (полное) | 3 | 4 RTT |
| TCP + TLS 1.2 (возобновление сессии) | 2 | 3 RTT |
| TCP + TLS 1.3 | 2 | 3 RTT |
| TCP + TLS 1.3 0-RTT (возобновление) | 1 | 2 RTT |
| QUIC (HTTP/3) | 1 | 2 RTT |
| QUIC 0-RTT (возобновление) | 0 | 1 RTT |
| Переиспользованное keep-alive соединение | 0 | 1 RTT |

- Добавь DNS-запрос при холодном кэше ([[dns-resolution]]). Детали TCP-рукопожатия — в [[tcp-handshake-and-connection-states]]; сообщения TLS — в [[tls-handshake-and-certificates]].
- Внутри одного дата-центра RTT ~0,2–0,5 мс, поэтому рукопожатия почти не добавляют задержки, но всё равно стоят CPU: каждое полное TLS-рукопожатие требует обмена ключами ECDHE и проверки подписи сертификата ([[latency-numbers]]).
- Между регионами или до мобильных клиентов (RTT 50–200 мс) рукопожатия доминируют для маленьких запросов.

### Медленный старт на свежем соединении
- Новое соединение не знает пропускной способности пути. Оно начинает с начального окна перегрузки в 10 сегментов (RFC 6928, ~14 КБ) и примерно удваивает его каждый RTT ([[tcp-congestion-control]]).
- Поэтому ответ на 100 КБ занимает около 3 RTT передачи данных после рукопожатия (14 + 29 + 58 КБ). На «прогретом» соединении, окно которого уже выросло, он может уйти за один.
- Linux сбрасывает окно после простоя (`net.ipv4.tcp_slow_start_after_idle=1`, простой дольше одного RTO). Соединение из пула, простоявшее несколько секунд, снова стартует медленно; для долгоживущих каналов репликации или gRPC это часто ставят в 0.

### Пулы и keep-alive: настоящее решение
- HTTP/1.1 по умолчанию держит соединения открытыми (`Connection: keep-alive`); HTTP/2 идёт дальше и мультиплексирует все запросы в одном соединении ([[http-1-1-vs-2-vs-3]]).
- Драйверы баз данных и HTTP-клиенты держат пулы: HikariCP для JDBC ([[hikaricp-pool-sizing]]), пулы Reactor Netty или Apache HttpClient для REST ([[rest-clients]]), клиенты Kafka держат одно долгоживущее соединение на брокер ([[kafka-producer]]). Механику пулов см. в [[sockets-and-connection-pooling]].
- Согласуй тайм-ауты простоя по всему пути: пул клиента должен закрыть соединение раньше, чем это сделает балансировщик или NAT, иначе следующий запрос попадёт в мёртвый сокет ([[load-balancers-l4-vs-l7]]).
- Для Postgres серверный пулер (PgBouncer) ещё и избавляет от fork серверного процесса на каждое соединение, который стоит дороже сетевого рукопожатия ([[network-access-to-databases]]).

### Сокращения в TLS
- **Возобновление сессии** (session tickets / PSK) пропускает обмен сертификатами и подпись: на один RTT меньше в TLS 1.2 и меньше CPU на обеих сторонах.
- **0-RTT в TLS 1.3** (early data): клиент отправляет запрос в первой же порции сообщений, используя ключ из предыдущей сессии. Атакующий может **повторить** (replay) early data, поэтому серверы принимают их только для идемпотентных запросов; многие серверы их отключают.

### TCP Fast Open (RFC 7413)
- Первое соединение: SYN клиента запрашивает cookie; сервер возвращает его (зашифрованный токен IP клиента) в SYN-ACK.
- Следующие соединения: SYN несёт cookie и первые байты запроса. Сервер проверяет cookie и отдаёт данные приложению до завершения рукопожатия, экономя 1 RTT.
- Ограничения: данные в SYN могут продублироваться, поэтому они должны быть идемпотентными; промежуточное оборудование (middleboxes) отбрасывает или вырезает SYN с данными или неизвестными опциями; браузеры пробовали TFO и выключили. Linux его поддерживает (`net.ipv4.tcp_fastopen=3` для клиента и сервера), но в JDK API для него нет. На практике он редко встречается вне контролируемых сетей.

### QUIC
- QUIC работает поверх UDP и выполняет рукопожатие транспорта и TLS 1.3 за одну порцию сообщений: 1 RTT для нового соединения, 0-RTT при возобновлении с той же оговоркой про повтор. Соединения к тому же переживают смену IP клиента ([[udp-in-depth]]).

## Пример
Замер фаз через curl; второй URL переиспользует соединение.
```bash
$ cat fmt.txt
dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n

$ curl -s -o /dev/null -o /dev/null -w @fmt.txt \
    https://api.example.eu/v1/tariffs https://api.example.eu/v1/tariffs
dns=0.012 tcp=0.074 tls=0.139 ttfb=0.204 total=0.205   # новое: TCP 1 RTT + TLS 1.3 1 RTT + запрос 1 RTT (~62 мс каждый)
dns=0.000 tcp=0.000 tls=0.000 ttfb=0.063 total=0.063   # переиспользованное: один RTT

$ curl -s -o /dev/null --tlsv1.2 --tls-max 1.2 -w @fmt.txt https://api.example.eu/v1/tariffs
dns=0.001 tcp=0.063 tls=0.189 ttfb=0.252 total=0.253   # TLS 1.2: два RTT на рукопожатие
```

## Подводные камни
- Создание HTTP-клиента или `RestTemplate` на каждый запрос (или `new Socket()` на каждый вызов) выбрасывает пул и каждый раз оплачивает полное рукопожатие.
- Слишком маленький для всплесков пул открывает свежие соединения под нагрузкой — именно тогда, когда лишние RTT и медленный старт вредят больше всего.
- Простаивающие соединения из пула, которые молча убил NAT или балансировщик, приводят к тому, что первый запрос после затишья падает или зависает; ставь максимальное время простоя в пуле меньше самого короткого тайм-аута промежуточного оборудования и включай валидацию.
- Включить 0-RTT в TLS, не ограничив его безопасными методами, — значит открыть повтор POST-запросов.
- Связанное: [[head-of-line-blocking]] — что происходит, когда одно соединение несёт всё; [[nagle-and-delayed-ack]] — задержки уже после установки соединения.
