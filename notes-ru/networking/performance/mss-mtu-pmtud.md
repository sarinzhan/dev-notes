## Кратко
**MTU** — самый большой IP-пакет, который может передать канал (1500 байт в Ethernet, 9000 с jumbo frames). **MSS** в TCP — самая большая полезная нагрузка, которую TCP кладёт в один сегмент: MTU минус 40 байт заголовков IPv4 и TCP, то есть 1460 в Ethernet. Каждая сторона объявляет свой MSS в SYN, но значение имеет наименьший MTU на всём *пути*, и TCP находит его через **Path MTU discovery** (PMTUD): пакеты отправляются с битом Don't Fragment, а размер уменьшается, когда маршрутизатор отвечает ICMP «fragmentation needed». Если файрвол отбрасывает этот ICMP, большие пакеты молча пропадают (**чёрная дыра PMTUD**): рукопожатие проходит, маленькие запросы работают, большие ответы зависают. Туннели (VPN, VXLAN, Docker overlay, WireGuard) добавляют заголовки и уменьшают доступный MTU — обычно именно так на это и натыкаются.

## Основное
### MTU и MSS
- **MTU** (maximum transmission unit) — свойство канального уровня, считается от начала IP-заголовка. Ethernet: 1500. Jumbo frames: 9000, используются внутри дата-центров и в сетях хранения; все устройства в L2-сегменте должны быть согласны.
- **MSS** (maximum segment size) считает только полезную нагрузку TCP. Заголовок IPv4 20 + заголовок TCP 20 = 40 байт, поэтому MSS = 1460 при MTU 1500. У IPv6 заголовок 40 байт, поэтому MSS = 1440. Опции TCP (timestamps занимают 12 байт) ещё уменьшают реальную нагрузку на сегмент, обычно до 1448.
- Накладные расходы на заголовки — ~3% для полноразмерных сегментов и ~30% для 100-байтных записей, отправляемых по одной в пакете; это мотивация [[nagle-and-delayed-ack|алгоритма Нейгла]]. Jumbo frames сокращают работу CPU на каждый пакет при массовой передаче (репликация, бэкапы), но не задержку.

### Согласование MSS
- Каждая сторона кладёт свою опцию MSS в SYN / SYN-ACK, вычисляя её из MTU своего исходящего интерфейса. Затем каждый отправитель использует меньшее из своего значения и значения собеседника ([[tcp-handshake-and-connection-states]]).
- Более узкий канал посередине этому не виден; для этого и нужен PMTUD.

### Фрагментация и Don't Fragment
- Маршрутизаторы IPv4 могут **фрагментировать** пакет, который больше MTU следующего канала. Если теряется любой фрагмент, теряется весь пакет, а фрагменты после первого не содержат номеров портов (плохо для файрволов и балансировщиков), поэтому фрагментации избегают ([[ip-packet-structure]]).
- TCP в современных стеках ставит бит **DF** (Don't Fragment) на каждый пакет. Маршрутизатор, который не может переслать пакет с DF, отбрасывает его и отправляет ICMP type 3 code 4, «fragmentation needed», с MTU следующего перехода ([[icmp-ping-traceroute]]).
- Маршрутизаторы IPv6 никогда не фрагментируют; это может только отправитель. Аналогичное сообщение — ICMPv6 «Packet Too Big», и его блокировка просто ломает IPv6.
- У UDP нет MSS: приложение, отправившее датаграмму в 4000 байт, получит IP-фрагментацию, а с DF — ошибку отправки. Поэтому DNS поверх UDP и QUIC держат датаграммы около 1200–1450 байт ([[udp-in-depth]]).

### Path MTU discovery
- Отправитель начинает с размера, вычисленного из MSS, ставит DF и при «fragmentation needed» уменьшает path MTU для этого адресата (кэшируется в таблице маршрутов, видно в `ip route get`) и повторяет отправку сегментами поменьше.
- **Чёрная дыра**: файрвол или security group отбрасывает весь ICMP «ради безопасности». Большой пакет отбрасывается, отправитель так и не узнаёт почему и повторяет тот же размер, пока не сдастся. Симптомы: TCP подключается, TLS-рукопожатие то проходит, то нет (цепочка сертификатов — первый большой пакет), `GET /health` работает, JSON-ответ на 50 КБ зависает, SSH логинится и замирает на `ls -la`.
- **PLPMTUD** (RFC 4821, `net.ipv4.tcp_mtu_probing=1`) подбирает размер настоящими TCP-сегментами, а не доверяет ICMP, и поэтому переживает чёрные дыры. QUIC делает так же по своей конструкции.
- **MSS clamping**: маршрутизатор или VPN-шлюз переписывает опцию MSS в проходящих SYN до размера, который пролезает в туннель, так что конечные точки никогда не отправляют слишком большие сегменты. Классическое правило — `iptables ... -j TCPMSS --clamp-mss-to-pmtu`; большинство домашних роутеров делают это на PPPoE (MTU 1492).

### Туннели уменьшают MTU
| Инкапсуляция | Накладные расходы | Внутренний MTU на канале 1500 |
|---|---|---|
| PPPoE | 8 | 1492 |
| GRE | 24 | 1476 |
| IPsec (ESP, tunnel mode) | 50–70 | ~1400–1440 |
| WireGuard | 60 (IPv4) / 80 (IPv6) | 1420 (его значение по умолчанию) |
| VXLAN (Docker overlay, Flannel, многие CNI) | 50 | 1450 |

- Контейнер, у которого интерфейс показывает MTU 1500 в VXLAN-оверлее, отправляет пакеты, которые не помещаются. Overlay-сети Docker по умолчанию ставят 1450, но собственный bridge на хосте, у которого внешний канал уже идёт через VPN, может этого не сделать; задай `com.docker.network.driver.mtu` или опцию демона `mtu` ([[docker-networking]]). У CNI в Kubernetes (Calico, Flannel, Cilium) свои настройки MTU ([[kubernetes-basics]]).

## Пример
Поиск реального path MTU и проверка соединения:
```bash
# Самая большая нагрузка, которая проходит с DF: 1472 + 8 (ICMP) + 20 (IP) = 1500
$ ping -M do -s 1472 -c 2 db.internal
ping: local error: message too long, mtu=1450        # наш собственный интерфейс меньше (VXLAN)
$ ping -M do -s 1422 -c 2 db.internal
2 packets transmitted, 2 received                     # 1422 + 28 = 1450 помещается

$ tracepath -n db.internal                             # показывает pmtu по переходам, root не нужен
 1?: [LOCALHOST]   pmtu 1450
 3:  10.20.0.7     0.912ms reached
     Resume: pmtu 1450 hops 3 back 3

$ ss -ti dst 10.20.0.7 | grep -o 'mss:[0-9]* pmtu:[0-9]*'
mss:1398 pmtu:1450

# Сеть Docker Compose на хосте за WireGuard
#   networks:
#     backend:
#       driver_opts:
#         com.docker.network.driver.mtu: "1380"
```

## Подводные камни
- «Блокировать ICMP безопаснее» ломает PMTUD. Разреши как минимум ICMP type 3 code 4 (и ICMPv6 type 2) в security groups и файрволах хостов.
- Если маленькие запросы работают, а большие зависают, — это подпись проблемы с MTU, а не медленного бэкенда. Проверь `ping -M do -s` до того, как читать логи приложения.
- Jumbo frames на одном хосте и 1500 на коммутаторе или у собеседника дают потери; опция MSS при этом выглядит нормально, потому что каждая сторона сообщает только свой интерфейс.
- Связанное: [[tcp-segment-structure]] — поля заголовка, из которых складываются 40 байт; [[network-debugging-toolkit]] и [[tcpdump]] — как поймать ICMP-сообщения в сети.
