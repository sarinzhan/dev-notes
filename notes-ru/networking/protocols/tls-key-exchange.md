## Кратко
TLS использует асимметричную криптографию только для того, чтобы договориться о секрете и доказать идентичность, а затем переключается на быстрое симметричное AEAD-шифрование данных. Секрет получается из эфемерного обмена (EC)Diffie-Hellman, поэтому записанный трафик остаётся в безопасности, даже если закрытый ключ сервера позже утечёт (прямая секретность, forward secrecy); ключ сертификата только подписывает. TLS 1.3 отправляет key share в первом же сообщении и завершается за 1 RTT вместо 2, с необязательным возобновлением 0-RTT, которое можно воспроизвести повторно. Для локального HTTPS ты генерируешь ключ, самоподписанный сертификат или CSR через `openssl` и отдаёшь Java файл PKCS12 или PEM-файлы через SSL bundle в Spring Boot.

## Основное
### Зачем нужны и симметричное, и асимметричное шифрование
| | Симметричное (AES-GCM, ChaCha20-Poly1305) | Асимметричное (RSA, ECDSA, X25519) |
|---|---|---|
| Ключи | один общий секрет | пара: публичный + закрытый |
| Скорость | ГБ/с на ядро с AES-NI | тысячи операций в секунду |
| Проблема | как двум незнакомцам получить один и тот же ключ? | слишком медленное и ограниченное по размеру для потоковых данных |
| Роль в TLS | шифрует и аутентифицирует каждую запись | согласование ключей и подписи в рукопожатии |

- Рукопожатие один раз использует медленную асимметричную часть, чтобы получить общий секрет; HKDF разворачивает его в отдельные ключи для каждого направления — для рукопожатия и для данных приложения. Подробности о примитивах: [[symmetric-and-asymmetric-crypto]], [[hashing-vs-encryption]].

### Обмен ключами: RSA против (EC)DHE
- **Обмен ключами через RSA (TLS 1.2 и старше)**: клиент генерирует pre-master secret и шифрует его публичным RSA-ключом сервера из сертификата. Любой, кто записал трафик и позже получил этот закрытый ключ (утечка, судебный запрос, списанный диск), расшифрует все прошлые сессии. Прямой секретности нет.
- **(EC)DHE**: обе стороны генерируют одноразовую пару ключей на каждое соединение, обмениваются публичными половинами и вычисляют один и тот же секрет; закрытые половины удаляются после рукопожатия. Ключ сертификата только **подписывает** обмен (`ServerKeyExchange` в 1.2, `CertificateVerify` в 1.3), поэтому его утечка позволяет атакующему выдавать себя за сервер в будущем, но не читать прошлое. Это и есть **прямая секретность**.
- Группы: X25519 (по умолчанию почти везде), P-256; браузеры и Cloudflare уже используют гибридную постквантовую `X25519MLKEM768`, которая защищает записанный трафик от будущего квантового компьютера.

### TLS 1.2 против TLS 1.3
| | TLS 1.2 | TLS 1.3 (RFC 8446, 2018) |
|---|---|---|
| Round trip до данных | 2 | 1; 0 при возобновлении + early data |
| Обмен ключами | RSA, DH, ECDHE | только ECDHE / DHE, всегда с прямой секретностью |
| Шифры | много, включая CBC, RC4, 3DES | пять наборов AEAD |
| Имена наборов шифров | обмен ключами + аутентификация + шифр + MAC (`TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256`) | только шифр + хеш (`TLS_AES_128_GCM_SHA256`) |
| Шифрованное рукопожатие | нет, сертификат виден | всё после ServerHello |
| Удалено | | пересогласование, сжатие, статические RSA/DH, SHA-1, собственные группы DH |

- 1.3 экономит round trip, потому что клиент угадывает группу и отправляет свой key share в ClientHello. Если догадка неверна, сервер отвечает `HelloRetryRequest`, и рукопожатие стоит 2 RTT. Поток сообщений анимирован в [[tls-handshake-and-certificates]]; арифметика round trip вместе с TCP — в [[connection-establishment-cost]].

### 0-RTT и повтор
- После полного рукопожатия сервер присылает session ticket (pre-shared key). В следующий раз клиент может положить запрос в первый пакет как **early data**.
- Early data зашифрованы, но не защищены от повтора (replay): атакующий на пути копирует первый пакет и отправляет его снова, возможно, на другой сервер кластера. Разрешай их только для идемпотентных запросов; серверы отклоняют их ответом `425 Too Early`, а прокси пересылают их с заголовком `Early-Data: 1`. TLS-стек JDK поддерживает возобновление, но не отправляет и не принимает early data.

### Ключи, CSR и форматы файлов
- **Закрытый ключ**: PEM `BEGIN PRIVATE KEY` (PKCS#8) или более старый `BEGIN RSA PRIVATE KEY` (PKCS#1). **CSR** (PKCS#10): публичный ключ + запрошенные субъект и SAN, подписанные закрытым ключом; его отправляют в CA, а ключ никогда не покидает хост.
- **Самоподписанный сертификат**: издатель = субъект; годится для локальной разработки и тестов, бесполезен для публичных клиентов, если они явно не доверяют именно этому сертификату.
- **PEM** — это текст в Base64, **DER** — те же байты в бинарном виде. **PKCS12** (`.p12`, `.pfx`) упаковывает ключ + цепочку под паролем и является типом keystore по умолчанию начиная с Java 9; **JKS** — устаревший формат только для Java.

## Пример
Локальный CA, ключ сервера с CSR, подписанный сертификат и файл PKCS12 для JVM (OpenSSL 3.x).
```bash
# локальный CA: ключ + самоподписанный сертификат
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes \
  -keyout ca.key -out ca.crt -days 3650 -subj "/CN=esim dev CA"

# ключ сервера и CSR с SAN, которые будут проверять клиенты
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out server.key
openssl req -new -key server.key -out server.csr -subj "/CN=esim-api.local" \
  -addext "subjectAltName=DNS:esim-api.local,DNS:localhost,IP:127.0.0.1"

# подписать CSR ключом CA, сохранив расширение SAN из CSR
openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial \
  -days 90 -copy_extensions copy -out server.crt
openssl x509 -in server.crt -noout -subject -issuer -ext subjectAltName

# ключ + цепочка в PKCS12 для Java, затем просмотр
openssl pkcs12 -export -inkey server.key -in server.crt -certfile ca.crt \
  -name esim-api -out server.p12 -passout pass:changeit
keytool -list -keystore server.p12 -storetype PKCS12 -storepass changeit

# проверка: доверять только dev CA
curl --cacert ca.crt https://localhost:8443/actuator/health
```
```yaml
# Spring Boot 3.1+: отдавать HTTPS из PEM-файлов (или указать jks bundle на server.p12)
server:
  port: 8443
  ssl:
    bundle: esim-server
spring:
  ssl:
    bundle:
      pem:
        esim-server:
          keystore:
            certificate: "file:/etc/esim/tls/server.crt"
            private-key: "file:/etc/esim/tls/server.key"
          reload-on-update: true
```

## Подводные камни
- Сертификат без SAN: современные клиенты игнорируют CN и падают с несовпадением имени хоста. Всегда передавай `subjectAltName`.
- `openssl x509 -req` до OpenSSL 3.0 теряет расширения из CSR; добавь их через `-extfile`, иначе в сертификате не будет SAN.
- Включение 0-RTT на прокси перед API с неидемпотентными POST: повторённый запрос на оплату выполнится дважды ([[idempotency]]).
- Коммит `server.key` или `.p12` с паролем в `application.yml`; храни их в хранилище секретов ([[secrets-management]]).
- Сервер, который всё ещё предлагает TLS 1.2 с наборами `TLS_RSA_*`, не даёт этим клиентам прямой секретности; ограничь 1.2 наборами ECDHE.
- Связанные заметки: [[tls-handshake-and-certificates]] — цепочки, trust store и сообщения об ошибках; [[mtls-and-service-to-service-auth]] — клиентские сертификаты.
