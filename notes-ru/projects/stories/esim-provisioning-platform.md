## Кратко
В Beeline Кыргызстан я делаю бэкенд, который позволяет абоненту получить eSIM, не приходя в офис продаж: заказ → резервирование профиля → взаимодействие с SM-DP+ и entitlement-сервером → активация в биллинге и HLR → уведомление клиента. Стек — Java 21 / Spring Boot 3 на PostgreSQL и Kafka, а длительный процесс оркестрирует Temporal. Мой главный вклад — сделать многошаговый процесс, проходящий через ненадёжные внешние системы, надёжным, идемпотентным и наблюдаемым.

## Контекст и цель
- Было: выдача eSIM шла вручную силами операторов, и никто не мог сказать, где застряла активация.
- Цель: самообслуживание из мобильного приложения на Flutter и веб-клиента, автоматический retry или компенсация каждого шага, полная прозрачность по каждому заказу.
- Команда: [~4 бэкенд-разработчика, 1 Flutter/веб-разработчик, 1 QA] <!-- fill in real number -->. Я пишу задачи по API для клиентской части.
- Нагрузка: [~5 тыс. активаций в день] <!-- fill in real number --> с пиками во время кампаний. Каждая активация затрагивает 3–4 внешние системы с задержками от 200 мс до десятков секунд.

## Архитектура
- REST API на Spring Boot 3 (заказы, статус, QR/код активации) за корпоративным шлюзом; аутентификация через JWT ([[jwt-authentication]]).
- PostgreSQL для заказов, профилей и outbox-таблицы; Kafka для доменных событий, которые потребляют уведомления и аналитика ([[outbox-pattern]]).
- Отдельный Temporal workflow на каждый заказ: activities `reserveProfile`, `callSmDpPlus`, `entitlement`, `activateBilling`, `activateHlr`, `notify`. У каждой activity своя политика retry и свой таймаут ([[temporal-concepts]]).
- Гексагональная структура: домен и прикладные сервисы в ядре, адаптеры для SM-DP+, биллинга, HLR, Kafka и JPA на границе ([[ddd-basics]]).
- Трассировка OpenTelemetry через Flutter-приложение, API и Temporal-воркеры с помощью W3C `traceparent` ([[distributed-tracing]]); Grafana/Tempo для поиска по id заказа.
- Deploy через Docker Compose на корпоративных виртуальных машинах ([[docker-fundamentals]]).

```
Flutter / web ──HTTP──▶ API (Spring) ──start──▶ Temporal server
                           │                         │
                      Postgres (orders,       Worker (activities)
                       outbox) ──relay──▶ Kafka   ├─▶ SM-DP+ (profile)
                                                  ├─▶ Entitlement server
                                                  ├─▶ Billing
                                                  ├─▶ HLR
                                                  └─▶ Notify (push/SMS)
```

## Моя роль и решения
- Выбрал Temporal вместо самописной машины состояний на Kafka: retry, таймеры, таймауты и история достаются бесплатно, а на вопрос «где застрял заказ X» отвечает Temporal UI вместо раскопок в логах. Сначала оценил хореографическую [[saga]] и отказался от неё из-за объёма служебного кода.
- Внедрил transactional outbox, чтобы состояние заказа и события в Kafka не могли разойтись. Написал ретранслятор (relay) с `FOR UPDATE SKIP LOCKED` для работы в двух экземплярах.
- Определил ключи идемпотентности для каждого внешнего вызова (id заказа + шаг), чтобы повторная activity не могла зарезервировать два профиля или списать деньги дважды ([[idempotency]]).
- Написал контракт API и задачи для Flutter-клиента, включая проброс заголовков трассировки.
- Настроил уровни тестирования: Mockito для доменных правил, Testcontainers для Postgres/Kafka, `TestWorkflowEnvironment` из Temporal с пропуском времени (time skipping) для логики workflow ([[junit-and-mockito]], [[testcontainers]]).

## Самая сложная проблема и как я её решил
Вызов SM-DP+ мог завершиться по таймауту уже после того, как профиль на самом деле был зарезервирован. Наивный retry резервировал второй профиль, а наивный отказ оставлял абонента ни с чем и «терял» профиль в пуле. Исправление состояло из трёх частей:
1. Каждый запрос на резервирование несёт детерминированный ключ идемпотентности (`orderId:reserve`). Перед новым резервированием адаптер запрашивает состояние профиля по этому ключу.
2. Activity резервирования получила короткий таймаут с ограниченной политикой retry и компенсирующую activity `releaseProfile`, зарегистрированную в списке в стиле саги внутри workflow. Если более поздний шаг (биллинг, HLR) окончательно падает, компенсации выполняются в обратном порядке.
3. Для застрявших заказов я добавил heartbeat в долгие activities и workflow query `status()`, доступный через API. Поддержка видит текущий шаг и последнюю ошибку, не читая логи, а один trace id связывает запрос из мобильного приложения с вызовом HLR.
Второй урок касался детерминизма: я поместил `LocalDateTime.now()` и генератор случайных id в код workflow, и после deploy это сломало replay. Я перенёс их в activities / `Workflow.sideEffect` и добавил replay-тест в CI.

## Что бы я сделал иначе
- Сразу заложил бы гексагональные границы: первая версия смешивала JPA-сущности с workflow activities, и рефакторинг был болезненным.
- Раньше договорился бы о контрактах ошибок с командами SM-DP+ и биллинга: половина логики компенсаций существует потому, что «таймаут» и «уже выполнено» невозможно было различить.
- Добавил бы нагрузочные тесты до первой кампании, а не после неё (пик в [~2x] <!-- fill in real number --> обнаружили в продакшене).
- Использовал бы Kubernetes вместо Compose для воркеров: масштабировать Temporal-воркеры вручную неудобно ([[kubernetes-basics]]).

## Вероятные вопросы на собеседовании
- Почему Temporal, а не Kafka плюс машина состояний? Надёжное выполнение (durable execution), retry, таймеры и история из коробки; код читается как последовательный процесс; UI отвечает на вопрос «где застряло».
- Как гарантировать, что событие опубликуется, когда заказ сохранён? Transactional outbox в той же транзакции Postgres, ретранслятор в Kafka, доставка at-least-once плюс идемпотентные consumers.
- Что означает идемпотентность в вашем процессе? У каждого внешнего вызова есть ключ, построенный из id заказа и шага; при retry выполняется запрос состояния или повтор результата, а не повторное действие.
- Что такое детерминизм в Temporal и как ты его нарушил? Код workflow при replay должен выдавать те же команды. Я использовал `now()` и random внутри workflow; исправил через activities и `sideEffect`.
- Как компенсировать упавший шаг? Регистрировать действия отмены по мере успешного выполнения шагов; при окончательном сбое выполнять их в обратном порядке (освободить профиль, отменить строку биллинга).
- Как отследить одну активацию от начала до конца? W3C `traceparent` из Flutter через API в заголовки Temporal; OTel Collector в Tempo; поиск по атрибуту id заказа.
- Как тестировать workflow? `TestWorkflowEnvironment` с замоканными activities и пропуском времени; Testcontainers для адаптеров; replay-тест на историях из продакшена.
- Какой был самый крупный инцидент в продакшене? Двойное резервирование профиля после таймаутов SM-DP+; исправлено ключами идемпотентности и компенсацией.
