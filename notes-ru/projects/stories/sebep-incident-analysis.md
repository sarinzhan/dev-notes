## Кратко
«Себеп» (по-кыргызски «причина») — внутренний инструмент, который я сделал в Beeline. Он превращает алерт Sentry в объяснение корневой причины в Telegram в течение минуты: вебхук Sentry → мост на Spring Boot → Python-пайплайн, который собирает стектрейс и связанный код из GitLab → Claude пишет объяснение → Telegram. Параллельно я развернул стек наблюдаемости (OTel Collector, Mimir, Grafana, Loki, Tempo) и добился от руководства и службы информационной безопасности одобрения на отправку контекста кода в LLM.

## Контекст и цель
- Было: ошибка в продакшене означала 15–40 минут, пока разработчик копался в Sentry, коммитах и коде, прежде чем кто-то понимал, серьёзно ли это.
- Цель: для каждой новой или регрессировавшей задачи (issue) в Sentry публиковать в Telegram короткое сообщение с вероятной причиной, подозрительными строками и коммитом, который их внёс, чтобы разбор (triage) начинался с гипотезы.
- Масштаб: [~12] <!-- fill in real number --> бэкенд-сервисов, self-hosted Sentry, GitLab. Большую часть времени я был единственным разработчиком Себепа, с бюджетом side-проекта в [~2 месяца] <!-- fill in real number -->.

## Архитектура
- Self-hosted Sentry (со своими Kafka, ClickHouse, Redis, Postgres) отправляет вебхуки по issues.
- Мост на Spring Boot: проверяет HMAC-подпись с помощью client secret Sentry, выполняет дедупликацию и debounce (один id issue → не больше одного анализа за окно), сохраняет запрос в Postgres и публикует задание во внутреннюю очередь.
- Python-пайплайн на FastAPI: получает событие и стектрейс через Sentry API, сопоставляет фреймы с файлами в GitLab, вытягивает нужные фрагменты и недавние коммиты, которые их затрагивали (`git blame` через GitLab API), собирает ограниченный по размеру промпт и вызывает Claude.
- Результат публикуется в Telegram со ссылками обратно на Sentry и GitLab. Кнопки обратной связи («полезно / неверно») сохраняются для отслеживания качества.
- Стек наблюдаемости для всех сервисов: OTel Collector → Mimir (метрики), Loki (логи), Tempo (трейсы), дашборды и алерты в Grafana ([[logging-stacks]], [[otel-metric-types]], [[distributed-tracing]]).
- Всё работает в Docker Compose на внутренних виртуальных машинах за корпоративным прокси FortiGate ([[docker-fundamentals]]).

```
Sentry ──webhook (HMAC)──▶ Bridge (Spring) ──job──▶ Pipeline (FastAPI)
                              │ debounce,                 ├─▶ Sentry API (event, frames)
                              │ Postgres                  ├─▶ GitLab API (code, blame)
                              ▼                           ├─▶ Claude (root-cause draft)
                          Grafana / Loki / Tempo ◀─OTel──┴─▶ Telegram
```

## Моя роль и решения
- Предложил проект, написал одностраничный дизайн-документ и представил его руководству и службе информационной безопасности. Одобрение зависело от минимизации данных: только фреймы стека, ±30 строк вокруг них и метаданные коммитов; никаких конфигов, секретов и данных клиентов; белый список файлов и regex-очистка токенов и MSISDN, прежде чем что-либо покинет сеть.
- Намеренно разделил систему на два языка: Spring для частей, которые должны быть надёжными и проходить аудит (проверка подписи, сохранение, retry), Python для частей, которые быстро меняются (промпты, разбор ответов).
- Сделал дашборды и правила алертов в Grafana, которыми команда пользуется каждый день. Сам Себеп отдаёт метрики (анализов в час, задержка LLM, количество токенов, доля положительных отзывов).

## Самая сложная проблема и как я её решил
Первую неделю в продакшене занимали три практические проблемы, а вовсе не качество ИИ.
1. **Шторм алертов.** Баг в Kafka consumer породил тысячи одинаковых событий в Sentry, и мост ставил анализ в очередь для каждого. Я добавил двухуровневый debounce: окно в памяти с ключом по id issue плюс строку в Postgres с `last_analysed_at` и ограничением уникальности, так что даже два экземпляра моста не могут проанализировать одно и то же дважды. Теперь анализ запускают только действия вебхука «new issue» и «regression», а обычные действия «event» игнорируются.
2. **Корпоративная инспекция TLS.** Прокси FortiGate переподписывает исходящий TLS, поэтому Python падал с ошибками сертификатов, а Java — с `PKIX path building failed`. Решением был импорт корпоративного CA в оба хранилища доверенных сертификатов на этапе сборки образа, а не отключение проверки. Секреты переехали из `.env`-файлов в Docker secrets.
3. **Выдуманные причины.** Claude иногда обвинял файл, которого не было в трейсе. Я ограничил промпт: модель обязана цитировать фрейм и строку, на которые опирается, может ответить «недостаточно контекста», а пайплайн отклоняет ответы, ссылающиеся на путь вне переданных фрагментов. Размер промпта ограничен глубиной фреймов и бюджетом токенов. Кнопки обратной связи дают измеримую долю «полезно» — [~70%] <!-- fill in real number -->.
Эксплуатация self-hosted Sentry оказалась отдельной работой: однажды у ClickHouse закончилось место на диске, а его Kafka consumers отставали после перезапуска. Я добавил настройки хранения (retention) и алерты в Grafana на оба случая.

## Что бы я сделал иначе
- Собрал бы набор для оценки из прошлых инцидентов с известными причинами, прежде чем настраивать промпты на ощущениях.
- С самого начала поставил бы очередь между мостом и пайплайном вместо HTTP с retry ([[rabbitmq-basics]]).
- Написал бы политику обработки данных до демо: круг согласования занял больше времени, чем код.
- Пересмотрел бы использование двух рантаймов: один Spring-сервис с LLM-клиентом на Java было бы проще разворачивать и мониторить.

## Вероятные вопросы на собеседовании
- Как проверить, что вебхук действительно от Sentry? HMAC-SHA256 от сырого тела запроса с общим секретом, сравниваемый за постоянное время с заголовком `sentry-hook-signature`.
- Как обработать 1000 алертов за минуту? Запускать анализ только на новые/регрессировавшие issues, окно в памяти плюс ограничение уникальности в БД на issue и период охлаждения (cooldown), глобальный rate limit.
- Как ты получил одобрение безопасности на отправку кода в LLM? Минимизация данных, очистка, белый список, никаких данных клиентов, письменная политика, демо на реальных анонимизированных случаях.
- Как ограничить галлюцинации? Заставлять ссылаться на переданные фреймы, разрешать ответ «недостаточно контекста», отклонять ответы со ссылками на неизвестные файлы, измерять через обратную связь.
- Зачем Spring и Python вместе? Надёжная проверяемая граница на Java; быстрые итерации над промптами на Python; у каждого своя OTel-инструментация.
- Что сломалось в продакшене? Прокси с инспекцией TLS, работа с секретами, диск и отставание собственных Kafka/ClickHouse у Sentry.
- Как ты измерял пользу? Время от алерта до первой гипотезы, доля положительных отзывов, количество анализов, указавших на правильный коммит.
- Что входит в твой стек наблюдаемости и почему не Elastic? OTel Collector в Mimir/Loki/Tempo, сверху Grafana; одно семейство языков запросов, более дешёвое хранение и трейсы, связанные с логами по trace id.
