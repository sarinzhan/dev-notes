## Кратко
Распределённая блокировка говорит: «делать X одновременно может только один процесс», но никакой сервис блокировок не может заставить *приостановленного* или *отрезанного сетью* владельца остановиться. После паузы GC или потерянного heartbeat блокировка истекает, её захватывает другой процесс, а первый просыпается, всё ещё считая, что держит её: два писателя одновременно. Решение — **fencing-токен (fencing token)**: число, которое растёт с каждым захватом блокировки и которое проверяет **защищаемый ресурс** (база данных, сервис хранения), отклоняя любую запись с токеном меньше наибольшего из уже виденных. Без fencing распределённая блокировка — это оптимизация эффективности, а не гарантия корректности.

## Основное

### Две причины блокировать с разными требованиями
| Цель | Если не сработает | Что нужно |
|---|---|---|
| **Эффективность**: не делать одну и ту же дорогую работу дважды (отправить отчёт, перестроить кеш) | потраченная впустую работа, дубль письма | блокировка с TTL в Redis, ShedLock, advisory lock в БД; дёшево и достаточно |
| **Корректность**: не дать двум писателям испортить общее состояние (двойная активация, двойное списание) | потеря данных или денег | блокировка **плюс fencing** на ресурсе или вообще без блокировки — транзакционный/идемпотентный дизайн |

- Большинство разговоров «нам нужна распределённая блокировка» относятся к первому случаю. Во втором случае сначала спроси, может ли база данных обеспечить инвариант напрямую (уникальное ограничение, условное обновление, `SELECT ... FOR UPDATE`), прежде чем добавлять сервис блокировок ([[postgres-locks]], [[jpa-locking]]).

### Почему одной блокировки недостаточно
1. Клиент A захватывает блокировку с TTL 30 с.
2. У A случается stop-the-world пауза GC на 40 с или пропадает сеть до сервиса блокировок.
3. Блокировка истекает; клиент B захватывает её и пишет.
4. A возобновляет работу, считает, что всё ещё держит блокировку, и записывает устаревшие данные поверх данных B.

Никакая настройка таймаутов это не исправит: владелец не может узнать о своей паузе раньше, чем она закончится ([[time-and-clocks]], [[failure-modes-and-timeouts]]). Сервис блокировок ни в чём не ошибся; ресурс доверился клиенту, у которого не было способа узнать, что он опоздал.

### Fencing-токены
- Сервис блокировок при каждой выдаче возвращает **монотонно возрастающий** токен: `zxid` / версия znode в ZooKeeper, lease id плюс revision в etcd, последовательность Postgres или колонка `term` в таблице аренды ([[quorums-and-leader-election]]).
- Каждая запись в защищаемый ресурс несёт токен. Ресурс хранит наибольший принятый токен и отклоняет всё, что меньше: в стиле `UPDATE ... WHERE fence_token <= :token` или compare-and-set по версии объекта ([[lock-free-and-cas]]).
- Ресурс должен уметь это обеспечивать, что исключает «ресурсы» вроде SMTP-сервера или стороннего API. Для них приходится возвращаться к ключам идемпотентности ([[idempotency]]).

### Сравнение сервисов блокировок
| | Redis `SET NX PX` (один узел) | Redlock (N мастеров Redis) | ZooKeeper / etcd | Advisory lock / блокировка строки в Postgres |
|---|---|---|---|---|
| Безопасность при потере узла | блокировка может потеряться при failover (асинхронная репликация) | спорно: полагается на ограниченный дрейф часов и отсутствие пауз, сам по себе fencing-токена не даёт | на основе консенсуса, линеаризуем, даёт монотонный токен | безопасен настолько же, насколько БД; блокировка умирает вместе с сессией |
| Живучесть при падении владельца | истечение TTL | истечение TTL | истечение сессии/аренды (heartbeat) | закрытие соединения |
| Задержка | меньше мс | мс, N сетевых обменов | мс (запись в кворум) | меньше мс, та же БД |
| Хорош для | блокировок ради эффективности, rate limits | не рекомендуется по сравнению с более простыми вариантами | выбора лидера, блокировок ради корректности с fencing | блокировок, защищающих данные в той же БД |

- Спор о Redlock (Kleppmann против antirez): Redlock предполагает, что пауз процесса дольше TTL не бывает и часы ведут себя хорошо; без fencing это всё ещё «заблокируй и надейся». Для эффективности он годится; для корректности используй хранилище на консенсусе или базу данных ([[redis-patterns-and-persistence]]).
- В Spring: ShedLock (`@SchedulerLock`) для «запусти эту задачу на одном экземпляре», `JdbcLockRegistry`/`RedisLockRegistry` из Spring Integration для явных блокировок; workflows в Temporal устраняют необходимость в большинстве блокировок, гарантируя одно выполнение на workflow id ([[temporal-concepts]]).

### Альтернативы без блокировок (часто лучше)
- **Уникальное ограничение** для «только одна активация на ICCID»: арбитр — база данных.
- **Условное обновление** с колонкой версии: оптимистичная блокировка — это fencing-токен, который у тебя уже есть ([[jpa-locking]]).
- **Один писатель на ключ (single-writer)**: направляй всю работу по одному ключу в одну партицию Kafka и одному consumer ([[sharding-strategies]], [[kafka-consumer]]).

## Пример
Проверка fencing в защищаемом ресурсе. Сервис блокировок (etcd, ZooKeeper или таблица аренды из [[quorums-and-leader-election]]) выдаёт `token`; хранилище отклоняет устаревших писателей на уровне строки.
```java
@Repository
@RequiredArgsConstructor
public class ProfileStateRepository {
    private final JdbcTemplate jdbc;

    /** Возвращает false, если более новый владелец блокировки уже записал: вызывающий код должен прерваться. */
    public boolean writeState(String iccid, String newState, long fenceToken) {
        int rows = jdbc.update("""
            UPDATE esim_profile
               SET state = ?, last_fence_token = ?, updated_at = now()
             WHERE iccid = ?
               AND last_fence_token < ?          -- отклонить, если мы устарели
            """, newState, fenceToken, iccid, fenceToken);
        return rows == 1;
    }
}

// в сервисе
long token = lock.acquire("profile:" + iccid);         // например, revision аренды в etcd
try {
    if (!repo.writeState(iccid, "DOWNLOADED", token)) {
        throw new StaleLockException("fence token " + token + " rejected for " + iccid);
    }
} finally {
    lock.release("profile:" + iccid);
}
```
Клиент, проспавший свой TTL, всё равно позже вызовет `writeState`, но с токеном меньше того, который уже использовал новый владелец, поэтому update затронет ноль строк, и устаревший писатель об этом узнает ([[postgres-locks]]).

## Подводные камни
- Освобождение блокировки Redis обычным `DEL`: можно удалить чужую блокировку после истечения своего TTL. Храни случайное значение и удаляй, только если оно совпадает, в Lua-скрипте.
- Продление TTL в фоновом потоке («watchdog») прячет проблему пауз, а не решает её; поток продления встаёт на паузу вместе с остальной JVM.
- Захват распределённой блокировки, а внутри неё блокировки в БД, тогда как другой путь берёт их в обратном порядке: межсистемная взаимоблокировка, которую не видит ни один детектор ([[deadlocks-and-synchronization-primitives]]).
- Удержание блокировки во время внешнего HTTP-вызова без таймаута; TTL блокировки становится единственным ограничением ([[circuit-breaker]]).
- Связанные заметки: [[leases-heartbeats-and-health]] — про живучесть, [[raft-explained]] — почему revision в etcd заслуживает доверия, [[idempotency]] — для ресурсов, которые не умеют проверять токен.
