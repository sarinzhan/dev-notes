## Кратко
**Кворум** — минимальный набор узлов, которые должны согласиться, чтобы действие засчиталось. При кворуме **большинства** (больше N/2) любые два кворума пересекаются хотя бы в одном узле, поэтому две группы никогда не могут одновременно считать себя главными: именно это пересечение предотвращает **split brain** (расщепление мозга). Выбор лидера (leader election) — это «получить кворум большинства для утверждения *я лидер в терме T*», а **аренда (lease)** добавляет ограничение по времени, чтобы лидер мог действовать, не переспрашивая на каждой операции. Цена: при N узлах ты переживаешь потерю меньше половины, и чтобы выдерживать f отказов, нужно 2f+1 узлов.

## Основное

### Арифметика большинства
| Узлов N | Кворум | Выдерживает отказов | Примечания |
|---|---|---|---|
| 1 | 1 | 0 | единственный primary |
| 2 | 2 | 0 | хуже, чем 1: отказ любого узла блокирует запись |
| 3 | 2 | 1 | обычный минимум для etcd/ZooKeeper/KRaft |
| 4 | 3 | 1 | та же устойчивость, что у 3, но больше накладных расходов |
| 5 | 3 | 2 | выдерживает отказ одного узла во время обслуживания другого |
| 7 | 4 | 3 | убывающая отдача; каждая запись ждёт 4 подтверждения |

- Устойчивость f = floor((N−1)/2). Для голосующих узлов всегда используй нечётное N; дополнительные неголосующие реплики (observers, learners) могут обслуживать чтение, не влияя на кворум.
- Свойство пересечения — вся суть: кворум A ∩ кворум B ≠ ∅. Узел в пересечении знает об обоих утверждениях и отклоняет то, у которого терм более поздний.

### Кворумы для данных, а не только для лидеров
- В стиле Dynamo **W + R > N**: запись в W реплик, чтение из R, и хотя бы один узел в наборе чтения имеет последнюю запись. `N=3, W=2, R=2` — частый вариант; `W=1` быстро и небезопасно; `W=N` безопасно и недоступно ([[multi-leader-and-leaderless]]).
- **ISR** в Kafka — кворум другой формы: не большинство, а «все реплики, которые сейчас синхронизированы», с `min.insync.replicas` в качестве нижней границы. Данные считаются закоммиченными, когда они есть у каждого члена ISR, поэтому Kafka выдерживает N−1 отказов с точки зрения надёжности ценой сжимающегося ISR под нагрузкой ([[kafka-architecture]]).
- Синхронная репликация Postgres с `synchronous_standby_names = 'ANY 1 (s1, s2)'` — это кворум записи 2 из 3 ([[postgres-replication-and-failover]]).

### Split brain: как возникает и как кворум его останавливает
- Разделение сети отрезает {A, B} от {C}. C перестаёт слышать лидера A и начинает выборы. Без правил кворума C становится лидером своей стороны, а A остаётся лидером другой: две расходящиеся истории, которые потом невозможно безопасно слить.
- С кворумом большинства C не может получить 2 голоса из 3, остаётся follower и отказывает в записи; A и B продолжают работать. Когда разделение исчезает, C видит более высокий терм и догоняет. Доступностью стороны меньшинства жертвуют сознательно ([[cap-and-pacelc]]).
- **Fencing** — вторая половина: старый лидер может быть на паузе, а не мёртв, и всё ещё писать в общее хранилище; каждая запись должна нести терм/эпоху, которые проверяет получатель ([[distributed-locks-and-fencing]]).

### Механизмы выбора лидера
| Механизм | Как | Кто использует |
|---|---|---|
| Голосование консенсуса (Raft/ZAB) | кандидаты просят голоса, большинство выигрывает терм | etcd, ZooKeeper, KRaft, Consul ([[raft-explained]]) |
| Блокировка в сервисе координации | узлы наперегонки создают эфемерный ключ; владелец — лидер; истечение сессии освобождает его | приложения на ZooKeeper/etcd, старый выбор контроллера в Kafka, `LockRegistryLeaderInitiator` в Spring Integration |
| Аренда на базе БД | строка с `leader, lease_until`; условный `UPDATE ... WHERE lease_until < now()` | небольшие сервисы, кластеризация Quartz, ShedLock |
| Внешний сторож (watchdog) | Patroni использует аренду в etcd/Consul для primary Postgres | HA Postgres |
| Bully / рассылка эпохи | побеждает наибольший id, без кворума | legacy, небезопасно при разделении сети |

### Аренда: выборы без голосования на каждую операцию
- **Аренда** — это лидерство со сроком действия. Лидер продлевает её до истечения (heartbeat); followers начинают выборы только после истечения. Лидер, которому не удалось продлить аренду, должен **прекратить действовать** до момента истечения, иначе два лидера пересекутся.
- Корректность зависит от ограниченного дрейфа часов между узлами и от того, заметит ли владелец истечение, несмотря на паузы GC; поэтому одной аренды недостаточно для безопасной записи, нужен fencing-токен ([[leases-heartbeats-and-health]], [[time-and-clocks]]).

### Как отвечать на собеседовании
- «Три узла, один умер?» Большинство из 2 продолжает писать; два мёртвых означают режим только для чтения или недоступность — так задумано.
- «etcd в двух датацентрах?» Не при чётном разделении: 2+2 теряет кворум, когда рвётся связь. Используй 3+2 или 2+2+1 с узлом-арбитром.

## Пример
Аренда лидерства на базе БД с термом (fencing-токеном) для небольшого сервиса, который должен запускать один экземпляр планировщика. Условное обновление — это кворум из одного: Postgres сериализует доступ к строке, поэтому терм выигрывает только один экземпляр.
```sql
CREATE TABLE leader_lease (
    name        text PRIMARY KEY,
    holder      text NOT NULL,
    term        bigint NOT NULL,
    lease_until timestamptz NOT NULL
);

-- попытаться захватить или продлить; возвращает строку только победителю
UPDATE leader_lease
SET holder = :me,
    term = CASE WHEN holder = :me THEN term ELSE term + 1 END,
    lease_until = now() + interval '10 seconds'
WHERE name = 'esim-scheduler'
  AND (holder = :me OR lease_until < now())
RETURNING term;
```
Сервис вызывает это каждые 3 секунды; если строка не вернулась, он немедленно прекращает планирование. Каждая запись, которую выполняет планировщик, несёт `term`, чтобы устаревший экземпляр, проснувшийся после паузы, был отклонён проверкой `WHERE term >= :current_term` ниже по цепочке (почему `now()` внутри одного оператора согласован — см. [[postgres-locks]]).

## Подводные камни
- «Кластеры» из двух узлов с автоматическим failover: большинства не существует, поэтому либо оба могут стать primary (split brain), либо ни один (нет доступности). Добавь узел-свидетель (witness).
- Использование Redis `SETNX` с TTL для выборов: безопасно, только если выбранный узел также защищает свои записи fencing; TTL может истечь во время паузы ([[redis-patterns-and-persistence]]).
- Подсчёт кворума по зонам без учёта потери зоны: 3 голосующих узла в одной AZ — в одном отказе от полного отсутствия кворума.
- Observers/learners, случайно настроенные как голосующие: чётное количество, и теперь кворуму нужно больше подтверждений через самый медленный канал.
- Связанные заметки: [[raft-explained]] — полный протокол выборов, [[failure-modes-and-timeouts]] — почему «мёртвый» лидер может быть не мёртв.
