## Кратко
Когда данные шардированы, дорогими становятся две вещи: **запрос**, фильтр которого не содержит ключа шардирования (его нужно отправить на каждый шард и слить результаты: scatter-gather), и **транзакция**, затрагивающая строки на двух шардах (ей нужен протокол атомарного commit, например **двухфазный commit** (two-phase commit), который медленный и блокируется при отказе координатора). Практический ответ — спроектировать ключ шардирования так, чтобы и то и другое было редкостью, оставшиеся межшардовые чтения обслуживать из отдельной модели чтения, а межшардовые записи заменить сагами или идемпотентными шагами с согласованностью в конечном счёте.

## Основное

### Чтения scatter-gather
- Маршрутизатор рассылает запрос на все N шардов параллельно, ждёт все ответы (или кворум — для приблизительных результатов) и сливает: конкатенирует, заново сортирует, заново применяет `LIMIT`, заново агрегирует.
- Задержка = самый медленный шард (усиление хвостовой задержки, tail latency amplification): при 100 шардах и p99 = 50 мс на шард почти каждая рассылка натыкается на шард с 50 мс ([[latency-numbers]]).
- Ловушка — пагинация: `ORDER BY created_at LIMIT 20 OFFSET 1000` должен достать 1020 строк с *каждого* шарда. Используй пагинацию по ключу (keyset, `WHERE created_at < :cursor`), чтобы каждый шард возвращал только 20 ([[api-design-for-system-design]]).
- Агрегаты: `COUNT`/`SUM` сливаются тривиально; для `AVG` нужны сумма и количество с каждого шарда; `DISTINCT` и перцентилям нужны все значения или скетчи ([[bloom-filters-and-probabilistic]]).
- Elasticsearch и Cassandra делают это внутри себя; самописному маршрутизатору шардов нужна такая же логика слияния и таймауты.

### Как избежать scatter-gather
- **Располагать вместе** всё, что нужно одному сценарию, под одним ключом шардирования (абонент и все его SIM и заказы).
- **Глобальный вторичный индекс** или **таблица поиска**: `email → subscriber_id` на собственном шарде, затем один адресный запрос. Поддерживается асинхронно, поэтому может ненадолго отставать ([[sharding-strategies]]).
- **Модель чтения**, построенная из событий: отчёты по всем тенантам, админский поиск и аналитика идут в Elasticsearch, ClickHouse или отчётную реплику, которую наполняют CDC/outbox ([[cqrs]], [[search-and-indexing-services]], [[outbox-pattern]]).

### Межшардовые транзакции: двухфазный commit
- Участники: **координатор** и шарды (**участники**, participants). Фаза 1 `PREPARE`: каждый участник надёжно записывает свои изменения и запись о подготовке и голосует да/нет. Фаза 2 `COMMIT`/`ABORT`: координатор надёжно записывает решение, затем сообщает всем. Участник, проголосовавший «да», **обязан** ждать решения; отменить в одностороннем порядке он не может.
- Гарантирует атомарность между узлами. Цена: два сетевых круга плюс три fsync на критическом пути; блокировки удерживаются на протяжении обеих фаз; и знаменитая проблема **блокировки**: если координатор умирает после того, как участники подготовились, они держат блокировки и неопределённое состояние (in-doubt), пока он не вернётся ([[failure-modes-and-timeouts]]).
- Postgres это поддерживает (`PREPARE TRANSACTION`, `max_prepared_transactions`), в Java есть XA (`XADataSource`, JTA через Narayana/Atomikos); в Kafka XA нет. Осиротевшие подготовленные транзакции в Postgres блокируют vacuum и держат блокировки бесконечно ([[postgres-vacuum-and-bloat]], [[postgres-locks]]).
- 3PC добавляет фазу pre-commit, чтобы уменьшить блокировку, но предполагает ограниченные задержки; её никто не использует. Современные системы (Spanner, CockroachDB, YugabyteDB) выполняют 2PC *поверх групп Raft*, так что состояние координатора само реплицировано и не может потеряться ([[raft-explained]]).

### Альтернативы 2PC
| Подход | Атомарность | Изоляция | Когда |
|---|---|---|---|
| **Избежать**: перепроектировать ключ так, чтобы запись была на одном шарде | полная (локальная транзакция) | полная | первый выбор; большинство «межшардовых» потребностей — ошибки моделирования |
| **Сага** (хореография или оркестрация) | в конечном счёте, через компенсации | нет между шагами | бизнес-процессы: заказ → оплата → провижининг ([[saga]], [[temporal-concepts]]) |
| **Идемпотентные асинхронные шаги** через outbox/события | в конечном счёте | нет | денормализованные копии, счётчики, проекции ([[outbox-pattern]], [[idempotency]]) |
| **Единый источник истины + копия в конечном счёте** | источник истины атомарен; копии сходятся | нет для копий | один шард владеет фактом, остальные его кэшируют |
| **2PC / XA** | полная | зависит от участников | редко: две legacy-БД без других вариантов, JMS + JDBC |
| **Distributed SQL** (Spanner, CockroachDB) | полная | serializable | когда сложную часть делает вендор и задержка приемлема |

- Сага — не транзакция: шаг может увидеть частичный результат другой саги. Проектируй с учётом этого через состояния резервирования (`RESERVED` → `CONFIRMED`), а не притворяйся, что изоляция есть.

### Что делает транзакцию «распределённой»
- Любая единица работы, записи которой попадают в несколько независимых хранилищ со своим журналом коммитов: два шарда, базы двух сервисов, база и брокер сообщений. Каждый участник может закоммититься или упасть сам по себе, поэтому атомарность нужно координировать (2PC) или отказаться от неё и компенсировать (саги, outbox).
- Большинства «распределённых транзакций» в микросервисах лучше избегать, держа данные, которые меняются вместе, под одним ключом или в одном сервисе ([[saga]], [[outbox-pattern]]).

### Как подавать на собеседовании
- «Перевод денег между двумя пользователями на разных шардах?» Не делай 2PC по балансам. Добавь запись о переводе на шарде отправителя (списание + событие в outbox), идемпотентно обработай её на шарде получателя, пометь перевод завершённым; при отказе — компенсация. Леджер с неизменяемыми записями делает это естественным ([[design-payment-processing]]).
- «Поиск пользователей по имени по всем шардам?» Scatter-gather работает при малом N с ограниченной рассылкой; на масштабе — поисковый индекс, наполняемый событиями.

## Пример
Scatter-gather с ограниченной рассылкой, дедлайном и пагинацией по ключу поверх маршрутизатора шардов из [[sharding-strategies]].
```java
public record Page<T>(List<T> items, Instant nextCursor) {}

public Page<OrderRow> recentOrdersAcrossTenants(Instant cursor, int size) {
    String sql = """
        SELECT id, tenant_id, created_at FROM orders
        WHERE created_at < ? ORDER BY created_at DESC LIMIT ?""";   // LIMIT на каждый шард, без OFFSET

    List<CompletableFuture<List<OrderRow>>> calls = shards.values().stream()
        .map(ds -> CompletableFuture.supplyAsync(
            () -> new JdbcTemplate(ds).query(sql, ORDER_ROW, Timestamp.from(cursor), size), fanOutPool))
        .toList();

    List<OrderRow> merged = new ArrayList<>();
    for (var f : calls) {
        try { merged.addAll(f.get(800, TimeUnit.MILLISECONDS)); }       // дедлайн на шард
        catch (TimeoutException e) { f.cancel(true); partialResult.increment(); }  // деградировать, а не падать
    }
    merged.sort(Comparator.comparing(OrderRow::createdAt).reversed());
    List<OrderRow> page = merged.subList(0, Math.min(size, merged.size()));
    Instant next = page.isEmpty() ? null : page.getLast().createdAt();
    return new Page<>(page, next);
}
```
Каждый шард возвращает не больше `size` строк, слияние — это сортировка N·size строк, а медленный шард даёт помеченную частичную страницу вместо таймаута всего запроса ([[completable-future]], [[executors-and-thread-pools]]).

## Подводные камни
- Пагинация через `OFFSET` по шардам: цена растёт как номер страницы × число шардов; всегда используй keyset.
- XA, «потому что фреймворк поддерживает»: первая осиротевшая подготовленная транзакция после падения координатора объяснит, почему его избегают.
- Саги без идемпотентных шагов: повторённый шаг списывает деньги дважды; каждому шагу нужен ключ ([[idempotency]]).
- Неограниченные пулы потоков для рассылки: 50 шардов × 200 конкурентных запросов = 10 000 заблокированных потоков; используй ограниченный пул или виртуальные потоки с семафором ([[virtual-threads]]).
- Связанные заметки: [[sharding-strategies]] — как выбрать ключ, сохраняющий записи локальными, [[saga]] — замена через workflow, [[transactions-acid-and-isolation]] — от чего отказываешься, уходя с одного узла.
