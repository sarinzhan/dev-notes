## Кратко
Шардирование (sharding, горизонтальное разбиение по узлам) делит один логический набор данных по **ключу шардирования** (shard key), так что каждый узел владеет срезом ключей и срезом нагрузки. Три способа отобразить ключ → шард: **по диапазону** (range: непрерывные интервалы ключей, хорошо для сканирования диапазонов, склонно к горячим диапазонам), **по хешу** (hash: равномерное распределение, убивает запросы по диапазону), **через справочник** (directory: явная таблица поиска, гибко, но это зависимость на каждом запросе). Выбор ключа шардирования — это и есть весь дизайн: он решает, какие запросы остаются локальными, какие превращаются в scatter-gather и где появятся горячие точки. Декларативное партиционирование Postgres внутри одного узла — родственник этого и описано в [[postgres-partitioning]].

## Основное

### Зачем шардировать и почему пока не стоит
- Шардируй, когда один узел не может вместить данные или выдержать темп записи, после того как исчерпаны индексы, реплики для чтения и кэширование ([[database-scaling-path]]). Одни лишь чтения редко оправдывают шардирование; реплики дешевле ([[read-replicas-and-stale-reads]]).
- Шардирование на практике необратимо и отнимает то, что казалось само собой разумеющимся: межшардовые join, внешние ключи, ограничения уникальности, транзакции на одном узле ([[cross-shard-queries-and-transactions]]).

### Три стратегии
| Стратегия | Отображение | Запросы по диапазону | Риск горячих точек | Ребалансировка | Примеры |
|---|---|---|---|---|---|
| **По диапазону** | интервалы ключей: `[a–f] → s1, [g–m] → s2` | да, локальность по ключу | высокий: метки времени или последовательные id скапливаются на последнем шарде | разделить диапазон, переместить его | регионы HBase, таблеты Bigtable, ranged в MongoDB, Spanner |
| **По хешу** | `hash(key) mod N` или диапазоны хешей | нет, соседние ключи разбегаются | низкий для распределения ключей; всё ещё высокий для одного горячего ключа | `mod N` перемещает почти всё; диапазоны хешей / консистентное хеширование перемещают 1/N ([[consistent-hashing]]) | партиции Kafka, token ring в Cassandra, DynamoDB, слоты Redis Cluster |
| **Через справочник** | сервис поиска: `tenant 42 → shard 7` | зависит от того, что лежит вместе | размещением управляешь ты | перемещение по одной записи за раз | мультитенантный SaaS, vindexes в Vitess, Citus с `tenant_id` |

- Гибриды — норма: хешировать тенанта в шард, внутри него партиционировать по времени диапазонами; `(partition_key, clustering_key)` в Cassandra делает ровно это.

### Выбор ключа шардирования
- Бери ключ, по которому уже фильтрует большинство запросов: `subscriber_id` для телекома, `tenant_id` для SaaS, `order_id` для заказов, `account_id` для леджера ([[design-payment-processing]]).
- Все данные, которые нужно затронуть в одной транзакции, должны иметь общий ключ: абонент, его SIM-профили, его заказы. Это граница агрегата из DDD ([[aggregates-and-invariants]]).
- Запросы без ключа превращаются в **scatter-gather** по всем шардам; делай их редкими или обслуживай из отдельной модели чтения ([[cqrs]], [[search-and-indexing-services]]).
- Кардинальность и разброс: ключ с малым числом значений (страна) даёт мало неравных шардов; ключ с перекосом (один аккаунт знаменитости, один гигантский тенант) даёт горячий шард при любой стратегии.

### Горячие партиции
- Причины: последовательные ключи при шардировании по диапазону (все сегодняшние записи попадают на один шард), один горячий ключ при шардировании по хешу (вирусный пост, тенант с 40% трафика), перекос по времени суток.
- Исправления: **соль** в ключе (`userId + random(0..9)` — распределяет записи и стоит 10 чтений), **разделение** горячего диапазона, **изоляция** тяжёлого тенанта на собственный шард через справочник, **кэширование** горячего ключа перед базой ([[caching]]), а для счётчиков — шардированные счётчики, суммируемые при чтении.
- Вариант для Kafka: один ключ с большинством сообщений означает, что нагрузку несут одна партиция и один consumer; исправление — лучший ключ или подключи, а не больше партиций ([[kafka-architecture]]).

### Вторичные индексы при шардировании
- **Локальный** индекс (document-partitioned): каждый шард индексирует свои строки; чтения по вторичному атрибуту — scatter-gather. Записи остаются локальными. MongoDB, SAI в Cassandra, шарды Elasticsearch.
- **Глобальный** индекс (term-partitioned): сам индекс шардирован по индексируемому значению; чтения попадают на один шард, но запись обновляет индекс на другом шарде асинхронно (GSI в DynamoDB, с согласованностью в конечном счёте).

### Ребалансировка
- Фиксированное число партиций, большее числа узлов (например, 1024 на 10 узлов), при подключении узлов перемещаются целые партиции: Elasticsearch, Riak, 16384 слота Redis Cluster. Просто и предсказуемо.
- Динамическое разделение, когда диапазон перерастает размер: HBase, MongoDB.
- Никогда не используй `hash mod N`, где N = число узлов; добавление одного узла переназначает почти каждый ключ ([[consistent-hashing]]).
- Ребалансировка конкурирует с боевым трафиком за IO; ограничивай её скорость и не запускай автоматически на «мигающем» узле ([[failure-modes-and-timeouts]]).

### Шардирование вручную (демо из курса)
- Три контейнера Postgres (`pgshard1..3`) с одинаковой схемой `url_table(id serial, url text, url_id char(5))`. Приложение держит **консистентное хэш-кольцо** из трёх серверов ([[consistent-hashing]]).
- **Запись**: хэшировать URL в 5-символьный `url_id`, спросить кольцо, какой сервер владеет этим id, вставить туда, вернуть id. **Чтение**: один только id говорит приложению, какой шард спрашивать, — один круговой обмен, без рассылки по всем.
- Что показывает демо: маршрутизация — это код приложения, все клиенты должны использовать одно и то же кольцо, добавление четвёртого сервера означает миграцию переезжающих ключей, и нет ни межшардовых запросов, ни транзакций.

### Преимущества и недостатки
| Преимущества | Недостатки |
|---|---|
| масштабирует хранение, запись и память за пределы одной машины | сложный клиент или прокси, маршрутизация должна быть правильной везде |
| индексы на шарде меньше, кэш попадает чаще | нет межшардовых транзакций, соединений и глобальных ограничений |
| отказ одного шарда затрагивает только его ключи | изменения схемы на N серверах; ребалансировка — целый проект |
| шарды можно размещать ближе к их пользователям | запросы без ключа расходятся на все шарды |
- Когда задуматься о шардировании, по порядку: оптимизировать запросы и индексы, добавить кэш, добавить реплики на чтение, секционировать, увеличить сервер, разделить по сервисам (у каждого сервиса своя база). Шардировать, только когда запись или объём данных всё ещё перерастают один узел; Vitess в YouTube и шарды Postgres в Instagram — примеры стадии «выбора не было» ([[database-scaling-path]]).

## Пример
Маршрутизатор в стиле справочника для мультитенантной схемы на Postgres: по одному `DataSource` на шард, тенанты отображаются маленькой таблицей, закэшированной в памяти, горячий тенант изолирован на собственном шарде.
```java
@Component
public class ShardRouter {
    private final Map<String, DataSource> shards;              // "s0", "s1", "s2-big-tenant"
    private final LoadingCache<Long, String> tenantToShard;    // Caffeine, обновляется каждые 60 с

    public ShardRouter(Map<String, DataSource> shards, JdbcTemplate directoryDb) {
        this.shards = shards;
        this.tenantToShard = Caffeine.newBuilder().refreshAfterWrite(Duration.ofMinutes(1))
            .build(tenantId -> directoryDb.queryForObject(
                "SELECT shard FROM tenant_shard WHERE tenant_id = ?", String.class, tenantId));
    }

    public JdbcTemplate forTenant(long tenantId) {
        String shard = tenantToShard.get(tenantId);
        return new JdbcTemplate(shards.get(shard));
    }

    /** Scatter-gather для редкого запроса по всем тенантам; выполняется параллельно, сливается в памяти. */
    public <T> List<T> acrossAllShards(Function<JdbcTemplate, List<T>> query) {
        return shards.values().parallelStream()
            .flatMap(ds -> query.apply(new JdbcTemplate(ds)).stream()).toList();
    }
}
```
Каждый репозиторий, привязанный к тенанту, сначала вызывает `forTenant(tenantId)`; миграция тенанта — это: скопировать строки на новый шард, переключить строку в справочнике, удалить со старого ([[multi-tenancy-strategies]], [[schema-migrations-flyway-liquibase]]).

## Подводные камни
- Выбрать последовательный id или метку времени ключом шардирования по диапазону и обнаружить, что 100% вставок попадают на один узел.
- Шардировать, не починив схему: N+1 запросов и отсутствующие индексы становятся в N раз хуже ([[postgres-performance-checklist]]).
- Забыть, что `UNIQUE(email)` теперь действует в пределах шарда; глобальной уникальности нужен справочник, выделенный шард поиска или детерминированное размещение по этому атрибуту.
- Сервис-справочник, который является единой точкой отказа на горячем пути; кэшируй его агрессивно и делай реплицированным.
- Связанные заметки: [[consistent-hashing]] — шардирование по хешу с мягкой ребалансировкой, [[cross-shard-queries-and-transactions]] — что ломается между шардами, [[postgres-partitioning]] — партиционирование внутри одного узла Postgres.
