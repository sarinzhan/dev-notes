## Кратко
`hash(key) mod N` — ужасный способ распределять ключи по N узлам, потому что изменение N переназначает почти каждый ключ. **Консистентное хеширование** (consistent hashing) размещает и узлы, и ключи на кольце хеш-значений (от 0 до 2^32−1); ключ принадлежит первому узлу по часовой стрелке от него. Добавление или удаление узла перемещает только ключи одной дуги — примерно 1/N от всех. **Виртуальные узлы** (virtual nodes: много позиций на кольце для одного физического узла) исправляют неравные дуги, которые даёт случайное размещение, и позволяют большой машине владеть большей частью кольца. Используется в Cassandra, DynamoDB, Riak, клиентах Memcached, балансировке Envoy/nginx и CDN.

## Основное

### Проблема с остатком от деления
- 4 узла кэша, `node = hash(key) % 4`. Добавляем пятый: `hash % 5` отличается от `hash % 4` примерно для 80% ключей. Каждый такой ключ теперь промах кэша на новом узле и устаревшая запись на старом; база данных за кэшем получает всю нагрузку разом ([[distributed-cache-coherence]]).
- То же касается шардированных баз данных: решардинг по остатку означает перенос большей части данных ([[sharding-strategies]]).

### Кольцо
- Хешируй id узлов (`"cache-1"`, `"cache-2"`) и ключи одной и той же функцией в кольцевое пространство. Каждым ключом владеет ближайший узел по часовой стрелке (его **преемник**, successor).
- Добавляем узел X между A и B: от B к X переходят только ключи дуги (A, X]. Удаляем узел B: его дуга переходит к его преемнику. Ожидаемое перемещение на одно изменение: K/N ключей.
- Репликация получается естественно: хранить ключ на его преемнике и на следующих R−1 различных физических узлах по часовой стрелке (**список предпочтений**, preference list, в Dynamo).

### Виртуальные узлы (vnodes)
- При одной позиции на узел случайное размещение даёт дуги очень разного размера: один узел может владеть 3× от среднего. Решение: каждый физический узел получает V позиций (`"cache-1#0"` … `"cache-1#149"`). При V ≈ 100–200 нагрузка на узел отличается от средней на несколько процентов.
- Разнородное железо: узлу с вдвое большим объёмом RAM дай вдвое больше vnodes.
- В Cassandra по умолчанию 16 vnodes на узел (раньше было 256); DynamoDB и Riak используют фиксированные партиции, назначаемые узлам, — та же идея, только кольцо заранее нарезано на равные куски.
- Цена: поиск преемника — это поиск в отсортированной map, O(log(N·V)); метаданные кольца растут с V; восстановление данных узла при отказе идёт потоками от большего числа соседей (что на самом деле хорошо для скорости).

### Варианты, которые стоит назвать на собеседовании
- **Rendezvous-хеширование (HRW)**: для каждого ключа вычислить `hash(key, node)` для каждого узла и выбрать максимум. Без кольца, идеально равномерно, O(N) на поиск; годится для малых N — например, горстки кэш-серверов или балансировщика.
- **Jump consistent hash** (Google): O(1) памяти, отображает ключи в номера корзин 0..N−1 с минимальным перемещением; корзины можно удалять только с конца, поэтому подходит для пронумерованных шардов, а не для потери произвольного узла.
- **Maglev** (балансировщик Google): таблица поиска, построенная так, что изменения бэкендов затрагивают мало записей, с поиском за O(1).

### Аналогия с Kafka (и отличие)
- Kafka *не* использует консистентное хеширование: producer вычисляет `murmur2(key) % numPartitions`. Поэтому **изменение числа партиций ломает стабильность отображения ключ→партиция**: записи по ключу начинают попадать в другую партицию, и порядок по ключу на этой границе теряется ([[kafka-producer]], [[kafka-architecture]]).
- Фиксированное число партиций работает как заранее нарезанное кольцо: партиции — это единицы, которые перемещаются между брокерами (reassignment) и между consumer (rebalance); отображение ключ→партиция никогда не меняется. Assignor consumer group **sticky/cooperative** — это свойство «перемещать как можно меньше», применённое к партициям вместо ключей ([[kafka-consumer]]).

### Где это встречается
- Шардирование кэша на стороне клиента: Memcached (Ketama), Redis Cluster использует 16384 хеш-слота, назначенных узлам (заранее нарезанное кольцо), с `CRC16(key) % 16384` ([[redis-patterns-and-persistence]]).
- Балансировщики с привязкой сессий: nginx `hash $cookie_sid consistent`, ring hash и Maglev в Envoy — так что удаление одного бэкенда перемещает только его собственные сессии ([[load-balancing]]).
- Базы данных: token ring в Cassandra, DynamoDB, диапазоны CockroachDB (по диапазонам, но идея ребалансировки та же), ScyllaDB.
- Объединение запросов и ограничение частоты: направлять все запросы по одному ключу на один узел, чтобы его локальное состояние было авторитетным ([[rate-limiting]]).

## Пример
Компактное кольцо с виртуальными узлами и 32-битными позициями на основе MD5 — как маршрутизатор на стороне клиента поверх узлов кэша или шардов.
```java
public final class HashRing<N> {
    private final TreeMap<Integer, N> ring = new TreeMap<>();
    private final int vnodes;

    public HashRing(Collection<N> nodes, int vnodes) {
        this.vnodes = vnodes;
        nodes.forEach(this::add);
    }

    public void add(N node) {
        for (int i = 0; i < vnodes; i++) ring.put(hash(node + "#" + i), node);
    }

    public void remove(N node) {
        for (int i = 0; i < vnodes; i++) ring.remove(hash(node + "#" + i));
    }

    /** Владелец ключа: первая позиция на кольце по часовой стрелке, с переходом через начало. */
    public N nodeFor(String key) {
        if (ring.isEmpty()) throw new IllegalStateException("no nodes");
        Map.Entry<Integer, N> e = ring.ceilingEntry(hash(key));
        return (e != null ? e : ring.firstEntry()).getValue();
    }

    /** Владелец ключа плюс следующие (replicas-1) различных физических узлов по часовой стрелке. */
    public List<N> preferenceList(String key, int replicas) {
        List<N> result = new ArrayList<>(replicas);
        for (N n : ring.tailMap(hash(key), true).values()) if (!result.contains(n) && result.size() < replicas) result.add(n);
        for (N n : ring.values()) if (result.size() < replicas && !result.contains(n)) result.add(n);
        return result;
    }

    private static int hash(String s) {
        byte[] d = md5().digest(s.getBytes(StandardCharsets.UTF_8));   // MD5/murmur3: равномерно и достаточно быстро
        return (d[0] & 0xff) << 24 | (d[1] & 0xff) << 16 | (d[2] & 0xff) << 8 | (d[3] & 0xff);
    }
    private static MessageDigest md5() {
        try { return MessageDigest.getInstance("MD5"); } catch (NoSuchAlgorithmException e) { throw new IllegalStateException(e); }
    }
}
```
Добавление четвёртого узла к кольцу из трёх по 150 vnodes перемещает около 25% ключей, каждый ровно от одного старого владельца, вместо ~75% при остатке от деления.

## Подводные камни
- Использовать для кольца `String.hashCode()` или `Objects.hash`: плохое распределение и нестабильность между JVM/языками; бери murmur3 или усечённый MD5/SHA.
- Слишком мало vnodes: один узел получает гораздо большую дугу и становится той самой горячей точкой, которой пытались избежать.
- Хеширование по ключу с перекосом: консистентное хеширование распределяет *ключи*, а не *нагрузку*; один горячий ключ всё равно попадает на один узел ([[sharding-strategies]]).
- Считать число партиций Kafka свободно изменяемым, потому что «это же просто хеширование»: это хеширование по остатку, и существующие ключи переезжают.
- Связанные заметки: [[hash-tables]] — основы хеширования, [[caching]] — сценарий с кластером кэша, [[load-balancing]] — привязка через ring hash.
