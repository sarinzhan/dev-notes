## Кратко
Когда одного лидера мало — потому что пользователи пишут в нескольких регионах или потому что нужно, чтобы записи проходили даже при недоступных узлах, — записи разрешают принимать больше чем одному узлу. При **нескольких лидерах** (multi-leader) есть несколько лидеров (по одному на датацентр), которые асинхронно реплицируют друг другу; при **репликации без лидера** (leaderless: Dynamo, Cassandra, Riak) клиент может писать в любую реплику, а используются кворумы чтения/записи. Оба подхода покупают доступность и локальность ценой **конфликтов записи**: два узла приняли разные изменения одного и того же элемента, и кто-то должен их слить. Last-writer-wins молча теряет данные; CRDT и слияние на уровне приложения их сохраняют.

## Основное

### Несколько лидеров
- Типичная топология: по одному лидеру на регион, клиенты пишут локально, лидеры асинхронно обмениваются журналами изменений. Также: клиенты с приоритетом офлайна (offline-first: телефон — это лидер с очень большой задержкой репликации), совместное редактирование.
- Преимущества: задержка записи равна локальной задержке, регион продолжает работать во время разделения между регионами ([[multi-region-basics]]).
- Цена: конфликты неизбежны, ключи автоинкремента сталкиваются, триггеры и ограничения выполняются на каждом лидере отдельно (ограничение уникальности нельзя обеспечить глобально), а топология репликации (кольцо, звезда, все со всеми) определяет, что происходит при обрыве одного канала.
- Встроенного multi-master в Postgres нет; существуют BDR/pgEdge и двусторонняя логическая репликация с обработкой конфликтов, и они требовательны в эксплуатации ([[postgres-replication-and-failover]]).

### Без лидера (в стиле Dynamo)
- Лидера нет, все реплики равны. Запись идёт на все N реплик параллельно и считается успешной, когда подтвердили W; чтение опрашивает все и успешно, когда ответили R; клиент берёт самую новую версию.
- **W + R > N** даёт пересечение: хотя бы одна из R реплик содержит последнюю подтверждённую запись. `N=3, W=2, R=2` — обычное значение по умолчанию; `W=1, R=1` — «что получится».
- Поддержание сходимости реплик: **read repair** (клиент записывает самую новую версию обратно в увиденные устаревшие реплики) и **anti-entropy** (фоновое сравнение через деревья Меркла).
- **Нестрогие кворумы** (sloppy quorums) и **hinted handoff**: если назначенные реплики недоступны, записать на любые N доступных узлов и передать данные позже. Повышает доступность, но ломает гарантию пересечения, пока передача не завершится.
- Даже при строгих кворумах конкурентные записи и частичные отказы означают, что чтения без лидера не линеаризуемы; относись к ним как к «вероятно последним» ([[consistency-models]]).

### Обнаружение конфликтов: версии и векторные часы
- «Конкурентные» означает, что ни одна запись не знала о другой, а не «в одну миллисекунду». Каждый ключ несёт **вектор версий** (version vector: счётчики по репликам); запись, включающая прочитанную версию, — потомок, иначе это **сиблинг** (sibling) ([[time-and-clocks]]).
- Сиблинги нужно хранить и возвращать приложению для слияния или схлопывать по правилу.

### Разрешение конфликтов
| Стратегия | Как | Теряет данные? | Кто использует |
|---|---|---|---|
| **Last-writer-wins (LWW)** | побеждает самая поздняя метка времени, остальные отбрасываются | да, молча; зависит от рассинхронизации часов | Cassandra (на уровне ячейки), многие кэши |
| **Слияние при чтении** | хранить сиблингов, приложение сливает (объединение товаров в корзине) | нет, но сложность в приложении | Riak, корзина покупок из статьи о Dynamo |
| **Свой обработчик при записи** | функция пользователя на каждую таблицу | зависит от функции | BDR/pgEdge, хуки CouchDB |
| **CRDT** | типы данных, слияние которых коммутативно, ассоциативно и идемпотентно | нет, по построению | типы данных Riak, Redis Enterprise, совместные редакторы (Yjs, Automerge) |
| **Избежать конфликта** | направлять все записи по одному ключу на одного лидера / домашний регион | неприменимо | прагматичный ответ для большинства бэкендов ([[sharding-strategies]]) |

- Примеры CRDT: G-counter (счётчики по узлам, суммируемые), PN-counter (два G-counter), OR-set (добавление побеждает конкурентное удаление), LWW-register (честное название для LWW). PN-counter подходит для лайков; он не подходит для баланса счёта, который не должен уходить в минус, потому что этот инвариант глобальный.

### Как подавать на собеседовании
- «Как обрабатывать записи в двух регионах?» Первый ответ: не делать этого; дать каждой записи домашний регион и направлять записи туда (абонент телеком-оператора принадлежит одной стране). Второй: несколько лидеров с бесконфликтными данными (события только на добавление, CRDT-счётчики). Третий, только если вынуждают: LWW с явно проговорённой потерей данных.
- «Cassandra с `QUORUM` ведь согласована?» Согласована в смысле `W + R > N`; не линеаризуема, не транзакционна, и LWW при конфликтах записи.

## Пример
Keyspace и таблица Cassandra, которые делают компромиссы явными: кворумные чтения/записи для состояния абонента (у каждого абонента один домашний регион, поэтому конфликты редки) и `ONE` для таблицы счётчика использования, которая по замыслу только на добавление и без конфликтов.
```yaml
# keyspace: 3 реплики на регион
CREATE KEYSPACE telecom WITH replication = {
  'class': 'NetworkTopologyStrategy', 'eu-central': 3, 'asia-central': 3 };

# состояние абонента: пишется только из домашнего региона, читается на LOCAL_QUORUM (2 из 3)
#   профиль драйвера
datastax-java-driver:
  profiles:
    subscriber:
      basic.request.consistency: LOCAL_QUORUM        # W=2, R=2 из N=3 -> пересечение
    usage-events:
      basic.request.consistency: ONE                 # только на добавление, разрешать нечего
      basic.request.timeout: 500 milliseconds
```
Межрегиональная репликация остаётся асинхронной; `LOCAL_QUORUM` означает, что запись подтверждают 2 из 3 реплик в собственном регионе писателя, так что трансатлантическое разделение её не блокирует, а читатель в другом регионе может отставать ([[column-and-wide-column-stores]]).

## Подводные камни
- LWW с несинхронизированными часами: «самая новая» запись — та, что пришла с узла, чьи часы спешат, а не та, что пользователь сделал последней.
- Автоинкрементные id на нескольких лидерах: используй UUID или диапазоны с префиксом региона ([[time-money-and-ids]]).
- Считать, что ограничение уникальности действует глобально в схеме с несколькими лидерами; оно действует на каждом лидере, и конфликты проявляются после репликации как две строки с одинаковым «уникальным» email.
- Нестрогий кворум, включённый по умолчанию (hinted handoff в Cassandra): запись подтверждена узлами, которые не являются настоящими репликами, и невидима читателям до передачи.
- Связанные заметки: [[leader-follower-replication]] — базовый вариант с одним лидером, [[cap-and-pacelc]] — почему эти схемы выбирают доступность, [[event-sourcing]] — модели только на добавление, обходящие конфликты.
