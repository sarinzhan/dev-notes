## Кратко
«Доставка ровно один раз» (exactly-once delivery) между двумя независимыми системами невозможна: получатель не может подтвердить и применить сообщение одним атомарным шагом, если обе стороны не живут в одной транзакционной системе. Вместо этого любая работающая система делает **фактически однократную обработку** (effectively-once): доставляет хотя бы один раз со стабильным id сообщения и делает получателя **идемпотентным**, чтобы вторая доставка ничего не меняла. Exactly-once semantics в Kafka — настоящая полезная функция, но ограниченная конвейерами Kafka → Kafka; как только consumer пишет в Postgres или вызывает HTTP API, гарантию приходится строить самому: [[outbox-pattern]] на стороне producer и [[idempotency]] на стороне consumer.

## Основное

### Невозможность, сформулированная один раз
- Получатель делает: (1) применяет побочный эффект, (2) подтверждает. Падение между 1 и 2 → повторная доставка → дубликат. Поменяй порядок → падение между шагами → потеря. Две независимые системы, нет общего commit, нет третьего варианта. Это задача двух генералов, применённая к одному сообщению ([[failure-modes-and-timeouts]], [[delivery-guarantees]]).
- Единственный выход — поместить побочный эффект и подтверждение в **один** атомарный commit: транзакции Kafka делают это, когда обе стороны — топики Kafka; база данных делает это, когда и бизнес-строка, и маркер «обработано» — строки в одной и той же базе.

### Что даёт Kafka EOS и чего не даёт
| Уровень | Механизм | Убирает дубликаты от | Не покрывает |
|---|---|---|---|
| Идемпотентный producer (`enable.idempotence=true`, по умолчанию) | producer id + последовательность по партиции; брокер отбрасывает повторы | сетевых retry одной сессии producer | приложение, вызывающее `send()` дважды; рестарт producer (новый pid) |
| Транзакции (`transactional.id`, consumer с `read_committed`) | offset входа и записи выхода коммитятся атомарно | цикла consume-transform-produce | любых побочных эффектов вне Kafka; consumer с `read_uncommitted` |
| Kafka Streams `exactly_once_v2` | всё вышеперечисленное в упаковке со state stores | топологий потоковой обработки | внешних приёмников (sink-коннекторы Connect должны быть идемпотентными/upsert) |

- Даже внутри Kafka транзакционный producer, перезапустившийся с тем же `transactional.id`, отсекает (fences) старый инстанс (увеличение epoch): это fencing-токен, та же идея, что в [[distributed-locks-and-fencing]].
- Цена: сетевые круги к координатору транзакций, `transaction.timeout.ms`, большая сквозная задержка (consumer видят только закоммиченные данные) и по одному `transactional.id` на набор входных партиций для правильного fencing ([[kafka-producer]]).

### Effectively-once от начала до конца
1. **Стабильная идентичность**: каждое сообщение несёт id, который переживает retry: id строки outbox, id заказа + имя шага или детерминированный хеш бизнес-ключа. Offset Kafka недостаточно, потому что повторная обработка из другой consumer group или после изменения партиций даёт другой offset.
2. **Producer**: записывать событие в той же транзакции, что и изменение ([[outbox-pattern]]). At-least-once, без фантомов.
3. **Consumer**: в одной локальной транзакции вставить id в таблицу дедупликации (или сделать upsert целевой строки по нему), применить эффект, commit. Затем ack. Дубликаты упираются в уникальный ключ и ничего не делают ([[idempotency]]).
4. **Внешние эффекты**, которые нельзя обернуть в свою транзакцию (платёжный шлюз, SMS, заказ профиля в SM-DP+): использовать ключ идемпотентности провайдера или делать вызов идемпотентным по природе (`PUT state=ACTIVE`, а не `POST activate`) и записывать id ответа провайдера до ack ([[esim-provisioning-platform]]).
5. **Порядок по ключу**: держать все события одного ключа в одной партиции и обрабатывать их по порядку; дедупликация не защищает от применения двух разных событий не в том порядке ([[kafka-architecture]]).

### Откуда берутся дубликаты (чтобы перечислить на собеседовании)
- Retry producer (закрываются идемпотентным producer), повторный запуск ретранслятора outbox после падения, rebalance consumer посреди батча, повторная доставка после `max.poll.interval.ms`, переигрывание DLQ, переигрывание топика для пересборки проекции, человек, повторно отправивший webhook, вышестоящий партнёр, повторивший HTTP-вызов ([[dead-letter-queues-and-retries]]).
- Любой из этих пунктов сам по себе оправдывает идемпотентных consumer; вместе они делают это обязательным.

### Естественная идемпотентность и таблица дедупликации
- **Естественная**: обновления через присваивание (`status = 'ACTIVE'`), upsert по бизнес-id, «вставить, если нет». Дешевле всего, без дополнительной таблицы, но инкрементальные операции (`balance = balance - 10`) идемпотентными по природе не являются.
- **Таблица дедупликации**: `processed_events(event_id, consumer, processed_at)` с уникальным ключом, в той же транзакции, что и эффект. Работает для чего угодно, нужны очистка по сроку и индекс ([[postgres-indexes]]).
- **Проверка версии/последовательности**: применять, только если `event.version > row.version`; вдобавок отклоняет устаревшие события, пришедшие не по порядку, чего таблица дедупликации не делает.

## Пример
Конвейер Kafka Streams с настоящим exactly-once внутри Kafka и честная граница, где он заканчивается: приёмник в Postgres использует upsert по id события.
```yaml
# streams-приложение: входной топик -> обогащение -> выходной топик, exactly-once внутри Kafka
spring:
  kafka:
    streams:
      application-id: activation-enricher
      properties:
        processing.guarantee: exactly_once_v2     # транзакционный producer + consumer с read_committed
        commit.interval.ms: 100
    consumer:
      isolation-level: read_committed            # consumer ниже по цепочке тоже должны это включить
```
```sql
-- consumer-приёмник (обычный @KafkaListener + JDBC): граница, где EOS перестаёт быть заботой Kafka
INSERT INTO activation_projection (event_id, iccid, status, updated_at)
VALUES (:eventId, :iccid, :status, now())
ON CONFLICT (event_id) DO NOTHING;             -- повторная доставка -> без изменений
```
Этап Streams никогда не дублирует и не теряет записи между двумя топиками, даже при рестартах; приёмник превращает доставку at-least-once в корректную проекцию одним upsert.

## Подводные камни
- Прочитать «exactly-once» на маркетинговой странице брокера и пропустить идемпотентность consumer; первый rebalance во время deploy порождает дубликат.
- Дедупликация по `topic-partition-offset` Kafka: ломается при переигрывании из новой группы, миграции топика или изменении числа партиций.
- Проверка дедупликации и побочный эффект в **разных** транзакциях (проверка в Redis, запись в Postgres): падение между ними снова открывает окно.
- Сделать producer транзакционным и оставить consumer на `read_uncommitted` (по умолчанию), так что они всё равно видят отменённые записи.
- Связанные заметки: [[delivery-guarantees]] — классификация, [[outbox-pattern]] и [[idempotency]] — две половины решения, [[saga]] — многошаговые процессы, где это нужно каждому шагу.
