## Кратко
Кэш — это реплика без протокола репликации: ничто не сообщает ему, что источник истины изменился, поэтому устаревание — поведение по умолчанию, а любой механизм «согласованности» — компромисс между устареванием, ценой записи и сложностью. Практический набор инструментов: короткие **TTL** как страховочная сетка, **инвалидация при записи** (удалять, а не обновлять) для того, что замечают пользователи, **версионированные ключи**, когда инвалидация ненадёжна, и **объединение запросов** (request coalescing) плюс **истечение с разбросом** (jittered expiry), чтобы истёкший горячий ключ не отправил в базу «бегущее стадо» (thundering herd). *Стратегии* кэширования (aside, read-through, write-through, write-behind) описаны в [[caching]]; эта заметка — о том, как не дать множеству кэшей и базе данных разойтись.

## Основное

### Почему кэши устаревают
- При **cache-aside** записи идут в БД, а кэш обновляет или инвалидирует приложение; падение между этими двумя шагами или два конкурентных писателя оставляют кэш неверным до истечения TTL.
- **Много кэшей**: у каждого инстанса сервиса локальный кэш Caffeine плюс общий Redis; инвалидация Redis ничего не делает с локальными копиями ([[spring-cache-abstraction]]).
- **Отставание репликации**: кэш, наполняемый с реплики для чтения, может закэшировать значение, которое уже перезаписано на primary ([[read-replicas-and-stale-reads]]).
- Между кэшами приложений нет протокола согласованности вроде MESI в процессоре ([[cpu-caches-and-cache-lines]]); нужную согласованность строишь сам.

### Инвалидировать, а не обновлять
- **Удалять при записи** (cache-aside): после commit в БД — `DEL key`. Следующий читатель наполняет заново. Удаление идемпотентно и не может записать устаревшее значение; **обновление** может, когда два писателя соревнуются: писатель A читает v1, писатель B пишет v2 в БД и кэш, A пишет v1 в кэш. Устаревшее значение до истечения TTL.
- Классическая оставшаяся гонка: читатель промахивается, читает v1 из БД; писатель коммитит v2 и удаляет; читатель записывает v1 в кэш. Редко (чтение из БД у читателя должно быть медленнее целой записи), но реально; короткий TTL или проверка версии ограничивают ущерб.
- Удалять **после** commit, а не до: удаление до commit позволяет конкурентному читателю заново заполнить старое значение во время транзакции. В Spring `@CacheEvict` срабатывает при возврате из метода, что при `@Transactional` на том же методе происходит *до* commit; для вытеснения используй `@TransactionalEventListener(AFTER_COMMIT)` или `TransactionSynchronization.afterCommit` ([[spring-transactional]]).

### Распространение инвалидации на все кэши
| Механизм | Задержка | Надёжность | Примечания |
|---|---|---|---|
| **Только TTL** | до TTL | работает всегда | нижняя планка, которую сохраняет любой дизайн |
| **Рассылка ключей через Redis pub/sub** | мс | отправил и забыл; отключённый инстанс её пропустит | так делают двухуровневые кэши Caffeine + Redis; сочетать с TTL |
| **Топик Kafka с событиями изменений** (из outbox/CDC) | мс–с | надёжно, можно переиграть; опоздавшие догоняют | тяжелее; естественно, если уже есть [[outbox-pattern]] / [[event-driven-architecture]] |
| **Версионированные ключи** `tariff:v{version}:{id}` | сразу для новых читателей | инвалидация не нужна; старые версии устаревают сами | версия должна быть дёшево доступна (счётчик в Redis, колонка версии сущности) |
| **Аренда / валидация** (в стиле ETag, `If-None-Match` к источнику) | на каждое чтение | точно | сетевой круг на каждое чтение; так делают HTTP-кэши ([[http-caching]]) |

### Thundering herd (лавина на кэш, cache stampede)
- Горячий ключ истекает; 2 000 конкурентных запросов все промахиваются, все запрашивают у БД одну и ту же строку, БД насыщается, задержка подскакивает, запросов набивается ещё больше ([[backpressure-and-flow-control]]).
- Исправления, обычно в сочетании:
  - **Объединение запросов / single-flight**: только один загрузчик на ключ на инстанс; остальные ждут тот же future. `LoadingCache.get` в Caffeine уже делает это в пределах JVM; между инстансами используй короткую блокировку в Redis (`SET key:lock NX PX 2000`), чтобы обновлял один инстанс, а остальные отдавали устаревшее или ждали.
  - **TTL с разбросом**: `ttl + random(0, 10%)`, чтобы ключи, заполненные вместе, не истекали вместе.
  - **Раннее / вероятностное обновление** (XFetch): обновлять чуть раньше истечения с вероятностью, растущей по мере приближения к нему; `refreshAfterWrite` в Caffeine — простая версия (отдавать устаревшее, обновлять в фоне).
  - **Отдавать устаревшее во время перепроверки** (serve stale while revalidating): хранить истёкшее значение в течение льготного периода и возвращать его, пока один запрос обновляет.
  - **Негативное кэширование**: ненадолго кэшировать «не найдено», чтобы шторм промахов по несуществующему ключу (атака или баг) не бил в БД.
- Родственная лавина: холодный кэш после deploy или рестарта Redis; прогревай критичные ключи при старте или выкатывай постепенно ([[kubernetes-basics]]).

### Сколько согласованности покупать
- Справочные данные, меняющиеся раз в неделю: TTL в несколько часов плюс эндпоинт ручного сброса.
- Состояние, которое пользователь только что изменил (профиль, корзина): удаление при записи после commit, локальные кэши на секунды, чтение своих записей через primary ([[consistency-models]]).
- Данные для принятия решений (баланс, остатки, блокировки): не кэшировать или сверять версию с источником в момент решения.

## Пример
Двухуровневый кэш (Caffeine на инстанс, общий Redis) с объединённой загрузкой, TTL с разбросом и рассылкой инвалидации после commit через Redis pub/sub.
```java
@Service
@RequiredArgsConstructor
public class TariffCache {
    private final StringRedisTemplate redis;
    private final TariffRepository repo;
    private final LoadingCache<Long, Tariff> local = Caffeine.newBuilder()
        .maximumSize(10_000).expireAfterWrite(Duration.ofSeconds(30))
        .build(this::loadShared);                        // single-flight на ключ в пределах JVM

    public Tariff get(long id) { return local.get(id); }

    private Tariff loadShared(long id) {
        String key = "tariff:" + id;
        String json = redis.opsForValue().get(key);
        if (json != null) return Json.read(json, Tariff.class);
        Tariff t = repo.findById(id).orElseThrow();
        long ttl = 600 + ThreadLocalRandom.current().nextLong(60);   // 10 мин + разброс
        redis.opsForValue().set(key, Json.write(t), Duration.ofSeconds(ttl));
        return t;
    }

    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)   // только после commit в БД
    public void onChanged(TariffChangedEvent e) {
        redis.delete("tariff:" + e.id());
        redis.convertAndSend("cache-invalidate", "tariff:" + e.id());    // другие инстансы сбрасывают локальную копию
    }

    @EventListener
    public void onInvalidateMessage(InvalidateMessage m) {
        if (m.key().startsWith("tariff:")) local.invalidate(Long.parseLong(m.key().substring(7)));
    }
}
```
Локальный TTL в 30 с ограничивает ущерб, если сообщение pub/sub потеряется; TTL в Redis ограничивает его, если путь инвалидации в коде вообще пропущен ([[redis-patterns-and-persistence]]).

## Подводные камни
- `@CacheEvict` на методе с `@Transactional`: вытеснение происходит до commit, и конкурентное чтение заново заполняет кэш данными до commit.
- Обновлять кэш записанным значением, «чтобы сэкономить чтение»: проигрывает гонку конкурентному писателю; вместо этого удаляй.
- Одинаковый TTL для всех ключей, выставленный в одном цикле прогрева: они все истекают вместе, и каждые N минут на БД приходит волна.
- Кэширование без TTL, «потому что мы инвалидируем при каждой записи»: первая пропущенная инвалидация (deploy, сетевой сбой, забытый кем-то путь записи) остаётся устаревшей навсегда.
- Связанные заметки: [[caching]] — выбор стратегии, [[consistent-hashing]] — шардирование кластера кэша без массовых промахов, [[cdn]] — та же проблема на краю сети.
