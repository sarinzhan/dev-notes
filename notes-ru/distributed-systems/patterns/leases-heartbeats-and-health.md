## Кратко
**Heartbeat** — периодическое сообщение «я жив»; **аренда** (lease) — это право («ты владеешь этой партицией / ты лидер / эта сессия действительна»), которое истекает, если его не продлевать heartbeat. Вместе они — способ, которым распределённые системы определяют живость без глобальных часов и надёжной сети: пропусти достаточно heartbeat — аренда истечёт, и ресурс переназначат. Напряжение в дизайне везде одно и то же: короткая аренда быстро обнаруживает отказ, но ложно срабатывает на GC-паузах и сетевых сбоях; длинная аренда стабильна, но медленно восстанавливается. И аренда сообщает только *другим*, что тебя нет; держатель должен сам заметить истечение и остановиться — поэтому записям нужен fencing.

## Основное

### Heartbeat и обнаружение отказов
- Интервал heartbeat I, таймаут T (обычно 3–10 × I). Узел **подозревается** после T без heartbeat; подозреваемый — не мёртвый, heartbeat может задержаться из-за паузы или разделения ([[failure-modes-and-timeouts]]).
- Направления: узел → координатор (Kafka consumer → координатор группы, kubelet → API server), лидер → follower (Raft `AppendEntries`), peer-to-peer gossip (Cassandra, Consul).
- Детекторы **φ-accrual** заменяют фиксированный T уровнем подозрения, вычисленным из наблюдаемых интервалов между приходами.
- Поток heartbeat продолжает работать, пока рабочий поток в deadlock, так что узел выглядит живым и ничего не делает. Для этого в Kafka существует `max.poll.interval.ms`: heartbeat идут в фоне, но `poll()` всё равно нужно вызывать вовремя.

### Аренды
- Аренда = владение + срок истечения. Выдающий (координатор, консенсусное хранилище, строка в базе данных) выдаёт аренду с TTL; держатель продлевает её до истечения; при истечении выдающий переназначает.
- **Допущение о часах**: часы держателя и часы выдающего дрейфуют с ограниченной скоростью, и держатель отказывается от аренды в момент `expiry − safetyMargin` по *своим* часам. На этом построены и Chubby от Google, и etcd ([[time-and-clocks]]).
- **Проблема держателя**: после GC-паузы в 20 с аренда держателя истекла 10 с назад, и ею владеет кто-то другой. Держатель не может этого узнать, пока снова не свяжется с выдающим. Поэтому любая запись под арендой должна нести **fencing-токен**, который проверяет ресурс ([[distributed-locks-and-fencing]]).
- Аренда и блокировка: блокировку без TTL упавший процесс держит вечно; аренда — это блокировка, которая освобождается сама. TTL — цена: живость в обмен на окно возможного двойного владения.

### Где в стеке живут аренды
| Система | Аренда / heartbeat | Интервал / TTL по умолчанию | При истечении |
|---|---|---|---|
| Kafka consumer group | `heartbeat.interval.ms` → `session.timeout.ms`; `max.poll.interval.ms` для обработки | 3 с / 45 с; 5 мин | consumer удаляется, партиции ребалансируются ([[kafka-consumer]]) |
| Kafka ISR | свежесть fetch у follower, `replica.lag.time.max.ms` | 30 с | follower исключается из ISR ([[kafka-architecture]]) |
| etcd | аренда с TTL, поток `KeepAlive` | задаёт приложение, например 10 с | ключи, привязанные к аренде, удаляются; наблюдатели уведомляются |
| ZooKeeper | сессия с heartbeat по `tickTime` | таймаут сессии 2–20 тиков | эфемерные znode удаляются |
| Kubernetes | аренда узла kubelet (`kube-node-lease`) | продление 10 с, `node-monitor-grace-period` 40 с | узел `NotReady`, pod вытесняются после toleration ([[kubernetes-basics]]) |
| Выбор лидера в Kubernetes | объект `Lease`, `coordination.k8s.io` | длительность 15 с, продление 10 с, retry 2 с | управление перехватывает другая реплика контроллера |
| Patroni | ключ лидера в etcd/Consul с `ttl` | 30 с, `loop_wait` 10 с | standby повышается ([[postgres-replication-and-failover]]) |
| Temporal | heartbeat activity с `heartbeatTimeout` | на каждую activity | activity завершается по таймауту и повторяется на другом worker ([[temporal-concepts]]) |
| Raft | heartbeat лидера = пустой `AppendEntries`; таймаут выборов | ~100 мс / 150–300 мс (etcd) | новые выборы ([[raft-explained]]) |

### Проверки здоровья — это аренды с точки зрения балансировщика
- **Liveness**: «нужно ли перезапустить этот процесс?» Проваливай её только при неустранимом состоянии (deadlock, испорченное внутреннее состояние). Провал liveness из-за медленной зависимости перезапускает здоровые pod по кругу.
- **Readiness**: «должен ли этот инстанс получать трафик?» Проваливай её, когда необходимая зависимость лежит, во время прогрева и во время корректного завершения (graceful shutdown), чтобы балансировщик слил соединения до выхода процесса ([[signals-and-process-lifecycle]]).
- **Startup**-проба для медленно стартующих JVM, чтобы liveness не убивала их посреди загрузки.
- Spring Boot Actuator выставляет `/actuator/health/liveness` и `/readiness` как отдельные группы; readiness может включать индикаторы `db`, `kafka`, liveness — не должна ([[spring-boot-starters-and-autoconfiguration]]).
- Проверка здоровья без таймаута — ложь: она зависает вместе с зависимостью, и балансировщик продолжает слать трафик.

### Эмпирические правила настройки
- Таймаут ≥ 3 × интервал, и оба длиннее худшей наблюдаемой GC-паузы ([[garbage-collection]]); продлевать на трети TTL; прекращать действовать на 70–80% TTL, если продление не подтверждено.

## Пример
Пробы Kubernetes и соответствующая конфигурация Spring Boot для сервиса-consumer Kafka: readiness привязана к реальным зависимостям, liveness от них не зависит.
```yaml
# deployment.yaml
livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  periodSeconds: 10
  failureThreshold: 3            # 30 с настоящей неисправности до рестарта
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 8080 }
  periodSeconds: 5
  failureThreshold: 2            # выведен из ротации за 10 с
startupProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  failureThreshold: 30           # до 5 мин для холодной JVM
  periodSeconds: 10

# application.yaml
management:
  endpoint.health.probes.enabled: true
  endpoint.health.group:
    readiness.include: readinessState, db, kafka      # учитывает зависимости
    liveness.include: livenessState                   # никогда не зависит от сети
server.shutdown: graceful
spring.lifecycle.timeout-per-shutdown-phase: 30s      # доделать текущую работу до выхода
spring.kafka.consumer.properties:
  session.timeout.ms: 45000
  heartbeat.interval.ms: 3000
  max.poll.interval.ms: 300000
```
По `SIGTERM` Spring сначала переключает readiness в `OUT_OF_SERVICE`, балансировщик перестаёт направлять трафик, текущие запросы завершаются, затем Kafka consumer чисто покидает группу (корректный выход запускает rebalance сразу, а не после ожидания `session.timeout.ms`).

## Подводные камни
- Liveness-проба, которая обращается к базе данных: отказ БД перезапускает каждый pod, который затем стартует холодным и усугубляет отказ БД.
- `session.timeout.ms` короче полного GC: consumer выкидывают посреди батча, его партиции уходят другому инстансу, и оба обрабатывают одни и те же записи ([[delivery-guarantees]]).
- Держатель аренды, который продлевает её из фонового потока и никогда не проверяет результат; неудачное продление должно останавливать работу, а не просто писаться в лог.
- Heartbeat, доказывающие только «поток heartbeat работает»: сочетай их с проверкой прогресса (обработанные записи, метка времени последнего цикла).
- Связанные заметки: [[quorums-and-leader-election]] — аренды как механизм выборов, [[backpressure-and-flow-control]] — как сохранить `poll()` живым под нагрузкой, [[slo-sli-and-alerting]] — как превратить сигналы здоровья в алерты.
