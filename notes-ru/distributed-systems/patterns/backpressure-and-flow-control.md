## Кратко
Когда producer быстрее consumer, чем-то придётся пожертвовать: **буферизовать** (с ограничением — а что потом?), **отбрасывать** (какие сообщения?) или **замедлить producer**. Обратное давление (backpressure) — это третий вариант: consumer сообщает, сколько может принять, и producer это уважает. Неограниченная очередь — не стратегия, а отложенная ошибка нехватки памяти. TCP управляет потоком через окно приёма, Reactive Streams — через `request(n)`, Kafka — через pull-модель consumer с видимым lag, пулы потоков — через ограниченные очереди и политики отказа.

## Основное

### Три варианта, когда нагрузка превышает мощность
| Вариант | Механизм | Как ломается |
|---|---|---|
| **Буферизовать** | очередь в памяти или на диске | растёт память, растёт задержка (каждый элемент ждёт за всей очередью), затем OOM или заполненный диск |
| **Отбросить / сбросить нагрузку (shed)** | отклонять новую работу, сэмплировать, хранить самые новые или самые старые | потерянная работа; приемлемо для метрик, присутствия, дублирующихся уведомлений |
| **Обратное давление** | consumer просит producer замедлиться; блокировка или кредиты | вызывающие producer начинают копиться; давление распространяется к краю системы, где ему и место |

- Закон Литтла (Little's law): элементов в системе = интенсивность поступления × время в системе. Ограниченный буфер ограничивает время в системе; неограниченный позволяет задержке расти без предела, пока пропускная способность выглядит нормальной ([[amdahls-law-and-parallel-speedup]]).
- Правильное место для сброса нагрузки — точка входа (API gateway, rate limiter), где можно вернуть `429`/`503` с `Retry-After`, а не глубоко внутри конвейера, где запрос уже потратил ресурсы ([[rate-limiting]], [[api-gateway-and-service-discovery]]).

### Где управление потоком уже есть
- **TCP**: получатель объявляет окно; медленный читатель заставляет отправителя остановиться. Поэтому заблокированный поток consumer в итоге блокирует `write()` producer через сеть ([[tcp-vs-udp]]).
- В **HTTP/2** есть окна на каждый поток; стриминг **gRPC** для той же цели даёт `isReady()`/`onReady` ([[grpc-and-protobuf]]).
- **Reactive Streams** (Project Reactor, RxJava): `Subscriber.request(n)` — это кредит; операторы `Flux` вроде `onBackpressureBuffer(n)`, `onBackpressureDrop`, `onBackpressureLatest` делают стратегию явной ([[spring-reactive-webclient-sse]]).
- **Kafka**: consumer *забирают* (pull) с `max.poll.records`; медленный consumer просто реже вызывает poll, и lag растёт в брокере, где это дёшево и видно. Брокер никогда не отправляет быстрее, чем просит consumer. Со стороны producer: `buffer.memory` заполнен → `send()` блокируется на `max.block.ms`, затем бросает исключение — это обратное давление на приложение ([[kafka-producer]], [[kafka-consumer]]).
- **RabbitMQ**: модель push, поэтому prefetch count в `basic.qos` ограничивает число неподтверждённых сообщений на consumer; без prefetch быстрая очередь топит медленного consumer ([[rabbitmq-basics]]).
- **Пулы потоков**: `ThreadPoolExecutor` с ограниченной `ArrayBlockingQueue` и `CallerRunsPolicy` заставляет отправляющий поток делать работу самому, что замедляет отправителя: обратное давление в одну строку ([[executors-and-thread-pools]]).
- **Java streams и `BlockingQueue`**: `put()` блокируется, когда очередь полна; эта блокировка и есть сигнал.

### Consumer lag в Kafka как манометр системы
- Lag = последний offset − закоммиченный offset по партиции. Растущий lag означает, что consumer медленнее producer. *Хорошо*, что очередь копится в Kafka (надёжно, ограничено retention), а не в куче consumer.
- Ответы: масштабировать consumer до числа партиций, батчить работу ниже по цепочке, ускорить обработчик или принять lag при retention, достаточном, чтобы его пережить. Сверх числа партиций дополнительные consumer ничего не дают ([[kafka-architecture]]).
- Если обработчик блокируется дольше `max.poll.interval.ms` (по умолчанию 5 мин), брокер выкидывает consumer, запускает rebalance, и те же записи доставляются другому инстансу, который тоже будет медленным: шторм rebalance. Используй `pause()`/`resume()` на consumer или обрабатывай в ограниченном пуле и коммить по завершении ([[spring-kafka-consumer]]).

### Проектирование конвейера с обратным давлением
1. Каждая очередь ограничена, с задокументированной политикой при заполнении: блокировать, отбрасывать самое старое, отклонять.
2. Дедлайны распространяются, чтобы работа, уже пропустившая свой SLO, отбрасывалась, а не обрабатывалась ([[failure-modes-and-timeouts]]).
3. Глубина очередей, lag и число отказов выставлены как метрики ([[grafana-dashboards-and-red-use]]).
4. Между сервисами предпочитай pull, а не push; а если push — используй кредиты (prefetch).
5. Изолируй медленных consumer (bulkheads, «переборки»): одна медленная зависимость не должна осушать пул, используемый для всего ([[circuit-breaker]]).

## Пример
Kafka listener, который передаёт работу в ограниченный пул и ставит партицию на паузу, когда пул полон, вместо того чтобы блокироваться внутри `poll()` или буферизовать без ограничений.
```java
@Component
public class SmsDispatchListener {
    private final ThreadPoolExecutor pool = new ThreadPoolExecutor(
        8, 8, 0, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(200),                        // ограничено: максимум 200 в работе
        new ThreadPoolExecutor.AbortPolicy());               // полон -> RejectedExecutionException

    @KafkaListener(topics = "sms.outbound", groupId = "sms-gateway", containerFactory = "manualAckFactory")
    public void on(ConsumerRecord<String, SmsCommand> rec, Acknowledgment ack, Consumer<?, ?> consumer) {
        try {
            pool.execute(() -> { gateway.send(rec.value()); ack.acknowledge(); });
        } catch (RejectedExecutionException full) {
            // обратное давление: перестать забирать эту партицию, пока пул не опустеет, затем доставить повторно
            consumer.pause(Set.of(new TopicPartition(rec.topic(), rec.partition())));
            resumeLater(consumer, rec);                      // планировщик возобновляет, когда очередь < 50%
            throw full;                                      // без ack -> повторная доставка после resume
        }
    }
}
```
С `max.poll.records=50` и `max.poll.interval.ms` по умолчанию consumer остаётся живым во время замедления SMS-шлюза; lag растёт в Kafka, а память в pod не растёт ([[dead-letter-queues-and-retries]] — что делать, когда шлюз лежит, а не тормозит).

## Подводные камни
- `Executors.newFixedThreadPool`: фиксированное число потоков, **неограниченная** очередь; он примет каждую задачу и исчерпает кучу при длительной перегрузке.
- `onBackpressureBuffer()` без размера или `Flux.create` со стратегией по умолчанию `BUFFER`: та же неограниченная очередь, только с реактивным названием.
- Повторять вызов медленной зависимости внутри потока consumer: retry добавляют нагрузку ровно тогда, когда мощности меньше всего.
- Масштабировать consumer сверх числа партиций и называть это «горизонтальным масштабированием».
- Связанные заметки: [[kafka-consumer]] — механика poll/commit, [[rate-limiting]] — сброс нагрузки на краю, [[leases-heartbeats-and-health]] — почему consumer на паузе должен продолжать слать heartbeat.
