## Кратко
Сообщение между двумя процессами по ненадёжной сети может быть доставлено **не более одного раза** (at-most-once: отправил и забыл — может потеряться, но не задублируется), **хотя бы один раз** (at-least-once: повторять до подтверждения — не потеряется, но может задублироваться) или, в очень узком смысле, **ровно один раз** (exactly-once) внутри одной системы, которая контролирует обе стороны. Через границы систем доставка exactly-once невозможна; построить можно **фактически однократную обработку** (effectively-once processing): доставка at-least-once плюс идемпотентный consumer. Всё, что в Kafka называется «exactly-once semantics», — частный случай этого, ограниченный конвейерами Kafka → Kafka.

## Основное

### Три гарантии
| Гарантия | Механизм | Теряет | Дублирует | Кому нужна |
|---|---|---|---|---|
| **At-most-once** | отправил и забыл; ack до обработки | да | нет | метрики, логи, пинги присутствия, всё, где новое значение заменяет старое |
| **At-least-once** | ack только после надёжной обработки; retry по таймауту | нет | да | почти все бизнес-события; поведение по умолчанию в Kafka, RabbitMQ, SQS, HTTP-retry |
| **Exactly-once** | at-least-once + дедупликация, или атомарный commit, охватывающий offset входа и выход | нет | нет (с точки зрения наблюдателя) | платежи, провижининг, складские остатки |

- Выбор определяется тем, **где происходит ack** относительно побочного эффекта, а не флагом на брокере.
- Kafka consumer: при `enable.auto.commit=true` offset коммитится на следующем `poll()`, независимо от того, полностью ли обработан предыдущий батч; падение в промежутке может потерять записи (обработка запоздала) или задублировать их (commit запоздал). Для чистого at-least-once коммить вручную после побочного эффекта ([[kafka-consumer]], [[spring-kafka-consumer]]).

### Почему настоящий exactly-once через границы невозможен
- Consumer выполняет побочный эффект (HTTP-вызов, запись в БД, email) и потом подтверждает. Если он падает между этими шагами, сообщение доставляется повторно, и эффект происходит дважды. Если сначала подтвердить, падение теряет сообщение. Третьего порядка нет, потому что побочный эффект и ack находятся в разных системах без общей транзакции ([[failure-modes-and-timeouts]]).
- 2PC между брокером и базой данных формально закрывает этот разрыв, но блокируется при отказе координатора и не поддерживается ни Kafka, ни большинством облачных сервисов ([[cross-shard-queries-and-transactions]]).

### Что на самом деле покрывает «exactly-once» в Kafka
- **Идемпотентный producer** (`enable.idempotence=true`, по умолчанию с Kafka 3.0): producer id плюс номера последовательности по партициям позволяют брокеру отбрасывать дубликаты, вызванные *retry producer*. Это не покрывает приложение, которое вызывает `send()` дважды, или producer, перезапустившийся с новым pid.
- **Транзакции** (`transactional.id`, `isolation.level=read_committed`): цикл consume-transform-produce атомарно коммитит offset входа и выходные записи. Exactly-once соблюдается *внутри Kafka*: входной топик → выходной топик. Как только transform пишет в Postgres или вызывает API, для этого побочного эффекта ты снова в at-least-once.
- `processing.guarantee=exactly_once_v2` в Kafka Streams — это та же механика в упаковке.

### Effectively-once: паттерн, который работает везде
1. Сторона producer: записать событие в той же транзакции БД, что и бизнес-изменение, и публиковать асинхронно ([[outbox-pattern]]). Доставка at-least-once со стабильным id события.
2. Сторона consumer: дедуплицировать по этому id **в той же транзакции**, что и побочный эффект: вставить в `processed_events(event_id PRIMARY KEY)`, выполнить работу, commit; дубликат упирается в уникальное ограничение и пропускается ([[idempotency]]).
3. Для внешних побочных эффектов, которые нельзя включить в свою транзакцию (SMS-шлюз), использовать ключ идемпотентности провайдера или делать операцию идемпотентной по природе (установить статус X, а не увеличить счётчик).

### Порядок — отдельная ось
- At-least-once с retry меняет порядок: сообщение 3 падает, 4 проходит, 3 повторяется после 4. Kafka сохраняет порядок внутри партиции, только если у producer `max.in.flight.requests.per.connection ≤ 5` при включённой идемпотентности и если consumer не делает retry в обход очереди ([[kafka-producer]], [[dead-letter-queues-and-retries]]).
- Consumer, которому нужна и обработка без потерь, и порядок по ключу, при ошибке должен блокировать партицию или откладывать ключ, а не перескакивать вперёд.

### Как подавать на собеседовании
- «Даёт ли Kafka exactly-once?» Да, внутри транзакции Kafka → Kafka; нет — для побочных эффектов в твоей базе данных или по HTTP. Затем объясни outbox + идемпотентный consumer ([[exactly-once-myth]]).
- «At-least-once или at-most-once для X?» Решай, спросив, что дешевле исправить: потерянное сообщение, которое никто не заметит, или дубликат, который можно дедуплицировать. Почти всегда второе.

## Пример
Consumer, превращающий доставку at-least-once в effectively-once обработку: строка дедупликации и бизнес-запись в одной транзакции Postgres, offset коммитится только после её commit.
```java
@Component
@RequiredArgsConstructor
public class ProfileDownloadedListener {
    private final JdbcTemplate jdbc;

    @KafkaListener(topics = "esim.events", groupId = "billing")
    @Transactional                                   // транзакция БД; commit происходит до ack в Kafka
    public void on(ConsumerRecord<String, String> rec, Acknowledgment ack) {
        UUID eventId = UUID.fromString(new String(rec.headers().lastHeader("event-id").value(), UTF_8));
        int inserted = jdbc.update(
            "INSERT INTO processed_events(event_id, consumer) VALUES (?, 'billing') ON CONFLICT DO NOTHING",
            eventId);
        if (inserted == 1) {                          // видим впервые
            jdbc.update("UPDATE subscription SET status = 'ACTIVE', activated_at = now() WHERE iccid = ?",
                rec.key());
        }                                             // дубликат: работу пропускаем, но ack всё равно делаем
        ack.acknowledge();                            // ручной ack, AckMode.MANUAL
    }
}
```
Если pod умирает после commit в БД, но до `acknowledge()`, запись доставляется повторно, вставка упирается в конфликт, и ничего не происходит дважды. Таблице `processed_events` нужна задача очистки по сроку хранения; обычно хватает недели ([[postgres-indexes]] — про трюк с частичным индексом для таблиц-очередей).

## Подводные камни
- Auto-commit плюс асинхронная обработка (передача записей в executor): offset продвигаются раньше, чем завершается работа, — это замаскированный at-most-once.
- Дедупликация в множестве в памяти или в кэше с TTL: рестарт или вытеснение снова открывают окно; состояние дедупликации должно быть таким же надёжным, как побочный эффект.
- Понимать `enable.idempotence=true` как «дубликатов не будет никогда»: это покрывает только retry на стороне брокера в рамках одной сессии producer.
- Ставить внешний HTTP-вызов перед транзакцией БД, так что откат оставляет внешний эффект на месте; упорядочивай побочные эффекты от наиболее к наименее обратимым.
- Связанные заметки: [[exactly-once-myth]] — сквозной аргумент, [[outbox-pattern]] — половина со стороны producer, [[message-queues-and-streams]] — как устроены ack в RabbitMQ/SQS для сравнения.
