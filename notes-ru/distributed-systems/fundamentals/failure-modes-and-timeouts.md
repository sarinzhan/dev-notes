## Кратко
В распределённой системе запрос может сломаться в четырёх местах: он так и не дошёл, удалённая сторона упала во время работы, удалённая сторона сделала работу, но ответ потерялся, или удалённая сторона просто медленная. Со стороны вызывающего эти случаи **неразличимы**: видно только «ответа пока нет». Единственный инструмент обнаружения отказа в асинхронной сети — **таймаут**, а таймаут — это догадка, а не факт. Всё остальное — retry, идемпотентность, аренды (leases), fencing — существует, чтобы действовать по этой догадке было безопасно.

## Основное

### Классификация отказов
| Вид | Что происходит | Пример |
|---|---|---|
| **Падение с остановкой (crash-stop)** | Узел останавливается и остаётся лежать | pod убит по OOM, `kill -9` |
| **Падение с восстановлением (crash-recovery)** | Узел останавливается, позже перезапускается, возможно со старым состоянием | рестарт брокера Kafka, восстановление Postgres после сбоя из WAL |
| **Пропуск (omission)** | Сообщения теряются или не отправляются | потеря пакета, переполненный буфер сокета, `send()` прошёл успешно, но процесс умер до flush |
| **Тайминговые / «серые» (gray)** | Узел отвечает, но слишком поздно или непоследовательно | GC-пауза 30 с, диск загружен на 100%, одна AZ с 10% потерь пакетов |
| **Сетевое разделение (network partition)** | Группы узлов не могут достучаться друг до друга, но каждая группа здорова | отказ коммутатора, ошибочно применённое правило файрвола, изоляция AZ в облаке |
| **Византийский (byzantine)** | Узел отправляет неверные или злонамеренные данные | вне рамок почти всех внутренних систем; важно для блокчейнов |

- **Серые отказы** — самые дорогие: узел, который проходит health check, но обслуживает 1% запросов с задержкой 20 с, отравляет пулы соединений и бюджеты retry повсюду ([[circuit-breaker]]).
- **Разделение** выглядит в точности как падение другой стороны. Обе стороны могут решить «они упали, лидер теперь я» — это split brain ([[quorums-and-leader-election]]).

### Задача двух генералов в одну строку
В сети, которая может терять сообщения, никакой конечный обмен не позволяет обеим сторонам быть уверенными, что другая знает результат. Поэтому у вопроса «моя запись произошла?» после таймаута три ответа: нет, да или ещё выполняется. Код должен быть корректен при всех трёх.

### Таймауты — догадки с двумя неправильными ответами
- **Слишком короткий**: здоровый, но медленный узел объявляется мёртвым, запрос повторяется в другом месте, и работа выполняется дважды (двойной платёж, двойной заказ на загрузку eSIM). Кроме того, нагрузка перекладывается на оставшиеся узлы ровно в тот момент, когда система и так медленная, и перегрузка усиливается.
- **Слишком длинный**: потоки и соединения висят заблокированными, пул иссякает ([[hikaricp-pool-sizing]]), у вызывающего вызывающего таймаут срабатывает раньше, и отказ каскадом поднимается наверх.
- Правильного значения нет; есть бюджет. Задавай таймауты от **SLO вызывающего** вниз: если API обещает 2 с, сумма таймаутов нижестоящих вызовов плюс retry должна уложиться в 2 с ([[service-communication-sync-vs-async]]).
- Разделяй таймаут **соединения** (connect: падать быстро, ~1 с) и таймаут **чтения** (read: зависит от операции). Зависший TCP connect означает, что хоста или сети нет; зависшее чтение может означать медленный запрос ([[tcp-handshake-and-connection-states]]).

### Как сделать действия по таймауту безопасными
- **Идемпотентные операции**: retry после неизвестного исхода не должен удваивать эффект. Используй ключ идемпотентности на каждый логический запрос ([[idempotency]]).
- **Retry с backoff и jitter**, плюс **бюджет retry** (например, retry не больше 10% базового трафика), чтобы медленная зависимость не получила шторм повторов ([[dead-letter-queues-and-retries]]).
- **Аренды и fencing-токены**: когда таймаут приводит к появлению нового лидера или держателя блокировки, старый может быть всё ещё жив; монотонный токен позволяет хранилищу отклонять его запоздалые записи ([[distributed-locks-and-fencing]], [[leases-heartbeats-and-health]]).
- **Circuit breaker** превращает повторяющиеся таймауты в быстрые отказы, чтобы потоки перестали накапливаться ([[circuit-breaker]]).
- **Дедлайны распространяются**: передавай оставшийся бюджет вниз по цепочке (дедлайны gRPC, отмена через `Context`), а не позволяй каждому звену выбирать своё число ([[grpc-and-protobuf]]).

### Детекторы отказов
- Heartbeat с окном таймаута — это детектор отказов с настраиваемой долей ложных срабатываний. φ-accrual детекторы (Cassandra, Akka) выдают уровень подозрения вместо булева значения, так что порог подстраивается под наблюдаемую задержку.
- Liveness- и readiness-пробы в Kubernetes — ровно это: readiness убирает pod из балансировщика при подозрении, liveness перезапускает его при более сильных свидетельствах ([[kubernetes-basics]]).

### Как подавать на собеседовании
- «Вызов упал по таймауту, что делаешь?» Не «повторяю»: сначала проверить, что операция идемпотентна и бюджет retry ещё есть, затем повторить с jitter на другой инстанс, а когда бюджет исчерпан — вернуть коррелированную ошибку ([[distributed-tracing]]).

## Пример
Вызов Spring `RestClient` к серверу entitlement для eSIM с явными таймаутами соединения и чтения, ограниченным retry с jitter и ключом идемпотентности, чтобы повтор не мог активировать дважды.
```java
@Configuration
public class EntitlementClientConfig {
    @Bean
    RestClient entitlementClient(RestClient.Builder builder) {
        var factory = new JdkClientHttpRequestFactory(
            HttpClient.newBuilder().connectTimeout(Duration.ofSeconds(1)).build());
        factory.setReadTimeout(Duration.ofSeconds(3));          // активация — быстрый вызов
        return builder.baseUrl("https://es.internal/v1").requestFactory(factory).build();
    }
}

@Service
@RequiredArgsConstructor
public class ActivationClient {
    private final RestClient client;

    @Retryable(retryFor = {ResourceAccessException.class, HttpServerErrorException.class},
               maxAttempts = 3, backoff = @Backoff(delay = 200, multiplier = 2, random = true))
    public ActivationResult activate(UUID orderId, String iccid) {
        return client.post().uri("/activations")
            .header("Idempotency-Key", orderId.toString())  // один и тот же ключ при каждом retry
            .body(new ActivationRequest(iccid))
            .retrieve().body(ActivationResult.class);
    }
}
```
Три попытки с 200/400/800 мс (со случайным разбросом) укладываются в бюджет вызывающего; без ключа вторая попытка после потерянного ответа создала бы вторую активацию ([[rest-clients]]).

## Подводные камни
- Отсутствие таймаута вообще: JDK `HttpClient` и многие настройки Kafka/JDBC по умолчанию «ждут вечно» при чтении; одна зависшая зависимость может положить весь сервис.
- Повторять неидемпотентные `POST`, потому что «сеть нестабильная»: дубликат проявится как двойное списание или второе SMS.
- Health check, проверяющие только «процесс запущен» и не замечающие серых отказов; проверяй реальный путь к зависимости с коротким таймаутом.
- Синхронный retry внутри Kafka listener при медленной зависимости: вся партиция встаёт, consumer lag растёт, и запускается rebalance ([[spring-kafka-consumer]], [[backpressure-and-flow-control]]).
- Связанные заметки: [[cap-and-pacelc]] — почему разделение вынуждает делать выбор, [[exactly-once-myth]] — что retry делают с гарантиями доставки, [[sockets-and-connection-pooling]] — чего стоит зависшее соединение.
