## Кратко
Настенные часы на разных машинах расходятся (рассинхронизация, skew), идут с разной скоростью (дрейф, drift) и могут прыгнуть назад после коррекции NTP. Поэтому вопрос «какое событие произошло раньше» нельзя решить сравнением временных меток с двух узлов. Для упорядочивания используй **логические часы**: **часы Лэмпорта** (Lamport clock) дают полный порядок, согласованный с причинностью, **векторные часы** (vector clock) вдобавок обнаруживают конкурентность, а **гибридные логические часы** (hybrid logical clock) сохраняют метки читаемыми, оставаясь причинными. Настенное время оставь для людей и TTL, а длительности измеряй **монотонными** часами.

## Основное

### Почему физическое время ненадёжно
- **Рассинхронизация (skew)**: два синхронизированных по NTP сервера в одном датацентре обычно расходятся на несколько миллисекунд; между облаками или при неправильно настроенном хосте — на секунды. Google Spanner нужны атомные часы и GPS, чтобы ограничить неопределённость примерно 7 мс, и даже так он выжидает этот интервал при commit.
- **Дрейф (drift)**: кварцевые генераторы дрейфуют на десятки ppm, то есть на секунды в сутки без синхронизации.
- **Скачки**: NTP плавно подгоняет (slew) малые ошибки, но большие исправляет *скачком* (step); `System.currentTimeMillis()` может пойти назад. Високосные секунды ломали системы, которые считали настенное время монотонным.
- **Паузы**: stop-the-world GC, живая миграция VM или закрытая крышка ноутбука останавливают процесс, а не мир. Аренда (lease), у которой «осталось 2 с», может уже истечь к моменту, когда поток проснётся ([[distributed-locks-and-fencing]], [[garbage-collection]]).

### Два вида часов в Java
| Задача | Использовать | Не использовать |
|---|---|---|
| Временная метка записи, строки лога, TTL | `Instant.now()` / `Clock` (время суток, может прыгать) | `System.nanoTime()` (бессмысленно между процессами) |
| Измерение прошедшего времени, таймауты, ограничение частоты | `System.nanoTime()` (монотонное, в пределах одной JVM) | разницы `currentTimeMillis()` (ломаются при скачке NTP) |

- Внедряй `java.time.Clock` в сервисы, чтобы тесты могли управлять временем ([[testing-async-and-kafka-flows]]).

### Часы Лэмпорта (логические, полный порядок)
- Каждый узел хранит счётчик. При локальном событии: `c = c + 1`. При отправке: приложить `c`. При получении: `c = max(c, received) + 1`.
- Гарантия: если A произошло раньше B (happened-before), то `L(A) < L(B)`. Обратное **неверно**: `L(A) < L(B)` не означает причинной связи; события могут быть конкурентными.
- Ничьи разрешаются по id узла, что даёт полный порядок, пригодный, например, для детерминированного выбора победителя среди конфликтующих записей.

### Векторные часы (обнаруживают конкурентность)
- Каждый узел хранит вектор `[c1, c2, ..., cn]`, по одному слоту на узел. При событиях увеличивай свой слот; при получении бери поэлементный максимум, затем увеличивай свой.
- `V(A) < V(B)` (каждая компонента ≤ и хотя бы одна <) означает, что A произошло раньше B. Если ни одно не ≤ другого — события **конкурентны**: настоящий конфликт, который нужно сливать ([[multi-leader-and-leaderless]]).
- Цена: O(число узлов) на метку; хранилища в стиле Dynamo используют векторы версий на ключ с обрезкой. Cassandra обошлась без них и использует «последняя запись побеждает» (last-writer-wins) по настенным часам — с хорошо известными последствиями.

### Гибридные логические часы (HLC)
- Метка = `(physicalTime, logicalCounter)`. Физическая часть следует за локальными часами, но никогда не идёт назад; счётчик увеличивается для событий в пределах одной миллисекунды или когда полученная метка опережает.
- Сохраняет причинность, как у Лэмпорта, остаётся на ограниченном расстоянии от реального времени и сортируется как 64-битное число. Используется в CockroachDB, YugabyteDB, cluster time в MongoDB.

### Где это бьёт по backend-разработчику
- **Last-writer-wins** по `updated_at` из разных сервисов молча теряет обновления, когда часы расходятся.
- **Упорядочивание событий** по метке времени producer между партициями Kafka — это не причинный порядок; для порядка внутри ключа используй offset партиции ([[kafka-architecture]]).
- **Истечение токена / TTL**, проверяемое на узле, чьи часы спешат на 30 с, отклоняет валидные JWT ([[jwt-authentication]]); закладывай допуск на рассинхронизацию.
- **Распределённые трейсы** со span, которые заканчиваются раньше, чем начинаются: рассинхронизация часов между сервисами ([[distributed-tracing]]).
- **UUID v7 и Snowflake id** содержат настенное время: на практике сортируемы, но не доказывают отношение happened-before ([[time-money-and-ids]]).

## Пример
Часы Лэмпорта в виде небольшого потокобезопасного класса плюс сравнение порядка с разрешением ничьих по id узла, которое использовал бы разрешатель конфликтов.
```java
public final class LamportClock {
    private final AtomicLong counter = new AtomicLong();

    /** Локальное событие или отправка: возвращает метку, которую надо приложить к сообщению. */
    public long tick() {
        return counter.incrementAndGet();
    }

    /** Получение: слить метку отправителя перед обработкой. */
    public long receive(long remote) {
        return counter.updateAndGet(local -> Math.max(local, remote) + 1);
    }

    public record Stamp(long time, String nodeId) implements Comparable<Stamp> {
        @Override public int compareTo(Stamp o) {
            int byTime = Long.compare(time, o.time);
            return byTime != 0 ? byTime : nodeId.compareTo(o.nodeId);  // детерминированное разрешение ничьей
        }
    }
}

// использование в Kafka consumer: метка приходит в заголовке, обработка идёт в согласованном порядке
long stamp = clock.receive(Long.parseLong(new String(record.headers().lastHeader("lamport").value())));
```
Два узла, каждый из которых обновляет одного и того же абонента «в одно и то же время», дадут метки, при которых везде побеждает ровно одна, независимо от того, чьи настенные часы спешат.

## Подводные камни
- `new Date()`/`Instant.now()` для таймаутов: скачок NTP заставляет 5-секундный таймаут сработать мгновенно или никогда. Используй `nanoTime()` или `Duration` на основе `Clock`.
- Сортировать объединённый поток событий из нескольких сервисов по `createdAt` и называть это «порядком, в котором всё происходило».
- Хранить локальное время без зоны (`timestamp` вместо `timestamptz`), а потом сравнивать между серверами в разных зонах ([[time-money-and-ids]]).
- Верить, что у аренды «ещё есть время» после долгой паузы; держатель должен перепроверять с fencing-токеном при каждой защищённой записи.
- Связанные заметки: [[consistency-models]] — что может означать «последняя запись», [[leases-heartbeats-and-health]] — аренды, построенные на часах, [[failure-modes-and-timeouts]] — почему медленный узел выглядит мёртвым.
