## Кратко
Модель согласованности (consistency model) — это контракт о том, какие значения может вернуть чтение, когда данные лежат на нескольких узлах. От сильной к слабой: **линеаризуемость** (linearizable: одна копия, порядок реального времени), **последовательная** (sequential: один глобальный порядок, но не привязанный к настенным часам), **причинная** (causal: сохраняется только порядок «причина — следствие»), **в конечном счёте** (eventual: реплики сходятся, если записи прекратились). Между ними — **сессионные гарантии** (session guarantees), которые реально запрашиваются в коде приложения: чтение своих записей (read-your-writes), монотонные чтения (monotonic reads), монотонные записи (monotonic writes). Более сильные модели стоят задержки и доступности; выбирай самую слабую модель, которая сохраняет бизнес-инвариант.

## Основное

### Лестница
| Модель | Гарантия | Цена | Где встречается |
|---|---|---|---|
| **Линеаризуемая** | Каждая операция выглядит так, будто выполнилась атомарно в некоторый момент между своим началом и концом; все клиенты согласны с этим порядком, и он совпадает с реальным временем | Круг до кворума или лидера на каждую операцию; недоступна при разделении (CP в [[cap-and-pacelc]]) | etcd, ZooKeeper, primary Postgres, чтения Kafka с лидера, проверки уникальности, блокировки ([[distributed-locks-and-fencing]]) |
| **Последовательная** | Все клиенты видят один и тот же порядок операций, и операции каждого клиента идут в порядке программы; глобальный порядок не обязан совпадать с реальным временем | Дешевле линеаризуемой: реплика может отставать, пока все видят одну и ту же историю | Одна партиция Kafka для одного consumer group; большинство схем «serializable, но с репликацией» |
| **Причинная** | Если запись B сделана после чтения A, никто не увидит B без A; конкурентные записи могут быть видны в любом порядке | Нужны векторы версий (version vectors) или отслеживание зависимостей | Комментарий к посту никогда не появляется раньше поста; causal sessions в MongoDB |
| **В конечном счёте** | Если записи прекратились, все реплики сходятся к одному значению; нет ни ограничения на время, ни обещаний порядка | Самая дешёвая; всегда доступна | DNS, асинхронные реплики для чтения, Cassandra на `ONE`, кэши |

### Сессионные гарантии (те, под которые пишется код)
- **Чтение своих записей (read-your-writes)**: после того как я сохранил профиль, следующий мой запрос его показывает. Ломается асинхронными репликами, когда чтение уходит на отстающий follower ([[read-replicas-and-stale-reads]]). Исправление: направлять чтения пользователя на лидера в течение N секунд после записи или передавать LSN/offset последней записи и ждать, пока реплика догонит.
- **Монотонные чтения (monotonic reads)**: увидев версию 5, я больше никогда не увижу версию 4. Ломается при round-robin по репликам. Исправление: «липкая» маршрутизация (sticky routing) по пользователю/сессии.
- **Монотонные записи (monotonic writes)**: мои записи применяются в том порядке, в котором я их отправил. Ломается в схемах с несколькими лидерами и независимыми путями ([[multi-leader-and-leaderless]]).
- **Запись после чтения (writes-follow-reads)**: ответ, который я пишу после чтения сообщения, упорядочен после этого сообщения. Это причинная гарантия на уровне сессии.

### Линеаризуемость и сериализуемость
- Линеаризуемость — про **один объект** и **реальное время**: один регистр, чтения видят последнюю запись.
- Сериализуемость (serializability) — про **транзакции над многими объектами**: результат равен *какому-то* последовательному порядку, не обязательно порядку реального времени ([[transactions-acid-and-isolation]], [[postgres-isolation-levels]]).
- «Строгая сериализуемость» (strict serializable) = обе сразу. Postgres на одном узле с `SERIALIZABLE` фактически строго сериализуем; добавь асинхронную реплику — и чтения с неё сериализуемы, но устаревшие.

### Почему линеаризуемые чтения дороги
- Лидер может ответить на линеаризуемое чтение, только если *уверен*, что всё ещё лидер. Смещённый лидер с просроченной арендой (lease) ответил бы старыми данными. Raft решает это через read index (раунд heartbeat до большинства) или чтения на основе аренды ([[raft-explained]], [[leases-heartbeats-and-health]]).
- Кворумное чтение в системах в стиле Dynamo (`R + W > N`) даёт «чтение видит последнюю *подтверждённую* запись», но при конкурентных записях без read repair всё равно не линеаризуемо; классический пример из DDIA.

### Выбор на практике
- Деньги, складские остатки, уникальные имена, выбор лидера: линеаризуемость, через одного лидера или консенсусное хранилище.
- Ленты, счётчики, аналитика, уведомления: согласованность в конечном счёте плюс сессионные гарантии там, где пользователь заметит.
- Всё, что «пользователь только что сделал и теперь ожидает увидеть»: чтение своих записей — минимум.

### Согласованность в конечном счёте на деле
- Откуда она берётся: асинхронная реплика, отстающая на 200 мс, запись в кэше, живущая до своего TTL, поисковый индекс, наполняемый через CDC, второй регион. В каждом случае чтение сразу после записи может вернуть старое значение.
- Это не только про распределённые базы: один Postgres с репликой на чтение или Redis перед ним уже согласованы в конечном счёте для того, кто читает из реплики или кэша ([[read-replicas-and-stale-reads]], [[caching]]).
- Сделай её приемлемой, а не притворяйся, что её нет: читай свои записи с primary, показывай состояния «обрабатывается», версионируй ключи кэша и проектируй идемпотентных потребителей, переживающих перестановку сообщений ([[idempotency]]).
- Два значения слова «согласованность» (ACID и CAP) сравниваются в [[transactions-acid-and-isolation]].

## Пример
Чтение своих записей поверх потоковой репликации Postgres: писатель возвращает LSN commit, а читатель перед обслуживанием следующего запроса ждёт, пока реплика проиграет WAL дальше этой точки (или откатывается на primary).
```java
@Service
@RequiredArgsConstructor
public class SubscriberService {
    private final JdbcTemplate primary;
    private final JdbcTemplate replica;

    /** Возвращает позицию WAL, которую клиент должен прислать обратно как токен. */
    @Transactional
    public String updateTariff(UUID subscriberId, String tariff) {
        primary.update("UPDATE subscriber SET tariff = ? WHERE id = ?", tariff, subscriberId);
        return primary.queryForObject("SELECT pg_current_wal_insert_lsn()::text", String.class);
    }

    public Subscriber get(UUID subscriberId, String lsnToken) {
        boolean caughtUp = lsnToken == null || Boolean.TRUE.equals(replica.queryForObject(
            "SELECT pg_last_wal_replay_lsn() >= ?::pg_lsn", Boolean.class, lsnToken));
        JdbcTemplate source = caughtUp ? replica : primary;   // дешёвый путь, иначе лидер
        return source.queryForObject("SELECT id, tariff FROM subscriber WHERE id = ?",
            (rs, i) -> new Subscriber(rs.getObject("id", UUID.class), rs.getString("tariff")), subscriberId);
    }
}
```
Токен может передаваться в cookie или заголовке ответа; он даёт одной сессии собственную согласованность, не заставляя каждое чтение идти на primary ([[postgres-replication-and-failover]]).

## Подводные камни
- Называть асинхронно реплицируемую систему «согласованной», потому что она ACID на каждом узле: ACID — про транзакции на одном узле, а модели согласованности — про то, что видят другие узлы.
- Отдавать чтение из кэша или реплики сразу после записи, а потом «исправлять» это обновлением на клиенте: это отсутствующая гарантия чтения своих записей, а не баг интерфейса ([[distributed-cache-coherence]]).
- Считать Kafka линеаризуемой между партициями: порядок соблюдается только внутри одной партиции; consumer, читающий две партиции, может увидеть эффекты не в причинном порядке ([[kafka-consumer]]).
- Выбирать линеаризуемость везде «на всякий случай», а потом удивляться, почему p99-задержка удвоилась и система падает вместе с одной зоной доступности ([[latency-numbers]]).
- Связанные заметки: [[cap-and-pacelc]] — компромисс, в котором живут эти модели, [[time-and-clocks]] — почему для «последней» записи нужны логические часы, [[leader-follower-replication]] — механика отставания.
