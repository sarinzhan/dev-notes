## Кратко
**Хеширование** (hashing) одностороннее: дайджест фиксированного размера, из которого нельзя восстановить вход; используется для проверки целостности, дедупликации, адресации по содержимому и, с медленным алгоритмом и солью, для хранения паролей. **Шифрование** (encryption) двустороннее: шифртекст плюс ключ дают обратно открытый текст; используется, когда данные нужно прочитать снова (данные карт в хранилище, персональные данные в базе, TLS в сети). **Кодирование** (encoding: Base64, hex, URL-кодирование) — ни то ни другое, это просто представление, и секретности оно не даёт никакой. Пароли никогда не шифруют и никогда не хешируют простым SHA-256; они проходят через **bcrypt, scrypt или Argon2id** с солью для каждого пользователя и коэффициентом стоимости, который делает перебор дорогим. Типы ключей и подписи описаны в [[symmetric-and-asymmetric-crypto]].

## Основное
### Три операции
| | Хеширование | Шифрование | Кодирование |
|---|---|---|---|
| Обратимо | нет | да, с ключом | да, кем угодно |
| Нужен ключ | нет (HMAC: да) | да | нет |
| Размер результата | фиксированный (SHA-256: 32 байта) | ≈ размер входа + IV/тег | больше входа |
| Назначение | целостность, идентичность содержимого, проверка пароля | конфиденциальность | передача байтов в виде текста |
| Примеры | SHA-256, SHA-3, BLAKE3, bcrypt, Argon2 | AES-GCM, ChaCha20-Poly1305, RSA-OAEP | Base64, hex, URL-кодирование |

- Криптографический хеш должен быть *стойким к нахождению прообраза* (нельзя найти вход по хешу), *стойким к нахождению второго прообраза* и *стойким к коллизиям* (нельзя найти два входа с одинаковым хешем). MD5 и SHA-1 взломаны в части коллизий; для контрольных сумм без требований безопасности они ещё годятся, для подписей и сертификатов — нет.
- `hashCode()` в Java — не криптографический хеш: 32 бита, предназначен для распределения по корзинам, коллизии находятся тривиально ([[hash-tables]], [[equals-and-hashcode]]).
- Хеширование детерминировано: один и тот же вход всегда даёт один и тот же дайджест. Именно это делает его полезным для дедупликации и ключей идемпотентности ([[idempotency]]) и именно это делает его опасным для паролей без соли.

### Хранение паролей
- Почему не SHA-256: он быстрый by design. GPU вычисляет миллиарды SHA-256 в секунду; утёкшая таблица несолёных хешей за несколько часов поддаётся радужным таблицам и атакам по словарю.
- **Соль** (salt): случайное значение длиной от 16 байт для каждого пользователя, хранится рядом с хешем. Делает заранее вычисленные таблицы бесполезными и заставляет атакующего взламывать каждого пользователя отдельно. Соль не секретна.
- **Перец** (pepper): дополнительный секрет, применяемый к каждому паролю и хранящийся вне базы (в хранилище секретов, [[secrets-management]]); защищает хеши, если утекла только БД.
- **Медленные функции с большими затратами памяти** (memory-hard): bcrypt (cost 10–12, ~100–250 мс), scrypt, **Argon2id** (текущая рекомендация: память ≥ 64 МБ, 2–3 итерации, параллелизм 1–4). Стоимость настраивают так, чтобы вход занимал ~100 мс на твоём железе, а атакующему понадобились десятилетия.
- Проверка — это `hash(candidate, stored_salt, stored_params) == stored_hash`, сравнение за постоянное время. Современные библиотеки кодируют алгоритм, параметры и соль в одну строку (`$argon2id$v=19$m=65536,t=3,p=4$...`), поэтому параметры можно позже повысить, а старые хеши обновить при следующем успешном входе.
- Spring Security: `PasswordEncoderFactories.createDelegatingPasswordEncoder()` хранит хеши с префиксами `{bcrypt}`/`{argon2}` и проверяет тем алгоритмом, который использовался; `BCryptPasswordEncoder(12)` или `Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8()` ([[spring-security-basics]]).
- Не «шифруй» пароли: тот, у кого ключ (твой сервис), может прочитать любой пароль, а утечка ключа раскрывает их все в открытом виде.

### Хеши с ключом и целостность
- **HMAC** (hash-based message authentication code) = хеш + секретный ключ. Доказывает, что сообщение создано кем-то, у кого есть ключ, и не было изменено: подписи вебхуков (`X-Signature: sha256=...`), JWT `HS256` ([[jwt-authentication]]), подписанные cookie, подпись API-запросов ([[api-security-checklist]]).
- Сравнивай MAC через `MessageDigest.isEqual`, а не `Arrays.equals` или `String.equals`, которые возвращаются на первом отличающемся байте и раскрывают информацию через время выполнения.
- Контрольные суммы для целостности без противника: CRC32 в ZIP и пакетах записей Kafka, SHA-256 для дайджестов Docker-образов и проверки артефактов Maven. Если атакующий может подменить и файл, и его хеш, помогут только подпись или HMAC.

### Шифрование в хранилище, вкратце
- Используй режим AEAD (AES-256-GCM, ChaCha20-Poly1305): конфиденциальность и целостность вместе, случайный 12-байтовый nonce на каждое сообщение, никогда не используемый повторно с тем же ключом. Механика — в [[symmetric-and-asymmetric-crypto]].
- Шифрование на уровне полей в БД (PAN карты, номера документов) означает, что этот столбец нельзя индексировать и по нему нельзя искать; храни отдельный HMAC значения для поиска на равенство или столбец с последними 4 цифрами для отображения. PCI DSS требует именно этого для PAN ([[emv-card-processing]]).
- Ключи шифрования — это секреты с жизненным циклом (ротация, отзыв); стандартный паттерн — конвертное шифрование (envelope encryption): ключ данных для каждой записи, обёрнутый мастер-ключом в KMS.

## Пример
Регистрация и вход с Argon2 через Spring Security, плюс HMAC для вебхука.
```java
@Service
public class CredentialService {
    private final PasswordEncoder encoder =
            Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8(); // m=16MB,t=2,p=1; в проде увеличь m
    private final UserRepository users;
    private final byte[] webhookKey;   // из хранилища секретов, а не из application.yml

    CredentialService(UserRepository users, @Value("${webhook.key}") String keyB64) {
        this.users = users;
        this.webhookKey = Base64.getDecoder().decode(keyB64);
    }

    public void register(String login, char[] password) {
        String hash = encoder.encode(CharBuffer.wrap(password)); // соль генерируется и встраивается
        users.save(new User(login, hash));
        Arrays.fill(password, '\0');
    }

    public boolean login(String login, char[] password) {
        return users.findByLogin(login)
                .map(u -> encoder.matches(CharBuffer.wrap(password), u.passwordHash()))
                .orElseGet(() -> { encoder.matches("dummy", DUMMY_HASH); return false; }); // то же время выполнения
    }

    public boolean webhookSignatureValid(byte[] body, String headerHex) throws GeneralSecurityException {
        Mac mac = Mac.getInstance("HmacSHA256");
        mac.init(new SecretKeySpec(webhookKey, "HmacSHA256"));
        byte[] expected = mac.doFinal(body);
        return MessageDigest.isEqual(expected, HexFormat.of().parseHex(headerHex));
    }
}
```

## Подводные камни
- Простой `SHA-256(password)` или `MD5(password + salt)`: с солью или без, быстрые хеши взламываются со скоростью GPU. Допустимы только bcrypt/scrypt/Argon2.
- Считать Base64 защитой: «токен», который является Base64 от `userId:role`, может прочитать и подделать кто угодно. Подписывай его (HMAC/JWT) или делай непрозрачным и случайным.
- Хешировать данные с низкой энтропией (номера телефонов, национальные идентификаторы) и называть это анонимизацией: пространство входов маленькое, словарь всех номеров хешируется за секунды. Используй HMAC с секретным ключом или токенизацию.
- Логировать пароль в открытом виде или включать его в сообщение исключения при неудачном входе; Sentry и ELK потом хранят его вечно ([[owasp-top-10-for-backend]]).
- Писать собственное сравнение, генерировать соль через `java.util.Random` или самодельное «шифрование» через XOR. `SecureRandom`, JCA и Spring Security существуют не просто так.
- Связанные заметки: [[symmetric-and-asymmetric-crypto]] — что на самом деле делают AES, RSA и подписи; [[jwt-authentication]] — токены с HMAC и с подписью RSA.
