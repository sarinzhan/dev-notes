## Кратко
Секрет — это всё, раскрытие чего даёт доступ: пароли БД, API-ключи, ключи подписи, приватные ключи TLS, client secret OAuth, секреты вебхуков. Они никогда не должны лежать в git, в Docker-образе, в закоммиченном в репозиторий `application.yml` или в логах. Лестница зрелости: переменные окружения, внедряемые при deploy → секреты Kubernetes/Docker, смонтированные как файлы → менеджер секретов (HashiCorp Vault, AWS Secrets Manager, GCP Secret Manager, Azure Key Vault), из которого приложение читает при старте или во время работы, с **короткоживущими, ротируемыми** учётными данными и журналом аудита. Spring Boot читает всё это как обычные свойства ([[spring-boot-properties-and-profiles]]), поэтому код приложения между этапами не меняется. Криптографическое использование ключей описано в [[symmetric-and-asymmetric-crypto]].

## Основное
### Где секретов быть не должно
- **Git**: история вечна; секрет, однажды закоммиченный и «удалённый» в следующем commit, всё ещё есть в каждом клоне и в интерфейсе GitLab. Если это случилось, сначала ротируй секрет, затем переписывай историю. Сканеры в pre-commit (gitleaks, GitLab Secret Detection, `detect-secrets`) ловят типичные шаблоны (`AKIA...`, `-----BEGIN PRIVATE KEY-----`, `password=`).
- **Docker-образы**: слой `COPY .env` или `ENV DB_PASSWORD=` читается через `docker history` и при любом pull из реестра; секреты для сборки передаются через `--mount=type=secret` ([[dockerfile-and-images]]).
- **Логи, трейсы, трекеры ошибок**: `toString()` объекта конфигурации, залогированный URL `DataSource` с паролем, заголовок `Authorization` в логе запросов, heap dump из actuator ([[owasp-top-10-for-backend]]).
- **Клиентская сторона**: всё, что отправлено в браузер или мобильное приложение, публично, включая «обфусцированные» API-ключи.

### Механизмы доставки
| Механизм | Как приложение его получает | Ротация | Аудит | Подходит для |
|---|---|---|---|---|
| Переменные окружения | `${DB_PASSWORD}` в `application.yml`, задаётся CI/compose/K8s | redeploy | нет | небольшие установки, 12-factor приложения |
| Смонтированные файлы секретов | K8s `Secret` → volume → `spring.config.import=configtree:/etc/secrets/` | обновить Secret, приложение перечитывает или перезапускается | журнал аудита K8s | вариант по умолчанию в Kubernetes |
| Менеджер секретов (Vault, облачный SM) | SDK или Spring Cloud Vault/AWS при старте, или агент-sidecar, записывающий файлы | динамические секреты с TTL, автоматически | полный | прод, соответствие требованиям |
| Sealed/External Secrets | зашифрованные манифесты в git (SOPS, Sealed Secrets) или оператор, синхронизирующий из SM в K8s Secrets | через SM | через SM | GitOps |

- Переменные окружения видны каждому процессу в контейнере (`/proc/<pid>/environ`), наследуются дочерними процессами и часто попадают в дампы падений. Файлы с правами `0400` — шаг вперёд; менеджер секретов с идентичностью для каждого сервиса — настоящее решение.
- Объекты `Secret` в Kubernetes только закодированы в base64; включи шифрование etcd в хранилище и ограничь через RBAC, кто может делать `get secrets` ([[kubernetes-basics]]). Предпочитай проецирование в файлы, а не `envFrom`.
- Docker Compose на одном хосте: блок верхнего уровня `secrets:` монтирует файлы в `/run/secrets/`; Docker Swarm шифрует их в журнале Raft ([[docker-swarm]]).

### Идентичность вместо статических учётных данных
- Самый сильный паттерн — вообще без долгоживущего секрета: рабочая нагрузка доказывает, *кто она* (токен service account в Kubernetes, IAM-роль в облаке, сертификат SPIFFE, [[mtls-and-service-to-service-auth]]), а менеджер секретов выдаёт **динамические учётные данные**: роль Postgres, созданную на лету с TTL в 1 час, облачный токен, действующий 15 минут.
- Тогда ротация становится рутиной, а не инцидентом. Для статических секретов ротацию нужно заложить в дизайн: два валидных ключа одновременно (старый и новый), потребители перечитывают без перезапуска, старый ключ отзывается после переходного периода. Точки подключения на стороне приложения: `@RefreshScope` в Spring Cloud, `setPassword` у работающего пула HikariCP или эндпоинт JWKS с несколькими `kid` ([[jwt-authentication]]).
- Проблема начальной загрузки («секрет ноль», secret zero): приложению нужны учётные данные, чтобы обратиться к Vault. Решай её идентичностью платформы (метод аутентификации K8s, AWS IAM auth), а не ещё одним статическим токеном.

### Операционные правила
- Один секрет на одно назначение и одно окружение; staging никогда не делит ключ с продом.
- Минимальные привилегии: роль приложения в БД владеет только своей схемой; токен CI может пушить образы, но не читать продовые секреты.
- Аудит и алерты на чтение продовых секретов вне окон deploy.
- Сценарий инцидента: сначала ротировать, потом расследовать; веди перечень, где используется каждый секрет, чтобы ротация была чек-листом, а не археологией.
- Локальная разработка: файлы `.env` в `.gitignore`, шаблон `application-local.yml` с заглушками или Testcontainers, чтобы у разработчиков никогда не было настоящих учётных данных ([[testcontainers]]).

## Пример
Секрет Kubernetes, спроецированный в файлы и читаемый через config tree Spring Boot; пароль datasource ротируется без изменения образа.
```yaml
# k8s: секрет создан External Secrets Operator из Vault, никогда не пишется руками
apiVersion: v1
kind: Secret
metadata:
  name: esim-api-secrets
type: Opaque
stringData:                      # показано для наглядности; в git это ExternalSecret, а не значения
  db-password: "..."
  smdp-api-key: "..."
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: esim-api
spec:
  template:
    spec:
      serviceAccountName: esim-api          # идентичность для аутентификации в Vault/K8s, без статического токена
      containers:
        - name: app
          image: registry.example/esim-api:2026.10.27
          env:
            - name: SPRING_CONFIG_IMPORT
              value: "optional:configtree:/etc/secrets/"
          volumeMounts:
            - name: secrets
              mountPath: /etc/secrets
              readOnly: true
      volumes:
        - name: secrets
          secret:
            secretName: esim-api-secrets
            defaultMode: 0400
```
```yaml
# application.yml в репозитории: никаких значений, только ссылки
spring:
  datasource:
    url: jdbc:postgresql://${DB_HOST}:5432/esim
    username: esim_api
    password: ${db-password}        # файл /etc/secrets/db-password через configtree
smdp:
  api-key: ${smdp-api-key}
management:
  endpoints:
    web:
      exposure:
        include: health,prometheus   # никогда env, configprops или heapdump в проде
```
С `configtree:` каждое имя файла становится свойством; один и тот же `application.yml` работает локально с `DB_PASSWORD` из `.env` и в проде — со смонтированным Secret.

## Подводные камни
- `application-prod.yml` с настоящими паролями, «потому что репозиторий приватный»: он есть у каждого разработчика, каждого CI-раннера и каждого будущего подрядчика; приватный не значит секретный.
- Логировать итоговую конфигурацию при старте (дамп `Environment`, `/actuator/env`, `--debug`) или класс `@ConfigurationProperties` со сгенерированным `toString()`, который включает ключ.
- Секреты в переменных CI без флагов `masked`/`protected` или напечатанные через `set -x` в скрипте пайплайна.
- Ротация, которая требует одновременного перезапуска всех потребителей; закладывай две валидные версии одновременно, иначе ротации не будет никогда.
- Считать приемлемым HMAC-ключ для JWT без `kid`, который никогда не ротировался, потому что «он в Vault»: хранение — только половина работы; вторая половина — жизненный цикл.
- Связанные заметки: [[spring-boot-properties-and-profiles]] — порядок источников свойств, благодаря которому работает внедрение, [[api-security-checklist]] — как ключи предъявляются и проверяются на краю API.
