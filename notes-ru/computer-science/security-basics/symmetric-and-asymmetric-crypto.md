## Кратко
**Симметричное** шифрование (AES, ChaCha20) использует один общий ключ в обе стороны: быстро, подходит для больших объёмов данных, но у обеих сторон ключ уже должен быть. **Асимметричная** криптография (RSA, эллиптические кривые) использует пару ключей: зашифрованное открытым ключом может открыть только закрытый ключ, а **подписанное** закрытым ключом любой может проверить открытым. Реальные системы их комбинируют: асимметричное рукопожатие (обмен ключами + подпись для доказательства идентичности) согласует свежий симметричный ключ, а затем трафик защищает симметричный AEAD; так устроены TLS ([[tls-handshake-and-certificates]]), SSH и конвертное шифрование в KMS. **HMAC** — симметричный родственник подписи: целостность и подлинность, когда у обеих сторон есть общий секрет. Одностороннее хеширование против шифрования — в [[hashing-vs-encryption]].

## Основное
### Симметричная
- **AES** (ключи 128/256 бит) — блочный шифр; пригодным к использованию его делает *режим*. ECB раскрывает закономерности (никогда не используй), CBC требует дополнения (padding) и MAC, **GCM** — аутентифицированное шифрование (AEAD): выдаёт шифртекст плюс 16-байтовый тег, и расшифровка падает, если изменён хотя бы один бит. ChaCha20-Poly1305 — предпочтительный AEAD там, где нет аппаратного ускорения AES.
- Каждому шифрованию нужен уникальный **nonce/IV** (12 байт для GCM). Повторное использование nonce с тем же ключом в GCM ломает и конфиденциальность, и ключ целостности. Генерируй через `SecureRandom` и храни рядом с шифртекстом или используй сохраняемый счётчик; ротируй ключ задолго до 2^32 сообщений.
- Производительность: AES-GCM с AES-NI работает на гигабайтах в секунду; поэтому TLS и шифрование дисков после рукопожатия симметричны.
- Размеры ключей: AES-128 всё ещё нормален, AES-256 — вариант по умолчанию для соответствия требованиям. Ключи — это случайные байты из `KeyGenerator`/`SecureRandom`, никогда не выводимые напрямую из пароля; если иначе нельзя, используй PBKDF2/Argon2 (KDF) с солью.

### Асимметричная
| | RSA | Эллиптические кривые (ECDSA / Ed25519, ECDH / X25519) |
|---|---|---|
| Размер ключа для ~128-битной стойкости | 3072 бита | 256 бит |
| Операции | шифрование (OAEP), подпись (PSS) | подпись, согласование ключей; прямого шифрования нет |
| Скорость | медленная подпись, быстрая проверка | быстро и то и другое; крошечные ключи и подписи |
| Где встречается | старые сертификаты, JWT `RS256`, устаревшие ключи эмитента в HSM/EMV | обмен ключами в TLS 1.3, SSH-ключи, JWT `ES256`/`EdDSA`, современные сертификаты |

- **Шифрование открытым ключом** используется только для небольших данных (симметричный ключ, PIN-блок): RSA-OAEP может зашифровать максимум размер ключа минус дополнение. Зашифровать файл «через RSA» на самом деле означает сгенерировать ключ AES, зашифровать им файл, а ключ AES зашифровать RSA: **гибридное / конвертное шифрование**. Сервисы KMS (AWS KMS, Vault transit) предоставляют именно это: ключ данных на каждый объект, обёрнутый мастер-ключом, который никогда не покидает HSM.
- **Согласование ключей** (ECDH / X25519): каждая из двух сторон комбинирует свой закрытый ключ с открытым ключом другой и приходит к одному и тому же общему секрету, не пересылая его. Со свежими эфемерными ключами на каждую сессию это даёт *прямую секретность* (forward secrecy): украденный долговременный ключ не позволит расшифровать прошлый трафик. TLS 1.3 сделал это обязательным.
- **Цифровая подпись**: хешировать сообщение, зашифровать хеш закрытым ключом (RSA) или выполнить алгоритм подписи на эллиптических кривых; проверяющий пересчитывает хеш и проверяет его открытым ключом. Даёт целостность, подлинность и *неотказуемость* (non-repudiation): подписать мог только владелец закрытого ключа. Сертификаты — это подписи CA над открытым ключом плюс идентичностью; EMV-карты несут подписанные эмитентом данные, которые терминал проверяет офлайн ([[emv-card-processing]]).
- Открытый ключ публичен, но трудная задача — *привязать* его к идентичности: цепочки PKI/CA, `known_hosts` в SSH, пиннинг ключей или отпечатки, переданные по другому каналу. Идентичность между сервисами на этой основе описана в [[mtls-and-service-to-service-auth]].

### HMAC и когда его достаточно
- HMAC-SHA256 над сообщением с общим секретом даёт целостность и подлинность, но **не** неотказуемость: создать его могла любая из сторон. Подходит внутри одного домена доверия (два твоих собственных сервиса, вебхук от провайдера, который делит с тобой секрет, JWT `HS256`, выпущенный и проверяемый одним и тем же сервисом). Используй подписи, когда проверяющий не должен иметь возможности подделать (токены, проверяемые многими сервисами, документы, релизы ПО) ([[jwt-authentication]], [[api-security-checklist]]).

### Выбор на практике
| Нужно | Использовать |
|---|---|
| Шифровать данные в хранилище в своей БД | AES-256-GCM, ключ данных на запись, мастер-ключ в KMS/Vault |
| Защищать трафик между сервисами | TLS 1.3 (mTLS, если важна идентичность клиента) |
| Подписать токен, который проверяют многие сервисы | ES256 / EdDSA / RS256, открытый ключ через JWKS |
| Аутентифицировать вебхук партнёра | HMAC-SHA256 с общим секретом и меткой времени |
| Хранить пароли | не шифрование: Argon2id / bcrypt |

## Пример
Конвертное шифрование номера документа абонента: случайный ключ данных AES на каждую запись, обёрнутый мастер-ключом (здесь локальный ключ AES вместо вызова KMS), с id записи в качестве ассоциированных данных GCM, чтобы шифртекст нельзя было перенести между строками.
```java
public final class FieldCrypto {
    private static final SecureRandom RNG = new SecureRandom();
    private final SecretKey masterKey;  // в проде: wrap/unwrap через KMS/Vault, ключа никогда нет в JVM

    public FieldCrypto(SecretKey masterKey) { this.masterKey = masterKey; }

    public record Sealed(byte[] wrappedDataKey, byte[] iv, byte[] ciphertext) {}

    public Sealed seal(String recordId, byte[] plaintext) throws GeneralSecurityException {
        SecretKey dataKey = KeyGenerator.getInstance("AES").generateKey();      // 256 бит по умолчанию в современных JDK
        byte[] iv = new byte[12];
        RNG.nextBytes(iv);
        Cipher gcm = Cipher.getInstance("AES/GCM/NoPadding");
        gcm.init(Cipher.ENCRYPT_MODE, dataKey, new GCMParameterSpec(128, iv));
        gcm.updateAAD(recordId.getBytes(StandardCharsets.UTF_8));              // привязывает шифртекст к строке
        byte[] ct = gcm.doFinal(plaintext);

        Cipher wrap = Cipher.getInstance("AESWrap");                            // обёртывание ключа по RFC 3394
        wrap.init(Cipher.WRAP_MODE, masterKey);
        return new Sealed(wrap.wrap(dataKey), iv, ct);
    }

    public byte[] open(String recordId, Sealed s) throws GeneralSecurityException {
        Cipher unwrap = Cipher.getInstance("AESWrap");
        unwrap.init(Cipher.UNWRAP_MODE, masterKey);
        SecretKey dataKey = (SecretKey) unwrap.unwrap(s.wrappedDataKey(), "AES", Cipher.SECRET_KEY);
        Cipher gcm = Cipher.getInstance("AES/GCM/NoPadding");
        gcm.init(Cipher.DECRYPT_MODE, dataKey, new GCMParameterSpec(128, s.iv()));
        gcm.updateAAD(recordId.getBytes(StandardCharsets.UTF_8));
        return gcm.doFinal(s.ciphertext());                                     // AEADBadTagException при подделке
    }
}
```
Ротация мастер-ключа означает повторное обёртывание небольших ключей данных, а не повторное шифрование каждой записи.

## Подводные камни
- `AES/ECB` (вариант JDK по умолчанию, если написать `Cipher.getInstance("AES")`) или CBC без MAC: утечка закономерностей и атаки padding oracle. Всегда указывай полное преобразование и предпочитай GCM.
- Статические или повторно используемые IV «ради детерминированности» с GCM: катастрофа. Если нужно детерминированное шифрование для поиска на равенство, используй вместо этого отдельный столбец с HMAC.
- RSA с дополнением PKCS#1 v1.5 для шифрования, 1024-битные ключи, подписи на SHA-1: всё устарело; используй OAEP/PSS или переходи на эллиптические кривые.
- Ключи в `application.yml`, в образе или в git ([[secrets-management]]); ключ рядом с шифртекстом — это не шифрование.
- Самописные протоколы: «мы шифруем JSON через AES и отправляем по HTTP» — это слабее обычного HTTPS и гораздо больше работы. Используй TLS и подписывай на уровне приложения, только когда нужна неотказуемость или сквозная защита через посредников.
- Связанные заметки: [[tls-handshake-and-certificates]] — как эти примитивы сочетаются в сети, [[hashing-vs-encryption]] — дайджесты, соли и хеширование паролей.
