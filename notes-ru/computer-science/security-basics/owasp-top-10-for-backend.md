## Кратко
OWASP Top 10 — стандартный список категорий рисков веб-приложений. Для бэкенда на Java/Spring реальные инциденты дают: **внедрение** (injection: SQL, команды ОС, LDAP, JPQL), **нарушенный контроль доступа** (IDOR, отсутствие авторизации на методе), **нарушенная аутентификация** (слабые сессии, токены без срока действия), **SSRF** (твой сервер запрашивает URL, выбранный атакующим), **небезопасная десериализация** (сериализация Java, полиморфный JSON), **ошибки конфигурации безопасности** (открытый actuator, отладочные эндпоинты, учётные данные по умолчанию) и **утечка секретов или персональных данных в логи**. Почти у всех одна и та же форма исправления: никогда не доверяй входным данным, привязывай параметры вместо конкатенации, авторизуй каждое обращение к объекту и не отключай настройки фреймворка по умолчанию. Потоки аутентификации описаны в [[authentication-vs-authorization]] и [[spring-security-basics]]; укрепление эндпоинтов — в [[api-security-checklist]].

## Основное
### Категории и как они выглядят в Spring-сервисе
| Категория OWASP (список 2021) | Симптом в бэкенде | Основная защита |
|---|---|---|
| A01 Нарушенный контроль доступа | `GET /orders/{id}` возвращает заказ любого пользователя (IDOR); админский эндпоинт только скрыт в UI | авторизация на уровне объекта: `WHERE id = ? AND owner = ?`, `@PreAuthorize`, запрет по умолчанию |
| A02 Криптографические сбои | персональные данные в открытом виде, пароли в MD5, HTTP между сервисами | [[hashing-vs-encryption]], [[symmetric-and-asymmetric-crypto]], TLS везде |
| A03 Внедрение | SQL/JPQL, собранный из строк, `Runtime.exec` с пользовательским вводом, внедрение в логи | привязанные параметры, списки разрешённого, никакого shell |
| A04 Небезопасный дизайн | нет rate limit на OTP, сброс пароля только по номеру телефона | моделирование угроз для потока, лимиты, step-up аутентификация |
| A05 Ошибки конфигурации безопасности | `/actuator/env` и `/actuator/heapdump` публичны, стектрейсы в ответах, CORS `*` с учётными данными | закрыть actuator, обобщённые тела ошибок, явный CORS ([[cookies-sessions-and-cors]]) |
| A06 Уязвимые компоненты | Log4Shell, старый Jackson, Spring4Shell | сканирование зависимостей (OWASP Dependency-Check, Trivy), быстрый путь обновления |
| A07 Сбои идентификации и аутентификации | JWT с `alg: none`, без срока действия, фиксация сессии, нет защиты от перебора | [[jwt-authentication]], короткоживущие токены, блокировка/backoff |
| A08 Целостность ПО и данных | `ObjectInputStream` на недоверенных байтах, default typing в Jackson, неподписанные артефакты CI | избегать сериализации Java, явные полиморфные типы, подписанные сборки |
| A09 Сбои логирования и мониторинга | нет аудита событий аутентификации, персональные данные и токены в логах, никто не получил алерт | структурированный журнал аудита, очистка, алерты ([[error-tracking-with-sentry]]) |
| A10 SSRF | поле «импорт по URL» или URL вебхука запрашивает `http://169.254.169.254/` или внутренний сервис | список разрешённых хостов, резолвить и блокировать приватные диапазоны, исходящий прокси |

### Внедрение
- SQL: `"... WHERE msisdn = '" + msisdn + "'"` пропускает `' OR 1=1 --`. `PreparedStatement`, `JdbcTemplate` с `?`, именованные параметры JPQL и выводимые запросы Spring Data привязывают значения, так что они никогда не разбираются как SQL. Динамические *идентификаторы* (столбец сортировки, имя таблицы) привязать нельзя; пропускай их через список разрешённых значений.
- JPQL/HQL уязвимы точно так же; `@Query("... :status")` безопасен, `em.createQuery("... '" + s + "'")` — нет.
- Команды ОС: `ProcessBuilder(List.of("ffmpeg", "-i", file))` со списком аргументов, никогда `bash -c "..." + input`. Ещё лучше — вообще без shell.
- Внедрение в логи: `\n` в пользовательском поле подделывает фальшивую строку лога; структурированное JSON-логирование ([[logging-stacks]]) это предотвращает. Log4Shell был внедрением через конвейер логирования. Кроме того: роль приложения в Postgres не должна быть суперпользователем (`COPY ... TO PROGRAM` существует).

### Контроль доступа и аутентификация
- Аутентификация (кто ты) — это не авторизация (что тебе можно). Валидный токен в запросе ничего не говорит о том, может ли *этот* пользователь читать *этот* заказ. Проверяй владение в запросе или доменной проверкой и тестируй это: тест, в котором пользователь B запрашивает ресурс пользователя A.
- Безопасность на уровне методов `@PreAuthorize("hasRole('OPS') or #orderId == principal.orderId")` и запрет всего по умолчанию `.anyRequest().authenticated()`; внутренние эндпоинты выноси на отдельный порт или за network policy, а не прячь.
- Токены: срок действия, привязка к audience, ротация refresh-токенов, проверка подписи с зафиксированным алгоритмом ([[jwt-authentication]]). Сессии: менять id при входе, `HttpOnly; Secure; SameSite`.
- Массовое присваивание (mass assignment): привязка тела запроса прямо к сущности позволяет клиенту выставить `role` или `balance`. Используй DTO запроса только с разрешёнными полями ([[spring-mvc-validation-and-uploads]]).

### SSRF и десериализация
- SSRF: любое место, где сервер делает запрос на URL, переданный пользователем (регистрация вебхука, импорт аватара, «проверить соединение»). Обычные цели — эндпоинты метаданных облака и внутренние админские API. Защита: список разрешённых хостов/схем, резолвить DNS и отвергать приватные/link-local диапазоны *в момент соединения* (DNS rebinding), отключить редиректы или перепроверять после каждого, направлять через исходящий прокси со своим списком разрешённого, использовать клиент с таймаутами ([[rest-clients]]).
- Сериализация Java (`ObjectInputStream`) на недоверенных байтах — это удалённое выполнение кода через цепочки гаджетов; `ObjectInputFilter` (JEP 290) ограничивает классы, но правильный ответ — «не надо» (JSON, protobuf). Jackson: никогда не включай default typing глобально; `@JsonTypeInfo` с явным закрытым набором подтипов. XML: отключай DTD и внешние сущности (XXE) в каждом парсере.

### Логирование, ошибки и неправильная конфигурация
- Никогда не логируй заголовки `Authorization`, пароли, OTP-коды, полный PAN, сессионные cookie; маскируй в конвертере Logback и в `beforeSend` Sentry, чтобы ничего не попадало в [[sebep-incident-analysis]] неочищенным.
- Ответы с ошибками: клиенту — обобщённое сообщение и correlation id; стектрейс остаётся в логе (`server.error.include-stacktrace=never` в проде).
- Actuator: открывай только `health,prometheus`, на management-порту внутри сети кластера; `heapdump` содержит все секреты, которые есть в памяти.
- Цепочка поставок: фиксируй версии, сканируй образы, держи путь обновления по CVE за один день; Renovate и сканирование зависимостей в CI делают это рутиной ([[maven]]).

## Пример
Один и тот же поиск, написанный уязвимо и безопасно, плюс проверка URL, защищённая от SSRF.
```java
@Repository
public class SubscriberRepository {
    private final JdbcTemplate jdbc;
    private static final Set<String> SORTABLE = Set.of("created_at", "msisdn", "status");

    SubscriberRepository(JdbcTemplate jdbc) { this.jdbc = jdbc; }

    // УЯЗВИМО: msisdn = "' OR '1'='1" выгружает таблицу; sort = "1; DROP TABLE ..." выполняет это.
    public List<Subscriber> findBad(String msisdn, String sort) {
        return jdbc.query("SELECT * FROM subscriber WHERE msisdn = '" + msisdn + "' ORDER BY " + sort,
                SubscriberRepository::map);
    }

    // БЕЗОПАСНО: значение привязано; идентификатор проходит через список разрешённых; владение проверяется в запросе.
    public Optional<Subscriber> find(String msisdn, String sort, long accountId) {
        if (!SORTABLE.contains(sort)) throw new IllegalArgumentException("sort");
        var rows = jdbc.query(
                "SELECT * FROM subscriber WHERE msisdn = ? AND account_id = ? ORDER BY " + sort,
                SubscriberRepository::map, msisdn, accountId);
        return rows.stream().findFirst();
    }

    private static Subscriber map(ResultSet rs, int i) throws SQLException {
        return new Subscriber(rs.getLong("id"), rs.getString("msisdn"), rs.getString("status"));
    }
}

final class WebhookUrlValidator {
    static URI validate(String raw) throws Exception {
        URI uri = URI.create(raw);
        if (!"https".equals(uri.getScheme()) || uri.getPort() != -1) throw new IllegalArgumentException("scheme/port");
        for (InetAddress a : InetAddress.getAllByName(uri.getHost())) {
            if (a.isLoopbackAddress() || a.isSiteLocalAddress() || a.isLinkLocalAddress() || a.isAnyLocalAddress())
                throw new IllegalArgumentException("private address");
        }
        return uri; // и HTTP-клиент не должен следовать редиректам или должен перепроверять каждый переход
    }
}
```

## Подводные камни
- «Мы используем ORM, значит, мы в безопасности»: конкатенация JPQL, нативные запросы и `ORDER BY`, собранный из параметров запроса, всё равно уязвимы для внедрения.
- Проверять авторизацию в контроллере и забыть про consumer Kafka, задачу по расписанию и GraphQL-резолвер, которые вызывают тот же метод сервиса; ставь проверку в сервис или в запрос.
- Набор тестов с `@WithMockUser`, проверяющий только счастливый путь; добавь негативные тесты (чужой пользователь, истёкший токен, нет роли) и считай их регрессионными.
- Маскировать персональные данные в логе приложения, но отправлять полные тела запросов в Sentry, бэкенд трассировки или отладочный топик Kafka.
- Блокировать SSRF сравнением строки хоста (`!host.startsWith("10.")`): обходится через DNS rebinding, IPv6, десятичные IP и редиректы. Проверяй разрешённый адрес и последний переход.
- Связанные заметки: [[api-security-checklist]] — rate limiting, защита от повторного воспроизведения и валидация входа на краю; [[secrets-management]] — как держать ключи вне кода и логов.
