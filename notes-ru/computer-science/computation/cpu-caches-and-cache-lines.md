## Кратко
Основная память примерно в 100 раз медленнее ядра, поэтому каждое ядро держит небольшие быстрые копии недавно использованной памяти в **кэшах L1/L2**, а более крупный **L3** общий для всех ядер. Кэши перемещают данные фиксированными **кэш-линиями (cache lines)** (64 байта на x86 и большинстве ARM), а не отдельными байтами. Код работает быстро, когда у него есть **локальность**: он повторно использует те же линии (временная) или проходит память последовательно (пространственная). Два потока, пишущие в разные переменные, которые случайно оказались в одной линии, вызывают **ложное разделение (false sharing)**: линия мечется между ядрами, и «lock-free» счётчик становится медленнее синхронизированного. Это аппаратная причина того, что «массивы обгоняют связные списки» ([[arrays-and-dynamic-arrays]], [[linked-lists]]), а также причина появления `@Contended` и полосатых (striped) счётчиков в JDK.

## Основное
### Иерархия
| Уровень | Типичный размер | Задержка | Кем разделяется |
|---|---|---|---|
| Регистры | ~1 КБ | 0–1 такт | одно ядро |
| L1 (раздельный: данные + инструкции) | по 32–64 КБ | ~4 такта | одно ядро |
| L2 | 512 КБ – 2 МБ | ~12–14 тактов | одно ядро |
| L3 (LLC) | 16–96 МБ | ~40–60 тактов | все ядра сокета |
| DRAM | гигабайты | ~70–100 нс (200–300 тактов) | все |

- Чтение сначала проверяет L1, затем L2, L3, затем память; каждый промах стоит задержки следующего уровня. CPU также *предвыбирает* (prefetch) линии наперёд при последовательном доступе, поэтому линейный проход работает почти на пропускной способности памяти, а случайный доступ — на задержке DRAM ([[latency-numbers]]).
- **TLB** кэширует трансляцию виртуальных адресов в физические; промах TLB добавляет обход таблицы страниц. Огромные страницы (huge pages, `-XX:+UseTransparentHugePages`) уменьшают промахи TLB для больших куч ([[memory-management]]).

### Кэш-линии и локальность
- Память загружается линиями по 64 байта. Чтение одного `int` бесплатно подтягивает 15 его соседей; проход по `int[]` затрагивает новую линию каждые 16 элементов, проход по `LinkedList<Integer>` затрагивает минимум одну новую линию на элемент (объект узла) плюс ещё одну для упакованного `Integer`.
- **Пространственная локальность**: данные, используемые вместе, должны храниться вместе. Массивы примитивов, поля `record`, расположенные в одном объекте, колоночное хранение для аналитики ([[column-and-wide-column-stores]]).
- **Временная локальность**: недавно использованные данные скоро понадобятся снова. Обрабатывай фрагмент полностью, прежде чем переходить дальше (блокирование циклов, loop blocking), держи горячие структуры достаточно маленькими, чтобы они оставались в L2.
- Размещение объектов в JVM: заголовок 12–16 байт, поля переупорядочиваются JVM для минимизации выравнивания, ссылки по 4 байта при сжатых указателях (compressed oops). Поиск в `HashMap` — это погоня за указателями: таблица → узел → объект ключа → поля ключа, и каждый шаг потенциально отдельная линия ([[hashmap-internals]], [[hash-tables]]).

### Когерентность и ложное разделение
- Ядра поддерживают согласованность кэшей протоколом **MESI** (Modified, Exclusive, Shared, Invalid): чтобы записать линию, ядро должно владеть ею эксклюзивно, а это инвалидирует копии в других ядрах. Следующее чтение на другом ядре промахивается и загружает линию заново.
- Когерентность работает на уровне *линии*, а не переменной. Если поток A пишет `counterA`, а поток B пишет `counterB`, и обе лежат в тех же 64 байтах, каждая запись инвалидирует копию другого ядра: это **ложное разделение**. Пропускная способность может упасть в 10 раз без какой-либо видимой гонки данных.
- Исправления: вынести горячие поля в отдельную линию с помощью выравнивания (padding) (`@jdk.internal.vm.annotation.Contended`, требует `-XX:-RestrictContended`) или вручную добавить семь неиспользуемых полей `long`; использовать отдельный счётчик на поток и суммировать при чтении (`LongAdder` делает именно это своими полосатыми ячейками); держать состояние каждого потока в отдельных объектах, а не в соседних ячейках массива.
- Истинное разделение горячей линии (один `AtomicLong`, который инкрементируют 16 потоков) страдает от той же стоимости передачи; конкуренция за `CAS` — отчасти конкуренция за кэш-линию ([[lock-free-and-cas]]).

### Вопросы в стиле собеседования
- *Почему `ArrayList` быстрее `LinkedList` даже при вставке в середину?* Сдвиг непрерывного блока через `System.arraycopy` — это последовательная операция с памятью, для которой работает предвыборка; проход по связному списку до нужной позиции — это один промах кэша на узел.
- *Что такое memory-bound и CPU-bound?* Memory-bound-код ждёт промахов кэша; добавление ядер почти не помогает, и исправлять нужно размещение данных, а не алгоритмические трюки. Профайлеры показывают для такого кода низкий IPC.
- *Сбрасывает ли `volatile` кэш?* Нет. Кэши всегда когерентны; `volatile` ограничивает переупорядочивание и видимость через буфер записи (store buffer) ([[memory-models-and-visibility]], [[java-memory-model]]).

## Пример
Два потока инкрементируют соседние поля против полей с выравниванием. Запускать через JMH; версия с выравниванием обычно в 5–10 раз быстрее на многоядерной машине.
```java
public class FalseSharingDemo {

    // Оба счётчика делят одну 64-байтную линию: каждая запись инвалидирует копию другого ядра.
    static final class Packed {
        volatile long a;
        volatile long b;
    }

    // Выравнивание сдвигает b в другую линию. (@Contended делает то же самое без лишнего шума.)
    static final class Padded {
        volatile long a;
        long p1, p2, p3, p4, p5, p6, p7;
        volatile long b;
    }

    static void run(Runnable incA, Runnable incB) throws InterruptedException {
        Thread t1 = new Thread(() -> { for (int i = 0; i < 100_000_000; i++) incA.run(); });
        Thread t2 = new Thread(() -> { for (int i = 0; i < 100_000_000; i++) incB.run(); });
        t1.start(); t2.start(); t1.join(); t2.join();
    }

    public static void main(String[] args) throws InterruptedException {
        Packed p = new Packed();
        long t0 = System.nanoTime();
        run(() -> p.a++, () -> p.b++);
        System.out.printf("packed: %d ms%n", (System.nanoTime() - t0) / 1_000_000);

        Padded q = new Padded();
        t0 = System.nanoTime();
        run(() -> q.a++, () -> q.b++);
        System.out.printf("padded: %d ms%n", (System.nanoTime() - t0) / 1_000_000);
    }
}
```
`LongAdder`, счётчики размера в `ConcurrentHashMap` и кольцевые буферы в стиле Disruptor опираются на этот приём.

## Подводные камни
- Добавлять поля выравнивания, которые JIT может удалить: неиспользуемые не-volatile поля могут быть выброшены или переупорядочены. Используй `@Contended` или вынеси поля выравнивания в иерархию суперклассов (классический приём `long p1..p7` в родительском классе), чтобы размещение было стабильным.
- Рассуждать о размещении Java-объекта по порядку объявления полей: HotSpot переупорядочивает поля по размеру и типу. Проверяй с помощью JOL (`jol-core`), а не гадай.
- Бенчмарки на ноутбуке с 2 ядрами или с потоками, привязанными к одному ядру, не показывают ложного разделения; эффект проявляется только между физическими ядрами и сокетами.
- Раздутые «оптимизированные» структуры: выравнивание всего подряд вытесняет реальные данные из L1. Выравнивай только поля, в которые конкурентно пишут разные потоки.
- Связанные заметки: [[cpu]] — про конвейер, [[lru-cache-design]] и [[caching]] — про кэши на программном уровне, которые следуют той же логике локальности.
