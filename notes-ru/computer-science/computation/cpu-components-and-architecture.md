## Кратко
Ядро процессора — это небольшой набор частей, собранных вокруг тактового генератора: **устройство управления (control unit)**, которое читает инструкции и направляет всё остальное, **АЛУ (ALU)**, выполняющее арифметику и логику, **регистры**, хранящие те немногие значения, с которыми идёт работа прямо сейчас, и **блоки load/store**, которые перемещают данные между регистрами и иерархией кэшей. Современный чип повторяет такое ядро много раз, часто позволяет каждому ядру выполнять два аппаратных потока и окружает их общими кэшами, контроллером памяти и межсоединением. **ISA** (x86-64, ARM64) — это контракт, который видит софт; **микроархитектура** — то, как конкретный чип его реализует, и именно она меняется от поколения к поколению.

## Основное
### Части одного ядра
| Часть | Задача | Что это значит для кода |
|---|---|---|
| Тактовый генератор | Тикает несколько миллиардов раз в секунду; каждая стадия продвигается по тику | 3 ГГц = 0,33 нс на такт; промах кэша до RAM — ~300 тактов ожидания |
| Устройство управления / front end | Читает байты инструкций, декодирует их в микрооперации, предсказывает ветвления | Декодировать x86 сложно; горячий цикл, который помещается в кэш декодированных µop, работает быстрее |
| Регистры | 16–32 64-битных слота общего назначения плюс векторные регистры и флаги; единственное хранилище, которое АЛУ читает напрямую | Метод, чьи значения помещаются в регистры, быстрый; «выталкивание» (spilling) на стек стоит загрузок и сохранений |
| АЛУ | Целочисленное сложение, вычитание, сравнение, сдвиг, логика; обычно несколько на ядро | Простая целочисленная работа почти бесплатна; стоимость — в ожидании операндов |
| FPU / векторные блоки | Плавающая точка и SIMD (AVX, NEON): одна инструкция над 4–16 значениями | JIT автоматически векторизует простые циклы по массивам; `BigDecimal` не выигрывает никогда |
| Блоки load/store + кэш L1 | Читают и пишут память через кэш; отслеживают незавершённые промахи | В большинстве бэкенд-кода доминирует доступ к памяти, а не арифметика ([[cpu-caches-and-cache-lines]]) |
| Предсказатель ветвлений | Угадывает цель перехода до того, как известно условие | Предсказуемые ветвления ничего не стоят; ветвление 50/50 стоит сброса конвейера ([[how-cpu-executes-code]]) |
| Буфер переупорядочивания / планировщик | Держит инструкции в полёте, выпускает их, когда операнды готовы, завершает (retire) в порядке программы | Позволяет ядру прятать задержки, выполняя более поздние независимые инструкции раньше |

### Регистры чуть подробнее
- **Счётчик команд (program counter)** (instruction pointer): адрес следующей инструкции. Меняется переходами, вызовами, возвратами и прерываниями.
- **Указатель стека (stack pointer)** и **указатель кадра (frame pointer)**: где находятся вершина стека и кадр текущего потока ([[anatomy-of-a-process]]).
- **Общего назначения**: аргументы, возвращаемые значения, счётчики циклов, адреса. Соглашение о вызовах (calling convention) фиксирует, какие регистры несут первые аргументы, поэтому вызов с шестью параметрами `int` не трогает память.
- **Флаги**: результат последнего сравнения (ноль, отрицательное, перенос, переполнение); условные переходы их читают.
- **Управляющие и системные регистры**: база таблицы страниц, режим привилегий, маски прерываний; записываются только в режиме ядра ([[operating-system-architecture]]).

### ISA и микроархитектура
- **Архитектура набора команд (instruction set architecture)** определяет инструкции, регистры и модель памяти, на которые может полагаться программа. x86-64 и ARM64 — две, которые важны для серверов; у JVM есть JIT-бэкенд для каждой.
- **Микроархитектура** — одна реализация: сколько декодеров, насколько глубокий конвейер, насколько большие кэши, насколько агрессивный предсказатель. Два чипа с одной ISA выполняют один и тот же бинарник с разной скоростью.
- Упорядочивание памяти — часть ISA: x86 строго упорядочен (загрузки и сохранения в основном видны в порядке программы), ARM упорядочен слабо. Один и тот же Java-код с пропущенным `volatile` может работать на x86 и ломаться на ARM ([[memory-models-and-visibility]], [[java-memory-model]]).

### За пределами одного ядра
- **Многоядерность**: у каждого ядра свои кэши L1/L2 и свой front end; ядра делят L3 и контроллер памяти. Потоки на разных ядрах работают по-настоящему параллельно; планировщик ОС решает, какой поток куда попадёт ([[cpu-scheduling]]).
- **Одновременная многопоточность (simultaneous multithreading)** (hyper-threading): одно ядро представляется двумя аппаратными потоками, которые делят его исполнительные блоки. Полезно, когда один поток простаивает на памяти; почти нулевой выигрыш, когда оба упираются в вычисления. Облачный инстанс «16 vCPU» — это обычно 8 ядер × 2 потока.
- **Когерентность кэшей (cache coherence)**: железо поддерживает копию строки кэша у каждого ядра согласованной; трафик этого протокола и делает дорогими конкурентные блокировки и false sharing ([[cpu-caches-and-cache-lines]]).
- **NUMA**: на многосокетных серверах у каждого сокета своя RAM; обращение к памяти другого сокета медленнее. Большие кучи JVM, растянутые на несколько сокетов, могут видеть неравномерные задержки.

### Где с этим соприкасаются ОС и JVM
- Переключение контекста сохраняет и восстанавливает перечисленные выше регистры; стоимость — не столько само копирование, сколько холодные кэши и состояние предсказателя после него ([[processes-and-threads]]).
- JIT размещает локальные переменные Java в регистрах, встраивает (inline) маленькие методы, чтобы их значения не покидали регистры, и генерирует векторные инструкции для простых циклов ([[compilation-interpretation-jit]]).
- Лимиты CPU в контейнерах применяются планировщиком через кванты времени, а не отъёмом ядер: лимит `1` на 16-ядерном узле всё равно позволяет потоку работать на любом ядре, но только 100 мс в каждом окне в 100 мс ([[docker-containers-and-resources]]).

## Пример
Что видит процессор, когда Java складывает два поля (`this.total += item.price`), после JIT, на x86-64:

```text
mov   rax, [rdi + 0x10]     ; загрузить this.total   → блок load, попадание в L1 ~4 такта
mov   rcx, [rsi + 0x18]     ; загрузить item.price   → блок load, независима, выполняется параллельно
add   rax, rcx              ; АЛУ, 1 такт, ждёт обе загрузки
mov   [rdi + 0x10], rax     ; блок store, буферизуется, не блокирует следующую инструкцию
```

Четыре инструкции, две из них — обращения к памяти. Если `item` только что создан, он горячий в L1, и всё занимает ~6 тактов; если `item` пришёл из большого массива, пройденного не по порядку, вторая загрузка промахивается до RAM, и те же четыре инструкции занимают ~300 тактов, пока буфер переупорядочивания пытается найти другую работу.

## Подводные камни
- Тактовая частота — не производительность. Серверное ядро на 2,5 ГГц с широким исполнением и большими кэшами обгоняет ноутбучное ядро на 4 ГГц на нагрузках баз данных.
- «vCPU» означает аппаратный поток, а не ядро. Два потока одного ядра делят его АЛУ; пулы потоков для CPU-bound работы планируй по физическим ядрам ([[executors-and-thread-pools]]).
- Процессор не выполняет Java и даже x86 в том виде, как он записан: front end переводит инструкции во внутренние микрооперации, а back end их переупорядочивает. То, что ты читаешь в дизассемблере `perf`, — контракт, а не расписание ([[instruction-lifecycle-and-pipelining]]).
- Связанные заметки: [[cpu-pipeline-walkthrough]] — цикл, прослеженный такт за тактом, [[numbers-bits-and-floating-point]] — что на самом деле вычисляют АЛУ и FPU.
