## Кратко
Целые числа хранятся в **дополнительном коде (two's complement)**, поэтому `Integer.MAX_VALUE + 1` превращается в отрицательное число без всякой ошибки. Дробные числа хранятся как **двоичная плавающая точка** IEEE 754: знак, порядок (экспонента) и 52-битная (double) или 23-битная (float) мантисса. У большинства десятичных дробей (0.1, 0.2, 0.3) нет точного двоичного представления, поэтому `0.1 + 0.2 == 0.30000000000000004`. Для денег, количеств и всего, что человек будет сверять, используй `BigDecimal` в Java и `numeric` в Postgres; `double` — для измерений, геометрии и статистики, где относительная ошибка 1e-16 допустима. Размеры типов Java и правила упаковки — в [[primitives-and-wrappers]].

## Основное
### Целые числа
- *n*-битное целое в дополнительном коде покрывает −2^(n−1) … 2^(n−1)−1. Смена знака — это «инвертировать биты и прибавить единицу»; старший бит — знаковый. `int` 32-битный: −2 147 483 648 … 2 147 483 647; `long` 64-битный.
- Переполнение происходит молча и с заворачиванием: `Integer.MAX_VALUE + 1 == Integer.MIN_VALUE`, а `Math.abs(Integer.MIN_VALUE)` по-прежнему отрицателен. `Math.addExact`/`multiplyExact` вместо этого бросают `ArithmeticException`; используй их для счётчиков, которые не должны заворачиваться (балансы, квоты).
- Деление отбрасывает дробную часть в сторону нуля; `%` сохраняет знак делимого, поэтому `-7 % 3 == -1`. `Math.floorMod` даёт неотрицательный результат, который обычно и нужен для индексов кольцевого буфера и корзин хеш-таблицы ([[hash-tables]]).
- Классический баг переполнения: `(low + high) / 2` в [[binary-search-and-variants|двоичном поиске]] переполняется на больших массивах; пиши `low + (high - low) / 2` или `(low + high) >>> 1`.
- В Java нет беззнаковых примитивов, но `Integer.toUnsignedString`, `Integer.compareUnsigned`, `Long.divideUnsigned` и `>>>` покрывают нужные случаи (разбор двоичных протоколов, байтовые поля EMV, хеши). Битовые трюки — в [[bit-manipulation]].
- Порядок байтов важен, когда целые числа передаются по сети: сетевой порядок — big-endian, x86 — little-endian; с этим справляются `ByteBuffer.order(...)` и `DataInputStream` (всегда big-endian) ([[java-nio]]).

### Плавающая точка IEEE 754
| Тип | Биты (знак/порядок/мантисса) | Десятичных знаков | Диапазон |
|---|---|---|---|
| `float` | 1 / 8 / 23 | ~7 | ±3.4e38 |
| `double` | 1 / 11 / 52 | ~15–16 | ±1.8e308 |

- Значение — это ±1.мантисса × 2^(порядок−смещение). Точны только дроби, знаменатель которых — степень двойки (0.5, 0.25, 0.375); 0.1 — периодическая двоичная дробь, округляемая на 53-м бите. Сложение двух округлённых чисел накапливает ошибку, отсюда `0.1 + 0.2 != 0.3`.
- Особые значения: `+0.0` и `-0.0` (равны по `==`, различаются по `Double.compare`), `Infinity` от переполнения или `1.0 / 0`, `NaN` от `0.0 / 0` или `sqrt(-1)`. `NaN != NaN`, поэтому единственная проверка — `Double.isNaN(x)`; `Double.equals` и `compareTo` считают NaN равным самому себе ради сортировки.
- Точность относительная: double около 1 отстоят друг от друга на ~2e-16, около 1e16 — на 2, поэтому `1e16 + 1 == 1e16`. Суммирование миллиона маленьких значений в один большой аккумулятор их теряет (используй суммирование Кэхэна (Kahan summation) или сортируй по возрастанию).
- Сравнение: никогда не `a == b` после арифметики; сравнивай `Math.abs(a - b) <= eps * Math.max(Math.abs(a), Math.abs(b))`.
- `float` занимает 4 байта и в бэкенд-коде редко оправдан, кроме больших массивов (ML-эмбеддинги, графика); `double` — тип по умолчанию, и на современных CPU он так же быстр.

### Десятичные типы для денег
- `BigDecimal` хранит немасштабированный `BigInteger` плюс масштаб (scale): `new BigDecimal("19.99")` — это ровно 1999 × 10^-2. Создавай из `String` или через `BigDecimal.valueOf(double)`; `new BigDecimal(0.1)` захватывает двоичный мусор (`0.1000000000000000055511151231257827...`).
- `equals` сравнивает и масштаб: `new BigDecimal("2.0").equals(new BigDecimal("2.00"))` даёт `false`; для равенства значений используй `compareTo`, а перед сохранением убирай или фиксируй масштаб.
- Делению нужен явный `MathContext` или масштаб и `RoundingMode`: `price.divide(BigDecimal.valueOf(3), 2, RoundingMode.HALF_EVEN)`; без этого бесконечный результат бросает `ArithmeticException`. Банковское округление (`HALF_EVEN`) — обычное значение по умолчанию в бухгалтерии; правила НДС могут предписывать `HALF_UP`.
- Альтернатива: хранить минорные единицы как `long` (тыйыны, центы) и конвертировать на границах. Быстро и просто, когда валюта одна и нет долей цента; ломается на курсах валют и процентных комиссиях. Оба подхода вместе со стороной БД — в [[time-money-and-ids]].
- Postgres: `numeric(19,4)` точный и с произвольной точностью; `real`/`double precision` — это IEEE 754; `money` зависит от локали, и его лучше избегать.

## Пример
Один и тот же расчёт тарифа на `double` и на `BigDecimal`.
```java
public class TariffDemo {
    public static void main(String[] args) {
        // Три пополнения по 0.10 KGS плюс бонус 0.20: должно быть ровно 0.50
        double d = 0.1 + 0.1 + 0.1 + 0.2;
        System.out.println(d);                 // 0.5000000000000001
        System.out.println(d == 0.5);          // false

        BigDecimal b = new BigDecimal("0.10")
                .add(new BigDecimal("0.10"))
                .add(new BigDecimal("0.10"))
                .add(new BigDecimal("0.20"));
        System.out.println(b);                 // 0.50
        System.out.println(b.compareTo(new BigDecimal("0.5")) == 0); // true

        // НДС 12% на 199.99, округлённый до ближайшего тыйына
        BigDecimal vat = new BigDecimal("199.99")
                .multiply(new BigDecimal("0.12"))
                .setScale(2, RoundingMode.HALF_EVEN);
        System.out.println(vat);               // 24.00  (23.9988 после округления)

        // Молчаливое целочисленное переполнение против точной арифметики
        int subscribers = Integer.MAX_VALUE;
        System.out.println(subscribers + 1);               // -2147483648
        System.out.println(Math.addExact(subscribers, 1)); // ArithmeticException
    }
}
```

## Подводные камни
- Колонки или поля типа `double` для цен, балансов и количеств: итоги уплывают на копейку, сверка не сходится, и баг всплывает через месяцы в финансах. Используй `BigDecimal` ↔ `numeric` от начала до конца, включая JSON (сериализуй как строку или десятичное число, но никогда как JS `number` больше 2^53).
- `BigDecimal` в ключах `HashMap` или проверках `equals` с несовпадающим масштабом; нормализуй через `setScale` или сравнивай через `compareTo`.
- Счётчики `int` для смещений сообщений, числа байтов или миллисекунд эпохи: `System.currentTimeMillis()` уже требует `long`; offset-ы Kafka и размеры файлов — тоже.
- Округлять на каждом промежуточном шаге вместо одного раза в конце или округлять `HALF_UP` в одном сервисе и `HALF_EVEN` в другом; договорись об одной политике округления на расчёт.
- `float` для всего, что разбирается из пользовательского ввода: 7 значащих цифр теряются после нескольких операций.
