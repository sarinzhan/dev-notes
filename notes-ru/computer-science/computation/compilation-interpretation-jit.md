## Кратко
Исходный код попадает на процессор одним из трёх путей. **Компилятор заранее (ahead-of-time, AOT)** (C, Go, Rust, GraalVM native-image) создаёт машинный код до запуска программы. **Интерпретатор** (CPython, shell, интерпретатор байт-кода JVM) читает промежуточное представление и выполняет его шаг за шагом. **JIT-компилятор (just-in-time)** начинает с интерпретации, следит, какой код «горячий», и компилирует его в машинный код прямо во время выполнения, используя реальные данные профилирования для оптимизации. JVM сочетает все три подхода: `javac` — это AOT-компилятор в байт-код, HotSpot интерпретирует байт-код, а затем C1/C2 JIT-компилируют горячие методы. Компромисс — время старта и прогрев (warm-up) против пиковой пропускной способности. Устройство самой JVM (JVM/JRE/JDK, загрузка классов) описано в [[jvm-jre-jdk]].

## Основное
### Три стратегии
| | AOT-компиляция | Интерпретация | JIT-компиляция |
|---|---|---|---|
| Когда код становится машинным | при сборке | никогда (машинный код — это сам интерпретатор) | во время выполнения, для горячих путей |
| Старт | самый быстрый | быстрый | медленнее: сначала интерпретация, потом компиляция |
| Пиковая производительность | высокая, но оптимизирована под обобщённый CPU и без профиля выполнения | самая низкая (в 10–50× медленнее) | самая высокая: знает реальный CPU, реальные типы, реальные частоты ветвлений |
| Переносимость | отдельный бинарник под каждую ОС/CPU | одна программа, много платформ | одна программа, JIT под каждую платформу внутри среды выполнения |
| Память | мало | мало | потоки компилятора, кэш кода, профили |
| Примеры | C, Go, Rust, GraalVM native-image | CPython, Ruby MRI (старые версии), bash | HotSpot, V8, .NET CLR, PyPy, LuaJIT |

- Все компиляторы проходят цепочку: лексический анализ → синтаксический разбор (AST) → семантический анализ (типы) → промежуточное представление → оптимизация → генерация кода. [[type-systems]] определяют, сколько может проверить фронтенд и сколько может предполагать бэкенд.
- Байт-код — это золотая середина: компактный стековый набор инструкций, который дёшево интерпретировать и легко проверять. `javac` почти ничего не оптимизирует; это намеренно оставлено JIT, у которого больше информации.

### Как это делает HotSpot (многоуровневая компиляция (tiered compilation), по умолчанию с Java 8)
1. **Интерпретатор** выполняет байт-код и для каждого метода считает вызовы и обратные переходы циклов (back-edges).
2. После ~200 вызовов (пороги уровней) метод уходит в **C1** (клиентский компилятор): быстрая компиляция, лёгкие оптимизации, вставка счётчиков профилирования.
3. После ~10–15 тыс. вызовов с профилем **C2** (серверный компилятор) перекомпилирует метод с агрессивными оптимизациями: встраивание (inlining, самая важная из всех), анализ убегания (escape analysis: размещение на стеке / скалярная замена объектов, которые никуда не утекают), развёртка циклов (loop unrolling), автовекторизация, девиртуализация на основе наблюдаемых типов.
4. Скомпилированный код хранится в **кэше кода (code cache)**; его размер ограничивает `-XX:ReservedCodeCacheSize`. Когда кэш заполняется, компиляция останавливается, и всё, что ещё не скомпилировано, остаётся интерпретируемым — классическая причина ситуации «сервис замедлился через две недели».
- **Спекуляция и деоптимизация**: C2 компилирует при допущениях («этот `List` всегда `ArrayList`», «эта ветка никогда не выполняется»). *Необычная ловушка (uncommon trap)* проверяет допущение; если оно нарушено, метод деоптимизируется обратно в интерпретатор и позже перекомпилируется. Мономорфное место вызова, ставшее мегаморфным после изменения конфигурации, может заметно замедлиться.
- **Замена на стеке (on-stack replacement, OSR)** позволяет долго работающему циклу переключиться на скомпилированный код прямо посреди выполнения, поэтому даже `main` с одним гигантским циклом получает выгоду.
- Полезные флаги: `-XX:+PrintCompilation` — посмотреть, что компилируется, `-XX:TieredStopAtLevel=1` — для быстро стартующих короткоживущих утилит, `-Xint` — принудительная интерпретация (только для отладки).

### Где это бьёт по бэкенд-разработчику
- **Прогрев**: первые несколько сотен запросов после deploy медленные. Readiness-пробы Kubernetes и балансировщики нагрузки не должны отправлять полный трафик на холодный pod; прогрей его несколькими синтетическими вызовами или используй CDS/CRaC (см. ниже).
- **JMH** существует потому, что наивные бенчмарки измеряют интерпретатор, удаление мёртвого кода (dead-code elimination) или свёртку констант (constant folding) вместо самого кода ([[how-cpu-executes-code]]).
- **Class Data Sharing (AppCDS)** и **CRaC** (checkpoint/restore) сокращают время старта за счёт снимка загруженных классов или целой прогретой JVM.
- **GraalVM native-image** — это AOT для Java: старт за миллисекунды и малый RSS, но закрытый мир (рефлексию, прокси и динамическую загрузку классов нужно объявлять заранее), долгие сборки и обычно более низкая пиковая пропускная способность, чем у C2. Spring Boot 3 его поддерживает; это имеет смысл для serverless и CLI-утилит, но редко — для долгоживущего Kafka-консьюмера.
- Project Leyden (Java 24+) добавляет в обычную JVM заблаговременное кэширование профилей и скомпилированного кода, перенося прогрев из времени выполнения во время сборки без ограничения закрытого мира.

### Вопросы в стиле собеседования
- *Java компилируемая или интерпретируемая?* И то и другое: заранее компилируется в байт-код, а байт-код интерпретируется и затем JIT-компилируется во время выполнения.
- *Почему JIT может обогнать AOT-компилятор?* Он видит реальную нагрузку: какие ветки выполняются, какие реализации действительно вызываются, какие инструкции есть у CPU. AOT обязан оставаться корректным для всех входных данных и базового CPU.
- *Почему `final` у локальной переменной не влияет на производительность?* JIT сам выводит фактическую неизменяемость (effective finality); `final` у полей и классов помогает в основном читаемости и модели памяти ([[immutable-objects]]).

## Пример
Наблюдение за работой JIT на горячем методе. Запуск: `java -XX:+PrintCompilation Warmup.java`.
```java
public class Warmup {
    // Имитирует работу на один запрос: разбирает строку, похожую на ICCID, и суммирует её цифры.
    static int checksum(String iccid) {
        int sum = 0;
        for (int i = 0; i < iccid.length(); i++) {
            sum += iccid.charAt(i) - '0';
        }
        return sum;
    }

    public static void main(String[] args) {
        String iccid = "8999700000000000001";
        for (int round = 0; round < 5; round++) {
            long t0 = System.nanoTime();
            int acc = 0;
            for (int i = 0; i < 2_000_000; i++) acc += checksum(iccid);
            System.out.printf("round %d: %d ms (acc=%d)%n",
                    round, (System.nanoTime() - t0) / 1_000_000, acc);
        }
    }
}
```
Типичный вывод: раунд 0 занимает десятки миллисекунд, пока `checksum` проходит через интерпретатор, C1 (`PrintCompilation` показывает уровень 3) и C2 (уровень 4, со встроенным `String.charAt`); последующие раунды занимают несколько миллисекунд. В сервисе та же кривая проявляется как p99-задержка в первую минуту после deploy.

## Подводные камни
- Измерять без прогрева и делать вывод «Java медленная» или «подход A быстрее»: первый прогон измеряет компиляцию, а не код. Используй JMH с итерациями прогрева.
- Заполненный кэш кода (`CodeCache is full. Compiler has been disabled`) незаметно опускает долгоживущую JVM до скорости интерпретатора; следи за `jvm_memory_used_bytes{area="nonheap"}` и при необходимости увеличивай `ReservedCodeCacheSize`.
- Мегаморфные места вызова в обобщённом коде фреймворков (один `handle(Event)`, диспетчеризующий на 20 обработчиков) нельзя встроить; `switch` по sealed-типу или отдельные слушатели на каждый тип сохраняют места вызова мономорфными.
- Сюрпризы native-image: библиотека, использующая рефлексию или `ServiceLoader`, работает на JVM и падает во время выполнения в нативном бинарнике, если не предоставлены метаданные достижимости (reachability metadata). Тестируй нативную сборку в CI, а не только JVM-сборку.
- Связанные заметки: [[jvm-memory-areas]] — где живут кэш кода и metaspace, [[garbage-collection]] — другой компонент среды выполнения, который конкурирует с JIT за CPU.
