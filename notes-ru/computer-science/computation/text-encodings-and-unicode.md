## Кратко
**Unicode** присваивает каждому символу номер — **кодовую точку (code point)** (U+0000 … U+10FFFF, ~1,1 млн позиций). **Кодировка** превращает кодовые точки в байты: **UTF-8** использует 1–4 байта на кодовую точку, совместима с ASCII и является стандартом везде — в сети и на диске; **UTF-16** использует 2 или 4 байта, и именно её раскрывают `char` и API `String` в Java. `char` в Java — это *кодовая единица (code unit)* UTF-16, а не символ: эмодзи или редкий иероглиф CJK — это два char (суррогатная пара), а видимый пользователю символ вроде «é» может быть одной кодовой точкой или двумя (e + комбинируемое ударение) в зависимости от **нормализации**. Большинство ошибок с кодировками возникает из-за того, что (1) полагаются на кодировку платформы по умолчанию, (2) считают `length()` числом символов, (3) сравнивают строки без нормализации. Внутреннее устройство `String` в Java — в [[strings-and-string-pool]].

## Основное
### Кодовые точки, кодовые единицы, графемы
| Термин | Значение | Пример: e + U+0301 + U+1F600 (эмодзи) |
|---|---|---|
| Графемный кластер (grapheme cluster) | то, что пользователь видит как один символ | 2 |
| Кодовая точка | скалярное значение Unicode | 3: U+0065, U+0301, U+1F600 |
| Кодовая единица UTF-16 (`char`) | 16-битная единица; кодовые точки выше U+FFFF используют суррогатную пару | 4 |
| Байт UTF-8 | 1–4 байта на кодовую точку | 1 + 2 + 4 = 7 |

- `String.length()` считает char (единицы UTF-16). `codePointCount(0, length())` считает кодовые точки. Для подсчёта графем нужен `BreakIterator.getCharacterInstance()` (или ICU4J для полной корректности).
- `charAt(i)` на половине суррогатной пары возвращает мусор; используй потоки `codePoints()` или `Character.isSurrogate`. `substring` посередине пары даёт непарный суррогат, который при кодировании превращается в `?` или U+FFFD.
- С Java 9 (компактные строки, compact strings) `String` внутри хранит Latin-1 по 1 байту на char, а UTF-16 — только при необходимости; для API это незаметно.

### Кодировки
- **ASCII**: 7 бит, 128 символов, подмножество всех кодировок ниже.
- **Latin-1 / Windows-1251 / KOI8-R**: однобайтовые унаследованные кодировки; кириллический текст в неверной кодировке превращается в «кракозябры» (mojibake). До сих пор встречаются в старых телеком- и банковских интерфейсах (SMS в GSM 7-bit или UCS-2, теги EMV).
- **UTF-8**: байты ASCII не меняются (один байт, старший бит 0); у многобайтовых последовательностей характерные ведущие и продолжающие байты (`110xxxxx 10xxxxxx` …), поэтому декодер может пересинхронизироваться, а побайтовый поиск ASCII-разделителей безопасен. Проблемы порядка байтов нет. Стандарт для тел HTTP, JSON (RFC 8259 его требует), строковых сериализаторов Kafka, баз Postgres (кодировка `UTF8`) и, начиная с Java 18 (JEP 400), для `Charset.defaultCharset()`.
- **UTF-16**: 2 байта для BMP, 4 для остального; есть порядок байтов (BE/LE) и необязательный BOM. Используется внутри Java, JavaScript и Windows API; в сети встречается редко.
- **UTF-32**: фиксированные 4 байта на кодовую точку; простая индексация, расточительно; для хранения практически не используется.
- Всегда явно указывай кодировку: `new String(bytes, StandardCharsets.UTF_8)`, `str.getBytes(UTF_8)`, `Files.readString(path, UTF_8)`, `Content-Type: application/json; charset=utf-8`. До Java 18 перегрузки без аргумента использовали локаль ОС, которая различалась на ноутбуке разработчика и в Docker-образе (`POSIX` → ASCII).

### Нормализация и сравнение
- Один и тот же текст может иметь несколько последовательностей кодовых точек: «é» как U+00E9 (составной, NFC) или `e` + U+0301 (разложенный, NFD). `equals` считает их разными; уникальный индекс по `email` или `username` пропустит оба.
- Вызывай `java.text.Normalizer.normalize(s, Normalizer.Form.NFC)` перед сохранением и сравнением. NFKC дополнительно сворачивает совместимые варианты (полноширинные цифры, лигатуры); используй её для идентификаторов и поисковых ключей, но не для отображаемого текста.
- Регистр: `toLowerCase(Locale.ROOT)` для технических сравнений. Турецкая i без точки и немецкая ß (`"ß".toUpperCase()` даёт `"SS"`) показывают, почему локаль и длина могут меняться. Правила сортировки (collation) — настройка базы данных; в Postgres `ORDER BY name COLLATE "und-x-icu"` и `"C"` дают разные результаты и влияют на возможность использовать индекс ([[postgres-indexes]]).
- Безопасность: гомоглифы (кириллическая «а» против латинской «a») и невидимые символы (пробел нулевой ширины, переопределения направления текста bidi) проходят валидацию и появляются в фишинговых именах пользователей; валидируй по явному списку разрешённых символов, а не по «любой букве».

### Где это ломается в бэкенде
- Ограничения длины: `varchar(50)` в Postgres считает символы, а сегмент SMS считает септеты GSM-7 или единицы UCS-2, сообщение Kafka или ключ `S3` — байты. Валидируй в той единице, в которой определён лимит.
- `Content-Length` — это байты закодированного тела, а не `string.length()`.
- URL-кодирование, Base64 и экранирование JSON — преобразования над *байтами* или *кодовыми точками*, а не над char; `URLEncoder.encode(s, UTF_8)` требует кодировку не просто так.
- Кракозябры в логах и событиях Sentry обычно означают, что на каком-то шаге декодировали не той кодировкой; исправляй источник, а не «перекодируй» ниже по цепочке.

## Пример
Как выглядят подсчёты и ловушка нормализации на идентификаторе пользователя.
```java
import java.nio.charset.StandardCharsets;
import java.text.Normalizer;

public class UnicodeDemo {
    public static void main(String[] args) {
        String s = "é😀";            // «é» (разложенная) + эмодзи-смайлик
        System.out.println(s.length());             // 4  кодовые единицы UTF-16
        System.out.println(s.codePointCount(0, s.length())); // 3 кодовые точки
        System.out.println(s.getBytes(StandardCharsets.UTF_8).length);  // 7 байтов
        System.out.println(s.getBytes(StandardCharsets.UTF_16).length); // 10 (BOM + 8)

        String nfc = "é";                      // составная é
        String nfd = "é";                     // e + комбинируемое акутовое ударение
        System.out.println(nfc.equals(nfd));        // false
        System.out.println(Normalizer.normalize(nfc, Normalizer.Form.NFC)
                .equals(Normalizer.normalize(nfd, Normalizer.Form.NFC))); // true

        // Безопасный обход реальных символов
        s.codePoints().forEach(cp ->
                System.out.printf("U+%04X %s%n", cp, Character.getName(cp)));

        // Унаследованный интерфейс: кириллическое название города в Windows-1251, декодированное как UTF-8 -> кракозябры
        byte[] cp1251 = "Бишкек".getBytes(java.nio.charset.Charset.forName("windows-1251"));
        System.out.println(new String(cp1251, StandardCharsets.UTF_8)); // ������
    }
}
```
Для колонки с именем пользователя: `Normalizer.normalize(input, NFC).toLowerCase(Locale.ROOT)` перед валидацией, проверкой уникальности и сохранением.

## Подводные камни
- `new String(bytes)` / `getBytes()` без кодировки в коде, который должен работать на Java 17 и старше: на ноутбуке работает, а в контейнере с `LANG=C` портит текст. Всегда передавай `UTF_8`.
- Обрезать строку под лимит в байтах через `substring(0, n)`: n char могут занимать до 4n байт, а разрез может разделить суррогатную пару. Сначала закодируй, затем режь по границе кодовой точки.
- `.` и `\w` в регулярных выражениях по умолчанию работают с кодовыми единицами; `[a-zA-Z]` отвергает любое неанглийское имя. Используй `\p{L}` и `Pattern.UNICODE_CHARACTER_CLASS`, когда имеются в виду «буквы».
- Хранить базу данных или топик Kafka в кодировке, отличной от UTF-8, «потому что legacy»: каждый потребитель обязан об этом знать, а JSON-библиотеки предполагают UTF-8. Конвертируй один раз в адаптере на границе.
