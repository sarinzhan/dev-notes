## Кратко
Ядро процессора крутит бесконечный цикл **выборка → декодирование → выполнение → запись результата (fetch → decode → execute → write-back)** над машинными инструкциями, используя в качестве рабочего хранилища горстку быстрых **регистров**. Современные ядра **конвейеризуют** множество инструкций сразу, выполняют несколько за такт (суперскалярность), переупорядочивают их (внеочередное выполнение, out-of-order execution) и **угадывают**, куда пойдёт ветвление, ещё до того, как это известно. Итог: число инструкций само по себе значит гораздо меньше, чем предсказуемость кода и то, как далеко лежат его данные ([[cpu-caches-and-cache-lines]]). Для Java-разработчика это объясняет, почему JIT ([[compilation-interpretation-jit]]) так заботится о встраивании (inlining) и почему код с обилием ветвлений или погоней за указателями медленный даже при низкой [[big-o-and-complexity|асимптотике (Big-O)]].

## Основное
### Базовый цикл
- **Выборка (fetch)**: прочитать из памяти (на деле из кэша инструкций) инструкцию по адресу в *счётчике команд* (program counter, PC / `RIP` на x86-64).
- **Декодирование (decode)**: определить код операции и операнды; x86 декодирует инструкции переменной длины в микрооперации фиксированного размера (uops).
- **Выполнение (execute)**: ALU складывает, сравнивает, сдвигает; блок загрузки/сохранения читает или пишет память; блок FPU/SIMD работает с плавающей точкой и векторами.
- **Запись результата (write-back)**: сохранить результат в регистр или память, обновить флаги (ноль, перенос, переполнение), сдвинуть PC.
- Всё, что «видит» программа, — это регистры (16 общего назначения на x86-64, 31 на ARM64), адреса памяти и флаги. Локальные переменные JIT-скомпилированного Java-метода живут в регистрах, когда компилятор может их там удержать; иначе — на стеке ([[stack-vs-heap-memory]]).

### Почему одна инструкция за такт — не предел
| Техника | Идея | Чего стоит неудача |
|---|---|---|
| Конвейеризация (pipelining) | разбить цикл на стадии, каждая стадия работает над своей инструкцией; 14–20 стадий на современных x86 | простой (stall) опустошает конвейер |
| Суперскалярность | несколько исполнительных блоков, 4–8 инструкций запускаются за такт | зависимые инструкции не могут выполняться параллельно |
| Внеочередное выполнение | выполнять более поздние независимые инструкции, пока ранняя ждёт память | сложность железа; всё равно ограничено буфером переупорядочивания (reorder buffer) |
| Предсказание ветвлений (branch prediction) | угадать направление `if`/циклов и выполнять спекулятивно | неверное предсказание выбрасывает 15–20 тактов работы |
| Спекулятивное выполнение | выполнять дальше загрузок и ветвлений до их разрешения | атаки по сторонним каналам (Spectre/Meltdown) и защита от них |
| SIMD (AVX, NEON) | одна инструкция на 4–16 дорожек данных | помогает только линейному числовому коду; JIT автоматически векторизует простые циклы, Vector API в Java всё ещё в инкубаторе |

- **Тактовая частота против IPC**: производительность = частота × инструкции за такт. Примерно с 2005 года частота почти не росла; выигрыш дали IPC, больше ядер и большие кэши. Поэтому [[amdahls-law-and-parallel-speedup|параллелизм]] и поведение кэшей важнее, чем «быстрый CPU».
- **Иерархия задержек**: регистр ~0 тактов, L1 ~4, L2 ~12, L3 ~40, DRAM ~200–300 тактов. Один промах кэша стоит больше сотни простых инструкций ([[latency-numbers]]).

### Предсказание ветвлений на практике
- Предсказатели учатся на истории: условие цикла, которое 999 раз истинно, а потом ложно, почти бесплатно; `if (x % 2 == 0)` на случайных данных ошибается в 50% случаев.
- Сортировка массива перед ветвлением, зависящим от данных, может ускорить цикл в несколько раз исключительно за счёт предсказания. Код без ветвлений (`Math.max`, условные пересылки, битовые трюки из [[bit-manipulation]]) полностью избегает проблемы.
- Виртуальные вызовы — это косвенные переходы: *встроенный кэш (inline cache)* JIT превращает мономорфное место вызова в прямой вызов плюс проверку типа, которая предсказывается идеально; мегаморфные места (много реализаций в одном месте вызова) откатываются к медленному переходу через vtable.

### Вопросы в стиле собеседования
- *Что такое регистр?* Самое быстрое хранилище в машине — несколько десятков именованных ячеек, с которыми ALU работает напрямую; всё остальное сначала нужно в них загрузить.
- *Что такое переключение контекста (context switch) и почему оно дорогое?* Сохранить все регистры и PC одного потока, загрузить регистры другого и потерять содержимое кэшей и TLB; см. [[processes-and-threads]].
- *Почему `i++` не атомарна?* Это загрузка → сложение → сохранение, три инструкции; другое ядро может вклиниться между ними ([[race-conditions-and-critical-sections]], [[lock-free-and-cas]] — про исправление одной инструкцией `CAS`).
- *При чём здесь CPU и «переупорядочивание памяти»?* Внеочередное выполнение и буферы записи (store buffers) позволяют загрузкам и сохранениям становиться видимыми в ином порядке, чем их написала программа; барьеры (fences) и `volatile` восстанавливают порядок ([[memory-models-and-visibility]]).

## Пример
Одна и та же работа, два цикла; второй быстрее на случайных данных, потому что ветвление заменено арифметикой и цикл автоматически векторизуется.
```java
// Подсчитать значения >= 128 в массиве байтов со случайными данными.
static int branchy(byte[] data) {
    int count = 0;
    for (byte b : data) {
        if ((b & 0xFF) >= 128) {   // непредсказуемое ветвление: ~50% ошибок на случайных данных
            count++;
        }
    }
    return count;
}

static int branchless(byte[] data) {
    int count = 0;
    for (byte b : data) {
        count += ((b & 0xFF) >> 7); // бит 7 равен 1 ровно тогда, когда значение >= 128; без ветвления
    }
    return count;
}
```
В JMH-бенчмарке на 1M случайных байтов версия без ветвлений обычно в 3–5 раз быстрее; если сначала отсортировать массив, версия с ветвлением догоняет, потому что предсказатель выучивает единственную точку перехода.

## Подводные камни
- Судить о производительности по числу строк исходника или даже байт-кодов: один промах кэша или одно неверно предсказанное ветвление перевешивают десятки операций ALU. Измеряй через JMH и смотри на счётчики промахов кэша и ветвлений (`perf stat`), прежде чем заниматься микрооптимизацией.
- Считать, что CPU выполняет программу по порядку. Это не так, поэтому несинхронизированный обмен данными между потоками ломается так, как будто это невозможно ([[java-memory-model]]).
- Микробенчмарки, в которых JIT видит константные входные данные: он сворачивает ветвление, и ты не измеряешь ничего. Используй `Blackhole` из JMH и случайные данные.
- Защита от атак класса Spectre (retpolines, сброс при переключении контекста) заметно замедлила системные вызовы и переключения контекста; модель «поток на запрос» платит за это при каждом блокирующем вызове ([[io-models-blocking-nonblocking-epoll]], [[virtual-threads]]).
- Связанные заметки: [[cpu-caches-and-cache-lines]] — про память, [[jvm-memory-areas]] — как JVM ложится на это железо.
