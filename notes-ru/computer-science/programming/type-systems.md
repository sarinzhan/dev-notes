## Кратко
Система типов присваивает значениям типы и отвергает программы, которые неправильно их сочетают. **Статическая** типизация проверяет на этапе компиляции (Java, Go, Rust, TypeScript); **динамическая** — во время выполнения (Python, JavaScript, Clojure). **Сильная** и **слабая** — о том, насколько свободно значения преобразуются: Java и Python сильные (никаких тихих сюрпризов в духе `"1" + 1 → "11"`, кроме конкатенации строк), JavaScript и C слабые. Дженерики добавляют параметрический полиморфизм (`List<T>`), а **вариантность** (variance) говорит, можно ли использовать `List<Dog>` как `List<Animal>` (нельзя, поэтому в Java есть `? extends` и `? super`). Особенности Java (стирание, wildcard, PECS) описаны в [[generics]]; эта заметка — общая картина.

## Основное

### Две оси
| | Статическая | Динамическая |
|---|---|---|
| **Сильная** | Java, Kotlin, Go, Rust, Scala, Haskell | Python, Ruby, Clojure, Erlang |
| **Слабая** | C, C++ (неявные приведения, переинтерпретация указателей) | JavaScript, PHP, Perl |

- Статическая: ошибки находятся до запуска; навигация, рефакторинг и автодополнение в IDE; типы как документация; более быстрый код, потому что компилятор знает раскладку данных. Цена: церемонии, более медленное прототипирование, часть корректных программ отвергается.
- Динамическая: кратко, гибко, утиная типизация; ошибки находят тесты или прод. Постепенная типизация (TypeScript, подсказки типов в Python + mypy) возвращает статические проверки поверх.
- Сильная/слабая — это спектр, а не переключатель: Java разрешает расширение `int → long` и `String + что угодно`, но не `int + String → int`.

### Виды типизации, о которых спросят
| Термин | Смысл | Java |
|---|---|---|
| Номинальная | совместимость по объявленному имени/иерархии | да: `implements Comparable` |
| Структурная | совместимость по форме | нет (в TypeScript и интерфейсах Go — структурная) |
| Утиная (duck typing) | «если крякает»: структурная, во время выполнения | нет; только рефлексия или `instanceof` |
| Вывод типов | компилятор выводит типы | `var` (10), параметры лямбд, ромб `<>`, аргументы generic-методов |
| Параметрический полиморфизм | один код для многих типов | дженерики ([[generics]]) |
| Ad-hoc полиморфизм | перегрузка, классы типов | перегрузка ([[methods-overloading-overriding]]); классов типов нет |
| Полиморфизм подтипов | подтип может заменить супертип | наследование, интерфейсы ([[oop-principles]]) |
| Алгебраические типы данных | типы-суммы (одно из) и типы-произведения (всё сразу) | sealed-интерфейсы (17) + records (16) |
| Null-безопасность | тип говорит, допустим ли null | в Java нет (`Optional`, аннотации `@Nullable`, JSpecify); в Kotlin `String?` |

### Вариантность
Если `Dog <: Animal`, как `F<Dog>` соотносится с `F<Animal>`?
| Вариантность | Отношение | Безопасно для | Синтаксис Java |
|---|---|---|---|
| Инвариантность | нет отношения | чтения и записи | `List<Animal>` (по умолчанию) |
| Ковариантность | `F<Dog> <: F<Animal>` | чтения (производитель) | `List<? extends Animal>`, массивы (некорректно) |
| Контравариантность | `F<Animal> <: F<Dog>` | записи (потребитель) | `List<? super Dog>`, `Comparator<? super T>` |

- Изменяемые контейнеры должны быть инвариантными: если бы `List<Dog>` был `List<Animal>`, в него можно было бы сделать `add(new Cat())`. Массивы в Java ковариантны и расплачиваются `ArrayStoreException` во время выполнения — известная ошибка проектирования.
- PECS: producer `extends`, consumer `super`; `Collections.copy(List<? super T> dest, List<? extends T> src)` — каноническая сигнатура.
- Kotlin и C# задают вариантность в объявлении (`out T`, `in T`); Java — в месте использования через wildcard.

### Реализация дженериков: стирание против реификации
- Java стирает аргументы типов при компиляции: `List<String>` и `List<Integer>` во время выполнения — один и тот же класс, нет `new T[]`, нет `instanceof List<String>`, примитивам нужна упаковка. Выбрано ради обратной совместимости в Java 5. Project Valhalla стремится специализировать дженерики для value-типов ([[generics]], [[primitives-and-wrappers]]).
- C# и Kotlin/Native реифицируют; шаблоны C++ генерируют код для каждой инстанциации (мономорфизация), как и Rust; дженерики Go (1.18) используют словарь + частичную мономорфизацию.

### Типы как инструмент проектирования в бэкенде
- Сделай недопустимые состояния непредставимыми: `Money` вместо `BigDecimal` + `String currency`, `Iccid` вместо `String`; валидация при создании ([[value-objects-and-entities]]).
- Sealed-типы результатов вместо исключений для ожидаемых отказов ([[error-handling-strategies]]).
- Исчерпывающий `switch` по sealed-типам означает, что добавление нового типа события ломает компиляцию везде, где оно не обработано, — противоположность ветке `else`, которая тихо его проглатывает.
- Границы сериализации — это место, где статические типы заканчиваются: JSON в `Map<String, Object>` — это динамическая типизация под другим именем; предпочитай типизированные DTO и правила эволюции схем ([[message-schema-evolution]]).

- На собеседовании: «почему `var` не делает Java динамической?» Тип всё равно фиксирован на этапе компиляции, просто выведен.

## Пример
Вариантность на практике: обобщённый помощник для репозитория, который принимает любого производителя подтипа и любого потребителя супертипа, плюс sealed-результат, который компилятор заставляет вызывающих обработать.

```java
public final class Batching {
    /** PECS: читать из производителя T (или подтипов), писать в потребителя T (или супертипов). */
    public static <T> int drain(Collection<? extends T> source, Collection<? super T> target, int max) {
        int moved = 0;
        for (Iterator<? extends T> it = source.iterator(); it.hasNext() && moved < max; moved++) {
            target.add(it.next());
            it.remove();
        }
        return moved;
    }
}

sealed interface Parsed<T> permits Parsed.Ok, Parsed.Invalid {
    record Ok<T>(T value) implements Parsed<T> {}
    record Invalid<T>(String field, String reason) implements Parsed<T> {}
}

static Parsed<Iccid> parseIccid(String raw) {
    if (raw == null || !raw.matches("\\d{19,20}")) return new Parsed.Invalid<>("iccid", "19–20 digits expected");
    return new Parsed.Ok<>(new Iccid(raw));
}

// вызывающий обязан обработать оба случая; добавление третьего разрешённого типа ломает этот switch при компиляции
String describe(Parsed<Iccid> p) {
    return switch (p) {
        case Parsed.Ok<Iccid> ok -> "valid " + ok.value();
        case Parsed.Invalid<Iccid> inv -> inv.field() + ": " + inv.reason();
    };
}

// использование drain с вариантностью
List<SimEvent> events = ...;            // SimEvent extends DomainEvent
List<DomainEvent> outbox = new ArrayList<>();
Batching.drain(events, outbox, 100);    // Collection<? extends DomainEvent>, Collection<? super SimEvent>
```

## Подводные камни
- Возвращать `List<? extends T>` из публичного API: вызывающие не могут ничего в него добавить и получают запутанные ошибки; wildcard уместны в параметрах, а не в возвращаемых типах.
- Сырые типы (`List list`) тихо отключают проверки и порождают `ClassCastException` далеко от причины; считай предупреждения `rawtypes` ошибками.
- Считать полезные нагрузки `Object`/`Map<String, Object>` «гибкими»: каждый потребитель разбирает их заново, а ошибки типов всплывают в проде ([[message-schema-evolution]]).
- Полагаться на ковариантность массивов (`Object[] arr = new String[1]; arr[0] = 1;`): компилируется и падает во время выполнения.
- Связанные заметки: [[generics]] — wildcard и стирание в Java, [[programming-paradigms]] — откуда взялись АТД, [[value-objects-and-entities]] — доменные типы.
