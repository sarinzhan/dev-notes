## Кратко
Парадигма — это способ структурировать программы: **императивный** код говорит, как (инструкции, меняющие состояние), **декларативный** — что (SQL, конфигурация Spring, манифесты Kubernetes), **объектно-ориентированный** группирует состояние с операциями над ним за интерфейсами, а **функциональный** строит результаты из чистых функций и неизменяемых значений. Современные языки мультипарадигменные: идиоматичная Java начиная с 8 — это ООП для структуры, функциональный стиль для преобразования данных (стримы, лямбды, records, sealed-типы и pattern matching) и декларативный там, где работу делает фреймворк (аннотации, SQL, YAML).

## Основное

### Карта
| Парадигма | Единица композиции | Состояние | Поток управления | Типичные языки / места |
|---|---|---|---|---|
| Императивная / процедурная | процедура | изменяемое, общее | циклы, условия, явная последовательность | C, Go, скрипты, тело большинства методов Java |
| Объектно-ориентированная | объект (состояние + поведение) | инкапсулированное, изменяемое или неизменяемое | передача сообщений / вызовы методов, полиморфизм | Java, C#, Kotlin; доменные модели, Spring-бины |
| Функциональная | чистая функция | неизменяемые значения | выражения, рекурсия, функции высшего порядка | Haskell, Clojure, Scala; стримы Java, коллекции Kotlin |
| Декларативная | правило / запрос / спецификация | не видно | решает движок | SQL, regex, Prolog, HTML, query-методы Spring Data, манифесты K8s |
| Логическая | предикат + факты | — | унификация, поиск | Prolog, Datalog, некоторые движки правил |
| Событийная / реактивная | обработчик, поток | у каждого обработчика | колбэки, конвейеры, обратное давление | Node.js, Project Reactor, consumer'ы Kafka ([[event-driven-architecture]]) |
| Модели конкурентности (акторы, CSP) | актор / горутина | изолировано в каждом акторе | сообщения, каналы | Erlang/Akka, Go ([[actor-and-message-passing-models]]) |

### Императивная против декларативной
- Императивно: `for (Order o : orders) if (o.status() == PAID) total += o.amount();`.
- Декларативно: `SELECT sum(amount) FROM orders WHERE status = 'PAID'` или `orders.stream().filter(...).mapToLong(...).sum()`. Способ выполнения выбирает планировщик или конвейер стрима ([[query-planning-and-execution]]).
- Декларативный подход выигрывает, когда движок умеет оптимизировать (SQL, reconciliation в Kubernetes) или когда способ выполнения один и очевиден; императивный — когда нужен контроль над порядком, памятью и побочными эффектами.

### Объектно-ориентированная
- Столпы: инкапсуляция, наследование, полиморфизм, абстракция; описаны в [[oop-principles]], а правила проектирования — в [[solid]].
- Предпочитай композицию наследованию; моделируй поведение за интерфейсами, чтобы реализации (Kafka или in-memory, Postgres или тестовый двойник) можно было заменять ([[hexagonal-architecture]]).
- Где ООП хорошо: долгоживущее доменное состояние с инвариантами ([[aggregates-and-invariants]]), точки расширения, фреймворки. Где мешает: глубокие иерархии, анемичные модели, которые представляют собой просто структуры плюс сервис, полный процедур.

### Функциональная
- **Чистая функция**: выход зависит только от входов, побочных эффектов нет; тривиально тестируется, кэшируется, распараллеливается ([[immutability-and-side-effects]]).
- **Функции высшего порядка** принимают или возвращают функции: `map`, `filter`, `reduce`, `Comparator.comparing`.
- **Неизменяемость** и **ссылочная прозрачность** упрощают рассуждения о конкурентности.
- **Алгебраические типы данных** (типы-суммы и типы-произведения): sealed-интерфейсы Java 17 + records + pattern matching в `switch` дают исчерпывающую обработку закрытого набора случаев — так в ФП моделируют события и результаты ([[error-handling-strategies]], [[type-systems]]).
- В Java: лямбды и ссылки на методы (Java 8), `Stream`, `Optional`, `CompletableFuture` как конвейер, похожий на монаду, records (16), sealed-типы (17), pattern matching для `switch` (21). См. [[functional-interfaces]], [[stream-api]].
- Ограничения в Java: нет оптимизации хвостовых вызовов (глубокая рекурсия переполняет стек, [[recursion-and-backtracking]]), проверяемые исключения не компонуются с лямбдами, в JDK нет персистентных коллекций.

### Где находится Java
- В основе — ООП на классах со статической типизацией; всё находится в классе, но `static` утилитные классы и records на практике процедурны и ориентированы на данные.
- Функциональный стиль для преобразования данных и колбэков; императивные циклы всё ещё предпочтительны на горячих путях и там, где цикл читается яснее длинной цепочки стрима.
- Декларативность через аннотации и фреймворки: `@Transactional`, `@Cacheable`, вывод запросов Spring Data, Bean Validation; фреймворк превращает декларацию в императивный код через прокси ([[spring-aop]]).
- «Программирование, ориентированное на данные» (data-oriented programming; Брайан Гётц, эпоха Java 21): моделировать данные как неизменяемые records и sealed-иерархии, а поведение держать в функциях, которые делают switch по ним; середина между ООП и ФП, которая хорошо подходит для сервисов.

### Ракурсы на собеседовании
- «ООП или ФП?» Это не соревнование: ООП организует состояние и точки расширения, ФП организует преобразования; Spring-сервис использует и то и другое.
- «SQL — язык программирования?» Декларативный, Тьюринг-полный с рекурсивными CTE, выполняется планировщиком.
- «Зачем неизменяемость?» Потокобезопасность и локальные рассуждения ([[immutability-and-side-effects]]).

## Пример
Одно и то же бизнес-правило в трёх стилях; в реальном сервисе стоит оставить вариант с sealed-типами.

```java
// 1. Императивно: как, шаг за шагом, изменяемый аккумулятор
static long paidTotal(List<Order> orders) {
    long total = 0;
    for (Order o : orders) {
        if (o.status() == Status.PAID) total += o.amountMinor();
    }
    return total;
}

// 2. Функционально: что, как конвейер чистых шагов
static long paidTotalFp(List<Order> orders) {
    return orders.stream()
            .filter(o -> o.status() == Status.PAID)
            .mapToLong(Order::amountMinor)
            .sum();
}

// 3. Ориентированно на данные: закрытый набор случаев, исчерпывающий switch (Java 21)
sealed interface PaymentEvent permits Authorized, Captured, Refunded {}
record Authorized(String id, long amountMinor) implements PaymentEvent {}
record Captured(String id, long amountMinor) implements PaymentEvent {}
record Refunded(String id, long amountMinor, String reason) implements PaymentEvent {}

static long ledgerDelta(PaymentEvent e) {
    return switch (e) {                       // компилятор требует все случаи
        case Authorized a -> 0;
        case Captured c   -> c.amountMinor();
        case Refunded r   -> -r.amountMinor();
    };
}
```

## Подводные камни
- «Функциональная» Java, которая меняет захваченное состояние внутри `forEach` или `map`, сочетает худшее от обоих стилей: скрытые побочные эффекты и отсутствие исчерпываемости; держи лямбды чистыми.
- Наследование ради переиспользования кода (`BaseService` с 20 protected-помощниками) вместо композиции; иерархия становится точкой связанности ([[coupling-cohesion-and-general-principles]]).
- Чрезмерная декларативная магия: имя метода Spring Data с шестью `And` или стек аннотаций на 200 строк отлаживать труднее, чем SQL, который они скрывают.
- Проверяемые исключения внутри лямбд стрима вынуждают писать обёртки; проектируй API на границе с непроверяемыми исключениями или типами-результатами ([[error-handling-strategies]]).
- Связанные заметки: [[oop-principles]] и [[solid]] — сторона ООП, [[stream-api]] и [[functional-interfaces]] — функциональный инструментарий, [[type-systems]] — как вписываются sealed-типы и дженерики.
