## Кратко
Вероятностные структуры данных жертвуют точностью ради огромной экономии памяти. **Фильтр Блума (Bloom filter)** отвечает на вопрос «видел ли я этот ключ?» без ложноотрицательных ответов и с настраиваемой долей ложноположительных, используя несколько бит на элемент. **HyperLogLog** считает число различных элементов (мощность, cardinality) с точностью ~1%, используя 12 КБ независимо от n. **Count-min sketch** оценивает, как часто встречался ключ, никогда не занижая счёт. Они появляются везде, где точные множества или счётчики не помещаются: в движках хранения баз данных, кэшах, Redis, Kafka, аналитике и конвейерах дедупликации.

## Основное

### Фильтр Блума
- Битовый массив из m бит и k хеш-функций. **Добавление**: установить биты `h1(x) … hk(x)`. **Запрос**: если все k битов установлены — «вероятно, есть»; если какой-то бит сброшен — «точно нет».
- Ложноположительные ответы возникают из-за того, что другие ключи установили те же биты. Удаления нет (сброс бита может стереть след другого ключа); **считающий фильтр Блума (counting Bloom filter)** использует вместо битов маленькие счётчики, чтобы разрешить удаление; **фильтр с кукушкой (cuckoo filter)** поддерживает удаление и экономнее по памяти при низкой доле ошибок.
- Расчёт размера: для n элементов и целевой доли ложноположительных p — `m ≈ −n·ln p / (ln 2)²` бит и `k ≈ (m/n)·ln 2`. Пример: 10M ключей при 1% требуют ~12 МБ и 7 хешей; `HashSet<String>` с теми же ключами потребовал бы сотни МБ.
- Хеширование: используй один хороший 64-битный хеш (Murmur3, xxHash) и получай k хешей как `h1 + i·h2` (Кирш–Митценмахер), а не k независимых функций.

| Операция | Сложность | Примечание |
|---|---|---|
| add / query | O(k) | k мало (5–10), не зависит от n |
| память | ~1.44·log₂(1/p) бит на элемент | 1% → ~9.6 бит на элемент |
| объединение двух фильтров | OR битовых массивов | одинаковые m и хеши |
| удаление | не поддерживается | считающий вариант / cuckoo |

### Где используются фильтры Блума
- **LSM-движки хранения** (RocksDB, Cassandra, HBase, хранилища состояния Kafka Streams): по фильтру на SSTable, чтобы точечный поиск пропускал файлы, которые не могут содержать ключ ([[column-and-wide-column-stores]]).
- **Postgres**: класс операторов bloom для BRIN и индекс расширения `bloom` для предикатов равенства по многим колонкам ([[postgres-indexes]]).
- **Кэши и CDN**: «чудеса одного обращения» (one-hit wonders) не кэшируются, пока фильтр не скажет, что URL уже встречался ([[caching]], [[cdn]]).
- **Дедупликация на входе**: был ли этот id события / id уведомления уже обработан? Фильтр перед точным хранилищем (Redis/БД) превращает большинство ответов «нет» в ноль сетевых обращений ([[idempotency]], [[design-notification-service]]).
- **Распределённые join-ы**: отправлять на другую сторону фильтр ключей соединения вместо полного набора ключей; а также проверка орфографии и списки вредоносных URL в браузерах.

- **«Занято ли это имя пользователя?»** перед таблицей пользователей: отрицательный ответ фильтра экономит поход в базу; положительный (возможно) идёт в базу для подтверждения. Удаления — проблема: классический фильтр не умеет удалять элемент, поэтому устаревшие «возможно» копятся, пока фильтр не перестроят (удаление поддерживают считающие фильтры Блума и cuckoo-фильтры).

### HyperLogLog (мощность множества)
- Хешируем каждый элемент; число ведущих нулей в хеше — подсказка о том, сколько различных значений встретилось (хеш с 20 ведущими нулями намекает на ~2²⁰ различных элементов). Храним максимум в каждом из 2^p регистров и объединяем через гармоническое среднее.
- Стандартная ошибка ≈ 1.04/√(2^p): p = 14 даёт 16384 регистра, ошибку ~0.8%, 12 КБ. Считает миллиарды.
- Объединяемы (максимум по каждому регистру), поэтому дневные скетчи складываются в месячные без пересчёта.
- Redis `PFADD`/`PFCOUNT`/`PFMERGE` ([[redis-data-structures]]); расширение `hll` в Postgres; `uniq` в ClickHouse; агрегация `cardinality` в Elasticsearch; уникальные посетители, уникальные MSISDN на соту, уникальные IP в минуту.

### Count-min sketch (частота)
- Матрица счётчиков d×w и d хеш-функций. Добавление: увеличить `row[i][hi(x)]` в каждой строке. Запрос: минимум по строкам. Коллизии только завышают счёт, поэтому оценка ≥ истинного значения; ошибка ≤ ε·N с вероятностью 1−δ при w = e/ε, d = ln(1/δ).
- Применения: «тяжёлые» ключи / top-k самых активных, ограничение частоты по ключу с ограниченной памятью ([[rate-limiting]]), обнаружение горячих ключей в кэшах, трендовые элементы.

### Сравнение
| Структура | Вопрос | Тип ошибки | Память | Удаление | Объединение |
|---|---|---|---|---|---|
| Фильтр Блума | принадлежность | только ложноположительные | ~10 бит/элем. при 1% | нет (считающий/cuckoo: да) | OR |
| Фильтр с кукушкой | принадлежность | только ложноположительные | ~7–8 бит/элем. при 1% | да | нет простого объединения |
| HyperLogLog | число различных | ±~1% | фиксированные 12 КБ | нет | максимум по регистру |
| Count-min sketch | частота ключа | только завышение | КБ–МБ, фиксированно | нет (с оговорками) | сложение матриц |
| t-digest / DDSketch | квантили (задержка p99) | относительная ошибка по рангу/значению | КБ | нет | да |

Квантильные скетчи — это то, для чего созданы гистограммы Prometheus и экспоненциальные гистограммы OTel ([[otel-metric-types]]).

## Пример
Фильтр Блума поверх битового набора `long[]` с двойным хешированием плюс формула расчёта размера; такое ставят перед таблицей идемпотентности, чтобы не ходить в БД для впервые увиденных id.

```java
public final class BloomFilter {
    private final long[] bits;
    private final int numBits;
    private final int numHashes;

    public BloomFilter(long expectedInsertions, double falsePositiveRate) {
        double m = -expectedInsertions * Math.log(falsePositiveRate) / (Math.log(2) * Math.log(2));
        this.numBits = (int) Math.max(64, Math.ceil(m));
        this.numHashes = Math.max(1, (int) Math.round(numBits / (double) expectedInsertions * Math.log(2)));
        this.bits = new long[(numBits + 63) / 64];
    }

    public void add(String key) {
        long h = hash64(key);
        int h1 = (int) h, h2 = (int) (h >>> 32);
        for (int i = 0; i < numHashes; i++) {
            int idx = Math.floorMod(h1 + i * h2, numBits);          // Кирш–Митценмахер
            bits[idx >>> 6] |= 1L << (idx & 63);
        }
    }

    /** false = точно никогда не добавлялся; true = вероятно, добавлялся. */
    public boolean mightContain(String key) {
        long h = hash64(key);
        int h1 = (int) h, h2 = (int) (h >>> 32);
        for (int i = 0; i < numHashes; i++) {
            int idx = Math.floorMod(h1 + i * h2, numBits);
            if ((bits[idx >>> 6] & (1L << (idx & 63))) == 0) return false;
        }
        return true;
    }

    private static long hash64(String s) {                       // FNV-1a; в production используй Murmur3
        long h = 0xcbf29ce484222325L;
        for (byte b : s.getBytes(StandardCharsets.UTF_8)) { h ^= b; h *= 0x100000001b3L; }
        return h ^ (h >>> 29);
    }
}

// использование: не ходить в БД для id, которые точно никогда не обрабатывались
if (!seen.mightContain(eventId) || !repo.existsById(eventId)) { process(event); seen.add(eventId); }
```

## Подводные камни
- Использовать фильтр Блума там, где ложноположительный ответ недопустим (решить, что сообщение — дубликат, и выбросить его). Используй его только для быстрого отсечения отрицательного случая; положительные ответы подтверждай по точному хранилищу.
- Переполнение: фильтр, рассчитанный на 1M ключей и хранящий 5M, даёт долю ложноположительных около 100%. Либо отслеживай количество и перестраивай, либо используй масштабируемый фильтр Блума (цепочку растущих фильтров).
- Слабые или коррелированные хеш-функции (`String.hashCode` плюс сдвиг) скучивают биты и завышают ошибку; используй Murmur3/xxHash с двумя независимыми seed-ами.
- Сохранять фильтр между перезапусками без версионирования хеш-функции или `m`: изменённый параметр делает каждый старый бит бессмысленным.
- Связанные заметки: [[hash-tables]] — точная структура, которую они аппроксимируют, [[redis-data-structures]] — готовые модули HyperLogLog и Bloom, [[caching]] и [[rate-limiting]] — системы, которым они нужны.
