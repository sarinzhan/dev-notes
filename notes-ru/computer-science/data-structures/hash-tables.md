## Кратко
Хеш-таблица отображает ключ на ячейку массива по формуле `index = hash(key) mod capacity`, что даёт `get`/`put`/`remove` за O(1) в среднем. Два ключа могут попасть в одну ячейку (коллизия); таблица либо складывает их в список в каждой корзине (bucket) (метод цепочек, `HashMap` в Java), либо ищет свободную соседнюю ячейку (открытая адресация: словари CPython, `HashMap` в Rust, map в Go). **Коэффициент заполнения (load factor)** (записей / ёмкость) управляет частотой коллизий; когда он превышает порог, таблица удваивается и всё перехешируется. Структура описана в этой заметке; детали, специфичные для JDK (корзины-деревья, `hash ^ (hash >>> 16)`, разделение при расширении), — в [[hashmap-internals]].

## Основное

### Как работает поиск
1. Вычислить `h = hash(key)` (в Java — `hashCode()`, см. [[equals-and-hashcode]]).
2. Свести к ячейке: `h & (capacity - 1)`, когда ёмкость — степень двойки (то же, что `mod`, но одной инструкцией).
3. Сравнивать ключи в этой ячейке через `equals` до совпадения или до конца цепочки/последовательности проб.

Хеш-функция должна быть быстрой, детерминированной и равномерно распределять ключи по битам; плохая функция (все ключи в одну корзину) деградирует таблицу до O(n).

### Разрешение коллизий
| Стратегия | Размещение | Удаление | Поведение кэша | Где используется |
|---|---|---|---|---|
| **Метод цепочек (separate chaining)** | каждая корзина — связный список (или дерево) записей | отцепить узел | один переход по указателю на пробу; записи — отдельные объекты | `HashMap`, `ConcurrentHashMap` в Java |
| **Открытая адресация, линейное пробирование (linear probing)** | записи живут в массиве; при коллизии пробуется `i+1, i+2, ...` | нужны надгробия (tombstones) или обратный сдвиг | отличное (последовательно), страдает от первичной кластеризации | Go, Rust (Swiss tables), dict в Python |
| **Квадратичное / двойное хеширование** | шаг пробы растёт или зависит от второго хеша | надгробия | меньше кластеров, больше промахов кэша | некоторые библиотеки C++ |
| **Хеширование Робин Гуда (Robin Hood hashing)** | линейное пробирование, где «богатые» записи уступают «бедным» | обратный сдвиг | низкий разброс длины проб | Rust до 2018 года, многие кэши |
| **Хеширование с кукушкой (cuckoo hashing)** | две таблицы/два хеша, вытеснение и перемещение | просто | поиск O(1) в худшем случае, дорогие вставки | аппаратные таблицы, некоторые KV-хранилища |

Метод цепочек переносит коэффициент заполнения выше 1 и сохраняет простоту вставок; открытая адресация плотнее упаковывает данные в кэш-линии, но должна оставаться ниже заполнения ~0.7–0.9.

### Коэффициент заполнения и расширение
- В Java по умолчанию: ёмкость 16, коэффициент заполнения 0.75, расширение при 13 записях, ёмкость удваивается. Каждое расширение — O(n), но амортизированно O(1) на вставку, как у динамического массива ([[arrays-and-dynamic-arrays]]).
- Ожидаемая длина цепочки при методе цепочек равна самому коэффициенту заполнения; при линейном пробировании ожидаемое число проб растёт как `1/(1-α)²` и взрывается вблизи α = 1.
- Задавай размер таблицы заранее, когда n известно: `HashMap.newHashMap(n)` (Java 19) или `new HashMap<>((int)(n / 0.75) + 1)` избегают повторного перехеширования.

### Сложность
| Операция | В среднем | В худшем случае | Примечание |
|---|---|---|---|
| `get` / `put` / `remove` | O(1) | O(n) (все ключи сталкиваются) | Java ограничивает худший случай до O(log n), превращая длинные цепочки в деревья |
| Обход | O(capacity + n) | — | обход огромной, почти пустой таблицы медленный; порядок не имеет смысла |
| Расширение | O(n) | O(n) | амортизируется по вставкам |

### Хеш-множества, упорядоченные варианты и родственники
- Хеш-**множество** — это хеш-таблица только с ключами (`HashSet` оборачивает `HashMap`).
- **Порядок вставки/доступа** требует дополнительного двусвязного списка, протянутого через записи (`LinkedHashMap`); на этом же основан LRU-кэш ([[lru-cache-design]], [[linked-lists]]).
- Отсортированные ключи — это другая структура: сбалансированное дерево, O(log n), `TreeMap` ([[trees-and-bst]]).
- Конкурентные таблицы шардируют блокировки по корзинам или используют CAS на головах корзин ([[concurrent-collections]]).
- Распределённые хеш-таблицы и партиционирование по хешу ключа — та же идея в масштабе нескольких машин ([[consistent-hashing]], [[sharding-strategies]]).

### Безопасность: хеш-флуд (hash flooding)
- Атакующий, знающий хеш-функцию, может создать тысячи сталкивающихся ключей (имена HTTP-параметров, ключи JSON) и превратить O(1) в O(n) на каждый запрос — это DoS по CPU. Корзины-деревья в Java, рандомизированные seed-ы в Python/Ruby/Go и SipHash в Rust существуют именно поэтому ([[owasp-top-10-for-backend]]).

## Пример
Компактная хеш-map с методом цепочек, ёмкостью-степенью двойки и расширением при заполнении 0.75 — та структура, которую ожидает любой вопрос на собеседовании «реализуйте HashMap».

```java
public final class ChainingMap<K, V> {
    private static final class Entry<K, V> {
        final K key; V value; final int hash; Entry<K, V> next;
        Entry(K key, V value, int hash, Entry<K, V> next) {
            this.key = key; this.value = value; this.hash = hash; this.next = next;
        }
    }

    private Entry<K, V>[] buckets = newTable(16);
    private int size;

    @SuppressWarnings("unchecked")
    private static <K, V> Entry<K, V>[] newTable(int n) { return (Entry<K, V>[]) new Entry[n]; }

    private static int spread(Object key) {            // подмешать старшие биты в младшие
        int h = key.hashCode();
        return h ^ (h >>> 16);
    }

    public V get(K key) {
        int h = spread(key);
        for (Entry<K, V> e = buckets[h & (buckets.length - 1)]; e != null; e = e.next) {
            if (e.hash == h && e.key.equals(key)) return e.value;
        }
        return null;
    }

    public V put(K key, V value) {
        int h = spread(key), i = h & (buckets.length - 1);
        for (Entry<K, V> e = buckets[i]; e != null; e = e.next) {
            if (e.hash == h && e.key.equals(key)) { V old = e.value; e.value = value; return old; }
        }
        buckets[i] = new Entry<>(key, value, h, buckets[i]);   // добавить в начало цепочки
        if (++size > buckets.length * 3 / 4) resize();
        return null;
    }

    private void resize() {                            // O(n): перехешировать каждую запись
        Entry<K, V>[] old = buckets;
        buckets = newTable(old.length * 2);
        for (Entry<K, V> head : old) {
            for (Entry<K, V> e = head; e != null; ) {
                Entry<K, V> next = e.next;
                int i = e.hash & (buckets.length - 1);
                e.next = buckets[i]; buckets[i] = e;
                e = next;
            }
        }
    }

    public int size() { return size; }
}
```

## Подводные камни
- Изменяемый ключ: изменение поля, используемого в `hashCode`, после вставки делает запись недостижимой (она лежит не в той корзине). Используй неизменяемые ключи ([[immutable-objects]]).
- Переопределить `equals` без `hashCode`: равные ключи попадают в разные корзины, и в map появляются «дубликаты».
- Полагаться на порядок обхода хеш-map: он меняется при расширении и между версиями JDK. Используй `LinkedHashMap` или сортируй явно.
- Хеширование значений с плавающей точкой или `BigDecimal` с разным масштабом (`1.0` против `1.00`) даёт разные хеши для «равных» сумм ([[numbers-bits-and-floating-point]]).
