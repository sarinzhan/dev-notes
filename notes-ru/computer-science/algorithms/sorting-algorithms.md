## Кратко
Сортировка сравнениями не может быть быстрее O(n log n) в худшем случае; сортировка слиянием, пирамидальная сортировка и быстрая сортировка с хорошим выбором опорного элемента достигают этой границы. Java использует **быструю сортировку с двумя опорными элементами** (dual-pivot quicksort) для массивов примитивов и **TimSort** (стабильный гибрид слияния и вставок) для объектов, `List.sort` и стримов. Сортировка подсчётом и поразрядная сортировка преодолевают барьер n log n для целых чисел с ограниченным диапазоном. На собеседованиях нужно знать про **стабильность**, сортировку на месте vs с дополнительной памятью и про то, когда полная сортировка вообще не нужна (top-k через кучу, частичный порядок через quickselect).

## Основное

### Сортировки сравнениями
| Алгоритм | Лучший | Средний | Худший | Доп. память | Стабильная | Примечания |
|---|---|---|---|---|---|---|
| Вставками | O(n) | O(n²) | O(n²) | O(1) | да | самая быстрая для n < ~32 или почти отсортированных данных; TimSort использует её для серий |
| Выбором | O(n²) | O(n²) | O(n²) | O(1) | нет | минимум обменов, в остальном бесполезна |
| Пузырьком | O(n) | O(n²) | O(n²) | O(1) | да | только для вопросов-викторин на собеседовании |
| Слиянием | O(n log n) | O(n log n) | O(n log n) | O(n) | да | предсказуемая, распараллеливается, внешняя сортировка данных на диске |
| Быстрая | O(n log n) | O(n log n) | O(n²) | O(log n) стек | нет | дружелюбна к кешу, лучшие постоянные множители; случайный/медианный опорный элемент избегает худшего случая |
| Пирамидальная | O(n log n) | O(n log n) | O(n log n) | O(1) | нет | гарантированная граница, плохая локальность ([[heaps-and-priority-queues]]) |
| TimSort | O(n) | O(n log n) | O(n log n) | O(n) | да | находит уже упорядоченные серии и сливает их; по умолчанию для объектов в Java/Python |

- **Стабильность**: равные элементы сохраняют исходный порядок. Нужна при сортировке по вторичному ключу после первичного (отсортировать заказы по дате, затем стабильно отсортировать по клиенту, и заказы каждого клиента останутся упорядоченными по дате). `Comparator.thenComparing` избавляет от трюка с двумя проходами, но именно стабильная сортировка заставляет `sort by status` сохранять существующий порядок внутри каждого статуса.
- **Почему n log n — нижняя граница**: сортировка сравнениями должна различить n! упорядочений; каждое сравнение делит кандидатов пополам, поэтому нужно log₂(n!) ≈ n log n сравнений ([[big-o-and-complexity]]).

### Сортировки без сравнений
- **Сортировка подсчётом** (counting sort): O(n + k) для целых чисел в диапазоне k. Подсчитать вхождения, взять префиксные суммы счётчиков, расставить элементы. Стабильная. Отлично подходит для сортировки статусов, байтов, маленьких id.
- **Поразрядная сортировка** (radix sort): сортировка подсчётом по каждому разряду, начиная с младшего, O(d · (n + k)). Используется для ключей фиксированной ширины (32-битные int, ICCID как строки цифр).
- **Блочная сортировка** (bucket sort): распределить по блокам, отсортировать каждый; O(n) в среднем для равномерно распределённых данных.

### Что делает Java
- `Arrays.sort(int[])`: быстрая сортировка с двумя опорными элементами (Java 7+), с сортировкой вставками для крошечных диапазонов и запасной пирамидальной сортировкой (Java 14+), так что худший случай — O(n log n). Не стабильна, но у примитивов нет идентичности, так что это не важно.
- `Arrays.sort(Object[])`, `List.sort`, `Collections.sort`, `Stream.sorted`: TimSort, стабильная, O(n) дополнительной памяти. Бросает `IllegalArgumentException: Comparison method violates its general contract!`, если компаратор несогласован (например, вычитание int с переполнением или нетранзитивный компаратор).
- `Arrays.parallelSort`: параллельная сортировка слиянием через [[fork-join-framework]]; окупается примерно с 10⁵ элементов.
- `TreeMap`/`TreeSet` держат данные отсортированными при вставке за O(log n) каждая: построение — O(n log n), как одна сортировка, но каждая последующая вставка остаётся дешёвой ([[trees-and-bst]]).

### Когда не нужно сортировать всё
- Top-k из n: min-куча размера k — O(n log k) ([[heaps-and-priority-queues]]).
- k-й наименьший: quickselect, O(n) в среднем.
- Слияние уже отсортированных входов: k-путевое слияние с кучей, O(n log k).
- Сортировка в базе данных: `ORDER BY` по индексированной колонке — бесплатный проход по индексу; без индекса это сортировка в памяти или на диске, видимая в `EXPLAIN` как `Sort Method: external merge` ([[explain-analyze]]).

## Пример
```java
// Сортировка слиянием для int[]: форма, которую ждёт любой вопрос «реализуй сортировку».
static void mergeSort(int[] a) { if (a.length > 1) sort(a, new int[a.length], 0, a.length); }

private static void sort(int[] a, int[] tmp, int lo, int hi) {   // сортирует [lo, hi)
    if (hi - lo < 2) return;
    int mid = (lo + hi) >>> 1;                                     // без переполнения
    sort(a, tmp, lo, mid);
    sort(a, tmp, mid, hi);
    if (a[mid - 1] <= a[mid]) return;                              // уже упорядочено: трюк из TimSort
    merge(a, tmp, lo, mid, hi);
}

private static void merge(int[] a, int[] tmp, int lo, int mid, int hi) {
    int i = lo, j = mid, k = lo;
    while (i < mid && j < hi) tmp[k++] = a[i] <= a[j] ? a[i++] : a[j++];  // <= сохраняет стабильность
    while (i < mid) tmp[k++] = a[i++];
    while (j < hi)  tmp[k++] = a[j++];
    System.arraycopy(tmp, lo, a, lo, hi - lo);
}

// Продакшн-код: стабильная сортировка по нескольким ключам, без самописного алгоритма.
orders.sort(Comparator.comparing(Order::status)
                      .thenComparing(Order::createdAt, Comparator.reverseOrder()));
```

## Подводные камни
- Компаратор `(a, b) -> a.amount - b.amount` переполняется на больших int и нарушает контракт; используй `Integer.compare` или `Comparator.comparingInt`.
- Компараторы, не согласованные с `equals`, в `TreeSet` молча теряют элементы, которые множество считает «равными» ([[equals-and-hashcode]]).
- Сортировка `BigDecimal` через `compareTo` считает `1.0` и `1.00` равными; `equals` — нет ([[time-money-and-ids]]).
- Быстрая сортировка с первым элементом в качестве опорного на отсортированном входе работает за O(n²) и может переполнить стек; на собеседовании всегда говори «случайный опорный элемент».
- Сортировка результата на миллион строк в приложении вместо того, чтобы дать Postgres использовать индекс, — классический баг производительности ([[postgres-indexes]]).
- Связанные заметки: [[data-structures]] — контейнеры, которые сортируют, [[greedy-algorithms]] — потому что большинство жадных решений начинаются с сортировки, [[interview-problem-patterns]] — «сначала отсортируй, потом два указателя».
