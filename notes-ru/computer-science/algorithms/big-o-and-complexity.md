## Кратко
Big-O описывает, как время работы или память **растут с размером входных данных**, без учёта констант и младших членов. Это верхняя граница скорости роста, а не показания секундомера: алгоритм O(n) с огромной константой может проиграть O(n log n) на реальных данных. На собеседовании от тебя ждут, что для каждого решения ты назовёшь временную и пространственную сложность, различишь лучший/средний/худший случай и знаешь, что значит «амортизированное O(1)» для `ArrayList.add` и `HashMap.put`.

## Основное

### Семейство обозначений
| Обозначение | Смысл | Использование на собеседовании |
|---|---|---|
| O(f) | растёт **не быстрее** f (верхняя граница) | то, что имеют в виду все |
| Ω(f) | растёт **не медленнее** f (нижняя граница) | «любая сортировка сравнениями — Ω(n log n)» |
| Θ(f) | и то и другое: точная граница | когда хочется быть точным |
| o(f) | строго более медленный рост | редко |

- Константы и младшие члены отбрасываются: `3n² + 50n + 7` — это O(n²). Два вложенных цикла по одному массиву — O(n²); два последовательных цикла — O(n) + O(n) = O(n).
- Разные входные данные получают разные переменные: слияние списков размеров n и m — O(n + m), а не O(n).
- Логарифмы: основание не важно (постоянный множитель), поэтому O(log₂ n) = O(log n). Деление области поиска пополам на каждом шаге даёт log n ([[binary-search-and-variants]]); высота сбалансированного дерева — log n ([[trees-and-bst]]).

### Типичные классы, с реальным примером для каждого
| Класс | Название | Пример | n = 1 000 000 |
|---|---|---|---|
| O(1) | константная | `HashMap.get`, доступ по индексу массива, `ArrayDeque.push` | 1 |
| O(log n) | логарифмическая | бинарный поиск, `TreeMap.get`, push/pop в куче | ~20 |
| O(n) | линейная | проход по списку, `ArrayList.contains`, BFS по n вершинам | 10⁶ |
| O(n log n) | линейно-логарифмическая | `Arrays.sort`, сортировка слиянием, пирамидальная сортировка, построение `TreeMap` | 2 × 10⁷ |
| O(n²) | квадратичная | вложенные циклы, сортировка пузырьком/вставками, наивная проверка дубликатов | 10¹² |
| O(2ⁿ) | экспоненциальная | все подмножества, наивный рекурсивный Фибоначчи | безнадёжно |
| O(n!) | факториальная | все перестановки | безнадёжно при n больше ≈ 11 |

Эмпирическое правило для вопроса «уложится ли»: около 10⁸ простых операций в секунду. n = 10⁵ исключает O(n²); при n = 10³ O(n²) вполне годится; n ≤ 20 позволяет перебор O(2ⁿ) по битовым маскам ([[bit-manipulation]]).

### Лучший, средний, худший
- Быстрая сортировка: в среднем O(n log n), в худшем O(n²) на уже отсортированных данных с наивным выбором опорного элемента. Поиск в хеш-таблице: в среднем O(1), в худшем O(n), когда все ключи коллизируют ([[hash-tables]]; в Java 8 бакеты превращаются в деревья, что даёт O(log n)).
- Если не просят иного, называй худший случай и упоминай средний, когда они различаются.

### Амортизированная сложность
- Отдельная операция может быть дорогой, но **среднее по последовательности** дёшево. `ArrayList.add` при расширении копирует весь массив (O(n)), но удвоение ёмкости означает, что n добавлений в сумме стоят O(n), поэтому каждое добавление — амортизированное O(1) ([[arrays-and-dynamic-arrays]]).
- То же рассуждение: расширение `HashMap`, `StringBuilder.append`, union-find со сжатием путей ([[topological-sort-and-union-find]]).
- Амортизированная сложность — это не средний случай: амортизированная — гарантия для любой последовательности, а средний случай предполагает распределение вероятностей на входных данных.

### Пространственная сложность
- Считай **дополнительную** память сверх входных данных. Сортировка слиянием — O(n) дополнительно, пирамидальная — O(1), быстрая — O(log n) на стек рекурсии.
- Глубина рекурсии — это память: наивный DFS по пути из 10⁶ вершин переполнит стек Java задолго до кучи ([[recursion-and-backtracking]], [[stack-vs-heap-memory]]).
- «На месте» (in-place) означает O(1) дополнительной памяти, а не «вообще без выделений».

### Как прочитать сложность по Java-коду
- `for (i..n) for (j = i..n)`: всё равно O(n²) (n²/2 операций).
- `for (i = 1; i < n; i *= 2)`: O(log n).
- Цикл из n итераций, вызывающий `List.contains` на `ArrayList`: O(n²); замени список на `HashSet`, и станет O(n). Это самое частое исправление «сделай быстрее» на собеседовании.
- `String s += x` внутри цикла: O(n²), потому что каждая конкатенация копирует ([[strings-and-string-pool]]); используй `StringBuilder`.
- Стримы не меняют сложность: `list.stream().filter(...).toList()` — O(n), `sorted()` добавляет O(n log n) ([[stream-api]]).

## Пример
```java
// Три способа узнать, есть ли у двух пользователей общий ICCID; ответ один, рост разный.
record Sim(String iccid) {}

static boolean quadratic(List<Sim> a, List<Sim> b) {          // время O(n*m), память O(1)
    for (Sim x : a)
        for (Sim y : b)
            if (x.iccid().equals(y.iccid())) return true;
    return false;
}

static boolean sortBased(List<Sim> a, List<Sim> b) {          // время O((n+m) log(n+m))
    String[] all = Stream.concat(a.stream(), b.stream())
            .map(Sim::iccid).sorted().toArray(String[]::new);
    for (int i = 1; i < all.length; i++)
        if (all[i].equals(all[i - 1])) return true;
    return false;
}

static boolean hashBased(List<Sim> a, List<Sim> b) {          // время O(n+m), память O(n)
    Set<String> seen = new HashSet<>();
    for (Sim x : a) seen.add(x.iccid());                       // амортизированное O(1) на add
    for (Sim y : b) if (seen.contains(y.iccid())) return true;
    return false;
}
```
Типичный ход на собеседовании: написать `quadratic`, назвать O(n·m), затем улучшить до `hashBased` и объяснить размен времени на память.

## Подводные камни
- Говорить «O(1), потому что это HashMap», не упоминая стоимость хеш-функции: хеширование длинной `String` — O(длины), а плохой `hashCode` превращает поиск в O(n) ([[equals-and-hashcode]]).
- Путать сортировку O(n log n) с «достаточно быстро»: сортировка 10⁸ строк в памяти всё равно занимает секунды и гигабайты; БД может сделать это лучше с индексом ([[database-indexes]]).
- Забывать про стек рекурсии, заявляя O(1) по памяти.
- Называть сложность не по той переменной: графовый алгоритм — O(V + E), а не O(n).
- Big-O игнорирует константы, а железо — нет: линейный проход по маленькому массиву быстрее поиска в хеш-таблице благодаря кеш-линиям ([[cpu-caches-and-cache-lines]]).
