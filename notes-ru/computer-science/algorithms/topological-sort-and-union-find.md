## Кратко
**Топологическая сортировка** (topological sort) упорядочивает вершины ориентированного ациклического графа так, чтобы каждое ребро шло от более ранней к более поздней: разрешение зависимостей, порядок сборки, порядок миграций, планирование шагов workflow. Алгоритм Кана (BFS по входящим степеням) заодно бесплатно обнаруживает циклы: если на выходе меньше V вершин, есть цикл. **Union-find** (система непересекающихся множеств, disjoint set union, DSU) отслеживает, какие элементы принадлежат одной группе, с почти O(1) `find` и `union`; он отвечает на вопросы о связности графов, рёбра которых поступают по одному, и лежит в основе алгоритма Краскала для минимального остовного дерева.

## Основное

### Топологическая сортировка
- Определена только на DAG. Обычно существует несколько допустимых порядков; используй `PriorityQueue` вместо очереди, когда нужен порядок «сначала наименьший» (лексикографически наименьшее расписание).
- **Алгоритм Кана**: вычислить входящую степень каждой вершины, поставить в очередь все с входящей степенью 0, извлечь, добавить в порядок, уменьшить входящую степень каждого соседа, поставить в очередь, когда она дойдёт до 0. O(V + E).
- **Версия на DFS**: запустить DFS, класть каждую вершину в стек при завершении; стек, извлекаемый по порядку, — топологический порядок. Для обнаружения циклов нужна серо-чёрная раскраска ([[graph-traversal-bfs-dfs]]).
- Самый длинный путь в DAG (критический путь, «минимум семестров») — это DP по топологическому порядку ([[dynamic-programming]]).
- Формулировки на собеседованиях: расписание курсов, инопланетный словарь (упорядочить буквы по отсортированным словам), системы сборки, «могут ли все задачи завершиться».
- В работе: Flyway упорядочивает миграции по номеру версии, но зависимости между изменениями схемы — это DAG, который держишь в голове ([[schema-migrations-flyway-liquibase]]); Spring определяет порядок создания бинов по рёбрам зависимостей и падает на циклах ([[spring-ioc-and-di]]); дочерние workflow и activity Temporal с `await` образуют DAG выполнения ([[temporal-concepts]]).

### Union-find
- Каждый элемент указывает на родителя; корень представляет множество. `find(x)` идёт по родителям до корня; `union(a, b)` подвешивает один корень под другой.
- Две оптимизации делают его практически константным по времени:
  - **Сжатие путей** (path compression): при `find` каждая посещённая вершина перенаправляется прямо на корень.
  - **Объединение по рангу/размеру** (union by rank/size): меньшее дерево подвешивается под большее.
  - Вместе: амортизированное O(α(n)) на операцию, где α — обратная функция Аккермана, ≤ 4 для любого реалистичного n ([[big-o-and-complexity]]).
- Применение: компоненты связности при потоковом поступлении рёбер, «число провинций», лишнее ребро (ребро, замыкающее цикл в неориентированном графе), слияние аккаунтов (одинаковый email → один человек), MST Краскала (отсортировать рёбра, объединять, если концы в разных множествах), перколяция, классы эквивалентности уравнений.
- Храни `size[]` для каждого корня, чтобы отвечать на «насколько велика компонента», и `count` множеств, чтобы отвечать на «сколько компонент» без прохода.
- Он не умеет удалять рёбра и не работает для достижимости в ориентированном графе; для этого нужен обход.

### Выбор
| Вопрос | Инструмент |
|---|---|
| допустимый порядок с учётом зависимостей или есть ли цикл (ориентированный граф) | топологическая сортировка |
| связаны ли a и b, сколько компонент (неориентированный граф, рёбра добавляются со временем) | union-find |
| связаны ли a и b, статический граф, один запрос | BFS/DFS |
| цикл в неориентированном графе при добавлении рёбер | union-find (`find(a) == find(b)` перед объединением) |
| минимальное остовное дерево | Краскал с union-find или Прим с кучей ([[heaps-and-priority-queues]]) |

### Сложность
| Операция | Время |
|---|---|
| топосортировка Кана / на DFS | O(V + E) |
| `find` / `union` в DSU с обеими оптимизациями | амортизированное O(α(n)) ≈ O(1) |
| Краскал | O(E log E) на сортировку |

## Пример
```java
// Топологическая сортировка Кана по шагам провижининга: шаг -> шаги, от которых он зависит.
// Бросает исключение, если в графе зависимостей есть цикл.
static List<String> executionOrder(Map<String, List<String>> dependsOn) {
    Map<String, Integer> inDegree = new HashMap<>();
    Map<String, List<String>> dependents = new HashMap<>();
    for (var e : dependsOn.entrySet()) {
        inDegree.putIfAbsent(e.getKey(), 0);
        for (String dep : e.getValue()) {
            inDegree.merge(e.getKey(), 1, Integer::sum);
            inDegree.putIfAbsent(dep, 0);
            dependents.computeIfAbsent(dep, k -> new ArrayList<>()).add(e.getKey());
        }
    }
    Deque<String> ready = new ArrayDeque<>();
    inDegree.forEach((step, d) -> { if (d == 0) ready.add(step); });
    List<String> order = new ArrayList<>();
    while (!ready.isEmpty()) {
        String step = ready.poll();
        order.add(step);
        for (String next : dependents.getOrDefault(step, List.of()))
            if (inDegree.merge(next, -1, Integer::sum) == 0) ready.add(next);
    }
    if (order.size() != inDegree.size()) throw new IllegalStateException("cycle in step dependencies");
    return order;
}

// Union-find со сжатием путей и объединением по размеру.
final class DSU {
    private final int[] parent, size;
    DSU(int n) { parent = new int[n]; size = new int[n];
                 for (int i = 0; i < n; i++) { parent[i] = i; size[i] = 1; } }
    int find(int x) { return parent[x] == x ? x : (parent[x] = find(parent[x])); }
    boolean union(int a, int b) {
        a = find(a); b = find(b);
        if (a == b) return false;                       // уже связаны: это ребро замыкает цикл
        if (size[a] < size[b]) { int t = a; a = b; b = t; }
        parent[b] = a; size[a] += size[b];
        return true;
    }
}
```

## Подводные камни
- Построение графа не в ту сторону (`a depends on b` для порядка Кана должно стать ребром `b → a`).
- Вершины, которые встречаются только как зависимости и никогда как ключи, теряются, если не зарегистрировать их с входящей степенью 0 (вызовы `putIfAbsent` выше).
- Union-find без сжатия путей на враждебных входах деградирует до цепочек O(n); только с одной из двух оптимизаций он всё ещё O(log n), что нормально, но скажи, какую именно ты реализовал.
- Рекурсивный `find` на DSU из 10⁷ элементов до сжатия может переполнить стек; в продакшне используй итеративную двухпроходную версию.
- Считать топологический порядок единственным; тесты, которые проверяют конкретный порядок, ломаются при изменении порядка обхода `HashMap`.
