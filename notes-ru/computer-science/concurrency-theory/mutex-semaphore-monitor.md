## Кратко
Три классических примитива, три разные гарантии. **Мьютекс (mutex)** даёт взаимное исключение с владением: один владелец за раз, и освобождает только владелец. **Семафор (semaphore)** — это счётчик с атомарными `acquire` (ждать, пока > 0, затем уменьшить) и `release` (увеличить): со значением N он ограничивает конкурентность, с 1 служит сигналом между потоками, и никто им не владеет. **Монитор (monitor)** объединяет мьютекс с защищаемыми им данными и **условными переменными (condition variables)**, чтобы потоки могли ждать внутри критической секции выполнения предиката («очередь не пуста») и просыпаться при его изменении; `synchronized` + `wait/notify` и `ReentrantLock` + `Condition` в Java — это мониторы. Сами API Java — в [[synchronization-and-monitors]], [[locks-and-lock-free]] и [[synchronizers]]; реализации в ОС (futex, pthread) — в [[deadlocks-and-synchronization-primitives]].

## Основное

### Рядом друг с другом
| | Мьютекс | Семафор | Монитор |
|---|---|---|---|
| Состояние | заблокирован / разблокирован + владелец | целый счётчик ≥ 0 | мьютекс + защищаемые данные + очереди условий |
| Кто освобождает | только владелец | кто угодно | владелец (при выходе или при `wait`) |
| Счётчик | 1 | N | 1 (мьютекс) |
| Назначение | защита общих данных | ограничение конкурентности, сигнализация событий | защита данных и координация по их состоянию |
| Блокирующее ожидание условия | нет (спин или сон снаружи) | частично (ожидание счётчика > 0) | да: `wait(cond)` атомарно освобождает мьютекс и засыпает |
| Реентерабельность | опционально (рекурсивный мьютекс) | не имеет смысла | обычно да (Java) |
| Java | `ReentrantLock`, `synchronized` | `java.util.concurrent.Semaphore` | `synchronized` + `wait/notify`, `Lock` + `Condition` |
| Аналог в Postgres | блокировка строки `FOR UPDATE` | лимит соединений, `max_connections` | advisory lock + `LISTEN/NOTIFY` |

### Мьютекс
- Гарантии: внутри не более одного потока; продвижение; при честной (fair) реализации — ограниченное ожидание. Владение позволяет обнаруживать ошибки (разблокировка не владельцем), рекурсию и **наследование приоритета (priority inheritance)** (высокоприоритетный ожидающий одалживает свой приоритет владельцу).
- Стоимость: захват без конкуренции — один CAS (~20 нс). При конкуренции проигравший должен либо крутиться в спине (дёшево, если время удержания — наносекунды и есть свободные ядра), либо припарковаться в ядре ОС (микросекунды, futex). Адаптивные мьютексы недолго крутятся, затем паркуются.
- Вариант чтения-записи (read-write): много читателей или один писатель. Помогает, только когда чтения длинные и сильно превосходят записи числом; иначе дополнительный учёт стоит больше, чем обычный мьютекс.

### Семафор
- Изобретён Дейкстрой (`P`/`V`). **Считающий семафор**, инициализированный N, пропускает N потоков: пулы соединений, переборки (bulkheads), ограничивающие конкурентные вызовы медленного нижестоящего сервиса ([[circuit-breaker]] часто работает в паре с ним), ограничение числа запросов в полёте, ограничение ёмкости очереди.
- **Двоичный семафор** (N = 1) похож на мьютекс, но им не является: поток A может вызвать `release()` для того, что захватил поток B, — это ровно то, что нужно для **сигнализации** («данные готовы, разбуди потребителя»), и ровно то, что не нужно для критической секции (нет владения, нет наследования приоритета, нет обнаружения двойного освобождения).
- Производитель/потребитель с двумя семафорами (`empty = N`, `full = 0`) плюс мьютекс для индекса буфера — хрестоматийное решение для ограниченных буферов; `ArrayBlockingQueue` в Java реализует то же самое одной блокировкой и двумя условиями.

### Монитор
- Предложен Хоаром и Бринчем Хансеном: класс, методы которого выполняются под одним неявным мьютексом, с условными переменными для ожидания. Ключевая операция — `wait(cond)`: **атомарно** освободить мьютекс и заблокироваться; при пробуждении снова захватить мьютекс перед возвратом. Без атомарности между «проверить предикат» и «заснуть» есть окно потерянного пробуждения (lost wakeup).
- **Семантика Хоара против семантики Mesa**: мониторы Хоара передают блокировку прямо сигнализированному потоку, поэтому при пробуждении предикат гарантированно истинен. Мониторы Mesa (Java, pthreads, любая реальная система) просто переносят ожидающего в очередь готовых; к моменту, когда он снова захватит блокировку, другой поток мог изменить состояние. Отсюда правило: **всегда жди в цикле `while`**, никогда в `if`. Ложные пробуждения (spurious wakeups) разрешены по той же причине.
- `signal`/`notify` будит одного ожидающего на условии; `broadcast`/`notifyAll` будит всех. Используй одно условие на предикат (`notFull`, `notEmpty`) с `signal` или одно условие с `broadcast`. Сигнал не тому единственному ожидающему при одном общем условии — классическая взаимная блокировка.
- Особенности Java: каждый объект — монитор (`synchronized`, `wait`, `notify`); `ReentrantLock.newCondition()` даёт несколько условий на одну блокировку ([[synchronization-and-monitors]]).

### Выбор
- Защитить структуру данных: мьютекс (или CAS для состояния из одного слова, [[lock-free-and-cas]]). Ограничить, сколько потоков одновременно может делать X: считающий семафор. Однократное «это произошло»: защёлка (latch) или future ([[synchronizers]], [[completable-future]]). Ждать изменения состояния защищённых данных: монитор с условиями или блокирующая очередь, которая уже это реализует.

## Пример
```java
// Ограниченный буфер как монитор с двумя условиями (то, что ArrayBlockingQueue делает внутри),
// используется для передачи заказов на загрузку eSIM из HTTP-потоков небольшому пулу воркеров SM-DP+.
final class OrderBuffer {
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull  = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();
    private final Deque<Order> items = new ArrayDeque<>();
    private final int capacity;

    OrderBuffer(int capacity) { this.capacity = capacity; }

    void put(Order o) throws InterruptedException {
        lock.lock();
        try {
            while (items.size() == capacity) notFull.await();   // while, а не if: семантика Mesa
            items.addLast(o);
            notEmpty.signal();                                   // разбудить ровно одного потребителя
        } finally { lock.unlock(); }
    }

    Order take() throws InterruptedException {
        lock.lock();
        try {
            while (items.isEmpty()) notEmpty.await();
            Order o = items.removeFirst();
            notFull.signal();
            return o;
        } finally { lock.unlock(); }
    }
}

// Версия на семафоре для «не более 8 конкурентных вызовов к серверу SM-DP+» (переборка, bulkhead):
private final Semaphore smdpSlots = new Semaphore(8, true);
Response callSmdp(Request r) throws InterruptedException {
    if (!smdpSlots.tryAcquire(2, TimeUnit.SECONDS)) throw new BulkheadFull();
    try { return smdpClient.send(r); } finally { smdpSlots.release(); }
}
```
В production используй `ArrayBlockingQueue` и `Bulkhead` из Resilience4j; смысл в том, чтобы узнавать, каким примитивом является каждый из них.

## Подводные камни
- Использовать семафор как мьютекс: двойной `release()` молча пропускает два потока; нет наследования приоритета; нет реентерабельности. Бери мьютекс, когда есть владелец.
- `if (!condition) wait()` вместо `while`: неверно при семантике Mesa и ложных пробуждениях; проявляется как редкое `NoSuchElementException` или отрицательный счётчик.
- `notify()` с одной общей условной переменной для двух разных предикатов: будит производителя, когда нужен был потребитель; всё встаёт. Используй два условия или `notifyAll()`.
- Удерживать монитор во время ввода-вывода (`synchronized` вокруг HTTP-вызова): пропускная способность падает до одного запроса за раз, а таймауты превращаются в зависания, похожие на взаимную блокировку.
- Забывать, что разрешения `Semaphore` не привязаны к потокам: `release()` в `finally`, выполняющийся после неудачного `tryAcquire`, добавляет разрешение, которого никогда не было.
- Связанные заметки: [[deadlocks-and-synchronization-primitives]] — как всё это построено на futex и откуда берутся взаимные блокировки, [[race-conditions-and-critical-sections]] — что на самом деле представляет собой защищаемая ими критическая секция.
