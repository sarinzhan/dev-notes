## Кратко
**Состояние гонки (race condition)** — это ошибка корректности, при которой результат зависит от относительного тайминга конкурентных операций. **Гонка данных (data race)** — понятие более узкое и низкоуровневое: два потока обращаются к одной ячейке памяти без синхронизации, и хотя бы один пишет; в Java и C++ это определённый термин, делающий поведение (или видимость) неопределённым. Бывает состояние гонки без гонки данных (два атомарных шага, которые должны были быть одним) и гонка данных, на практике безвредная. Исправление в обоих случаях построено на одной идее: определить **критическую секцию (critical section)** (составное действие, которое для остальных должно выглядеть атомарным) и обеспечить **взаимное исключение (mutual exclusion)** либо превратить составное действие в одну атомарную операцию. Инструменты Java для этого (`synchronized`, `Atomic*`, `ConcurrentHashMap`) — в [[synchronization-and-monitors]], [[locks-and-lock-free]] и [[concurrent-collections]]; зоопарк опасностей (взаимная блокировка, livelock, голодание) — в [[concurrency-hazards]].

## Основное

### Состояние гонки против гонки данных
| | Состояние гонки | Гонка данных |
|---|---|---|
| Уровень | логика / инварианты | обращение к памяти |
| Определение | результат зависит от чередования так, что нарушается спецификация | несинхронизированный конкурентный доступ, хотя бы одна запись |
| Как обнаруживается | рассуждением, тестами под нагрузкой, проверкой моделей (model checking) | инструментами: ThreadSanitizer, `jcstress` в Java, модель памяти |
| Пример одного без другого | `if (!exists(k)) insert(k)`, где каждый вызов внутри синхронизирован | два потока пишут в флаг `boolean done` одно и то же значение |
| Исправление | сделать всё составное действие атомарным | добавить синхронизацию или использовать атомики, чтобы модель памяти дала ребро happens-before ([[memory-models-and-visibility]]) |
- Две классические формы состояния гонки: **«проверь-затем-действуй» (check-then-act)** (`if (balance >= amount) balance -= amount`; TOCTOU в файловых системах: `if exists(file) then open(file)`) и **«прочитай-измени-запиши» (read-modify-write)** (`count++`, `map.put(k, map.get(k) + 1)`).
- Математика чередований: при двух потоках, каждый из которых делает `count++` (загрузка, сложение, запись), возможно 20 чередований; два из исходов теряют инкремент. Баг, воспроизводящийся в 1% случаев под нагрузкой, — всё равно баг.

### Критическая секция
- Участок кода, который работает с общим состоянием и не должен чередоваться с другими такими участками над тем же состоянием. Требования к корректному решению (эпоха Дейкстры/Петерсона): **взаимное исключение**, **продвижение** (если внутри никого нет, кто-то из желающих войти войдёт), **ограниченное ожидание** (нет голодания).
- Секцию определяет **инвариант**, а не синтаксис: «сумма обоих счетов постоянна» делает оба обновления одной критической секцией, даже если это разные методы. Слишком маленькая секция даёт гонки; слишком большая — конкуренцию и риск взаимной блокировки ([[deadlocks-and-synchronization-primitives]]).
- Защищай каждое обращение, а не только записи: читатель, видящий наполовину обновлённую структуру (`HashMap` посреди рехеширования при расширении, 64-битный `long`, записанный двумя половинами на 32-битной JVM), — это тоже гонка.

### Атомарность на разных уровнях
| Уровень | Что атомарно | Инструмент |
|---|---|---|
| Железо | выровненная загрузка/запись слова, CAS, fetch-and-add | `lock cmpxchg`, `ldxr/stxr` |
| Язык | чтение/запись `volatile`, `AtomicLong.incrementAndGet`, `ConcurrentHashMap.compute` | [[lock-free-and-cas]] |
| Блок кода | всё внутри мьютекса/монитора | [[mutex-semaphore-monitor]] |
| База данных | транзакция или одиночный оператор `UPDATE ... SET n = n + 1 WHERE ...` | [[transactions-acid-and-isolation]], [[postgres-isolation-levels]] |
| Распределённая система | compare-and-set по версии, ключ идемпотентности, аренда (lease) | [[idempotency]], [[distributed-locks-and-fencing]] |
- Одна и та же гонка мигрирует между уровнями. `SELECT balance`, а затем `UPDATE balance = ?` в Java — это «проверь-затем-действуй» против базы данных; два экземпляра сервиса гоняются так же, как два потока. И исправление той же формы: один атомарный оператор (`UPDATE ... WHERE balance >= ?` с проверкой числа строк), блокировка строки (`FOR UPDATE`) или оптимистическое версионирование (`WHERE version = ?`, [[jpa-locking]]).

### Поиск гонок
- Эвристики для код-ревью: любое общее изменяемое поле, которое читается в одном операторе и пишется в другом; любой `get`, а затем `put`; ленивая инициализация; счётчики; кэши; «синглтон» с проверкой на null.
- Тесты: запускать операцию из N потоков со стартом через `CyclicBarrier` ([[synchronizers]]) и проверять инвариант; `jcstress` для гонок на уровне памяти; нагрузочный тест против настоящего Postgres для SQL-версии (собственный скрипт `pgbench`).
- Production: дубликаты записей с одинаковым бизнес-ключом, отрицательные балансы, счётчики, расходящиеся с источником истины, «невозможные» состояния.

## Пример
```java
// Квота активаций eSIM на абонента: не более N активных профилей.
// Гонка: «проверь-затем-действуй» между двумя экземплярами приложения. Поток/экземпляр A и B оба видят 2 < 3 и оба вставляют.
@Transactional
public void activate(UUID subscriberId, String iccid) {
    int active = repo.countActive(subscriberId);          // прочитать
    if (active >= 3) throw new QuotaExceeded();           // проверить
    repo.insertActive(subscriberId, iccid);               // действовать  <- проскакивают две вставки
}

// Исправление 1: сделать составное действие одним атомарным оператором на уровне базы данных
@Transactional
public void activateAtomic(UUID subscriberId, String iccid) {
    int inserted = jdbc.update("""
        INSERT INTO active_profile (subscriber_id, iccid)
        SELECT ?, ?
        WHERE (SELECT count(*) FROM active_profile WHERE subscriber_id = ?) < 3
        """, subscriberId, iccid, subscriberId);
    // всё ещё гонка при READ COMMITTED: оба SELECT могут выполниться до того, как станет видна любая из вставок.
    // Поэтому ещё и сериализуем по абоненту:
    if (inserted == 0) throw new QuotaExceeded();
}

// Исправление 2: сериализовать критическую секцию по абоненту блокировкой строки, после чего «проверь-затем-действуй» безопасно
@Transactional
public void activateLocked(UUID subscriberId, String iccid) {
    jdbc.queryForObject("SELECT id FROM subscriber WHERE id = ? FOR UPDATE", UUID.class, subscriberId);
    if (repo.countActive(subscriberId) >= 3) throw new QuotaExceeded();
    repo.insertActive(subscriberId, iccid);
}
```
Блокировка строки — это мьютекс; граница транзакции — критическая секция; инвариант «≤ 3 активных на абонента» — то, что её определяет. Ограничение `UNIQUE` на `(subscriber_id, slot)` было бы lock-free-альтернативой: пусть база данных отвергнет проигравшего ([[constraints-and-relationships]]).

## Подводные камни
- Сделать каждый метод `synchronized` и поверить, что класс потокобезопасен: `if (!list.contains(x)) list.add(x)` на `synchronizedList` — всё равно «проверь-затем-действуй».
- «Это всего лишь счётчик, кого волнует изредка потерянное обновление»: метрики уплывают, ограничители частоты пропускают лишние запросы, квоты теряют деньги.
- `volatile` для исправления `count++`: он исправляет видимость, а не атомарность «прочитай-измени-запиши». Используй `AtomicLong`/`LongAdder`.
- Полагаться на базу данных, не выбрав уровень изоляции осознанно: `READ COMMITTED` позволяет двум транзакциям обеим пройти проверку количества; для «проверь-затем-действуй» над агрегатами нужен `SERIALIZABLE` или явная блокировка ([[postgres-isolation-levels]]).
- Блокировка с двойной проверкой без `volatile` у поля: классическая гонка «опубликован раньше, чем сконструирован» в Java как до, так и после правил JDK 5.
- Связанные заметки: [[memory-models-and-visibility]] — почему гонка данных больше, чем ошибка тайминга, [[immutability-and-side-effects]] — дизайн, полностью убирающий общее изменяемое состояние.
