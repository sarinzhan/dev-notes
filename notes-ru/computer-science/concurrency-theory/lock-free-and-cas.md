## Кратко
**Сравнение с обменом (compare-and-swap, CAS)** — это одна аппаратная инструкция: «если слово по этому адресу всё ещё равно `expected`, записать `new` и вернуть true, иначе вернуть false». Любой lock-free-алгоритм — это цикл: прочитать текущее значение, вычислить новое, выполнить CAS; если другой поток успел его изменить, повторить. **Lock-free (без блокировок)** означает, что хотя бы один поток в системе продвигается за ограниченное число шагов (ни один поток не может заблокировать остальных, будучи снятым с CPU с удерживаемой блокировкой); **wait-free (без ожидания)** означает, что каждый поток завершается за ограниченное число шагов. Классическая ловушка — **проблема ABA**: значение вернулось к `A`, поэтому CAS успешен, но мир за это время изменился; лечится версией/меткой или указателями опасности (hazard pointers). `Atomic*`, `VarHandle`, `LongAdder` в Java и сравнение блокировок с lock-free — в [[locks-and-lock-free]]; эта заметка — про общий механизм.

## Основное

### Примитив
- Железо: `lock cmpxchg` на x86 (одна инструкция, кэш-линия заблокирована на время её выполнения), пары load-linked/store-conditional `ldxr`/`stxr` на ARM (сохранение не удаётся, если кто-то трогал линию в промежутке). Обе — атомарные операции чтение-изменение-запись с полным барьером или барьером acquire/release ([[memory-models-and-visibility]]).
- Стоимость: ~5–20 нс без конкуренции, примерно как захват мьютекса без конкуренции (который сам является CAS). При конкуренции цикл CAS крутится на передачах кэш-линии между ядрами: каждая неудачная попытка — это круг через протокол когерентности кэшей (~50–100 нс), и при многих ядрах на одной линии пропускная способность обваливается ([[cpu-caches-and-cache-lines]]).
- Родственники: выборка со сложением (fetch-and-add, `lock xadd`, используется в `getAndIncrement`; никогда не проваливается, поэтому wait-free), проверка с установкой (test-and-set, спинлоки), CAS двойной ширины (`cmpxchg16b`, CAS указателя и счётчика вместе).
- Консенсусное число: CAS решает wait-free-консенсус для любого числа потоков (Херлихи), поэтому любую lock-free-структуру в принципе можно построить на `AtomicReference`.

### Гарантии продвижения
| Гарантия | Значение | Пример |
|---|---|---|
| Блокирующая | снятый с CPU или упавший владелец блокировки останавливает всех | мьютекс, `synchronized` |
| Obstruction-free | поток завершится, если будет работать в одиночку достаточно долго | некоторые реализации STM |
| Lock-free | какой-то поток всегда завершается за ограниченное число шагов; отдельные потоки могут голодать | циклы повтора CAS, стек Трайбера (Treiber stack), очередь Майкла–Скотта (Michael-Scott queue), `ConcurrentLinkedQueue` |
| Wait-free | каждый поток завершается за ограниченное число шагов | счётчики на fetch-and-add, инкременты `LongAdder`, кольцевые буферы с одним производителем и одним потребителем |
- Lock-free — это про **продвижение при вытеснении и сбоях**, а не про голую скорость. Lock-free-структура может быть медленнее структуры с блокировкой при низкой конкуренции; её ценность в том, что поток, приостановленный ОС ([[process-management]]), safepoint-ом GC или page fault-ом, не может застопорить остальных, и нет ни инверсии приоритетов, ни взаимной блокировки ([[deadlocks-and-synchronization-primitives]]).

### Цикл CAS
```c
// Псевдокод в стиле C: lock-free push в стек Трайбера
void push(Stack* s, Node* n) {
    Node* head;
    do {
        head = atomic_load(&s->head);     // 1. прочитать
        n->next = head;                   // 2. вычислить на его основе
    } while (!CAS(&s->head, head, n));    // 3. зафиксировать, только если head за это время никто не изменил
}
```
- Шаг 2 должен быть без побочных эффектов или идемпотентным, потому что может выполниться много раз. Создание нового неизменяемого объекта на каждой итерации (`AtomicReference.updateAndGet` в Java с персистентной структурой) — распространённый функциональный паттерн; он также согласуется с [[immutability-and-side-effects]].
- Дисциплина спина: при неудаче несколько раз повторить сразу, затем отступить (`Thread.onSpinWait()` выдаёт `pause`), потому что долбёжка по спорной линии замедляет поток, который вот-вот преуспеет.

### Проблема ABA
- Поток 1 читает `head = A` (с `A.next = B`) и вытесняется. Поток 2 снимает `A`, снимает `B`, кладёт `A` обратно. Поток 1 продолжает: `head` всё ещё `A`, CAS успешен, и он устанавливает `head = B`, хотя `B` уже нет в стеке. В C это повреждение памяти; в Java встречается реже (идентичность объекта, на который есть ссылка, никогда не переиспользуется), но всё же возможно, когда узлы переиспользуются или значения — примитивы.
- Исправления:
  - **Помеченные указатели / метки версий**: выполнять CAS над `(pointer, counter)` вместе, чтобы у переиспользованного `A` был другой счётчик. В Java: `AtomicStampedReference`, `AtomicMarkableReference` или упаковка версии в `long`.
  - **Указатели опасности / эпохальное освобождение (epoch reclamation)**: не освобождать и не переиспользовать узел, пока его может читать какой-либо поток. GC в Java даёт это бесплатно, пока объекты узлов не переиспользуются.
  - **Новые объекты на каждое обновление**: каждый раз создавать новый узел/снимок; старый `A` никогда не вернётся.
- Тот же баг встречается в базах данных и распределённых системах: оптимистическая блокировка по `WHERE version = ?` — это CAS с меткой ([[jpa-locking]]); токен ограждения (fencing token) на распределённой блокировке — это версия, не дающая записать устаревшему владельцу ([[distributed-locks-and-fencing]]); заголовок `etag`/`If-Match` — это CAS поверх HTTP ([[http-caching]], [[idempotency]]).

### Когда использовать
- Состояние из одного слова, которое обновляют многие потоки: счётчики (`LongAdder`, когда много записей), порядковые номера, enum-ы статусов, кэшированные ссылки; очереди передачи между потоками-производителями и потоками-потребителями.
- Не для: инвариантов из нескольких полей, если они не упакованы в одно слово или один неизменяемый снимок, длинных критических секций или ввода-вывода внутри «критической секции». Там мьютекс проще и часто быстрее ([[mutex-semaphore-monitor]]).

## Пример
```java
// Lock-free «ведро токенов» для ограничения частоты API-запросов по абоненту (один CAS на запрос, без блокировки).
final class TokenBucket {
    private record State(long tokens, long lastRefillNanos) {}
    private final AtomicReference<State> state;
    private final long capacity, refillPerSecond;

    TokenBucket(long capacity, long refillPerSecond) {
        this.capacity = capacity; this.refillPerSecond = refillPerSecond;
        this.state = new AtomicReference<>(new State(capacity, System.nanoTime()));
    }

    boolean tryAcquire() {
        while (true) {
            State cur = state.get();                                            // прочитать
            long now = System.nanoTime();
            long refilled = Math.min(capacity,
                cur.tokens() + (now - cur.lastRefillNanos()) * refillPerSecond / 1_000_000_000L);
            if (refilled == 0) return false;
            State next = new State(refilled - 1, now);                          // вычислить, без побочных эффектов
            if (state.compareAndSet(cur, next)) return true;                    // зафиксировать или повторить
            Thread.onSpinWait();
        }
    }
}
```
Новый неизменяемый `State` на каждую попытку обходит ABA (старый объект `State` никогда снова не становится текущим) и сохраняет согласованность двух полей, потому что ссылка — это то единственное слово, над которым выполняется CAS ([[rate-limiting]]).

## Подводные камни
- Цикл CAS на горячем общем счётчике из 32 потоков: «пинг-понг» кэш-линии делает его медленнее полосатого `LongAdder` или счётчиков на поток, сливаемых позже.
- Выполнять неидемпотентную работу внутри цикла повтора (логирование, инкремент другого счётчика, отправку сообщения): она выполняется на каждую неудачную попытку.
- Считать, что «lock-free» означает «в остальных местах синхронизация не нужна»: CAS публикует только то, что произошло-до (happens-before) него; изменяемые объекты, достижимые из подменённой ссылки, всё равно нуждаются в собственной защите.
- ABA через переиспользование объектов или примитивные значения: пул переиспользуемых объектов-узлов или слот `long`, возвращающийся к тому же значению, ломает наивный `compareAndSet`. Добавь метку.
- Писать собственную lock-free-очередь или map для production: тонко, зависит от железа, трудно тестировать; используй `java.util.concurrent` и прибегай к своему коду только с тестами на `jcstress`.
- Связанные заметки: [[locks-and-lock-free]] — API Java и компромиссы блокировок против CAS, [[race-conditions-and-critical-sections]] — баг «проверь-затем-действуй» (check-then-act), который CAS призван закрыть.
