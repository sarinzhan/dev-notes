## Кратко
**Модель памяти (memory model)** — это контракт между программой и компилятором + железом о том, какие значения может увидеть чтение, когда несколько потоков работают с одной и той же памятью. Компиляторы переупорядочивают инструкции, а CPU выполняют их вне очереди и буферизуют записи, поэтому без синхронизации второй поток может увидеть записи поздно, никогда или в ином порядке, чем они стоят в исходном коде. Модели памяти определяют отношение **«происходит-до» (happens-before)**: частичный порядок, построенный из программного порядка плюс рёбер синхронизации (освобождение блокировки → захват, запись volatile → чтение, запуск потока, join потока). Чтение гарантированно видит запись, только если запись происходит-до чтения. `volatile`/атомики существуют, чтобы создавать эти рёбра без блокировки. Правила, специфичные для Java, и семантика `synchronized`/`volatile` — в [[java-memory-model]]; эта заметка — общая картина, применимая к C++, Go, Rust и железу.

## Основное

### Откуда берётся переупорядочивание
| Источник | Что делает | Пример |
|---|---|---|
| Компилятор / JIT | выносит загрузки из циклов, кэширует поля в регистрах, переупорядочивает независимые записи | `while (!stop) {}` превращается в `if (!stop) while (true) {}`: цикл никогда не увидит `stop = true` |
| Внеочередное выполнение в CPU | выполняет независимые инструкции раньше | более поздняя загрузка завершается раньше более ранней записи |
| Буфер записи (store buffer) | запись сидит в буфере ядра, прежде чем дойти до кэша | ядро A пишет `x = 1`, затем читает `y`; ядро B пишет `y = 1`, затем читает `x`; на x86 оба могут прочитать 0 |
| Иерархия кэшей | когерентна (MESI), но асинхронна: инвалидации ставятся в очередь | ядро продолжает использовать устаревшую линию, пока инвалидация не обработана ([[cpu-caches-and-cache-lines]]) |
- Правило, которому следует любой оптимизатор, — **«как если бы последовательно» (as-if-serial)**: один поток не может заметить разницу. Многопоточные программы могут, поэтому синхронизация служит ещё и барьером для оптимизаций.
- Аппаратные модели различаются: x86-64 — это **TSO** (total store order: видимо только переупорядочивание запись→чтение, записи видны по порядку), ARM и POWER — **слабо упорядоченные** (без барьеров переупорядочить можно почти что угодно). Код, который «работает на моём ноутбуке» (x86), может падать на ARM-сервере (Graviton, Apple silicon, Ampere), потому что JIT выдаёт там меньше барьеров, а железо пользуется свободой.

### Happens-before
- Частичный порядок над действиями. Правила, общие для Java, C++11 и Go:
  - Программный порядок внутри одного потока.
  - Освобождение мьютекса происходит-до каждого последующего захвата того же мьютекса.
  - Запись volatile/атомика (release) происходит-до каждого последующего чтения (acquire) этой переменной, которое видит записанное значение.
  - `Thread.start()` происходит-до всего в потоке; всё в потоке происходит-до возврата из `join()`.
  - Транзитивность.
- Следствие: синхронизация на **одной** переменной публикует **всё**, что было записано до неё. `volatile boolean ready = true` после заполнения обычной `HashMap` делает содержимое map видимым читателю, который видит `ready == true`. Такое «подсаживание» (piggybacking) — это то, как `ConcurrentHashMap.put` публикует объект-значение и как `ExecutorService.submit` публикует состояние задачи.
- Без ребра в программе есть **гонка данных (data race)**; в Java каждое чтение всё равно видит *какую-то* запись в эту переменную (плюс возможный разрыв `long`/`double` на 32-битных JVM). В C++ гонка данных — неопределённое поведение ([[race-conditions-and-critical-sections]]).

### Зачем существует volatile
- Блокировка даёт три вещи: взаимное исключение, видимость, упорядочивание. Часто нужны только последние две: флаг остановки, атомарно подменяемый снимок конфигурации, однократно публикуемая ссылка. `volatile` (Java), `std::atomic` с `memory_order_acquire/release` (C++), `atomic.Load/Store` (Go) дают видимость и упорядочивание без блокирования.
- Механически: компилятор не должен кэшировать или переупорядочивать через это обращение, а JIT выдаёт барьер, нужный железу (инструкцию с префиксом `lock` или `mfence` на x86 для записи; `dmb`/`stlr` + `ldar` на ARM).
- Стоимость: чтение volatile на x86 — обычная загрузка; запись volatile — полный барьер (~20–50 тактов). На ARM обе что-то стоят. Это гораздо дешевле, чем блокировка под конкуренцией.
- `volatile` **не** делает `i++` атомарной: одна загрузка и одна запись с окном между ними. Используй CAS ([[lock-free-and-cas]]).

### Уровни упорядочивания (от сильного к слабому)
| Уровень | Гарантия | Java | C++ |
|---|---|---|---|
| Последовательная согласованность (sequentially consistent) | все потоки согласны с единым глобальным порядком всех атомарных операций | `volatile`, `VarHandle.setVolatile/getVolatile` | `memory_order_seq_cst` |
| Acquire / release | release-запись публикует предыдущие записи для acquire-чтения, которое её видит; нет глобального порядка между несвязанными атомиками | `VarHandle.setRelease/getAcquire`, `AtomicX.lazySet` (устаревшее) | `acquire`/`release` |
| Opaque / relaxed | атомарно, рано или поздно видимо, без упорядочивания с другими переменными | `VarHandle.setOpaque/getOpaque` | `relaxed` |
| Обычный (plain) | никаких гарантий между потоками | обычное поле | обычная переменная |
- Большинству кода нужны только `volatile`/`synchronized`. Acquire/release важны в lock-free кольцевых буферах (Disruptor, Aeron), где полный барьер на каждую запись — узкое место.
- Та же идея на других уровнях: уровни изоляции — это модель памяти для транзакций ([[postgres-isolation-levels]]); [[consistency-models]] — межузловая версия, а «happens-before» пришло из часов Лэмпорта ([[time-and-clocks]]).

## Пример
```java
// Горячая перезагрузка конфигурации: фоновый поток подменяет весь снимок; потоки запросов его читают.
// Обычное поле: читатель может вечно видеть старую ссылку (JIT вынес загрузку) или,
// хуже того, на слабом CPU увидеть новую ссылку на наполовину сконструированный объект.
final class RatePlanCache {
    private volatile Map<String, RatePlan> plans = Map.of();   // release при записи, acquire при чтении

    void reload(List<RatePlan> fresh) {
        Map<String, RatePlan> next = new HashMap<>();           // обычные записи в обычную HashMap...
        for (RatePlan p : fresh) next.put(p.code(), p);
        plans = Map.copyOf(next);                              // ...публикуются ОДНОЙ записью volatile
    }

    RatePlan lookup(String code) {
        return plans.get(code);                                // чтение volatile видит map целиком
    }
}
```
Читатели никогда не блокируются и никогда не видят частично построенную map, потому что каждая запись в `next` происходит-до записи volatile, которая происходит-до любого чтения, видящего новую ссылку. Замена `volatile` на обычное поле компилируется и проходит модульные тесты; ломается это на ARM-узле под нагрузкой через месяцы ([[immutability-and-side-effects]]).

## Подводные камни
- «Проблемы видимости требуют блокировки»: блокировка — один из способов получить ребро happens-before, но не единственный; `volatile`, атомики, `Executor.submit`, передача через `BlockingQueue` и `Thread.join` тоже работают.
- Принимать поведение x86 за модель: CI на Graviton или Mac серии M выявит переупорядочивания, которые никогда не проявлялись на ноутбуках разработчиков с Intel.
- Считать `volatile` универсальным модификатором «потокобезопасности»: годится для флага или подмены ссылки, неверно для счётчиков, «проверь-затем-действуй» или инвариантов из нескольких полей.
- Блокировка с двойной проверкой (double-checked locking) с не-volatile полем: ссылка может быть опубликована раньше, чем станут видимы записи конструктора. Используй `volatile`, класс-холдер или просто `synchronized`.
- Искать баги видимости модульными тестами: они зависят от таймингов и железа; используй `jcstress` или рассуждай через happens-before.
- Связанные заметки: [[java-memory-model]] — точные правила Java и что гарантирует `synchronized`, [[cpu-caches-and-cache-lines]] — железо, из-за которого всё это необходимо.
