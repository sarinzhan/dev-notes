## Кратко
Конкурентность на общей памяти (потоки + блокировки) терпит неудачу, потому что любой поток может тронуть любое состояние; **передача сообщений (message passing)** убирает общее состояние и позволяет конкурентным единицам общаться только отправкой данных. Две основные школы: **модель акторов (actor model)** (Erlang, Akka/Pekko, Orleans, по духу — workflow в Temporal), где каждый актор владеет приватным состоянием, имеет почтовый ящик (mailbox), обрабатывает по одному сообщению за раз и может создавать других акторов; и **CSP** (каналы Go, Clojure core.async, конвейеры на `BlockingQueue` в Java), где анонимные процессы синхронизируются через типизированные каналы. Оба подхода меняют блокировки на очереди: гонок данных нет по построению, но теперь нужно думать о росте почтового ящика, порядке, гарантиях доставки и обратном давлении (backpressure). В Java-бэкенде эти идеи уже используются: Kafka-консьюмеры, конвейеры «поток на партицию», workflow в Temporal и activity движка workflow — всё это системы с передачей сообщений.

## Основное

### Зачем уходить от общей памяти
- С блокировками корректность зависит от того, что каждый писатель следует одной и той же дисциплине; один пропущенный где-то `synchronized` ломает инвариант ([[race-conditions-and-critical-sections]]). Композиция трудна: два по отдельности потокобезопасных класса, объединённые вместе, требуют новой блокировки, а вложенные блокировки провоцируют взаимную блокировку (deadlock) ([[deadlocks-and-synchronization-primitives]]).
- Передача сообщений делает владение явным: у состояния ровно один владелец, и единственный способ его изменить — отправить сообщение, которое владелец обработает последовательно. «Блокировкой» становится почтовый ящик, и он никогда не блокирует сам себя.
- Модель также естественно ложится на распределённость: сообщение локальному актору и сообщение актору на другом узле выглядят одинаково, поэтому модель масштабируется от потоков до кластеров ([[service-communication-sync-vs-async]], [[event-driven-architecture]]).

### Модель акторов
- У актора есть: приватное состояние, почтовый ящик (очередь), поведение, обрабатывающее одно сообщение за раз, и адрес. В ответ на сообщение он может изменить своё состояние, отправить сообщения и породить акторов. Никто другой не может читать его состояние.
- Обычно предлагаемые гарантии: доставка «не более одного раза» (at-most-once) по умолчанию (Akka), порядок FIFO для каждой пары отправитель–получатель, отсутствие конкурентной обработки внутри актора. Надёжность строится поверх: подтверждения, персистентность (акторы на event sourcing, [[event-sourcing]]), супервизия.
- **Супервизия (supervision)**: акторы образуют дерево; родитель решает, что делать, когда дочерний актор падает (перезапустить, продолжить, остановить, эскалировать). «Пусть падает» (let it crash, Erlang) заменяет защитный код перезапуском из известного корректного состояния.
- **Прозрачность местоположения (location transparency)**: адрес может быть локальным или удалённым; шардирование кластера (cluster sharding) размещает по одному актору на идентификатор сущности (один актор на абонента, на заказ) на каком-то узле, поэтому все команды для этой сущности сериализуются без распределённой блокировки ([[distributed-locks-and-fencing]]).
- Цена: трассировки стека обрываются на почтовом ящике, порядок между акторами не определён, запрос/ответ требует идентификаторов корреляции и таймаутов, а неограниченный почтовый ящик — это утечка памяти, ждущая всплеска трафика ([[backpressure-and-flow-control]]).

### CSP и каналы
- Communicating Sequential Processes Хоара: анонимные процессы, типизированные каналы как полноценные объекты; отправка в небуферизованный канал блокируется, пока получатель её не заберёт (рандеву), что бесплатно даёт обратное давление. `select` ждёт сразу на нескольких каналах.
- Принцип Go «разделяй память, общаясь» — это CSP; в Java ту же форму дают `BlockingQueue` между стадиями, потоки Reactor с обратным давлением на основе спроса ([[spring-reactive-webclient-sse]]) и структурная конкурентность (structured concurrency, JDK 25) с [[virtual-threads]].

### Сравнение
| | Потоки + блокировки | Акторы | CSP / каналы |
|---|---|---|---|
| Состояние | общее, защищено блокировками | приватное у каждого актора | приватное у каждого процесса; данные движутся по каналам |
| Общение | записи в память | асинхронные сообщения в именованный почтовый ящик | синхронная или буферизованная отправка в анонимный канал |
| Обработка сбоев | исключения распространяются в вызывающем потоке | дерево супервизии, перезапуск | значения ошибок / закрытие каналов |
| Взаимная блокировка | ошибки порядка захвата блокировок | на состоянии невозможна; возможна при циклах синхронных `ask` | возможна, когда обе стороны блокируются на отправке друг другу |
| Обратное давление | неявное (потоки блокируются) | нужно строить (ограниченные почтовые ящики, pull-потоки) | встроено для небуферизованных каналов |
| Распределённость | отдельная задача | встроенная (удалённые акторы, шардирование) | обычно в пределах процесса |
| Отладка | трассировки стека, дампы потоков | трассы сообщений, идентификаторы корреляции | дампы горутин |
| Варианты в Java/Kotlin | `java.util.concurrent` | Akka/Pekko, акторы Kotlin, verticles в Vert.x | `BlockingQueue`, Reactor, каналы Kotlin, структурная конкурентность JDK |

### Те же паттерны в сервисе на Spring/Kafka
- Партиция Kafka с одним консьюмером — это почтовый ящик актора с долговечными, упорядоченными сообщениями с доставкой «хотя бы один раз» (at-least-once); состояние по ключу, которое он обновляет, — это состояние актора ([[kafka-consumer]], [[delivery-guarantees]]).
- Workflow в Temporal — это актор с персистентным почтовым ящиком (историей): одно выполнение на бизнес-сущность, сигналы — это сообщения, activity — сообщения воркерам, replay — это история с перезапуском ([[temporal-concepts]], [[workflow-engines-vs-sagas]]).
- Однопоточный `ExecutorService` вместе со своей очередью — это система из одного актора: простейший способ сериализовать доступ к непотокобезопасному ресурсу без блокировок ([[executors-and-thread-pools]]).

## Пример
```java
// Однопоточный «актор», владеющий единственным изменяемым состоянием одного eSIM-профиля:
// все команды идут через его очередь, поэтому нет ни блокировок, ни чередования.
final class ProfileActor implements AutoCloseable {
    sealed interface Msg permits Download, Enable, Query {}
    record Download(String iccid, CompletableFuture<Void> reply) implements Msg {}
    record Enable(CompletableFuture<Void> reply) implements Msg {}
    record Query(CompletableFuture<ProfileState> reply) implements Msg {}

    private final BlockingQueue<Msg> mailbox = new ArrayBlockingQueue<>(1_000);   // ограниченная: обратное давление
    private final Thread loop;
    private ProfileState state = ProfileState.EMPTY;                               // приватное, только для владельца

    ProfileActor(String name) {
        loop = Thread.ofVirtual().name("profile-" + name).start(this::run);        // виртуальный поток JDK 21
    }

    void tell(Msg m) throws InterruptedException {
        if (!mailbox.offer(m, 1, TimeUnit.SECONDS)) throw new MailboxFull();        // не расти без ограничений
    }

    private void run() {
        try {
            while (!Thread.currentThread().isInterrupted()) {
                switch (mailbox.take()) {                                          // по одному сообщению за раз
                    case Download d -> { state = state.download(d.iccid()); d.reply().complete(null); }
                    case Enable e   -> { state = state.enable();            e.reply().complete(null); }
                    case Query q    -> q.reply().complete(state);
                }
            }
        } catch (InterruptedException ignored) { }
    }

    @Override public void close() { loop.interrupt(); }
}
```
`CompletableFuture` для ответа — это паттерн `ask`; ограниченная `ArrayBlockingQueue` — почтовый ящик с обратным давлением; `switch` по sealed-интерфейсу — поведение. Akka/Pekko добавляет супервизию, кластеризацию и персистентность поверх ровно такой формы.

## Подводные камни
- Неограниченные почтовые ящики: актор «никогда не блокируется», пока у JVM не закончится куча при первом всплеске. Ограничивай их и решай, что происходит при переполнении (отбросить, сбросить нагрузку, замедлить производителя).
- Отправлять в сообщениях изменяемые объекты: получатель и отправитель снова делят память, и гарантия модели пропадает. Отправляй неизменяемые record или копии ([[immutability-and-side-effects]]).
- Цепочки синхронных `ask` между акторами (A спрашивает B, B спрашивает A) взаимно блокируются так же, как вложенные блокировки; ставь таймауты и предпочитай «отправил и забыл» (fire-and-forget) с ответными сообщениями.
- Рассчитывать на порядок между акторами или партициями: соблюдается только FIFO на отправителя и на почтовый ящик; сага через несколько сущностей всё равно требует явного упорядочивания ([[saga]]).
- Тянуть Akka в Spring-сервис, которому нужно лишь сериализовать работу по ключу: `ConcurrentHashMap` из однопоточных исполнителей или ключи Kafka обычно достаточны и сохраняют привычные команде инструменты отладки.
- Связанные заметки: [[mutex-semaphore-monitor]] — что заменяет почтовый ящик, [[message-queues-and-streams]] — та же модель через границы процессов.
