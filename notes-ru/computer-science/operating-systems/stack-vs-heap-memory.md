## Кратко
**Стек** (stack) — это область памяти, своя у каждого потока и работающая по принципу LIFO: каждый вызов функции кладёт **фрейм** (аргументы, локальные переменные, адрес возврата) и снимает его при возврате; выделение — это одно перемещение указателя, а время жизни привязано к вызову. **Куча** (heap) — общая область для объектов, которые живут дольше создавшего их вызова; выделение идёт через аллокатор (`malloc` или bump-pointer TLAB в JVM), а освобождение — вручную (C) или сборщиком мусора (Java). **Переполнение стека** (stack overflow) происходит, когда фреймы превышают фиксированный размер стека, почти всегда из-за неограниченной рекурсии. Устройство памяти в JVM (поколения кучи, metaspace, TLAB) описано в [[jvm-memory-areas]].

## Основное

### Стек
- Один стек на поток, выделяется при старте потока: у главного потока в Linux по умолчанию 8 МиБ (`ulimit -s`), у остальных потоков в JVM 1 МиБ (`-Xss`); резервируется как виртуальная память и выделяется постранично при первом обращении ([[virtual-memory-and-paging]]).
- Фрейм содержит: параметры, локальные переменные, сохранённые регистры, адрес возврата и сохранённый указатель фрейма. Компилятор знает размер каждого фрейма на этапе компиляции, поэтому вход в функцию — это `sub rsp, N`, а выход — `add rsp, N; ret`.
- На x86 растёт вниз; **сторожевая страница** (guard page) под стеком не отображена, поэтому выход за неё вызывает ошибку страницы, а не тихую перезапись кучи. JVM перехватывает эту ошибку и бросает `StackOverflowError`.
- Дёшево и дружелюбно к кэшу: вершина стека почти всегда в L1 ([[cpu-caches-and-cache-lines]]). Нет фрагментации, нет синхронизации: каждый поток владеет своим стеком.
- Ограничения: фиксированный размер, время жизни привязано к вызову, нельзя вернуть указатель на локальную переменную (ошибка в C, невозможная в Java, потому что объекты никогда не лежат на стеке, если только их туда не поместит escape analysis JIT).

### Куча
- Одна на процесс, общая для всех потоков. В C ею управляют `malloc`/`free` поверх `brk`/`mmap`; в Java управляемая GC куча резервируется заранее (`-Xmx`), а объекты выделяются сдвигом указателя внутри буфера выделения потока (thread-local allocation buffer), поэтому `new` почти так же дёшев, как push на стек.
- Дорогое — в другом месте: поиск свободного места во фрагментированной куче C, а в Java — стоимость поддержания объектов живыми на протяжении циклов GC ([[garbage-collection]]). Короткоживущие объекты в поколенческом сборщике почти бесплатны; долгоживущие обходятся дорого на каждой полной сборке или сборке старого поколения.
- Общая — значит, нужна синхронизация: `malloc` использует арены на поток (glibc), чтобы избежать глобальной блокировки; JVM по той же причине использует TLAB. Медленный путь, когда TLAB исчерпан, делает CAS по общему указателю eden ([[lock-free-and-cas]]).
- Нативная память в процессе JVM — тоже куча в смысле ОС: metaspace, кэш JIT-кода, direct `ByteBuffer`, стеки потоков — всё это учитывается в лимите контейнера, хотя находится вне `-Xmx`.

### Сравнение
| | Стек | Куча |
|---|---|---|
| Владелец | один поток | весь процесс |
| Выделение | перемещение указателя, O(1) | аллокатор / сдвиг в TLAB; GC при освобождении |
| Время жизни | до возврата из функции | до освобождения или потери достижимости |
| Размер | фиксированный на поток (МиБ) | до `-Xmx` / объёма RAM |
| Отказ | `StackOverflowError` / `SIGSEGV` | `OutOfMemoryError` / `malloc` возвращает `NULL` / OOM killer |
| Потокобезопасность | изначально | нужна синхронизация |
| Локальность | отличная | зависит от характера выделений |

### Почему происходит переполнение стека
- Неограниченная или очень глубокая рекурсия: рекурсивный обход вырожденного дерева (в форме связного списка), рекурсивный маппинг в JSON сущности, ссылающейся на саму себя, цикл `toString()`/`hashCode()` между двумя JPA-сущностями ([[jpa-entities-and-relationships]]), Spring-бин, вызывающий сам себя через прокси ([[spring-aop]]).
- Большие фреймы: метод с большими локальными массивами в C; в Java локальные переменные — это ссылки, поэтому фреймы маленькие, но глубокие цепочки вызовов после инлайнинга JIT и очень длинные конвейеры лямбд/стримов могут их раздуть.
- Число потоков × размер стека: 5 000 платформенных потоков × 1 МиБ = 5 ГиБ зарезервировано; это не переполнение, но причина исчерпать адресное пространство или упереться в `ulimit -u`. Виртуальные потоки хранят свои фреймы в куче и наращивают их по мере надобности ([[virtual-threads]]).
- Решение: итерировать с явным `Deque` вместо рекурсии, ограничить глубину рекурсии или увеличить `-Xss` только для отдельного потока (`new Thread(group, task, name, stackSize)`), а не глобально ([[recursion-and-backtracking]]).

## Пример
```java
// Удаление дерева eSIM-профилей (родитель -> потомки) в глубину без рекурсии:
// явный стек в куче, ограниченный памятью, а не -Xss.
void deleteSubtree(UUID rootId) {
    Deque<UUID> stack = new ArrayDeque<>();
    stack.push(rootId);
    while (!stack.isEmpty()) {
        UUID id = stack.pop();                       // аналог фрейма: один UUID, а не фрейм метода
        for (UUID child : repo.childIds(id)) {
            stack.push(child);
        }
        repo.delete(id);
    }
}

// Рекурсивная версия короче и подходит для глубины < ~10 000,
// но испорченный цикл parent_id превращает её в StackOverflowError во время выполнения:
void deleteSubtreeRecursive(UUID id) {
    repo.childIds(id).forEach(this::deleteSubtreeRecursive);
    repo.delete(id);
}
```
Стек по умолчанию в 1 МиБ вмещает примерно 10–20 тысяч простых Java-фреймов; точное число зависит от JIT, поэтому один и тот же код может переполнить стек в холодном интерпретаторе и нормально работать после компиляции.

## Подводные камни
- Обращаться со `StackOverflowError` как с `Exception`: это `Error`, и после его перехвата поток остаётся в неизвестном состоянии; исправь рекурсию.
- Увеличивать `-Xss` глобально, чтобы «исправить» переполнение: каждый поток теперь резервирует больше виртуальной памяти, а настоящая ошибка (цикл) остаётся.
- Считать, что Java-объекты всегда живут в куче: escape analysis может заменить неубегающий объект скалярами; бенчмарки, которые «измеряют выделение», могут быть оптимизированы до нуля ([[jvm-memory-areas]]).
- Путать кучу ОС с кучей Java, когда контейнер убит OOM: `-Xmx` в пределах лимита, но direct-буферы (`Netty`, клиент Kafka) и metaspace вытолкнули RSS за `limits.memory`.
- В C — возвращать адрес локальной переменной или использовать `alloca`/VLA с размером, который задаёт пользователь: и то и другое — ошибки порчи стека, которые Java предотвращает by design.
- Связанные заметки: [[virtual-memory-and-paging]] — как обе области обеспечиваются страницами, [[processes-and-threads]] — почему каждому потоку нужен свой стек.
