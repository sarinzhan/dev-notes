## Кратко
[[anatomy-of-a-process]] показывает, как один процесс выглядит в памяти; эта заметка — о том, как ядро **управляет многими процессами**. Для каждого процесса оно хранит **блок управления процессом** (PCB) в **таблице процессов** ядра; для каждого потока — **блок управления потоком** (TCB). **Поток** — это облегчённый процесс: он делит код, кучу, данные, открытые файлы и таблицу страниц и владеет только своим стеком, счётчиком команд и регистрами. CPU ничего не знает о процессах; ОС загружает в него регистры процесса и указатель на таблицу страниц (его **контекст**), а **переключение контекста** сохраняет один контекст в его PCB и загружает другой. Переключение между процессами ещё и делает TLB недействительным, если записи не помечены **ASID/PCID**, поэтому переключать потоки одного процесса дешевле. **Планировщик** решает, какой поток на каком ядре и сколько выполняется: с вытеснением, квантами времени, отдавая предпочтение потокам, ждущим ввода-вывода, когда они просыпаются. Много процессов или потоков дают изоляцию или конкурентность, а вместе с общей памятью приходит и цена — **состояния гонки**.

## Основное
### Что ядро хранит для процесса: PCB
- Ядру нужны метаданные о каждом процессе. **Блок управления процессом** (`task_struct` в Linux) содержит:

| Поле | Что это |
|---|---|
| PID, PID родителя, состояние | идентификатор и текущее состояние (выполняется, готов, заблокирован, остановлен, зомби) |
| Сохранённые счётчик команд и регистры | где продолжить и с какими значениями, пока процесса нет на CPU |
| Управляющая информация | приоритет, значение nice, класс планирования, привязка к CPU |
| Указатель на таблицу страниц | значение, которое загружается в регистр базы таблицы страниц при запуске ([[memory-management]]) |
| Информация об управлении памятью | где его код, данные, куча и стеки (`mm_struct`, список отображений) |
| Учёт | использованное время CPU, память, page faults, число переключений контекста — то, что показывают `ps`, `top` и `/proc/<pid>/status` |
| Информация о вводе-выводе | таблица файловых дескрипторов: файлы, сокеты, каналы ([[syscalls-and-file-descriptors]]) |
| Информация об IPC | семафоры, сегменты разделяемой памяти, очереди сообщений; обработчики сигналов и ожидающие сигналы |
| Учётные данные, cgroups, пространства имён | пользователь и группа, лимиты ресурсов, в каком контейнере процесс |
- **Таблица процессов** отображает каждый PID на его PCB для быстрого поиска. Она лежит в пространстве ядра; пользовательские программы видят её только через `/proc`.
- Само **адресное пространство** приватно: MMU не даёт процессу читать чужую память, если оба не отобразили разделяемый сегмент ([[ipc-mechanisms]]).

### Потоки и TCB
- **Поток** — облегчённый процесс: независимый поток выполнения внутри процесса. Потоки одного процесса делят код, кучу, секцию данных, открытые файлы и таблицу страниц; у каждого потока **свой стек** (в том же адресном пространстве, ниже главного стека) и свои **счётчик команд и регистры**.
- Для каждого потока ядро хранит **блок управления потоком**: TID, состояние, сохранённые PC и регистры, указатель стека, приоритет, учёт CPU и указатель на PCB родительского процесса. **Таблица потоков** отображает TID на TCB.
- В Linux отдельного TCB нет: каждый поток — это `task_struct`, созданный `clone()` с общими с родителем адресным пространством (`mm`), таблицей файлов и обработчиками сигналов. «Процесс» — просто группа задач с общим `mm`; планировщик всегда планирует задачи. `ls /proc/<pid>/task` показывает потоки процесса.

### Процесс и поток
| | Процесс | Поток |
|---|---|---|
| Память | собственное адресное пространство | общая с процессом |
| Стоимость создания | высокая (`fork` копирует таблицы страниц, страницы копируются при записи) | низкая (`clone` с общей VM; только новый стек и регистры) |
| Переключение контекста | сохранить регистры + переключить таблицы страниц → сброс TLB (смягчается PCID/ASID) | сохранить регистры + переключить указатель стека; TLB остаётся валидным |
| Изоляция отказов | падение убивает только этот процесс | один segfault или непойманная нативная ошибка убивает все потоки |
| Взаимодействие | IPC: каналы, сокеты, разделяемая память | обычная память; нужна синхронизация ([[race-conditions-and-critical-sections]]) |
| Типичное применение | воркеры NGINX, бэкенды Postgres, вкладки Chrome | обработчики запросов Tomcat, IO-потоки клиента Kafka, рабочие потоки GC |

### Многопроцессные и многопоточные серверы
- **Многопроцессный**: программа запускает несколько изолированных друг от друга процессов. **NGINX** запускает по воркеру на ядро; **Postgres** создаёт через fork по процессу-бэкенду на каждое соединение. Падение или порча памяти остаются в одном процессе; цена — больше памяти, создание процессов и IPC для всего общего. Поэтому соединения с Postgres дорогие и нуждаются в пуле ([[hikaricp-pool-sizing]]).
- **Многопоточный**: один процесс запускает много потоков, которые делят его память. **MySQL** держит поток на соединение; **libuv** (Node.js) использует пул потоков для файлового IO и DNS; JVM — один процесс со многими потоками. Дешевле, и разделение данных бесплатно, но одно нативное падение или нехватка памяти роняет всё, а общие данные требуют синхронизации.
- Обоим видам серверов нужно делить один слушающий порт между воркерами: унаследовав слушающий сокет через `fork` или с помощью сокетов `SO_REUSEPORT`. Как это работает — в [[socket-management]].
- **Fork** создаёт новый процесс: у потомка должна быть своя виртуальная память, но благодаря copy-on-write страницы общие, пока одна из сторон не запишет. Именно так Redis обеспечивает асинхронную долговечность (`BGSAVE`). Подробности и анимация — в [[memory-management]]; жизненный цикл (`exec`, `wait`, зомби) — в [[signals-and-process-lifecycle]].

- **Postgres и процессная модель.** Каждое соединение — отдельный порождённый бэкенд, поэтому `max_connections` по умолчанию — 100, а тысячи соединений — плохая идея: тысячи процессов, таблиц страниц и сбросов TLB. Приложения ставят перед базой пул (HikariCP в приложении, PgBouncer между приложениями и базой) и делят несколько соединений между многими пользователями. Помимо бэкендов, Postgres запускает вспомогательные процессы: checkpointer, background writer, WAL writer, autovacuum launcher и воркеры, logger, archiver и воркеры параллельных запросов.
- В 2023 году разработчики Postgres начали долгое обсуждение перехода на потоки. Один из аргументов: на больших машинах с множеством соединений переключение между процессами стоит дороже, чем между потоками одного процесса, и заметная часть этого времени уходит на промахи TLB, которых процессная модель избежать не может. Контраргументы — объём работы (глобальные переменные по всему коду) и потеря изоляции при падениях. Вопрос всё ещё открыт.
- **Конвейер на соединении с базой**: режим pipeline в Postgres (libpq, Postgres 14+; драйвер JDBC так же делает пакеты) позволяет клиенту отправить несколько запросов без ожидания. Результаты возвращаются **в том порядке, в каком отправлены запросы**, так что клиент сопоставляет их по позиции; идентификаторов запросов нет (в лекции предполагается, что есть). Медленный первый запрос задерживает остальные — та же блокировка начала очереди (head-of-line blocking), что и в конвейере HTTP/1.1 ([[cpu]]).
- **Потоки меняют изоляцию на скорость.** Все потоки процесса делят кучу, поэтому ошибочный или скомпрометированный поток может прочитать или перезаписать данные любого другого; ядро их ничем не разделяет. Выполнить внедрённый код мешают не потоки, а права доступа к памяти: куча и стеки не исполняемые, код недоступен для записи ([[anatomy-of-a-process]]).

### Смотрим fork и copy-on-write: `smaps`
Демонстрация из лекции: программа на C делает `malloc` на 10 MB, записывает их через `memset` (до этого у страниц нет фреймов, и RSS остаётся маленьким), вызывает fork, и оба процесса крутятся в бесконечном цикле.

```bash
top -p 999,1000                      # RES ~10 MB у обоих: выглядит как 20 MB в сумме
grep -A 20 heap /proc/999/smaps      # одно отображение процесса подробно
#   Rss:            10244 kB
#   Pss:             5122 kB          <- пропорционально: общие страницы делятся на число владельцев
#   Shared_Clean:       0 kB
#   Shared_Dirty:   10240 kB          <- записаны до fork, теперь отображены и у родителя, и у потомка
#   Private_Clean:      0 kB
#   Private_Dirty:      4 kB          <- страницы, которые отображает только этот процесс
cat /proc/999/smaps_rollup           # те же итоги по всему процессу
```

- **Dirty** значит, что в страницу писали; **clean** — что она всё ещё совпадает с источником (файлом или вообще не тронута). **Shared**-страницы отображены более чем одним процессом; **private** — только этим.
- Во второй версии потомок пишет по байту через каждые 1 000 байт (через каждые 4 096 каждая страница затрагивалась бы ровно один раз). С каждым обновлением `Private_Dirty` потомка растёт, а `Shared_Dirty` уменьшается: каждая записанная страница копировалась для потомка, а оригинал становился приватным для родителя.
- **RSS дважды учитывает общие страницы**; сумма RSS по 20 форкнутым воркерам может показать в несколько раз больше реальной RAM. **Pss** даёт каждому процессу его долю, поэтому сумма Pss — настоящий итог. `smem` показывает его по процессам.

### Разделяемая память
- Процессы и потоки могут разделять память. Потоки разделяют всё адресное пространство автоматически. Отдельные процессы разделяют её, отображая одни и те же физические страницы: `mmap(MAP_SHARED)` или `shm_open`. **Виртуальные** адреса у процессов могут отличаться; **физические** страницы одни и те же.
- Классический пример — **общие буферы** базы данных: каждый процесс-бэкенд Postgres подключается к одному сегменту `shared_buffers`, так что страница, прочитанная одним соединением, лежит в памяти для всех ([[postgres-performance-checklist]]).

### CPU и контекст
- CPU не знает, что такое процесс. ОС загружает данные процесса в регистры CPU: pc, sp, bp, lr, регистры общего назначения и указатель на его таблицу страниц (регистр базы таблицы страниц, ptbr: CR3 на x86, TTBR на ARM). Этот набор называется **контекстом**. Дальше CPU просто выполняет инструкции.
- **Переключение контекста** сохраняет текущий контекст в PCB текущего процесса (запись в память) и загружает PCB следующего процесса в регистры (чтение из памяти): pc, bp, sp, lr, ptbr и другие. Снятый процесс становится **готовым**, новый — **выполняющимся**.
- Когда это происходит: закончился квант (прерывание таймера), поток заблокировался (IO, блокировка, `sleep`), проснулся поток с более высоким приоритетом или поток завершился.

- Регистр базы таблицы страниц должен хранить **физический** адрес: будь он виртуальным, для его трансляции понадобилась бы та самая таблица, на которую он указывает. Копия PC в PCB устаревает, пока процесс выполняется; актуальный PC есть только в CPU и записывается обратно при переключении.

### Сброс TLB и ASID
- **TLB** кэширует трансляции виртуальных адресов в физические. Процессы не могут делить эти отображения: виртуальный адрес 4000 у процесса 100 означает одну физическую страницу, а у 200 — другую. Поэтому при переключении на другой процесс TLB нужно **сбросить**, и новый процесс промахивается на первых обращениях к памяти и платит обходами таблицы страниц. Это медленно и обычно дороже, чем сохранение регистров.
- **Потоки одного процесса переключаются быстрее**: та же память, та же таблица страниц, TLB остаётся валидным. Но только пока оба потока принадлежат одному процессу.
- **ASID** (address space ID на ARM) и **PCID** (process-context ID на x86) помечают каждую запись TLB процессом, которому она принадлежит, так что записи нескольких процессов живут рядом, и переключение не требует сброса. Метки маленькие (8 или 16 бит на ARM, 12 на x86), поэтому ядро переиспользует их и сбрасывает TLB, только когда они заканчиваются.
- Защита от Spectre/Meltdown (изоляция таблиц страниц) сделала дороже само переключение пользователь↔ядро; именно PCID делает его терпимым.

- В лекции высказаны сомнения, что ASID практичны при таком малом числе бит и таком множестве процессов. Ядро решает это поколениями: раздаёт метки, пока они не кончатся, затем один раз сбрасывает весь TLB, начинает новое поколение и заново раздаёт метки по мере выполнения процессов. Устаревшие записи давно не работавшего процесса просто вытесняются новыми. Linux использует PCID на x86 начиная с 4.14 и ASID на ARM64.

### Стоимость переключения контекста
- Прямая стоимость: переход в ядро, сохранение и восстановление регистров, учёт в планировщике. Обычно 1–3 мкс на современном железе ([[latency-numbers]]).
- Косвенная стоимость, обычно бо́льшая: рабочего набора нового потока нет в L1/L2, TLB и предсказатель переходов холодные ([[cpu-caches-and-cache-lines]]). Поток, который блокируется после каждых нескольких микросекунд работы, тратит на переключения больше времени, чем на работу.
- `vmstat 1` показывает переключения контекста в секунду в столбце `cs`; `pidstat -w` показывает по процессам добровольные (блокировка на IO или блокировке) и принудительные (истёк квант, вытеснение) переключения. Много принудительных — конкуренция за CPU; много добровольных — ожидание IO или блокировок.

### Состояния процессов и потоков
- `New → Ready → Running → (Blocked ↔ Ready) → Terminated`. «Заблокирован» — нормальное состояние серверного потока: ожидание сокета, блокировки или чтения с диска. Running → Ready — это вытеснение; Running → Blocked — поток сам отдаёт CPU.
- В `ps`: `R` выполняется или готов, `S` спит (прерываемо), `D` непрерываемый сон (обычно дисковый IO), `T` остановлен, `Z` зомби ([[linux-processes]]).
- `Thread.State` в Java соответствует им приблизительно: `RUNNABLE` покрывает и выполнение, и готовность с точки зрения ОС (и даже блокировку в нативном IO), `BLOCKED` — ожидание монитора, `WAITING`/`TIMED_WAITING` — поток припаркован ([[threads-basics]]).

### Вытесняющая многозадачность
- Некоторые процессы работают долго. В **кооперативной** многозадачности программа держит CPU, пока сама не уступит; та, что никогда не уступает, морит голодом всех остальных — так одна зависшая программа замораживала Windows 3.1 или классическую Mac OS.
- В **вытесняющей** многозадачности ОС снимает такие процессы: каждые несколько миллисекунд срабатывает прерывание таймера, и когда **квант** потока израсходован, ядро забирает у него CPU. Так работает любое современное ядро.
- Многие планировщики в пространстве пользователя всё ещё кооперативные: Java [[virtual-threads]], event loop в JavaScript, Go до 1.14. Виртуальный поток, крутящийся в цикле на CPU, блокирует свой поток-носитель (carrier) и лишает CPU другие виртуальные потоки на нём.
- Для серверов путь пробуждения важнее кванта: поток запроса заблокирован на сокете, просыпается, когда приходят данные, работает несколько сотен микросекунд и снова блокируется. **Задержка планирования** — время между пробуждением и фактическим запуском.

### Алгоритмы планирования
- Планировщик решает, какой процесс или поток получает какое ядро CPU и на сколько. На эту тему написано множество статей; трудно быть одновременно справедливым, быстрым и отзывчивым. Он также предпочитает запускать потоки одного процесса на одном ядре или хотя бы там, где их кэши тёплые.
- Цели: пропускная способность (работа в секунду), задержка (время от пробуждения до запуска), справедливость и соблюдение приоритетов. Максимизировать все четыре нельзя: длинные кванты помогают пропускной способности (меньше переключений, тёплые кэши), но ухудшают задержку.

| Алгоритм | Идея | Проблема |
|---|---|---|
| FCFS | выполнять в порядке поступления | одна длинная задача задерживает всех (эффект конвоя) |
| SJF / SRTF | сначала самая короткая задача | нужно знать длину задачи; длинные задачи голодают |
| Round-robin | фиксированный квант, по кругу по очереди готовых | квант слишком мал → накладные расходы на переключение; слишком велик → задержка |
| Приоритетный | сначала самый высокий приоритет | голодание, если приоритеты не «стареют» |
| Многоуровневая очередь с обратной связью | понижать задачи, жадные до CPU, повышать интерактивные | эвристики, настройка |
| CFS (Linux 2.6.23–6.5) | выбрать задачу с наименьшим виртуальным временем выполнения (красно-чёрное дерево); вес по nice | нет понятия дедлайна для задач, чувствительных к задержке |
| EEVDF (Linux 6.6+) | веса CFS плюс виртуальные дедлайны для каждой задачи; выбирает допустимую задачу с самым ранним дедлайном | новее, меньше настроек |

### Нагрузка на CPU и на ввод-вывод
- **CPU-bound** работа в основном использует процессор: шифрование (TLS), сжатие, планирование запросов, сортировка, разбор протоколов (HTTP/2, QUIC), сериализация JSON. Она использует каждый полученный квант; планировщик должен следить, чтобы она не голодала и не морила голодом других.
- **IO-bound** работа в основном ждёт: запросы к базе данных, чтение и запись в сеть, чтение и запись файлов. Она работает недолго и блокируется. Справедливый планировщик вознаграждает её быстрыми пробуждениями, потому что она мало использовала CPU.
- Следствие для размеров пулов: для вычислений пул ≈ числу ядер (больше потоков лишь добавляет переключений); для ввода-вывода пулы могут быть гораздо больше, либо стоит взять виртуальные потоки или неблокирующий IO ([[executors-and-thread-pools]], [[socket-management]]).

- **Конкурентность и параллелизм**: конкурентные задачи выполняются в один период и по очереди, как два потока на одном ядре или два аппаратных потока при hyper-threading; параллельные задачи буквально выполняются в один и тот же момент на разных ядрах. Конкурентность прячет ожидание, параллелизм добавляет вычислений.
- Каждое TLS-соединение тратит CPU на обоих концах, так что «просто открыть ещё одно соединение» никогда не бесплатно. Даже уменьшение TLS имеет цену в CPU: сжатие сертификатов (RFC 8879) экономит несколько КБ на рукопожатие, но клиенту нужно распаковывать, а вредоносный сервер может прислать «бомбу» распаковки, поэтому применяют его осторожно.
- libuv (Node.js) выполняет файловый ввод-вывод на пуле из 4 потоков по умолчанию (`UV_THREADPOOL_SIZE`), потому что чтение обычных файлов блокирует; `io_uring` может сделать его асинхронным без потоков.

### Что в Linux можно наблюдать
- Классы планирования: `SCHED_OTHER` (обычный, CFS/EEVDF), `SCHED_BATCH`, `SCHED_IDLE` и классы реального времени `SCHED_FIFO`/`SCHED_RR` (фиксированные приоритеты 1–99, вытесняют всё обычное; используются в аудио и некоторых торговых системах, опасны тем, что крутящийся RT-поток может занять ядро намертво).
- `nice` от -20 до 19 отображается на вес: каждый шаг — примерно 1,25× доли CPU; nice 0 получает примерно в 10 раз больше, чем nice 10. Это меняет долю только при конкуренции; на простаивающей машине процесс с nice 19 работает на полной скорости.
- Очереди готовых задач на каждый CPU с периодической балансировкой и миграцией; планировщик предпочитает держать задачу на ядре, где её кэш тёплый. `taskset`/`sched_setaffinity` привязывает потоки к ядрам.
- Квант не фиксирован: целевая задержка (`sched_latency`, ~6 мс × log(ядер)) делится между готовыми задачами, с минимальной гранулярностью (~0,75 мс). Больше готовых потоков → меньше кванты → больше переключений.

### Средняя нагрузка
- `uptime` / `/proc/loadavg`: экспоненциально сглаженные средние за 1, 5 и 15 минут числа задач, которые **выполняются или готовы к выполнению**, плюс, только в Linux, задач в **непрерываемом сне** (`D`, обычно дисковый или NFS IO).
- Эмпирическое правило: нагрузка ≈ числу ядер означает насыщение; нагрузка 8 на 4 ядрах означает, что в среднем 4 задачи ждут CPU или застряли в IO. Чтобы понять, что именно, сравнивайте с `%iowait` и `%steal` в `vmstat`/`mpstat`.
- JVM с 200 потоками и нагрузкой 1,5 — это нормально: заблокированные потоки (`S`) не считаются.

### Cgroups и контейнеры
- `cpu.max = 100000 100000` (Kubernetes `limits.cpu: 1`) — это **квота на период 100 мс**, а не ядро. Многопоточная JVM может сжечь свои 100 мс за первые 20 мс на 8 потоках, а затем быть **затроттлена** на 80 мс; p99 задержки взрывается, хотя средний CPU выглядит низким. Смотрите `nr_throttled` в `cpu.stat`.
- `cpu.weight` (requests) — пропорциональное распределение, как nice, только при конкуренции.
- JVM читает лимиты cgroup начиная с JDK 10: `availableProcessors()`, число потоков GC и размеры пулов по умолчанию следуют лимиту ([[docker-containers-and-resources]], [[kubernetes-basics]]).

### Потоки пользовательского уровня и потоки ядра
| Модель | Кто планирует | Блокирующий системный вызов | Примеры |
|---|---|---|---|
| 1:1, потоки ядра | ядро | блокирует только этот поток | Linux NPTL, платформенные потоки JVM |
| N:1, пользовательские потоки (green threads) | библиотека в пространстве пользователя | блокирует весь процесс | ранние JVM, классические библиотеки корутин |
| M:N | оба: библиотека мультиплексирует M пользовательских потоков на N потоков ядра | библиотека должна перехватывать блокирующие вызовы и вместо них парковать пользовательский поток | горутины Go, Java [[virtual-threads]] (JDK 21) |
- Платформенные потоки Java — 1:1: `new Thread().start()` заканчивается в `clone()`, и их видно через `top -H -p <pid>` или `ls /proc/<pid>/task`. Виртуальные потоки — M:N поверх `ForkJoinPool` из потоков-носителей; JDK снимает их с носителя на блокирующем IO и `LockSupport.park`, но **закрепляет** (pinning) на `synchronized` (исправлено в JDK 24) и в нативных фреймах.
- Почему M:N вернулась: поток ядра стоит около 1 МиБ зарезервированного стека плюс `task_struct`, и десятки тысяч таких потоков замедляют планировщик. Стек виртуального потока — от нескольких сотен байт до нескольких КиБ в куче ([[jvm-memory-areas]]).

### Проблемы конкурентности
- Вместе с конкурентностью приходят трудности: **два потока работают с одной переменной** (потокобезопасность) или **два процесса пишут в одну разделяемую память**.
- `a++` — это три шага: загрузить `a` в регистр, прибавить 1, записать обратно. Если два потока чередуются (T1 читает 1, T2 читает 1, оба прибавляют, оба записывают 2), одно увеличение теряется: это **состояние гонки**. Каждый поток держал свою копию в своих регистрах, которые сохраняются в его TCB при переключениях.
- Решения: сделать чтение-изменение-запись неделимым с помощью мьютекса (`synchronized`, `ReentrantLock`, мьютекс для процессов в разделяемой памяти) или атомарной инструкции (`lock xadd`, compare-and-swap, `AtomicInteger`) ([[race-conditions-and-critical-sections]], [[lock-free-and-cas]]). У блокировок свои проблемы: конкуренция и взаимоблокировки ([[deadlocks-and-synchronization-primitives]]).

- **У мьютекса есть владелец**: разблокировать его может только поток, который его заблокировал. Если этот поток погибнет, удерживая его, мьютекс может остаться заблокированным навсегда, и все ожидающие попадут в дедлок. *Робастные* (robust) мьютексы POSIX вместо этого сообщают следующему захватывающему `EOWNERDEAD`. В Java `synchronized` освобождается автоматически даже при исключении; `ReentrantLock` освобождается только вызовом `unlock()`, поэтому он всегда стоит в `finally`.
- **Семафор** — просто счётчик с операциями `wait` (уменьшить, заблокироваться на нуле) и `signal` (увеличить); владельца у него нет, поэтому сигналить может любой поток. Инициализированный единицей, он ведёт себя как мьютекс без проверок владения ([[deadlocks-and-synchronization-primitives]]).
- Базы данных освобождают блокировки строк при завершении транзакции и никогда не берут новую блокировку после освобождения: это **двухфазная блокировка** (фаза роста, затем фаза сокращения при commit или rollback). В лекции это названо двухфазным коммитом — но это другой протокол, для фиксации сразу в нескольких базах.

## Пример
```bash
# Приложение на Spring Boot: один процесс, много потоков ядра
PID=$(pgrep -f 'esim-provisioning.jar')
ls /proc/$PID/task | wc -l          # число потоков (задач ядра)
grep -E 'Threads|VmRSS|voluntary' /proc/$PID/status
#   VmRSS:      812 004 kB
#   Threads:  57
#   voluntary_ctxt_switches:    183 214   <- блокировки на IO или замках
#   nonvoluntary_ctxt_switches:   1 042   <- вытеснения: конкуренция за CPU небольшая

# CPU по потокам: какие потоки JVM горячие?  (nid в дампе jstack = TID в hex)
top -H -p $PID -n 1 | head -20
printf '%x\n' 12345                 # перевести TID в nid, который показывает jstack

# Сервис медленный из-за планирования CPU?
mpstat -P ALL 1 3            # %usr %sys %iowait %steal по ядрам
cat /proc/loadavg            # 7.80 6.90 5.10 3/612 41233  -> 3 готовых из 612 задач
pidstat -w -t -p $PID 1 3    # cswch/s (добровольные)  nvcswch/s (принудительные) по потокам

# Троттлинг контейнера (cgroup v2, внутри pod)
cat /sys/fs/cgroup/cpu.max          # 100000 100000  -> квота 1 CPU
cat /sys/fs/cgroup/cpu.stat
#   nr_periods 48211  nr_throttled 9120  throttled_usec 712003000
# 19% периодов затроттлены: поднимите лимит или ограничьте потоки JVM
#   (-XX:ActiveProcessorCount, пулы поменьше), либо уберите лимит CPU и оставьте request.

# Понизить приоритет пакетной переиндексации, чтобы потоки запросов выигрывали при конкуренции
nice -n 15 java -jar reindex.jar
```
Строка дампа потоков вида `"kafka-producer-network-thread" ... nid=0x3039` указывает на задачу ядра 12345: это один и тот же поток, увиденный ОС и JVM. Растущий `nr_throttled` при `%usr` узла намного ниже 100% — признак слишком жёсткого лимита CPU для JVM с всплесками нагрузки.

## Подводные камни
- Складывать RSS форкнутых воркеров (бэкенды Postgres, воркеры gunicorn или nginx), чтобы рассчитать память: общие страницы учитываются в каждом процессе. Используйте Pss из `smaps_rollup` или `smem`.
- Считать потоки бесплатными: каждый платформенный поток резервирует `-Xss` (по умолчанию 1 МиБ) виртуальной памяти и структуру ядра; архитектура «поток на запрос» умирает на нескольких тысячах одновременных запросов. Используйте ограниченный пул ([[executors-and-thread-pools]]) или виртуальные потоки.
- Забывать, что переключение процессов стоит сброса TLB (или расхода ASID): архитектура, которая гоняет каждый запрос через несколько локальных процессов (sidecar, локальные прокси), платит за это на каждом переходе.
- Измерять только загрузку CPU: сервис с 20% CPU и огромным `cs` упирается в ожидание блокировок или IO, а не в вычисления. Проверьте `pidstat -w`, прежде чем добавлять ядра.
- Читать среднюю нагрузку как загрузку CPU. Нагрузка 12 на 16 ядрах — это нормально; нагрузка 4 на 2 ядрах при 5% CPU — это ожидание IO, а не вычисления.
- Ставить в Kubernetes лимиты CPU равными requests для JVM «ради предсказуемости»: GC и JIT-компиляция работают всплесками и троттлятся именно тогда, когда важна задержка. Многие команды задают requests без лимитов или лимиты в 2–4 раза больше requests.
- Подбирать размер пулов потоков по `Runtime.availableProcessors()` в контейнере в host-режиме без лимитов: получаете 64 ядра хоста и 64-поточный GC в pod, который должен использовать 2.
- Использовать `Thread.setPriority()` в Java и ждать эффекта: в Linux JVM это игнорирует, если не запущена с `-XX:ThreadPriorityPolicy=1` от root. Используйте `nice`/cgroups на уровне ОС.
- Планирование реального времени «для низкой задержки»: поток `SCHED_FIFO`, который никогда не блокируется, делает ядро непригодным для всего остального, включая SSH.
- `ps` показывает процесс в состоянии `R`, хотя все потоки JVM, кроме GC, могут быть припаркованы: состояние процесса — сводка по его потокам.
