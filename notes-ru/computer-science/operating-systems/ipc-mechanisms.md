## Кратко
У процессов раздельные адресные пространства, поэтому они общаются через ядро: **каналы** (pipes; поток байтов между родителем и потомком или между командами shell), **Unix domain sockets** (двунаправленные, в пределах хоста, их используют Docker, Postgres и большинство sidecar), **TCP-сокеты** (тот же API между хостами), **разделяемая память** (shared memory; самая быстрая, без копирований, но синхронизацию приносишь сам), **очереди сообщений** и **сигналы** (небольшие уведомления). Выбор определяется связанностью, скоростью и тем, может ли другая сторона оказаться на другой машине. Почти любая бэкенд-система, с которой ты работаешь, — это межпроцессное взаимодействие (IPC): JDBC-соединение, клиент Kafka, экспортёр OTel, `docker.sock`. Внутри одного процесса потоки просто разделяют память ([[process-management]]); между сервисами по сети это превращается в [[service-communication-sync-vs-async]].

## Основное

### Механизмы
| Механизм | Направление | Область | Модель данных | Копирования | Типичное применение |
|---|---|---|---|---|---|
| Анонимный канал (`pipe()`) | одностороннее | родственные процессы (fork) | поток байтов, буфер 64 КиБ | 2 (пользователь→ядро→пользователь) | shell `a \| b`, stdin/stdout в `ProcessBuilder` |
| Именованный канал (FIFO) | одностороннее | один хост, по пути | поток байтов | 2 | пересылка логов между несвязанными демонами |
| Unix domain socket | двустороннее | один хост, по пути | поток или датаграммы, можно передавать fd и учётные данные | 2 | `/var/run/docker.sock`, Postgres `/var/run/postgresql/.s.PGSQL.5432`, socket activation в systemd, sidecar Envoy/Istio |
| TCP/UDP-сокет | двустороннее | любой хост | поток / датаграммы | 2 + сетевой стек | всё удалённое: HTTP, gRPC, Kafka, JDBC поверх TCP |
| Разделяемая память (`shm_open`+`mmap`, SysV `shmget`) | n-стороннее | один хост | сырые байты | 0 | shared buffers Postgres между бэкендами, рендерер Chrome ↔ GPU, Aeron/Chronicle в трейдинге |
| Файл, отображённый в память (memory-mapped file) | n-стороннее | один хост | сырые байты, сохраняются | 0 (page cache) | сегменты лога Kafka, Lucene, `MappedByteBuffer` |
| Очередь сообщений POSIX/SysV | n-стороннее | один хост | отдельные сообщения с приоритетом | 2 | редко в современных бэкендах; заменены брокерами |
| Сигналы | одностороннее | один хост | число (плюс `siginfo`) | 0 | `SIGTERM`, перезагрузка конфигурации по `SIGHUP` ([[signals-and-process-lifecycle]]) |
| eventfd / futex | одностороннее | один хост | счётчик | 0 | пробуждения между потоками/процессами; Netty, блокировки JVM |
| D-Bus / gRPC поверх UDS | двустороннее | один хост | типизированный RPC | 2 | десктопные сервисы; плагины CRI/CSI в Kubernetes общаются с kubelet через UDS |

### Потоки против сообщений
- Каналы и потоковые сокеты доставляют **байты**, а не сообщения: два вызова `write(100)` могут прийти одним `read(200)` или тремя частичными чтениями. Любому протоколу поверх нужно кадрирование (framing): префикс длины (gRPC, Kafka, wire-протокол Postgres), разделитель (заголовки HTTP/1.1, JSON с разделением переводом строки) или фиксированный размер ([[http-fundamentals]], [[grpc-and-protobuf]]).
- Датаграммные сокеты и очереди сообщений сохраняют границы; UDP вдобавок теряет и переупорядочивает ([[tcp-vs-udp]]).
- Атомарность канала: записи до `PIPE_BUF` (4 КиБ) атомарны, поэтому многие процессы могут дописывать отдельные строки лога в один канал без перемешивания, но более длинные строки могут перемешаться.

### Unix domain sockets против TCP на localhost
- Тот же API `socket()`/`connect()`/`read()`, поэтому клиентская библиотека часто поддерживает оба варианта (`jdbc:postgresql://localhost/db` против пути UDS через `socketFactory`).
- UDS обходит стек TCP/IP: нет контрольных сумм, маршрутизации через loopback, номеров портов, пропускная способность ~в 2 раза выше и задержка ниже для небольших сообщений; через него ядро может передавать **файловые дескрипторы** (`SCM_RIGHTS`) и uid/pid собеседника (`SO_PEERCRED`) — так Docker авторизует клиентов по членству в группе на `docker.sock` ([[docker-socket-dind-dood]]).
- Контроль доступа — это права файловой системы на путь, а не правила файрвола. Sidecar в Kubernetes и плагины CNI/CSI используют UDS, смонтированные через `hostPath`/`emptyDir`.

### Разделяемая память: самая быстрая и самая опасная
- Ядро отображает одни и те же физические страницы в два адресных пространства; после этого общение — это запись в память без системного вызова. Пропускная способность ограничена пропускной способностью памяти, задержка — когерентностью кэшей ([[cpu-caches-and-cache-lines]]).
- Синхронизация в комплект не входит: нужен мьютекс или семафор в разделяемом сегменте (`PTHREAD_PROCESS_SHARED`) или lock-free кольцевой буфер с барьерами памяти ([[lock-free-and-cas]], [[memory-models-and-visibility]]). Упавший писатель может оставить структуру наполовину обновлённой; устойчивые мьютексы (robust mutexes) существуют именно для этого.
- Как устроено отображение и где оно используется (`shared_buffers` в Postgres, зоны NGINX, `/dev/shm` из Java, `fork`) — в [[memory-management]].

### Как выбрать
- Родитель–потомок, одно направление: канал (`ProcessBuilder`). Один хост, несвязанные процессы: Unix domain socket; TCP на localhost — только если собеседник может переехать на другой хост. Один хост, большой объём и низкая задержка: разделяемая память с кольцевым буфером. Разные хосты: TCP, а затем выбор протокола ([[service-communication-sync-vs-async]], [[message-queues-and-streams]]).

## Пример
```bash
# 1. Каналы: анонимный канал — это просто два fd
strace -e trace=pipe2,dup2,clone,execve sh -c 'ps aux | grep java' 2>&1 | head -6
#   pipe2([3, 4], 0) = 0
#   clone(...) = 5120                 <- ps:   dup2(4, 1), затем execve
#   clone(...) = 5121                 <- grep: dup2(3, 0), затем execve

# 2. Unix domain sockets на типичном узле
ss -xlp | grep -E 'docker|postgres|otel'
#   u_str LISTEN 0 4096 /var/run/docker.sock 23011 * 0  users:(("dockerd",pid=1210,fd=5))
#   u_str LISTEN 0 224 /var/run/postgresql/.s.PGSQL.5432 ... users:(("postgres",pid=2231,fd=6))

# 3. Разделяемая память: кто подключён к сегменту Postgres?
ls -l /dev/shm | head            # объекты POSIX shm (PostgreSQL.xxxx, otel, perf data JVM)
ipcs -m                           # сегменты SysV, столбец nattch = подключённые процессы
grep -E 'Shmem|Mapped' /proc/meminfo
```
`ls /proc/<pid>/fd -l` показывает те же категории для одного процесса: `pipe:[inode]`, `socket:[inode]`, а отображения `/dev/shm/...` видны в `/proc/<pid>/maps` ([[syscalls-and-file-descriptors]]).

## Подводные камни
- Читать только stdout дочернего процесса: когда заполняется его канал stderr (64 КиБ), потомок блокируется на `write`, и твой `waitFor()` зависает навсегда. Используй `redirectErrorStream(true)` или вычитывай оба.
- Считать потоковый сокет основанным на сообщениях: «локально работало», потому что на loopback небольшие записи редко разбиваются; ломается под нагрузкой или по сети. Всегда используй кадрирование.
- Монтировать `docker.sock` в контейнер для удобства: кто может писать в этот сокет, тот root на хосте; это IPC без авторизации, кроме прав на файл.
- Разделяемая память без владельца, отвечающего за очистку: сегменты SysV и файлы в `/dev/shm` переживают создавшие их процессы и тихо занимают RAM до перезагрузки (`ipcrm` или `shm_unlink`).
- Именованные каналы с одним читателем и многими писателями при записях больше `PIPE_BUF`: на выходе перемешанный мусор.
- Связанные заметки: [[sockets-and-connection-pooling]] — подробно про TCP-вариант, [[socket-management]] — ожидание на многих таких fd одновременно.
