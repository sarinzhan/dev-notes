## Кратко
**Программа** — это файл на диске: машинный код плюс описание того, как разложить его в памяти. **Процесс** — это та же программа, загруженная в собственное виртуальное адресное пространство и работающая: копия кода (**text**), глобальные переменные (**data** и **bss**), растущая область для объектов, выделяемых во время работы (**куча, heap**), по одному **стеку (stack)** на поток для вызовов функций и набор регистров процессора, которые говорят, какая инструкция выполнится следующей. Выполнение — это всего лишь процессор, повторяющий «взять инструкцию по счётчику команд, выполнить, перейти дальше», причём каждый вызов функции кладёт кадр на стек, а каждый возврат его снимает.

## Основное
### Программа
- Программа — это исполняемый файл (ELF в Linux, `.class`/`.jar` для JVM, которая сама является ELF-программой). Он состоит из секций: машинный код, инициализированные константы, размер неинициализированных глобальных переменных и заголовок, который говорит, куда в памяти должна попасть каждая секция и откуда начинается выполнение (точка входа).
- Сама по себе программа ничего не делает. Она становится процессом, когда ядро читает заголовок, строит адресное пространство, отображает в него секции и ставит счётчик команд процессора на точку входа ([[processes-and-threads]]).
- Одна программа может быть многими процессами: десять команд `java` — это десять процессов, которые делят одни и те же страницы кода в RAM (они только для чтения, поэтому ядро отображает их один раз), но у каждого свои данные, куча и стеки.

### Раскладка памяти процесса
От младших адресов к старшим, в типичном процессе Linux:

| Область | Что хранит | Время жизни | Рост |
|---|---|---|---|
| Text | Машинный код программы и разделяемых библиотек | Весь процесс | Фиксирована, только для чтения, общая для процессов |
| Data | Глобальные и статические переменные с начальным значением (`static int retries = 3;`) | Весь процесс | Фиксирована |
| BSS | Глобальные и статические переменные, которые начинаются с нуля; файл хранит только их размер | Весь процесс | Фиксирована, заполняется нулями при загрузке |
| Heap | Всё, что выделяется во время работы: `malloc`, `new`, куча JVM | Пока не освобождено (или не собрано) | Вверх, по запросу (`brk`, `mmap`) |
| Область memory-mapped | Разделяемые библиотеки, отображённые файлы, крупные выделения, стеки потоков | По-разному | В обе стороны |
| Stack | Кадры вызовов главного потока: параметры, локальные переменные, адреса возврата | Один вызов функции | Вниз, автоматически |

Между кучей и стеком лежит большой промежуток неотображённых адресов; они растут навстречу друг другу. В 64-битном процессе этот промежуток — терабайты, поэтому они никогда не встречаются; «переполнение стека» — это лимит на поток (8 МБ по умолчанию, 1 МБ для потока JVM), а не куча, вставшая на пути ([[stack-vs-heap-memory]]).

### Выполнение процесса
- Процессор держит состояние процесса в регистрах: **счётчик команд (program counter)** (адрес следующей инструкции), **указатель стека (stack pointer)** (вершина текущего стека), регистры общего назначения для арифметики и аргументов и флаги.
- Выполнение — это цикл: взять инструкцию по счётчику команд, декодировать, выполнить, сдвинуть счётчик ([[how-cpu-executes-code]]). Переходы и вызовы меняют счётчик вместо того, чтобы сдвигать его.
- Когда ядро переключается на другой поток, оно сохраняет эти регистры в структуру потока в ядре и загружает регистры другого потока. Это сохранение и восстановление и есть переключение контекста ([[processes-and-threads]]).
- JVM добавляет слой: интерпретатор и JIT-компилятор превращают байткод в машинный код, но после компиляции Java-метод выполняется ровно в этом же цикле, с теми же стеком и регистрами ([[compilation-interpretation-jit]]).

### Стек
- Область на каждый поток, используется как LIFO. Указатель стека отмечает вершину; «положить» (push) — значит сдвинуть указатель вниз и записать, «снять» (pop) — сдвинуть его обратно вверх. Выделение и освобождение стоят по одной инструкции, поэтому локальные переменные дёшевы.
- Каждый вызов функции создаёт **кадр (frame)**: адрес возврата (где продолжить после вызова), сохранённые регистры вызывающей стороны, параметры функции и локальные переменные.
- При возврате кадр отбрасывается, поэтому всё, что в нём хранилось, пропадает. Указатель на локальную переменную, возвращённый из функции, — классическая ошибка в C; Java исключает её тем, что держит объекты в куче, а на стеке — только ссылки.

### Выполнение процесса со стеком
Последовательность вызовов `main → handle → parse`, прослеженная по шагам:

```text
                 стек (растёт вниз)                   счётчик команд
main() стартует  [ кадр main: локальные ]             в main
main вызывает    push адрес возврата, аргументы       переход в handle
handle() работает [ main ][ кадр handle ]             в handle
handle вызывает  push адрес возврата, аргументы       переход в parse
parse() работает [ main ][ handle ][ кадр parse ]     в parse
parse возвращает pop кадр parse, загрузить адрес возврата  снова в handle, после вызова
handle возвращает pop кадр handle                     снова в main, после вызова
```

Трассировка стека (stack trace) — это та же картина, прочитанная сверху вниз: исключение создано в `parse`, которую вызвала `handle`, которую вызвала `main`. Рекурсия без базового случая кладёт кадры, пока не упрётся в лимит потока, и ядро доставляет ошибку, которую JVM сообщает как `StackOverflowError`.

### Секция данных
- Глобальные переменные и поля `static` живут здесь всю жизнь процесса; они не освобождаются и не привязаны к потоку. В Java статические поля загруженного класса живут в metaspace JVM, а объекты, на которые они ссылаются, — в куче; идея та же: одна копия, видимая каждому потоку.
- Поскольку они общие, они первые подозреваемые в ошибках многопоточности: счётчик `static`, инкрементируемый без синхронизации, — это гонка данных ([[race-conditions-and-critical-sections]]).
- Разделение на data (инициализированные) и BSS (нули) существует для того, чтобы исполняемый файл не хранил мегабайты нулей.

### Куча
- В куче лежат объекты, чьё время жизни не привязано к вызову: объект запроса, который переживает создавший его метод, кэш, пул соединений. Выделение идёт через аллокатор, который ищет свободное место; освобождение явное (`free`) или автоматическое (сборка мусора).
- Процесс просит у ядра страницы для кучи крупными порциями (`brk`, `mmap`), а затем сам раздаёт маленькие кусочки. Поэтому «used heap» в JVM и «resident memory» процесса в ядре — разные числа: JVM может удерживать страницы, которые сейчас не использует ([[jvm-memory-areas]], [[garbage-collection]]).
- Память кучи общая для всех потоков процесса. Два потока могут держать ссылки на один и тот же объект, что одновременно и смысл (общее состояние), и опасность (нужна синхронизация).

## Пример
Крошечная программа в духе C и куда попадает каждая её часть:

```c
int max_retries = 3;          // data: инициализированная глобальная переменная
int request_count;            // bss: глобальная переменная, инициализированная нулём
static char buffer[4096];     // bss: статический массив, заполнен нулями

int parse(const char *s) {    // text: машинный код
    int n = 0;                // stack: локальная переменная в кадре parse
    while (*s) n = n * 10 + (*s++ - '0');
    return n;                 // кадр снят; n больше нет
}

int main(void) {
    char *body = malloc(1024);         // heap: живёт до free()
    int id = parse("42");              // вызов: положить кадр, выполнить, снять
    request_count++;                   // data/bss: один и тот же адрес на весь процесс
    free(body);
    return 0;
}
```

Та же программа на Java переносит `body` и строку в кучу под управлением GC, а `max_retries`/`request_count` — в статические поля, но `n`, `id` и ссылка `body` по-прежнему на стеке, а `parse` по-прежнему получает кадр на каждый вызов.

## Подводные камни
- Java-объект никогда не лежит на стеке, только его ссылка. «Выделение на стеке» в Java существует лишь как оптимизация JIT (escape analysis), на которую нельзя полагаться.
- Стеки потоков не находятся в области «stack» раскладки. Там только стек главного потока; стек каждого другого потока — отдельная memory-mapped область, поэтому тысячи платформенных потоков стоят реальной памяти ([[virtual-threads]]).
- `ps` показывает виртуальный размер (VSZ) и резидентный размер (RSS). VSZ считает каждую отображённую страницу, включая неиспользуемый резерв кучи и разделяемые библиотеки; RSS — то, что реально находится в RAM. С лимитом памяти контейнера сравнивай RSS, никогда не VSZ ([[docker-containers-and-resources]]).
- `fork` копирует раскладку лениво (copy-on-write), поэтому процесс с кучей в 4 ГБ форкается быстро, но первая запись в каждую страницу после fork стоит page fault ([[virtual-memory-and-paging]]).
- Связанные заметки: [[stack-vs-heap-memory]] для подробного сравнения, [[jvm-memory-areas]] о том, как JVM делит свою часть этой раскладки.
