## Кратко
**Программа** — это исполняемый файл: исходный код, скомпилированный и слинкованный в машинный код для одной архитектуры CPU и сохранённый в формате, который ОС умеет загружать (ELF в Linux). **Процесс** — это запущенная программа. Ядро загрузило её в память, выдало ей идентификатор (PID) и управляющий блок (PCB) и направило **счётчик команд (program counter, PC)** процессора на её первую инструкцию. Одна программа может одновременно работать как множество процессов. Внутри у каждого процесса одна и та же раскладка: **text** (код), **data** (глобальные переменные), **куча (heap)**, растущая вверх, и **стек (stack)**, растущий вниз. Выполнение — это повторение процессором цикла *прочитать инструкцию по адресу из PC, выполнить её, сдвинуть PC*. Каждый вызов функции добавляет на стек **фрейм**, положение которого задают два регистра: **указатель стека (stack pointer, SP)** и **базовый указатель (base pointer, BP)**. Сохранённый во фрейме **адрес возврата** позволяет вызывающей функции продолжить работу. Кучей управляет аллокатор (`malloc` или TLAB в JVM), который запрашивает у ядра страницы крупными порциями; стек быстр не по волшебству, а благодаря локальности: его данные лежат рядом, поэтому одна кэш-линия приносит сразу несколько переменных.

## Основное
### Программа
- **Скомпилирована и слинкована под один CPU.** Компилятор переводит исходный код в набор инструкций конкретной архитектуры (x86-64, ARM64). Линкер объединяет объектные файлы и библиотеки в один исполняемый файл. Результат **работает только на этой архитектуре CPU**: бинарник x86-64 без эмуляции ничего не сделает на машине ARM64.
- **Также привязана к одной ОС.** Различаются формат файла и системные вызовы: ELF в Linux, PE в Windows, Mach-O в macOS. Тот же процессор x86-64 не может нативно запустить `.exe` из Windows в Linux.
- **В состоянии покоя хранится в формате исполняемого файла.** Для ELF:


| Часть ELF-файла | Что содержит | Кто читает |
|---|---|---|
| Заголовок ELF (ELF header) | Магические байты `7f 45 4c 46`, целевой CPU, адрес точки входа | Ядро, инструменты |
| Таблица заголовков программы (program header table) | **Сегменты**: какие диапазоны байтов отобразить в память, куда и с какими правами (R-X для кода, RW- для данных) | Загрузчик ядра при `exec` |
| `.text` | Машинный код | Попадает в сегмент кода (R-X) |
| `.rodata` | Константы и строковые литералы | Сегмент только для чтения |
| `.data` | Глобальные переменные с начальным значением | Сегмент для чтения и записи |
| `.bss` | Размер глобальных переменных, инициализированных нулём (байтов в файле нет) | Загрузчик выделяет обнулённые страницы |
| Таблица заголовков секций (section header table) | **Секции**: имена, типы и смещения для линкера, отладчика, `objdump` | Инструменты сборки, для запуска не нужна |

Одни и те же байты описаны дважды. **Секции** — детальное представление линкера; **сегменты** — грубое представление загрузчика о том, что отображать в память. `readelf -S` показывает первое, а `readelf -l` — второе.
- Java — сознательное исключение: `javac` порождает независимый от CPU байткод в файлах `.class`. Сама команда `java` — это ELF-программа, скомпилированная под твой CPU, и её JIT во время выполнения превращает горячий байткод в машинный код для текущего CPU ([[compilation-interpretation-jit]]).

### Компиляция и линковка
- **Компиляция** переводит каждый исходный файл в **объектный файл** (`.o`): машинный код для одного CPU с «дырами» там, где вызываются функции, определённые в другом месте (`printf`, `SSL_connect`). **Линковка** заполняет эти дыры и выдаёт один исполняемый файл.
- Большая часть кода, который вы запускаете, — в библиотеках (libc для `printf` и `malloc`, OpenSSL для TLS, libcurl для HTTP), скомпилированных под тот же CPU. Линкер может подключить их двумя способами:

| | Статическая линковка | Динамическая линковка |
|---|---|---|
| Что попадает в файл | Ваш код плюс копия каждой использованной функции библиотеки | Ваш код плюс список нужных разделяемых библиотек и версий (`NEEDED: libc.so.6`) |
| Размер файла | Большой | Маленький |
| При запуске | Искать нечего: отобразить и запустить | Динамический загрузчик находит каждый `.so` на диске и отображает его в процесс |
| Обновления | Чтобы получить исправление библиотеки, нужно пересобрать | Обновить библиотеку один раз (исправление безопасности OpenSSL), и его получат все программы |
| RAM | У каждой программы своя копия | Одна копия кода libc в RAM, общая для всех процессов |
| Падает, когда | Из-за отсутствующих библиотек — никогда | Библиотеки нет или она слишком старая: `error while loading shared libraries` (Windows: «DLL not found») |
| Примеры | Бинарники Go, Rust с musl, нативные образы GraalVM; Docker-образы `FROM scratch` | Почти всё в обычной системе Linux; `.dll` в Windows, `.dylib` в macOS |

- Это «DLL not found» — старая история о том, как копируешь один `.exe` с компьютера друга на дискету: программа приехала, а её библиотеки — нет. Docker-образы сегодня решают ту же проблему, поставляя программу вместе с её библиотеками.
- В Java тот же выбор на уровень выше: **fat jar** Spring Boot несёт все jar-зависимости внутри себя (как статическая линковка), а тонкий jar с classpath ожидает, что они уже есть (как динамическая).
- Линковка — сама по себе трудная задача (поиск символов среди тысяч объектных файлов, версии, дубликаты), и в больших проектах на C++ она может занимать минуты; новые линкеры вроде **mold** и **lld** во много раз быстрее классического GNU `ld`.

### Кто запускает программу
- `execve()` просит **ядро** прочитать заголовок ELF, создать новое адресное пространство и отобразить сегменты. Если программа слинкована динамически, в её заголовке указан **интерпретатор**, `/lib64/ld-linux-x86-64.so.2`; ядро отображает и его и начинает выполнение с него. Загрузчик отображает разделяемые библиотеки (`ldd ./app` показывает их список) и подставляет адреса вызовов.
- **Точка входа** в заголовке ELF — не `main`, а `_start`: несколько инструкций среды выполнения C (`crt1.o`), которые готовят аргументы и окружение и затем вызывают `main`. Когда `main` возвращается, выполняется `exit()`, и процесс завершается. В лекции это упрощено до «заголовок говорит начать с main».
- Инструменты, понимающие формат, могут читать и даже переписывать его (патчить код, добавлять секции). Так работают отладчики, профилировщики и, менее приятно, часть вредоносных программ; поэтому же существует подпись кода.

### Получение машинного кода
Каждая строка исходного кода превращается в несколько инструкций. Вот функция на C, скомпилированная в упрощённый ассемблер в стиле ARM — та же форма, что у настоящего вывода, но с меньшим числом деталей:

```text
int main() {                       mov r0, #1         ; a = 1, хранится в регистре r0
    int a = 1;                     mov r1, #3         ; b = 3, хранится в регистре r1
    int b = 3;            compile  add r3, r0, r1     ; c = a + b, вычисляет ALU
    int c = a + b;        ──────▶  str r3, [sp, #4]   ; сохранить c в его ячейку на стеке
    printf("%d", c);               ...                ; затем вызвать printf
}
```

Переменные, которые компилятор может держать в **регистрах**, вообще не касаются памяти. Перемещают данные между регистрами и RAM только `str` (store, запись) и `ldr` (load, чтение). На x86-64 та же функция использует `mov`, `add` и адреса вида `[rbp-4]`, но идея та же.

### Процесс
- **Когда программу запускают, получается процесс.** `execve()` просит ядро прочитать заголовки ELF, создать новое адресное пространство, отобразить сегменты, подготовить стек и перейти на точку входа ([[signals-and-process-lifecycle]]).
- **Процесс живёт в памяти.** Его код, данные, куча и стеки занимают страницы RAM (виртуальные страницы, отображённые на физические фреймы, [[memory-management]]). Когда процесс завершается, они освобождаются.
- **Он однозначно определяется идентификатором.** **PID** уникален среди работающих процессов на этой машине (или в PID namespace этого контейнера).
- **У него есть указатель инструкции / счётчик команд.** PC хранит адрес следующей инструкции для выполнения. Строго говоря, собственный PC и стек есть у каждого *потока*. У однопоточного процесса их по одному.
- **Ядро хранит для него управляющий блок процесса (Process Control Block, PCB)**, в Linux это `task_struct`. В PCB записаны PID и родитель, состояние (выполняется, спит…), сохранённые регистры, включая PC и SP, карта памяти, открытые файлы и данные планировщика. Переключение контекста (context switch) сохраняет регистры CPU в PCB и загружает регистры из другого ([[process-management]]).

- **Двух одинаковых процессов не бывает.** Они стартуют с одного кода, но каждый ветвится по своим входным данным, времени и окружению (`if hour == 7 …`), поэтому каждый оказывается на других инструкциях с другими значениями. Код — это программа; состояние — это процесс.
- **Как выдаются PID**: Linux раздаёт возрастающие номера до `/proc/sys/kernel/pid_max` (4 194 304 в большинстве 64-битных систем), а затем начинает сначала, пропуская занятые PID. PID не освобождается в момент смерти процесса: его держит *зомби*, пока родитель не заберёт код завершения через `wait()` ([[signals-and-process-lifecycle]]). Повторное использование всё же возможно, поэтому «убить процесс с PID 4242» может задеть новый, посторонний процесс; в Linux 5.3 появились дескрипторы `pidfd`, которые так не перепутать.
- **PID свои в каждом пространстве имён (namespace).** Контейнер получает собственное PID namespace: ваше Java-приложение внутри него — PID 1, а на хосте — скажем, PID 31877, и у трёх контейнеров может быть по своему PID 700. Пространства имён также изолируют сеть (интерфейсы, порты), точки монтирования, имя хоста, IPC и идентификаторы пользователей; вместе с cgroups они и есть контейнер ([[docker-fundamentals]]). Раньше контейнеры называли *jails* (FreeBSD).
- **PC — это регистр, а не переменная в памяти.** Обновлять копию в памяти после каждой инструкции значило бы платить за запись в память каждый раз, поэтому PC живёт только в CPU. В память он записывается, лишь когда поток перестаёт выполняться на этом ядре: при переключении контекста — в PCB (точка сохранения, как в игре), при входе в ядро — на стек ядра.

### Программа и процесс
Один файл программы может одновременно быть многими процессами. У каждого свой PID, свой PC (каждый находится в своей точке кода) и свои данные, куча и стек. Страницы кода только для чтения общие: ядро отображает одни и те же физические страницы `postgres` в каждую копию.

```text
                      /usr/lib/postgresql/17/bin/postgres      ← одна программа (ELF-файл)
            ┌──────────────────────┼──────────────────────┐
   postgres pid 2231      postgres pid 2240      postgres pid 2241   ← три процесса
   PC 0x5583…a10          PC 0x5583…f48          PC 0x5583…3c0         (каждый в своём месте)
   своя куча + стек       своя куча + стек       своя куча + стек
```

PostgreSQL действительно так работает: он форкает по одному backend-процессу на каждое клиентское соединение, поэтому `ps` показывает много строк `postgres` и поэтому важен пул соединений (connection pooling) ([[hikaricp-pool-sizing]]).

### Раскладка памяти процесса
От младших адресов к старшим, в типичном процессе Linux:

| Область | Что хранит | Время жизни | Рост |
|---|---|---|---|
| Text | Машинный код программы и разделяемых библиотек | Весь процесс | Фиксирована, только для чтения, общая для процессов |
| Data | Глобальные и статические переменные с начальным значением (`static int retries = 3;`) | Весь процесс | Фиксирована |
| BSS | Глобальные и статические переменные, начинающиеся с нуля; в файле хранится только их размер | Весь процесс | Фиксирована, заполняется нулями при загрузке |
| Куча (heap) | Всё, что выделено во время выполнения: `malloc`, `new`, куча JVM | Пока не освобождено (или не собрано) | Вверх, по запросу (`brk`, `mmap`) |
| Область отображений (memory-mapped area) | Разделяемые библиотеки, отображённые файлы, крупные выделения, стеки потоков | По-разному | В обе стороны |
| Стек | Фреймы вызовов главного потока: параметры, локальные переменные, адреса возврата | Один вызов функции | Вниз, автоматически |

Между кучей и стеком лежит большой промежуток неотображённых адресов, и они растут навстречу друг другу. В 64-битном процессе этот промежуток — терабайты, так что они никогда не встречаются. «Переполнение стека» (stack overflow) означает упор в лимит на поток (по умолчанию 8 МБ, 1 МБ для потока JVM), а не столкновение с кучей (раздел о переполнении стека ниже).

### Смотрим вживую: `/proc/<pid>/maps`
Ядро публикует карту памяти каждого процесса как текстовый файл. Каждая строка — одна область: диапазон адресов, права (`r` — чтение, `w` — запись, `x` — выполнение, `p` — private или `s` — shared), смещение, устройство, inode и файл, из которого она взята.

```text
$ cat /proc/13503/maps            (адреса сокращены)
5600a000-5600b000 r-xp ... /home/pi/high_cpu     код: машинные инструкции, 4 KiB
5601a000-5601b000 r--p ... /home/pi/high_cpu     данные только для чтения: константы, строки
5601b000-5601c000 rw-p ... /home/pi/high_cpu     данные: инициализированные глобальные
5602c000-5604d000 rw-p ... [heap]                куча: 0x21000 = 132 KiB
7f8a1000-7f9f6000 r-xp ... /usr/lib/…/libc.so.6  код libc, общий для всех процессов
7f9f6000-7f9fa000 rw-p ... /usr/lib/…/libc.so.6  собственные данные libc, приватные
7ffc2000-7ffe3000 rw-p ... [stack]               стек главного потока
```

- Размер = конец − начало: `0x5600b000 − 0x5600a000 = 0x1000` = 4 KiB. В сегменте данных лежит один `int`, а занимает он 4 KiB: память отображается целыми **страницами** ([[memory-management]]).
- Код, константы и данные берутся из исполняемого файла; у кучи и стека файла нет, потому что они создаются во время работы процесса.
- Каждая разделяемая библиотека занимает несколько строк (код, данные только для чтения, данные). Если бы злоумышленник смог подменить `libc.so.6` на диске, его код выполняла бы каждая программа, которая её загружает, поэтому системные каталоги библиотек доступны на запись только root.
- `pmap -x <pid>` выводит то же самое с резидентными размерами. У JVM в карте сотни строк (куча Java, metaspace, кэш кода, стеки потоков, `libjvm.so`); `jcmd <pid> VM.native_memory summary` (с `-XX:NativeMemoryTracking=summary`) называет их ([[jvm-memory-areas]]).

### Как выполняется процесс
- CPU хранит состояние выполняемого потока в **регистрах**: регистры общего назначения для значений (`r0`–`r3` ниже), **PC**, **регистр инструкции (IR)**, в котором лежит выполняемая инструкция, **указатель стека** и флаги ([[cpu]]).
- Выполнение — это один цикл, повторяемый миллиарды раз в секунду:
    1. **Выборка (fetch)**: прочитать инструкцию по адресу из PC в IR. Это чтение памяти, обычно обслуживаемое кэшем инструкций L1.
    2. **Декодирование и выполнение**: устройство управления определяет, что означает инструкция, а ALU или блок загрузки/записи (load/store unit) её выполняет.
    3. **Увеличение PC**: переход к следующей инструкции (+4 байта на ARM; 1–15 байт на x86, где инструкции разной длины). Переходы, вызовы и возвраты не увеличивают PC, а *заменяют* его.
    4. **Запись (store)**, если инструкция пишет в память: значение сначала попадает в кэш L1 и лишь позже доходит до RAM.

```anim

```

Реальные ядра совмещают эти стадии для многих инструкций одновременно ([[cpu]]), но каждая инструкция всё равно проходит их в этом порядке ([[cpu]]).

- **Почему всё решает доступ к памяти.** Примерная стоимость, а также те же числа, растянутые так, чтобы 1 нс стала 1 секундой:

| Доступ | Время | Если бы 1 нс была 1 с |
|---|---|---|
| Регистр | < 1 нс | меньше секунды |
| Кэш L1 | ~1 нс | 1 секунда |
| Кэш L2 | ~4 нс | 4 секунды |
| Кэш L3 (общий для ядер) | ~10–20 нс | 15 секунд |
| RAM | ~100 нс | почти 2 минуты |
| Чтение с NVMe SSD | ~20–150 мкс | от 6 часов до 2 суток |
| Позиционирование HDD | ~10 мс | 4 месяца |

- **Выборка инструкций обычно попадает в кэш.** Чтение из RAM приносит целую 64-байтную кэш-линию, в которой 16 четырёхбайтных инструкций, поэтому следующие уже лежат в кэше инструкций L1. Код, который выполняется подряд, дешёв; код, прыгающий по всему бинарнику, — нет (см. инлайнинг ниже).
- **Вопрос из лекции**: в `mov r0,#1; mov r1,#3; add r3,r0,r1` один `add`, но PC тоже сдвигался три раза. Лекция считает и эти сдвиги сложениями; в железе PC сдвигает собственный маленький инкрементор, а не ALU, поэтому они не конкурируют с вашей арифметикой.
- **Размер инструкции — не размер слова.** Инструкции ARM64 занимают 4 байта, хотя регистры 64-битные; инструкции x86-64 — от 1 до 15 байт. В демонстрации с gdb в лекции PC сдвинулся на 8 после `next`, потому что эта строка C скомпилировалась в две инструкции, а не потому, что 64-битный CPU использует 8-байтные инструкции.
- **Одно ядро выполняет один поток за раз.** При **hyper-threading** (SMT) одно физическое ядро видно как два логических CPU: у каждого свои регистры и PC, но исполнительные блоки и кэши L1/L2 общие. Когда один поток ждёт память, может работать другой, поэтому одним нагрузкам это помогает, а другим вредит.
- **Сегмент кода доступен только для чтения** (а стек и куча — не исполняемые), поэтому ошибка не может перезаписать код, а внедрённые данные не могут выполниться. JIT-компиляторам, как в JVM, нужно *генерировать* код во время работы, поэтому они пишут его в отдельное отображение — **кэш кода** (`-XX:ReservedCodeCacheSize`), переключая его страницы между «можно писать» и «можно выполнять».
- **Посмотрите сами** (любая машина с Linux; на ARM регистры называются `x0`…, на x86-64 — `rax`…):

```bash
uname -a                       # версия ядра и архитектура CPU (aarch64, x86_64)
gcc -S -o test.s test.c        # остановиться после компиляции: читаемый ассемблер
gcc -g -o test test.c          # полная сборка с отладочными символами (строка исходника ↔ адрес)
gdb ./test
(gdb) start                    # запустить до первой строки main и остановиться
(gdb) info registers pc sp     # счётчик команд и указатель стека прямо сейчас
(gdb) next                     # одна строка C; снова info registers: pc сдвинулся
(gdb) disassemble              # машинный код вокруг pc
```
Отладочные символы — это карта от адресов машинного кода обратно к файлу и строке, поэтому бинарники с `-g` гораздо больше, а трассировки стека у бинарников без символов показывают только адреса.

### Стек
- **Стек — простая и гениальная структура данных:** последним пришёл, первым ушёл (LIFO). Это в точности соответствует вызовам функций: функция, вызванная последней, возвращается первой.
- **У функции есть локальные переменные**, и **каждый вызов функции получает фрейм**: блок стека с её локальными переменными, сохранённым базовым указателем вызывающей функции и адресом возврата.
- **Он растёт от старших адресов к младшим.** Новый фрейм располагается *ниже* фрейма вызывающей функции.
- **Место на стеке ограничено**: по умолчанию 8 МБ для главного потока (`ulimit -s`), 1 МБ на платформенный поток JVM (`-Xss`). Глубокая или неограниченная рекурсия его исчерпывает.

- **Всё лежит рядом**, и в этом весь секрет его скорости. Чтение одной локальной переменной приносит её 64-байтную кэш-линию, и соседние переменные приходят бесплатно. По той же причине отсортированные листовые страницы B+-дерева ускоряют диапазонные запросы в базе данных: одно чтение — много полезных значений.
- Один стек на поток; он резервируется при старте потока и обеспечивается реальными страницами только по мере обращения. Под ним лежит неотображённая **сторожевая страница** (guard page): выход за предел попадает в неё и вызывает ошибку страницы, а не тихую перезапись другой памяти, и JVM превращает эту ошибку в `StackOverflowError`.
- Когда функция возвращается, её фрейм не очищается: байты остаются, пока следующий вызов их не перезапишет. Чтение неинициализированной локальной переменной в C возвращает этот мусор, а утечки содержимого стека — классический источник уязвимостей.
- Компилятор знает размер каждого фрейма, поэтому выделяет весь фрейм одним `sub sp` на входе, а не по сдвигу на каждую переменную, и держит стек выровненным (16 байт на x86-64 и ARM64).

### Указатель стека и базовый указатель
- **Указатель стека (SP)** — регистр CPU (`rsp` на x86-64, `sp` на ARM64), который **указывает на конец** стека: на самый младший используемый адрес.
- **Выделить и освободить память на стеке — значит сдвинуть SP**: `sp = sp - 12` резервирует 12 байт, `sp = sp + 12` освобождает их. Ничего не очищается и не освобождается; старые байты просто позже перезаписываются. Поэтому выделение на стеке стоит одну инструкцию.
- **SP меняется постоянно** — при push, вызовах и подготовке аргументов, — поэтому он плохая точка отсчёта для поиска переменной. Функции нужна **фиксированная точка отсчёта**.
- **Базовый указатель (BP)**, он же **указатель фрейма (frame pointer)** (`rbp` на x86-64, `x29` на ARM64), не меняется на протяжении всего вызова и отмечает верх текущего фрейма. Локальные переменные адресуются относительно него: `a` — это `[bp-4]`, `b` — `[bp-8]`, как бы ни двигался SP.

### Вызов функции по шагам
Когда `main` вызывает `func1`, на x86-64:

| Шаг | Инструкция | Что происходит со стеком |
|---|---|---|
| 1. Вызов | `call func1` | CPU кладёт на стек **адрес возврата** (адрес инструкции в `main`, следующей за вызовом) и устанавливает PC на `func1` |
| 2. Сохранить фрейм вызывающей функции | `push rbp` | Сохраняется **предыдущий BP** (от main), чтобы фрейм main можно было найти снова |
| 3. Новый фрейм | `mov rbp, rsp` | Теперь BP отмечает верх фрейма func1 |
| 4. Локальные переменные | `sub rsp, 16` | SP сдвигается вниз, освобождая место для `x` и `y` |
| 5. Работа | … | `x` и `y` читаются и записываются как `[rbp-4]`, `[rbp-8]` |
| 6. Освободить локальные переменные | `mov rsp, rbp` | **Освобождение**: SP прыгает обратно вверх; `x` и `y` больше нет (их байты остаются, пока не будут перезаписаны) |
| 7. Восстановить фрейм вызывающей функции | `pop rbp` | BP снова указывает на фрейм main |
| 8. Возврат | `ret` | **Адрес возврата снимается со стека в PC**: main продолжает сразу после вызова |

Шаги 2–4 — это *пролог* функции, а шаги 6–8 — её *эпилог*. Каждая скомпилированная функция начинается и заканчивается так, с небольшими вариациями.

```anim
call-stack-frames
```

- **Зачем нужен адрес возврата**: после вызова у main ещё есть работа, но как только PC переходит на `func1`, CPU теряет своё место в main. Сохранённый адрес возврата при возврате снова *становится PC*.
- **x86-64 и ARM64**: на x86-64 `call` сохраняет адрес возврата **на стеке**. На ARM64 `bl func1` вместо этого сохраняет его в **регистре связи (link register)** (`x30`), что быстрее для листовых функций, которые больше ничего не вызывают. Функция, которая вызывает другие, сначала сохраняет `x29` (указатель фрейма) и `x30` (адрес возврата) в своём фрейме на стеке (`stp x29, x30, [sp, #-16]!`), потому что следующий `bl` перезаписал бы регистр связи.
- В обоих соглашениях сохранённый адрес возврата лежит *выше* сохранённого указателя фрейма, по более старшему адресу.
- Трассировка стека (stack trace) — это цепочка фреймов, прочитанная сверху вниз: исключение выброшено в самом новом фрейме, который был вызван из фрейма над ним, и так далее вплоть до `main`.

### Параметры, возвращаемые значения и регистры при вызовах
- Аргументы передаются **в регистрах**, а не через стек, пока их немного. Правила задаёт **соглашение о вызовах** (calling convention, ABI) платформы:

| | Аргументы | Возвращаемое значение | Адрес возврата |
|---|---|---|---|
| x86-64 Linux/macOS (System V) | `rdi, rsi, rdx, rcx, r8, r9`, дальше стек | `rax` | кладётся на стек инструкцией `call` |
| ARM64 | `x0`–`x7`, дальше стек | `x0` | регистр связи `x30` |

- Вызываемая функция вправе использовать регистры для своей работы, поэтому соглашение также определяет, кто что сохраняет: **сохраняемые вызывающим** (caller-saved) регистры может перезаписать любой вызов, и всё нужное вызывающая функция должна держать в памяти или в **сохраняемых вызываемым** (callee-saved) регистрах, которые вызываемая функция обязана восстановить перед возвратом. Поэтому в неоптимизированном разборе ниже `main` заново читает `a` и `b` со стека после возврата из `func1`: `func1` перезаписала `r0`.
- `malloc(4)` подчиняется тем же правилам: `4` кладётся в первый регистр аргументов, а указатель возвращается в регистре результата.

### Сколько стоит вызов, и инлайнинг
- Вызов не бесплатен: сохранить адрес возврата и старый указатель фрейма (записи в память), сдвинуть SP, перебросить PC в другое место, а при возврате прочитать всё обратно. Аргументы в регистрах, возможно, сначала придётся сохранить. Для маленькой функции эта бухгалтерия может стоить больше, чем её тело.
- Важен и сам прыжок. Код вызываемой функции лежит в другом месте сегмента кода, возможно, не в кэше инструкций; программа, состоящая из глубокой сети мелких функций, постоянно вытесняет и заново подгружает код. В лекции есть история о том, что MySQL 8.0 на некоторых нагрузках медленнее 5.7, и одна из предполагаемых причин — гораздо больше мелких вызовов функций, которые «перемалывают» кэш инструкций. Считайте это гипотезой, но сам механизм реален.
- **Инлайнинг** убирает вызов: компилятор копирует тело вызываемой функции в вызывающую, и оно становится ещё несколькими инструкциями подряд. Цена — больший бинарник, который тоже давит на кэш инструкций, поэтому компиляторы встраивают только маленькие или горячие функции.
- В Java это делает JIT во время работы, по реальному профилю: горячие методы меньше `-XX:FreqInlineSize` (325 байт байт-кода) встраиваются, поэтому геттеры, мелкие вспомогательные методы и лямбды обычно ничего не стоят. Место вызова, которое видит много разных реализаций интерфейса (*мегаморфное*), встроить нельзя, и оно остаётся настоящим вызовом.
- **Рекурсия** платит эту цену на каждом уровне и тратит фрейм на уровень, поэтому очень глубокая рекурсия и медленная, и ограничена размером стека.

### Всё вместе: программа в работе
Всё описанное выше сразу: маленькая программа на C (`main` задаёт `a` и `b`, вызывает `func1`, которая считает `z = z + 1`, затем `main` считает `c = a + b`), скомпилированная в упрощённые инструкции в стиле ARM и выполняемая по одной инструкции за шаг. Следите, как меняются три вещи одновременно: **pc** идёт по машинному коду и прыгает на `bl` и `ret`; регистры (**r0**, **r1**, **r3**) держат значения только пока их считают; а каждый `str` / `ldr` — это путь между CPU и стеком в RAM. Адреса десятичные и маленькие для наглядности; каждая инструкция занимает 4 байта.

```anim
program-execution
```

- `bl func1` кладёт адрес возврата в регистр связи `lr`, а не в стек. Функция, которая никого не вызывает (*листовая*, как `func1`), может его там и оставить; `main` сохранила свой `lr` в прологе, потому что `bl` его перезаписывает.
- Неоптимизированный код (`-O0`) хранит каждую переменную в памяти и каждый раз перечитывает её, как здесь. С `-O2` вся программа сжимается почти до нуля, потому что результаты нигде не используются.

### Секция данных
- Глобальные переменные и `static`-поля живут здесь всё время жизни процесса; они не освобождаются и не принадлежат отдельным потокам. В Java статические поля загруженного класса живут в metaspace JVM, а объекты, на которые они ссылаются, — в куче; идея та же: одна копия, видимая всем потокам.
- Поскольку они общие, это первые подозреваемые в ошибках конкурентности: `static`-счётчик, увеличиваемый без синхронизации, — это гонка данных (data race) ([[race-conditions-and-critical-sections]]).
- Разделение на data (инициализированные) и BSS (нулевые) существует, чтобы исполняемый файл не хранил мегабайты нулей.

### Куча
Куча — это область для памяти, размер или время жизни которой заранее неизвестны: она выделяется во время работы программы и остаётся, пока её кто-нибудь не освободит.

| Свойство | Что это значит |
|---|---|
| Данные, которые переживают вызов | Объект запроса, который возвращается из создавшего его метода, кэш, пул соединений. Не только «большие» данные: `malloc` на 16 байт — тоже куча; решают время жизни и размер, известный только во время выполнения |
| Живёт, пока не освободят | Освобождается явно (`free` в C, `delete` в C++) или, в Java, сборщиком мусора, когда на объект больше никто не ссылается. Возврат из функции ничего в куче не освобождает |
| Доступна из любой функции, через указатель | У самого блока нет имени. Код добирается до него по адресу, который хранится в стеке, в секции данных или в другом блоке кучи. Потеряли все копии адреса — потеряли блок |
| Растёт от младших адресов к старшим | Навстречу стеку, который растёт вниз. Аллокатор получает страницы у ядра крупными порциями (`brk`, `mmap`) и сам раздаёт их небольшими кусками |
| API | C: `malloc` / `free`. C++: `new` / `delete`. Java: `new`, освобождает GC |

- Поскольку процесс запрашивает страницы крупными порциями, «используемая куча» JVM и «резидентная память» процесса с точки зрения ядра — разные числа: JVM может держать страницы, которые сейчас не использует ([[jvm-memory-areas]], [[garbage-collection]]).
- Память кучи общая для всех потоков процесса. Два потока могут держать ссылки на один и тот же объект, и в этом одновременно смысл (общее состояние) и опасность (нужна синхронизация).

### Как работают malloc и free
- **`malloc` — библиотечная функция, а не системный вызов** (в лекции он назван системным вызовом). Она часть libc и управляет кучей внутри процесса. Лишь когда место кончается, она просит у ядра ещё: сдвигает **program break** — верхнюю границу кучи — через `brk`/`sbrk` для маленьких блоков и создаёт отдельное отображение через `mmap` для больших (порог glibc по умолчанию — 128 KiB). Большинство вызовов `malloc` в ядро вообще не заходит.
- **`free(p)` знает размер благодаря заголовку.** Аллокатор хранит небольшой заголовок (в glibc 8–16 байт с размером блока и флагами) прямо перед адресом, который возвращает. `free` отступает назад от `p`, читает его и кладёт блок в список свободных. Это накладные расходы на каждое выделение: `malloc` на 4 байта занимает в 64-битной glibc блок в 32 байта.
- `free` возвращает память **аллокатору**, а не обязательно ядру. Блок в середине кучи не может опустить program break, поэтому RSS процесса после всплеска выделений часто остаётся высоким. Сразу возвращаются только блоки, выделенные через `mmap`.
- Множество крошечных выделений в цикле — худший шаблон: каждое платит за бухгалтерию аллокатора и заголовок, а блоки разбросаны. Программы, знающие свою нагрузку, выделяют оптом: **memcached** нарезает память на slab'ы из блоков фиксированного размера, серверы используют арены и пулы, а в Java Netty по той же причине держит пул `ByteBuf`. Лекция винит ООП-конструкторы, выделяющие память на каждый объект, в поощрении плохого шаблона; в Java дешёвое выделение в TLAB это смягчает, но большие буферы всё равно стоит переиспользовать.
- glibc выдаёт потокам отдельные **арены**, чтобы избежать глобальной блокировки. JVM с сотнями потоков может создать много арен, каждая из которых держит освобождённую нативную память, и RSS контейнера вырастает далеко за `-Xmx`; обычное решение — `MALLOC_ARENA_MAX=2` или jemalloc.

### Указатели
- **Указатель** — переменная, значение которой — адрес. Его **тип** говорит, сколько байт читать по этому адресу: `int *p` читает 4 байта, `char *c` — 1. Без типа CPU не знал бы, где кончается значение.
- У самого указателя тоже есть размер: 4 байта в 32-битном процессе, 8 — в 64-битном. Указатель может лежать на стеке, в секции данных или в куче и указывать на любую из них. Ссылки Java — это указатели, с которыми нельзя делать арифметику (сжатые до 4 байт, когда куча меньше 32 ГБ).

### Утечки памяти
- В C утечка — это блок, который всё ещё выделен, но его адреса больше ни у кого нет. Классический случай показан в анимации: единственный указатель был локальной переменной, и функция вернулась без `free`. Освободить эту память уже ничто не сможет до завершения процесса.
- Утечка в короткой консольной программе безвредна: при завершении процесса ядро забирает всю память. В сервере, который работает неделями, несколько килобайт на запрос складываются в убийство по нехватке памяти.
- Обратные ошибки не лучше: использовать блок после `free` (*use-after-free*, через *висячий указатель*) и вызвать `free` дважды (*double free*). Обе портят служебные данные аллокатора и являются классическим источником уязвимостей.
- В Java так утечь нельзя: GC освобождает каждый недостижимый объект. Утечка в Java — это объект, который всё ещё **достижим**, но уже не нужен: `static Map` в роли кэша без вытеснения, слушатели, которые регистрируют и никогда не удаляют, `ThreadLocal`, оставленный в потоке из пула, растущая очередь, которую никто не разбирает.
- Симптом утечки в Java: после каждой полной сборки мусора old generation остаётся чуть выше, пока не случится `OutOfMemoryError: Java heap space`. Диагностика — дамп кучи (`-XX:+HeapDumpOnOutOfMemoryError`, затем дерево доминаторов в Eclipse MAT), чтобы увидеть, какой объект удерживает остальные.

- Висячий указатель или double free хуже утечки: утечка лишь тратит память, а эти ошибки роняют процесс или позволяют злоумышленнику испортить его память. Если специально составленный HTTP-запрос может вызвать double free в сервере на C, повторяя его, можно уронить все воркеры: отказ в обслуживании. Rust исключает такие ошибки на этапе компиляции; в языках со сборкой мусора они невозможны.
- **JVM не считает ссылки.** В лекции сказано, что сборщики мусора используют подсчёт ссылок; CPython так делает (и платит записью в память при каждом изменении ссылки, см. [[operating-system-introduction]]), но сборщики HotSpot **трассируют**: начинают от корней (стеки, статические поля) и помечают всё достижимое. Чтение объекта никогда в него не пишет, а циклы собираются естественным образом.

### Стек и куча: производительность
| | Стек | Куча |
|---|---|---|
| Выделить и освободить | Сдвинуть `sp`: одна инструкция, и всё освобождается автоматически при возврате | Аллокатор ищет место в списках свободных блоков, может брать блокировку, иногда делает системный вызов; память нужно освобождать вручную или силами GC |
| Локальность | Фреймы идут подряд и недавно использовались, поэтому лежат в кэше L1 | После множества выделений и освобождений связанные блоки оказываются разбросаны («куча случайна»), и обход по ним даёт промахи кэша ([[cpu-caches-and-cache-lines]]) |
| Размер | Небольшой и фиксированный на поток: 8 МБ для главного потока в Linux (`ulimit -s`), от 512 КБ до 1 МБ для потока Java (`-Xss`). Переполнение — `StackOverflowError` | Ограничен RAM, адресным пространством, а в Java — `-Xmx` |
| Фрагментация | Нет: стек всегда один непрерывный блок | Дыры между живыми блоками, как освобождённые 100 байт в анимации, которые могут оказаться слишком малы для повторного использования |
| Владелец | Один поток: синхронизация не нужна | Весь процесс: общие объекты требуют синхронизации |
| Время жизни | До возврата из функции | До освобождения или, в Java, до потери достижимости |
| Отказ | `StackOverflowError` / `SIGSEGV` | `OutOfMemoryError`, `malloc` возвращает `NULL` или OOM killer |

- В Java выделение почти так же дёшево, как на стеке: каждый поток сдвигает указатель внутри собственного буфера в young generation (TLAB). Стоимость переносится на сборку мусора, поэтому правило «выделяйте меньше» по-прежнему про производительность ([[garbage-collection]]).

- **Раскладка важнее числа инструкций.** В какой бы области ни лежали данные, поля, которые используются вместе, должны находиться в одной кэш-линии. В 2024 году (Linux 6.8) инженеры Google переупорядочили поля основных сетевых структур ядра (`struct sock`, `tcp_sock`, `net_device`) так, чтобы поля, читаемые на горячем пути, делили кэш-линии. Больше ничего не менялось, а пропускная способность TCP при множестве одновременных соединений выросла на некоторых машинах примерно до 40%. Java не даёт упорядочивать поля (JVM сама раскладывает объекты), но та же идея объясняет, почему `int[]` обходится гораздо быстрее, чем `List<Integer>` из разбросанных упакованных объектов ([[cpu-caches-and-cache-lines]]).
- **Escape analysis** переносит выделения из кучи на стек, когда это возможно: компилятор Go кладёт значение на стек, если ни один указатель на него не переживает функцию. JIT HotSpot делает похожее (скалярная замена): неубегающий объект раскладывается на локальные переменные и вообще не выделяется. Полагаться на это нельзя, но именно поэтому мелкие временные объекты часто ничего не стоят.
- Нативная память в процессе JVM — тоже «куча» в смысле ОС: metaspace, кэш кода JIT, direct `ByteBuffer` и стеки потоков — всё это учитывается в лимите контейнера, хотя находится вне `-Xmx`.

### Почему происходит переполнение стека
- Неограниченная или очень глубокая рекурсия: рекурсивный обход вырожденного дерева (в форме связного списка), рекурсивный маппинг в JSON сущности, ссылающейся на саму себя, цикл `toString()`/`hashCode()` между двумя JPA-сущностями ([[jpa-entities-and-relationships]]), Spring-бин, вызывающий сам себя через прокси ([[spring-aop]]).
- Большие фреймы: большие локальные массивы в C. В Java локальные переменные — ссылки, поэтому фреймы маленькие, но глубокие цепочки встроенных вызовов и очень длинные конвейеры стримов их раздувают.
- Число потоков × размер стека: 5 000 платформенных потоков × 1 МиБ = 5 ГиБ зарезервированного адресного пространства. Это не переполнение, но причина исчерпать память или упереться в `ulimit -u`. Виртуальные потоки хранят свои фреймы в куче и наращивают их по мере надобности ([[virtual-threads]]).
- Решение: итерировать с явным `Deque` вместо рекурсии (см. второй пример), ограничить глубину или дать стек побольше одному отдельному потоку (`new Thread(group, task, name, stackSize)`), а не увеличивать `-Xss` для всех ([[recursion-and-backtracking]]).

## Пример
От исходного кода до трёх запущенных процессов, и куда попадает каждая часть программы:

```c
int max_retries = 3;          // .data → сегмент данных: инициализированная глобальная переменная
int request_count;            // .bss  → страница, заполненная нулями: глобальная переменная, инициализированная нулём
static const char *name = "api";  // строковый литерал живёт в .rodata

int parse(const char *s) {    // .text → сегмент кода (только чтение, общий)
    int n = 0;                // стек: локальная переменная во фрейме parse, [bp-4]
    while (*s) n = n * 10 + (*s++ - '0');
    return n;                 // эпилог: фрейм освобождён, адрес возврата → PC
}

int main(void) {
    char *body = malloc(1024);         // куча: живёт до free()
    int id = parse("42");              // вызов: push адреса возврата, новый фрейм
    request_count++;                   // data: один адрес на весь процесс
    free(body);
    return 0;
}

/*
  $ gcc -O0 -o api api.c          компиляция + линковка под этот CPU (x86-64)
  $ file api                      → ELF 64-bit LSB pie executable, x86-64
  $ readelf -l api | grep LOAD    → сегменты R / R E / RW, которые отображает загрузчик
  $ ./api & ./api & ./api &       одна программа, три процесса
  $ pgrep -a api                  → три PID, один и тот же файл
*/
```

Та же программа на Java переносит `body` и строку в кучу, управляемую GC, а `max_retries`/`request_count` — в статические поля, но `n`, `id` и ссылка `body` по-прежнему на стеке, и `parse` по-прежнему получает фрейм на каждый вызов.

Как избежать переполнения стека с явным стеком в куче:

```java
// Удаление дерева eSIM-профилей (родитель -> потомки) в глубину без рекурсии:
// явный стек в куче, ограниченный памятью, а не -Xss.
void deleteSubtree(UUID rootId) {
    Deque<UUID> stack = new ArrayDeque<>();
    stack.push(rootId);
    while (!stack.isEmpty()) {
        UUID id = stack.pop();                       // аналог фрейма: один UUID, а не фрейм метода
        for (UUID child : repo.childIds(id)) {
            stack.push(child);
        }
        repo.delete(id);
    }
}

// Рекурсивная версия короче и подходит для глубины < ~10 000,
// но испорченный цикл parent_id превращает её в StackOverflowError во время выполнения:
void deleteSubtreeRecursive(UUID id) {
    repo.childIds(id).forEach(this::deleteSubtreeRecursive);
    repo.delete(id);
}
```
Стек по умолчанию в 1 МиБ вмещает примерно 10–20 тысяч простых Java-фреймов; точное число зависит от JIT, поэтому один и тот же код может переполнить стек в холодном интерпретаторе и нормально работать после компиляции.

## Подводные камни
- **«exec format error»** — это программа, собранная под другой CPU. Типичный случай — Docker-образ `linux/amd64` на машине ARM64 (Apple Silicon, AWS Graviton). Собирай мультиархитектурные образы (`docker buildx --platform linux/amd64,linux/arm64`) или запускай под эмуляцией, что гораздо медленнее.
- Объект Java никогда не лежит на стеке, там только ссылка на него. «Выделение на стеке» в Java существует лишь как оптимизация JIT (escape analysis), на которую нельзя полагаться.
- Стеки потоков находятся не в области «стек» раскладки. Там только стек главного потока; стек любого другого потока — отдельная отображённая область памяти, поэтому тысячи платформенных потоков стоят реальной памяти ([[virtual-threads]]).
- Оптимизированные сборки часто опускают указатель фрейма (`-fomit-frame-pointer`), чтобы освободить регистр. Тогда профилировщикам и `perf` трудно обходить стек. Для flame graph в JVM используй `-XX:+PreserveFramePointer`.
- В C запись за пределы локального массива может перезаписать сохранённый адрес возврата. Это классический эксплойт *переполнения буфера на стеке* (stack buffer overflow), и именно поэтому существуют стековые канарейки (stack canaries) и неисполняемые стеки.
- `ps` показывает виртуальный размер (VSZ) и резидентный размер (RSS). VSZ учитывает каждую отображённую страницу, включая неиспользуемый резерв кучи и разделяемые библиотеки; RSS — то, что действительно находится в RAM. С лимитом памяти контейнера сравнивай RSS, никогда не VSZ ([[docker-containers-and-resources]]).
- `fork` копирует раскладку лениво (копирование при записи, copy-on-write), поэтому процесс с кучей 4 ГБ может форкнуться быстро, но первая запись в каждую страницу после форка стоит page fault ([[memory-management]]).
- Ловить `StackOverflowError` как обычное исключение: это `Error`, и поток остаётся в неизвестном состоянии. Исправьте рекурсию.
- Увеличивать `-Xss` глобально, чтобы «исправить» переполнение: каждый поток теперь резервирует больше памяти, а настоящая ошибка (обычно цикл) остаётся.
- Контейнер убит OOM, хотя куча Java далеко не дошла до `-Xmx`: виновата нативная память (direct-буферы Netty или клиента Kafka, metaspace, стеки потоков, арены malloc), которую показатели кучи Java не видят.
- В C — возвращать адрес локальной переменной или использовать `alloca`/массивы переменной длины с размером, который задаёт пользователь: и то и другое портит стек, чего Java не допускает by design.
- Ошибки «нет библиотеки» после копирования бинарника на другую машину (`error while loading shared libraries`): поставляйте его в контейнере, линкуйте статически или установите нужную версию библиотеки.
- Связанные заметки: [[jvm-memory-areas]] — как JVM делит свою часть этой раскладки, [[process-management]] — потоки, PCB и переключение контекста, [[memory-management]] — страницы и виртуальная память, [[compilation-interpretation-jit]] — как байт-код превращается в машинный код.
