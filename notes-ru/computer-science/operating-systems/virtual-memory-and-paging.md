## Кратко
Каждый процесс работает в собственном **виртуальном адресном пространстве**; MMU процессора переводит виртуальные адреса в физические фреймы через **таблицы страниц** (page tables) процесса, а **TLB** кэширует недавние трансляции. Страницы отображаются лениво, при первом обращении (**ошибка страницы**, page fault), поэтому зарезервированная память (`VmSize`) намного больше резидентной (`RSS`). Когда физическая RAM заканчивается, ядро освобождает page cache, выгружает анонимные страницы в swap и в крайнем случае **OOM killer** завершает процесс. Инструменты Linux (`free`, `/proc/meminfo`, swappiness, page cache) описаны в [[linux-memory-filesystems-io]]; эта заметка — о механизме и о том, что он значит для JVM-сервиса.

## Основное

### Зачем нужна виртуальная память
- **Изоляция**: процесс не может адресовать память другого процесса; недопустимое обращение вызывает `SIGSEGV`, а не порчу соседа.
- **Иллюзия непрерывности**: куча выглядит как один непрерывный диапазон, хотя физические фреймы разбросаны, а некоторых вообще нет в памяти.
- **Разделение**: `libc.so` и `libjvm.so` JVM загружены в RAM один раз и видны в каждом процессе; `fork()` разделяет все страницы с копированием при записи ([[linux-processes]]).
- **Overcommit**: ядро раздаёт больше виртуальной памяти, чем есть RAM, рассчитывая, что не вся она будет задействована (`vm.overcommit_memory`).

### Механика трансляции
- Размер страницы 4 КиБ на x86-64 (16 КиБ на Apple silicon, 64 КиБ на некоторых ARM-серверах). Виртуальный адрес делится на индексы таблиц страниц плюс 12-битное смещение внутри страницы.
- x86-64 использует 4-уровневое (5-уровневое при 57-битной адресации) префиксное дерево таблиц страниц. Полный обход — это четыре зависимых чтения памяти, поэтому **TLB** (несколько тысяч записей на ядро) кэширует трансляции. Промах TLB при случайном доступе может стоить дороже самого обращения к данным.
- **Большие страницы** (huge pages; 2 МиБ, 1 ГиБ) сокращают промахи TLB в 512 раз; JVM может использовать их с `-XX:+UseTransparentHugePages` или `-XX:+UseLargePages`. Прозрачные большие страницы (THP) также могут вызывать всплески задержки из-за уплотнения (`khugepaged`), поэтому базы данных вроде Redis и MongoDB рекомендуют отключать THP.
- Каждая запись таблицы страниц несёт флаги: присутствует, доступна для записи, исполняемая (NX), пользователь/супервизор, было обращение (accessed), изменена (dirty). Ядро использует биты accessed/dirty при решениях об освобождении памяти.

### Ошибки страниц
| Вид | Причина | Стоимость |
|---|---|---|
| Мелкая (minor, soft) | страница в RAM, но ещё не отображена: первое обращение к памяти `malloc`/`mmap`, разрыв copy-on-write, попадание в page cache | ~1 мкс, без диска |
| Крупная (major, hard) | страницу нужно прочитать с диска: выгруженная в swap страница или страница файла, которой нет в кэше | мс (диск) |
| Недопустимая | адрес вообще не отображён или нарушены права доступа | `SIGSEGV`; в JVM — лог падения (`hs_err_pid`) или, для проверки на null, `NullPointerException` (HotSpot намеренно использует ошибку на странице 0) |
- `-Xms`, равный `-Xmx`, плюс `-XX:+AlwaysPreTouch` оплачивают все мелкие ошибки при старте, а не на первых запросах; это оправдано для сервисов, чувствительных к задержке ([[jvm-memory-areas]]).
- `ps -o min_flt,maj_flt` или `/proc/<pid>/stat` показывают число ошибок; растущий `maj_flt` на сервере означает, что он свопится или перечитывает вытесненные файлы.

### Освобождение памяти, swap и OOM killer
- Порядок освобождения под давлением: чистый page cache (просто отбросить), грязный page cache (записать, затем отбросить), анонимные страницы (куча, стеки) в swap. `vm.swappiness` смещает баланс между последними двумя.
- Своп для JVM катастрофичен, потому что цикл GC затрагивает всю кучу: куча на 4 ГиБ, наполовину лежащая на диске, превращает паузу в 50 мс в минуты. Продовые хосты с JVM работают почти или совсем без swap и полагаются на правильный расчёт размеров.
- **OOM killer** запускается, когда освобождение не может высвободить страницу. Он выбирает задачу с наибольшим `oom_score` (примерно RSS с поправкой на `oom_score_adj`) и шлёт `SIGKILL`; в контейнере с `memory.max` то же самое происходит внутри cgroup, и pod показывает код выхода 137 / `OOMKilled` ([[docker-containers-and-resources]]).
- `memory.max` учитывает RSS **плюс page cache**, отнесённый к cgroup; сервис, который стримит большие файлы, может быть убит из-за кэша, который он не контролирует, если ядро не успеет его освободить. `limits.memory` в Kubernetes должен оставлять место для кучи, metaspace, стеков потоков, direct-буферов и кэша кода, а не только для `-Xmx`.

### Файлы, отображённые в память
- `mmap()` отображает файл в адресное пространство: чтения становятся ошибками страниц, обслуживаемыми из page cache, записи — грязными страницами, сбрасываемыми позже. Так работают индексные файлы Kafka и Lucene; в Java это доступно как `MappedByteBuffer` ([[java-nio]]). Zero-copy `sendfile()` передаёт страницы page cache прямо в сокет — это путь fetch у consumer'а Kafka ([[kafka-architecture]]).

## Пример
```bash
PID=$(pgrep -f esim-provisioning.jar)
grep -E 'VmSize|VmRSS|RssAnon|RssFile|VmSwap' /proc/$PID/status
#   VmSize:  6 402 112 kB   зарезервировано (куча -Xmx + стеки + кэш кода + mmap)
#   VmRSS:   1 213 400 kB   резидентно сейчас
#   RssAnon: 1 150 200 kB   куча, metaspace, стеки
#   RssFile:    63 200 kB   отображённые jar и библиотеки, разделяются с другими JVM
#   VmSwap:          0 kB   любое другое значение здесь — тревожный знак для JVM

# Ошибки страниц в секунду во время нагрузочного теста
perf stat -e page-faults,major-faults -p $PID -- sleep 10

# Что убило pod?
dmesg -T | grep -iE 'oom|killed process' | tail -3
#   Out of memory: Killed process 41233 (java) total-vm:6402112kB, anon-rss:3980120kB
#   -> anon RSS упёрся в лимит cgroup; куча + нативная память превысили limits.memory
```
`anon-rss`, близкий к `limits.memory`, при `-Xmx`, равном тому же числу, означает, что нативной памяти (metaspace, потоки, direct-буферы) не осталось места: задай `-XX:MaxRAMPercentage=70` или уменьши `-Xmx`, а не поднимай лимит вслепую.

## Подводные камни
- Ставить `-Xmx` равным лимиту памяти контейнера. JVM нужно на 20–40% больше кучи; OOM killer не бросает `OutOfMemoryError`, он шлёт `SIGKILL` без стектрейса.
- Судить о памяти по `VmSize`/`VSZ`: это адресное пространство, а не RAM. Смотри на `RSS`, а для cgroup — на `memory.current` за вычетом освобождаемых страниц `file` в `memory.stat`.
- Включать swap «на всякий случай» на хосте с базой данных или JVM: это превращает быстрый отказ в медленное, трудно диагностируемое разрушение с крупными ошибками страниц на каждом GC.
- Прозрачные большие страницы в режиме `always` на машине с Redis/Postgres: всплески задержки и раздувание памяти из-за уплотнения; используй `madvise` и дай JVM включать их явно.
- Оставлять `oom_score_adj` по умолчанию для sidecar: ядро может убить основную JVM (у неё больше RSS) вместо текущего лог-шиппера.
- Связанные заметки: [[stack-vs-heap-memory]] — как выделение памяти строится поверх страниц, [[cpu-caches-and-cache-lines]] — уровень под TLB.
