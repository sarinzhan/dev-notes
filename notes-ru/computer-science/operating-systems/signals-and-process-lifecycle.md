## Кратко
Процесс в Unix рождается через `fork()` (клонировать родителя) и обычно `execve()` (заменить себя новой программой), живёт, пока не вызовет `exit()` или не будет убит сигналом, и остаётся **зомби**, пока родитель не сделает `wait()` и не заберёт его код завершения. **Сигналы** — асинхронные уведомления ядра: `SIGTERM` просит процесс завершиться и может быть обработан, `SIGKILL` уничтожает его и не перехватывается. В контейнерах запущенный тобой процесс — это PID 1, и это меняет две вещи: для него отключена обработка сигналов по умолчанию, и он обязан подбирать сирот. Корректное завершение (graceful shutdown) JVM-сервиса — это цепочка: оркестратор шлёт `SIGTERM` → JVM запускает shutdown hooks → Spring перестаёт принимать запросы и дорабатывает текущие → процесс завершается с кодом 0 до таймаута на убийство. Взгляд на уровне команд Linux (`ps`, `kill`, таблица сигналов, `systemd`) — в [[linux-processes]].

## Основное

### Жизненный цикл
```c
// C-подобный псевдокод: то, что делает каждый shell и ProcessBuilder
pid_t pid = fork();                 // возвращается дважды: pid потомка в родителе, 0 в потомке
if (pid == 0) {
    dup2(logfd, STDOUT_FILENO);     // перенаправить до exec; fd переживают exec
    execve("/usr/bin/java", argv, envp);   // при успехе не возвращается
    _exit(127);                     // достигается, только если exec не удался
}
int status;
waitpid(pid, &status, 0);           // блокируется; подбирает зомби, получает код завершения или убивший сигнал
```
- `fork` дешёвый благодаря копированию страниц при записи (copy-on-write) ([[virtual-memory-and-paging]]); `posix_spawn`/`vfork` обходятся даже без этого, и именно их JDK использует для `ProcessBuilder` начиная с JDK 12.
- Код завершения: 8-битный код из `exit(n)`; если процесс убит сигналом, shell сообщает `128 + номер сигнала`. Выход 137 = `SIGKILL` (OOM killer или таймаут на убийство), 143 = `SIGTERM`, 139 = `SIGSEGV`.
- **Зомби**: завершился, но его ещё не подобрали через wait; держит только PID и статус. В небольшом количестве безвреден, но если родитель никогда не подбирает потомков, это утечка таблицы PID. **Сирота** (orphan): родитель умер раньше; процесс переподчиняется PID 1 (или ближайшему subreaper), который обязан его подобрать.
- `D` (непрерываемый сон, обычно дисковый/NFS IO) — единственное состояние, в котором даже `kill -9` ждёт, пока вернётся системный вызов; остальные состояния `ps` описаны в [[linux-processes]].

### Сигналы
- Доставка: ядро выставляет бит ожидания; сигнал обрабатывается, когда целевой поток в следующий раз возвращается в режим пользователя. В многопоточном процессе сигнал, адресованный процессу, получает **один** поток, который его не блокирует; в JVM для этого выделен поток «Signal Dispatcher».
- Реакции: действие по умолчанию (завершить, сделать дамп ядра, остановить, игнорировать), игнорирование (`SIG_IGN`) или обработчик. `SIGKILL` и `SIGSTOP` нельзя перехватить, заблокировать или игнорировать.
- Обработчики выполняются посреди того, что делал поток, поэтому внутри разрешены только async-signal-safe функции (никакого `malloc`, никаких блокировок). Реальные программы выставляют флаг или пишут в канал/`signalfd` и обрабатывают событие в главном цикле; нативный обработчик JVM ставит событие в очередь, а поток-диспетчер выполняет Java-код.
- Системные вызовы, прерванные сигналом, возвращают `EINTR`. `Thread.interrupt()` в Java с сигналами не связан: это флаг плюс пробуждение припаркованных потоков ([[threads-basics]]).
- Как JVM использует сигналы: `SIGSEGV` — для неявных проверок на null и опроса safepoint, `SIGQUIT` (`kill -3`) — для дампа потоков в stdout, `SIGTERM`/`SIGINT`/`SIGHUP` — для запуска shutdown hooks. `-Xrs` отключает последнее.

### SIGTERM против SIGKILL и корректное завершение
| | `SIGTERM` (15) | `SIGKILL` (9) |
|---|---|---|
| Можно обработать | да | нет |
| Что делает JVM | запускает хуки `Runtime.addShutdownHook`, затем выходит с 143 | ничего; ядро освобождает всё, выход 137 |
| Текущая работа | можно доработать | теряется; соединения сбрасываются, файлы записаны наполовину |
| Кто отправляет | `kill`, `docker stop`, kubelet при удалении pod, `systemctl stop` | те же вызывающие после таймаута; OOM killer |
- Spring Boot: `server.shutdown=graceful` и `spring.lifecycle.timeout-per-shutdown-phase=20s` перестают принимать новые соединения, завершают активные запросы, затем закрывают пулы и consumer'ы Kafka в обратном порядке бинов ([[spring-bean-lifecycle]], [[spring-kafka-consumer]]).
- Последовательность в Kubernetes: pod помечается Terminating → удаление из endpoints и `SIGTERM` происходят **параллельно** → `terminationGracePeriodSeconds` (по умолчанию 30 с) → `SIGKILL`. Поскольку удаление из endpoints запаздывает, `preStop` со sleep на 5–10 с перед `SIGTERM` не даёт слать новые запросы серверу, который уже завершает работу ([[kubernetes-basics]]).
- Бюджет: `preStop` + таймаут корректного завершения + время на rebalance Kafka и хуки должны уложиться в `terminationGracePeriodSeconds`, иначе JVM всё равно убьют посреди завершения.

### PID 1 в контейнерах
- Ядро не применяет действия по умолчанию к PID 1: `SIGTERM`, отправленный PID 1 без обработчика, **игнорируется**. JVM устанавливает обработчики, поэтому `java` в роли PID 1 — это нормально; shell-скрипт в entrypoint — нет.
- `sh -c "java -jar app.jar"` делает PID 1 процесс `sh`, а `java` — его потомком; `docker stop` шлёт сигнал `sh`, тот его игнорирует, и через 10 с всё убивается `SIGKILL`. Решение: `exec java -jar app.jar` в скрипте или exec-форма `ENTRYPOINT ["java", "-jar", "app.jar"]` ([[dockerfile-and-images]]).
- PID 1 также должен подбирать осиротевших зомби; `java` никогда не вызывает `wait()` для процессов, которые не запускала сама. Если приложение запускает вспомогательные процессы, используй `tini` или `docker run --init` в роли PID 1.

## Пример
```bash
# Наблюдать корректное завершение от начала до конца
PID=$(pgrep -f esim-provisioning.jar)
strace -f -e trace=rt_sigaction,shutdown,close,exit_group -p $PID 2>&1 &
kill -TERM $PID
#   --- SIGTERM {si_signo=SIGTERM, si_pid=3301} ---
#   [pid 4120] shutdown(104, SHUT_RD)      <- Tomcat перестаёт читать новые запросы
#   [pid 4155] close(142)                  <- Hikari закрывает сокеты Postgres
#   exit_group(143)                        <- shutdown hooks завершились до таймаута на убийство

# Проверить, какой процесс в контейнере PID 1 (от этого зависит вся история с корректным завершением)
kubectl exec esim-provisioning-7c9d -- cat /proc/1/cmdline | tr '\0' ' '
#   java -XX:MaxRAMPercentage=70 -jar /app/app.jar       <- хорошо
#   /bin/sh -c java -jar /app/app.jar                      <- SIGTERM игнорируется

# Зомби копятся под PID 1, который их не подбирает
ps -eo pid,ppid,stat,cmd | awk '$3 ~ /Z/'
```
Код выхода 143 в last-state pod означает, что JVM завершилась сама после `SIGTERM`; 137 — что она ещё работала, когда истёк grace period, или в cgroup закончилась память.

## Подводные камни
- Shell-форма `ENTRYPOINT`/`CMD` или скрипт-обёртка без `exec`: каждый deploy превращается в `SIGKILL` после таймаута, текущие запросы падают, а rebalance Kafka занимает полный session timeout.
- Медленная работа в shutdown hook без дедлайна (сброс данных в удалённый сервис, ожидание блокировки): если она превысит grace period, `SIGKILL` всё равно придёт, и наполовину завершённое состояние хуже быстрой остановки.
- Рассчитывать, что блоки `finally` или `@PreDestroy` выполнятся при `SIGKILL`: ничего не выполнится. Проектируй с расчётом на падения (идемпотентные consumer'ы, [[outbox-pattern]]), а не на чистые выходы.
- `kill -9` как первый рефлекс на процесс в состоянии `D`: он ничего не сделает, пока не вернётся IO, и скроет настоящую проблему (мёртвое NFS-монтирование или умирающий диск).
- Забывать, что readiness-пробы и удаление из endpoints асинхронны: без задержки в `preStop` завершающийся pod ещё несколько секунд получает трафик и отвечает connection refused.
- Связанные заметки: [[linux-processes]] — таблица сигналов и `systemd`, [[docker-containers-and-resources]] — `--stop-timeout`, `--init` и коды выхода на практике.
