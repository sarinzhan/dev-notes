## Кратко
**Взаимоблокировка** (deadlock) — это набор потоков, каждый из которых вечно ждёт ресурс, удерживаемый другим участником набора. Для неё нужны четыре условия одновременно: **взаимное исключение**, **удержание и ожидание**, **отсутствие вытеснения**, **циклическое ожидание**; нарушь любое — и взаимоблокировка невозможна. На практике её предотвращают глобальным порядком захвата блокировок, ограниченным ожиданием (`tryLock` с таймаутом) и правилом никогда не держать блокировку во время вызова кода, который ты не контролируешь. На уровне ОС примитивы такие: **мьютекс** (mutex; есть владелец, один держатель), **семафор** (semaphore; счётчик, владельца нет) и **условная переменная** (condition variable; ждать выполнения предиката, отпустив мьютекс); в Linux все они построены на **futex**. Мониторы Java, `ReentrantLock` и взаимоблокировки на уровне JVM описаны в [[synchronization-and-monitors]] и [[concurrency-hazards]]; общая теория примитивов — в [[mutex-semaphore-monitor]].

## Основное

### Четыре условия Коффмана
| Условие | Смысл | Как нарушить |
|---|---|---|
| Взаимное исключение | ресурс нельзя разделять | использовать lock-free или неизменяемые данные ([[lock-free-and-cas]], [[immutability-and-side-effects]]) |
| Удержание и ожидание | поток держит ресурсы, запрашивая новые | захватить всё сразу или отпустить перед запросом (двухфазно, `tryLock` по принципу «всё или ничего») |
| Отсутствие вытеснения | ресурс нельзя отобрать | таймауты: `tryLock(1, SECONDS)`, `lock_timeout` в Postgres; транзакции можно откатить, поэтому базы данных *могут* вытеснять |
| Циклическое ожидание | цикл в графе ожидания (wait-for graph) | глобальный порядок блокировок (всегда блокировать счета по возрастанию id) |
- Базы данных обнаруживают взаимоблокировки, ища циклы в графе ожидания, и убивают одну жертву с ошибкой (`40P01` в Postgres); приложение делает retry. У блокировок в приложении такого детектора нет, поэтому взаимоблокировка в JVM вечна: `jstack` печатает «Found one Java-level deadlock», и помогает только перезапуск ([[postgres-locks]]).

### Стратегии
- **Предотвращение** (prevention): спроектировать так, чтобы условие не могло выполниться. Основной инструмент — порядок блокировок; обычно он ломается на вложенных `synchronized` между бинами.
- **Избегание** (avoidance): алгоритм банкира выдаёт ресурс, только если система остаётся в безопасном состоянии. Требует заранее знать максимальные потребности; материал учебников, в системах общего назначения не используется.
- **Обнаружение и восстановление** (detection and recovery): позволить случиться, найти циклы, прервать жертву. Базы данных, Temporal и движки workflow (таймауты), liveness-пробы Kubernetes, перезапускающие зависший pod.
- **Игнорирование** («страус»): приемлемо, когда взаимоблокировки редки, а перезапуски дёшевы; ядра ОС так поступают с блокировками в пространстве пользователя. Ошибки порядка ловят заранее с помощью `ThreadSanitizer`, `jcstress` или `jstack` под нагрузкой.

### Примитивы уровня ОС
| Примитив | Состояние | Владелец | Типичное применение | Реализация в Linux |
|---|---|---|---|---|
| Спинлок (spinlock) | 1 бит | держатель | ядро, очень короткие критические секции, спать нельзя | атомарный test-and-set, активное ожидание в цикле |
| Мьютекс | заблокирован/свободен | да; разблокирует только владелец | защита структуры данных | `pthread_mutex_t` поверх futex: CAS в пространстве пользователя, `futex(FUTEX_WAIT)` только при конкуренции |
| Семафор | счётчик ≥ 0 | владельца нет; `post` может сделать кто угодно | ограничить N одновременных пользователей; сигналы между потоками | `sem_t` поверх futex |
| Условная переменная | очередь ожидающих | в паре с мьютексом | ждать, пока предикат станет истинным | `pthread_cond_t`; `wait` атомарно отпускает мьютекс и засыпает |
| Блокировка чтения-записи (read-write lock) | счётчик читателей + флаг писателя | писатель или читатели | данные, которые в основном читают | `pthread_rwlock_t` |
| Барьер (barrier) | счётчик | нет | синхронизация по фазам | `pthread_barrier_t` |
- **futex** (fast user-space mutex): слово блокировки лежит в пользовательской памяти; захват и освобождение без конкуренции — это один CAS без системного вызова. `futex()` вызывается, только когда потоку нужно заснуть или разбудить другой. Поэтому `strace -c` на JVM с конкуренцией показывает тысячи вызовов `futex`, и поэтому `synchronized` без конкуренции стоит около 20 нс.
- **Мьютекс против двоичного семафора**: у обоих два состояния, но у мьютекса есть владелец (разблокировка из другого потока — ошибка; возможны наследование приоритета и рекурсивный захват), а у семафора нет (поток A может сделать `post` того, на чём сделал `wait` поток B, что делает его инструментом сигнализации). Интервьюеры любят это различие.
- **Инверсия приоритетов** (priority inversion): низкоприоритетный поток держит мьютекс, нужный высокоприоритетному, а поток среднего приоритета не даёт работать низкоприоритетному, и высокоприоритетный ждёт бесконечно (Mars Pathfinder, 1997). Решение: наследование приоритета (`PTHREAD_PRIO_INHERIT`), которое обычный семафор дать не может, потому что у него нет владельца.

- Блокировки чтения-записи меняют одно голодание на другое: с приоритетом писателей голодают читатели, с приоритетом читателей — писатели ([[locks-and-lock-free]]).

## Пример
```java
// Перевод между двумя балансовыми счетами SIM: классическая взаимоблокировка из-за порядка блокировок и её исправление.
// У каждого Account свой ReentrantLock (или synchronized); блокировать a, затем b в одном потоке
// и b, затем a в другом — это циклическое ожидание.

void transfer(Account from, Account to, long amount) {
    Account first  = from.id().compareTo(to.id()) < 0 ? from : to;   // глобальный порядок по id
    Account second = first == from ? to : from;
    first.lock().lock();
    try {
        second.lock().lock();
        try {
            from.withdraw(amount);
            to.deposit(amount);
        } finally { second.lock().unlock(); }
    } finally { first.lock().unlock(); }
}

// Альтернатива: без порядка, но и без бесконечного удержания и ожидания
boolean tryTransfer(Account from, Account to, long amount) throws InterruptedException {
    if (!from.lock().tryLock(200, TimeUnit.MILLISECONDS)) return false;
    try {
        if (!to.lock().tryLock(200, TimeUnit.MILLISECONDS)) return false;  // отступить, вызывающий повторит с джиттером
        try { from.withdraw(amount); to.deposit(amount); return true; }
        finally { to.lock().unlock(); }
    } finally { from.lock().unlock(); }
}
```
В базе данных тот же перевод попадает во взаимоблокировку, если две транзакции делают `UPDATE` строк в противоположном порядке; упорядочи `SELECT ... FOR UPDATE` по первичному ключу или дай Postgres обнаружить её и сделай retry на `40P01`.

## Подводные камни
- Вызывать неизвестный код (слушатели, колбэки, бин другого сервиса, логгер со своей блокировкой), держа блокировку: неизвестно, что он блокирует, поэтому порядок соблюсти нельзя.
- Вложенный `synchronized` на `this` плюс `ConcurrentHashMap.compute`, который обращается обратно к тому же объекту: `compute` держит блокировку корзины, повторный вход приводит к взаимоблокировке или бросает `IllegalStateException: Recursive update`.
- Взаимоблокировка пула потоков без единой блокировки: задачи в ограниченном пуле отправляют подзадачи в тот же пул и блокируются на их `Future`; все рабочие потоки ждут работу из очереди, которая никогда не выполнится ([[executors-and-thread-pools]]).
- Таймауты скрывают, а не исправляют ошибки порядка: с `tryLock` система «работает» с 1% отказов; логируй таймауты и ставь на них алерты, чтобы найти первопричину.
- Семафор вместо мьютекса: ошибка, при которой `release()` вызывается дважды, пускает два потока в критическую секцию, и семафор не может это обнаружить.
- Связанные заметки: [[mutex-semaphore-monitor]] — примитивы как абстрактные понятия, [[distributed-locks-and-fencing]] — та же проблема между процессами, где граф ожидания заменяют таймауты и fencing-токены.
