## Кратко
Пользовательский код не может напрямую обращаться к железу, другим процессам или структурам данных ядра; он просит ядро через **системные вызовы** (syscalls), которые переключают CPU из режима пользователя в режим ядра, выполняют код ядра и переключают обратно. Каждый открытый ресурс (файл, сокет, канал, таймер, экземпляр epoll) представлен процессу небольшим целым числом — **файловым дескриптором** (file descriptor, fd), индексом в таблице процесса, которая указывает на объекты ядра. «Всё есть файл» означает, что большинство из них можно `read`, `write`, `close` и `poll` одними и теми же вызовами. `strace` показывает системные вызовы процесса, а таблица fd видна в `/proc/<pid>/fd`.

## Основное

### Граница между пользователем и ядром
- Кольца привилегий CPU: режим пользователя (ring 3) не может выполнять привилегированные инструкции и обращаться к памяти ядра; режим ядра (ring 0) может. Именно эта граница делает возможными [[process-management|изоляцию процессов]] и [[memory-management|виртуальную память]].
- Системный вызов — это контролируемый вход: номер вызова и аргументы кладутся в регистры, выполняется `syscall` (x86-64), CPU прыгает в точку входа ядра, ядро проверяет аргументы (пользовательские указатели проверяются, им никогда не доверяют), выполняет работу и возвращает значение или `-errno`.
- Стоимость: около 100–300 нс на само переключение после защит от Spectre/Meltdown плюс то, что делает сам вызов. Тысячи мелких вызовов `read(fd, buf, 1)` медленные из-за переключений, а не из-за байтов; поэтому существуют буферизованные потоки ([[java-io-streams]]), и поэтому `vDSO` отображает `clock_gettime` в пространство пользователя, так что `System.nanoTime()` вообще не переходит в ядро.
- Блокирующие системные вызовы (`read` на пустом сокете, `accept`, ожидание `futex`) усыпляют поток; ядро будит его, когда приходит событие. Это и есть «поток заблокирован» на уровне ОС ([[io-models-blocking-nonblocking-epoll]]).
- Библиотеки оборачивают системные вызовы: `fopen` → `openat`, Java `FileInputStream.read` → JNI → `read`. `strace -f -p <pid>` показывает настоящие вызовы под любой абстракцией.

### Распространённые семейства системных вызовов
| Область | Вызовы |
|---|---|
| Файлы | `openat`, `read`, `write`, `pread64`, `lseek`, `fstat`, `fsync`, `close`, `mmap` |
| Процессы | `clone`, `execve`, `wait4`, `exit_group`, `kill`, `getpid` ([[linux-processes]]) |
| Сокеты | `socket`, `bind`, `listen`, `accept4`, `connect`, `sendto`, `recvfrom`, `setsockopt`, `shutdown` ([[sockets-and-connection-pooling]]) |
| Мультиплексирование | `poll`, `epoll_create1`, `epoll_ctl`, `epoll_wait`, `io_uring_*` |
| Синхронизация | `futex` (сюда приходит любая конкуренция за `synchronized`/`ReentrantLock`), `nanosleep` |
| Память | `brk`, `mmap`, `munmap`, `madvise`, `mprotect` |

### Файловые дескрипторы
- **Таблица fd** у каждого процесса: индекс → указатель на **описание открытого файла** (open file description: смещение, флаги, режим) → указатель на нижележащий inode/сокет. 0, 1, 2 — это stdin, stdout, stderr; следующий `open` возвращает наименьший свободный номер.
- `fork()` копирует таблицу: родитель и потомок разделяют одни и те же описания открытых файлов, включая смещение в файле. `dup2(fd, 1)` перенаправляет stdout; shell реализует `>` и `|` через `open`/`pipe` + `dup2` перед `execve`.
- `FD_CLOEXEC` / `O_CLOEXEC`: автоматически закрыть этот fd при `exec`, чтобы дочерняя программа не унаследовала твой сокет базы данных. Java выставляет его на всё, что открывает.
- Лимиты: `ulimit -n` (мягкий, часто 1024 в старых настройках по умолчанию, 1 048 576 в современных дистрибутивах и в контейнерах) и общесистемный `fs.file-max`. Считается каждый сокет, каждый открытый файл лога, каждый экземпляр `epoll`, каждый JAR, отображённый JVM. «Too many open files» (`EMFILE`) — классический симптом утёкшего `HttpClient`, пула соединений без лимитов или незакрытых стримов `Files.list`.
- Сокеты — тоже fd: HTTP-сервер с 10 тыс. keep-alive соединений держит 10 тыс. fd. `ss -tnp` сопоставляет сокеты процессам; `lsof -p <pid>` или `ls -l /proc/<pid>/fd` показывает всё.
- Специальные fd: `eventfd` (счётчик пробуждений, используется в Netty), `timerfd`, `signalfd`, `inotify` (`WatchService` в [[java-nio]]), `memfd`. Они существуют, чтобы один `epoll_wait` мог ждать на всех них сразу.

### «Всё есть файл» и где это ломается
- Единый интерфейс: `cat /proc/cpuinfo`, `echo 1 > /sys/...`, `read` из сокета, `write` в канал. Благодаря этому инструменты комбинируются.
- Не всё вписывается: сокетам нужны `connect`/`accept`, `ioctl` — запасной выход для управления конкретными устройствами, а обычные файлы для `epoll` всегда «готовы», поэтому файловый IO в Linux не может быть по-настоящему неблокирующим без AIO или `io_uring`.

## Пример
```bash
# Что на самом деле делает JVM, когда открывает соединение с Postgres?
strace -f -e trace=socket,connect,setsockopt,write,read -p $(pgrep -f esim-provisioning.jar) 2>&1 | head
#   socket(AF_INET, SOCK_STREAM|SOCK_CLOEXEC, IPPROTO_TCP) = 142
#   setsockopt(142, SOL_TCP, TCP_NODELAY, [1], 4) = 0
#   connect(142, {sa_family=AF_INET, sin_port=htons(5432), sin_addr=...}, 16) = 0
#   write(142, "\0\0\0\10\4\322\26/", 8) = 8            <- SSLRequest / стартовое сообщение
#   read(142, "N", 1) = 1

# Какие fd держит процесс, сгруппированные по типу?
ls -l /proc/$(pgrep -f esim-provisioning.jar)/fd | awk '{print $NF}' | sed 's/:.*//' | sort | uniq -c | sort -rn
#   312 socket      <- пул Hikari + Kafka + входящие HTTP keep-alive
#    86 /opt/app/lib/...jar
#     4 anon_inode  <- epoll, eventfd
#     3 /dev/null

# Подсчитать системные вызовы по типам за 5 с: найти «болтливый» путь в коде
strace -c -f -p $(pgrep -f esim-provisioning.jar) -- sleep 5 2>&1 | head -15
```
Если в `strace -c` вызовов `futex` намного больше, чем `read`/`write`, это конкуренция за блокировки, а не IO ([[synchronization-and-monitors]]).

## Подводные камни
- Запускать `strace` на нагруженной продовой JVM: он использует `ptrace`, который останавливает процесс на каждом системном вызове и может замедлить его в 10–50 раз. Используй `-c` ненадолго или `perf trace` / eBPF (`bpftrace`, `opensnoop`).
- Читать или писать по несколько байтов за системный вызов в цикле (небуферизованный `FileOutputStream`, `OutputStream.write(int)`): доминирует стоимость переключения; оберни в буфер или используй пакеты `ByteBuffer`.
- Утечки fd — бомбы замедленного действия: сервис работает днями, потом каждый новый сокет падает с `EMFILE`, а health check всё ещё проходит, потому что использует существующее соединение. Ставь алерт на `process_open_fds` из Micrometer-биндера JVM.
- Считать, что контейнер наследует `ulimit -n` хоста: Docker и Kubernetes задают свои значения (`--ulimit nofile` или значение runtime по умолчанию); проверяй внутри pod.
- `close()` может завершиться ошибкой (`EIO` на NFS, `EINTR`), и именно там проявляются отложенные ошибки записи; игнорирование его результата тихо теряет данные. Кроме того, закрытие fd, который использует другой поток, — это гонка: номер может немедленно переиспользоваться для нового сокета.
- Связанные заметки: [[io-models-blocking-nonblocking-epoll]] — что происходит, когда fd не готов, [[linux-memory-filesystems-io]] — `/proc`, `/sys` и page cache за файловыми системными вызовами.
