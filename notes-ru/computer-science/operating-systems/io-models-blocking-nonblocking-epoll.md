## Кратко
Программа может ждать данные на сокете четырьмя способами. **Блокирующий**: поток спит в `read`, пока не придут байты (один поток на соединение). **Неблокирующий**: `read` сразу возвращает `EAGAIN`, и ты опрашиваешь в цикле (сам по себе тратит CPU впустую). **Мультиплексирование** (multiplexing): один поток спрашивает ядро «скажи, какие из этих N дескрипторов готовы» через `select`/`poll`/`epoll`, а затем делает неблокирующие чтения из готовых; так Netty, nginx, Node и Java NIO обслуживают 100 тыс. соединений на нескольких потоках. **Асинхронный**: ядро само выполняет IO и сообщает о завершении (IOCP в Windows, `io_uring` в Linux). API `Selector` в Java поверх epoll описан в [[java-nio]]; [[virtual-threads]] дают код в блокирующем стиле поверх мультиплексирования.

## Основное

### Пять моделей (классификация Стивенса)
| Модель | Ожидание данных | Копирование данных в пространство пользователя | Потоков на соединение | Системные вызовы |
|---|---|---|---|---|
| Блокирующий IO | поток спит | поток блокируется | 1 | `read` |
| Неблокирующий IO | приложение опрашивает (`EAGAIN`) | поток ненадолго блокируется | меньше, но CPU крутится вхолостую | `read` с `O_NONBLOCK` |
| Мультиплексирование IO | поток спит в `epoll_wait` на многих fd | поток сам делает `read` | мало | `epoll_wait` + `read` |
| Управляемый сигналами | `SIGIO` при готовности | поток сам делает `read` | мало | используется редко |
| Асинхронный IO | ядро делает и то, и другое и сообщает о завершении | в потоке приложения ничего | мало | `io_uring`, POSIX AIO, IOCP |
- По-настоящему асинхронна только последняя: в первых четырёх копирование выполняет поток приложения. «Async» в Java-библиотеках (Netty, WebFlux, [[spring-reactive-webclient-sse]]) обычно означает мультиплексирование с колбэками, а не AIO ядра.
- Готовность против завершения: epoll сообщает, что fd **готов** (есть байты для чтения или место в буфере для записи); `io_uring` сообщает, что операция **завершена** и данные уже в твоём буфере.

### Почему «поток на соединение» перестаёт масштабироваться
- Каждый заблокированный поток стоит задачу ядра, стек (1 МиБ резервируется), работу планировщика и переключение контекста на каждое пробуждение ([[processes-and-threads]], [[cpu-scheduling]]). 10 тыс. простаивающих keep-alive соединений = 10 тыс. спящих потоков, которые ничего не делают, а только занимают память. Это проблема C10K.
- При мультиплексировании простаивающее соединение стоит только fd и буфер сокета в ядре; число потоков зависит от числа CPU, а не от числа соединений.
- Цена — стиль программирования: состояние каждого соединения должно быть явным (конечный автомат или реактивный конвейер), потому что нет потока, который держал бы его на своём стеке. Виртуальные потоки и горутины Go это скрывают: среда выполнения паркует «поток» на блокирующем вызове и использует epoll под капотом, так что ты пишешь блокирующий код и получаешь мультиплексированный IO.

### select против poll против epoll
| | `select` | `poll` | `epoll` |
|---|---|---|---|
| Набор отслеживаемых fd | фиксированная битовая карта, `FD_SETSIZE` = 1024 | массив `pollfd` любого размера | объект ядра; `epoll_ctl` добавляет/удаляет fd один раз |
| Стоимость вызова | O(max fd): копирование карты туда и обратно, сканирование | O(n): копирование массива туда и обратно, сканирование | O(готовых): ядро ведёт список готовых |
| Результат | сам сканируешь все fd на готовность | сам сканируешь все записи | возвращает только готовые fd |
| Срабатывание | по уровню | по уровню | по уровню (по умолчанию) или по фронту (`EPOLLET`) |
| Переносимость | везде | POSIX | только Linux (`kqueue` в BSD/macOS, IOCP в Windows) |
- **По уровню** (level-triggered): `epoll_wait` продолжает сообщать о fd, пока в нём остаются непрочитанные данные. Просто, безопасно, используется в Java NIO.
- **По фронту** (edge-triggered): сообщается один раз при изменении состояния; нужно вычитать fd до `EAGAIN`, иначе пробуждение потеряется. Меньше системных вызовов (используют nginx и нативный транспорт `epoll` в Netty), легче ошибиться.
- Эффект «громового стада» (thundering herd): много потоков, ждущих на одном слушающем сокете, просыпаются от одного соединения; решение — `EPOLLEXCLUSIVE` или `SO_REUSEPORT` (свой слушающий сокет на каждый поток).

### Цикл реактора
```c
// C-подобный псевдокод того, что делают EventLoop в Netty и Selector в Java
int ep = epoll_create1(0);
epoll_ctl(ep, EPOLL_CTL_ADD, listen_fd, &(struct epoll_event){.events = EPOLLIN, .data.fd = listen_fd});
for (;;) {
    int n = epoll_wait(ep, events, MAX, -1);          // спит, пока что-то не станет готовым
    for (int i = 0; i < n; i++) {
        int fd = events[i].data.fd;
        if (fd == listen_fd) {                          // новое соединение
            int c = accept4(listen_fd, NULL, NULL, SOCK_NONBLOCK);
            epoll_ctl(ep, EPOLL_CTL_ADD, c, &(struct epoll_event){.events = EPOLLIN, .data.fd = c});
        } else {
            ssize_t r = read(fd, buf, sizeof buf);      // неблокирующий: возвращает то, что есть
            if (r == 0) { close(fd); continue; }        // собеседник закрыл соединение
            if (r < 0 && errno == EAGAIN) continue;     // ложное срабатывание, пока ничего нет
            handle(fd, buf, r);                         // НЕ ДОЛЖЕН блокироваться, иначе встанут все соединения
        }
    }
}
```
Инвариант из последнего комментария — вся дисциплина реактивного программирования: блокирующий вызов JDBC или `Thread.sleep` внутри цикла замораживает все соединения этого event loop. Поэтому [[spring-reactive-webclient-sse|WebFlux]] нужен R2DBC, и поэтому Netty предупреждает о блокирующих обработчиках.

### Дисковый IO устроен иначе
- Обычные файлы для epoll всегда «готовы»; чтение всё равно может зависнуть на диске. Варианты: блокирующие чтения в пуле потоков (Netty, Node, Tomcat), `O_DIRECT` + `libaio` (базы данных) или `io_uring` (Linux 5.1+): настоящие асинхронные очереди отправки и завершения, которые покрывают и сокеты; у Postgres 18 и Netty есть бэкенды на `io_uring`.

## Пример
```bash
# Посмотреть, какую модель использует работающий сервер
strace -f -e trace=epoll_wait,epoll_ctl,accept4,read,futex -p $(pgrep -f esim-provisioning.jar) 2>&1 | head -20
#   [pid 4121] epoll_wait(89, [{EPOLLIN, {u32=104}}], 1024, -1) = 1    <- поток-поллер Tomcat NIO
#   [pid 4121] read(104, ..., 8192) = 517                                <- байты запроса
#   [pid 4137] futex(0x7f..., FUTEX_WAIT_PRIVATE, ...)                   <- рабочий поток припаркован, ждёт работу
#   [pid 4140] read(97, ..., 8192) = -1 EAGAIN                           <- клиент Kafka, неблокирующий сокет
```
Tomcat — гибрид: один или два потока-поллера выполняют `epoll_wait` и передают готовые соединения в ограниченный пул рабочих потоков, который затем делает блокирующий JDBC. Netty/WebFlux держат всё на event loop. Виртуальные потоки делают пул рабочих неограниченным и дешёвым, а планировщик JDK мультиплексирует их поверх epoll.

## Подводные камни
- Блокировка внутри event loop (JDBC, `RestTemplate`, файловый IO, блок `synchronized` с конкуренцией) останавливает все соединения этого цикла; симптомы — всплески задержки при низком CPU.
- Мыслить лимитами эпохи `FD_SETSIZE`: `select` ломается на fd 1024, даже если открыто всего несколько; современный код никогда не должен его использовать.
- Epoll по фронту без вычитывания до `EAGAIN`: соединения молча зависают с непрочитанными данными.
- Путать «неблокирующий» с «быстрым»: неблокирующий `read`, возвращающий `EAGAIN` в плотном цикле, сжигает ядро. Всегда сочетай его с уведомлением о готовности.
- Ждать, что epoll поможет при нагрузке, упирающейся в диск: файловые fd всегда готовы; используй пул потоков или `io_uring`.
- Связанные заметки: [[syscalls-and-file-descriptors]] — таблица fd, за которой следит epoll, [[sockets-and-connection-pooling]] и [[tcp-handshake-and-connection-states]] — что значит «готов» для сокета.
