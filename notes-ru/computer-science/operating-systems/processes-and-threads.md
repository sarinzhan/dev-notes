## Кратко
**Процесс** — это единица изоляции: собственное виртуальное адресное пространство, таблица файловых дескрипторов, учётные данные и PID. **Поток** — это единица планирования: контекст выполнения (регистры, стек, счётчик команд), который живёт внутри процесса и разделяет его память с соседними потоками. Переключение между потоками одного процесса дешевле, чем между процессами, в основном потому, что адресное пространство (а значит, TLB и кэши) остаётся тёплым. Особенности Linux, `fork`/`exec` и сигналы описаны в [[linux-processes]]; эта заметка — о понятиях, которых ждёт интервьюер.

## Основное

### Что ядро хранит для каждого процесса
- **Блок управления процессом** (process control block, PCB; `task_struct` в Linux) содержит: PID и родителя, состояние (выполняется, готов, заблокирован, зомби), сохранённые регистры CPU, указатель на таблицы страниц, открытые файловые дескрипторы, обработчики сигналов, приоритет планирования, счётчики учёта, принадлежность к cgroup.
- **Адресное пространство** приватное: код (text), инициализированные данные, куча (`brk`/`mmap`), разделяемые библиотеки и по одному стеку на поток ([[memory-management]], [[stack-vs-heap-memory]]).
- Изоляцию обеспечивает MMU: процесс не может читать память другого процесса, если оба явно не отобразили разделяемый сегмент ([[ipc-mechanisms]]).

### Процесс против потока
| | Процесс | Поток |
|---|---|---|
| Память | собственное адресное пространство | общая с процессом |
| Стоимость создания | высокая (`fork` копирует таблицы страниц, страницы копируются при записи) | низкая (`clone` с общей VM; только новый стек и регистры) |
| Переключение контекста | сохранить регистры + переключить таблицы страниц → сброс TLB (смягчается PCID/ASID) | сохранить регистры + переключить указатель стека; TLB остаётся валидным |
| Изоляция отказов | падение убивает только этот процесс | один segfault или непойманная нативная ошибка убивает все потоки |
| Взаимодействие | IPC: каналы, сокеты, разделяемая память | обычная память; нужна синхронизация ([[race-conditions-and-critical-sections]]) |
| Типичное применение | воркеры nginx, бэкенды Postgres, вкладки Chrome | обработчики запросов Tomcat, IO-потоки клиента Kafka, рабочие потоки GC |
- Postgres выбрал модель «процесс на соединение»; поэтому соединения дорогие и поэтому важен пул соединений ([[hikaricp-pool-sizing]]). JVM выбрала один процесс с многими потоками, поэтому `StackOverflowError` в одном потоке можно пережить, а `OutOfMemoryError` в нативной памяти — нет.

### Стоимость переключения контекста
- Прямая стоимость: переход в ядро, сохранение и восстановление регистров, учёт в планировщике. Обычно 1–3 мкс на современном железе ([[latency-numbers]]).
- Косвенная стоимость, обычно бо́льшая: рабочего набора нового потока нет в L1/L2, а предсказатель переходов холодный ([[cpu-caches-and-cache-lines]]). Поток, который блокируется после каждых нескольких микросекунд работы, тратит на переключения больше времени, чем на работу.
- `vmstat 1` показывает переключения контекста в секунду в столбце `cs`; `pidstat -w` показывает по процессам добровольные (блокировка на IO или блокировке) и принудительные (истёк квант, вытеснение) переключения. Много принудительных — конкуренция за CPU; много добровольных — ожидание IO или блокировок.

### Потоки пользовательского уровня против потоков ядра
| Модель | Кто планирует | Блокирующий системный вызов | Примеры |
|---|---|---|---|
| 1:1, потоки ядра | ядро | блокирует только этот поток | Linux NPTL, платформенные потоки JVM |
| N:1, пользовательские потоки (green threads) | библиотека в пространстве пользователя | блокирует весь процесс | ранние JVM, классические библиотеки корутин |
| M:N | оба: библиотека мультиплексирует M пользовательских потоков на N потоков ядра | библиотека должна перехватывать блокирующие вызовы и вместо них парковать пользовательский поток | горутины Go, Java [[virtual-threads]] (JDK 21) |
- Платформенные потоки Java — 1:1: `new Thread().start()` заканчивается в `clone()`, и их видно через `top -H -p <pid>` или `ls /proc/<pid>/task`. Виртуальные потоки — M:N поверх `ForkJoinPool` из потоков-носителей (carrier threads); JDK снимает их с носителя на блокирующем IO и `LockSupport.park`, но **закрепляет** (pinning) на `synchronized` (исправлено в JDK 24) и в нативных фреймах.
- Почему M:N вернулась: поток ядра стоит около 1 МиБ зарезервированного стека плюс `task_struct`, и десятки тысяч таких потоков замедляют планировщик. Стек виртуального потока — от нескольких сотен байт до нескольких КиБ в куче ([[jvm-memory-areas]]).

### Состояния процессов и потоков
- `New → Ready → Running → (Blocked ↔ Ready) → Terminated`. «Заблокирован» — нормальное состояние серверного потока: ожидание сокета, блокировки или чтения с диска.
- `Thread.State` в Java соответствует им приблизительно: `RUNNABLE` покрывает и выполнение, и готовность с точки зрения ОС (и даже блокировку в нативном IO), `BLOCKED` — ожидание монитора, `WAITING`/`TIMED_WAITING` — поток припаркован ([[threads-basics]]).

## Пример
```bash
# Приложение на Spring Boot: один процесс, много потоков ядра
PID=$(pgrep -f 'esim-provisioning.jar')
ls /proc/$PID/task | wc -l          # число потоков (задач ядра)
cat /proc/$PID/status | grep -E 'Threads|VmRSS|VmSize|voluntary'
#   VmSize:   6 412 340 kB   -> зарезервированное виртуальное пространство (куча + стеки + mmap)
#   VmRSS:      812 004 kB   -> реально резидентно
#   Threads:  57
#   voluntary_ctxt_switches:    183 214
#   nonvoluntary_ctxt_switches:   1 042

# CPU по потокам: какие потоки JVM горячие?  (nid в дампе jstack = TID в hex)
top -H -p $PID -n 1 | head -20
printf '%x\n' 12345                 # перевести TID в nid, который показывает jstack
```
Строка дампа потоков вида `"kafka-producer-network-thread" ... nid=0x3039` указывает на задачу ядра 12345: это один и тот же поток, увиденный ОС и JVM.

## Подводные камни
- Считать потоки бесплатными: каждый платформенный поток резервирует `-Xss` (по умолчанию 1 МиБ) виртуальной памяти и структуру ядра; архитектура «поток на запрос» умирает на нескольких тысячах одновременных запросов. Используй ограниченный пул ([[executors-and-thread-pools]]) или виртуальные потоки.
- Забывать, что переключение контекста между процессами сбрасывает TLB: архитектура, которая гоняет запрос через несколько процессов (sidecar, локальные прокси), платит за это на каждом переходе.
- Измерять только загрузку CPU: сервис с 20% CPU и огромным `cs` упирается в ожидание блокировок или IO, а не в вычисления. Проверь `pidstat -w`, прежде чем добавлять ядра.
- `ps` показывает процесс в состоянии `R`, хотя все потоки JVM, кроме GC, могут быть припаркованы: состояние процесса — это сводка по его потокам.
- Связанные заметки: [[cpu-scheduling]] — как ядро выбирает следующий поток, [[linux-processes]] — `fork`, `exec`, сигналы и `systemd`.
