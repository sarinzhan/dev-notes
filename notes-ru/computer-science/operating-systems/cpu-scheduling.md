## Кратко
Планировщик (scheduler) решает, какой готовый к выполнению поток получит ядро и на сколько. Современные ядра общего назначения **вытесняющие** (preemptive): поток прерывается по таймеру или при пробуждении потока с более высоким приоритетом. И они **справедливые** (fair): Linux CFS и пришедший ему на смену EEVDF дают каждой готовой задаче долю CPU, взвешенную по `nice`. «Средняя нагрузка» (load average) считает задачи, которым нужен CPU (а в Linux ещё и задачи в непрерываемом ожидании диска), а не процент загрузки CPU. Для бэкенд-разработчика практические вопросы такие: почему задержка растёт, когда машина занята, что на самом деле делают `nice` и квоты CPU в cgroup, и почему контейнер с `cpu: 1` троттлится.

## Основное

### Цели и базовый компромисс
- Пропускная способность (throughput, работа в секунду), задержка (latency, время от пробуждения до запуска), справедливость и соблюдение приоритетов. Максимизировать все четыре нельзя: длинные кванты времени помогают пропускной способности (меньше переключений контекста, тёплые кэши), но ухудшают задержку.
- **Вытесняющая** многозадачность: ядро может отобрать CPU по тику таймера или когда просыпается задача с более высоким приоритетом. **Кооперативная**: задача работает, пока сама не уступит. Ядра вытесняющие; многие планировщики в пространстве пользователя (Java [[virtual-threads]], event loop в JavaScript, Go до 1.14) кооперативные: виртуальный поток, крутящийся в цикле на CPU, блокирует свой поток-носитель (carrier) и лишает CPU другие виртуальные потоки.
- Для серверов путь пробуждения важнее кванта: поток запроса обычно заблокирован на сокете, просыпается, когда приходят данные, работает несколько сотен микросекунд и снова блокируется. Задержка планирования = время между пробуждением и фактическим запуском.

### Классические алгоритмы (словарь для собеседований)
| Алгоритм | Идея | Проблема |
|---|---|---|
| FCFS | выполнять в порядке поступления | одна длинная задача задерживает всех (эффект конвоя) |
| SJF / SRTF | сначала самая короткая задача | нужно знать длину задачи; длинные задачи голодают |
| Round-robin | фиксированный квант, по кругу по очереди готовых | квант слишком мал → накладные расходы на переключение; слишком велик → задержка |
| Приоритетный | сначала самый высокий приоритет | голодание, если приоритеты не «стареют» |
| Многоуровневая очередь с обратной связью | понижать задачи, жадные до CPU, повышать интерактивные | эвристики, настройка |
| CFS (Linux 2.6.23–6.5) | выбрать задачу с наименьшим виртуальным временем выполнения (красно-чёрное дерево); вес по nice | нет понятия дедлайна для задач, чувствительных к задержке |
| EEVDF (Linux 6.6+) | веса CFS плюс виртуальные дедлайны для каждой задачи; выбирает допустимую задачу с самым ранним дедлайном | новее, меньше настроек |

### Что в Linux можно наблюдать
- Классы планирования: `SCHED_OTHER` (обычный, CFS/EEVDF), `SCHED_BATCH`, `SCHED_IDLE` и классы реального времени `SCHED_FIFO`/`SCHED_RR` (фиксированные приоритеты 1–99, вытесняют всё обычное; используются в аудио и некоторых торговых системах, опасны тем, что крутящийся RT-поток может занять ядро намертво).
- `nice` от -20 до 19 отображается на вес: каждый шаг — примерно 1,25× доли CPU; nice 0 получает примерно в 10 раз больше, чем nice 10. Это меняет долю только при конкуренции; на простаивающей машине процесс с nice 19 работает на полной скорости.
- Очереди готовых задач на каждый CPU с периодической балансировкой нагрузки и миграцией; планировщик предпочитает держать задачу на ядре, где её кэш тёплый ([[cpu-caches-and-cache-lines]]). `taskset`/`sched_setaffinity` привязывает потоки к ядрам.
- Квант не фиксирован: целевая задержка (`sched_latency`, ~6 мс × log(ядер)) делится между готовыми задачами, с минимальной гранулярностью (~0,75 мс). Больше готовых потоков → меньше кванты → больше переключений ([[processes-and-threads]]).

### Средняя нагрузка
- `uptime` / `/proc/loadavg`: экспоненциально сглаженные средние за 1, 5 и 15 минут числа задач, которые **выполняются или готовы к выполнению**, плюс, только в Linux, задач в **непрерываемом сне** (`D`, обычно дисковый или NFS IO).
- Эмпирическое правило: нагрузка ≈ числу ядер означает насыщение; нагрузка 8 на 4 ядрах означает, что в среднем 4 задачи ждут CPU или застряли в IO. Чтобы понять, что именно, всегда сравнивай с `%iowait` и `%steal` в `vmstat`/`mpstat`.
- JVM с 200 потоками и нагрузкой 1,5 — это нормально: заблокированные потоки (`S`) не считаются.

### Cgroups и контейнеры
- `cpu.max = 100000 100000` (Kubernetes `limits.cpu: 1`) — это **квота на период 100 мс**, а не ядро. Многопоточная JVM может сжечь свои 100 мс за первые 20 мс на 8 потоках, а затем быть **затроттлена** (throttled) на 80 мс; p99 задержки взрывается, хотя средний CPU выглядит низким. Смотри `nr_throttled` в `cpu.stat`.
- `cpu.weight` (requests) — пропорциональное распределение, как nice, только при конкуренции.
- JVM читает лимиты cgroup начиная с JDK 10: `availableProcessors()`, число потоков GC и размеры пулов по умолчанию следуют лимиту ([[docker-containers-and-resources]], [[kubernetes-basics]]).

## Пример
```bash
# Сервис медленный из-за планирования CPU?
mpstat -P ALL 1 3            # %usr %sys %iowait %steal по ядрам
cat /proc/loadavg            # 7.80 6.90 5.10 3/612 41233  -> 3 готовых из 612 задач
pidstat -w -t -p $(pgrep -f esim-provisioning.jar) 1 3
#   cswch/s (добровольные, блокировка)  nvcswch/s (принудительные, вытеснение)

# Троттлинг контейнера (cgroup v2, внутри pod)
cat /sys/fs/cgroup/cpu.max          # 100000 100000  -> квота 1 CPU
cat /sys/fs/cgroup/cpu.stat
#   nr_periods 48211  nr_throttled 9120  throttled_usec 712003000
# 19% периодов затроттлены: подними лимит или ограничь потоки JVM
#   (-XX:ActiveProcessorCount, пулы поменьше), либо убери лимит CPU и оставь request.

# Понизить приоритет пакетной переиндексации, чтобы потоки запросов выигрывали при конкуренции
nice -n 15 java -jar reindex.jar
```
Растущий `nr_throttled` при `%usr` узла намного ниже 100% — характерный признак слишком жёсткого лимита CPU для JVM с всплесками нагрузки.

## Подводные камни
- Читать среднюю нагрузку как загрузку CPU. Нагрузка 12 на 16 ядрах — это здорово; нагрузка 4 на 2 ядрах при 5% CPU — это ожидание IO, а не вычисления.
- Ставить в Kubernetes лимиты CPU равными requests для JVM «ради предсказуемости»: GC и JIT-компиляция работают всплесками и троттлятся именно тогда, когда важна задержка. Многие команды задают requests без лимитов или лимиты в 2–4 раза больше requests.
- Подбирать размер пулов потоков по `Runtime.availableProcessors()` в контейнере в host-режиме без лимитов: получаешь 64 ядра хоста и 64-поточный GC в pod, который на самом деле должен использовать 2 ядра ([[executors-and-thread-pools]]).
- Использовать `Thread.setPriority()` в Java и ждать эффекта: в Linux JVM это игнорирует, если не запущена с `-XX:ThreadPriorityPolicy=1` от root. Используй `nice`/cgroups на уровне ОС.
- Планирование реального времени «для низкой задержки»: поток `SCHED_FIFO`, который никогда не блокируется, делает ядро непригодным для всего остального, включая SSH.
- Связанные заметки: [[processes-and-threads]] — стоимость переключения контекста, [[linux-processes]] — `nice`, `renice`, состояния в `ps` и лимиты CPU в `systemd`.
