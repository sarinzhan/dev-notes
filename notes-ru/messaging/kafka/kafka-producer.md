## Кратко
Продюсер сериализует запись, выбирает партицию (по хешу ключа, явно или sticky round-robin для пустых ключей), накапливает записи в пакеты для каждой партиции и отправляет их лидеру партиции. `acks`, `retries`, `enable.idempotence` и `min.insync.replicas` вместе определяют, получишь ли ты доставку в топик at-most-once, at-least-once или (с транзакционным API) exactly-once. Начиная с Kafka 3.0 значения по умолчанию — `acks=all` и `enable.idempotence=true`, так что обычный продюсер уже даёт «at-least-once без дубликатов при retry».

## Основное

### Конвейер отправки
1. При первом использовании продюсер получает **метаданные кластера** (брокеры, лидеры партиций) от bootstrap-брокера, а не от ZooKeeper/KRaft, и кеширует их; обновляет по `metadata.max.age.ms` или при ошибке `NotLeaderOrFollower`. Создание продюсера дорогое (потоки, метаданные, соединения) — создавай **один на приложение** и переиспользуй его; `KafkaProducer` потокобезопасен.
2. Полезная нагрузка оборачивается в `ProducerRecord(topic, partition?, key?, value, headers?, timestamp?)`.
3. Ключ и значение **сериализуются** (`key.serializer`, `value.serializer`): JSON, Avro/Protobuf со schema registry или собственный сериализатор. Брокер видит только байты.
4. **Партиционер** назначает партицию (см. ниже).
5. Запись попадает в **RecordAccumulator** — пакет для конкретной партиции. Необязательное **сжатие** (`compression.type=lz4|zstd|snappy|gzip`) применяется ко всему пакету.
6. Фоновый поток **Sender** отправляет готовые пакеты брокерам-лидерам, по одному запросу на брокер со всеми его готовыми пакетами, и ждёт подтверждений (acks) согласно настройкам. Неудачные пакеты отправляются повторно (retry).

### Партиционирование
| Ситуация | Поведение |
|---|---|
| Явная партиция в записи | Используется как есть |
| Непустой ключ | `murmur2(keyBytes) % numPartitions` (**на основе хеша**): один ключ → одна партиция → порядок по ключу |
| Пустой ключ, Kafka ≥ 2.4 | **Sticky-партиционер**: заполняет один пакет для партиции, затем переключается; равномерное распределение, лучшее пакетирование. В 3.3 он стал учитывать `partitioner.ignore.keys` и распределять равномерно по байтам, а не по числу пакетов |
| Пустой ключ, старые клиенты | Обычный round-robin, по одной записи в каждую партицию по очереди |
| Свой `partitioner.class` | Любая логика, например направить VIP-арендатора в выделенную партицию |

- Выбор ключа — главное проектное решение: он задаёт порядок (все события одного абонента по порядку) и баланс нагрузки (горячий ключ = горячая партиция). Используй id агрегата в качестве ключа, как это делает [[outbox-pattern]].
- Изменение числа партиций меняет `hash % n` и ломает порядок для существующих ключей ([[kafka-architecture]]).

### Пакетирование и задержка
- `batch.size` (по умолчанию 16 КБ): пакет отправляется, когда заполнен. `linger.ms` (по умолчанию 0, часто ставят 5–100 мс): сколько продюсер ждёт новых записей, прежде чем отправить неполный пакет. Большие пакеты = меньше запросов, лучше сжатие, выше пропускная способность, немного выше задержка.
- Если к одному брокеру готовы сразу несколько пакетов, они уходят одним запросом; `max.request.size` (1 МБ) ограничивает запрос, `buffer.memory` (32 МБ) ограничивает накопитель — когда он заполнен, `send()` блокируется на время до `max.block.ms`.
- `send()` асинхронный и возвращает `Future<RecordMetadata>`; передавай `Callback` или используй `.get()`, только когда нужно синхронное подтверждение.

### Надёжность: `acks`
| `acks` | Лидер отвечает, когда | Гарантия |
|---|---|---|
| `0` | никогда — отправил и забыл | Быстрее всего; записи теряются при любом сбое; **at-most-once** |
| `1` | лидер дописал запись в свой журнал | Теряется, если лидер умрёт до репликации на фолловеров |
| `all` / `-1` | все **синхронные реплики** (ISR) дописали запись | Надёжно, пока `min.insync.replicas` ≥ 2; **по умолчанию начиная с 3.0** |

- `acks=all` означает лишь «записано в ISR»; ISR может сжаться до одного лидера, если `min.insync.replicas` это не запрещает. Надёжность — это `acks=all` **плюс** `min.insync.replicas=2` **плюс** фактор репликации 3.
- `retries` (по умолчанию `Integer.MAX_VALUE`), а реальная граница — `delivery.timeout.ms` (120 с); `retry.backoff.ms` между попытками. Ошибки, допускающие retry: идут выборы лидера, `NotEnoughReplicas`, сетевые таймауты. Не допускающие: ошибки сериализации, слишком большая запись, авторизация.

### Семантика доставки (продюсер → топик)
- **At-most-once**: `acks=0` или `retries=0`. Сообщения могут теряться, но никогда не дублируются. Метрики, логи.
- **At-least-once**: `acks=all` с retry. Ничего не теряется, но retry после потерянного ack записывает запись дважды.
- **Exactly-once**: без потерь и без дубликатов. Стоит задержки и требует идемпотентного продюсера (в пределах партиции) или транзакций (между партициями и вместе с потреблением).

### Идемпотентный продюсер
- Даже с `acks=all` дубликат появляется, когда брокер записал пакет, но ack потерялся в сети: продюсер делает retry, брокер дописывает ещё раз.
- `enable.idempotence=true` (по умолчанию начиная с 3.0; требует `acks=all`, `retries>0`, `max.in.flight.requests.per.connection ≤ 5`): брокер назначает продюсеру **PID**, а продюсер прикрепляет к каждому пакету **порядковый номер** (sequence number) в пределах партиции. Брокер хранит последние 5 номеров для каждой пары PID/партиция и молча отбрасывает пакет, который у него уже есть, а также отвергает номера не по порядку, поэтому **порядок сохраняется даже при 5 запросах в полёте**.
- Область действия: одна сессия продюсера, одна партиция. Перезапущенный продюсер получает новый PID, поэтому дубликат между перезапусками не ловится — для этого существуют транзакции и [[idempotency]] на стороне консьюмера.

### Транзакции и exactly-once
- `transactional.id` включает транзакционный API: `initTransactions()`, `beginTransaction()`, `send()` в любое число партиций, `sendOffsetsToTransaction()`, чтобы закоммитить потреблённые offsets в той же транзакции, затем `commitTransaction()` или `abortTransaction()`. **Координатор транзакций** на брокере записывает состояние в `__transaction_state` и помечает записи управляющими записями commit/abort.
- `transactional.id` также отсекает экземпляр-зомби (fencing): после того как новый продюсер с тем же id вызывает `initTransactions()`, старый получает `ProducerFencedException`. Начиная с 2.5 (KIP-447) отсечение работает через поколение consumer group, поэтому достаточно одного `transactional.id` на экземпляр приложения.
- Консьюмеры видят транзакционные записи только с `isolation.level=read_committed` (по умолчанию — `read_uncommitted`).
- Это даёт exactly-once для конвейеров **consume → transform → produce** внутри Kafka (Kafka Streams `processing.guarantee=exactly_once_v2`). Это **не** покрывает побочный эффект в Postgres или HTTP-вызов: там по-прежнему нужен [[outbox-pattern]] на стороне записи и [[idempotency]] на стороне чтения.

## Пример
```java
Properties p = new Properties();
p.put(BOOTSTRAP_SERVERS_CONFIG, "kafka-1:9092,kafka-2:9092");
p.put(KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
p.put(VALUE_SERIALIZER_CLASS_CONFIG, KafkaJsonSerializer.class);
p.put(ACKS_CONFIG, "all");                      // по умолчанию начиная с 3.0, явно — для читателей кода
p.put(ENABLE_IDEMPOTENCE_CONFIG, true);
p.put(LINGER_MS_CONFIG, 20);
p.put(BATCH_SIZE_CONFIG, 64 * 1024);
p.put(COMPRESSION_TYPE_CONFIG, "zstd");
p.put(DELIVERY_TIMEOUT_MS_CONFIG, 60_000);

KafkaProducer<String, ActivationRequested> producer = new KafkaProducer<>(p); // один на приложение

// ключ = id абонента: все события одного абонента остаются упорядоченными в одной партиции
ProducerRecord<String, ActivationRequested> rec =
        new ProducerRecord<>("esim.activation", evt.subscriberId(), evt);
rec.headers().add("trace-id", traceId.getBytes(UTF_8));

producer.send(rec, (meta, ex) -> {
    if (ex != null) log.error("publish failed for {}", evt.id(), ex); // после исчерпания retry
    else log.debug("stored at {}-{}@{}", meta.topic(), meta.partition(), meta.offset());
});
```

## Подводные камни
- `acks=all` при брокерском значении по умолчанию `min.insync.replicas=1` даёт ложное ощущение безопасности; задай его на топике ([[kafka-architecture]]).
- `max.in.flight.requests.per.connection > 1` **без** идемпотентности переупорядочивает записи при retry. С включённой идемпотентностью до 5 — безопасно.
- Вызов `producer.send(...).get()` для каждой записи убивает пропускную способность (один круг туда-обратно на запись). Используй колбэки и дай накопителю формировать пакеты; flush делай только при остановке.
- Продюсер, создаваемый на каждый запрос, оставляет утечки потоков и сокетов и каждый раз заново получает метаданные; это классическая причина `TimeoutException: Failed to update metadata`.
- Транзакции — это не межсистемный 2PC: «записать в БД и опубликовать ровно один раз» по-прежнему требует [[outbox-pattern]] и идемпотентных консьюмеров ([[idempotency]]).
- `DeliveryTimeout`, когда записи ещё в буфере, означает, что с точки зрения продюсера запись потеряна; колбэк получает исключение, и никто не сделает retry за тебя. В Spring этот продюсер оборачивает `KafkaTemplate` — действуют те же правила.
- Связанные заметки: [[kafka-consumer]], [[spring-kafka-consumer]].
