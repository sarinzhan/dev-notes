## Кратко
RabbitMQ — брокер с открытым исходным кодом на Erlang, реализующий AMQP 0-9-1 (а также MQTT, STOMP и, начиная с 3.9, собственный протокол Streams). Продюсер никогда не пишет в очередь напрямую: он публикует сообщение в **exchange** с **ключом маршрутизации** (routing key), exchange направляет сообщение в очереди, чей **ключ привязки** (binding key) совпадает, брокер **проталкивает** (push) сообщение потребителю, а потребитель **подтверждает** (ack) его, чтобы брокер мог его удалить. Это схема «умный брокер, глупый потребитель» — противоположность логу Kafka с «глупым брокером и умным потребителем».

## Основное

### Путь сообщения
1. Продюсер публикует сообщение в именованный exchange с ключом маршрутизации (и необязательными заголовками/свойствами).
2. Exchange направляет его в ноль или более очередей согласно привязкам (bindings). Продюсер часто понятия не имеет, получила ли его хоть одна очередь (если нужно знать — флаг `mandatory` + return callback или publisher confirms).
3. Очередь хранит ссылку; тело лежит в RAM и/или на диске в зависимости от persistence.
4. Когда потребитель готов (или у него есть свободные слоты prefetch), брокер проталкивает ему копию сообщения.
5. Потребитель обрабатывает его и отправляет **ack** (или nack/reject).
6. Брокер удаляет сообщение из очереди, памяти и с диска. В отличие от Kafka, после ack повторного чтения (replay) нет — сообщение потребляется один раз одним потребителем.

### Почему Erlang
- Erlang/OTP создан в Ericsson в 1980-х для телеком-коммутаторов, которым нужна доступность «пять девяток»: лёгкие процессы, обмен сообщениями, деревья супервизоров и горячая перезагрузка кода. RabbitMQ отображает одну очередь на один Erlang-процесс, поэтому один узел выдерживает десятки тысяч очередей и поэтому при перезапуске узла содержимое очередей (исторически первые 16 384 сообщения каждой очереди) загружается в память.

### Модель AMQP 0-9-1
| Компонент | Роль |
|---|---|
| **Producer** | Открывает соединение (TCP) и лёгкий **канал** (channel) внутри него, публикует в exchange |
| **Exchange** | Компонент маршрутизации; сравнивает ключ маршрутизации сообщения с ключом каждой привязки (точно или по шаблону) и копирует сообщение в подходящие очереди. Exchange существуют на каждом узле |
| **Binding** | Связь между exchange и очередью, несёт ключ привязки (или аргументы заголовков) |
| **Queue** | FIFO-буфер, хранящий сообщения, пока потребитель их не подтвердит; живёт на одном узле (classic) или реплицируется через Raft (quorum) |
| **Consumer** | Подписывается на очередь (`basic.consume`, push) или забирает одно сообщение (`basic.get`, избегать на горячих путях) |

- Сообщение = **заголовки** (ключ/значение на уровне AMQP, используются headers exchange), **свойства** (метаданные приложения: `content_type`, `correlation_id`, `reply_to`, `message_id`, `delivery_mode`, `expiration`, `priority`) и **тело** (массив байтов, непрозрачный для брокера). В сети сообщения разбиваются на фреймы; размер фрейма согласуется (максимум по умолчанию 131 072 байта = 128 KiB).

### Типы exchange
| Тип | Правило маршрутизации | Типичное применение |
|---|---|---|
| **Default** (безымянный, `""`) | Direct exchange, заранее привязанный к каждой очереди по её имени: публикация с `routing_key = имя очереди` выглядит как запись в очередь | Простые очереди задач |
| **Direct** | Ключ маршрутизации должен совпадать с ключом привязки | Маршрутизация по типу задачи, точка-точка |
| **Fanout** | Игнорирует ключ маршрутизации, копирует во все привязанные очереди | Pub/sub-рассылка |
| **Topic** | Ключ привязки — шаблон из слов через точку: `*` = ровно одно слово, `#` = ноль или более слов (`order.*.created`, `payment.#`) | Маршрутизация по категории |
| **Headers** | Сопоставляет заголовки сообщения с аргументами привязки через `x-match = all|any`; ключ маршрутизации игнорируется | Маршрутизация по нескольким атрибутам (редко) |
| **Dead letter** | Не тип — любой exchange, указанный как `x-dead-letter-exchange` очереди | Отклонённые/просроченные сообщения |
| Плагины | `x-consistent-hash`, `x-delayed-message` | Шардирование, отложенная доставка |

### Типы и свойства очередей
- **Classic**: одноузловая, быстрая, исходная. Classic mirrored queues (HA-политика) были старым механизмом репликации; **объявлены устаревшими в 3.9 и удалены в 4.0**.
- **Quorum** (3.8+, выбор по умолчанию для всего durable начиная с 3.13/4.0): реплицируется между узлами через Raft, всегда durable, надёжнее при сетевых разделениях (network partitions), поддерживает обработку ядовитых сообщений (poison messages) через `x-delivery-limit` (по умолчанию 20 в 4.0) и dead-lettering. Не поддерживает приоритеты больше 2 уровней, `x-max-priority`, флаги exclusive и transient.
- **Stream** (3.9+): реплицируемый лог только на дозапись (append-only) с неразрушающим чтением по offset и хранением по размеру/времени — семантика как у Kafka внутри RabbitMQ, чтение через AMQP или отдельный stream-протокол.
- Свойства очереди: `durable` (переживает перезапуск брокера; сообщения переживают его, только если ещё и опубликованы с `delivery_mode=2`/persistent), `auto-delete` (удаляется, когда отписывается последний потребитель), `exclusive` (одно соединение, удаляется при его закрытии), `x-max-priority` (только classic), `x-message-ttl` / `x-expires` (TTL сообщения и очереди), `x-max-length` / `x-overflow` (ограниченные очереди: `drop-head` или `reject-publish`), `x-queue-type`, `x-dead-letter-exchange` / `x-dead-letter-routing-key`. Ленивые очереди (lazy queues; всё сбрасывается на диск) в 3.12 стали единственным поведением classic-очередей.
- Свойства задаются при объявлении (в коде), **политиками** (policies; шаблоны, заданные оператором в management UI/CLI, предпочтительно) или значениями сервера по умолчанию.

### Подтверждения, prefetch, повторная доставка
- **Подтверждения потребителя** (consumer acks): `autoAck=true` означает, что брокер забывает сообщение сразу после отправки (at-most-once). При ручных ack `basic.ack` после обработки даёт **at-least-once**; `basic.nack`/`basic.reject` с `requeue=true` возвращает сообщение в очередь (и помечает `redelivered`), с `requeue=false` — отбрасывает его или отправляет в dead letter.
- **Prefetch** (`basic.qos(prefetch_count)`): сколько неподтверждённых сообщений брокер может протолкнуть одному потребителю. Неограниченный prefetch позволяет одному быстрому соединению забрать всё и раздувает память; `1` даёт идеальную справедливость, но round-trip на каждое сообщение. Типично: 10–300 в зависимости от времени обработки. Задаётся на канал или на потребителя (`global=false`, по умолчанию в Java).
- **Publisher confirms** (`confirmSelect`): брокер подтверждает *продюсеру*, что сообщение сохранено/реплицировано — аналог `acks=all` в Kafka на стороне продюсера. Без confirms и persistence падение брокера теряет сообщения в пути.
- **Dead letter exchange (DLX)**: сообщение уходит в dead letter, когда его отклонили без requeue, истёк его TTL, очередь переполнилась или (quorum) превышен лимит доставок. Заголовок `x-death` фиксирует причину и количество раз. В сочетании с TTL на DLQ и привязкой обратно к рабочей очереди получается retry с задержкой.
- Подтверждения потребителя обеспечивают at-least-once; дубликаты всё равно случаются (потребитель падает после обработки, но до ack), поэтому обработчикам нужна [[idempotency]], а надёжная публикация из транзакции БД всё равно требует [[outbox-pattern]].

### Шаблоны, которые даёт модель
- **Очередь задач / точка-точка**: одна очередь, N конкурирующих потребителей, round-robin с prefetch для справедливости.
- **Pub/sub**: fanout exchange, по одной очереди на подписчика.
- **Маршрутизация / topic**: direct или topic exchange, выборочные подписки.
- **RPC**: публикация с `reply_to` (часто эксклюзивная очередь на клиента или псевдоочередь `amq.rabbitmq.reply-to`) и `correlation_id`; сервер отвечает в `reply_to`.
- **Dead-letter / retry**: DLX + очереди с TTL.
- **Отложенное сообщение**: трюк TTL + DLX или плагин `rabbitmq_delayed_message_exchange`.

### RabbitMQ и Kafka
| | RabbitMQ | Kafka |
|---|---|---|
| Модель | Умный брокер маршрутизирует, проталкивает, удаляет по ack | Глупый брокер хранит лог, потребители забирают по offset |
| Время жизни сообщения | До ack (или TTL) | Retention/compaction; повторное чтение возможно |
| Маршрутизация | Богатая: типы exchange, заголовки, TTL на сообщение, приоритеты | Только по ключу партиции |
| Порядок | В пределах очереди с одним потребителем; теряется при requeue/конкурирующих потребителях | В пределах партиции, гарантирован |
| Пропускная способность | Типично десятки тысяч сообщений/с на узел | Миллионы сообщений/с на кластер, последовательный дисковый ввод-вывод |
| Потребители | Конкурирующие потребители масштабируются свободно | Параллелизм ограничен числом партиций |
| Подходит для | Очереди задач, RPC, сложная маршрутизация, много маленьких очередей, протоколы (MQTT/STOMP), команды с низкой задержкой | Потоковая обработка событий, event sourcing, несколько независимых читателей, аналитика, CDC |

Выбирай RabbitMQ, когда нужны *команды*, доставляемые один раз одному обработчику, с гибкой маршрутизацией и возможностями на уровне сообщения; выбирай [[kafka-architecture|Kafka]], когда нужен *лог событий*, который несколько команд читают в своём темпе, или очень высокая пропускная способность. Streams сокращают разрыв для малых и средних объёмов.

## Пример
Durable-очередь задач с dead-letter-очередью и ограниченным prefetch (Java-клиент, который оборачивает Spring AMQP).

```java
try (Connection conn = factory.newConnection(); Channel ch = conn.createChannel()) {
    ch.exchangeDeclare("esim", BuiltinExchangeType.TOPIC, true);
    ch.exchangeDeclare("esim.dlx", BuiltinExchangeType.FANOUT, true);
    ch.queueDeclare("esim.activation.dlq", true, false, false, Map.of());
    ch.queueBind("esim.activation.dlq", "esim.dlx", "");

    ch.queueDeclare("esim.activation", true, false, false, Map.of(
            "x-queue-type", "quorum",
            "x-dead-letter-exchange", "esim.dlx",
            "x-delivery-limit", 5));
    ch.queueBind("esim.activation", "esim", "activation.*");   // activation.requested, activation.retry

    ch.confirmSelect();                                        // publisher confirms
    ch.basicPublish("esim", "activation.requested",
            new AMQP.BasicProperties.Builder().deliveryMode(2).contentType("application/json")
                    .messageId(evt.id()).build(),
            json.writeValueAsBytes(evt));
    ch.waitForConfirmsOrDie(5_000);

    ch.basicQos(50);                                           // prefetch на потребителя
    ch.basicConsume("esim.activation", false, (tag, delivery) -> {
        try {
            provisioning.activateIdempotently(json.readValue(delivery.getBody(), ActivationRequested.class));
            ch.basicAck(delivery.getEnvelope().getDeliveryTag(), false);
        } catch (Exception e) {
            ch.basicNack(delivery.getEnvelope().getDeliveryTag(), false, true); // requeue; DLX после 5 попыток
        }
    }, tag -> {});
}
```

## Подводные камни
- Одного `durable=true` на очереди недостаточно, чтобы пережить перезапуск: сообщение должно быть ещё и опубликовано как persistent (`delivery_mode=2`), а то, что оно дошло до диска, можно узнать только через publisher confirms.
- Без лимита prefetch (`basicQos` не вызван) при медленном потребителе брокер проталкивает всю очередь в память этого потребителя, а остальные голодают.
- Nack с `requeue=true` без лимита доставок создаёт бесконечный цикл ядовитого сообщения со 100 % CPU; используй quorum `x-delivery-limit` или DLX со счётчиком повторов.
- Порядок слабее, чем принято думать: конкурирующие потребители, requeue и приоритеты — всё это переставляет сообщения. Если порядок важен — один потребитель на очередь или Streams / Kafka.
- Classic mirrored queues удалены в 4.0; миграция на quorum-очереди требует повторного объявления очередей (тип неизменяем) и отказа от неподдерживаемых возможностей вроде `x-max-priority` и флагов exclusive/transient.
- Соединения дорогие, каналы дешёвые, но канал не потокобезопасен: один канал на поток.
- Связанные заметки: [[kafka-architecture]], [[kafka-consumer]], [[activemq-basics]], [[outbox-pattern]], [[idempotency]].
