## Кратко
Система Linux — это стек: железо, ядро, системные библиотеки (glibc), системные демоны, оболочки и утилиты, пользовательские приложения. Только ядро работает в привилегированном режиме CPU (ring 0) и обращается к железу; всё остальное работает в пространстве пользователя (user space, ring 3) и попадает в ядро исключительно через **системные вызовы (system calls)**. Пространства имён (namespaces) и cgroups — обе возможности ядра — это то, из чего сделаны контейнеры ([[docker-fundamentals]]).

## Основное
### Уровни абстракции обычной системы Linux
1. **Железо**: CPU, RAM, SSD, GPU, сетевая карта. Выполняет только машинные инструкции.
2. **Ядро**: центральный слой ОС. Обязанности: управление процессами и планирование, управление памятью, файловые системы, драйверы устройств, сеть, безопасность. Ubuntu или Debian — это *дистрибутивы* поверх одного и того же ядра.
3. **Системные библиотеки**: слой, через который приложения общаются с ядром. Когда программа вызывает `printf()`, glibc в итоге выполняет системный вызов `write()`. Обычный набор: glibc (GNU C library, вместе с libm и libpthread) или musl в Alpine.
4. **Утилиты пространства пользователя и системные демоны**: фоновые системные программы: `systemd` (init и менеджер сервисов), `udev` (события устройств), `cron`, `sshd`, `dockerd`.
5. **Оболочка (shell)**: интерпретатор команд, обычная программа пространства пользователя, работающая поверх ядра. Интерпретирует команды и запускает программы. `sh` — историческая POSIX-оболочка, `bash` — расширенная версия GNU, `zsh`/`fish` — альтернативы.
6. **Базовые инструменты GNU**: `ls`, `cat`, `ps`, `chmod`, `grep` ([[linux-commands]]).
7. **Пользовательские приложения**: твоя JVM, Postgres, nginx.

### Пространство ядра и пространство пользователя
- Что где работает, режимы CPU, разделение адресного пространства и как поток пересекает границу — в [[kernel-vs-user-mode]].

### Системные вызовы
- API ядра: несколько сотен функций (`open`, `read`, `write`, `socket`, `clone`, `execve`, `mmap`, `futex`). Каждый переключает CPU в режим ядра, выполняет код ядра и переключает обратно; это переключение режима (не переключение контекста) стоит примерно 0,1–0,5 мкс, поэтому важна пакетная обработка (буферы, `epoll`, [[java-nio]]).
- Библиотеки оборачивают их: `FileInputStream.read()` -> JNI -> glibc `read()` -> `SYS_read`.
- `strace -f -p <pid>` показывает каждый системный вызов процесса; `strace -c` агрегирует их. Это самый быстрый способ увидеть, *почему* программа зависла (заблокирована в `futex`, `read` на сокете, таймаут `connect`).

### Системы инициализации и роли
- Ядро запускает ровно один пользовательский процесс, PID 1 (**init**), который запускает всё остальное. `systemd` — init почти во всех дистрибутивах; `OpenRC` (Alpine, Gentoo) и `runit` (Void) — альтернативы.
- PID 1 собирает осиротевшие зомби-процессы. В контейнере PID 1 становится entrypoint, поэтому и существуют `tini` и `--init` ([[docker-containers-and-resources]]).

### Внутри ядра
- **Драйверы устройств / модули ядра**: загружаются по требованию; `lsmod` перечисляет, `modprobe <mod>` загружает с зависимостями, `insmod` загружает один `.ko`, `rmmod` выгружает.
- **sysfs (`/sys`) и procfs (`/proc`)**: псевдофайловые системы в памяти, которые представляют объекты ядра в виде файлов. `cat /proc/<pid>/status`, `/proc/meminfo`, `/sys/class/net/eth0/`; запись в `/proc/sys/...` (или `sysctl -w`) настраивает ядро на лету.
- **Планировщик**: CFS (Completely Fair Scheduler) с 2.6.23 даёт каждой готовой к выполнению задаче справедливую долю времени CPU, взвешенную по значению nice; в ядре 6.6 (2023) заменён на **EEVDF** с тем же интерфейсом. См. [[linux-processes]].
- **Пространства имён** (что процесс видит) и **cgroups** (что ему можно использовать) — возможности ядра, из которых сделаны контейнеры; обе, с примерами, — в [[virtualization-and-containers]].

## Пример
```bash
# Посмотреть системные вызовы JVM, которая «зависает» при старте
sudo strace -f -tt -e trace=network,connect,openat -p "$(pgrep -f app.jar)" 2>&1 | head -40
# 12:03:11.118 connect(27, {sa_family=AF_INET, sin_port=htons(5432), ...}, 16) = -1 EINPROGRESS
# 12:03:41.120 ... ETIMEDOUT   -> недоступен хост БД, а не JVM

```

## Подводные камни
- «Контейнер — это лёгкая VM» — неверно: он использует ядро хоста, поэтому баг ядра или привилегированный контейнер затрагивают хост. Разница версий ядра также объясняет, почему образ работает на одном хосте и не работает на другом.
- `strace` заметно замедляет трассируемый процесс; не оставляй его подключённым в production.
- Изменения значений в `/proc/sys` не сохраняются после перезагрузки; помещай их в `/etc/sysctl.d/*.conf`.
- JVM читает лимиты cgroup для размера кучи по умолчанию только с JDK 10 (и cgroup v2 с 11.0.16 / 15); старые JVM видят память хоста и убиваются OOM killer ([[jvm-memory-areas]], [[garbage-collection]]).
