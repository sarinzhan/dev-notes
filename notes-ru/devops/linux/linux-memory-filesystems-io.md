## Кратко
Каждый процесс видит собственное **виртуальное адресное пространство**, отображённое на физическую RAM страницами по 4 KiB; остальную RAM ядро использует как **страничный кеш (page cache)** для файлов, поэтому на здоровом сервере `free` показывает почти ноль свободной памяти. Файловые системы (ext4, XFS, btrfs) хранят данные на блочных устройствах, псевдофайловые системы (`/proc`, `/sys`) показывают состояние ядра, а планировщик ввода-вывода (IO scheduler) упорядочивает запросы к диску. Классическую загадку «диск полон, а файлов нет» решает понимание того, что на самом деле измеряют `ls`, `du` и `df`.

## Основное
### Виртуальная память и страничная организация
- Каждый процесс получает приватное виртуальное адресное пространство (на x86-64 используются 47 бит). MMU переводит виртуальные страницы в физические фреймы через таблицы страниц; TLB кеширует эти переводы.
- Страницы по умолчанию — 4 KiB; большие страницы (huge pages, 2 MiB) уменьшают промахи TLB для больших куч (`-XX:+UseTransparentHugePages` для JVM).
- Память выделяется лениво: `mmap`/`malloc` резервируют адресное пространство, а физическая страница подключается при первом обращении (page fault). Поэтому JVM с `-Xmx4g` показывает 4 GiB виртуальной памяти (`VSZ`) и гораздо меньше резидентной (`RSS`), пока куча реально не используется ([[jvm-memory-areas]]).
- **Копирование при записи (copy-on-write)** после `fork()`: родитель и потомок разделяют страницы, пока один из них не запишет ([[linux-processes]]).
- **Swap**: когда RAM не хватает, ядро вытесняет анонимные страницы в swap на диске. Для чувствительной к задержкам JVM swapping — катастрофа (паузы GC затрагивают всю кучу); серверы с базами данных или JVM обычно работают с `vm.swappiness=1` или без swap и полагаются на OOM killer и правильные лимиты.
- **OOM killer**: когда память действительно исчерпана, ядро убивает процесс с наибольшим `oom_score` (обычно самый большой). Внутри cgroup с `memory.max` то же самое происходит для каждого контейнера: код выхода 137 ([[docker-containers-and-resources]]).
- **Страничный кеш**: прочитанное или записанное содержимое файлов остаётся в RAM как кеш; `free -h` показывает его в `buff/cache`, и оно считается *доступным* (available). Запись сначала идёт в кеш (грязные страницы, dirty pages) и сбрасывается ядром; `fsync()` делает это принудительно — так поступает Postgres при commit, а Kafka намеренно нет ([[kafka-architecture]]).

### Файловые системы
| ФС | Особенности | Типичное применение |
|---|---|---|
| **ext4** | Журналирование, зрелая, по умолчанию в Debian/Ubuntu, быстрый fsck, файлы до 16 TiB | Корневой раздел и данные общего назначения |
| **XFS** | Журналирование, отлично работает с большими файлами и параллельным IO, нельзя уменьшить, по умолчанию в RHEL | Базы данных, каталоги логов Kafka, большие тома |
| **btrfs** | Copy-on-write, снапшоты, контрольные суммы, встроенный RAID, сжатие; выше накладные расходы | Конфигурации с частыми снапшотами, по умолчанию в Fedora, вариант драйвера хранилища Docker |
| **overlay2** | Union FS, накладывающая слои только для чтения плюс один записываемый слой | Слои образов Docker ([[docker-fundamentals]]) |
| **tmpfs** | В RAM, теряется при перезагрузке | `/run`, `/dev/shm`, `/tmp` в некоторых дистрибутивах |
- Inode хранит метаданные (владелец, режим, временные метки, указатели на блоки); имена файлов — это записи каталога, указывающие на inode. Жёсткая ссылка (hard link) — второе имя того же inode; символическая ссылка (symlink) — файл, содержащий путь. Исчерпание inode (`df -i`) выглядит как полный диск при наличии свободного места.
- Монтирование подключает файловую систему к каталогу; `mount`, `/etc/fstab`, `findmnt`, `lsblk` для дерева устройств.

### Псевдофайловые системы
- `/proc`: информация о процессах и ядре, генерируемая при чтении: `/proc/<pid>/{status,maps,fd,limits}`, `/proc/meminfo`, `/proc/cpuinfo`, настраиваемые параметры в `/proc/sys/`.
- `/sys`: устройства, драйверы, шины, cgroups (`/sys/fs/cgroup`). Запись в файлы меняет состояние ядра ([[linux-architecture-and-kernel]]).

### Планирование ввода-вывода
- Планировщики блочного уровня переупорядочивают и объединяют запросы: **mq-deadline** (ограниченная задержка, хороший вариант по умолчанию для SSD/NVMe), **BFQ** (справедливая полоса на процесс, десктопы, медленные диски), **kyber** (низкая задержка для быстрых устройств), **none** (NVMe сам управляет очередями). CFQ — старый однопоточный (single-queue) планировщик, удалён в ядре 5.0.
- `cat /sys/block/nvme0n1/queue/scheduler` показывает активный в квадратных скобках.
- `iostat -x 1` — загрузка и время ожидания (await), `iotop` — IO по процессам, `vmstat 1` — `wa` (ожидание IO) и `si/so` (swap in/out).

### ls, du и df
| Инструмент | Что измеряет | Где может ввести в заблуждение |
|---|---|---|
| `ls -l` | **Видимый размер (apparent size)**, хранящийся в inode (длина файла) | Разреженные (sparse) файлы выглядят огромными; файл, удалённый по имени, исчезает из `ls`, даже если ещё открыт |
| `du` | **Выделенные блоки**, подсчитанные обходом записей каталогов (`du -sh *`) | Не видит удалённые, но открытые файлы; считает жёсткие ссылки один раз за запуск; переходит через точки монтирования, если не указан `-x` |
| `df` | Занято/свободно **на уровне файловой системы** по данным суперблока | Учитывает место, занятое открытыми удалёнными файлами, и зарезервированные для root блоки (5% в ext4) |
- «`df` говорит 95%, `du` — 40%»: процесс всё ещё держит открытым удалённый файл (ротированный лог, удалённый слой Docker). Найди его через `lsof +L1` или `find /proc/*/fd -ls | grep deleted`, затем перезапусти процесс или обрежь файл через `/proc/<pid>/fd/<n>`.
- `du` меньше суммы `ls`: разреженные файлы или сжатие (btrfs). `du` больше `ls`: каждый маленький файл занимает целый блок.

## Пример
```bash
# Диск «полон», но du не находит, чем
df -h /var                              # /dev/sda2  98G  93G  0  100% /var
sudo du -xsh /var/* | sort -h | tail -5 # самый большой — /var/lib/docker на 31G: не сходится
sudo lsof +L1 | head                    # файлы с числом ссылок 0 = удалены, но открыты
# java  4123 esim 7w REG 8,2 48G 0 /var/log/esim/app.log (deleted)
sudo truncate -s 0 /proc/4123/fd/7      # освободить место без перезапуска JVM

# Память: что действительно свободно
free -h
#               total   used   free  shared  buff/cache  available
# Mem:           15Gi  6.1Gi  412Mi  210Mi       9.2Gi       8.9Gi   <- важно именно 'available'
cat /proc/$(pgrep -f app.jar)/status | grep -E 'VmRSS|VmSwap|Threads'
```

## Подводные камни
- Смотреть на колонку «free» в `free` и делать вывод, что память исчерпана; смотри на `available`.
- Удаление лог-файла, в который пишет работающий процесс, ничего не освобождает; обрежь его или используй `copytruncate` в logrotate.
- Volumes и слои образов Docker лежат в `/var/lib/docker`; `docker system prune` — часто настоящее решение для заполненного диска ([[docker-volumes-and-registry]]).
- Значение `vm.max_map_count` по умолчанию (65530) слишком мало для Elasticsearch и некоторых нагрузок на JVM; задай его в `/etc/sysctl.d/`.
- Куча JVM больше лимита памяти cgroup внутри контейнера приводит к убийству процесса, а не к swapping; задавай `-XX:MaxRAMPercentage` вместо `-Xmx` ([[garbage-collection]]).
- Связанные заметки: [[linux-architecture-and-kernel]], [[linux-commands]], [[java-nio]].
