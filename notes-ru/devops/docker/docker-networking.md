## Кратко
Каждый контейнер получает собственное сетевое пространство имён (network namespace), а сетевой драйвер определяет, как это пространство подключено. По умолчанию это Linux-мост (bridge): пара veth соединяет `eth0` контейнера с мостом на хосте, исходящий трафик маскарадится, а `-p 8080:80` — это DNAT-правило iptables. Используй пользовательские сети (Compose создаёт по одной на проект): они добавляют разрешение имён через встроенный DNS на `127.0.0.11` и изолируют несвязанные стеки. `host` разделяет сетевой стек хоста, `none` даёт только loopback, `overlay` охватывает узлы Swarm, `macvlan` ставит контейнер прямо в LAN.

## Основное
### Драйверы
| Драйвер | Что получает контейнер | Для чего |
|---|---|---|
| `bridge` (сеть по умолчанию `bridge`, интерфейс `docker0`, `172.17.0.0/16`) | частный IP, NAT наружу, доступ только по IP; имена — только через устаревший `--link` | одноразовый `docker run` |
| пользовательский `bridge` (`docker network create`, каждый проект Compose) | свой мост `br-<id>` и подсеть, встроенный DNS по имени контейнера/сервиса, изоляция от других сетей, подключение/отключение на ходу | почти всё на одном хосте |
| `host` | интерфейсы и порты хоста; `-p` игнорируется | захват пакетов, очень высокая частота пакетов, инструменты, которым нужна сеть хоста |
| `none` | только `lo` | пакетные задачи, которые ни с кем не должны общаться |
| `overlay` | VXLAN-сеть между хостами | сервисы Swarm ([[docker-swarm]]) |
| `macvlan` / `ipvlan` | свой MAC (или общий MAC) и IP в физической LAN | legacy-приложения, которые ожидают быть хостом в LAN |

### Как работает мост
- `docker0` (или `br-<id>`) — виртуальный L2-коммутатор на хосте и шлюз по умолчанию (`172.17.0.1`) для подключённых к нему контейнеров ([[host-to-host-communication]], [[arp]]).
- Каждый контейнер получает **пару veth** (veth pair): один конец — `eth0` внутри его пространства имён, другой (`vethXXXX`) воткнут в мост. Сами пространства имён описаны в [[virtualization-and-containers]].
- Контейнер-контейнер на одном мосту — обычная L2-коммутация, без NAT. Трафик между разными пользовательскими сетями отбрасывается правилами изоляции Docker.
- Исходящий трафик: хост маршрутизирует пакет ([[network-routing]]), а правило `MASQUERADE` в `POSTROUTING` переписывает источник `172.17.0.x` на адрес хоста; conntrack сопоставляет ответы обратно ([[ip-addressing-and-nat]]).

### Публикация портов
- `-p 8080:80` добавляет DNAT-правило в цепочку `DOCKER` таблицы `nat`: пакеты на любой адрес хоста с портом 8080 получают назначение `172.17.0.2:80`, плюс `ACCEPT` на пути `FORWARD` в таблице `filter`. Ответ переписывается обратно через conntrack (обратная операция к этому DNAT), поэтому клиент видит источником `host:8080`.
- DNAT происходит в `PREROUTING`, поэтому пакет идёт по пути `FORWARD` и никогда не доходит до цепочки `INPUT`, где живут правила `ufw`/`firewalld`: опубликованные порты они не защищают. Фильтруй в цепочке `DOCKER-USER` или привязывайся к конкретному адресу.
- `-p 127.0.0.1:8080:80` публикует порт только на loopback хоста: доступно с самого хоста и через SSH-туннель, но не из сети. Вариант по умолчанию для баз данных и админок на общем сервере ([[network-access-to-databases]]).
- `EXPOSE` в Dockerfile — это документация; он ничего не публикует ([[dockerfile-and-images]]).
- Процесс внутри должен слушать `0.0.0.0`, а не `127.0.0.1`, иначе цели DNAT некому ответить (разобранный пример — в [[ip-addressing-and-nat]]).

### Встроенный DNS
- В пользовательских сетях `/etc/resolv.conf` каждого контейнера указывает на `127.0.0.11`; dockerd отвечает на имена контейнеров, сервисов Compose и псевдонимов `--network-alias`, а всё остальное пересылает резолверам хоста ([[dns-resolution]]).
- Масштабированный сервис Compose (`--scale api=3`) возвращает несколько A-записей; клиенты, которые кешируют первый IP (DNS-кеш JVM, HikariCP, держащий соединения), нагрузку не распределяют.
- В сети `bridge` по умолчанию встроенного DNS нет; контейнеры там получают копию resolv.conf хоста.

### Сети Compose и несколько сетей
- Compose создаёт `<project>_default` и подключает к ней все сервисы; имя сервиса — это имя хоста. Объяви дополнительные сети, чтобы разделить уровни: nginx в `frontend` и `backend`, приложение в `backend`, Postgres только в `backend`.
- У контейнера в двух сетях два интерфейса (`eth0`, `eth1`) и два IP; `docker network connect backend nginx` добавляет ещё один на ходу.
- `internal: true` создаёт сеть без шлюза: никакого исходящего трафика и никаких опубликованных портов для контейнеров, подключённых только к ней. Подходит для баз данных, которые никогда не должны ходить в интернет.
- Из контейнера к сервису на хосте: `host.docker.internal`, встроен в Docker Desktop; в Linux добавь `extra_hosts: ["host.docker.internal:host-gateway"]` (Docker 20.10+).


## Пример
Стек Compose с двумя сетями (обе есть только у nginx), портом БД только на loopback и командами, чтобы увидеть устройство.
```yaml
# compose.yaml
name: esim                              # сети станут esim_frontend, esim_backend
services:
  nginx:
    image: nginx:1.27
    ports: ["443:443"]                  # публичный вход
    networks: [frontend, backend]
  esim-api:
    image: registry.local/esim-api:1.8.0
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/esim   # имя сервиса через 127.0.0.11
    extra_hosts: ["host.docker.internal:host-gateway"]
    networks: [backend]
  postgres:
    image: postgres:16
    ports: ["127.0.0.1:5432:5432"]      # psql только с хоста
    networks: [backend]

networks:
  frontend: {}
  backend:
    ipam:
      config: [{ subnet: 10.30.0.0/24 }] # чтобы не пересекаться с 172.x от VPN
```
```bash
docker compose up -d
docker network inspect esim_backend -f '{{range .Containers}}{{.Name}} {{.IPv4Address}}{{"\n"}}{{end}}'
ip -br link | grep veth                                 # концы пар veth на стороне хоста
bridge link                                             # какой veth в каком br-*
sudo iptables -t nat -S DOCKER                          # DNAT: :443 -> nginx, 127.0.0.1:5432 -> postgres
docker compose exec esim-api getent hosts postgres      # 10.30.0.3  postgres
```

## Подводные камни
- `ports: ["5432:5432"]` на сервере, где `ufw` «блокирует» 5432: порт всё равно открыт всему миру.
- Расчёт на разрешение имён в сети `bridge` по умолчанию: его там нет; создай сеть.
- Пулы адресов Docker по умолчанию (`172.17.0.0/16` и выше) пересекаются с корпоративным VPN или офисными подсетями; задай `default-address-pools` в `daemon.json`.
- `--network host` в Docker Desktop (macOS/Windows) подключает к сети скрытой Linux-ВМ, а не твоего ноутбука, если не включена опциональная настройка host networking (4.34+).
- Жёстко прописанные IP контейнеров; они меняются при пересоздании. Используй имена сервисов.
- Связанные заметки: [[docker-fundamentals]], [[docker-swarm]] — overlay и routing mesh, [[tcpdump]] — захват на `docker0` или внутри контейнера, [[linux-networking]] — iptables/nftables.
