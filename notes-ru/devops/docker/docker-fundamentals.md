## Кратко
Docker упаковывает приложение со всеми зависимостями в лёгкий **контейнер**: изолированный процесс на ядре хоста, а не эмулированную машину. **Виртуальная машина** загружает полноценную гостевую ОС со своим ядром поверх гипервизора; контейнер использует ядро хоста, изолирован пространствами имён (namespaces) и ограничен cgroups. **Образ (image)** — неизменяемый шаблон из слоёв; **контейнер** — его запущенный экземпляр с одним тонким записываемым слоем сверху.

## Основное
### Зачем появился Docker
- Раньше: «у меня на машине работает». Деплой означал установку нужного JDK, библиотек, конфигурации и системных пакетов на каждый сервер вручную или через Ansible/Puppet; окружения расходились. Виртуальные машины решали проблему изоляции, но стоили гигабайты и минуты на каждый экземпляр.
- Docker (2013) сделал удобными Linux-контейнеры (namespaces + cgroups уже были в ядре; существовал LXC): `Dockerfile` для описания окружения, формат образа для его доставки, registry для распространения и одна команда, чтобы запустить его где угодно с одинаковым результатом.
- Что он решает: воспроизводимые окружения, изоляцию зависимостей, быстрый старт (миллисекунды), плотность (десятки контейнеров на хост), неизменяемые артефакты деплоя, основу для оркестрации ([[docker-swarm]], Kubernetes).
- Недостатки: общее ядро (изоляция слабее, чем у VM, Linux-контейнеры работают только на ядрах Linux; Docker Desktop запускает скрытую Linux VM на macOS/Windows), разрастание образов и расход диска, сеть и хранилище добавляют сложности, root-демон как поверхность атаки ([[docker-socket-dind-dood]]), stateful-нагрузки требуют аккуратности ([[docker-volumes-and-registry]]).

### Контейнеры и виртуальные машины
| | Контейнер | Виртуальная машина |
|---|---|---|
| Ядро | Использует ядро хоста; работает в пространстве процессов хоста | Собственное гостевое ядро поверх гипервизора |
| Изоляция | Namespaces (что процесс видит) + cgroups (что ему можно использовать) ([[linux-architecture-and-kernel]]) | На уровне железа, обеспечивается гипервизором (KVM, VMware, Hyper-V) |
| Время запуска | Миллисекунды (это просто `clone()` + `exec`) | От секунд до минут (BIOS, ядро, init) |
| Размер | Мегабайты (приложение + библиотеки) | Гигабайты (полная ОС) |
| Накладные расходы | Почти нулевые; нативные системные вызовы | Расширения виртуализации CPU плюс память для каждой гостевой ОС |
| Граница безопасности | Слабее; эксплойт ядра позволяет выбраться на хост | Сильнее |
| Переносимость | Любой хост с совместимым ядром | Любой хост с гипервизором |
- Гипервизор — это ПО, которое позволяет нескольким VM работать параллельно на одном железе и делит между ними CPU, память и IO. Тип 1 работает на голом железе (KVM, ESXi), тип 2 — поверх хостовой ОС (VirtualBox).
- `ps` на хосте показывает процессы контейнера как обычные процессы; `docker top <c>` сопоставляет их.

### Образ и контейнер
- **Образ**: шаблон только для чтения с приложением и всеми его зависимостями (базовые файлы ОС, JDK, jar, конфигурация). Хранится как упорядоченный набор слоёв; каждый слой — это разница в файловой системе, созданная одной инструкцией Dockerfile. Идентифицируется дайджестом содержимого (`sha256:...`) и тегом (`repo/app:1.4.2`). Неизменяем: новая инструкция создаёт новый слой, предыдущие слои не трогаются ([[dockerfile-and-images]]).
- **Контейнер**: запущенный (или остановленный) экземпляр образа: слои образа плюс один тонкий **записываемый слой** плюс состояние времени выполнения (PID, сетевое пространство имён, монтирования, переменные окружения). Многие контейнеры из одного образа разделяют слои только для чтения. Удаление контейнера удаляет его записываемый слой; данные, которые должны пережить контейнер, кладут в volume.
- Образы собирают из Dockerfile (`docker build`) или фиксируют из запущенного контейнера (`docker commit`; лучше избегать, это невоспроизводимо). Скачивают из registry командой `docker pull`.

### Слоистая файловая система
- Каждый слой — это каталог с файлами; драйвер хранилища (**overlay2** в современном Linux) накладывает их друг на друга через union mount: верхние слои скрывают или добавляют файлы нижних; файл, удалённый в верхнем слое, маскируется *whiteout*-меткой, а байты остаются в нижнем слое.
- Преимущества: слои разделяются между образами и контейнерами на диске и в registry (скачивается только то, чего нет), сборка кешируется послойно, при старте контейнера ничего не копируется.
- Запись внутри контейнера идёт в его записываемый слой по принципу копирования при записи (copy-on-write): первая запись в файл из нижнего слоя копирует наверх весь файл. Нагрузкам с интенсивной записью (базам данных) место на volumes.
- `docker history <image>` перечисляет слои и их размеры; `docker image inspect` показывает дайджесты `RootFS.Layers`; `docker system df -v` показывает общее и уникальное место.

### Архитектура Docker
- CLI `docker` -> REST API через `/var/run/docker.sock` -> `dockerd` -> `containerd` (жизненный цикл образов и контейнеров) -> `runc` (OCI runtime, который фактически делает `clone()` в пространства имён). Kubernetes общается с containerd напрямую; образы в том же формате OCI.
- Docker Compose описывает многоконтейнерные приложения в `compose.yaml` для одного хоста; Swarm и Kubernetes распределяют нагрузку по нескольким хостам.

## Пример
```bash
# Один образ, два контейнера; доказываем, что они разделяют слои и ядро
docker pull eclipse-temurin:21-jre-alpine
docker history eclipse-temurin:21-jre-alpine --format '{{.Size}}\t{{.CreatedBy}}' | head -5

docker run -d --name a eclipse-temurin:21-jre-alpine sleep 1d
docker run -d --name b eclipse-temurin:21-jre-alpine sleep 1d
docker system df -v | grep -A3 'Containers space'       # у каждого контейнера ~0 B уникального, образ общий

uname -r                                                 # ядро хоста
docker exec a uname -r                                   # то же самое: гостевого ядра нет
docker exec a cat /etc/os-release | head -2              # поверх него userland Alpine
ps -o pid,ppid,cmd -C sleep                              # оба sleep — обычные процессы хоста
docker inspect -f '{{.GraphDriver.Data.UpperDir}}' a      # записываемый слой на диске
```

## Подводные камни
- Относиться к контейнеру как к VM: ставить `sshd`, запускать несколько демонов, хранить данные в записываемом слое. Один процесс на контейнер, данные в volumes, логи в stdout.
- Образ `latest` — просто тег, который перемещается; для воспроизводимых деплоев фиксируй версии или дайджесты.
- Alpine использует musl, а не glibc; некоторые нативные библиотеки и поведение DNS отличаются. `-jre-alpine` маленький, но его нужно тестировать; distroless или `-jre-jammy` — альтернативы на glibc.
- Записи в слой контейнера теряются при `docker rm` и медленные в overlay2; см. [[docker-volumes-and-registry]].
- Связанные заметки: [[dockerfile-and-images]], [[docker-containers-and-resources]], [[linux-architecture-and-kernel]].
