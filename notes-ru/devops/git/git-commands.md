## Кратко
Git — система контроля версий с тремя локальными областями: **рабочий каталог (working directory)** — твои файлы, **индекс / область подготовки (staging area)** — то, что попадёт в следующий коммит, заполняется через `git add`, и **локальный репозиторий** — история коммитов, записывается через `git commit`; `push`/`fetch` синхронизируют с удалённым репозиторием (remote). Всё остальное — перемещение коммитов и указателей: `merge` сохраняет историю, `rebase` переписывает её линейно, `reset` двигает ветку, `revert` добавляет отменяющий коммит, `reflog` находит то, что ты считал потерянным.

## Основное
### Области и состояния файлов
![Как команды git перемещают изменения между областями](assets/git-command-flow.png)
- **Untracked**: файл существует, но Git его не отслеживает. **Modified**: отслеживается и изменён в рабочем каталоге. **Staged**: изменение добавлено в индекс и готово к следующему коммиту. **Committed**: сохранено в локальном репозитории.
- `git status` показывает все четыре; `git diff` сравнивает рабочий каталог с индексом, `git diff --staged` — индекс с `HEAD`.
- `HEAD` указывает на текущий коммит, обычно через ветку (подвижный указатель); тег — фиксированный указатель.

### Синхронизация с remote
- `git fetch` скачивает все обновления из remote в локальный репозиторий (`origin/main` сдвигается), но не сливает их в твою ветку. Безопасен в любой момент.
- `git pull` = `git fetch` + `git merge origin/<branch>` в текущую ветку (две операции в одной). `git pull --rebase` вместо создания merge-коммита переигрывает твои локальные коммиты сверху; для feature-веток задай `pull.rebase=true`.
- `git push`, `git push -u origin feature/x` (задать upstream), `git push --force-with-lease` (безопасный force: падает, если кто-то успел запушить; никогда не используй обычный `--force` на общих ветках).

### Ветвление
- `git checkout <branch>` переключает; `git checkout -b <new>` создаёт и переключает. Современное разделение: `git switch <branch>` / `git switch -c <new>` для веток, `git restore <file>` для файлов (Git 2.23+). `git checkout <commit> -- <file>` восстанавливает файл из коммита.
- `git branch -d` удаляет слитую ветку, `-D` — принудительно.

### Объединение работы: merge, rebase и squash
- **merge**: вливает изменения из одной ветки в другую, сохраняет полную историю и добавляет merge-коммит (если это не fast-forward). Ветвление остаётся видимым. Используй, чтобы влить готовую фичу в `main` или `develop`.
- **rebase**: берёт коммиты текущей ветки и переигрывает их поверх целевой ветки, как будто они сделаны после неё. Результат: линейная история без merge-коммитов. Он *переписывает* коммиты (новые хеши), поэтому применяй его на своих локальных или личных ветках, но никогда на ветках, которые уже забрали другие. Типично: `git fetch && git rebase origin/main` перед открытием merge request.
- **squash**: объединение нескольких мелких коммитов в один, чтобы история выглядела чисто; чаще всего через интерактивный rebase (`git rebase -i HEAD~5`, пометить коммиты `squash`/`fixup`) или `git merge --squash feature` при слиянии. GitLab/GitHub предлагают «squash on merge».
- **amend**: `git commit --amend` добавляет проиндексированные изменения в последний коммит (и позволяет отредактировать сообщение); `--no-edit` сохраняет сообщение. Тоже переписывание: только до push или push с `--force-with-lease`.
- **cherry-pick**: `git cherry-pick <sha> [<sha>...]` применяет один или несколько коммитов из другой ветки к текущей (hotfix из `main` в релизную ветку). `-x` записывает происхождение в сообщение.

### Отмена
- **stash**: сохраняет изменения рабочего каталога и индекса, чтобы можно было переключить ветку без коммита. `git stash` или `git stash push -m "wip: retry logic"` сохраняет; `git stash list`; `git stash pop` применяет заново и удаляет запись; `git stash apply` применяет и сохраняет запись; `git stash -u` включает неотслеживаемые файлы; `git stash drop`.
- **reset**: перемещает текущую ветку (HEAD) на другой коммит и при необходимости корректирует индекс и рабочий каталог. `--soft`: изменения остаются в индексе, рабочий каталог не трогается (`git reset --soft HEAD~3`, чтобы перекоммитить три коммита как один). `--mixed` (по умолчанию): очищает индекс, рабочий каталог не трогается (изменения становятся непроиндексированными). `--hard`: очищает индекс и рабочий каталог; незакоммиченная работа пропадает. `git reset <file>` убирает из индекса один файл (современная форма — `git restore --staged <file>`).
- **revert**: создаёт новый коммит, отменяющий изменения указанного коммита; история сохраняется, поэтому это правильный инструмент для уже запушенных веток. `git revert <sha>` открывает редактор для сообщения; `--no-edit` оставляет сообщение по умолчанию; `git revert HEAD~2..HEAD` отменяет диапазон; `-m 1` — для merge-коммита.
- **reflog**: `git reflog` показывает историю всех перемещений `HEAD` (checkout, reset, rebase, amend), включая коммиты, недостижимые ни из одной ветки. После неудачного `reset --hard` или rebase: `git reflog`, найти запись, `git reset --hard HEAD@{3}` или `git branch rescue <sha>`. Записи истекают через 90 дней.

### Конфликты
- Конфликт возникает, когда Git не может слить изменения автоматически: обе стороны изменили одни и те же строки (или одна удалила файл, который редактировала другая). Чаще всего при `merge`, `rebase`, `cherry-pick`, `stash apply/pop`.
- Порядок действий: `git status` перечисляет файлы с конфликтами (`both modified`); открыть их, разрешить маркеры `<<<<<<< HEAD` / `=======` / `>>>>>>> branch` (или использовать `git mergetool`, IDE); после разрешения добавить в индекс через `git add <file>`; завершить через `git commit` (merge, cherry-pick) или `git rebase --continue`.
- Чтобы сдаться: `git merge --abort`, `git rebase --abort`, `git cherry-pick --abort`. `git checkout --ours|--theirs <file>` берёт одну сторону целиком (внимание: при rebase «ours» — это ветка, *на которую* делается rebase).

### Просмотр
- `git log --oneline --graph --all`, `git log -p <file>`, `git blame -L 40,60 <file>`, `git show <sha>`, `git bisect`, чтобы найти коммит, сломавший тест.

## Пример
```bash
# Типичный цикл feature-ветки с чистой линейной историей
git switch -c feature/esim-retry origin/main
# ... работа ...
git add -p                                   # выборочно добавить куски в индекс
git commit -m "Add retry with backoff to SM-DP+ client"
git commit --amend --no-edit                 # забыл файл: добавить его в последний коммит

git fetch origin
git rebase -i origin/main                    # переиграть поверх main, схлопнуть fixup-коммиты
# конфликт в RetryPolicy.java
git status
$EDITOR src/main/java/.../RetryPolicy.java   # разрешить маркеры
git add src/main/java/.../RetryPolicy.java
git rebase --continue

git push --force-with-lease -u origin feature/esim-retry

# Упс: reset --hard не на той ветке
git reflog | head -5                         # 3f2a1c0 HEAD@{1}: commit: Add retry with backoff ...
git reset --hard HEAD@{1}

# Отменить плохой коммит, который уже в main, без переписывания истории
git revert --no-edit 9b1e7d4 && git push
```

## Подводные камни
- Rebase или amend коммитов, которые другие уже забрали, заставляет всех чинить свою историю; переписывай только приватные ветки и пушь переписанное с `--force-with-lease`.
- `git reset --hard` и `git checkout -- <file>` уничтожают незакоммиченную работу без записи в reflog; сначала сделай stash.
- `git pull` на грязном рабочем дереве со стратегией merge по умолчанию создаёт неожиданные merge-коммиты; используй `pull --rebase` или сначала сделай fetch и посмотри.
- `stash pop` с конфликтом оставляет stash в списке; после разрешения удали его вручную.
- Секреты, закоммиченные в историю, остаются там, если её не переписать (`git filter-repo`); секрет всё равно нужно ротировать, у каждого клона он уже есть.
