## Кратко
Предметно-ориентированное проектирование (domain-driven design, DDD) строит код по образу бизнеса: **домен** — это предметная область, **модель** — её представление в коде, **сущность** (entity) — объект модели с идентичностью, а **агрегат** (aggregate) — группа сущностей и объектов-значений, которая загружается, изменяется и сохраняется как одна единица согласованности через свой **корень** (root). Вокруг DDD есть словарь, в котором полезно не путаться: архитектурные *стили* (слоистая, гексагональная, событийно-ориентированная), *принципы* проектирования (SOLID, DRY, KISS) и *паттерны* проектирования (Factory, Observer) отвечают на разные вопросы.

## Основное
### Ключевые термины DDD
- **Домен** (domain): предметная область, которую обслуживает программа (биллинг, eSIM provisioning, реферальная программа).
- **Модель** (model): представление домена в коде, общее с экспертами предметной области через *единый язык* (ubiquitous language) — одни и те же слова в разговоре, коде и базе данных.
- **Сущность** (entity): конкретный доменный объект с идентичностью (`Subscriber #123`); две сущности с одинаковыми полями, но разными id — разные объекты.
- **Объект-значение** (value object): определяется только своими атрибутами, неизменяемый, без id (`Money(100, KGS)`, `PhoneNumber`). Хорошо подходят Java records ([[immutable-objects]]).
- **Инварианты** (invariants): условия, которые всегда должны выполняться для валидного состояния (сумма заказа равна сумме его строк; профиль eSIM нельзя активировать дважды).
- **Ограниченный контекст** (bounded context): граница, внутри которой модель и её язык согласованы. «Клиент» в биллинге и «клиент» в поддержке — разные модели; карта контекстов описывает, как они переводятся друг в друга.

### Агрегат
- Группа связанных объектов (сущности + объекты-значения), которая рассматривается как единое целое ради гарантии согласованности данных; логическая единица согласованности в домене.
- **Корень агрегата** (aggregate root): главная сущность, через которую управляются все внутренние объекты. Внешний код держит ссылку только на корень и меняет внутренности только через него.
- Инварианты обеспечиваются внутри агрегата; одна транзакция меняет один агрегат.
- Каждый агрегат загружается и сохраняется целиком **репозиторием** (repository) ([[spring-data-repositories]]); это естественная единица для ключа `aggregate_id` в [[outbox-pattern]] и для партиционирования в Kafka ([[kafka-architecture]]).
- Изменения между агрегатами идут через **доменные события** (domain events) и согласованность в конечном счёте (eventual consistency), а не через одну большую транзакцию.

### Архитектуры уровня приложения (структурные: как построена система)
- Слоистая (controller / service / repository), Clean, Onion, гексагональная (порты и адаптеры), микросервисы, модульный монолит. Цель — управляемость и разделение ответственности.
- Clean и Onion концептуально почти одинаковы; гексагональная делает акцент на интеграции с внешним миром через порты и адаптеры; слоистая — просто схема разбиения кода на слои.

### Подходы уровня системы (поведенческие: как общаются модули)
- Событийно-ориентированная архитектура (event-driven architecture), CQRS, очередь сообщений / pub-sub ([[rabbitmq-basics]], [[kafka-architecture]]), модель акторов. Цель — реактивность, асинхронность, гибкость.
- Данные и интеграция: data-centric, data mesh, data lake / lambda, общая база данных или база на сервис (database-per-service). Цель — согласованность и масштабирование данных.
- Инфраструктура: cloud-native, serverless, SOA, контейнеры / Kubernetes ([[docker-swarm]]). Цель — масштабирование, отказоустойчивость, развёртывание.

|---|---|---|
| Структурная | Как построена система | Слоистая, гексагональная |
| Поведенческая | Как движутся управление и события | EDA, CQRS |
| Данные | Как данные хранятся и управляются | Data mesh, Lambda |

### Принципы, паттерны и стили
- **Принципы** — это цель или правило: [[solid]], DRY, KISS, YAGNI, слабая связанность / высокая связность (loose coupling / high cohesion: компоненты сосредоточены на одной задаче и максимально независимы друг от друга).
- **Паттерны** — готовое решение, которое достигает цели: «чтобы получить слабую связанность, используем очередь сообщений»; [[creational-patterns]] создают объекты, [[structural-patterns]] компонуют их, [[behavioral-patterns]] учат их общаться.
- **Стили** — общая форма, следующая набору принципов: микросервисы, событийно-ориентированная архитектура.
- **Методологии** — способы работы: TDD, DDD.

## Пример
```java
// Корень агрегата: все изменения идут через Order; инварианты живут здесь, а не в сервисе.
public class Order {
    private final OrderId id;
    private final List<OrderLine> lines = new ArrayList<>();   // внутренние сущности
    private OrderStatus status = OrderStatus.NEW;
    private final List<DomainEvent> events = new ArrayList<>();

    public void addLine(ProductId product, Quantity qty, Money price) {
        if (status != OrderStatus.NEW) throw new IllegalStateException("order already " + status);
        lines.add(new OrderLine(product, qty, price));
    }

    public void confirm() {
        if (lines.isEmpty()) throw new IllegalStateException("empty order");   // инвариант
        status = OrderStatus.CONFIRMED;
        events.add(new OrderConfirmed(id, total()));   // другие агрегаты реагируют асинхронно
    }

    public Money total() { return lines.stream().map(OrderLine::subtotal).reduce(Money.ZERO, Money::plus); }
    public List<DomainEvent> pullEvents() { var copy = List.copyOf(events); events.clear(); return copy; }
}
```

## Подводные камни
- Анемичная модель: сущности — это геттеры и сеттеры, а вся логика сидит в классах `@Service`; инварианты тогда проверяются в нескольких местах или не проверяются вовсе.
- Слишком большие агрегаты (`Customer` со всеми заказами) блокируют и загружают слишком много; их стоит держать маленькими и ссылаться на другие агрегаты по id, а не по объекту ([[jpa-entities-and-relationships]], [[jpa-n-plus-one]]).
- Отображение агрегата 1:1 на граф JPA-сущностей с каскадами приводит к тому, что границу согласованности определяет ORM, а не домен ([[jpa-persistence-context-and-entity-lifecycle]]).
- Публикация доменных событий прямо из сервиса до commit теряет их при откате; нужен [[outbox-pattern]] и [[idempotency|идемпотентные]] потребители.
- Связанные заметки: [[solid]], [[architecture-resources]].
