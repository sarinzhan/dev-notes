## Кратко
Сервисы общаются либо **синхронно** (REST/gRPC: вызывающий блокируется в ожидании ответа и разделяет судьбу вызываемого), либо **асинхронно** (сообщения/события: вызывающий продолжает работу, а дело делается позже, at-least-once). Синхронное взаимодействие — для вопросов, на которые нужен ответ сейчас, асинхронное — для фактов и работы, которую можно отложить. Каждому синхронному вызову нужен **таймаут**, ограниченный **бюджет retry** с backoff и jitter и [[circuit-breaker]]; каждому асинхронному переходу нужен [[outbox-pattern]] у producer-а и [[idempotency]] у consumer-а. Типичная ошибка — выстраивать цепочки синхронных вызовов, пока доступность не перемножится до нуля.

## Какую проблему решает
- **Без осознанного выбора:** всё вызывают по REST, потому что так проще всего. Запрос на заказ eSIM тогда ждёт цепочку из проверки доступности, платежа, provisioning и биллинга: задержки складываются, доступность перемножается вниз, и одна медленная зависимость роняет весь поток. Или наоборот: проверка доступности идёт через Kafka, и пользователь ждёт ответа из reply-топика.
- **Что меняет правильный выбор:** вопросы, ответа на которые ждёт пользователь, остаются синхронными, с таймаутами и circuit breaker; факты и работа, которая может подождать, уходят асинхронно через outbox, поэтому простой биллинга стоит lag, а не упавших заказов.
- **Когда это неважно:** несколько сервисов с небольшой нагрузкой и одна команда. По умолчанию — синхронные вызовы с таймаутами, а в асинхронный вызов переводится только тогда, когда он становится реальной проблемой.

## Основное

### Сравнение
| | Синхронное (REST, gRPC) | Асинхронное (Kafka, RabbitMQ) |
|---|---|---|
| Связанность | Временная: вызываемый должен работать прямо сейчас | Только по контракту (схеме) |
| Задержка | Задержка запроса = сумма цепочки | Вызывающий возвращается быстро; сквозная — секунды |
| Согласованность | Вызывающий сразу видит результат | В конечном счёте |
| Обработка сбоев | Таймаут, retry, breaker, fallback | Retry-топик, DLQ, алерты на lag ([[dead-letter-queues-and-retries]]) |
| Отладка | Стек вызовов в одной трассе | Ссылки трасс во времени ([[distributed-tracing]]) |
| Подходит для | Запросов, валидаций, аутентификации, всего, чего ждёт пользователь | Побочных эффектов, fan-out, всплесков, долгой работы |
- Математика доступности: пять синхронных переходов по 99,9 % каждый дают 99,5 % для запроса. Асинхронность убирает переход с критического пути, но не убирает саму работу.
- Запрос/ответ через очередь (топики ответов, correlation id) с точки зрения вызывающего всё равно синхронный, только медленнее и сложнее в отладке; использовать редко.

### REST или gRPC для синхронной части
- REST/JSON: универсален, кэшируем ([[http-caching]]), читаем, инструменты OpenAPI ([[openapi-swagger]]). gRPC: бинарный, типизированный контракт, стриминг, в 5–10 раз меньше CPU на сериализацию, мультиплексирование HTTP/2; слабее с браузерами, для внешних клиентов нужен gateway ([[grpc-and-protobuf]], [[http-1-1-vs-2-vs-3]]).
- Внутреннее взаимодействие сервисов с множеством мелких вызовов: gRPC окупается. Публичный API и партнёрские интеграции: REST.

### Таймауты и бюджет retry
- Таймауты **соединения** (connect) и **чтения** (read) выставляются на каждом клиенте ([[rest-clients]]); без таймаута на каждый запрос висит поток, пока пул не кончится.
- Таймауты должны уменьшаться вниз по цепочке: если gateway ждёт 5 с, сервис за ним должен сдаться через 4 с, его база — через 3 с (`statement_timeout`), иначе вызывающий уже ушёл, а работа потрачена впустую ([[postgres-performance-checklist]]).
- Бюджет retry: retry как процент трафика (10 %), а не «3 на вызов», или хотя бы 3 попытки × короткий таймаут с экспоненциальным backoff + jitter, только для идемпотентных операций и только на временных ошибках. Retry на каждом уровне перемножаются (3 × 3 × 3 = 27 вызовов на один сбой): повторять нужно на одном уровне.
- Распространение дедлайна: gRPC передаёт дедлайны нативно; для REST передавать заголовок `X-Deadline` или полагаться на уменьшающиеся таймауты.

### Сдерживание сбоев
- Bulkhead-ы: отдельные пулы потоков или семафоры на каждую зависимость, чтобы один медленный партнёр не исчерпал Tomcat (конфигурация bulkhead и breaker описана в [[circuit-breaker]]).
- Fallback-и: закэшированное последнее известное значение, значение по умолчанию, деградированный ответ (`"status": "unknown"`) или поставить работу в очередь и ответить 202 Accepted. Для каждого вызова нужно решить, что для пользователя значит «частично».
- Плавная деградация лучше 500 для необязательных зависимостей (рекомендации, обогащение данных).

### Выбор для каждого взаимодействия
- «Подходит ли этот MSISDN для eSIM?» → синхронный запрос в сервис абонентов (пользователь ждёт) с таймаутом 300 мс и кэшированным fallback.
- «Профиль активирован, начать биллинг» → асинхронное событие; биллинг может лежать час, и ничего не потеряется.
- «Списать с карты» → синхронно в PSP с ключом идемпотентности и долгоиграющим fallback на шаг [[saga]], если PSP ответил неоднозначным таймаутом.
- «Заказ оформлен, выполнить provisioning в течение 24 ч» → движок workflow ([[temporal-concepts]]), то есть асинхронная оркестрация с синхронными activity внутри.

## Пример
`RestClient` с явными таймаутами и заголовком дедлайна, обёрнутый Resilience4j, и асинхронная альтернатива для того же бизнес-шага.

```java
@Configuration
class ClientConfig {
    @Bean
    RestClient subscriberClient(RestClient.Builder builder) {
        var factory = new JdkClientHttpRequestFactory(HttpClient.newBuilder()
                .connectTimeout(Duration.ofMillis(200)).build());
        factory.setReadTimeout(Duration.ofMillis(500));                  // пользователь ждёт: падать быстро
        return builder.baseUrl("http://subscriber-service").requestFactory(factory).build();
    }
}

@Service
@RequiredArgsConstructor
public class EligibilityGateway {
    private final RestClient subscriberClient;

    @Retry(name = "subscriber")                       // 2 попытки, backoff 100 мс с jitter, только IOException/5xx
    @CircuitBreaker(name = "subscriber", fallbackMethod = "unknown")
    public Eligibility check(Msisdn msisdn, Instant deadline) {
        return subscriberClient.get()
                .uri("/subscribers/{msisdn}/esim-eligibility", msisdn.value())
                .header("X-Deadline", deadline.toString())               // вызываемый может остановиться раньше
                .retrieve()
                .body(Eligibility.class);
    }

    Eligibility unknown(Msisdn msisdn, Instant deadline, Throwable t) {
        return Eligibility.unknown("subscriber-service unavailable");    // деградировать, а не отдавать 500
    }
}

// Асинхронная сторона того же процесса: факт записывается в outbox, биллинг реагирует позже.
@Transactional
public void activate(ActivateProfile cmd) {
    Sim sim = sims.findById(cmd.simId()).orElseThrow();
    sim.activate(cmd.iccid());
    sims.save(sim);
    outbox.save(OutboxRow.of("esim.sim.events", sim.id(), new ProfileActivatedV1(sim.id(), cmd.iccid().value())));
}
```

## Подводные камни
- Таймауты по умолчанию: у `RestClient` с JDK-клиентом нет таймаута чтения, у Apache HttpClient в некоторых версиях по умолчанию бесконечность; тогда одна медленная зависимость роняет весь сервис.
- Retry неидемпотентных POST по таймауту: двойные списания, двойные SMS. Нужен `Idempotency-Key`, иначе не повторять.
- Синхронный вызов из Kafka listener-а в сервис, который лежит: партиция встаёт, lag растёт, а шторм retry обрушивается на зависимость, когда она восстанавливается. Нужны breaker и retry-топик.
- Отношение к брокеру сообщений как к «всегда доступному»: producer-ам outbox нужен именно потому, что `send()` тоже может упасть.
