## Кратко
Паттерн «фикус-душитель» (strangler fig) заменяет legacy-систему **по одной возможности за раз**: перед монолитом ставится маршрутизирующий фасад (gateway, прокси), рядом строится новая реализация одной возможности, маршрут переключается, и так повторяется, пока старая система не опустеет и её можно будет удалить. Ничего не переписывается разом (big-bang), каждый шаг обратим переключением маршрута назад, и бизнес продолжает выпускать фичи. Самое сложное — не код, а **данные**: кто владеет таблицей во время перехода и как обе стороны остаются согласованными.

## Основное

### Почему не переписать
- Полное переписывание замораживает фичи на месяцы, по памяти заново реализует недокументированное поведение и выходит в прод одним гигантским переключением, которое нельзя откатить. Большинство переписываний систем старше нескольких лет бросают или выпускают с опозданием.
- «Удушение» приносит пользу с каждым срезом, оставляет старую систему эталоном поведения (сравнение выходных данных) и позволяет команде освоить новую платформу сначала на возможности с низким риском.

### Цикл для каждой возможности
1. **Выбрать шов** (seam): возможность с понятными входами/выходами и малым числом общих таблиц, в идеале — [[bounded-contexts-and-context-mapping|ограниченный контекст]], уже видимый в коде (уведомления, экспорт в PDF, поиск тарифа). Начинать с чего-то ценного, но не самого критичного.
2. **Перехватить**: пустить трафик через фасад: [[api-gateway-and-service-discovery|API gateway]], nginx ([[reverse-proxy-nginx-basics]]) или feature flag внутри монолита для внутренних вызовов. События из монолита можно захватывать через CDC (Debezium на его таблицах), если у него нет outbox.
3. **Построить и пустить в тень**: реализовать новый сервис; запустить его в теневом режиме (shadow mode: один и тот же запрос в оба, сравнить результаты, отдать старый) или сделать скрытый запуск (dark launch) для внутренних пользователей.
4. **Переключить** по маршруту, по проценту, по арендатору (tenant). Старый путь держать живым, а переключение — мгновенным.
5. **Вывести из эксплуатации**: удалить старый код и таблицы, когда их больше никто не вызывает; проверять по access-логам и [[grafana-dashboards-and-red-use|дашбордам]], а не по убеждениям.

### Данные во время перехода
| Стратегия | Как | Компромисс |
|---|---|---|
| **База на возможность с первого дня** | Новый сервис владеет своими таблицами; монолит вызывает его или потребляет его события | Чище всего; сначала нужно найти каждое чтение этих таблиц в монолите |
| **Общая база, временно** | Новый сервис читает/пишет таблицы монолита | Быстрый старт; схема теперь — контракт между двумя единицами развёртывания ([[coupling-cohesion-and-general-principles|связанность по общим данным]]) |
| **Двойная запись со сверкой** | Монолит пишет в свою таблицу и публикует; новый сервис держит свою копию | Классическая опасность двойной записи; нужен [[outbox-pattern]] или CDC плюс задача сверки |
| **Захват изменений данных** (CDC) | Debezium стримит изменения таблиц монолита в новый сервис | Код монолита не меняется; новый сервис — downstream и согласован в конечном счёте |
- Направление владения: выбрать момент, когда **новый сервис становится писателем**, а монолит — читателем (через API или реплицированное представление). До этого момента источник истины — монолит; никогда не должно быть двух писателей одного факта.
- Expand/contract на схеме для колонок, которые трогают обе стороны ([[schema-migrations-flyway-liquibase]]).

### Сначала внутри монолита
- Многим проектам «из монолита в микросервисы» стоит остановиться на [[modular-monolith]]: обеспечить границы модулей (Spring Modulith, ArchUnit), заменить прямые вызовы интерфейсами/событиями и только потом выделять модули, которым нужны независимое масштабирование или владение ([[monolith-vs-microservices]]).
- Техника branch by abstraction — это «душитель» внутри процесса: ввести интерфейс, оставить старую реализацию, добавить новую, переключить флагом, удалить старую.

### Тезисы для собеседования
- Порядок выделения: по ценности для бизнеса и по связанности (сначала наименее связанные), а не по принципу «то, что мне больше всего не нравится».
- История с откатом: каждое переключение — изменение конфигурации; старый путь удаляется только после периода выдержки (soak period).
- Наблюдаемость до миграции: нужны базовые задержка и доля ошибок, чтобы знать, что новый путь не хуже ([[slo-sli-and-alerting]]).
- Как избежать распределённого монолита: если выделенному сервису на каждый запрос нужен синхронный вызов обратно в монолит, шов выбран неверно.

## Пример
«Удушение» на уровне gateway со Spring Cloud Gateway: endpoint-ы уведомлений переходят в новый сервис для 10 % трафика, всё остальное по-прежнему идёт в монолит; заголовок принудительно включает новый путь для тестировщиков.

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: notifications-new-forced          # тестировщики и canary-клиенты
          uri: http://notification-service:8080
          predicates:
            - Path=/api/notifications/**
            - Header=X-Strangler, new
        - id: notifications-new-weighted
          uri: http://notification-service:8080
          predicates:
            - Path=/api/notifications/**
            - Weight=notifications, 10         # 10 % оставшегося трафика
        - id: notifications-legacy
          uri: http://legacy-monolith:8080
          predicates:
            - Path=/api/notifications/**
            - Weight=notifications, 90
        - id: everything-else
          uri: http://legacy-monolith:8080
          predicates:
            - Path=/**
      default-filters:
        - AddRequestHeader=X-Via-Gateway, true
```

Поднять вес до 100, а затем удалить legacy-маршруты — это и есть «удушение»; каждый шаг — deploy конфигурации, обратимый за секунды. Оба пути сравниваются в Grafana по тегу `route_id`, который Spring Cloud Gateway добавляет к своим метрикам.

## Подводные камни
- Общая база «временно» на два года: никто не может менять схему, потому что другая сторона может её читать. Нужны дата и план передачи владения.
- Выделение по техническому слою («сервис сущностей», отдающий CRUD над таблицами монолита): каждый бизнес-процесс теперь делает десять сетевых вызовов. Выделять нужно по возможностям.
- Нет фасада: вызывающие захардкодили URL монолита, поэтому переключение означает правку каждого клиента. Gateway нужно поставить до того, как что-либо выделять.
- Двойная запись из монолита через обычный `kafka.send()`: потерянные или фантомные события ([[outbox-pattern]]), и копия нового сервиса расползается; сверять ежедневно, пока старый писатель не выведен из эксплуатации.
- Связанные заметки: [[monolith-vs-microservices]], [[modular-monolith]], [[api-gateway-and-service-discovery]], [[event-driven-architecture]].
