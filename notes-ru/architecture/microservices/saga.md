## Кратко
Сага (saga) — это бизнес-транзакция, охватывающая несколько сервисов и реализованная как **последовательность локальных транзакций**, каждая из которых коммитится в своей базе данных. Если более поздний шаг падает, сага выполняет **компенсирующие транзакции** (compensating transactions), которые семантически отменяют предыдущие шаги. Саги заменяют распределённые транзакции 2PC согласованностью в конечном счёте плюс явной логикой «отмены»; управлять ими можно двумя способами — центральным **оркестратором** (orchestration) или событийной **хореографией** (choreography).

## Какую проблему решает
- **Без этого:** заказ eSIM затрагивает три сервиса со своими базами: резерв профиля, списание с карты, активация на HLR. Распределённой транзакции 2PC (XA) нужен координатор, который держит блокировки у каждого участника до глобального commit. Это медленно, блокируется при отказе координатора и не существует поверх Kafka, HTTP или стороннего API (процессинг карт, сервер SM-DP+). Без плана сбой после списания оставляет деньги списанными, а eSIM — недоставленной.
- **Что меняет:** микросервисы владеют своими данными ([[ddd-basics|ограниченные контексты]]), поэтому ACID между сервисами исключён. Вместо этого каждый шаг коммитится локально и имеет компенсирующий шаг, и заказ заканчивается либо полностью выполненным, либо полностью скомпенсированным: **атомарность между сервисами** без изоляции.
- **Когда не нужно:** вся операция живёт в одном сервисе и одной базе (хватит локальной транзакции) или упавший шаг можно просто повторять до успеха и отменять ничего не нужно.

## Основное

### Оркестрация и хореография
| | Оркестрация | Хореография |
|---|---|---|
| Кто решает следующий шаг | Центральный оркестратор саги (машина состояний) | Каждый сервис реагирует на события и порождает новые |
| Связанность | Сервисы знают только оркестратор | Сервисы знают контракты событий соседей |
| Наблюдаемость | Одно место, где видно «где заказ 42» | Размазано по логам/топикам; нужна трассировка |
| Риск | Оркестратор становится god-сервисом | Циклические зависимости событий, трудно менять |
| Подходит для | Длинных процессов с многими шагами, компенсациями, таймаутами | 2–4 шагов, простого fan-out |

- Реализации оркестратора: написанная вручную машина состояний с хранением в Postgres, Axon/Eventuate или движок workflow вроде Temporal. **Temporal — это оркестратор саг**: workflow — оркестратор, activity — шаги, хелпер `Saga` регистрирует компенсации, а история событий бесплатно даёт хранение состояния и replay ([[temporal-concepts]]).
- Хореография живёт в Kafka: `OrderCreated` → платёжный сервис порождает `PaymentAuthorized` → provisioning порождает `ProfileReserved`, а [[outbox-pattern]] делает публикацию каждого события атомарной с его локальным commit.

### Типы транзакций внутри саги
- **Компенсируемые** (compensatable) транзакции можно отменить (зарезервировать товар → снять резерв; авторизовать карту → отменить авторизацию).
- **Поворотная транзакция** (pivot transaction) — точка невозврата: после её commit сага должна завершиться и никогда не откатываться (списать платёж, отправить абоненту загрузку eSIM). Всё после поворотной транзакции должно быть **повторяемым** (retriable) до успеха.
- Компенсация семантическая, а не откат в БД: возврат денег — новая транзакция, исходный платёж остаётся в истории.

### Проблемы изоляции и контрмеры
- Сагам не хватает «I» из ACID: другие транзакции видят промежуточное состояние (потерянное обновление, грязное чтение заказа, который зарезервирован, но не оплачен).
- **Семантическая блокировка** (semantic lock): пометить запись (`status = PENDING`), чтобы другие процессы отказывали или ждали; снять пометку на последнем шаге или в компенсации.
- **Коммутативные обновления** (инкременты вместо присваивания), **пессимистичное представление** (переставить шаги так, чтобы рискованный шёл последним), **повторное чтение значения** перед поворотной транзакцией, **файл версий** (хранить последовательность операций, чтобы применять их по порядку).

### Состояние и надёжность
- Состояние саги (id, текущий шаг, результаты шагов, компенсации) хранится в таблице или в истории Temporal; после падения оркестратор продолжает с последнего сохранённого шага.
- Каждый шаг вызывается как минимум один раз, поэтому каждый шаг должен быть [[idempotency|идемпотентным]] (id саги как ключ идемпотентности), а компенсации должны выдерживать ситуацию «отменять нечего».
- Таймауты на каждый шаг; застрявший шаг превращается в компенсацию или в ручное состояние «требует внимания», но никогда не в молчаливое зависание.

## Пример
Написанный вручную оркестратор для заказа eSIM: зарезервировать профиль → списать с карты (поворотная транзакция) → активировать на HLR. Каждый шаг — локальная транзакция в другом сервисе, вызываемом по HTTP/Kafka.

```java
@Service
@RequiredArgsConstructor
public class EsimOrderSaga {
    private final ProfileClient profiles;
    private final PaymentClient payments;
    private final HlrClient hlr;
    private final SagaStateRepository states;

    @Transactional
    public void run(OrderId orderId, Msisdn msisdn, Money price) {
        Deque<Runnable> compensations = new ArrayDeque<>();
        SagaState state = states.start(orderId);
        try {
            String iccid = profiles.reserve(orderId.value());           // идемпотентно по orderId
            compensations.push(() -> profiles.release(iccid));
            state.step("PROFILE_RESERVED", iccid);

            String authId = payments.authorize(orderId.value(), price);
            compensations.push(() -> payments.voidAuth(authId));
            state.step("PAYMENT_AUTHORIZED", authId);

            payments.capture(authId);                                   // поворотная точка: после неё отката нет
            state.step("PAYMENT_CAPTURED");

            retryUntilDone(() -> hlr.activate(msisdn, iccid));          // повторяемый хвост
            state.complete();
        } catch (RuntimeException e) {
            while (!compensations.isEmpty()) compensations.pop().run();  // в обратном порядке
            state.compensated(e.getMessage());
            throw e;
        }
    }
}
```

## Подводные камни
- Компенсации, которые падают: ставить их в очередь на retry (таблица outbox, планировщик или политика retry в Temporal); молча потерянная компенсация оставляет деньги списанными, а ничего не доставленным.
- Порядок компенсаций важен: отменять в обратном порядке, потому что поздние шаги могут зависеть от ранних.
- Хореографию без явного id саги и correlation id невозможно отлаживать — нужна [[distributed-tracing]], а id саги должен быть в заголовке каждого события.
- Забыть о поворотной транзакции: повторить списание с карты после возврата или освободить профиль, который абонент уже скачал.
- Связанные заметки: [[outbox-pattern]] (атомарная публикация события каждого шага), [[idempotency]] (безопасные retry), [[temporal-concepts]] (движок-оркестратор), [[circuit-breaker]] (вызов ненадёжных участников), [[system-design-basics]].
