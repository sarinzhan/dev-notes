## Кратко
Слоистая архитектура (layered architecture) делит приложение на горизонтальные слои — представление (контроллеры), бизнес-логика (сервисы), доступ к данным (репозитории) — и разрешает зависимостям идти только вниз. Это форма по умолчанию почти любого сервиса на Spring Boot, и она вполне подходит для небольших и средних кодовых баз с преобладанием CRUD. Она ломается, когда бизнес-правила расползаются по контроллерам, сервисам и SQL, когда сервисы разрастаются в god-классы и когда доменная модель вырождается в мешки геттеров и сеттеров.

## Основное
### Слои и направление зависимостей
- **Представление (presentation)**: REST-контроллеры, Kafka-листенеры, планировщики. Переводят транспорт (HTTP, JSON, заголовки) в вызовы методов и обратно ([[spring-mvc-request-lifecycle]]).
- **Бизнес-логика / сервисы (business / service)**: сценарии использования, валидация, оркестрация репозиториев и внешних клиентов, границы транзакций ([[spring-transactional]]).
- **Доступ к данным (data access)**: репозитории, JPA-сущности, JDBC, внешние HTTP-клиенты ([[spring-data-repositories]]).
- Зависимости идут **только сверху вниз**: контроллер → сервис → репозиторий. Репозиторий никогда не вызывает сервис; сервис никогда не трогает `HttpServletRequest`.
- *Строгое* разбиение на слои разрешает слою вызывать только слой непосредственно под ним; *ослабленное* разрешает контроллеру вызывать репозиторий напрямую. На практике большинство Spring-проектов используют ослабленный вариант, и с этого начинаются протечки.
- Доменная модель (сущности) обычно общая для всех слоёв, поэтому она стоит «рядом» со стеком, а не внутри какого-то одного слоя.

### Анемичная доменная модель
- Сущности содержат только поля и методы доступа; все правила живут в методах `@Service`. Мартин Фаулер назвал это антипаттерном, потому что это процедурный код в объектно-ориентированном костюме.
- Последствие: один и тот же инвариант («профиль нельзя активировать дважды») проверяется в трёх сервисах или ни в одном. Сравни с богатым агрегатом в [[ddd-basics]].
- Это всё же честный выбор, когда «домен» действительно CRUD с минимумом логики: странице настроек агрегат не нужен.

### Где слоистая архитектура ломается
- **Логика протекает вверх**: контроллеры начинают делать `if (order.getStatus() == PAID)` перед вызовом сервиса, а Kafka-листенер дублирует проверку по-своему.
- **Логика протекает вниз**: бизнес-правила прячутся в JPQL-запросах, триггерах базы данных или колбэках `@PrePersist`, невидимые для тестов.
- **Границы транзакций размываются**: `@Transactional` на методе контроллера или сервис, вызывающий другой `@Transactional`-сервис в цикле, так что один сбой откатывает несвязанную работу или вообще ничего.
- **God-сервисы**: `SubscriberService` с 60 методами и 15 внедрёнными зависимостями; его трогает каждая фича, конфликты слияния постоянны, тестам нужна дюжина моков ([[junit-and-mockito]]).
- **Инфраструктура в центре**: сервисы зависят напрямую от `JpaRepository` и `RestTemplate`, поэтому «бизнес-слой» нельзя скомпилировать или протестировать без Spring и базы данных.
- **Пакеты по слоям** (package-by-layer: `controller/`, `service/`, `repository/`) прячут фичи: чтобы разобраться в «реферальном бонусе», приходится открыть шесть пакетов. Пакеты по фичам (package-by-feature) — см. [[modular-monolith]].

### Когда она вполне годится
- Небольшие команды, небольшие сервисы, в основном CRUD, короткий срок жизни или внутренний инструмент: дополнительные интерфейсы [[hexagonal-architecture]] или [[clean-architecture]] стоят больше, чем экономят.
- Правилам легко следовать: контроллеры тонкие, сервисы владеют транзакциями, репозитории владеют запросами, сущности несут очевидные инварианты.
- Это ещё и естественная отправная точка: большинство гексагональных сервисов были слоистыми, пока логика не выросла и ядро не выделили.

## Пример
Типичная раскладка Spring-проекта и обычная форма метода сервиса:

```text
com.beeline.esim
├── controller/   EsimOrderController
├── service/      EsimOrderService, PricingService
├── repository/   EsimOrderRepository (JpaRepository)
├── entity/       EsimOrder, Subscriber
└── dto/          CreateOrderRequest, OrderResponse
```

```java
@Service
@RequiredArgsConstructor
public class EsimOrderService {
    private final EsimOrderRepository orders;
    private final SubscriberRepository subscribers;
    private final PricingService pricing;
    private final ProfileClient profiles;                 // HTTP-клиент к SM-DP+

    @Transactional                                        // границей владеет сервис
    public OrderResponse create(CreateOrderRequest req) {
        Subscriber sub = subscribers.findByMsisdn(req.msisdn())
                .orElseThrow(() -> new NotFoundException("subscriber " + req.msisdn()));
        if (orders.existsBySubscriberAndStatus(sub, OrderStatus.PENDING)) {
            throw new ConflictException("pending order already exists");   // правило живёт здесь, а не в Subscriber
        }
        Money price = pricing.priceFor(sub.getTariff());
        EsimOrder order = orders.save(new EsimOrder(sub, price, OrderStatus.PENDING));
        profiles.reserve(order.getId());                  // удалённый вызов внутри транзакции: см. подводные камни
        return OrderResponse.from(order);
    }
}
```

Метод читается легко и тестируется с моками, и для сервиса такого размера это правильное количество структуры. Тревожные признаки — удалённый вызов внутри `@Transactional` и правило «один заказ в ожидании», о котором знает только этот метод.

## Подводные камни
- Удалённые вызовы (HTTP, отправка в Kafka) внутри метода `@Transactional` держат соединение с БД во время сетевой задержки ([[hikaricp-pool-sizing]]) и публикуют события, которые теряются при откате; перенеси их после commit или используй [[outbox-pattern]].
- Возврат JPA-сущностей из контроллеров связывает контракт API со схемой и приводит к сюрпризам ленивой загрузки ([[jpa-n-plus-one]]); маппь в DTO на слое представления.
- Самовызов (self-invocation) `@Transactional` внутри одного сервиса молча не работает, потому что прокси обходится стороной ([[spring-aop]]).
- Цепочки «сервис вызывает сервис, который вызывает сервис» без владельца сценария; если нельзя сказать, какой класс реализует «отмену заказа», выдели по сервису приложения на каждый сценарий.
- Связанные заметки: [[hexagonal-architecture]] и [[clean-architecture]] (что делать, когда ядро перерастает слои), [[modular-monolith]] (принудительное соблюдение границ), [[solid]], [[ddd-basics]].
