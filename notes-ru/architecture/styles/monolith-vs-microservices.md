## Кратко
Монолит — это одна единица развёртывания с локальными вызовами и одной транзакцией; микросервисы — это много единиц развёртывания с сетевыми вызовами и без общей транзакции. Микросервисы дают независимые deploy, масштабирование и владение командами ценой согласованности распределённых данных, эксплуатационных затрат и задержек. Делить стоит, когда этого требует организация — несколько команд, разный ритм релизов, неравномерное масштабирование, — а не потому, что архитектура в моде. Неудачное разделение даёт **распределённый монолит** (distributed monolith); безопасно делить помогает **strangler fig** («фикус-душитель»): по одной возможности за раз перенаправлять в новый сервис за шлюзом, пока старая система не опустеет.

## Основное
### Компромиссы
| Аспект | Монолит (включая [[modular-monolith]]) | Микросервисы |
|---|---|---|
| Deploy | Один артефакт, один пайплайн; любое изменение выкатывает всё | Каждый сервис выкатывается сам по себе; много пайплайнов, версионированные контракты |
| Масштабирование | Весь процесс масштабируется целиком; горячий путь тянет за собой остальное | Масштабируется только горячий сервис (Kafka-консьюмеры, воркеры провижининга) |
| Владение командами | Общая кодовая база; порядок держится на соглашениях и ревью | Сервис на команду; ясное владение, сложнее изменения между командами |
| Согласованность данных | ACID в одной базе данных ([[transactions-acid-and-isolation]]) | База данных на сервис; согласованность в конечном счёте (eventual consistency), [[saga]], [[outbox-pattern]], [[idempotency]] |
| Эксплуатационные затраты | Один лог, одну JVM настраивать, одну БД бэкапить | Оркестрация ([[kubernetes-basics]]), [[distributed-tracing]], [[logging-stacks]], алерты на каждый сервис, секреты, сетевые политики |
| Задержка | Вызовы методов внутри процесса, микросекунды | Сетевые переходы, сериализация, retry; хвостовые задержки (tail latency) складываются по цепочке вызовов |
| Режимы отказа | Падение процесса роняет всё | Частичные отказы, таймауты, каскадная перегрузка ([[circuit-breaker]]) |
| Тестирование | Быстрые модульные тесты, один набор интеграционных | Контрактные тесты, [[testcontainers]] на каждый сервис, медленные end-to-end-окружения |

### Когда делить
- **Размер команды**: одной команде из 5–8 человек это редко помогает; при трёх и более командах в одном репозитории конфликты слияния и координация релизов стоят дороже сетевых вызовов.
- **Независимое масштабирование**: воркеру опроса SM-DP+ нужно 20 экземпляров, а админскому API — 2, и они конкурируют за один пул соединений ([[hikaricp-pool-sizing]]).
- **Разный ритм релизов**: модуль биллинга, который меняется раз в квартал и проходит аудит, рядом с модулем уведомлений, который выкатывается ежедневно.
- **Изоляция отказов или другая среда выполнения**: сторонняя интеграция, которая не должна ронять ядро, ресурсоёмкая по CPU задача, другой язык.
- Микросервисы не делают плохой код хорошим; выделяй модуль только после того, как его граница уже существует в монолите.

### Антипаттерн «распределённый монолит»
- Сервисы, которые нужно разворачивать вместе, которые делят базу данных, синхронно вызывают друг друга длинными цепочками и используют общую библиотеку `common`, любое изменение которой вынуждает глобальный релиз.
- Симптомы: изменение одной фичи затрагивает три репозитория; авария во второстепенном сервисе блокирует вход в систему; интеграционным тестам нужна вся система целиком.
- Причины: деление по техническим слоям вместо бизнес-возможностей ([[ddd-basics|ограниченные контексты]]), общие таблицы, отношение к REST-вызовам как к вызовам методов.
- Лечение: слить обратно в модульный монолит или перерисовать границы вокруг возможностей, с владением данными и асинхронными событиями.

### Миграция по схеме strangler fig
- Поставь шлюз перед монолитом ([[api-gateway-and-service-discovery]]), чтобы весь трафик входил через один фасад.
- Выбери одну возможность с ясной границей и малым числом зависимостей (уведомления, рефералка, отчёты). Сделай её сервисом, перенеси её данные, переключи маршрут в шлюзе только для этого пути, оставь способ направить трафик обратно.
- Запись во время миграции: пусть новый сервис владеет данными, а монолит его вызывает, или наполняй новое хранилище из outbox монолита или из потока захвата изменений (change data capture); избегай голой двойной записи (dual writes).
- Повторяй возможность за возможностью; каждый шаг обратим, и бизнес продолжает выпускать изменения. Настрой [[distributed-tracing]] через шлюз, монолит и новый сервис до первого переключения маршрута.

## Пример
Чек-лист для решения, затем маршрут шлюза, который отправляет один путь в новый сервис.

| Вопрос | Говорит в пользу разделения, если |
|---|---|
| Сколько команд меняют этот код? | Больше двух, с отдельными бэклогами |
| Нужно ли одной части в 5 раз больше экземпляров, чем остальным? | Да, и она истощает общий пул |
| Выпускаются ли части в разном ритме или по разным правилам аудита? | Да |
| Есть ли ясный ограниченный контекст со своими данными? | Да, и нет join между модулями |
| Может ли вызов быть асинхронным или терпеть согласованность в конечном счёте? | Да |
| Уже есть трассировка, централизованное логирование и шлюз? | Да; иначе сначала построй их |
| Боль реальна уже сегодня? | Измеряется в конфликтах слияния, задержках релизов или инцидентах |

```yaml
# Spring Cloud Gateway (Spring Boot 3.x): /api/referrals/** уходит в новый сервис,
# всё остальное по-прежнему попадает в монолит.
spring:
  cloud:
    gateway:
      routes:
        - id: referral-service
          uri: lb://referral-service          # разрешается через service discovery
          predicates:
            - Path=/api/referrals/**
        - id: monolith
          uri: http://esim-monolith:8080
          predicates:
            - Path=/**
```

Маршруты проверяются по порядку, поэтому конкретный маршрут стоит первым; откат — это удаление одного маршрута.

## Подводные камни
- Деление до того, как граница ясна: новый сервис «временно» читает базу данных монолита, и эта связанность живёт годами.
- Синхронные цепочки (шлюз → A → B → C) перемножают задержку и вероятность отказа: четыре сервиса по 99,9% подряд дают примерно 99,6%. Где поток позволяет, предпочитай события.
- Двойная запись без outbox или сверки создаёт расхождение данных между старым и новым хранилищем, которое никто не замечает, пока не пожалуется клиент ([[outbox-pattern]]).
- Общие библиотеки, переносящие доменные модели между сервисами, воссоздают связанность монолита, да ещё и с сетью; делитесь контрактами ([[openapi-swagger]], схемы), а не сущностями.
- Связанные заметки: [[modular-monolith]] (обычно правильный первый ответ), [[saga]], [[api-gateway-and-service-discovery]], [[distributed-tracing]], [[kubernetes-basics]], [[system-design-basics]].
