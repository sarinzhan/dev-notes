## Кратко
SOLID — пять правил объектно-ориентированного проектирования, которые делают код удобным для изменений: одна причина для изменения на единицу (**S**), расширение без правки (**O**), подтипы обязаны соблюдать контракт базового типа (**L**), маленькие интерфейсы под конкретного клиента (**I**) и зависимость от абстракций, а не от реализаций (**D**). Это *принципы* (цели и правила), а не паттерны; паттерны вроде [[structural-patterns|Декоратора]] или [[behavioral-patterns|Стратегии]] — конкретные способы их выполнить.

## Какую проблему решает
- **Принцип единственной ответственности (SRP):** без него `UserService`, который валидирует, сохраняет и отправляет письма, меняется по трём причинам, и каждое изменение рискует сломать остальные две; с ним каждый класс меняется по запросу одного актора.
- **Принцип открытости/закрытости (OCP):** без него новый платёжный провайдер означает правку работающего кода checkout; с ним новый провайдер — это просто новый класс `PaymentProvider`.
- **Принцип подстановки Лисков (LSP):** без него вызывающий код обрастает проверками `instanceof`, потому что подтип нарушает контракт; с ним любой подтип безопасно подставить туда, где ожидается базовый тип.
- **Принцип разделения интерфейсов (ISP):** без него простая реализация бросает `UnsupportedOperationException` для методов, которые не может поддержать; с ним клиенты зависят только от того, что используют.
- **Принцип инверсии зависимостей (DIP):** без него бизнес-код создаёт JPA-репозиторий через `new` и не тестируется без базы данных; с ним тестовые двойники делаются тривиально.
- **Когда не нужно:** небольшие скрипты и код с одной реализацией и без тестового двойника; лишние интерфейсы и разбиения там — спекулятивная обобщённость (speculative generality).

## Основное
### Принцип единственной ответственности (SRP)
- У каждой единицы (класса, модуля, сервиса) ровно одна область ответственности и потому одна причина для изменения.
- `UserService`, который валидирует ввод, пишет в базу данных и отправляет письма, меняется по трём причинам. Его нужно разделить на валидатор, репозиторий и уведомитель.
- На уровне сервисов та же идея даёт ограниченные контексты ([[ddd-basics]]).

### Принцип открытости/закрытости (OCP)
- Код должен быть открыт для расширения, но закрыт для изменения: поведение добавляется новым классом, а не правкой работающего.
- Обычный инструмент — интерфейс плюс полиморфизм: новый платёжный провайдер = новая реализация `PaymentProvider`, код оформления заказа не меняется.
- В Spring именно на этом работают списки `@Bean`, внедрение `List<Handler>` и автоконфигурация ([[spring-ioc-and-di]]).

### Принцип подстановки Лисков (LSP)
- Везде, где используется базовый тип, должен подходить любой подтип так, чтобы программа этого не заметила. Подклассы должны сохранять контракт родителя: не усиливать предусловия, не ослаблять постусловия, не бросать новых исключений, которых родитель не обещал, не нарушать инварианты.
- Классические нарушения: `Square extends Rectangle`, где `setWidth` молча меняет высоту; `ReadOnlyList`, бросающий исключение из `add()`; подкласс репозитория, возвращающий `null` там, где родитель обещает пустой список.
- Проверка: прогнать набор тестов родителя на наследнике.

### Принцип разделения интерфейсов (ISP)
- Клиенты не должны зависеть от методов, которые они не используют. Несколько узких интерфейсов лучше одного широкого.
- `Printer` с `print`, `scan`, `fax` вынуждает простой принтер бросать `UnsupportedOperationException`; его нужно разделить на `Printer`, `Scanner`, `Fax`.
- В JDK семейство `Collection` в основном следует этому (`Iterable` -> `Collection` -> `List`); `java.sql.ResultSet` с ~190 методами — нет ([[collections-framework]]).

### Принцип инверсии зависимостей (DIP)
- Модули верхнего уровня не должны зависеть от модулей нижнего уровня; оба зависят от абстракций. Абстракции не должны зависеть от деталей; детали зависят от абстракций.
- На практике: бизнес-код зависит от интерфейса `OrderRepository`, и JPA-реализация тоже зависит от этого интерфейса. Это делает тестовых двойников тривиальными и позволяет TDD ([[testing-types-and-dev-cycles]]).
- **Внедрение зависимостей** (dependency injection) — техника, реализующая DIP: зависимости передаются снаружи (конструктор, контейнер), а не создаются через `new` внутри объекта. Контейнер Spring — реализация DI ([[spring-ioc-and-di]], [[spring-bean-lifecycle]]).
- DIP — это принцип, IoC — общая идея передачи управления фреймворку, DI — механизм. На собеседовании не стоит использовать их как синонимы.

## Пример
```java
// DIP + OCP: сценарий зависит от абстракции; провайдеры добавляются без его правки.
public interface PaymentProvider {
    boolean supports(Currency currency);
    PaymentResult charge(Money amount, CardToken token);
}

@Service
public class CheckoutService {
    private final List<PaymentProvider> providers;   // Spring внедряет все реализации

    public CheckoutService(List<PaymentProvider> providers) {
        this.providers = providers;
    }

    public PaymentResult pay(Order order, CardToken token) {
        return providers.stream()
                .filter(p -> p.supports(order.currency()))
                .findFirst()
                .orElseThrow(() -> new UnsupportedCurrencyException(order.currency()))
                .charge(order.total(), token);
    }
}

@Component
class KgsProvider implements PaymentProvider { /* ... */ }   // новая валюта = новый класс, ноль правок выше
```

## Подводные камни
- SRP, доведённый до крайности, порождает сотни классов с одним методом; «одна причина для изменения» — про *актора*, который запрашивает изменение, а не про число строк.
- OCP не значит «никогда не менять»; он значит, что изменения не должны расходиться волной. Интерфейс для класса ровно с одной реализацией и без тестового двойника — спекулятивная обобщённость (YAGNI).
- Нарушения LSP прячутся за кодом, который компилятор принимает; проверки `instanceof` в вызывающем коде — обычный признак того, что подтип нарушил контракт.
- Толстые интерфейсы молча растут в репозиториях Spring Data, когда каждый запрос попадает в один интерфейс; их нужно делить по сценариям ([[spring-data-repositories]]).
