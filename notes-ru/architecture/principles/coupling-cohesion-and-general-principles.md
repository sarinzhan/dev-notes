## Кратко
Почти любое правило проектирования сводится к двум измеримым идеям: **связность** (cohesion: насколько сильно части одной единицы относятся друг к другу) и **связанность** (coupling: сколько одна единица должна знать о другой, чтобы работать). Хороший дизайн — высокая связность внутри единицы и низкая связанность между единицами. KISS, DRY, YAGNI, разделение ответственности и правило зависимостей — разные взгляды на одну цель: сделать следующее изменение дешёвым и локальным. [[solid]] — версия тех же идей на уровне объектов.

## Основное

### Связность
- Единица (класс, пакет, модуль, сервис) связна, когда её элементы меняются по одной причине и служат одной цели. `SimActivationService` с `activate`, `deactivate`, `suspend` связен; `UtilService` с форматированием дат, отправкой SMS и экспортом в PDF — нет.
- Низкая связность проявляется так: класс, который нужно прочитать целиком, чтобы поменять один метод; тестовые классы с несвязанными фикстурами; модули, чьё имя — существительное во множественном числе (`helpers`, `common`).
- На уровне сервисов связность — это то, что даёт [[bounded-contexts-and-context-mapping|ограниченный контекст]]: одна команда, один язык, одна причина для deploy.

### Связанность
| Вид (от слабого к сильному) | Пример | Цена изменения |
|---|---|---|
| Связанность по сообщениям / событиям | Сервис публикует `ProfileActivated`, consumer-ы не знают, кто его опубликовал | Новому consumer-у ничего не нужно от producer-а |
| Связанность по данным | Метод принимает три нужных ему значения | Локальная |
| Связанность по структуре (stamp coupling) | Метод принимает весь `Order`, но использует только `order.id()` | Изменение `Order` вызывает перекомпиляцию повсюду |
| Связанность по управлению (control coupling) | Флаг `boolean sendEmail` меняет поведение внутри вызываемого | Вызывающий должен знать внутренности вызываемого |
| Связанность по общим данным (common coupling) | Общая изменяемая глобальная переменная, общая таблица базы между сервисами | Любое изменение ломает неизвестных пользователей |
| Связанность по содержимому (content coupling) | Доступ к приватному состоянию другого класса, рефлексия по полям | Всё |
- **Временная связанность** (temporal coupling): A должно выполняться раньше B, но в типах это никак не выражено (`init()`, затем `process()`). Лечится конструкторами, builder-ами или машиной состояний ([[constructors-and-initialization]]).
- **Связанность по развёртыванию** (deployment coupling): два сервиса должны выпускаться вместе. Классический провал микросервисов: распределённый монолит ([[monolith-vs-microservices]]).
- Афферентная и эфферентная связанность: сколько модулей зависит от тебя (афферентная, Ca) и от скольких зависишь ты (эфферентная, Ce). Нестабильность `I = Ce / (Ca + Ce)`; стабильные модули (низкий I) должны быть абстрактными, нестабильные — конкретными. ArchUnit и `jdeps` измеряют обе.

### Общие принципы
- **KISS** (keep it simple): простейший дизайн, отвечающий сегодняшним требованиям; сложность должна оплачиваться конкретной потребностью. `switch` лучше plugin-фреймворка с одним плагином.
- **DRY** (don't repeat yourself): одно авторитетное представление каждого элемента *знания*, а не каждой строки кода. Два сервиса, которые случайно одинаково валидируют MSISDN, — не дублирование; две копии налогового правила — дублирование. Преждевременный DRY создаёт связанность: общая `common-lib`, от которой зависит каждый сервис, часто хуже небольшого повторения.
- **YAGNI** (you aren't gonna need it): не строить под требование, которого ещё нет. Угаданная абстракция обычно оказывается неправильной, и её всё равно приходится сопровождать.
- **Разделение ответственности** (separation of concerns): каждая часть занимается одной заботой (маппинг HTTP, бизнес-правило, хранение). Слои ([[layered-architecture]]), порты и адаптеры ([[hexagonal-architecture]]) и AOP ([[spring-aop]]) — инструменты для этого.
- **Правило зависимостей** (dependency rule): зависимости в исходном коде направлены внутрь, к домену; домен ничего не знает о фреймворках, базах данных и транспортах. Это правило стоит за [[clean-architecture]] и буквой «D» в [[solid]].
- **Принцип наименьшего удивления** (principle of least astonishment): метод `get` ничего не меняет, `save` не отправляет письмо.
- **Закон Деметры** (Law of Demeter, «разговаривай только с друзьями»): `order.customer().address().city()` связывает тебя с тремя классами; `order.shippingCity()` — с одним.
- **Композиция вместо наследования**: наследование — сильнейшая форма связанности; лучше делегирование ([[class-relationships]], [[structural-patterns]]).

### Как это всплывает на собеседованиях
- «Что не так с этим `UserService`?» — низкая связность (три ответственности), связанность по общим данным (статическая конфигурация), связанность по управлению (булевы флаги).
- «Почему не одна общая библиотека сущностей для всех микросервисов?» — связанность по развёртыванию и по данным; каждое изменение схемы расходится волной по каждому сервису.
- «Когда дублирование допустимо?» — когда две копии будут меняться по разным причинам; критерий — причины изменения, а не похожесть текста.

## Пример
Уменьшение связанности по структуре и по управлению в вызове уведомления. До: вызывающий передаёт весь агрегат и флаг; после: маленькое связное значение и полиморфизм.

```java
// До: связанность по структуре (весь Subscriber) + связанность по управлению (boolean выбирает канал)
void notify(Subscriber subscriber, boolean useSms) {
    if (useSms) smsGateway.send(subscriber.getMsisdn(), subscriber.getLocale(), "activated");
    else emailGateway.send(subscriber.getEmail(), subscriber.getLocale(), "activated");
}

// После: связанность по данным + канал решает сам; добавление Push добавляет класс, а не ветку
public record Notification(String recipient, Locale locale, String template) {}

public interface NotificationChannel {
    boolean accepts(Subscriber s);
    void send(Notification n);
}

@Service
@RequiredArgsConstructor
public class Notifier {
    private final List<NotificationChannel> channels;

    public void profileActivated(Subscriber s) {
        var n = new Notification(s.preferredContact(), s.locale(), "profile-activated");
        channels.stream().filter(c -> c.accepts(s)).findFirst()
                .orElseThrow(() -> new NoChannelException(s.id()))
                .send(n);
    }
}
```

## Подводные камни
- «Низкая связанность», понятая как «интерфейс для всего»: интерфейс с одной реализацией и без тестового двойника добавляет косвенность, не уменьшая связанности с поведением.
- DRY, применённый между ограниченными контекстами, порождает общее ядро, которое никто не может изменить; см. [[bounded-contexts-and-context-mapping]].
- Связность по техническому типу (пакеты `controllers/`, `services/`, `repositories/`) скрывает низкую функциональную связность; лучше пакеты по фичам ([[modular-monolith]]).
- YAGNI — не оправдание, чтобы пропустить то, что дорого добавить потом: наблюдаемость, ключи идемпотентности, поля `version` в схемах ([[idempotency]], [[message-schema-evolution]]).
- Связанные заметки: [[solid]], [[ddd-basics]], [[oop-principles]]; [[monolith-vs-microservices]] применяет тот же словарь связанности к границам сервисов.
