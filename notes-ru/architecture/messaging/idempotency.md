## Кратко
Операция идемпотентна, если двукратное применение даёт тот же эффект, что и однократное. Любой канал с доставкой at-least-once ([[spring-kafka-consumer|Kafka]], retry HTTP, [[outbox-pattern]]) рано или поздно доставляет дубликаты, поэтому принимающая сторона должна быть либо естественно идемпотентной, либо дедуплицировать по ключу. Запись о дедупликации и бизнес-эффект должны коммититься в **одной транзакции**.

## Какую проблему решает
- **Без этого:** Kafka, retry HTTP и relay из outbox доставляют at-least-once. После rebalance или падения до commit offset-а событие `ActivationRequested` приходит повторно; клиент получает таймаут и заново шлёт `POST /payments`. Обработчик, который при каждом вызове делает `balance = balance - 100` или списывает с карты, спишет деньги с абонента дважды или отправит второе SMS.
- **Что меняет:** принимающая сторона либо делает операцию естественно повторяемой (абсолютное состояние вместо дельт), либо записывает ключ идемпотентности в той же транзакции, что и эффект, поэтому дубликат распознаётся и подтверждается без повторного выполнения эффекта.
- **Когда не нужно:** операция уже идемпотентна (`PUT` с полным состоянием, `UPDATE ... SET status = 'ACTIVE'`) или канал доставляет at-most-once и потеря сообщения допустима.

## Основное

### Естественная идемпотентность и дедупликация
- Естественная: `UPDATE sim SET status = 'ACTIVE' WHERE iccid = ?`, `INSERT ... ON CONFLICT DO NOTHING`, «установить баланс в X». Повтор безвреден, учёт не нужен.
- Не естественная: `balance = balance - 100`, «отправить SMS», «списать с карты», «добавить строку». Нужны ключ и хранилище для дедупликации.
- Лучше переписать операцию в естественно идемпотентную (абсолютное состояние вместо дельт), прежде чем добавлять таблицу дедупликации.

### Ключи идемпотентности
- Уникальный id, сгенерированный **отправителем запроса**: `id` события из строки outbox, заголовок `Idempotency-Key` от клиента, референс транзакции в платежах.
- Ключ хранится вместе с результатом. Повтор с тем же ключом возвращает сохранённый результат вместо повторного выполнения; повтор с тем же ключом, но другим payload — ошибка клиента (вернуть 422).
- Ключам нужен TTL (24 ч — соглашение Stripe) или задача очистки; Redis `SET key value NX EX 86400` подходит, если потеря ключа при перезапуске Redis допустима ([[redis-data-structures]]), Postgres — если нет.

### Идемпотентный Kafka consumer
- Таблица `processed_events(event_id uuid primary key, processed_at timestamptz)`.
- В одной транзакции: вставить ключ, выполнить бизнес-запись, commit. Если вставка падает с нарушением уникальности, событие уже обработано: подтвердить (ack) и пропустить.
- Почему не проверить сначала, а потом обработать? Два consumer-а (после rebalance) читают одну и ту же запись, оба видят «не обработано», оба выполняют. Ограничение уникальности — единственная проверка без гонки.
- Почему одна транзакция? Если ключ закоммитился, а бизнес-запись упала, событие потеряно навсегда; если бизнес-запись закоммитилась, а ключ нет, следующая доставка применит её дважды.

### Exactly-once в Kafka и почему consumer-у всё равно это нужно
- Идемпотентный producer (`enable.idempotence=true`, по умолчанию с Kafka 3.0): брокер дедуплицирует retry producer-а по producer id + порядковому номеру. Покрывает только «отправку повторили», а не «приложение вызвало send дважды».
- Транзакции (`transactional.id`, `isolation.level=read_committed`): атомарный consume-transform-produce **внутри Kafka**. Они не покрывают запись в Postgres, HTTP-вызов или SMS. Как только побочный эффект выходит за пределы Kafka, снова получается at-least-once плюс дедупликация.
- Commit offset-а и commit в БД — разные системы; падение между ними приводит к повторной доставке ([[kafka-consumer]]).

### Идемпотентные HTTP API
- `GET`, `PUT`, `DELETE` идемпотентны по контракту HTTP; `POST` и `PATCH` — нет ([[rest-and-http]]).
- `PUT /sims/{iccid}/profile` с полным состоянием идемпотентен по замыслу; `POST /payments` нужен `Idempotency-Key`.
- Поток на сервере: найти ключ; если найден и завершён — вернуть сохранённые статус + тело; если найден и в процессе — вернуть 409; иначе вставить ключ, обработать, сохранить ответ.

### Retry и таймауты в платежах
- Таймаут — неоднозначный случай: списание могло произойти, а могло и нет. Никогда не повторять списание без того же ключа идемпотентности; без него сначала нужно запросить статус.
- Обработка карт использует ту же идею: STAN/RRN и поток reversal/advice существуют потому, что терминал не может знать, видел ли хост запрос ([[emv-card-processing]]).
- Сочетать: ограниченные retry с backoff, стабильный ключ между retry и задачу сверки (reconciliation) для того, что осталось неизвестным после исчерпания бюджета retry.

## Пример
```java
@Component
@RequiredArgsConstructor
public class ActivationListener {
    private final JdbcTemplate jdbc;
    private final SimService sim;

    @KafkaListener(topics = "esim.activation", groupId = "provisioning")
    @Transactional
    public void on(ActivationRequested evt, Acknowledgment ack) {
        int inserted = jdbc.update(
            "INSERT INTO processed_events(event_id) VALUES (?) ON CONFLICT DO NOTHING",
            evt.id());
        if (inserted == 0) {           // повторная доставка
            ack.acknowledge();
            return;
        }
        sim.activate(evt.iccid());     // та же транзакция, что и ключ
        ack.acknowledge();             // после commit offset сдвигается; падение до этого просто приведёт к повторной доставке
    }
}
```
`ON CONFLICT DO NOTHING` избавляет от управления потоком через исключения и не помечает транзакцию на откат, как это сделало бы перехваченное `DataIntegrityViolationException` в JPA ([[spring-transactional]]).

## Подводные камни
- Проверка «уже обработано?» и сама работа в разных транзакциях снова открывают гонку. Ключ нужно вставлять в той же транзакции.
- При READ COMMITTED параллельный дубликат блокируется на уникальном индексе, пока первый не закоммитится, а затем падает или возвращает 0 строк; см. [[postgres-isolation-levels]].
- Дедупликация в памяти (`Set` в consumer-е) теряется при перезапуске и не разделяется между экземплярами.
- Использование offset-а или партиции Kafka в качестве ключа: они меняются при перепартиционировании и при replay из бэкапа.
- Идемпотентность не значит «можно повторять вечно»; ядовитому сообщению всё равно нужен dead letter topic ([[spring-kafka-consumer]]).
- Связанные заметки: компенсации в [[saga]] тоже должны быть идемпотентными; о том, когда прекращать retry, см. [[circuit-breaker]].
