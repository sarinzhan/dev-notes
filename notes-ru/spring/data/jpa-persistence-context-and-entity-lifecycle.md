## Кратко
Контекст персистентности (persistence context; `Session` в Hibernate, `EntityManager` в JPA) — это хранящаяся в памяти карта управляемых сущностей с ключом по id, живущая в течение транзакции. Сущность бывает **transient** (новый объект), **managed/persistent** (отслеживается, проверяется на изменения, записывается при flush), **detached** (имеет id, но больше не отслеживается) или **removed** (запланирована на `DELETE`). SQL не отправляется в момент вызова `persist()`; он отправляется при **flush**, который происходит перед commit, перед JPQL-запросом, затрагивающим те же таблицы, или при вызове `flush()`.

## Основное

### Контекст персистентности
- В Spring один на транзакцию (`EntityManager` с областью транзакции); `EntityManager`, внедрённый через `@PersistenceContext`, — это потокобезопасный прокси, который указывает на контекст текущей транзакции.
- Гарантирует **идентичность**: в пределах одного контекста `findById(1)` дважды возвращает один и тот же Java-объект, и второй вызов не обращается к БД; это кэш первого уровня (см. [[hibernate-caching]]).
- Хранит снимок каждой управляемой сущности; при flush сравнивает (**проверка изменений, dirty checking**) и выдаёт `UPDATE` только для изменённых сущностей. Ты никогда не вызываешь `update()`: измени управляемую сущность внутри транзакции, и она сохранится.
- Сущности, загруженные JPQL- или нативным запросом с отображением на сущность, становятся управляемыми; DTO-проекции — нет.
- `DataSource` — сторона JDBC (настройки соединения, пул HikariCP, [[hikaricp-pool-sizing]]); `EntityManager` — сторона JPA, построенная поверх соединения, взятого из пула на время транзакции.

### Состояния сущности
| Состояние | Есть id | Отслеживается | Как туда попасть |
|---|---|---|---|
| Transient (новая) | нет | нет | `new Order()` |
| Managed (persistent) | да | да | `persist()`, `find()`, `getReference()`, любой запрос сущностей, `merge()` возвращает такую |
| Detached | да | нет | контекст закрыт/очищен, `detach(e)`, сущность возвращена из метода после окончания транзакции, десериализована из кэша |
| Removed | да | до flush | `remove(e)`; строка удаляется при flush |

- `persist(e)` делает transient-сущность управляемой; при генерации id через `SEQUENCE` он только берёт номер, а `INSERT` ждёт flush. При `IDENTITY` `INSERT` выполняется сразу.
- `merge(detached)` загружает (или берёт из кэша) управляемую копию, копирует в неё состояние и **возвращает управляемый экземпляр**; аргумент остаётся detached. `save()` в Spring Data — это `persist` или `merge` в зависимости от того, новая ли сущность (см. [[spring-data-repositories]]).
- `detach(e)` / `clear()` прекращают отслеживание; несброшенные изменения теряются. `refresh(e)` перезаписывает состояние в памяти данными из БД.
- Колбэки жизненного цикла: `@PrePersist`, `@PostPersist`, `@PreUpdate`, `@PostUpdate`, `@PreRemove`, `@PostRemove`, `@PostLoad` или `@EntityListeners(AuditingEntityListener.class)` для `@CreatedDate`/`@LastModifiedDate`.

### Flush
- Flush = отправить ожидающие `INSERT`/`UPDATE`/`DELETE` в JDBC-соединение; это не commit. Порядок фиксирован: вставки, обновления, изменения коллекций, удаления.
- `FlushModeType.AUTO` (по умолчанию): flush перед commit и перед любым JPQL/Criteria-запросом, таблицы которого пересекаются с ожидающими изменениями, так что твой собственный запрос видит твои же записи. `COMMIT`: только при commit; быстрее для пакетов с преобладанием чтения, но запросы могут не увидеть несброшенные изменения. Hibernate добавляет `ALWAYS` и `MANUAL`.
- Нативные запросы не всегда надёжно вызывают автоматический flush, потому что Hibernate не может разобрать, какие таблицы они затрагивают; сначала вызови `em.flush()` или объяви затрагиваемую сущность через `addSynchronizedEntityClass`.
- Hibernate группирует выражения в пакеты при `spring.jpa.properties.hibernate.jdbc.batch_size=50` и `order_inserts=true`, `order_updates=true`; в длинных циклах вызывай `flush()` + `clear()` после каждого пакета, чтобы контекст не держал тысячи снимков.

### Транзакции и JPA
- Сама транзакция (распространение, правила отката, прокси) описана в [[spring-transactional]]; здесь — только взаимодействие с JPA.
- `@Transactional(readOnly = true)`: Spring делает JDBC-соединение только для чтения, а Hibernate переключает сессию в `FlushMode.MANUAL` и не делает снимков, поэтому загрузка дешевле и случайный `UPDATE` не проскочит. Изменения, сделанные внутри, молча не сбрасываются.
- Откат помечает контекст недействительным; после `RollbackException` управляемые сущности становятся detached, и их нужно перечитать.
- **Open Session In View** (`spring.jpa.open-in-view`, в Boot по умолчанию `true`, с предупреждением при запуске): веб-запрос держит `EntityManager` открытым на протяжении контроллера и отрисовки представления, поэтому ленивые коллекции работают в контроллерах и при сериализации Jackson. Цена: соединение с БД удерживается весь запрос (включая внешние HTTP-вызовы), а N+1 скрывается, вместо того чтобы проявиться. Выставь `false` и загружай нужное внутри сервиса через `join fetch`/`@EntityGraph` (см. [[jpa-n-plus-one]]).
- Логическая и физическая транзакция: один метод сервиса с `@Transactional` (логическая) обычно соответствует одной транзакции БД (физической), но `REQUIRES_NEW` открывает вторую физическую; см. [[transactions-acid-and-isolation]].

## Пример
```java
@Service
@RequiredArgsConstructor
public class OrderService {
    private final OrderRepository orders;
    private final EntityManager em;

    @Transactional
    public void importOrders(List<ImportRow> rows) {
        for (int i = 0; i < rows.size(); i++) {
            orders.save(Order.from(rows.get(i)));   // transient -> managed, INSERT отложен
            if (i % 50 == 0) {                        // совпадает с hibernate.jdbc.batch_size
                em.flush();                           // отправляем пакет
                em.clear();                           // сбрасываем снимки, освобождаем память
            }
        }
    }

    @Transactional
    public void rename(Long id, String name) {
        Order order = orders.findById(id).orElseThrow(); // managed
        order.setName(name);                             // save() не нужен: dirty checking
    }                                                    // flush + commit при выходе
}
```

## Подводные камни
- `LazyInitializationException`: обращение к ленивому полю detached-сущности (после транзакции, в контроллере при `open-in-view=false`, в асинхронном потоке). Загружай нужное внутри транзакции или отображай в DTO.
- Вызов `repository.save(entity)` для уже управляемой сущности безвреден, но бесполезен; вызов для detached-сущности с последующим изменением *аргумента* теряет изменения, потому что `merge` вернул другой объект.
- Массовое обновление через `@Modifying` не обновляет управляемые сущности; очисти контекст или перечитай их.
- Длинные циклы `importOrders` без `flush()/clear()` раздувают контекст и замедляют проверку изменений до O(n) на каждый flush.
- Слои кэширования над контекстом: [[hibernate-caching]], [[spring-cache-abstraction]]. Пессимистические и оптимистические блокировки ставятся только на управляемые сущности: [[jpa-locking]].
