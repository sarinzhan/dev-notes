## Кратко
**Инверсия управления (Inversion of Control, IoC)** означает, что объекты создаёт и связывает между собой фреймворк, а не твой код. **Внедрение зависимостей (dependency injection, DI)** — конкретный механизм: класс объявляет, что ему нужно (параметры конструктора, сеттеры или поля), а контейнер подставляет реализацию при создании бина. Контейнер — это `BeanFactory`; на практике всегда используется его более богатый подтип `ApplicationContext`.

## Основное
### Определения (ответы на собеседовании)
- **Фреймворк**: набор библиотек, которые решают типовые задачи (конфигурация, связывание, веб, доступ к данным) и задают структуру приложения; фреймворк вызывает твой код, а не наоборот.
- **IoC**: управление созданием объектов и ходом программы переходит от приложения к контейнеру. Spring управляет жизненным циклом объектов (бинов) и их зависимостями.
- **DI**: паттерн проектирования, который даёт слабую связанность (loose coupling) между взаимодействующими POJO. Вместо вызова `new` класс объявляет зависимость от интерфейса, а Spring внедряет реализацию. DI — один из способов реализовать IoC (другой классический — Service Locator).
- **Бин (bean)**: любой объект, жизненным циклом которого управляет контейнер.

### Зачем это нужно
- Меньше жёстких связей: классы зависят от абстракций, а не от конкретных классов.
- Проще тестировать: зависимость можно заменить моком или заглушкой (fake), не трогая класс.
- Проще конфигурировать: ты говоришь, что нужно, а контейнер создаёт и связывает.

### Три способа внедрения
| Способ | Как | Вывод |
|---|---|---|
| Через конструктор | `final`-поля задаются в конструкторе; единственному конструктору не нужен `@Autowired` (Spring 4.3+) | Предпочтительный: неизменяемость, зависимости обязательны и видны, работает без Spring в тестах |
| Через сеттер (метод) | `@Autowired` на сеттере | Для необязательных зависимостей или чтобы разорвать циклическую ссылку |
| Через поле | `@Autowired` на приватном поле | Самый короткий, но скрывает зависимости, требует рефлексии в тестах, позволяет циклическим ссылкам остаться незамеченными; избегать |

### BeanFactory и ApplicationContext
- `BeanFactory` — базовый контейнер: создание, поиск и настройка бинов; по умолчанию ленивый (бин создаётся при первом `getBean`).
- `ApplicationContext` расширяет его и добавляет: немедленное создание singleton'ов при запуске (поэтому ошибки конфигурации обнаруживаются сразу), `Environment` и разрешение свойств, `MessageSource` (i18n), события приложения (`ApplicationEventPublisher`), загрузку ресурсов и автоматическую регистрацию `BeanPostProcessor`'ов. Распространённые реализации: `AnnotationConfigApplicationContext`, `GenericWebApplicationContext`, а в Boot — `AnnotationConfigServletWebServerApplicationContext`.
- Контейнер хранит `BeanDefinition`'ы (класс, scope, аргументы конструктора, зависимости), построенные из XML, аннотаций или классов `@Configuration`, а затем создаёт по ним бины; шаги описаны в [[spring-bean-lifecycle]], стили конфигурации — в [[spring-bean-scopes-and-configuration]].

### Разрешение неоднозначной зависимости
Когда внедряемый интерфейс реализуют несколько бинов, Spring бросает `NoUniqueBeanDefinitionException`. Варианты: `@Primary` на кандидате по умолчанию, `@Qualifier("name")` в точке внедрения, имя параметра, совпадающее с именем бина, внедрение `List<T>`/`Map<String, T>` всех кандидатов (`@Order` управляет порядком в списке) или условные бины через `@Profile` ([[spring-boot-properties-and-profiles]]). Для необязательных зависимостей можно также внедрять `ObjectProvider<T>` или `Optional<T>`.

## Пример
```java
public interface SmsSender { void send(String msisdn, String text); }

@Component @Primary
class TwilioSmsSender implements SmsSender { /* ... */ }

@Component @Qualifier("local")
class LocalGatewaySmsSender implements SmsSender { /* ... */ }

@Service
public class OtpService {
    private final SmsSender sender;
    private final List<SmsSender> allSenders;   // оба, упорядочены по @Order

    OtpService(@Qualifier("local") SmsSender sender, List<SmsSender> allSenders) {
        this.sender = sender;
        this.allSenders = allSenders;
    }
}
```

## Подводные камни
- Циклическая зависимость между двумя бинами с внедрением через конструктор падает при запуске (`BeanCurrentlyInCreationException`); Boot 2.6+ к тому же по умолчанию запрещает циклические ссылки. Исправляй дизайн (выдели третий бин), а не переходи на внедрение через поле или `@Lazy`.
- Вызвать метод внедрённого бина из конструктора можно, но работа в стиле `@PostConstruct` не должна выполняться в конструкторе бина, от которого зависят другие, пока контекст не готов.
- Внедрение `prototype`-бина в `singleton` даёт один экземпляр навсегда; используй `ObjectProvider` или scoped proxy ([[spring-bean-scopes-and-configuration]]).
- Автосвязывание по типу работает через прокси: внедряй интерфейс, а не класс, когда бин проксируется [[spring-aop]] или [[spring-transactional]].
- Связанные заметки: [[spring-bean-lifecycle]], [[spring-boot-starters-and-autoconfiguration]], [[solid]] (принцип инверсии зависимостей).
