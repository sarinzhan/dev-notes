## Кратко
**REST** (Representational State Transfer) — архитектурный стиль для распределённых систем поверх HTTP: ресурсы идентифицируются URI, с ними работают стандартными методами, запросы не хранят состояния, ответы кэшируемы, интерфейс единообразен. API, которое соблюдает все ограничения, называется **RESTful**. Сам HTTP — текстовый (до HTTP/2) протокол прикладного уровня по схеме запрос/ответ: стартовая строка, заголовки, тело; методы с определённой безопасностью и идемпотентностью; коды статуса пяти классов. **CORS** — набор правил на стороне браузера для вызова API с другого источника (origin).

## Основное
### Определения
- **API** (Application Programming Interface): описание того, как одна программа общается с другой; для веб-сервиса это набор эндпоинтов, их входы и выходы.
- **REST**: набор ограничений (а не протокол или стандарт) для проектирования API, которые просты в использовании и хорошо масштабируются.
- **RESTful API**: API, удовлетворяющее всем ограничениям REST. Большинство «REST» API останавливаются до HATEOAS; на практике это нормально.

### Ограничения REST
- **Клиент-сервер**: клиент инициирует запрос, сервер его обрабатывает и возвращает представление **ресурса**. У ресурсов есть уникальный адрес (URI). Обе стороны развиваются независимо.
- **Отсутствие состояния (stateless)**: сервер не хранит сессию клиента между запросами; каждый запрос несёт всё необходимое (токен авторизации, параметры). Именно это делает горизонтальное масштабирование тривиальным.
- **Кэшируемость**: ответы сообщают, можно ли их кэшировать (`Cache-Control`, `ETag`, `Last-Modified`); промежуточные узлы (CDN, прокси) могут их отдавать.
- **Многоуровневая система**: клиент не может определить, общается ли он с исходным сервером или с прокси, балансировщиком нагрузки или шлюзом посередине.
- **Единообразный интерфейс (uniform interface)**: ресурсы идентифицируются URI; представления (JSON) отделены от ресурса; **самоописывающие сообщения** (тип контента, статус, заголовки говорят, как их обрабатывать); **HATEOAS**: ответы содержат ссылки на связанные ресурсы, чтобы клиент мог по ним переходить (реализовано в Spring HATEOAS; во внутренних API используется редко).

### HTTP
- Протокол прикладного уровня, изначально для HTML, теперь универсальный транспорт для веб-данных. Ресурсы адресуются по URL; клиент-сервер; в 1.x текстовый.
- Версии: 1.0, 1.1 (keep-alive; один запрос за раз на соединение), **2** (бинарный, мультиплексирование в одном соединении, сжатие заголовков), **3** (QUIC поверх UDP). Серверные настройки — в [[spring-boot-properties-and-profiles]].
- Структура сообщения: **стартовая строка** (запрос: метод, URL, версия; ответ: версия, статус, пояснение), **заголовки** (метаданные: `Content-Type`, `Authorization`, `Accept`, `Cache-Control`), пустая строка, **тело** (данные).
- Классы статусов: `1xx` информационные, `2xx` успех (200 OK, 201 Created, 202 Accepted, 204 No Content), `3xx` перенаправление (301/302/304 Not Modified), `4xx` ошибка клиента (400, 401 Unauthorized = не аутентифицирован, 403 Forbidden = аутентифицирован, но доступ запрещён, 404, 405, 409 Conflict, 415, 422, 429 Too Many Requests), `5xx` ошибка сервера (500, 502, 503, 504).

### Методы
| Метод | Действие | Безопасный | Идемпотентный | Тело |
|---|---|---|---|---|
| GET | чтение | да | да | нет |
| HEAD | только заголовки, метаданные ресурса | да | да | нет |
| OPTIONS | разрешённые методы, CORS preflight | да | да | редко |
| POST | создание / неидемпотентное действие | нет | нет | да |
| PUT | полная замена | нет | да | да |
| PATCH | частичное обновление | нет | нет (по спецификации; на практике обычно да) | да |
| DELETE | удаление | нет | да | допускается, но большинство серверов его игнорирует |
| TRACE | эхо запроса | да | да | нет |

- **Безопасный (safe)** = не меняет состояние сервера. **Идемпотентный (idempotent)** = повтор запроса даёт тот же эффект, что и однократное выполнение; именно это позволяет клиентам и прокси безопасно делать retry. POST повторяют только с ключом идемпотентности ([[idempotency]]).
- Эндпоинты аутентификации и авторизации (логин, обмен токенов, даже token endpoint OAuth 2.0 / OIDC) используют POST: учётные данные идут в теле, а не в URL, который попадёт в логи.

### Куда кладутся данные
- **Параметры пути** (`/orders/42`): идентифицируют ресурс; без них запрос не имеет смысла.
- **Параметры запроса (query)** (`?status=ACTIVE&page=2&sort=createdAt,desc`): фильтрация, сортировка, пагинация, необязательные переключатели.
- **Тело**: представление для создания или обновления (JSON); также для больших или чувствительных входных данных.
- Заголовки: сквозные метаданные (авторизация, согласование контента, идентификаторы трассировки, `Idempotency-Key`).

### CORS
- **Cross-Origin Resource Sharing** — механизм безопасности браузера, который определяет, может ли JavaScript, загруженный с одного *источника (origin)* (схема + хост + порт, например `https://my-frontend.com`), читать ответы с другого (`https://api-backend.com`).
- По умолчанию браузер блокирует такое чтение (политика одного источника, same-origin policy), чтобы ограничить атаки вроде CSRF и кражи данных через XSS. Сервер явно разрешает доступ через `Access-Control-Allow-Origin` / `-Methods` / `-Headers` / `-Credentials`; для непростых запросов браузер сначала отправляет **preflight**-запрос `OPTIONS`.
- Соблюдается только браузерами; curl, Postman и межсерверные вызовы его игнорируют. Это не аутентификация.
- Spring: `@CrossOrigin` на контроллере, глобальный `WebMvcConfigurer.addCorsMappings` или `http.cors()` с бином `CorsConfigurationSource`, когда подключён Spring Security ([[spring-security-basics]]).

## Пример
Ресурсно-ориентированное API для одной сущности:
```
GET    /api/v1/subscribers/{msisdn}/esims            200, list (query: ?status=ACTIVE&page=0&size=20)
POST   /api/v1/subscribers/{msisdn}/esims            201 + Location: /api/v1/esims/{iccid}
GET    /api/v1/esims/{iccid}                         200 | 404
PUT    /api/v1/esims/{iccid}                         200, full replace (idempotent)
PATCH  /api/v1/esims/{iccid}                         200, {"status":"SUSPENDED"}
DELETE /api/v1/esims/{iccid}                         204 | 404 (second call also 404; still idempotent in effect)
POST   /api/v1/esims/{iccid}/activations             202, action as a sub-resource, Idempotency-Key header
```
Тело ошибки (RFC 9457 Problem Details, то, что выдаёт `ProblemDetail` в Spring 6):
```json
{ "type": "https://api.beeline.kg/errors/esim-not-found", "title": "Not Found",
  "status": 404, "detail": "ICCID 8999600000000000001 not found", "instance": "/api/v1/esims/8999600000000000001" }
```

## Подводные камни
- Глаголы в URL (`/getOrder`, `/createUser`) и GET для изменения состояния (краулеры и предзагрузка будут его вызывать).
- Возврат 200 с `{"error": ...}` внутри; клиенты и мониторинг опираются на коды статуса.
- Путаница между 401 и 403, а также раскрытие существования ресурса через разницу 403 и 404.
- Сессии в «stateless» API: sticky sessions ломают масштабирование; используй токены ([[jwt-authentication]]).
- Ломающие изменения без версионирования (`/v1/` или версионирование через media type); добавляющие изменения (новые необязательные поля) безопасны, удаления и переименования — нет.
- Связанные заметки: [[spring-mvc-request-lifecycle]] — как Spring всё это маппит, [[rest-clients]] — вызывающая сторона, [[openapi-swagger]] — документирование.
