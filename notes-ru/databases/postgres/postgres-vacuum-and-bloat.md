## Кратко
Postgres никогда не обновляет строку на месте: `UPDATE` записывает новую версию строки и помечает старую как истёкшую для последующих транзакций (MVCC). Истёкшие версии, **мёртвые кортежи (dead tuples)**, остаются на диске, пока **vacuum** не освободит их для повторного использования. Если vacuum не успевает, таблицы и индексы обрастают мусором (**раздувание, bloat**), сканирования замедляются, а в конце концов 32-битный счётчик идентификаторов транзакций приближается к **переполнению (wraparound)**, и тогда Postgres отказывается принимать запись. По умолчанию с этим справляется autovacuum; настройка его для каждой горячей таблицы и короткие транзакции — это большая часть эксплуатационной работы. Семантика изоляции, построенная на MVCC, — в [[postgres-isolation-levels]].

## Основное

### MVCC на диске
- Каждая версия строки несёт `xmin` (транзакция, которая её создала) и `xmax` (транзакция, которая её удалила или заменила). Снимок определяет видимость, сравнивая их с множеством закоммиченных транзакций; журнал коммитов (`commit log`, `pg_xact`) хранит исход каждого идентификатора транзакции.
- `DELETE` устанавливает `xmax`; `UPDATE` устанавливает `xmax` у старой версии и вставляет новую, возможно на другой странице. Индексы тоже указывают на новую версию, если только обновление не **HOT** (heap-only tuple): ни один индексированный столбец не изменился и на странице есть свободное место, поэтому индекс не трогается, а старая версия связывается в цепочку с новой на той же странице. `fillfactor = 90` на таблицах с частыми обновлениями оставляет место для HOT.
- Читатели никогда не блокируют писателей, потому что старая версия всё ещё на месте. Цена — кто-то должен убирать.

### Что делает VACUUM
| Операция | Что блокирует | Эффект |
|---|---|---|
| `VACUUM` (обычный, его запускает autovacuum) | ничего, кроме DDL | помечает мёртвые кортежи как место для повторного использования внутри страниц, подрезает HOT-цепочки, обновляет карту видимости и карту свободного места, удаляет мёртвые записи индексов, замораживает старые xid; не возвращает место ОС, кроме пустых страниц в конце |
| `VACUUM FULL` / `CLUSTER` | всю таблицу, `ACCESS EXCLUSIVE` | переписывает таблицу в новый файл, возвращает место; нужно вдвое больше диска; онлайн-аналог — `pg_repack` |
| `ANALYZE` | ничего | обновляет статистику планировщика ([[query-planning-and-execution]]) |
| `VACUUM (INDEX_CLEANUP, PARALLEL n)` | ничего | PG 13+ очищает индексы параллельно |

- Мёртвые кортежи можно удалить, только когда ни одна выполняющаяся транзакция больше не может их видеть: самый старый активный снимок (`backend_xmin` в `pg_stat_activity`), сессия idle-in-transaction, устаревший слот репликации или standby с `hot_standby_feedback` — всё это сдерживает vacuum во всём кластере. Долгий отчёт блокирует очистку горячей таблицы, которую он даже не трогает.

### Настройка autovacuum
- Запускается для таблицы, когда `dead tuples > autovacuum_vacuum_threshold (50) + autovacuum_vacuum_scale_factor (0.2) × rows`. Для таблицы на 100 миллионов строк это 20 миллионов мёртвых строк до первого запуска; на таких таблицах задавай `autovacuum_vacuum_scale_factor = 0.01` и `autovacuum_vacuum_cost_delay` в 2 мс (значение по умолчанию в PG 12). PG 13 добавил `autovacuum_vacuum_insert_threshold`, чтобы таблицы только со вставками тоже очищались (и у них устанавливалась карта видимости).
- По умолчанию `autovacuum_max_workers = 3`; на одну таблицу одновременно работает один воркер, поэтому несколько огромных таблиц могут оставить без внимания все остальные. На серверах с запасом по вводу-выводу увеличивай число воркеров и уменьшай cost delay.
- Следи за `pg_stat_user_tables`: `n_dead_tup`, `n_live_tup`, `last_autovacuum`, `autovacuum_count`. Таблица, у которой `n_dead_tup` продолжает расти между запусками, очищается недостаточно.
- Таблицы-очереди (outbox, таблицы заданий) с `DELETE` или обновлениями статуса каждой строки — классический источник раздувания: маленький живой набор, огромный мёртвый. Частичные индексы держат индексную сторону маленькой ([[postgres-indexes]]); пакетные удаления и агрессивные настройки autovacuum для таблицы держат маленьким heap; для удаления по сроку хранения партиционирование и `DROP` лучше `DELETE` ([[postgres-partitioning]]).

### Раздувание
- Раздувание = размер таблицы или индекса минус размер, который нужен её живым строкам. Симптомы: последовательные сканирования и index scan читают больше страниц, чем оправдывает число строк, `Buffers: shared read` растёт, доля попаданий в кэш падает.
- Измерение: расширение `pgstattuple` (`SELECT * FROM pgstattuple('outbox')` даёт `dead_tuple_percent` и `free_percent`) или запрос в стиле `pg_bloat_check` по `pg_class.relpages` против ожидаемого. Раздувание индексов: `pgstatindex`, `avg_leaf_density`.
- Исправление: `REINDEX INDEX CONCURRENTLY` (PG 12+) для индексов; `pg_repack` или `VACUUM FULL` в окно обслуживания для таблиц. Дедупликация B-tree (PG 13) и восходящее удаление из индексов (bottom-up index deletion, PG 14) заметно уменьшили раздувание индексов от не-HOT обновлений.

### Переполнение идентификаторов транзакций
- Идентификаторы транзакций 32-битные и сравниваются по кругу; версия строки старше примерно 2 миллиардов транзакций внезапно выглядела бы как принадлежащая будущему и исчезла бы. Vacuum **замораживает (freeze)** старые строки (помечает их как видимые всем), чтобы их xid больше не имел значения. `autovacuum_freeze_max_age` (200 миллионов) принудительно запускает на таблице **vacuum против переполнения (anti-wraparound vacuum)**, даже если autovacuum отключён.
- Следи за `age(datfrozenxid)` по каждой базе; на 1 миллиарде это срочно, на ~2 миллиардах Postgres перестаёт принимать запись, и vacuum придётся выполнять в однопользовательском режиме. Причины: autovacuum отключили, «потому что он был медленным», долго открытые подготовленные транзакции (`pg_prepared_xacts`), застрявший слот репликации.

## Пример
```sql
-- Кто прямо сейчас сдерживает vacuum
SELECT pid, state, now() - xact_start AS xact_age, backend_xmin, left(query, 60) AS query
FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL
ORDER BY age(backend_xmin) DESC
LIMIT 5;
--  pid  | state               | xact_age | backend_xmin | query
--  4182 | idle in transaction | 02:13:41 | 48811237     | SELECT * FROM outbox WHERE ...
-- JDBC-соединение в состоянии idle in transaction из-за забытого @Transactional вокруг HTTP-вызова.

-- Autovacuum на уровне таблицы для горячей таблицы-очереди
ALTER TABLE outbox SET (
    autovacuum_vacuum_scale_factor = 0.01,
    autovacuum_vacuum_threshold    = 1000,
    autovacuum_vacuum_cost_delay   = 1,
    fillfactor                     = 85
);

-- Расстояние до переполнения по каждой базе
SELECT datname, age(datfrozenxid) AS xid_age FROM pg_database ORDER BY 2 DESC;
```
Задай на сервере `idle_in_transaction_session_timeout = '5min'`, чтобы забытые транзакции не могли сдерживать vacuum часами ([[postgres-performance-checklist]]).

## Подводные камни
- Отключить autovacuum на «нагруженной» таблице, потому что vacuum появился в `top`: таблица раздувается, каждый запрос замедляется, а vacuum против переполнения всё равно приходит, только теперь с гораздо большим объёмом работы.
- `VACUUM FULL` в production на большой таблице берёт эксклюзивную блокировку на всё время перезаписи; приложение видит полную недоступность этой таблицы.
- `DELETE FROM events WHERE created_at < ...` на 50 миллионов строк: место не возвращается, таблица того же размера, только теперь в основном мёртвая; вместо этого партиционируй.
- Обновление индексированного столбца в каждой строке (`updated_at` проиндексирован и меняется при каждой записи) отключает HOT и удваивает усиление записи в индексы.
- Семантика изоляции поверх MVCC: [[postgres-isolation-levels]]; взаимодействие с репликацией (`hot_standby_feedback`, слоты): [[postgres-replication-and-failover]].
