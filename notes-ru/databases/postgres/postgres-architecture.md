## Кратко
Postgres **многопроцессный**, а не многопоточный: **postmaster** порождает по одному **backend-процессу** на каждое клиентское соединение плюс набор фоновых процессов (checkpointer, background writer, WAL writer, autovacuum, WAL senders, статистика). Они делят одну большую область памяти — **shared buffers** (страничный кэш базы), плюс буферы WAL и таблицы блокировок. Каждый UPDATE пишет **новую версию строки** вместо изменения старой (MVCC), и если обновление не **HOT**, каждый индекс таблицы получает новую запись. Это устройство объясняет лимиты соединений, нужду в пулере, раздувание и VACUUM.

## Основное
### Процессы
- **postmaster**: родитель. Слушает 5432, аутентифицирует, порождает backend на каждое соединение, перезапускает детей, если один упал (упавший backend заставляет все остальные сбросить разделяемую память).
- **Backend**: по одному на соединение, полноценный процесс ОС со своей памятью (`work_mem` для сортировок и хэшей, кэши каталога). Разбирает, планирует и выполняет запросы своего клиента ([[database-wire-protocols]]). Простаивающий backend всё равно стоит ~5–10 МБ и слот в `max_connections`.
- **Фоновые воркеры**: воркеры параллельных запросов (`max_parallel_workers_per_gather`), воркеры логической репликации, расширения (pg_cron).
- **Вспомогательные процессы**:
  - **checkpointer**: на каждой контрольной точке сбрасывает все грязные страницы и записывает точку начала redo ([[wal-redo-undo-and-durability]]);
  - **background writer**: понемногу отдаёт грязные страницы ОС между контрольными точками, чтобы backend-ам редко приходилось писать самим;
  - **WAL writer**: периодически сбрасывает буферы WAL на диск (для асинхронных коммитов);
  - **autovacuum launcher + воркеры**: VACUUM и ANALYZE для таблиц, перешедших пороги ([[postgres-vacuum-and-bloat]]);
  - **WAL sender / receiver**: стримят WAL на реплики ([[postgres-replication-and-failover]]);
  - **archiver**, **logger**, **stats** (статистика в разделяемой памяти с 15).
- Почему процессы: изоляция (падение одного backend не портит личную память другого), переносимость в 1996 году. Цена: создание процесса на соединение и большой расход памяти на соединение, поэтому 10 000 прямых соединений нереально; используй пул (HikariCP в приложении, PgBouncer перед базой) ([[hikaricp-pool-sizing]], [[process-management]]).

### Память
- **shared_buffers** (обычно ~25 % RAM): собственный страничный кэш базы, страницы по 8 КБ. Страницы есть ещё и в страничном кэше ОС, поэтому данные могут кэшироваться дважды; поэтому Postgres не забирает всю RAM.
- **Буферы WAL**: записи WAL до того, как они записаны.
- **work_mem** на каждый узел сортировки/хэша в каждом backend (запрос с 5 сортировками может занять 5× от него); **maintenance_work_mem** для VACUUM и CREATE INDEX.
- Таблица блокировок, proc array (кто выполняется и с каким снимком), CLOG/pg_xact (статус коммита каждого идентификатора транзакции).

### Жизнь UPDATE (MVCC на диске)
- У каждой версии строки (кортежа) есть `xmin` (транзакция, создавшая её) и `xmax` (транзакция, удалившая или заменившая её). Снимок решает, какие версии видны.
- `UPDATE t SET status = 'PAID' WHERE id = 7`:
  1. найти видимую версию через индекс;
  2. взять блокировку строки (записать в `xmax` идентификатор своей транзакции);
  3. записать **новый кортеж** с `xmin` = мы, в ту же страницу, если есть место, иначе в другую;
  4. `t_ctid` старого кортежа указывает на новый;
  5. вставить новую запись, указывающую на новый ctid, **в каждый индекс** таблицы;
  6. записать WAL для изменений heap и каждого индекса.
- Так UPDATE одной колонки в таблице с 8 индексами пишет в 9 структур. Это усиление записи, и именно на него жаловался Uber в 2016 году ([[primary-vs-secondary-indexes]]).

### HOT-обновления (heap-only tuples)
- Если **ни одна индексированная колонка не меняется** и новый кортеж **помещается в ту же страницу**, Postgres пропускает вставки в индексы: индексы продолжают указывать на старый кортеж, который внутри страницы перенаправляет на новый (HOT-цепочка). Позже очистка страницы (pruning) убирает мёртвые версии без VACUUM.
- Делай обновления HOT-дружелюбными: не индексируй часто меняющиеся колонки без нужды и оставляй место в страницах: `ALTER TABLE t SET (fillfactor = 80)`.
- Следи за долей: `n_tup_hot_upd / n_tup_upd` в `pg_stat_user_tables`.

### Postgres и MySQL одним предложением
- Postgres: heap + версии в heap + индексы на ctid + VACUUM. InnoDB: кластеризованный PK + обновление на месте + undo log + вторичные индексы на PK + потоки purge. Ни один не «лучше»; они переносят стоимость в разные места.

## Пример
```sql
-- processes you can see from SQL
SELECT pid, backend_type, state, query FROM pg_stat_activity ORDER BY backend_type;

-- MVCC in action
CREATE TABLE t (id int PRIMARY KEY, status text) WITH (fillfactor = 80);
INSERT INTO t VALUES (7, 'NEW');
SELECT ctid, xmin, xmax, * FROM t;            -- (0,1) xmin=1001
UPDATE t SET status = 'PAID' WHERE id = 7;
SELECT ctid, xmin, xmax, * FROM t;            -- (0,2): a new tuple

-- how many updates were HOT?
SELECT relname, n_tup_upd, n_tup_hot_upd FROM pg_stat_user_tables WHERE relname = 't';
```

## Подводные камни
- `max_connections = 2000` вместо пулера: взрыв памяти и конкуренция за proc array; держи максимум несколько сотен.
- Огромный `work_mem` глобально: много параллельных сортировок умножают его, и OOM killer забирает детей postmaster.
- Индекс по колонке, которая меняется при каждом обновлении (например, `updated_at`): убивает HOT, удваивает стоимость записи.
- Убить backend через `kill -9`: postmaster перезапускает все сессии; используй `pg_terminate_backend(pid)`.
