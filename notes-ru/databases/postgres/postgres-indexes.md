## Кратко
B-tree — выбор по умолчанию, и он верен в 90% случаев. GIN нужен для `jsonb` / массивов / полнотекстового поиска / триграмм, GiST — для геометрии и диапазонов, BRIN — для огромных таблиц только с дописыванием, а частичные индексы, индексы по выражению или покрывающие индексы стоит пробовать раньше, чем добавлять столбцы. Общая теория B-tree и селективности — в [[database-indexes]]; эта заметка о том, что предлагает именно Postgres и как проверить, что планировщик действительно это использует.

## Основное

### Методы доступа индексов
| Метод | Операторы | Когда применять |
|---|---|---|
| **B-tree** | `=`, `<`, `>`, `BETWEEN`, `IN`, `IS NULL`, `ORDER BY`, `LIKE 'abc%'` (с `text_pattern_ops` при collation, отличной от C) | по умолчанию; любой скалярный столбец |
| **Hash** | только `=` | длинные текстовые ключи, по которым никогда не ищут диапазоны; устойчив к сбоям с PG 10, редко стоит того по сравнению с B-tree |
| **GIN** | `@>`, `?`, `&&`, `@@`, `%` (pg_trgm) | `jsonb`, массивы, полнотекстовый `tsvector`, `LIKE '%x%'` через `pg_trgm`; большой, медленно обновляется, быстро ищет; список ожидания `fastupdate` |
| **GiST** | `&&`, `<@`, `<->`, `=` | диапазоны, геометрия/PostGIS, ограничения исключения (`EXCLUDE USING gist`), поиск ближайших соседей |
| **BRIN** | диапазоны по физически упорядоченным данным | таблицы только с дописыванием и `created_at`; несколько KB на миллиарды строк, бесполезен, если данные не коррелируют с физическим порядком |

### Варианты индексов
- **Составной** (многоколоночный) B-tree: используется начиная с **левого префикса**. `(status, created_at)` обслуживает `WHERE status = ?` и `WHERE status = ? AND created_at > ?`, но не `WHERE created_at > ?` сам по себе. Столбцы с равенством — первыми, столбец диапазона или `ORDER BY` — последним.
- **Частичный (partial)**: `WHERE published_at IS NULL` индексирует только горячие строки. Запрос должен содержать предикат, про который планировщик может доказать, что он влечёт предикат индекса. Идеален для таблиц-очередей ([[outbox-pattern]]).
- **По выражению (expression)**: `ON users (lower(email))` позволяет `WHERE lower(email) = ?` использовать индекс; запрос должен использовать идентичное выражение.
- **Покрывающий (covering)** (`INCLUDE (col)`, PG 11): неключевые столбцы хранятся в листовых страницах, чтобы запрос можно было обслужить **index-only scan**. Включённые столбцы не участвуют в уникальности, и по ним нельзя искать.

### Index-only scan и карта видимости
- Индекс не знает, видна ли версия строки твоей транзакции (MVCC). Планировщик использует **карту видимости (visibility map)**: по биту на страницу heap со значением «все кортежи видимы». Страницы с установленным битом пропускаются; остальные читаются (`Heap Fetches` в `EXPLAIN`).
- После интенсивных обновлений карта устаревает, и index-only scan деградирует до обычного index scan. Биты устанавливает `VACUUM` (autovacuum); большое значение `Heap Fetches` означает, что vacuum нужен чаще.

### Когда планировщик игнорирует индекс
- **Низкая селективность**: условие подходит под больше чем примерно 5–10% таблицы; последовательное сканирование дешевле случайных чтений heap. Решает статистика (`ANALYZE`), а не ты.
- **Функция над столбцом**: `WHERE date(created_at) = ?` или `lower(email)` без индекса по выражению.
- **Несовпадение типов**: `WHERE id = '42'` по `bigint` работает (приводится литерал), но `WHERE varchar_col = 42` приводит столбец и отключает индекс; то же для JDBC-параметра, отправленного с неправильным типом.
- **Ведущий шаблон**: `LIKE '%foo%'` не может пройти по B-tree; используй `pg_trgm` + GIN.
- **Маленькая таблица**: несколько страниц дешевле просканировать, чем обходить индекс; это корректное поведение.

### Чтение EXPLAIN ANALYZE
- `EXPLAIN (ANALYZE, BUFFERS)` выполняет запрос и выводит для каждого узла оценочное и фактическое число строк. Большой разрыв означает устаревшую статистику или ошибку оценки из-за коррелированных столбцов (`CREATE STATISTICS`).
- Типы узлов: `Seq Scan`, `Index Scan` (индекс, затем heap для каждой строки), `Index Only Scan`, `Bitmap Index Scan` + `Bitmap Heap Scan` (сначала собрать подходящие страницы, затем прочитать их по порядку; выбирается при средней селективности или `OR` по нескольким индексам).
- `Buffers: shared hit/read` показывает кэш против диска.

### Обслуживание и цена записи
- `CREATE INDEX` берёт блокировку `SHARE`: чтение продолжается, запись блокируется. `CREATE INDEX CONCURRENTLY` делает два сканирования таблицы без блокировки записи, не может выполняться внутри транзакции (Flyway: `-- flyway:executeInTransaction=false`) и при сбое оставляет индекс `INVALID`: удали и повтори.
- Каждый индекс добавляет работы каждому `INSERT`/`UPDATE`/`DELETE` и лишает HOT-обновлений, когда меняется индексированный столбец. Пять индексов на горячей таблице могут вдвое снизить пропускную способность записи.
- Раздувание (bloat): мёртвые кортежи индекса накапливаются; дедупликация B-tree (PG 13) и восходящее удаление (bottom-up deletion, PG 14) его уменьшают. Измеряй через `pgstattuple`/`pg_stat_user_indexes`, исправляй через `REINDEX INDEX CONCURRENTLY` (PG 12). Неиспользуемые удаляй (`pg_stat_user_indexes.idx_scan = 0`).

## Пример
```sql
-- таблица-очередь: крошечный частичный индекс только по горячим строкам
CREATE INDEX CONCURRENTLY outbox_pending_idx
  ON outbox (created_at)
  WHERE published_at IS NULL;

-- составной + покрывающий: поиск абонентов обслуживается index-only scan
CREATE INDEX CONCURRENTLY sim_msisdn_status_idx
  ON sim (msisdn, status) INCLUDE (iccid);

-- проверить план
EXPLAIN (ANALYZE, BUFFERS)
SELECT iccid FROM sim WHERE msisdn = '996555123456' AND status = 'ACTIVE';
--  Index Only Scan using sim_msisdn_status_idx on sim  (actual rows=1 loops=1)
--    Heap Fetches: 0
--    Buffers: shared hit=4
```

## Подводные камни
- `CREATE INDEX` без `CONCURRENTLY` в миграции блокирует запись в production-таблицу на всё время построения.
- `LIKE '%foo%'` не может использовать B-tree; используй `pg_trgm` + GIN (`gin_trgm_ops`).
- Частичный индекс с `WHERE status = 'PENDING'` игнорируется, когда запрос использует параметр привязки, про который планировщик не может доказать во время планирования, что он равен `'PENDING'` (generic-планы после 5 выполнений при `plan_cache_mode = auto`).
- Изоляция при [[postgres-isolation-levels]] взаимодействует с index scan только через видимость, а не через блокировки.
- Связанные заметки: [[database-indexes]] — теория, [[jpa-n-plus-one]] — почему запросы ORM часто не попадают в составные индексы.
