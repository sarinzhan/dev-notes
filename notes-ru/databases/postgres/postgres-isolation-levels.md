## Кратко
Postgres использует MVCC, поэтому читатели никогда не блокируют писателей. Уровень по умолчанию — **READ COMMITTED**: каждый оператор видит свежий снимок. **REPEATABLE READ** берёт один снимок на всю транзакцию (snapshot isolation), что в Postgres заодно предотвращает фантомы, и прерывает транзакцию, которая пытается обновить строку, изменённую кем-то после снимка. **SERIALIZABLE** добавляет сериализуемую изоляцию снимков (SSI): отслеживает зависимости чтения/записи и прерывает с `40001`, когда результат не мог получиться ни при каком последовательном порядке, — это ловит асимметрию записи (write skew). Каждое прерывание приложение должно повторить.

## Основное
| Уровень | Снимок | Неповторяемое чтение | Фантом | Потерянное обновление | Write skew | Типичное применение |
|---|---|---|---|---|---|---|
| READ COMMITTED | на оператор | возможно | возможен | возможно (прочитать, потом записать) | возможна | OLTP по умолчанию |
| REPEATABLE READ | на транзакцию | нет | нет (в PG) | обнаруживается → `40001` | возможна | отчёты, согласованное чтение |
| SERIALIZABLE | на транзакцию + SSI | нет | нет | обнаруживается | обнаруживается → `40001` | деньги, склад, инварианты |

- В Postgres нет READ UNCOMMITTED; он отображается на READ COMMITTED. Грязное чтение невозможно ни на одном уровне.

### READ COMMITTED
- Каждый оператор получает новый снимок, поэтому два одинаковых SELECT в одной транзакции могут вернуть разные строки.
- UPDATE, который натыкается на строку, изменяемую другой транзакцией, **ждёт**, затем перечитывает последнюю подтверждённую версию и заново проверяет свой WHERE (EvalPlanQual). Поэтому `UPDATE ... SET x = x - 1` здесь безопасен, а «прочитать в приложении, потом записать» — нет ([[concurrency-control]]).

### REPEATABLE READ (изоляция снимков)
- Снимок берётся на первом операторе, а не на BEGIN. Все чтения видят базу на этот момент, включая новые строки: вставки, подтверждённые позже, невидимы, поэтому **фантомы не появляются** (стандарт SQL на этом уровне их допускает; Postgres строже).
- Если транзакция обновляет или блокирует строку, которую изменили и подтвердили после её снимка, Postgres её прерывает: `could not serialize access due to concurrent update` (40001). Это предотвращает потерянные обновления.
- Write skew всё ещё возможна: две транзакции читают одно и то же множество, каждая обновляет **другую** строку, конфликта по строкам нет, обе коммитятся.
- REPEATABLE READ в MySQL InnoDB отличается: обычные чтения используют снимок, но `UPDATE` и блокирующие чтения видят последние данные и блокируют фантомы через gap/next-key блокировки.

### Фантомное чтение наглядно
- T1: `SELECT count(*) FROM orders WHERE day = today` → 10. T2 вставляет заказ на сегодня и коммитит. T1 снова выполняет тот же запрос.
- READ COMMITTED: 11 (фантом). REPEATABLE READ: 10 (тот же снимок). SERIALIZABLE: 10, а если T1 затем пишет что-то, зависящее от этого числа, SSI может прервать одну из сторон.

### SERIALIZABLE и REPEATABLE READ
- Оба читают один и тот же снимок; SERIALIZABLE дополнительно записывает **предикатные блокировки** (SIRead) на то, что прочитала каждая транзакция. Они никогда не блокируют; они только наполняют граф зависимостей.
- Когда две параллельные транзакции образуют опасную структуру (T1 прочитала то, что записала T2, а T2 прочитала то, что записала T1 — цикл rw-антизависимостей), одна прерывается с `40001`.
- Классическая write skew: дежурные врачи. Обе транзакции читают `count(*) WHERE on_call` = 2, каждая ставит своей строке `on_call = false`. REPEATABLE READ: обе коммитятся, дежурных нет. SERIALIZABLE: второй коммит падает.
- Альтернативы SERIALIZABLE против write skew: заблокировать строки, образующие инвариант (`SELECT ... FOR UPDATE` по всем врачам смены), материализовать конфликт в одну строку (строка `shift`, которую обе должны обновить) или ограничение (`EXCLUDE`, уникальность).
- Цена: больше прерываний при высокой конкуренции, память под предикатные блокировки, ложные срабатывания (прерывания, которые были не строго необходимы). Объявление транзакций `READ ONLY DEFERRABLE` позволяет долгим отчётам выполняться на serializable без риска прерывания.

### Снимки и долгие транзакции
- Снимок удерживает живыми все версии строк, которые могут ему понадобиться: VACUUM не может удалить кортежи новее самого старого работающего снимка ([[postgres-vacuum-and-bloat]]).
- Нужна ли транзакция для работы только на чтение? Одиночный SELECT и так атомарен и согласован. Несколько SELECT, которые должны согласовываться (отчёт), требуют REPEATABLE READ; иначе явная транзакция не нужна.

## Пример
```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT count(*) FROM doctors WHERE shift_id = 7 AND on_call;     -- 2
UPDATE doctors SET on_call = false WHERE id = 101;
COMMIT; -- may fail with SQLSTATE 40001: retry the whole transaction
```

```java
// Spring: retry the whole transactional method on serialization failures
@Retryable(retryFor = PessimisticLockingFailureException.class, maxAttempts = 5,
           backoff = @Backoff(delay = 20, multiplier = 2, random = true))
@Transactional(isolation = Isolation.SERIALIZABLE)
public void goOffCall(long doctorId) { ... }
```

## Подводные камни
- Write skew на REPEATABLE READ: выглядит безопасно, потому что снимок стабилен, но это не сериализуемо.
- SERIALIZABLE без повторов или повтор только упавшего оператора вместо всей транзакции.
- Смешение уровней: SSI защищает только транзакции, которые все выполняются на SERIALIZABLE.
- Долгие транзакции задерживают vacuum. Следи за `pg_stat_activity.xact_start`.
- Spring поддерживает `Isolation.SERIALIZABLE` в [[spring-transactional|@Transactional]]; SQLSTATE 40001 и 40P01 Spring превращает в подклассы `PessimisticLockingFailureException`, поэтому повторяй по нему. Связанное: [[transactions-acid-and-isolation]], [[concurrency-control]], [[idempotency]].
