## Кратко
`jsonb` хранит разобранный бинарный JSON, который можно индексировать через GIN и запрашивать операторами вхождения (`@>`), пути (`->`, `->>`, `#>>`), существования (`?`) и SQL/JSON path (`@?`, `@@`). Это правильный инструмент для разреженных или специфичных для поставщика атрибутов рядом с реляционным ядром, но не замена столбцам, по которым фильтруют, делают join или накладывают ограничения. Полнотекстовый поиск превращает текст в `tsvector` из нормализованных лексем, сопоставляет его с `tsquery`, ранжирует через `ts_rank` и использует то же семейство индексов GIN. Он хорошо покрывает задачу «поиск по полю description»; настройка релевантности, фасеты и нечёткое сопоставление по миллионам документов — это то место, где начинается [[elasticsearch-basics]].

## Основное

### json и jsonb
| | `json` | `jsonb` |
|---|---|---|
| Хранение | исходный текст | разобранный бинарный формат, ключи дедуплицированы и отсортированы |
| Запись | дёшево | стоимость разбора, чуть больше по размеру |
| Чтение | разбирается заново при каждом обращении | прямой доступ, индексируется |
| Сохраняет | пробелы, порядок ключей, дублирующиеся ключи | ничего из этого |
| Применение | аудит-копии payload в том виде, в каком он получен | всё остальное |

### Операторы и функции
- `->` возвращает `jsonb`, `->>` возвращает `text`; `#>'{a,b}'` и `#>>` — для путей. `data->>'iccid'` — это `text`, поэтому сравнение с числом требует приведения: `(data->>'retries')::int > 3`.
- Вхождение `@>`: `data @> '{"profileType": "prepaid"}'` — оператор, который GIN ускоряет лучше всего. `?` — ключ существует, `?|` — любой из, `?&` — все.
- SQL/JSON path (PG 12+): `data @? '$.tags[*] ? (@ == "vip")'`, `jsonb_path_query(data, '$.sims[*].iccid')`. PG 17 добавил стандартные `JSON_TABLE`, `JSON_EXISTS`, `JSON_QUERY`, `JSON_VALUE`.
- Изменение: `||` объединяет ключи верхнего уровня, `-` удаляет ключ, `jsonb_set(data, '{status}', '"ACTIVE"')`, `jsonb_build_object`, `jsonb_agg`. Обновление перезаписывает всё значение (TOAST), так что документ на 100 KB, обновлённый ради одного флага, каждый раз даёт 100 KB WAL.
- `jsonb_to_recordset` / `jsonb_array_elements` разворачивают массивы в строки для join и агрегации.

### Индексирование jsonb
- `CREATE INDEX ... USING gin (data)` с `jsonb_ops` по умолчанию: поддерживает `@>`, `?`, `?|`, `?&`, `@?`, `@@`; индексирует каждый ключ и значение.
- `USING gin (data jsonb_path_ops)`: поддерживает только `@>` и операторы путей, но меньше и быстрее; обычный выбор, когда запросы имеют форму вхождения.
- Для одного горячего поля B-tree по выражению лучше GIN: `CREATE INDEX ON sim ((data->>'eid'))` обслуживает `WHERE data->>'eid' = ?` с равенством и сортировкой и может быть `UNIQUE`. GIN не умеет диапазоны и сортировку.
- Запись в GIN дорогая; `fastupdate` буферизует записи в списке ожидания, который сливается vacuum-ом или при превышении `gin_pending_list_limit`. Следи за внезапно медленной вставкой, запустившей слияние ([[postgres-indexes]]).
- Статистика по jsonb бедная (нет гистограмм по ключам); планировщик принимает селективность `@>` за константу, поэтому ошибки оценки в `EXPLAIN ANALYZE` на предикатах по jsonb — это нормально ([[explain-analyze]]).

### Когда применять jsonb
- Специфичные для поставщика или необязательные атрибуты (метаданные профиля eSIM для каждого оператора), payload событий, блоки конфигурации, аудит-снимки, приём данных без схемы, пока модель не стабилизировалась.
- Не для: всего, что имеет внешний ключ, всего, по чему регулярно агрегируют или сортируют, денег, столбцов статуса. Переводи ключ в настоящий столбец, как только он появляется в `WHERE` горячего запроса или в ограничении ([[data-modeling-for-services]]).
- Проверяй форму через `CHECK (jsonb_typeof(data->'sims') = 'array')` или через `pg_jsonschema`; иначе схема живёт только в Java.
- Hibernate 6 отображает `jsonb` через `@JdbcTypeCode(SqlTypes.JSON)` на поле типа `Map` или record; дополнительная библиотека не нужна.

### Полнотекстовый поиск
- `to_tsvector('english', text)` приводит к нижнему регистру, убирает стоп-слова, выполняет стемминг (`activations` → `activ`) и запоминает позиции. `to_tsquery('english', 'activ & fail')` / `plainto_tsquery` / `websearch_to_tsquery('"profile download" -test')` строят запросы; `@@` выполняет сопоставление.
- Храни вектор как генерируемый столбец: `search tsvector GENERATED ALWAYS AS (to_tsvector('simple', coalesce(title,'') || ' ' || coalesce(body,''))) STORED` (PG 12+) и индексируй его через GIN. `setweight` позволяет совпадениям в заголовке ранжироваться выше совпадений в теле; `ts_rank_cd` упорядочивает результаты; `ts_headline` строит фрагменты.
- Конфигурация языка важна: `'simple'` только приводит к нижнему регистру и разбивает, безопасна для идентификаторов и многоязычного текста; `'english'`/`'russian'` выполняют стемминг. Для контента на смеси языков обычно берут `'simple'` плюс триграммный индекс.
- Триграммный поиск (`pg_trgm`, `GIN (col gin_trgm_ops)`) обрабатывает `LIKE '%abc%'`, `ILIKE` и `similarity()` для устойчивости к опечаткам; это не полнотекстовый поиск, но он решает большинство запросов «поиск по части имени/MSISDN».
- Ограничения по сравнению с поисковым движком: по умолчанию нет BM25, нет фасетов, нет синонимов без словаря-тезауруса, ранжирование не может использовать индекс, поэтому `ORDER BY ts_rank` сортирует все совпадения. Нормально до нескольких миллионов строк при селективных запросах ([[search-and-indexing-services]]).

## Пример
```sql
-- Атрибуты, специфичные для оператора, в jsonb; горячий ключ вынесен в индекс по выражению
ALTER TABLE sim ADD COLUMN attrs jsonb NOT NULL DEFAULT '{}';
CREATE INDEX CONCURRENTLY sim_attrs_gin ON sim USING gin (attrs jsonb_path_ops);
CREATE UNIQUE INDEX CONCURRENTLY sim_eid_idx ON sim ((attrs->>'eid')) WHERE attrs ? 'eid';

SELECT id, attrs->>'eid' AS eid, attrs #>> '{profile,type}' AS profile_type
FROM sim
WHERE attrs @> '{"profile": {"type": "prepaid"}, "flags": ["esim"]}'
  AND status = 'ACTIVE';

-- Поиск по тикетам поддержки со взвешенным ранжированием и фрагментом текста
ALTER TABLE tickets ADD COLUMN search tsvector
  GENERATED ALWAYS AS (
    setweight(to_tsvector('simple', coalesce(subject, '')), 'A') ||
    setweight(to_tsvector('simple', coalesce(body, '')),    'B')
  ) STORED;
CREATE INDEX CONCURRENTLY tickets_search_idx ON tickets USING gin (search);

SELECT id, subject, ts_rank_cd(search, q) AS rank,
       ts_headline('simple', body, q, 'MaxWords=20') AS snippet
FROM tickets, websearch_to_tsquery('simple', 'profile download failed') q
WHERE search @@ q
ORDER BY rank DESC
LIMIT 20;
```

## Подводные камни
- `WHERE data->>'status' = 'ACTIVE'` при наличии только GIN-индекса по `data`: GIN не поддерживает равенство через `->>`; используй `@>` или добавь B-tree по выражению.
- Столбец jsonb, который разрастается до всей доменной модели: нет ограничений, нет внешних ключей, каждый запрос — цепочка `->>`, и нет статистики для планировщика.
- Обновление одного ключа большого значения jsonb перезаписывает всё значение в TOAST и лишает HOT-обновлений; часто меняющиеся поля держи столбцами ([[postgres-vacuum-and-bloat]]).
- `to_tsvector` без явного аргумента конфигурации использует `default_text_search_config`, который может отличаться между окружениями и незаметно меняет содержимое сохранённого вектора.
- Когда поиска Postgres недостаточно: [[elasticsearch-basics]]; выбор между гибкими столбцами и документным хранилищем: [[sql-vs-nosql-choosing]].
