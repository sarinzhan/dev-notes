## Кратко
Партиционирование (partitioning) разбивает одну логическую таблицу на дочерние таблицы по ключу (диапазон дат, список значений, хеш id) внутри одного сервера Postgres. Планировщик читает только те партиции, которые может затронуть запрос (**отсечение партиций, partition pruning**), старые данные удаляются через `DROP TABLE` или `DETACH PARTITION` вместо `DELETE` на миллион строк, а индексы и vacuum работают с меньшими кусками. Это не шардирование: все партиции живут на одном экземпляре и делят его CPU и диск (многоузловая версия — [[sharding-strategies]]). Партиционирование окупается для больших (десятки миллионов строк), упорядоченных по времени таблиц или таблиц со сроком хранения, а в остальных случаях стоит немного, кроме времени планирования.

## Основное

### Стратегии
| Стратегия | `PARTITION BY` | Когда применять |
|---|---|---|
| **Range** | `RANGE (created_at)` | временные ряды, логи, события, всё со сроком хранения; самый частый случай |
| **List** | `LIST (region)` | небольшой фиксированный набор значений с разным жизненным циклом или размером (арендатор, страна) |
| **Hash** | `HASH (subscriber_id)` с `MODULUS n REMAINDER i` | равномерно распределить большую таблицу, когда естественного диапазона нет; индексы меньше, vacuum параллельно |

- Декларативное партиционирование (PG 10) заменило наследование плюс триггеры. С PG 11: партиция по умолчанию, первичные ключи и уникальные ограничения (должны включать ключ партиционирования), маршрутизация `INSERT`, `UPDATE`, переносящий строки между партициями, индексы, созданные на родителе, распространяются на все партиции. PG 12: отсечение во время выполнения для подготовленных выражений и параметров nested loop, внешние ключи, ссылающиеся на партиционированные таблицы. PG 13: логическая репликация партиционированных таблиц. PG 14: `DETACH PARTITION CONCURRENTLY`. PG 17: identity-столбцы и ограничения исключения на партиционированных таблицах.
- Подпартиционирование возможно (по диапазону месяцев, затем по хешу арендатора); не усложняй без замеров.

### Отсечение партиций
- Планировщик убирает партиции, границы которых не могут удовлетворить условию `WHERE`. Для этого предикат должен быть **по самому ключу партиционирования** с константами или параметрами: `WHERE created_at >= '2026-10-01'` отсекает; `WHERE date_trunc('day', created_at) = ...` — нет; `WHERE created_at >= now() - interval '1 day'` отсекает во время выполнения (PG 12+), потому что `now()` — stable, а не immutable.
- `EXPLAIN` показывает `Partitions removed: 11` или перечисляет только оставшиеся дочерние узлы `Append`; `enable_partition_pruning` по умолчанию включён ([[explain-analyze]]).
- Запрос без ключа партиционирования сканирует все партиции: `Append` из 36 index scan. Каждый важный запрос к партиционированной таблице должен содержать ключ, и это определяет схему: таблица `orders`, партиционированная по месяцам, не может дёшево ответить на «заказ по id», если id не кодирует время (UUID v7 или последовательность, коррелирующая со временем, см. [[time-money-and-ids]]).

### Ограничения и индексы
- Ограничение `PRIMARY KEY` или `UNIQUE` должно включать все столбцы партиционирования, потому что уникальность проверяется внутри каждой партиции. `PRIMARY KEY (id, created_at)` — обычный компромисс; глобальная уникальность одного `id` держится на генераторе.
- Внешним ключам **из** других таблиц **в** партиционированную таблицу тоже нужен полный ключ; часто проще ссылаться на родительскую сущность (абонента), а не на партиционированную строку события.
- `CREATE INDEX ON parent (...)` создаёт соответствующий индекс на каждой партиции и на будущих. Чтобы построить его без блокировки: `CREATE INDEX CONCURRENTLY` на каждой партиции, затем `CREATE INDEX ON ONLY parent` плюс `ALTER INDEX ... ATTACH PARTITION` ([[postgres-indexes]]).

### Обслуживание
- Создавай партиции **заранее**: вставка без подходящей партиции падает с `no partition of relation "events" found for row`. Партиция по умолчанию ловит отбившиеся строки, но затем мешает создать партицию, диапазон которой пересекается со строками, уже лежащими в партиции по умолчанию (её придётся сканировать). Расширение `pg_partman` или задание по расписанию создаёт месячные партиции заранее.
- Хранение с ограниченным сроком: `ALTER TABLE events DETACH PARTITION events_2026_04 CONCURRENTLY; DROP TABLE events_2026_04;` выполняется мгновенно и не оставляет раздувания, в отличие от `DELETE`, который пишет миллион мёртвых кортежей и держит место до vacuum ([[postgres-vacuum-and-bloat]]).
- Autovacuum работает по партициям, так что горячий текущий месяц очищается, а холодные месяцы не трогаются; `ANALYZE` на родителе собирает статистику по всем дочерним таблицам.
- Join и агрегации по партициям (partition-wise, `enable_partitionwise_join`) соединяют соответствующие партиции попарно, когда у обеих таблиц одинаковая разбивка; по умолчанию выключено из-за стоимости планирования.

### Стоимость планирования
- Каждая партиция — отношение, которое планировщик должен учесть; тысячи партиций заставляют простые запросы планироваться медленно (миллисекунды на запрос, заметно при высоком QPS). Целься в десятки — небольшие сотни партиций: помесячно на несколько лет, посуточно только для очень больших объёмов с коротким сроком хранения.
- Число блокировок: запрос, затрагивающий все партиции, берёт блокировку на каждую партицию и в большом `SELECT` может превысить `max_locks_per_transaction`.

## Пример
```sql
-- V12__partition_sim_events.sql: журнал событий хранится 12 месяцев, запросы по абоненту и времени
CREATE TABLE sim_events (
    id            uuid        NOT NULL,
    subscriber_id bigint      NOT NULL,
    type          text        NOT NULL,
    payload       jsonb       NOT NULL,
    created_at    timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

CREATE INDEX ON sim_events (subscriber_id, created_at);   -- распространяется на каждую партицию

CREATE TABLE sim_events_2026_10 PARTITION OF sim_events
    FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
CREATE TABLE sim_events_2026_11 PARTITION OF sim_events
    FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');
CREATE TABLE sim_events_default PARTITION OF sim_events DEFAULT;

-- Отсечение: сканируется только sim_events_2026_10
EXPLAIN SELECT type, payload FROM sim_events
WHERE subscriber_id = 4711 AND created_at >= '2026-10-20' AND created_at < '2026-10-27';
--  Index Scan using sim_events_2026_10_subscriber_id_created_at_idx on sim_events_2026_10
--    Index Cond: ((subscriber_id = 4711) AND (created_at >= ...) AND (created_at < ...))

-- Ежемесячное задание удаления старых данных
ALTER TABLE sim_events DETACH PARTITION sim_events_2025_10 CONCURRENTLY;
DROP TABLE sim_events_2025_10;
```
В JPA сущность, как обычно, отображается на `sim_events`; `@Id` должен быть составным `(id, created_at)`, либо репозиторий должен всегда фильтровать по `created_at`, иначе `findById` сканирует все партиции.

## Подводные камни
- Партиционировать таблицу на 2 GB «на будущее»: пользы нет, есть дополнительная стоимость планирования, а ORM вынужден работать с составным первичным ключом. Партиционируй, когда таблица большая или проблема в сроке хранения.
- Забыть создать партицию на следующий месяц: в полночь первого числа вставки начинают падать. Автоматизируй это и поднимай алерт, когда будущих партиций меньше двух.
- `UPDATE` ключа партиционирования переносит строку (delete + insert); при конкурентном `FOR UPDATE` он может выдать `tuple to be locked was already moved to another partition`.
- Преобразование существующей таблицы: `ATTACH PARTITION` старой таблицы как одной большой диапазонной партиции выполняется мгновенно, если уже есть ограничение `CHECK`, доказывающее границы; иначе вся таблица сканируется под блокировкой.
- Разбиение по нескольким узлам — это [[sharding-strategies]]; место партиционирования на пути масштабирования — [[database-scaling-path]].
