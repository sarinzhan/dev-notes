## Кратко
Elasticsearch (и его форк OpenSearch) — распределённый поисковый движок на основе Lucene: документы анализируются и разбиваются на термы, хранятся в **инвертированном индексе (inverted index)** (терм → список документов) и запрашиваются с оценкой релевантности (BM25), фильтрами, агрегациями и подсветкой. Он работает почти в реальном времени (refresh раз в секунду), согласован в конечном счёте и не является системой-источником истины. Используй его, когда поиску нужны ранжирование по релевантности, устойчивость к опечаткам, фасеты или аналитика логов по большим объёмам текста; Postgres оставляй источником истины, а индекс наполняй асинхронно ([[search-and-indexing-services]]). Более простые случаи покрывает полнотекстовый поиск Postgres ([[postgres-jsonb-and-full-text]]).

## Основное

### Инвертированный индекс
- B-tree отвечает на вопрос «каково значение поля X у строки Y»; инвертированный индекс отвечает на вопрос «какие документы содержат терм T». Текст каждого поля проходит через **анализатор (analyzer)** (фильтры символов → токенизатор → фильтры токенов: приведение к нижнему регистру, стемминг, стоп-слова, синонимы, n-граммы) и превращается в термы; индекс сопоставляет каждому терму список вхождений (postings list) с id документов, позициями и частотами терма.
- Оценка: BM25 учитывает частоту терма в документе, обратную частоту документов по индексу и длину документа. Запросы `match` вычисляют оценку; `term`/`range` в контексте `filter` её не вычисляют и кэшируются как битовые множества, поэтому точные условия (статус, арендатор, диапазон дат) клади в `filter`, а в `must` — только текст.
- Сегменты Lucene неизменяемы; **refresh** (по умолчанию 1 с) делает новые сегменты доступными для поиска, **flush** записывает translog на диск, **слияния (merges)** уплотняют сегменты в фоне. Тот же жизненный цикл в форме LSM, что и в [[column-and-wide-column-stores]]; удаления — это пометки до слияния.

### Маппинги
- Маппинг (mapping) — это схема: типы полей и анализаторы. Динамический маппинг угадывает типы по первому документу (строка становится одновременно `text` и `keyword`), что удобно и опасно: поле, впервые увидевшее `long`, отклоняет последующие строки. Задавай явные маппинги для всего важного и `"dynamic": "strict"` для production-индексов.
- Типы полей: `text` (анализируется, для поиска), `keyword` (точное значение, для фильтров, сортировки, агрегаций), `long`/`double`, `date`, `boolean`, `ip`, `geo_point`, `nested` (массив объектов, запрашиваемых независимо), `object` (уплощается). Тип поля нельзя поменять на месте: переиндексируй в новый индекс и переключи алиас.
- Индекс на временной период (`logs-2026.10.27`) с алиасом для записи и управлением жизненным циклом индексов (hot → warm → delete) — стандартный шаблон для логов; для поиска в приложении — один индекс на тип сущности.

### Кластер
- Индекс разбит на **первичные шарды (primary shards)** (число задаётся при создании) с **шардами-репликами (replica shards)**; шарды — это индексы Lucene, распределённые по узлам данных. Запрос веером расходится на одну копию каждого шарда, затем координирующий узел сливает результаты (scatter-gather, [[cross-shard-queries-and-transactions]]). Слишком много мелких шардов расходуют heap; целься в шарды по 10–50 GB.
- Запись идёт в первичный шард, затем синхронно реплицируется на реплики до подтверждения; документ становится видимым после следующего refresh. `GET` по id работает в реальном времени через translog; поиск — нет.
- Узлы, которые могут быть мастером (master-eligible), выбирают мастера по Raft-подобному протоколу (Zen2, 7.x+) с кворумом из master-eligible узлов ([[quorums-and-leader-election]]). Split-brain был классическим сбоем в 6.x, его исправили конфигурациями голосования.
- Глубокая пагинация (`from: 10000`) по умолчанию запрещена (`index.max_result_window`); для прохода по результатам используй `search_after` с дополнительным ключом сортировки для разрешения равенств.

### Основы Query DSL
| Запрос | Применение |
|---|---|
| `match`, `multi_match` | полнотекстовый поиск с анализом по одному или нескольким полям с весами |
| `match_phrase`, `slop` | слова по порядку, с допуском |
| `term`, `terms`, `range`, `exists` | точные фильтры по полям `keyword`/числовым/датам |
| `bool` с `must`/`should`/`filter`/`must_not` | комбинирование, оценка против фильтрации |
| `fuzzy`, `match` с `fuzziness: AUTO` | устойчивость к опечаткам по редакционному расстоянию |
| `nested` | запрос объектов внутри массивов как единого целого |
| агрегации: `terms`, `date_histogram`, `avg`, `percentiles` | фасеты, дашборды, аналитика логов |
- Подсказчики `completion` и анализаторы на edge n-граммах реализуют автодополнение; `highlight` возвращает фрагменты текста.

### Синхронизация индекса
- Приложение никогда не делает двойную запись в Postgres и Elasticsearch в одном запросе (почему — объясняет [[outbox-pattern]]). Варианты: outbox → Kafka → сервис-индексатор; Debezium CDC → Kafka Connect Elasticsearch sink; периодическая полная переиндексация для небольших наборов данных. Индексируй по бизнес-id, чтобы повторная доставка была идемпотентной ([[idempotency]]).
- Переиндексация при изменении маппинга: создать `products_v2`, выполнить `_reindex` или повторно проиграть данные из источника истины, затем атомарно переключить алиас `products` с v1 на v2.
- Удаляй из индекса, когда исходная строка удалена или скрыта; иначе поиск возвращает призраков, а UI показывает 404 при клике.

### Spring
- Spring Data Elasticsearch (`ElasticsearchOperations`, `@Document`, репозитории) или официальный Java-клиент (`ElasticsearchClient`, DSL на билдерах). Согласование версий клиента, сервера и Spring Boot строгое; OpenSearch требует собственного клиента.

## Пример
```json
PUT /tickets
{
  "settings": { "number_of_shards": 1, "number_of_replicas": 1 },
  "mappings": {
    "dynamic": "strict",
    "properties": {
      "id":        { "type": "keyword" },
      "subject":   { "type": "text", "analyzer": "english" },
      "body":      { "type": "text", "analyzer": "english" },
      "status":    { "type": "keyword" },
      "tenant":    { "type": "keyword" },
      "createdAt": { "type": "date" }
    }
  }
}

GET /tickets/_search
{
  "query": {
    "bool": {
      "must":   [{ "multi_match": { "query": "profile download failed",
                                    "fields": ["subject^3", "body"], "fuzziness": "AUTO" } }],
      "filter": [{ "term": { "tenant": "beeline-kg" } },
                 { "terms": { "status": ["OPEN", "IN_PROGRESS"] } },
                 { "range": { "createdAt": { "gte": "now-30d" } } }]
    }
  },
  "highlight": { "fields": { "body": {} } },
  "aggs": { "by_status": { "terms": { "field": "status" } } },
  "sort": [ "_score", { "createdAt": "desc" } ],
  "size": 20
}
```
Текстовый поиск вычисляет оценку; арендатор, статус и дата — это фильтры, они кэшируются и не участвуют в оценке; агрегация в том же запросе даёт счётчики фасетов для боковой панели.

## Подводные камни
- Использовать Elasticsearch как основное хранилище: нет транзакций, документы могут потеряться при некорректном переключении шарда, а ошибка в маппинге требует полной переиндексации откуда-то.
- Динамический маппинг в production: первый документ с `"amount": "12.50"` навсегда делает поле строкой в этом индексе.
- Сортировка или агрегация по полю `text` (`fielddata: true`): всё поле загружается в heap; используй подполе `.keyword`.
- Запрос сразу после индексации в тесте ничего не находит: refresh ещё не произошёл; в тестах вызывай `_refresh` или используй `refresh=wait_for` при записи.
- Когда достаточно Postgres: [[postgres-jsonb-and-full-text]]; место поиска в system design: [[search-and-indexing-services]].
