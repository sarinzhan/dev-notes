## Кратко
За «колоночными» базами скрываются две разные вещи. **Wide-column хранилище** (Cassandra, ScyllaDB, HBase, DynamoDB) — распределённое хранилище ключ-значение, где каждый ключ партиции соответствует отсортированному набору строк; оно создано для огромной пропускной способности записи и линейного горизонтального масштабирования ценой проектирования одной таблицы под каждый запрос и отказа от join и произвольных фильтров. **Колоночное (column-oriented) аналитическое хранилище** (ClickHouse, BigQuery, Redshift, файлы Parquet) хранит каждый столбец отдельно, так что сканирования и агрегации по миллиардам строк читают только нужные столбцы и очень хорошо сжимаются; оно создано для OLAP, а не для точечных обновлений. У обоих путь записи основан на журнале только для дописывания плюс отсортированных неизменяемых файлах (LSM-дерево), а не на B-деревьях.

## Основное

### Путь записи LSM-дерева (оба семейства)
- Запись попадает в журнал коммитов (commit log, ради долговечности) и в отсортированную таблицу в памяти (**memtable**). Когда memtable заполняется, она сбрасывается на диск как неизменяемый отсортированный файл (**SSTable**). Чтение проверяет memtable, затем SSTable от новых к старым, используя фильтры Блума ([[bloom-filters-and-probabilistic]]) и разреженные индексы, чтобы пропускать файлы. Фоновое **уплотнение (compaction)** сливает SSTable и отбрасывает перезаписанные или удалённые записи.
- Следствия: запись последовательная и быстрая независимо от размера таблицы; чтение может затронуть несколько файлов (усиление чтения, read amplification); удаления — это **надгробия (tombstones)**, которые занимают место до уплотнения; обновления — просто более новые записи. Сравни с моделью B-дерева с изменением на месте в Postgres ([[database-indexes]], [[postgres-vacuum-and-bloat]]).

### Wide-column: Cassandra / ScyllaDB
- Модель данных: `PRIMARY KEY ((partition_key), clustering_col1, clustering_col2)`. Ключ партиции хешируется в токен на кольце ([[consistent-hashing]]) и определяет узел; строки внутри партиции хранятся отсортированными по кластеризующим столбцам (clustering columns). Запрос обязан указать полный ключ партиции и затем может брать диапазон по кластеризующим столбцам по порядку; всё остальное требует `ALLOW FILTERING` (полное сканирование) или вторичного индекса, который опрашивает все узлы.
- **Моделирование от запросов (query-first)**: перечисли запросы, затем создай по таблице на каждый запрос с продублированными и денормализованными данными. «События по устройству, упорядоченные по времени» и «события по типу за последний час» — это две таблицы, обе пишет приложение (или материализованное представление, у которого были оговорки по надёжности). Нет join, нет внешних ключей, нет транзакций по нескольким партициям; лёгкие транзакции (lightweight transactions: `IF NOT EXISTS`, Paxos) существуют в пределах партиции и медленные.
- Размер партиции: целься ниже ~100 MB и нескольких сотен тысяч строк на партицию; разбивай временные ряды на корзины по `(device_id, day)`, чтобы одно устройство не превратилось в безграничную партицию. Горячий ключ партиции (один арендатор даёт 80 % трафика) перегружает один узел независимо от размера кластера ([[sharding-strategies]]).
- Репликация и согласованность: без лидера (leaderless), каждая партиция хранится на `RF` узлах; уровень согласованности задаётся на каждый запрос: `ONE`, `QUORUM`, `LOCAL_QUORUM`, `ALL`. Чтения `QUORUM` + записи `QUORUM` при RF 3 дают read-your-writes; `ONE` даёт согласованность в конечном счёте. Конфликты разрешаются по метке времени «побеждает последняя запись» (last-write-wins), поэтому важен рассинхрон часов ([[multi-leader-and-leaderless]], [[time-and-clocks]]). Repair выполняет anti-entropy, чтобы исправить разошедшиеся реплики.
- Эксплуатационные факты: все узлы равноправны, добавление узлов масштабирует запись линейно, репликация между несколькими дата-центрами встроена, TTL на строку делает хранение с ограниченным сроком бесплатным. Нагрузки с большим количеством надгробий (очереди, частые удаления) — известный антипаттерн.
- Сценарии: временные ряды и телеметрия, журналы событий устройств, история сообщений, ленты активности, всё с интенсивной записью и известными путями доступа. DynamoDB — управляемый аналог с той же дисциплиной ключа партиции.

### Колоночная аналитика: ClickHouse
- Каждый столбец — отдельный сжатый файл; запрос, читающий 5 столбцов из 200, читает 2,5 % данных, а похожие значения сжимаются в 10–100 раз. Векторизованное выполнение обрабатывает столбцы пачками размером с кэш CPU.
- Движки `MergeTree`: данные, отсортированные по ключу `ORDER BY`, лежат в частях (parts), которые сливаются в фоне (снова LSM). Разреженный первичный индекс (одна запись на 8192 строки) плюс индексы пропуска (skip indexes) заменяют B-деревья. `PARTITION BY toYYYYMM(ts)` позволяет мгновенно удалять месяцы ([[postgres-partitioning]]).
- Настоящих `UPDATE`/`DELETE` отдельных строк нет: мутации асинхронно перезаписывают части и предназначены для исправлений в духе GDPR, а не для OLTP. `ReplacingMergeTree`/`CollapsingMergeTree` дают дедупликацию в конечном счёте при слиянии.
- Вставляй пачками (тысячи строк), никогда по одной строке на запрос; каждая вставка создаёт часть. Таблицы с движком Kafka или буфер забирают данные прямо из [[kafka-architecture|Kafka]].
- Сценарии: аналитика событий, метрики и логи (хранилище под многими продуктами наблюдаемости), отчёты по миллиардам строк с `GROUP BY` быстрее секунды. Join поддерживаются, но правая сторона должна помещаться в память; таблицы измерений маленькие, таблицы фактов широкие.

### Сравнение
| | Postgres | Cassandra / Scylla | ClickHouse |
|---|---|---|---|
| Модель | реляционная, B-tree, MVCC | партиция → отсортированные строки, LSM | столбцы, отсортированные части, LSM |
| Масштаб | один primary + реплики, локальное партиционирование | линейное горизонтальное, без лидера | шардирование + репликация, один запрос использует много ядер/узлов |
| Запись | тысячи–десятки тысяч/с на primary | сотни тысяч/с на кластер | миллионы строк/с пачками |
| Чтение | точечные запросы, join, любой предикат | только по ключу партиции | полные сканирования и агрегации по немногим столбцам |
| Транзакции | ACID по нескольким строкам | в пределах партиции, LWT | нет |
| Обновления | на месте | побеждает более новая запись | только пакетные мутации |
| Типичная роль | система-источник истины | операционные события большого объёма | аналитика, метрики, логи |

## Пример
```sql
-- Cassandra (CQL): телеметрия устройств, разбитая на корзины по дням, чтобы партиции оставались ограниченными,
-- сначала самые новые показания, хранение 30 дней через TTL
CREATE TABLE esim.device_events (
    device_id   text,
    day         date,
    ts          timestamp,
    event_type  text,
    payload     text,
    PRIMARY KEY ((device_id, day), ts)
) WITH CLUSTERING ORDER BY (ts DESC)
  AND default_time_to_live = 2592000
  AND compaction = { 'class': 'TimeWindowCompactionStrategy', 'compaction_window_unit': 'DAYS', 'compaction_window_size': 1 };

-- Единственная дешёвая форма запроса: полный ключ партиции + диапазон по кластеризующему столбцу
SELECT ts, event_type, payload FROM esim.device_events
WHERE device_id = '8999600000000000001' AND day = '2026-10-27' AND ts > '2026-10-27T10:00:00Z';

-- ClickHouse: те же события для аналитики, вставляются пачками из Kafka
CREATE TABLE device_events (
    ts          DateTime,
    device_id   String,
    event_type  LowCardinality(String),
    latency_ms  UInt32
) ENGINE = MergeTree
PARTITION BY toYYYYMM(ts)
ORDER BY (event_type, device_id, ts);

SELECT event_type, quantile(0.99)(latency_ms) AS p99, count() AS n
FROM device_events WHERE ts >= now() - INTERVAL 1 DAY
GROUP BY event_type ORDER BY n DESC;
```

## Подводные камни
- Выбрать Cassandra, а потом спросить «найди все события, где payload содержит X»: это сканирование всего кластера; запрос должен быть известен до создания таблицы.
- Очередь на Cassandra (вставить, прочитать, удалить): надгробия накапливаются, и чтения замедляются до уплотнения; для очередей используй Kafka или Redis stream ([[redis-patterns-and-persistence]]).
- Использовать ClickHouse как OLTP-хранилище со вставками и обновлениями по одной строке: ошибки «too many parts» и слияния, которые никогда не успевают.
- Запись с `QUORUM` при RF 2: кворум из 2 — это 2, так что падение одного узла останавливает запись; RF 3 — минимум для расчётов доступности ([[quorums-and-leader-election]]).
- Связанные заметки: [[storage-choices]] — выбор по шаблону доступа, [[sql-vs-nosql-choosing]] — процедура принятия решения.
