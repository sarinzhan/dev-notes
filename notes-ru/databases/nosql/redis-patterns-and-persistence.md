## Кратко
В бэкенде Redis используют для пяти повторяющихся задач: кэш перед базой данных, кратковременная распределённая блокировка, ограничитель частоты запросов (rate limiter), шина pub/sub и лёгкая очередь или stream. Каждый паттерн — это несколько команд плюс один приём для атомарности: `SET NX PX` для блокировок, `INCR` + `EXPIRE` или sorted set для rate limit, Lua-скрипт или `MULTI`, когда несколько команд должны выполниться атомарно. Персистентность необязательна и настраивается: снимки RDB (компактные, с потерями), AOF (журнал дописывания, долговечность до одной секунды или одной записи) или оба. Считай Redis хранилищем, которое можно потерять, если только ты сознательно не настроил его иначе. Сами типы данных — в [[redis-data-structures]].

## Основное

### Кэш
- По умолчанию — cache-aside: читать Redis, при промахе читать Postgres и делать `SET key value EX ttl`. Варианты write-through и write-behind и их компромиссы по инвалидации — в [[caching]]; аннотации Spring — в [[spring-cache-abstraction]].
- Всегда ставь TTL; используй `maxmemory` с вытеснением `allkeys-lru` или `allkeys-lfu`, чтобы переполненный кэш вытеснял данные, а не возвращал ошибки. Добавляй к TTL случайный разброс (jitter), чтобы пачка ключей не истекала в одну секунду (stampede, см. [[distributed-cache-coherence]]).
- Горячие ключи и большие значения выстраиваются в очередь на единственном потоке выполнения команд; раздели список тарифов на 5 MB на отдельные hash по тарифу.

### Распределённая блокировка
- `SET lock:order:42 <token> NX PX 30000` захватывает блокировку; освобождать только при совпадении токена, в Lua-скрипте (`if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) end`). Без проверки токена медленный клиент удалит блокировку, которую уже держит второй клиент.
- Блокировка — это **аренда (lease)**: если держатель зависает (GC, сеть) дольше TTL, держателей становится двое. Блокировка в Redis хороша, чтобы уменьшить дублирование работы, но не для гарантии исключительности; система хранения всё равно должна отклонять устаревших писателей по fencing-токену ([[distributed-locks-and-fencing]]).
- **Redlock** (захват на большинстве из N независимых узлов Redis) спорен: он предполагает ограниченный дрейф часов и ограниченные паузы процессов, а реальные системы это нарушают; один Redis с коротким TTL плюс идемпотентные записи ниже по цепочке — обычно честный дизайн. Для взаимного исключения, критичного для корректности, используй advisory-блокировки Postgres ([[postgres-locks]]) или аренду в etcd/ZooKeeper.
- Spring: `RedisLockRegistry` из Spring Integration или `RLock` из Redisson с его watchdog, который продлевает TTL, пока поток жив.

### Ограничение частоты запросов
| Алгоритм | Ключи | Примечания |
|---|---|---|
| Фиксированное окно | `INCR rl:<client>:<minute>`, затем `EXPIRE` при первом обращении | проще всего; допускает всплеск 2× на границе окна |
| Журнал скользящего окна | sorted set меток времени запросов, `ZADD`, `ZREMRANGEBYSCORE`, `ZCARD` | точно; память растёт вместе с лимитом |
| Token bucket | hash с `tokens` и `last_refill`, обновляемый в Lua-скрипте | сглаживает всплески; один вызов скрипта на запрос |
- Чтение-изменение-запись должно быть атомарным для всех экземпляров, поэтому это Lua-скрипты (`EVALSHA`) или функции Redis, а не два сетевых обращения. Алгоритмы и место размещения — в [[rate-limiting]] и [[design-rate-limiter]].

### Pub/sub, списки и stream
- **Pub/sub**: «отправил и забыл» для подключённых в данный момент подписчиков; ничего не сохраняется. Инвалидация кэша между pod-ами, рассылка по websocket ([[websockets-sse-and-long-polling]]).
- **List** как очередь: `LPUSH` / `BRPOP`; сообщение, извлечённое упавшим воркером, теряется. `BLMOVE` в список обрабатываемых даёт at-least-once с ручной очисткой.
- **Stream** (`XADD`, `XREADGROUP`, `XACK`, `XPENDING`, `XAUTOCLAIM`): постоянный журнал с consumer group, ожидающими записями для каждого потребителя и повторной доставкой неподтверждённых сообщений. Самое близкое к Kafka в Redis, ограничено памятью (`MAXLEN ~ 100000`). Хорошо для потоков событий небольшого объёма внутри одного сервиса; для долговечных потоков с несколькими потребителями в большом масштабе используй [[kafka-architecture|Kafka]] ([[message-queues-and-streams]]).

### Персистентность и долговечность
| Режим | Что записывается | Потери при сбое | Цена |
|---|---|---|---|
| Нет | ничего | всё | быстрее всего; чистый кэш |
| RDB | снимок на момент времени каждые N секунд/изменений (`save 60 1000`), fork + copy-on-write | минуты | всплеск памяти при fork на больших наборах данных |
| AOF `appendfsync everysec` | каждая команда записи дописывается, fsync раз в секунду; периодически перезаписывается | ≤ 1 с | небольшая; рекомендуемый долговечный режим |
| AOF `appendfsync always` | fsync на каждую запись | нет | медленно |
| RDB + AOF (многочастный AOF в Redis 7) | оба; при перезапуске используется AOF | ≤ 1 с | по умолчанию для случая «мне нужны мои данные обратно» |

- Репликация (`REPLICAOF`) асинхронная; переключение через Sentinel или Cluster теряет последние записи, ещё не реплицированные. `WAIT n timeout` блокирует до подтверждения от `n` реплик, но не делает репликацию синхронной для всех ([[leader-follower-replication]]).
- Redis Cluster шардирует ключи по хеш-слотам (16384 слота); команды с несколькими ключами и Lua-скрипты требуют, чтобы все ключи были в одном слоте (хеш-теги `{order:42}:lock`). Sentinel обеспечивает failover для нешардированного primary.
- Ёмкость — это память: следи за `used_memory` против `maxmemory`, `evicted_keys`, `keyspace_misses` и за задержкой через `redis-cli --latency` или `latency-monitor-threshold`.

## Пример
```java
@Component
@RequiredArgsConstructor
public class RedisLeaseLock {
    private static final RedisScript<Long> RELEASE = RedisScript.of("""
        if redis.call('GET', KEYS[1]) == ARGV[1] then
          return redis.call('DEL', KEYS[1])
        end
        return 0
        """, Long.class);

    private final StringRedisTemplate redis;

    /** Выполняет action не более одного раза на ключ во всех pod-ах, пока действует аренда; дубликаты пропускаются. */
    public boolean runOnce(String key, Duration lease, Runnable action) {
        String token = UUID.randomUUID().toString();
        Boolean acquired = redis.opsForValue().setIfAbsent("lock:" + key, token, lease);
        if (!Boolean.TRUE.equals(acquired)) return false;
        try {
            action.run();                    // само действие должно быть идемпотентным: аренда может истечь посреди выполнения
            return true;
        } finally {
            redis.execute(RELEASE, List.of("lock:" + key), token);
        }
    }
}
```

## Подводные камни
- `DEL` при освобождении без проверки токена: клиент, чья аренда истекла, удаляет чужую блокировку.
- TTL блокировки короче работы: задачу выполняют два воркера; TTL намного длиннее работы: упавший воркер блокирует задачу на весь TTL. Выбирай TTL по p99 длительности и делай работу идемпотентной ([[idempotency]]).
- Использовать Redis как «базу данных» только с RDB, а после перезапуска обнаружить, что последних 10 минут заказов нет.
- `KEYS`, `FLUSHALL`, `SMEMBERS` на огромном множестве или Lua-скрипт с циклом по 1 миллиону записей блокируют всех остальных клиентов на время выполнения.
- Связанные заметки: [[caching]] — стратегия, [[redis-data-structures]] — команды, [[distributed-locks-and-fencing]] — почему одной блокировки недостаточно.
