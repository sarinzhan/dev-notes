## Кратко
Memcached — намеренно простой многопоточный **key-value кэш** в памяти: на входе строки, на выходе строки, без персистентности, без репликации, без типов данных, без кластеризации на стороне сервера. Памятью управляет **slab-аллокатор** (куски фиксированного размера, сгруппированные по классам размеров), чтобы избежать фрагментации, а вытеснение идёт по **LRU** на каждый класс. Потоки делят одну хэш-таблицу, защищённую мелкозернистыми блокировками. «Распределение» делает **клиент**, который хэширует каждый ключ на один сервер консистентным хэшированием; серверы друг о друге не знают. Он быстрый и предсказуемый; в большинстве новых систем его заменил Redis благодаря богатым типам и персистентности.

## Основное
### Модель данных
- Ключи до 250 байт, значения до 1 МБ по умолчанию (`-I`, чтобы увеличить). Команды: `get`, `set`, `add`, `replace`, `delete`, `incr/decr`, `cas` (check-and-set с токеном версии), `touch`.
- У каждого элемента есть TTL; просроченные элементы удаляются лениво (при обращении) и обходчиком LRU (LRU crawler).
- Персистентности нет: перезапуск очищает кэш. Это кэш, никогда не источник истины.

### Память: slab-ы, страницы, куски
- Память делится на **страницы** по 1 МБ. Каждая страница отдаётся **slab-классу** и режется на одинаковые **куски** (chunks): класс 1 = 96 Б, класс 2 = 120 Б, ... с ростом в 1,25 раза.
- Элемент кладётся в наименьший подходящий кусок: 100-байтный элемент занимает 120-байтный кусок. Потеря места на каждом элементе, зато **нет фрагментации** и выделение за O(1).
- Раньше страница, отданная классу, оставалась у него навсегда: если размеры значений меняются, один класс голодает, пока у другого есть свободная память («окаменение slab-ов», slab calcification). В современных версиях (1.4.25+) есть перебалансировщик slab-ов и **сегментированный LRU** (hot/warm/cold).
- Вытеснение идёт внутри slab-класса по порядку LRU. Полный кэш вытесняет давно не использованный элемент **этого класса размеров**, а не глобально.

### Потоки
- Многопоточный на libevent: один поток-слушатель принимает соединения и раздаёт их N рабочим потокам (`-t`, по умолчанию 4); каждый рабочий поток крутит свой цикл событий по своим соединениям ([[socket-management]]).
- Элементы лежат в одной общей хэш-таблице; блокировки на уровне корзины хэша (item locks) плюс по блокировке на каждый LRU, поэтому потоки редко конкурируют.
- Сравни: Redis выполняет команды в одном потоке (потоки ввода-вывода с 6.0), Memcached распределяет команды по ядрам.

### LRU и счётчик ссылок
- Каждый slab-класс держит двусвязный список LRU ([[lru-cache-design]]). `get` поднимает элемент (с ограничением: не чаще раза в 60 с, чтобы не нагружать блокировки).
- У элементов есть счётчик ссылок: элемент, который сейчас отправляется клиенту, не освобождается, даже если его тем временем вытеснили.

### Распределение (на клиенте)
- Серверы независимы. Клиентская библиотека хэширует ключ на сервер: изначально `hash(key) % N`, что при изменении N перекладывает почти всё; теперь **консистентное хэширование** (ketama), так что добавление узла переносит только ~1/N ключей ([[consistent-hashing]]).
- Репликации нет: упавший узел = промахи кэша по его ключам, пока клиент не уберёт его из кольца. mcrouter от Facebook добавляет пулы, репликацию и переключение при сбое как прокси.
- Memcached может использовать UDP для `get`, чтобы не держать состояние соединений на огромном масштабе ([[udp-in-depth]]).

### Memcached и Redis
| | Memcached | Redis |
|---|---|---|
| Типы | строки | строки, хэши, списки, множества, сортированные множества, потоки… |
| Потоки | многопоточный | один поток команд |
| Персистентность | нет | RDB, AOF |
| Репликация / кластер | только шардирование на клиенте | реплики, Sentinel, Cluster |
| Память | slab-аллокатор, LRU на класс | jemalloc, приближённые LRU/LFU |
| Применение сегодня | простые большие кэши с предсказуемыми значениями | почти всё остальное ([[redis-data-structures]]) |

## Пример
```bash
docker run -d --name mc -p 11211:11211 memcached:1.6 -m 256 -t 4
printf 'set user:42 0 300 5\r\nalice\r\nget user:42\r\nquit\r\n' | nc localhost 11211
# STORED / VALUE user:42 0 5 / alice / END
printf 'stats slabs\r\nquit\r\n' | nc localhost 11211   # chunk_size, used_chunks per class
```

```java
// Spring: cache-aside with spymemcached-style client
User u = (User) mc.get("user:" + id);
if (u == null) { u = repo.findById(id).orElseThrow(); mc.set("user:" + id, 300, u); }
```

## Подводные камни
- Значения намного больше или меньше запланированных размеров кусков: потеря памяти или окаменение; смотри `stats slabs`.
- Использовать как хранилище: каждый перезапуск или вытеснение теряет данные.
- Хэширование по модулю в клиенте: добавление одного сервера инвалидирует почти весь кэш (лавина запросов в базу).
- Горячие ключи: один ключ на одном узле забирает весь трафик; реплицируй его в клиенте или используй локальный уровень кэша ([[caching]]).
