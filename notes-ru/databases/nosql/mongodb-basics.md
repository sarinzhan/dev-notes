## Кратко
MongoDB хранит BSON-документы в коллекциях; каждый документ — самодостаточный агрегат (вложенные объекты и массивы) с `_id`, и запись одного документа всегда атомарна. Индексы работают как B-деревья по любому полю, включая поля внутри массивов; конвейер агрегации (aggregation pipeline) — язык запросов для всего, что выходит за рамки `find`. ACID-транзакции по нескольким документам существуют с 4.0 (replica set) и 4.2 (шардированный кластер), но стоят задержки и предназначены для исключений, а не для обычного пути. Выбирай её, когда данные естественно имеют форму документа, читаются в основном целиком, а схема меняется; выбирай Postgres, когда нужны join, ограничения или инварианты между сущностями ([[sql-vs-nosql-choosing]]).

## Основное

### Модель данных
- Документ = BSON-объект размером до 16 MB с типизированными полями (`ObjectId`, `Date`, `Decimal128`, массивы, вложенные документы). У коллекций нет принудительной схемы, если не добавить валидацию по JSON Schema (`validator` на коллекции); делай это для всего, что является системой-источником истины.
- Главное решение — **встраивать или ссылаться (embed vs reference)**. Встраивай то, что читается и пишется вместе и ограничено по размеру (строки заказа внутри заказа, адреса внутри клиента); ссылайся по id на то, что общее, неограниченное или обновляется независимо (товар, на который ссылается строка, события устройства). Неограниченные массивы (растущий массив `events` внутри документа) упираются в лимит 16 MB и заставляют каждое обновление перезаписывать документ.
- Join в реляционном смысле нет; `$lookup` в конвейере агрегации делает left outer join с другой коллекцией, выполняемый для каждого входного документа, поэтому он для небольших наборов результатов. Денормализуй поля, нужные при чтении, и смирись с тем, что они могут быть устаревшими ([[normalization-and-denormalization]]).
- `_id` по умолчанию — 12-байтовый `ObjectId` (метка времени + случайная часть + счётчик): примерно упорядочен по времени, что помогает локальности индекса так же, как UUID v7 ([[time-money-and-ids]]).

### CRUD и операторы обновления
- `find(filter, projection)` с операторами `$eq`, `$gt`, `$in`, `$regex`, `$elemMatch` для массивов, точечная нотация для вложенных полей (`"profile.type"`).
- Обновления — это **операторы изменения на месте**, а не замена всего документа: `$set`, `$inc`, `$push`, `$addToSet`, `$pull`, фильтры массивов (`arrayFilters`) для обновления одного элемента. `findOneAndUpdate` с фильтром по текущему состоянию — примитив оптимистической блокировки (`{_id, version: 3}` → `$set: {status}, $inc: {version: 1}`), который в большинстве случаев заменяет транзакцию.
- `upsert: true` вставляет документ, если ничего не найдено; вместе с уникальным индексом это идемпотентная запись ([[idempotency]]).

### Индексы
| Индекс | Применение |
|---|---|
| По одному полю / составной (`{status: 1, createdAt: -1}`) | те же правила левого префикса и сортировки, что в [[database-indexes]]; правило ESR: сначала поля равенства (Equality), затем поля сортировки (Sort), затем поля диапазона (Range) |
| Multikey | создаётся автоматически, когда поле — массив; одна запись на элемент; составной индекс может содержать не более одного поля-массива |
| Уникальный, частичный (`partialFilterExpression`), разреженный (sparse), TTL (`expireAfterSeconds`) | ограничения, горячие подмножества, автоматическое истечение сессий и токенов |
| Текстовый, 2dsphere, wildcard | базовый полнотекстовый поиск (один на коллекцию), гео-запросы, индексирование неизвестных динамических полей |
- `explain("executionStats")` показывает `COLLSCAN` против `IXSCAN`, `totalKeysExamined` против `nReturned`; большой разрыв — аналог `Rows Removed by Filter` ([[explain-analyze]]). С 4.2 индексы по умолчанию строятся в фоне.

### Конвейер агрегации
- Последовательность стадий: `$match` → `$group` → `$project` → `$sort` → `$limit`, плюс `$unwind` (массив в строки), `$lookup`, `$facet`, `$bucket`, `$merge` (записать результаты в коллекцию). Ставь `$match` и `$project` первыми, чтобы последующие стадии видели меньше документов меньшего размера, а `$match` мог использовать индекс.
- Каждая стадия ограничена 100 MB памяти, если нет `allowDiskUse: true`. Конвейеры заменяют и отчётный SQL, и большинство циклов на стороне приложения.

### Транзакции и согласованность
- **Replica set** (один primary, N secondary, автоматические выборы по Raft-подобному протоколу) — единица развёртывания; одиночный узел — только для разработки ([[leader-follower-replication]], [[raft-explained]]).
- **Write concern** `w: "majority"` ждёт большинства узлов и переживает переключение (failover); `w: 1` может потерять подтверждённые записи при отказе primary. **Read concern** `majority` возвращает только данные, закоммиченные большинством; `local` может вернуть данные, которые позже будут откачены. **Read preference** `secondaryPreferred` направляет чтения на реплики с задержкой ([[read-replicas-and-stale-reads]]).
- Транзакции по нескольким документам: `session.withTransaction(...)`, snapshot-изоляция, прерывание при конфликте записи (retry), время жизни по умолчанию 60 с, блокировки удерживаются на затронутых документах. Каждая транзакция держит снимок в кэше WiredTiger, поэтому длинные или многочисленные транзакции вредят. Моделируй агрегаты так, чтобы границей транзакции был один документ ([[aggregates-and-invariants]]).
- Шардирование: ключ шардирования, выбранный заранее (хешированный или диапазонный), определяет распределение; монотонный ключ вроде метки времени создаёт один горячий шард, ключ с малой кардинальностью создаёт гигантские чанки (jumbo chunks). Правила те же, что в [[sharding-strategies]].

### Spring Data MongoDB
- `MongoTemplate` для явных запросов и обновлений, `MongoRepository` для производных запросов; `@Document`, `@Indexed`, `@CompoundIndex`; `@Transactional` работает с `MongoTransactionManager`. Для денег отображай `Decimal128` в `BigDecimal`; `Double` по умолчанию для этого не подходит.

## Пример
```javascript
// Профиль абонента как один документ; настройки по операторам встроены, история — по ссылке
db.subscribers.insertOne({
  _id: ObjectId(),
  msisdn: "996555123456",
  status: "ACTIVE",
  profiles: [
    { iccid: "8999600000000000001", type: "prepaid", operator: "beeline_kg", activatedAt: ISODate() }
  ],
  version: 1,
  updatedAt: ISODate()
});

db.subscribers.createIndex({ msisdn: 1 }, { unique: true });
db.subscribers.createIndex({ "profiles.iccid": 1 });                         // multikey
db.subscribers.createIndex({ status: 1, updatedAt: -1 },
                           { partialFilterExpression: { status: "SUSPENDED" } });

// Оптимистическое обновление одного встроенного профиля, транзакция не нужна
db.subscribers.findOneAndUpdate(
  { msisdn: "996555123456", version: 1, "profiles.iccid": "8999600000000000001" },
  { $set: { "profiles.$.type": "postpaid", updatedAt: new Date() }, $inc: { version: 1 } },
  { returnDocument: "after" }
);

// Отчёт: активные профили по операторам
db.subscribers.aggregate([
  { $match: { status: "ACTIVE" } },
  { $unwind: "$profiles" },
  { $group: { _id: "$profiles.operator", n: { $sum: 1 } } },
  { $sort: { n: -1 } }
]);
```

## Подводные камни
- Моделировать реляционные данные как документы со ссылками повсюду, а потом нуждаться в `$lookup` при каждом чтении: медленнее join в Postgres и без целостности внешних ключей.
- В старых драйверах write concern по умолчанию был `w: 1`; подтверждённые записи исчезали при failover. Задавай `w: "majority"` в строке подключения.
- Неограниченные встроенные массивы (сообщения чата в документе беседы) растут до лимита 16 MB, и каждое добавление перезаписывает документ.
- Использовать транзакции по нескольким документам как обычный путь, потому что команда привыкла к `@Transactional`: пропускная способность рушится при конкуренции. Вместо этого перепроектируй агрегат.
- Гибкой схеме нужна та же дисциплина миграций, что и SQL: версионируй документы и мигрируй лениво при чтении или пачками ([[schema-migrations-flyway-liquibase]]); документное хранилище — всё равно выбор, который нужно обосновать, см. [[sql-vs-nosql-choosing]].
