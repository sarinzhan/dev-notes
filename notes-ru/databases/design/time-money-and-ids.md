## Кратко
Три столбца, которые есть в каждой схеме и которые большинство хотя бы раз делает неправильно. **Время**: храни моменты времени как `timestamptz` (UTC при передаче, преобразование при отображении), календарные факты (день рождения, дата начала тарифа в локальном календаре оператора) — как `date` или `timestamp` плюс имя часового пояса, и никогда не храни моменты как `timestamp` без пояса. **Деньги**: `numeric(19,4)` или минорные единицы в `bigint`, с валютой рядом; `BigDecimal` в Java, никогда `double`. **Идентификаторы**: `bigint` identity или последовательность для внутренних ключей, UUID v7, когда id генерируются вне базы или публикуются наружу, UUID v4 — только когда непредсказуемость важнее локальности индекса.

## Основное

### Время
| Тип Postgres | Хранит | Применение |
|---|---|---|
| `timestamptz` | момент времени (микросекунды от эпохи, нормализованные к UTC); `TimeZone` сессии влияет только на отображение и разбор | `created_at`, `expires_at`, время событий, всё, что произошло |
| `timestamp` (без часового пояса) | показание настенных часов без пояса; `2026-10-27 09:00` неоднозначно | избегать для моментов; допустимо для данных вида «правило по местному времени» в паре со столбцом пояса |
| `date` | календарный день | дни рождения, расчётные периоды, ключи партиционирования |
| `interval` | длительность с частями месяцы/дни/секунды | в столбцах редко; в запросах нормально |
| `tstzrange` | интервал моментов | периоды действия, с исключающим ограничением против пересечений |

- `timestamptz` не хранит пояс; он хранит UTC. Если пояс пользователя важен (показать активацию по времени Бишкека, запустить задачу в 09:00 по местному), храни имя пояса IANA (`Asia/Bishkek`) в отдельном столбце; смещения вроде `+06:00` уплывают вместе с правилами перехода на летнее время и политикой.
- Маппинг в Java: `Instant` или `OffsetDateTime` ↔ `timestamptz`; `LocalDate` ↔ `date`; `LocalDateTime` ↔ `timestamp`; `ZonedDateTime` — это `timestamptz` плюс отдельный столбец пояса. Hibernate 6 по умолчанию отображает `Instant` на `timestamptz` (`hibernate.timezone.default_storage = NORMALIZE_UTC`); запускай JVM в UTC (`-Duser.timezone=UTC`) и JDBC-сессию в UTC, чтобы ни один слой молча не преобразовывал значения.
- Сравнивай и вычисляй в UTC; отображай в поясе пользователя на краю. `date_trunc('day', created_at AT TIME ZONE 'Asia/Bishkek')` для отчётов «по местным дням».
- `created_at` не уникален, а часы у pod различаются ([[time-and-clocks]]): упорядочивай и делай пагинацию по `(created_at, id)`.
- `now()` — время начала транзакции, `clock_timestamp()` — настенные часы; в длинной транзакции они различаются.

### Деньги
- Плавающая точка не может точно представить 0.1; `0.1 + 0.2 != 0.3`, а суммы тысяч строк уплывают ([[numbers-bits-and-floating-point]]). Никогда не используй `double`/`float`/`real`/`double precision` для сумм.
- Два правильных представления:
  - `numeric(19, 4)` (произвольная точность, точно) с `BigDecimal` в Java и `RoundingMode.HALF_EVEN` (банковское округление) или тем режимом, который предписывает регулирование в точке округления. Четыре знака после запятой дают точность для промежуточных вычислений; итоговое округление определяет экспонента валюты (2 для KGS/USD, 0 для JPY, 3 для KWD).
  - **Минорные единицы** в `bigint` (`amount_minor = 12550` для 125.50) с `long` в Java: быстрее всего, никаких сюрпризов округления в хранилище, преобразование только на границе. Стандарт в процессинге карт и сообщениях ISO 8583 ([[emv-card-processing]]).
- Всегда храни **валюту** (`char(3)` по ISO 4217) рядом с суммой; объект-значение `Money(amount, currency)` в домене откажется складывать KGS с USD ([[value-objects-and-entities]]). Курсы валют — `numeric(19, 8)` или больше, с меткой времени курса.
- Вычисляй в `BigDecimal` с `MathContext.DECIMAL128`, округляй один раз в конце. Таблицы бухгалтерской книги (ledger) только на добавление: вставляй проводки и выводи баланс ([[design-payment-processing]]).

### Идентификаторы
| Генератор | Размер | Упорядочен | Кто генерирует | Применение |
|---|---|---|---|---|
| `bigint GENERATED ALWAYS AS IDENTITY` / последовательность | 8 байт | да | база данных | внутренние первичные ключи, столбцы FK, лучшая локальность индекса; `serial` — устаревшая форма |
| UUID v4 (случайный) | 16 байт | нет | кто угодно | непредсказуемые публичные id, токены; случайные вставки разбрасываются по B-дереву и раздувают его |
| UUID v7 (RFC 9562, 2024) | 16 байт | да (префикс из метки времени в миллисекундах + случайная часть) | кто угодно | id, генерируемые клиентами или до вставки (outbox, саги, идемпотентность), объединяемые между шардами; локальность почти как у последовательности |
| ULID / KSUID / Snowflake | 16 / 20 / 8 байт | да | приложение | та же роль, что у v7; Snowflake требует id воркера |
- Публикация `bigint` id наружу раскрывает объёмы (сегодня заказ 1 000 001, завтра 1 000 500) и провоцирует перебор; публикуй UUID или непрозрачный публичный id и держи `bigint` внутри либо используй UUID v7 для обоих.
- В последовательностях бывают пропуски (откаты, кэширование, падения); никогда не рассчитывай на их непрерывность.
- В Postgres 17 нет встроенной `uuidv7()` (она появится в 18); генерируй v7 в Java (в `java.util.UUID` нет фабрики для v7; используй небольшую библиотеку) или через расширение `pg_uuidv7`. Храни в нативном типе `uuid`, никогда в `varchar(36)`.
- Естественные ключи (MSISDN, ICCID, email) — это уникальные ограничения, а не первичные ключи: они меняются или переназначаются. Суррогатный id плюс `UNIQUE` на естественном ключе.
- Ключи партиционирования и упорядоченность v7: [[postgres-partitioning]]; случайные ключи и B-деревья: [[database-indexes]].

## Пример
```sql
-- V9__payments.sql
CREATE TABLE payment (
    id              uuid        PRIMARY KEY,            -- UUID v7 из приложения
    order_id        bigint      NOT NULL REFERENCES esim_order(id),
    amount_minor    bigint      NOT NULL CHECK (amount_minor > 0),
    currency        char(3)     NOT NULL CHECK (currency ~ '^[A-Z]{3}$'),
    fx_rate         numeric(19, 8),
    created_at      timestamptz NOT NULL DEFAULT now(),
    captured_at     timestamptz,
    customer_tz     text        NOT NULL DEFAULT 'Asia/Bishkek',
    UNIQUE (order_id, currency)
);
```
```java
public record Money(long minor, Currency currency) {
    public BigDecimal major() {
        return BigDecimal.valueOf(minor, currency.getDefaultFractionDigits());
    }
    public Money plus(Money other) {
        if (!currency.equals(other.currency)) throw new IllegalArgumentException("currency mismatch");
        return new Money(Math.addExact(minor, other.minor), currency);
    }
    public static Money of(BigDecimal major, Currency currency) {
        return new Money(major.setScale(currency.getDefaultFractionDigits(), RoundingMode.HALF_EVEN)
                              .movePointRight(currency.getDefaultFractionDigits()).longValueExact(), currency);
    }
}

@Entity class Payment {
    @Id UUID id = UuidV7.generate();                 // упорядочен по времени, генерируется до вставки
    long amountMinor; String currency;
    Instant createdAt = Instant.now();               // timestamptz
    String customerTz;                               // имя IANA, для отображения и отчётов по местным дням
}
```

## Подводные камни
- `timestamp` без пояса плюс JVM в `Asia/Bishkek` и база в UTC: каждое значение сдвигается на шесть часов при записи или чтении, и это обнаруживается через несколько месяцев в отчёте.
- `double` для денег, «потому что это всего лишь прототип»: прототип уходит в прод, и сверка расходится на один тыйын на каждую тысячу строк.
- Первичные ключи UUID v4 в таблице на 100 миллионов строк: случайные вставки затрагивают случайные листовые страницы, доля попаданий в кэш падает, раздувание индекса удваивается ([[postgres-vacuum-and-bloat]]).
- `varchar` для UUID: 37 байт вместо 16 и сравнение строк вместо сравнения целых чисел в каждом индексе.
- Связанные заметки: [[data-modeling-for-services]] — остальные стандартные столбцы, [[numbers-bits-and-floating-point]] — почему числа с плавающей точкой подводят, [[idempotency]] — id, сгенерированные клиентом, как ключи идемпотентности.
