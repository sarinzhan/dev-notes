## Кратко
Изменения схемы — это версионированные файлы в репозитории, которые применяются по порядку инструментом, записывающим выполненное в таблицу истории (`flyway_schema_history`, `databasechangelog`). Flyway — это SQL-файлы с соглашением об именах; Liquibase — наборы изменений (changesets) в XML/YAML/SQL с поддержкой отката и абстракцией от базы данных. Более трудная задача — не инструмент, а **работа без простоя** (zero-downtime): во время rolling deploy старый и новый код работают с одной и той же схемой, поэтому каждое изменение должно быть обратно совместимым на протяжении одного релиза. Паттерн **expand/contract** (расширение/сжатие: добавить новое, перенести данные, переключить код, удалить старое в следующем релизе) плюс `lock_timeout` и `CONCURRENTLY` покрывают почти все случаи.

## Основное

### Flyway против Liquibase
| | Flyway | Liquibase |
|---|---|---|
| Формат | `V3__add_eid.sql`, обычный SQL (возможны миграции на Java) | changesets в YAML/XML/JSON/SQL с `id`, `author`, предусловиями |
| Порядок | номер версии; повторяемые скрипты `R__` (представления, функции) перезапускаются при изменении контрольной суммы | порядок файлов в changelog; `runOnChange`, `runAlways` |
| Откат | платная функция (`undo`); на практике в community-версии — исправления только вперёд | блок `rollback` в каждом changeset, `rollback-count` |
| Переносимость между БД | нет, пиши SQL для Postgres | абстрактные типы изменений (`addColumn`) или сырой SQL |
| Spring Boot | стартер, запускается при старте до JPA; `spring.flyway.*` | стартер, `spring.liquibase.*` |
- Оба блокируют таблицу истории, чтобы параллельные pod не выполнили одну и ту же миграцию дважды (Flyway использует `SELECT ... FOR UPDATE` на своей строке истории; Liquibase — строку `databasechangeloglock`, которая может застрять после падения и требует ручного освобождения).
- Никогда не редактируй применённую миграцию: несовпадение контрольной суммы роняет старт (`flyway repair` — только для настоящей ошибки). Пиши новую.
- `ddl-auto: validate` с JPA во всех окружениях выше локального: Hibernate проверяет маппинг на соответствие мигрированной схеме и никогда не генерирует DDL ([[jpa-entities-and-relationships]]).

### Запуск миграций
- При старте приложения — нормально для небольших сервисов с одной базой; первый pod применяет, остальные ждут на блокировке. Проблемы: медленная миграция данных блокирует readiness-пробу и rollout; неудачная миграция оставляет pod в crash loop. Для больших изменений запускай миграции отдельной задачей (`Job` в Kubernetes или init-шаг в пайплайне) до rollout, с `spring.flyway.enabled=false` в приложении.
- Отделяй миграции **схемы** (быстрые, DDL) от миграций **данных** (медленные, пакетные, возобновляемые). Заполнению 50 миллионов строк место в пакетной задаче с `LIMIT` и commit на каждый пакет, а не в одном `UPDATE` внутри транзакции миграции.
- Миграции запускаются с выставленным `lock_timeout` (`SET lock_timeout = '5s';` первой строкой или `spring.flyway.init-sql`), чтобы DDL, ждущий за длинной транзакцией, падал и повторялся, а не выстраивал в очередь все запросы сервиса ([[postgres-locks]]).
- Каждая миграция Flyway по умолчанию выполняется в одной транзакции; `CREATE INDEX CONCURRENTLY` так не может, поэтому такой файл получает первой строкой `-- flyway:executeInTransaction=false` и больше ничего не содержит.

### Expand/contract для работы без простоя
Во время rolling deploy версии N и N+1 работают бок о бок; схема должна работать для обеих.
| Изменение | Опасный способ | Безопасная последовательность |
|---|---|---|
| Переименовать столбец | `ALTER TABLE ... RENAME` сразу ломает старый код | 1 добавить новый столбец; 2 код пишет в оба, читает новый с запасным вариантом; 3 заполнить пакетами; 4 код читает/пишет только новый; 5 удалить старый |
| Добавить столбец `NOT NULL` | `ADD COLUMN x NOT NULL` падает на существующих строках; волатильный `DEFAULT` переписывает таблицу | добавить nullable (в PG 11+ константное значение по умолчанию меняет только метаданные); заполнить; `ADD CONSTRAINT ... CHECK (x IS NOT NULL) NOT VALID`; `VALIDATE CONSTRAINT` (без долгой блокировки); затем `SET NOT NULL` (PG 12+ использует провалидированную проверку) |
| Сменить тип (`int` → `bigint`) | `ALTER COLUMN TYPE` переписывает таблицу под `ACCESS EXCLUSIVE` | новый столбец + двойная запись + заполнение + подмена, или окно обслуживания для небольших таблиц |
| Добавить индекс | `CREATE INDEX` блокирует запись | `CREATE INDEX CONCURRENTLY`, после сбоя проверить на `INVALID` ([[postgres-indexes]]) |
| Добавить внешний ключ | проверяет все строки под блокировкой | `ADD CONSTRAINT ... NOT VALID`, затем `VALIDATE CONSTRAINT` |
| Удалить столбец | старые pod всё ещё его выбирают | сначала выкатить код, который перестаёт его использовать; удалить в следующем релизе; JPA-сущности не должны его маппить |
| Добавить значение enum | `ALTER TYPE ... ADD VALUE` до PG 12 нельзя было выполнить в транзакции | использовать `text` + `CHECK` или добавить значение в отдельной нетранзакционной миграции |
- Шаг contract — это **отдельный релиз** после того, как релиз expand полностью выкачен и подтверждён. Список «на удаление» в репозитории не даёт забыть код двойной записи.
- Обратная совместимость касается и событий и API, которые несут переименованное поле ([[message-schema-evolution]]).

### Тестирование миграций
- Прогоняй всю цепочку миграций на настоящем Postgres в CI с [[testcontainers]]; Hibernate `validate` при старте ловит расхождение маппинга. Когда изменение рискованное, тестируй шаг expand с *предыдущей* версией приложения, работающей на новой схеме.
- Держи похожий на прод набор данных (анонимизированный дамп), чтобы замерять время миграций данных; заполнение, которое занимает 2 с на 10 000 строк, займёт час на 100 миллионах и будет всё это время держать блокировки, если написано одним оператором.

## Пример
```sql
-- V14__add_eid_to_sim_expand.sql  (релиз N: expand)
SET lock_timeout = '5s';
ALTER TABLE sim ADD COLUMN eid text;                     -- nullable, мгновенно
ALTER TABLE sim ADD CONSTRAINT sim_eid_format
    CHECK (eid ~ '^[0-9]{32}$') NOT VALID;               -- проверяется только для новых строк, без сканирования
```
```sql
-- V15__sim_eid_unique_index.sql  (релиз N, отдельный файл: без транзакции)
-- flyway:executeInTransaction=false
CREATE UNIQUE INDEX CONCURRENTLY sim_eid_uq ON sim (eid) WHERE eid IS NOT NULL;
```
```java
// Заполнение как пакетная задача, а не миграция: возобновляемо, commit на каждый пакет, без долгой блокировки
@Transactional
public int backfillBatch() {
    return jdbc.update("""
        UPDATE sim SET eid = attrs->>'eid'
        WHERE id IN (SELECT id FROM sim WHERE eid IS NULL AND attrs ? 'eid'
                     ORDER BY id LIMIT 5000 FOR UPDATE SKIP LOCKED)
        """);
}
```
```sql
-- V18__sim_eid_contract.sql  (релиз N+1: contract, после того как все pod пишут eid)
SET lock_timeout = '5s';
ALTER TABLE sim VALIDATE CONSTRAINT sim_eid_format;      -- SHARE UPDATE EXCLUSIVE, запись продолжается
ALTER TABLE sim ALTER COLUMN eid SET NOT NULL;           -- требует, чтобы у каждой строки был eid
ALTER TABLE sim DROP COLUMN legacy_eid;
```

## Подводные камни
- `ALTER TABLE ... ADD COLUMN ... DEFAULT now()`: волатильное значение по умолчанию, полная перезапись таблицы под эксклюзивной блокировкой; константные значения по умолчанию бесплатны начиная с PG 11, волатильные — нет.
- Миграция, которая смешивает DDL и `UPDATE` на миллионы строк: блокировка DDL держится всё время обновления, и сервис останавливается.
- Запуск миграций из каждого pod при старте с медленной миграцией: readiness-проба истекает, Kubernetes перезапускает pod посреди миграции, строка блокировки Liquibase остаётся заблокированной.
- Удаление столбца, пока предыдущая версия ещё получает трафик или пока список `SELECT` в Hibernate его упоминает: `column does not exist` на всё время rollout.
- Механика блокировок за каждым DDL: [[postgres-locks]]; соглашения моделирования, которые реализуют эти миграции: [[data-modeling-for-services]]; безопасность релизов: [[database-scaling-path]] — когда изменения схемы становятся изменениями шардирования.
