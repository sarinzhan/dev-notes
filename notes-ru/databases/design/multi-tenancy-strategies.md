## Кратко
Мультиарендный (multi-tenant) сервис хранит данные многих клиентов (арендаторов, tenants: операторов, партнёров, компаний) в одном развёртывании. Изолировать их можно тремя способами: **общая схема** со столбцом `tenant_id` в каждой таблице (дешевле всего, масштабируется до миллионов арендаторов, изоляция ровно настолько хороша, насколько хороши твои `WHERE`, поэтому обеспечивай её через row-level security), **схема на арендатора** внутри одной базы (чистое разделение, миграции на каждого арендатора, перестаёт работать после нескольких сотен арендаторов) и **база данных на арендатора** (самая сильная изоляция, независимые резервные копии и масштабирование, самые высокие операционные расходы, нужна для регулируемых или очень крупных арендаторов). Большинство систем начинают с общей схемы и выносят отдельных арендаторов по мере роста; id арендатора нужно определять один раз на запрос и никогда не доверять ему из тела запроса.

## Основное

### Сравнение
| | Общая схема (столбец `tenant_id`) | Схема на арендатора | База данных на арендатора |
|---|---|---|---|
| Изоляция | логическая, через предикат запроса (плюс RLS) | пространство имён; возможен отдельный пользователь БД на схему | физическая; отдельные учётные данные, резервные копии, ключи шифрования |
| Сколько арендаторов | миллионы | от десятков до сотен (разбухание каталога, время `pg_dump`, autovacuum на таблицу × арендаторов) | от десятков до сотен (пулы соединений на каждую БД, операционные издержки) |
| Миграции | один прогон | по прогону на схему, нужно обрабатывать частичный отказ | по прогону на базу, версии расходятся |
| Шумный сосед (noisy neighbour) | общие таблицы, индексы, пул; один крупный арендатор мешает всем | общие ресурсы инстанса | полностью раздельно, можно перенести в отдельный кластер |
| Запросы между арендаторами (аналитика, админка) | тривиально | `UNION ALL` по схемам | экспорт в хранилище данных |
| Настройка под арендатора | `jsonb` или feature-флаги | возможны свои столбцы/таблицы | что угодно |
| Стоимость на арендатора | самая низкая | низкая | высокая (минимальный размер инстанса, пул, мониторинг) |
| Пул соединений | один пул | один пул с `SET search_path` на каждый запрос (`search_path` действует на сессию: нужно сбрасывать, ломается с PgBouncer в режиме transaction) | пул на арендатора или динамическая маршрутизация `DataSource` |

### Общая схема, сделанная безопасно
- `tenant_id` — `NOT NULL` в каждой таблице, принадлежащей арендатору, и **первый столбец каждого составного индекса и уникального ограничения** (`UNIQUE (tenant_id, external_ref)`), что позже делает его естественным ключом партиционирования и шардирования ([[postgres-partitioning]], [[sharding-strategies]]).
- Определяй арендатора по аутентифицированному субъекту (claim в JWT, API-ключ, поддомен), сохраняй в контексте запроса и применяй в слое данных автоматически: Hibernate `@TenantId` (Hibernate 6) или фильтр, specification в Spring Data или `WHERE tenant_id = :tenant`, добавляемый базовым классом репозитория. Никогда не читай его из тела запроса или query-параметра ([[authentication-vs-authorization]]).
- **Row-level security** (RLS, безопасность на уровне строк) как страховочная сетка: `ALTER TABLE orders ENABLE ROW LEVEL SECURITY` с политикой `USING (tenant_id = current_setting('app.tenant_id')::bigint)`, а приложение выполняет `SET LOCAL app.tenant_id = ...` в начале каждой транзакции. Тогда забытый `WHERE` вернёт пустой результат, а не строки другого арендатора. RLS добавляет предикат в каждый план; индекс с `tenant_id` первым столбцом делает это дешёвым. Роль приложения не должна быть владельцем таблицы или суперпользователем (они обходят RLS, если не указан `FORCE ROW LEVEL SECURITY`).
- Внешние ключи должны включать `tenant_id` (`FOREIGN KEY (tenant_id, customer_id) REFERENCES customers (tenant_id, id)`), чтобы строка не могла ссылаться на родителя другого арендатора.

### Схема на арендатора
- `CREATE SCHEMA tenant_42` с одинаковыми таблицами; запрос выставляет `search_path`, или соединение привязано к схеме. Hibernate поддерживает `MultiTenantConnectionProvider` со стратегией `SCHEMA`; Flyway запускается в цикле с `schemas`, заданным для каждого арендатора.
- Подходит для десятков корпоративных арендаторов, которым нужна своя граница данных без стоимости отдельной базы для каждого, или для унаследованных настроек под конкретного клиента. Следи за каталогом: 300 арендаторов × 200 таблиц × 5 индексов — это 300 000 отношений; `pg_dump`, планирование autovacuum и кэш каталога в планировщике — всё замедляется.

### База данных на арендатора
- Необходима, когда этого требуют договоры или регулирование (локализация данных, отдельные ключи шифрования, резервное копирование под управлением клиента) или когда нагрузке одного арендатора всё равно нужен свой кластер.
- Маршрутизация: `AbstractRoutingDataSource` с ключом по арендатору и пулом HikariCP на каждую базу (число пулов × размер пула соединений, см. [[hikaricp-pool-sizing]]) или каталог строк подключения, загружаемый при старте, с ленивым созданием и вытеснением пулов. Миграции становятся операцией над целым парком баз с версией каждой базы, записанной централизованно.
- Часто комбинируют: общая схема для длинного хвоста, выделенные базы для немногих крупных или регулируемых арендаторов, с одним и тем же кодом приложения за слоем маршрутизации («гибридное» развёртывание или развёртывание на ячейках, cell-based, [[multi-region-basics]]).

### Сквозные вопросы
- Кэшам, топикам Kafka и поисковым индексам нужен арендатор в ключе (`cache:tenant:42:tariffs`, индекс на арендатора или keyword-поле `tenant`, [[elasticsearch-basics]]); общий кэш без арендатора в ключе — самый простой способ допустить утечку данных.
- Rate limit, квоты и SLO на арендатора; пакетная задача одного арендатора не должна занимать весь пул потоков или пул соединений (bulkhead, [[rate-limiting]]).
- Фоновые задачи явно перебирают арендаторов и выставляют контекст для каждого; планировщик без контекста арендатора — как раз то место, где тебя спасает RLS.
- Тестирование: каждый тест репозитория запускается с двумя арендаторами и проверяет, что данные другого арендатора не видны.

## Пример
```sql
-- V7__orders_tenant_rls.sql: общая схема с row-level security как страховочной сеткой
ALTER TABLE orders ADD COLUMN tenant_id bigint NOT NULL;
CREATE INDEX CONCURRENTLY orders_tenant_created_idx ON orders (tenant_id, created_at DESC);
ALTER TABLE orders ADD CONSTRAINT orders_tenant_ref_uq UNIQUE (tenant_id, external_ref);

ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
ALTER TABLE orders FORCE  ROW LEVEL SECURITY;          -- применяется и к владельцу
CREATE POLICY orders_tenant_isolation ON orders
    USING (tenant_id = current_setting('app.tenant_id', true)::bigint)
    WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::bigint);
GRANT SELECT, INSERT, UPDATE, DELETE ON orders TO app_rw;   -- app_rw не владелец
```
```java
// Выставить арендатора на соединении в начале каждой транзакции.
// Аспект выполняется внутри перехватчика транзакций (ниже приоритет = позже), поэтому
// SET LOCAL попадает на то же соединение, которое будут использовать вызовы репозитория.
@Aspect
@Component
@Order(Ordered.LOWEST_PRECEDENCE - 10)
@RequiredArgsConstructor
public class TenantTransactionAspect {
    private final JdbcTemplate jdbc;

    @Before("@annotation(org.springframework.transaction.annotation.Transactional)"
          + " || @within(org.springframework.transaction.annotation.Transactional)")
    public void applyTenant() {
        long tenantId = TenantContext.required();                  // из JWT, выставляется фильтром
        jdbc.execute("SET LOCAL app.tenant_id = " + tenantId);     // SET LOCAL заканчивается вместе с транзакцией
    }
}
```
С `SET LOCAL` настройка исчезает при commit, поэтому соединение из пула никогда не переносит арендатора в следующий запрос; запрос без `WHERE tenant_id` всё равно возвращает строки только этого арендатора.

## Подводные камни
- `SET` вместо `SET LOCAL` на соединении из пула: следующий запрос на этом соединении наследует предыдущего арендатора.
- Уникальные ограничения без `tenant_id`: `external_ref = 'INV-1'` арендатора A блокирует счёт арендатора B.
- Схема на арендатора с PgBouncer в режиме transaction: `search_path`, выставленный на одном серверном соединении, действует для того, кто получит его следующим.
- Роль приложения с правами суперпользователя или владельца таблицы молча обходит RLS; страховочной сетки на самом деле не было.
- Связанные заметки: [[data-modeling-for-services]] — базовые соглашения о схеме, [[sharding-strategies]] — когда `tenant_id` становится ключом шардирования, [[api-security-checklist]] — определение арендатора на краю.
