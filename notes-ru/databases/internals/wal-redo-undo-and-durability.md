## Кратко
Надёжность (durability) означает, что подтверждённая транзакция переживает сбой. Записывать каждую изменённую страницу на её место в файлах данных при коммите медленно (случайный IO, целые страницы ради нескольких байт), поэтому базы сначала пишут **журнал упреждающей записи (WAL)**: последовательную запись каждого изменения только в конец. Коммит = запись WAL сброшена через `fsync`; страницы данных пишутся позже контрольной точкой. После сбоя база **повторяет** (redo) журнал с последней контрольной точки. Журнал **undo** (InnoDB, Oracle) хранит старые версии, чтобы откатить неподтверждённую работу и обслуживать согласованное чтение; Postgres вместо этого держит старые версии в heap.

## Основное
### Техники обеспечения надёжности
- **WAL**: записать изменение в журнал, сбросить журнал, затем менять страницы в памяти. WAL в Postgres, redo log в InnoDB, журнал транзакций в SQL Server.
- **Асинхронный снимок**: периодически записывать весь набор данных в фоне (Redis RDB). Дёшево, но теряется всё, что было после последнего снимка.
- **Файл только для дописывания** (Redis AOF): журналировать каждую команду; при старте проигрывать. Та же идея, что WAL, на уровне команд ([[redis-patterns-and-persistence]]).
- Все они зависят от `fsync`: страничный кэш ОС держит записи в RAM ([[storage-management]]), и возврат из `write()` **не** означает, что данные на диске. Гарантию даёт только `fsync`/`fdatasync`/`O_DIRECT`+`O_DSYNC`, и это медленно (миллисекунды на HDD, десятки–сотни мкс на SSD с защитой от потери питания).

### Зачем журнал
- Файлы данных организованы для чтения (страницы heap, B+-деревья); изменение затрагивает случайные страницы. Записать их все при коммите = много случайных IO, и запись страницы может оборваться посередине при сбое.
- WAL **последовательный** и компактный: одно дописывание на изменение, один сброс на коммит. Групповой коммит (group commit) сбрасывает много транзакций одним `fsync`.
- Изменённые в памяти страницы — **грязные** (dirty), они пишутся позже в фоне; WAL делает это безопасным.
- WAL — это ещё и поток репликации: реплики его проигрывают ([[postgres-replication-and-failover]]), а CDC-инструменты (Debezium) его читают.

### Redo
- Записи redo описывают, как заново применить изменение («на странице 42 в слоте 7 записать байты ...»). При восстановлении база начинает с последней **контрольной точки** (checkpoint) и проигрывает каждую запись, эффект которой мог не попасть в файлы данных.
- **Контрольная точка**: сбросить все грязные страницы до некоторого момента и отметить этот момент в журнале. Всё до него больше не нужно для восстановления после сбоя, поэтому старый WAL можно переиспользовать. Частые контрольные точки = быстрее восстановление, больше IO; редкие = меньше IO, дольше восстановление и больше WAL на диске.
- **Запись полных страниц** (full-page writes, Postgres): первое изменение страницы после контрольной точки журналирует всю страницу, чтобы восстановить наполовину записанную («порванную») страницу. InnoDB для того же использует doublewrite buffer.

### Undo
- Записи undo описывают, как отменить изменение («в слоте 7 раньше было ...»). Используются, чтобы:
  - откатить прерванную транзакцию, а после сбоя откатить транзакции, которые так и не закоммитились;
  - отдать MVCC-читателям старую версию строки (InnoDB строит старые версии из undo log; Oracle так же через сегменты отката).
- Долгая транзакция удерживает undo, поэтому журнал undo растёт, а читатели проходят длинные цепочки версий: одна из причин, почему долгие транзакции вредят.
- **В Postgres нет журнала undo**: UPDATE пишет новый кортеж и оставляет старый в heap, помеченный идентификаторами транзакций. Откат бесплатен (новый кортеж просто невидим), но мёртвым кортежам нужен VACUUM ([[postgres-vacuum-and-bloat]]).

### Усиление записи
- Одно логическое изменение может вызвать много физических записей: запись WAL, образ полной страницы после контрольной точки, страницу heap, каждую страницу индекса, копию на реплике, а на SSD ещё и собственные перезаписи FTL ([[storage-management]]).
- Postgres: не-HOT обновление пишет новый кортеж плюс запись в каждом индексе плюс WAL для каждого ([[primary-vs-secondary-indexes]]). LSM-движки: compaction переписывает данные несколько раз ([[database-engines]]).
- Как уменьшить: меньше индексов, HOT-дружелюбные обновления (fillfactor), пакетная запись, `wal_compression`, не обновлять неизменившиеся колонки.

### Настройки надёжности
| Настройка | Эффект |
|---|---|
| Postgres `synchronous_commit = on` (по умолчанию) | коммит ждёт локального сброса WAL |
| `synchronous_commit = off` | коммит возвращается до сброса; сбой может потерять последние ~3× `wal_writer_delay` (≈600 мс) коммитов, но никогда не портит данные |
| `fsync = off` | никогда в проде: сбой может испортить кластер |
| InnoDB `innodb_flush_log_at_trx_commit = 1` | сброс redo на каждом коммите (надёжно) |
| `= 2` | запись в ОС при коммите, сброс раз в секунду: переживает падение mysqld, но не ОС |
| `= 0` | запись и сброс раз в секунду |
| Redis `appendfsync always / everysec / no` | на каждую команду / раз в секунду / когда решит ОС |

## Пример
```sql
-- Postgres: see WAL being produced by a statement
SELECT pg_current_wal_lsn();                 -- e.g. 0/3A2B1C8
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
SELECT pg_current_wal_lsn();                 -- moved forward

-- trade a little durability for throughput in one session only (e.g. bulk import of re-creatable data)
SET synchronous_commit = off;

-- checkpoint timing
SHOW checkpoint_timeout;   -- 5min
SHOW max_wal_size;         -- 1GB: a checkpoint is also forced when this much WAL accumulates
```

## Подводные камни
- Доверять `write()` или диску с энергозависимым кэшем записи без защиты от потери питания: история «fsyncgate» ([[storage-management]]).
- Отключать `fsync` или full-page writes ради скорости и получить испорченную базу после отключения питания.
- Долгие транзакции: они удерживают undo (InnoDB) или мёртвые кортежи (Postgres) и тормозят всех.
- Слишком маленький `max_wal_size`: контрольные точки каждые несколько секунд, огромные всплески IO из-за full-page writes.
