## Кратко
**Строковое хранилище** (row store) держит все колонки строки рядом в одной странице, поэтому прочитать или записать целую строку — это одно обращение к странице: идеально для OLTP (`SELECT * FROM orders WHERE id = ?`). **Колоночное хранилище** (column store) держит каждую колонку в своей серии страниц, поэтому агрегат по одной колонке читает только её и хорошо её сжимает: идеально для OLAP (`SELECT sum(amount) FROM orders`). Каждое медленно на чужой задаче. Postgres и MySQL — строковые; ClickHouse, Redshift, BigQuery, Snowflake, DuckDB — колоночные.

## Основное
### Строковое хранение (row store)
- Строки хранятся одна за другой: `1,John,Smith,101,555-1234,1000 | 2,Rick,...`. Страница содержит несколько целых строк.
- **Точечный поиск / чтение целой строки**: найти строку (индексом или сканированием), и все её колонки уже в прочитанной странице.
- **Агрегат по одной колонке** (`SUM(salary)`): нужно прочитать каждую страницу, потому что в каждой лежит кусочек `salary`, и вместе с ним тащатся остальные колонки. 1 млн строк × 100 байт = вся таблица ради 8 байт на строку.
- Запись дешёвая: одна строка = одно место записи.
- С индексом по колонке фильтра `WHERE id = 7` превращается в пару чтений страниц; без него полное сканирование останавливается раньше, только если строка найдена и в запросе есть `LIMIT`.

### Колоночное хранение (column store)
- Каждая колонка лежит отдельно: `id: 1,2,3,...`, `first_name: John,Rick,...`, `salary: 1000,2000,...`. Значения колонки сопоставляются со строкой по позиции (row id).
- **Агрегат** (`SUM(salary)`): читаются только страницы `salary`. Значения одного типа лежат вместе, поэтому отлично сжимаются (run-length, словарное, дельта-кодирование), и CPU обрабатывает их векторами.
- **Фильтр + несколько колонок** (`SELECT first, last WHERE ssn = 666`): просканировать колонку `ssn`, найти row id, затем прыгнуть в `first` и `last` на эти позиции. Стоимость растёт с числом запрошенных колонок.
- **`SELECT *` одной строки**: одно чтение на колонку, столько IO, сколько колонок. Ужасно.
- **Запись**: вставка одной строки затрагивает файл каждой колонки; обновления и удаления дорогие. Колоночные базы вставляют пачками и обычно работают в режиме «в основном дописывание».

### Сравнение
| | Строковое | Колоночное |
|---|---|---|
| Лучше всего для | OLTP: много мелких чтений/записей целых строк | OLAP: сканирования и агрегаты по немногим колонкам |
| `SELECT *` одной строки | 1 страница | 1 чтение на колонку |
| `SUM(col)` по всем строкам | читает всю таблицу | читает одну колонку, сжатую |
| Запись / обновление | дёшево | дорого, пачками |
| Сжатие | умеренное | высокое (серии одного типа) |
| Фильтры по нескольким колонкам | эффективно | каждая колонка читается отдельно |
| Примеры | Postgres, MySQL, Oracle, SQL Server | ClickHouse, Redshift, BigQuery, Snowflake, DuckDB, файлы Parquet |

### Почему `SELECT *` вредит даже в строковом хранилище
- Он читает TOAST-колонки (вынесенные из строки), которые не нужны: каждое широкое значение `text`/`jsonb` — это лишние чтения страниц и распаковка ([[how-tables-and-indexes-are-stored]]).
- Он убивает **index-only scan**: если индекс покрывает `id, status`, а запрошен `*`, базе приходится ходить в heap за каждой строкой.
- Больше байт сериализовать, передать по сети и десериализовать: протокол ([[database-wire-protocols]]) несёт каждую колонку, клиент выделяет объекты под каждую.
- Он молча ломается при добавлении колонки (маппинг ORM, `INSERT ... SELECT *`).
- В колоночной базе он хуже всего: каждая колонка = отдельное чтение.

### Смешанные подходы
- Расширения Postgres добавляют колоночные таблицы (Citus columnar, Hydra); в SQL Server есть columnstore-индексы; MySQL HeatWave; Oracle In-Memory column store. Частый шаблон: OLTP в строковой базе, изменения стримятся (CDC) в колоночную для аналитики.
- Wide-column хранилища (Cassandra) — **не** колоночные: это строковые хранилища с гибким набором колонок в строке ([[column-and-wide-column-stores]]).

## Пример
```sql
-- OLTP on Postgres (row store): one page via the primary key index
SELECT * FROM orders WHERE id = 1001;

-- OLAP: on a row store this reads every column of every row
SELECT date_trunc('day', created_at) AS day, sum(amount)
FROM orders WHERE created_at >= now() - interval '30 days'
GROUP BY 1;

-- the same query on ClickHouse (column store) reads only created_at and amount
SELECT toDate(created_at) AS day, sum(amount)
FROM orders WHERE created_at >= now() - INTERVAL 30 DAY
GROUP BY day;
```

## Подводные камни
- Строить дашборды с агрегатами по всей таблице на продовой OLTP-базе; уноси их на реплику или в колоночную базу.
- Использовать колоночную базу под нагрузку из обновлений отдельных строк (смена статусов, счётчики): каждое обновление переписывает части колонок.
- `SELECT *` в коде приложения: выбирай только нужные колонки; это ещё и включает покрывающие индексы.
- Путать «wide-column» (Cassandra) с «колоночным» (ClickHouse).
