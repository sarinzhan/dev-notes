## Кратко
**Кластеризованный (первичный) индекс** — это *и есть* таблица: строки хранятся в листовых страницах индекса, отсортированные по ключу. **Вторичный индекс** — отдельная структура, записи которой указывают обратно на строку. InnoDB (MySQL) и SQL Server кластеризуют таблицу по первичному ключу, а вторичные индексы хранят **значение первичного ключа**, поэтому поиск по вторичному индексу проходит через два B+-дерева. В Postgres кластеризованных таблиц нет: каждый индекс, включая первичный ключ, вторичный и указывает в heap по **ctid**. Эта одна разница объясняет, почему случайные UUID-ключи сильнее бьют по MySQL, почему обновления в Postgres трогают все индексы и почему Uber когда-то переехал с Postgres на MySQL.

## Основное
### Кластеризованный / первичный ключ (InnoDB, SQL Server)
- Таблица организована вокруг первичного ключа: листовые страницы B+-дерева PK содержат целые строки в порядке ключа. Одна таблица — один кластеризованный индекс.
- Диапазонные запросы по PK (`WHERE id BETWEEN 1000 AND 2000`) читают подряд идущие страницы: очень быстро.
- Место вставки определяется ключом: последовательные ключи дописываются в последнюю страницу; случайные попадают в середину и вызывают **расщепления страниц** (page split), полупустые страницы и случайный IO.
- Если PK не объявлен, InnoDB берёт первый уникальный NOT NULL индекс или добавляет скрытый 6-байтный row id.
- SQL Server: кластеризованный индекс может быть по любой колонке (колонкам), не обязательно по PK; таблица без него — heap. Выбирай узкий, уникальный, постоянно растущий, редко меняющийся ключ (классический совет по проектированию кластеризованного индекса).

### Вторичный индекс
- Записи — `вторичный ключ → указатель`. Что такое указатель, зависит от движка:
  - **InnoDB**: значение первичного ключа. Поиск = вторичное B+-дерево → значение PK → B+-дерево PK → строка. Два спуска по дереву. Широкий PK (UUID-строка, составной ключ) делает шире каждый вторичный индекс.
  - **Postgres**: ctid `(страница, слот)` версии строки в heap. Поиск = индекс → сразу страница heap.
- Выбор InnoDB означает, что строки могут переезжать (расщепления страниц), не трогая вторичные индексы. Выбор Postgres означает, что поиск — один переход, но каждая новая версия строки (её пишет каждый UPDATE) получает новый ctid, поэтому **каждый индекс должен получить новую запись**, если только обновление не HOT ([[postgres-architecture]]).

### Postgres и MySQL: фундаментальная разница
| | Postgres | MySQL InnoDB |
|---|---|---|
| Хранение таблицы | heap, без порядка | кластеризовано по PK |
| Вторичный индекс указывает на | ctid (физический адрес) | значение PK (логический адрес) |
| Поиск по вторичному ключу | индекс → heap | индекс → дерево PK → строка |
| UPDATE одной колонки | новый кортеж; обновляются все индексы, если не HOT | на месте; обновляются только индексы по изменённым колонкам; старая версия — в undo log |
| Сканирование диапазона по PK | index scan + случайные чтения heap (если нет корреляции) | последовательные листовые страницы |
| Цена случайного PK | раздувание индекса, разбросанный heap | расщепления страниц в самой таблице |

- **Усиление записи** (write amplification): в Postgres обновление одной колонки в таблице с 10 индексами может писать в 11 мест плюс WAL. Это суть поста Uber 2016 года о переезде с Postgres на MySQL (вместе с репликацией физического WAL и обновлениями версий); в Postgres давно есть HOT-обновления, и он продолжает улучшаться, но компромисс реален ([[wal-redo-undo-and-durability]]).

### UUID как ключи
- Случайные значения UUIDv4 разбросаны по всему пространству ключей. Каждая вставка попадает в случайную листовую страницу B+-дерева, поэтому рабочий набор — **весь индекс**, а не самая правая страница. Как только индекс больше памяти, вставки превращаются в чтения с диска; расщепления оставляют страницы заполненными на ~50–70 %.
- В InnoDB это бьёт по самой таблице (она кластеризована), плюс каждый вторичный индекс хранит 16-байтный (или 36-символьный строковый) PK.
- Shopify перешёл с UUIDv4 на упорядоченные по времени id в стиле ULID в нагруженной на запись таблице MySQL и получил большой прирост скорости вставок и эффективности буферного пула.
- Решения: **UUIDv7** (упорядочен по времени, RFC 9562, 2024) или ULID, либо внутри `bigint` из последовательности, а UUID только как публичный id; храни UUID как `uuid`/`BINARY(16)`, никогда как `varchar(36)` ([[time-money-and-ids]]).

### Index scan и index seek
- Терминология SQL Server: **seek** = спуск по B+-дереву к ключу или началу диапазона (в Postgres это Index Scan с условием индекса); **scan** = чтение всех листовых страниц индекса. «Index Scan» в Postgres может быть и тем, и другим — зависит от того, есть ли условие индекса.

## Пример
```sql
-- InnoDB: the PK is the table; idx_email stores (email, id)
CREATE TABLE users (
  id        BINARY(16) PRIMARY KEY,           -- UUIDv7 bytes: time-ordered
  email     VARCHAR(255) NOT NULL,
  name      VARCHAR(100),
  KEY idx_email (email)
) ENGINE=InnoDB;
-- SELECT name FROM users WHERE email = ?  → idx_email → id → PK tree → row

-- Postgres: heap + separate PK index; every index points to a ctid
CREATE TABLE users (
  id    uuid PRIMARY KEY DEFAULT uuidv7(),     -- uuidv7() is built in from Postgres 18
  email text NOT NULL UNIQUE,
  name  text
);
```

## Подводные камни
- Случайные первичные ключи UUIDv4 в большой нагруженной на запись таблице InnoDB; используй UUIDv7 или последовательность.
- Широкий составной PK в InnoDB молча расширяет каждый вторичный индекс.
- Добавить «ещё всего один индекс» в Postgres: каждое не-HOT обновление теперь пишет и его.
- Ожидать, что `CLUSTER` в Postgres будет поддерживать порядок; это разовая перезапись под эксклюзивной блокировкой.
