## Кратко
Таблица на диске — это не список строк, а файл из **страниц** фиксированного размера (8 КБ в Postgres, 16 КБ в InnoDB), и в каждой странице много строк. База никогда не читает одну строку: она читает целую страницу, поэтому стоимость запроса — это число страниц, которых он касается. **Heap** (куча) — неупорядоченный набор страниц, где лежат строки таблицы. **Индекс** — отдельная структура (B+-дерево, тоже из страниц), которая отображает ключ на расположение строки, так что запрос читает несколько страниц индекса и одну страницу heap вместо сканирования всей кучи.

## Основное
### Идентификатор строки и кортежа
- У каждой строки есть внутренний адрес. В Postgres это **ctid** `(номер страницы, слот в странице)`, например `(3, 7)`: страница 3, элемент 7. В MySQL/InnoDB отдельного адреса нет: адресом служит первичный ключ, потому что таблица хранится внутри B+-дерева первичного ключа ([[primary-vs-secondary-indexes]]).
- Пользователь эти идентификаторы видит редко, но каждая запись индекса указывает на один из них.

### Страницы
- Страница — единица ввода-вывода и кэширования. Строки упакованы в страницы: заголовок страницы, массив слотов (указателей на элементы) в начале и данные строк, растущие с конца. Свободное место — посередине.
- Прочитать строку `(3, 7)` значит: загрузить страницу 3 в буферный пул (из страничного кэша ОС или с диска) и взять слот 7. Остальные ~100 строк этой страницы достаются бесплатно; поэтому последовательное сканирование быстрое, и поэтому строки, которые запрашивают вместе, должны лежать рядом.
- Размер страницы фиксирован для базы: Postgres 8 КБ, InnoDB 16 КБ, SQL Server 8 КБ, в Oracle настраивается. Большие страницы: меньше операций ввода-вывода при сканировании, больше лишнего чтения при точечных запросах.
- Значения, которые не помещаются в страницу, выносятся отдельно: TOAST в Postgres, overflow-страницы в InnoDB. Поэтому широкие колонки `jsonb` или `text` стоят дополнительного обращения.

### Ввод-вывод
- IO — это один запрос на чтение к диску; он возвращает минимум одну страницу, часто несколько (упреждающее чтение, read-ahead). Цель любого пути доступа — **меньше IO**.
- Страницы кэшируются в буферном пуле базы (`shared_buffers`, `innodb_buffer_pool_size`) и в страничном кэше ОС ([[storage-management]]). «Горячая» страница стоит обращения к памяти, холодная — чтения с диска.
- Почему базы читают страницы, а не отдельные строки: диск и ОС и так работают блоками (4 КБ и больше), прочитать меньше блока невозможно, а соседние строки обычно нужны следующими.

### Heap
- Heap — это данные таблицы без определённого порядка. Вставка идёт туда, где есть свободное место (Postgres отслеживает его в карте свободного места, free space map).
- Найти строку в heap без индекса = **полное сканирование таблицы**: прочитать каждую страницу. Для 1 млн строк по 100 байт это ~12 500 страниц по 8 КБ.
- В Postgres UPDATE записывает новую версию строки, возможно на другую страницу; старые версии остаются до VACUUM ([[postgres-vacuum-and-bloat]]).

### Индекс
- Индекс — отдельная структура данных, обычно B+-дерево ([[b-tree-vs-b-plus-tree]]), записи которой — `ключ → идентификатор строки`. Он тоже живёт в страницах и тоже стоит IO, но намного меньше: 3–4 чтения страниц находят любой ключ среди миллиардов.
- Индекс говорит, **какую страницу** читать; затем одно чтение страницы heap достаёт строку. Без индекса пришлось бы читать все страницы.
- Если сам индекс содержит все колонки, нужные запросу, чтение heap пропускается: index-only scan ([[postgres-indexes]]).
- Маленькие индексы помещаются в память; большие вытесняются из кэша, и тогда случайные поиски по индексу начинают ходить на диск.

### Кластеризованные таблицы (index-organized)
- Некоторые движки хранят heap **внутри** индекса, отсортированным по ключу: таблицы InnoDB (по первичному ключу), кластеризованные индексы SQL Server, IOT в Oracle. Чтение диапазона по ключу тогда последовательное, но вставки со случайными ключами расщепляют страницы ([[primary-vs-secondary-indexes]]).
- Таблицы Postgres — всегда heap. `CLUSTER` один раз переупорядочивает таблицу, но порядок потом не поддерживается.

### NULL
- В Postgres строка, у которой хоть одна колонка NULL, получает в заголовке битовую карту NULL (1 бит на колонку), а само значение NULL места не занимает. Много NULL в широкой разреженной таблице уменьшают строки и, значит, помещают больше строк в страницу.
- `NULL` не равен ничему, включая другой `NULL`, поэтому `WHERE x = NULL` никогда не совпадает; нужно `IS NULL`. B-tree индексы в Postgres хранят NULL и могут обслуживать `IS NULL`.

## Пример
```sql
-- where does a row physically live?
SELECT ctid, id, name FROM employees WHERE id = 42;     -- ctid = (0,42)

-- how many pages does the table and its index take?
SELECT relname, relpages, reltuples
FROM pg_class WHERE relname IN ('employees', 'employees_pkey');

-- buffers = pages touched; shared hit = from cache, read = from disk
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM employees WHERE id = 42;
--  Index Scan using employees_pkey ...  Buffers: shared hit=4
```

## Подводные камни
- Думать строками, а не страницами: запрос, который возвращает 10 строк, разбросанных по 10 страницам, стоит 10 IO; 10 строк на одной странице — 1 IO.
- `SELECT *` тянет широкие TOAST-колонки, которые не нужны; перечисляй колонки ([[row-vs-column-storage]]).
- Раздутая куча (много мёртвых версий строк) — это больше страниц для тех же строк, поэтому каждое сканирование медленнее ([[postgres-vacuum-and-bloat]]).
- Кэш делает первый запуск медленным, а второй быстрым; измеряй с `BUFFERS` и смотри на `read`, а не только на время.
