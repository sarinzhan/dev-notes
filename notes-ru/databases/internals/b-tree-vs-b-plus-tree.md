## Кратко
Индекс базы данных должен находить один ключ среди миллиардов за очень малое число чтений страниц. **B-дерево** делает это широкими узлами (один узел = одна страница, сотни ключей в узле), поэтому дерево глубиной всего 3–4 уровня. Исходное B-дерево хранит ключи **и значения** в каждом узле, что тратит внутренние узлы на данные и заставляет сканирование диапазона прыгать вверх-вниз по дереву. **B+-дерево** хранит во внутренних узлах только ключи (поэтому их помещается больше, и они влезают в память), а все значения кладёт в листья, связанные в список, так что сканирование диапазона — это «найти первый ключ и идти по листьям». Практически каждый реляционный индекс (Postgres, InnoDB, SQL Server, Oracle, SQLite) — это B+-дерево.

## Основное
### Почему не полное сканирование таблицы
- Без индекса найти строку значит прочитать каждую страницу heap ([[how-tables-and-indexes-are-stored]]). Даже параллельно несколькими воркерами это O(n) IO.
- Дерево превращает это в O(log n), причём основание логарифма огромное: при ~400 ключах на страницу 8 КБ три уровня адресуют 400³ = 64 млн ключей, а четыре — 25 млрд.

### Исходное B-дерево
- B-дерево **степени m** (максимум детей у узла): у каждого узла до m детей и m−1 отсортированных ключей; внутренние узлы (кроме корня) заполнены минимум наполовину, поэтому дерево остаётся сбалансированным; все листья на одной глубине.
- Каждый узел — список элементов: пары **ключ + значение** плюс указатели на детей. Значение — указатель на строку (tuple id или сама строка).
- Поиск: начать с корневой страницы, бинарным поиском найти ключи, пойти по указателю между двумя ключами, которые ограничивают искомый, повторить. Каждый шаг = одно чтение страницы.
- Вставка: положить ключ в его лист; если лист переполнен, **расщепить** его на два и поднять средний ключ в родителя; расщепления могут каскадом идти вверх и вырастить корень.
- Удаление: убрать ключ; если узел заполнен меньше чем наполовину, занять у соседа или слить узлы.

### Ограничения исходного B-дерева
- **Значения во внутренних узлах**: каждый внутренний узел хранит ключи *и* значения, поэтому в страницу влезает меньше ключей. Меньше ключей в узле = больше уровней = больше IO. При большом значении (целая строка в кластеризованной таблице) внутренние узлы держат очень мало ключей.
- **Диапазонные запросы дорогие**: `WHERE id BETWEEN 1 AND 1000` приходится обходить дерево вверх и вниз, потому что ключи диапазона разбросаны по уровням. Каждый прыжок — случайное чтение страницы.
- Внутренние узлы трудно держать в памяти, потому что они большие.

### B+-дерево
- Внутренние узлы хранят **только ключи** (разделители) и указатели на детей. Больше ключей на страницу → дерево ниже, и все внутренние уровни обычно помещаются в RAM.
- **Листья хранят все ключи и значения**; ключ может встречаться дважды (во внутреннем узле как разделитель и в своём листе).
- Листья связаны (в большинстве движков двусвязно): сканирование диапазона один раз спускается к первому ключу, а затем читает лист за листом последовательно. `ORDER BY key` и `LIMIT` достаются бесплатно.
- Любой поиск заканчивается в листе, поэтому стоимость предсказуема: высота дерева + чтения листьев.

| | B-дерево | B+-дерево |
|---|---|---|
| Внутренние узлы | ключи + значения | только ключи |
| Значения | где угодно | только в листьях |
| Ключей во внутренней странице | меньше | больше → дерево ниже |
| Сканирование диапазона | обход дерева | один спуск, проход по связанным листьям |
| Повтор ключей | нет | ключи-разделители повторяются в листьях |
| Где используется | редко в современных БД (в части документации MongoDB B+-дерево WiredTiger называют «B-tree») | Postgres, InnoDB, SQL Server, Oracle, SQLite |

### Особенности в СУБД
- **Узел = страница**: размер узла B+-дерева равен странице базы (8 КБ Postgres, 16 КБ InnoDB), так что чтение узла — один IO.
- Внутренние узлы помещаются в память, часто все; листья читаются из буферного пула или с диска. Трёхуровневый индекс с закэшированными внутренними уровнями стоит одного IO на поиск.
- Связный список листьев делает сканирование диапазона последовательным, а последовательный IO намного дешевле случайного на HDD и всё ещё дешевле на SSD.
- Держи ключи маленькими: ключ `bigint` (8 Б) помещает в страницу примерно вдвое больше записей, чем 16-байтный UUID, и в 4–5 раз больше, чем 36-символьная строка. Шире ключ = выше дерево = больше памяти.
- Расщепления оставляют полупустые страницы; постоянно растущие ключи дописываются в самый правый лист и заполняют страницы полностью (Postgres и InnoDB оптимизируют этот случай). Случайные ключи (UUIDv4) вызывают расщепления везде ([[primary-vs-secondary-indexes]]).
- **Fill factor** оставляет в каждом листе свободное место под будущие обновления (`fillfactor` в Postgres, по умолчанию 90 для B-tree индексов).

### Стоимость хранения: MySQL и Postgres
- **InnoDB**: таблица — это B+-дерево PK, листья содержат целые строки. Листья вторичных индексов содержат значение PK, поэтому большой PK (UUID-строка) раздувает каждый вторичный индекс.
- **Postgres**: все индексы, включая PK, хранят в листьях 6-байтный ctid, поэтому размер индекса не зависит от типа PK, но heap отдельный, и каждая новая версия строки требует новых записей в индексах.
- Ещё Postgres дедуплицирует одинаковые ключи в листьях B-tree (начиная с 13): один ключ со списком ctid, что уменьшает индексы по колонкам с низкой кардинальностью.

## Пример
```sql
-- Postgres: inspect the tree with pageinspect
CREATE EXTENSION IF NOT EXISTS pageinspect;
SELECT * FROM bt_metap('orders_pkey');            -- root page, level (height - 1)
SELECT itemoffset, ctid, data
FROM bt_page_items('orders_pkey', 1) LIMIT 5;     -- leaf entries: key bytes → ctid

-- range scan: one descent, then leaf pages in order
EXPLAIN SELECT id FROM orders WHERE id BETWEEN 1000 AND 2000 ORDER BY id;
--  Index Only Scan using orders_pkey ... (no Sort node: leaves are already ordered)
```

## Подводные камни
- Называть любой индекс базы «B-деревом»: структура в Postgres и InnoDB — B+-дерево; это различие объясняет сканирование диапазонов и расход памяти.
- Широкие ключи индекса (длинные строки, много колонок) делают дерево выше и хуже для кэша; если нужно только равенство, индексируй хэш или префикс.
- Случайные вставки фрагментируют индекс; `REINDEX CONCURRENTLY` (Postgres) или `OPTIMIZE TABLE` (InnoDB) его уплотняют.
- B+-деревья оптимизированы под чтение; для нагрузки с большим числом записей LSM-деревья меняют стоимость чтения на последовательную запись ([[database-engines]]).
