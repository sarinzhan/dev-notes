## Кратко
Транзакция — последовательность операций с базой данных, выполняемая как единое целое: либо коммитится вся, либо ничего. ACID называет четыре гарантии (атомарность, согласованность, изоляция, долговечность). Изоляция — единственная из них с компромиссами: полная изоляция дорога, поэтому SQL определяет четыре уровня, каждый из которых допускает всё меньше аномалий: грязное чтение, неповторяющееся чтение, фантомное чтение и те, о которых стандарт забыл, — потерянное обновление и асимметрия записи (write skew). В Postgres по умолчанию READ COMMITTED; как он реализует каждый уровень — в [[postgres-isolation-levels]].

## Основное

### Логическая и физическая транзакция
- **Физическая транзакция**: единица на уровне СУБД между `BEGIN` и `COMMIT`/`ROLLBACK` на одном соединении (TCL, см. [[sql-joins-and-commands]]).
- **Логическая транзакция**: бизнес-операция, которая с точки зрения предметной области должна выполниться целиком («оформить заказ» = вставить заказ, зарезервировать товар, записать событие в outbox). Она может охватывать несколько методов и, в Spring, несколько границ `@Transactional`, которые *присоединяются* к одной физической транзакции (`REQUIRED`), или сознательно открывают отдельные (`REQUIRES_NEW` для строки аудита, которая должна пережить откат). Подробности — в [[spring-transactional]].
- Логическая транзакция через несколько **сервисов** или **систем** (БД + Kafka, БД + платёжный шлюз) не может быть одной физической; вместо 2PC получаешь доставку at-least-once плюс [[idempotency]], [[outbox-pattern]] или саги.

### ACID
- **Атомарность (atomicity)** — транзакция никогда не применяется частично; при сбое все изменения отменяются (Postgres: версии строк MVCC просто никогда не становятся видимыми; запись о коммите в WAL — атомарный переключатель).
- **Согласованность (consistency)** — закоммиченная транзакция переводит базу из одного корректного состояния в другое: соблюдаются все ограничения ([[constraints-and-relationships]]), триггеры и каскады. За бизнес-инварианты, которые схема выразить не может, отвечает приложение.
- **Изоляция (isolation)** — параллельные транзакции не влияют на результат друг друга; степень настраивается, см. ниже.
- **Долговечность (durability)** — после коммита изменение переживает сбой: журнал предзаписи (write-ahead log) сбрасывается через `fsync` до того, как `COMMIT` вернёт управление (`synchronous_commit`), а репликация позволяет пережить потерю диска.

### Аномалии изоляции
В источнике некоторые из них были смешаны; вот стандартный набор, каждая — с историей про две транзакции:
| Аномалия | История |
|---|---|
| **Грязное чтение (dirty read)** | T1 обновляет строку, но ещё не закоммитила; T2 читает новое значение; T1 откатывается. T2 работала с данными, которых никогда не существовало. |
| **Неповторяющееся чтение (non-repeatable read)** | T1 читает строку; T2 обновляет (или удаляет) её и коммитит; T1 снова читает ту же строку и в пределах одной транзакции получает другое значение. |
| **Фантомное чтение (phantom read)** | T1 выполняет `SELECT ... WHERE status = 'NEW'`; T2 вставляет или удаляет строки, подходящие под этот предикат, и коммитит; T1 повторяет запрос и получает другой **набор строк**. |
| **Потерянное обновление (lost update)** | T1 и T2 обе читают `balance = 100`; T1 записывает 90, T2 записывает 80 и коммитит последней («побеждает последний коммит»); изменение T1 пропало. Вариант: T2 откатывается после записи T1, и откат стирает и изменение T1 (возможно только при разрешённой грязной записи; ни одна серьёзная СУБД её не допускает). |
| **Асимметрия записи (write skew)** | T1 и T2 каждая читают *инвариант* (два дежурных врача), каждая решает, что безопасно обновить *другую* строку (каждый врач снимается с дежурства), обе коммитят; инвариант нарушен, хотя ни одна строка не была записана дважды. |

- Лекарство от потерянного обновления на уровне строки — блокировка или проверка версии ([[jpa-locking]]) либо атомарный `UPDATE ... SET balance = balance - 10`; асимметрию записи ловит только SERIALIZABLE.

### Четыре уровня изоляции (стандарт SQL)
| Уровень | Грязное чтение | Неповторяющееся чтение | Фантом | Write skew | Как обычно реализуется |
|---|---|---|---|---|---|
| READ UNCOMMITTED | допускается | допускается | допускается | допускается | нет блокировок на чтение / нет снимка; Postgres его не реализует (обрабатывает как READ COMMITTED) |
| READ COMMITTED | нет | допускается | допускается | допускается | каждый оператор видит данные, закоммиченные до его начала; распространённое значение по умолчанию |
| REPEATABLE READ | нет | нет | допускается стандартом; **не** в Postgres | допускается | снимок делается при первом операторе транзакции |
| SERIALIZABLE | нет | нет | нет | нет | результат совпадает с некоторым последовательным порядком: блокировки 2PL (MySQL, SQL Server) или сериализуемая snapshot-изоляция с прерыванием и повтором (Postgres) |

- Выше уровень — меньше аномалий, больше прерываний или ожиданий, меньше транзакций в секунду. Выбирай под задачу: READ COMMITTED для обычного CRUD, REPEATABLE READ для согласованных отчётов, SERIALIZABLE для инвариантов между строками (деньги, складские остатки) с циклом повторов.
- Задаётся на уровне транзакции (`SET TRANSACTION ISOLATION LEVEL ...`) или в Spring через `@Transactional(isolation = Isolation.SERIALIZABLE)`.
- Блокировки против MVCC: движки на блокировках заставляют читателей ждать писателей; движки с MVCC (Postgres, Oracle, InnoDB) хранят старые версии строк, поэтому читатели никогда не блокируют писателей и наоборот, а блокируют только конфликты «писатель — писатель».

## Пример
```sql
-- Потерянное обновление по шагам при READ COMMITTED (две сессии)
-- T1                                          -- T2
BEGIN;                                         BEGIN;
SELECT balance FROM accounts WHERE id = 1;     SELECT balance FROM accounts WHERE id = 1;  -- обе видят 100
UPDATE accounts SET balance = 90 WHERE id = 1;
COMMIT;                                        UPDATE accounts SET balance = 80 WHERE id = 1; -- дождалась T1, затем перезаписала
                                               COMMIT;                                        -- balance = 80, -10 от T1 потеряно

-- Исправление: сделать обновление относительным (атомарным) или сначала заблокировать строку
UPDATE accounts SET balance = balance - 10 WHERE id = 1 AND balance >= 10;
-- или
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
```

## Подводные камни
- «Мы используем транзакции, значит, защищены от багов конкурентности»: READ COMMITTED допускает потерянные обновления и асимметрию записи; транзакция даёт только атомарность, а не последовательную корректность.
- Длинные транзакции (HTTP-вызов внутри, время на раздумья пользователя) держат блокировки и в движках с MVCC блокируют vacuum; держи их в пределах миллисекунд.
- SERIALIZABLE без цикла повторов просто превращает гонки в ошибки `40001` для пользователей.
- Особенности Postgres и пример асимметрии записи: [[postgres-isolation-levels]]; аналоги на стороне Java (гонки check-then-act): [[concurrency-hazards]].
