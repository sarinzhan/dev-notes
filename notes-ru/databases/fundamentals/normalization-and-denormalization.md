## Кратко
Нормализация — это такое устройство таблиц, при котором каждый факт хранится один раз: она убирает дублирование и аномалии обновления/вставки/удаления, которые дублирование вызывает. На практике целятся в третью нормальную форму: атомарные значения (1НФ), каждый неключевой столбец зависит от всего ключа (2НФ) и только от ключа (3НФ). Денормализация — сознательное копирование или предварительная агрегация данных обратно в таблицу ради ускорения чтения, ценой поддержания копий в согласованном состоянии.

## Основное

### Зачем нормализовать
- У денормализованной таблицы `orders`, где `customer_name, customer_phone` повторяются в каждой строке, три аномалии: **обновления** (поменять телефон в 10 000 строк и пропустить одну), **вставки** (нельзя сохранить клиента без заказа), **удаления** (удаление последнего заказа удаляет клиента).
- Нормализованные схемы меньше, их проще менять, а ограничения ([[constraints-and-relationships]]) могут защищать каждый факт ровно один раз.
- Существует шесть нормальных форм плюс нормальная форма Бойса — Кодда (BCNF); 1НФ–3НФ — то, о чём спрашивают на собеседованиях и что используют production-схемы. 4НФ/5НФ касаются многозначных зависимостей и зависимостей соединения и встречаются редко.

### Формы
| Форма | Правило | Пример нарушения | Исправление |
|---|---|---|---|
| **1НФ** | каждый столбец хранит одно атомарное значение; нет повторяющихся групп; строки уникальны (есть ключ) | `phones = '+996 700..., +996 555...'` или столбцы `phone1, phone2, phone3` | дочерняя таблица `customer_phones(customer_id, phone)` |
| **2НФ** | 1НФ + каждый неключевой столбец зависит от **всего** первичного ключа, а не от его части (важно только для составных ключей) | `order_items(order_id, product_id, qty, product_name)`: `product_name` зависит только от `product_id` | перенести `product_name` в `products` |
| **3НФ** | 2НФ + нет транзитивных зависимостей: неключевые столбцы не зависят от других неключевых столбцов | `employees(id, department_id, department_name)`: `department_name` зависит от `department_id`, а не от `id` | перенести `department_name` в `departments` |
| BCNF | каждый детерминант — потенциальный ключ | пересекающиеся составные потенциальные ключи | разделить; встречается редко |

- Мнемоника для 3НФ: каждый неключевой столбец зависит *от ключа, от всего ключа и ни от чего, кроме ключа*.
- Столбец `jsonb` — сознательное нарушение 1НФ; нормально для данных, по которым никогда не фильтруют реляционно (настройки, сырые payload), плохо для всего, что join-ят или обновляют по отдельным полям.

### Денормализация
- Сознательный вывод схемы из нормальной формы ради ускорения чтения, ценой избыточности и дополнительной логики записи.
- Типичные формы:
  - **Скопированные столбцы**: `orders.customer_name`, зафиксированный в момент заказа (этот вариант ещё и семантически *правильный*: в счёте должно стоять имя, каким оно было тогда).
  - **Предагрегированные счётчики**: `posts.comment_count`, `accounts.balance` вместо `sum(transactions)`. Должны обновляться в той же транзакции, что и исходные строки, или триггером.
  - **Плоские модели чтения / материализованные представления** для дашбордов и поиска (см. [[database-fundamentals]]).
  - **Широкие таблицы** для аналитики (схема «звезда» (star schema): таблица фактов + таблицы измерений), где join во время запроса слишком медленные.
- Когда: измеренная задержка чтения на запросе с множеством join, которую не могут исправить [[database-indexes]]; соотношение чтения к записи сильно смещено в сторону чтения; отчётная нагрузка. Не раньше, чем появится медленный запрос, который можно показать.
- Как сохранять согласованность: та же транзакция ([[spring-transactional]]), триггер в БД или асинхронная проекция на основе событий ([[outbox-pattern]]), когда допустима согласованность в конечном счёте (eventual consistency); периодическая задача сверки ловит расхождения.

## Пример
```sql
-- 3НФ: каждый факт один раз
CREATE TABLE customers (
    id         bigint PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
    msisdn     varchar(15) NOT NULL UNIQUE,
    full_name  text NOT NULL
);
CREATE TABLE tariffs (
    id    bigint PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
    code  varchar(32) NOT NULL UNIQUE,
    price numeric(12,2) NOT NULL
);
CREATE TABLE subscriptions (
    id           bigint PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
    customer_id  bigint NOT NULL REFERENCES customers(id),
    tariff_id    bigint NOT NULL REFERENCES tariffs(id),
    activated_at timestamptz NOT NULL DEFAULT now(),
    -- сознательная денормализация: цена зафиксирована при активации, бизнес-снимок
    price_at_activation numeric(12,2) NOT NULL
);

-- сознательная денормализация: счётчик поддерживается в той же транзакции
ALTER TABLE customers ADD COLUMN active_subscriptions int NOT NULL DEFAULT 0;
-- в сервисе: INSERT INTO subscriptions ...; UPDATE customers SET active_subscriptions = active_subscriptions + 1 WHERE id = ?;
```

## Подводные камни
- Чрезмерная нормализация справочных значений (таблица `genders` из двух строк) добавляет join без пользы; достаточно ограничения `CHECK` или столбца-перечисления.
- Денормализованные счётчики, обновляемые вне транзакции, расходятся с реальностью; добавь запрос сверки и запускай его в CI на копии production.
- Столбцы-снимки (`price_at_activation`) часто принимают за «плохую денормализацию» и удаляют, после чего ломаются исторические счета.
- Нормализация ничего не говорит о производительности; схема в 3НФ без индексов всё равно медленная, см. [[database-indexes]].
- ORM подталкивают к 3НФ по принципу «одна сущность — одна таблица»; для моделей чтения лучше DTO-проекции или представления, а не денормализованные сущности, см. [[spring-data-repositories]].
