## Кратко
Начинай с реляционной базы (Postgres), если только конкретный шаблон доступа или требование к масштабу её не исключает. Выбор делается по четырём вопросам: насколько строгой должна быть согласованность, насколько схема меняется и насколько она вложенная, каковы шаблоны доступа (точечные запросы по ключу, диапазоны, join, полнотекстовый поиск, обход графа) и каковы объём записи и рост. Каждое семейство NoSQL (ключ-значение, документное, колоночное (wide-column), графовое, поисковое) отказывается от чего-то, что есть у реляционных баз (join, произвольные запросы, транзакции по нескольким строкам), чтобы выиграть на одном конкретном шаблоне. Сами семейства описаны в [[database-fundamentals]]; эта заметка — процедура принятия решения.

## Основное

### Четыре вопроса
| Вопрос | Указывает на SQL | Указывает на семейство NoSQL |
|---|---|---|
| **Согласованность** | деньги, складские остатки, всё, где есть инварианты между строками: ACID-транзакции ([[transactions-acid-and-isolation]]) | счётчики, кэши, ленты, аналитика, которые допускают согласованность в конечном счёте (eventual consistency) ([[consistency-models]]) |
| **Схема** | стабильные, хорошо понятные сущности со связями; ограничения проверяет БД ([[constraints-and-relationships]]) | разнородные документы, свои поля у каждого арендатора (tenant), быстрые итерации продукта: документное хранилище |
| **Шаблоны доступа** | произвольные запросы, отчёты, join между сущностями | один-два известных шаблона на огромном объёме (поиск по ключу, упорядоченная по времени запись в партицию, текстовый поиск, обход графа) |
| **Масштаб** | до десятков тысяч TPS и нескольких ТБ на одном primary плюс реплики | запись за пределами одной машины, multi-region active-active, петабайты: колоночное хранилище или управляемое KV ([[sharding-strategies]]) |

### Для чего на самом деле каждое семейство NoSQL
- **Ключ-значение** (Redis, DynamoDB): поиск по ключу за O(1), TTL, атомарные счётчики. Кэш, сессии, блокировки, ограничение частоты запросов (rate limits) ([[redis-data-structures]], [[redis-patterns-and-persistence]]). Вторичных запросов, заслуживающих этого названия, нет.
- **Документное** (MongoDB): агрегат хранится как один JSON-документ, индексируется по внутренним полям и атомарно обновляется как единое целое. Каталоги, профили, CMS ([[mongodb-basics]]). Слабое место — join.
- **Колоночное (wide-column)** (Cassandra, ScyllaDB; ClickHouse для аналитики): ключ партиции → отсортированные строки, запись дописывается в журнал, линейное горизонтальное масштабирование. Временные ряды, журналы событий, телеметрия ([[column-and-wide-column-stores]]). Запросы обязаны идти по ключу партиции; произвольной фильтрации нет.
- **Поисковое** (Elasticsearch, OpenSearch): инвертированный индекс, ранжирование по релевантности, фасеты ([[elasticsearch-basics]]). Никогда не является системой-источником истины (system of record).
- **Графовое** (Neo4j): обходы переменной глубины (друзья друзей, мошеннические группы). В SQL это рекурсивные CTE, которые становятся медленными уже после нескольких переходов.

### Почему Postgres — выбор по умолчанию
- `jsonb` с GIN-индексами покрывает большинство случаев «нам нужны гибкие поля» ([[postgres-jsonb-and-full-text]]); `tsvector` покрывает базовый поиск; партиционирование покрывает хранение временных рядов с ограниченным сроком ([[postgres-partitioning]]); логическая репликация покрывает наполнение поискового индекса или хранилища данных.
- Одна система — это одна стратегия бэкапов, один набор транзакционных гарантий, один объект мониторинга. Каждая дополнительная база добавляет [[outbox-pattern]] или CDC-конвейер для синхронизации и новый класс багов согласованности.
- Путь масштабирования до ухода от SQL: индексы → реплики для чтения → кэширование → партиционирование → шардирование ([[database-scaling-path]]).

### Признаки того, что второе хранилище действительно нужно
- Форма запроса, которую Postgres принципиально не может проиндексировать: нечёткий полнотекстовый поиск с релевантностью по миллионам документов, гео плюс текст плюс фасеты одновременно, глубокий обход графа.
- Интенсивность записи, которая насыщает один primary даже после пакетирования и партиционирования (сотни тысяч мелких записей в секунду, телеметрия с миллионов устройств).
- Данные, которые живут от секунд до часов и потерю которых можно допустить: используй кэш, а не базу данных.
- Multi-region active-active запись с требованиями к разрешению конфликтов ([[multi-leader-and-leaderless]]).

### Полиглотное хранение (polyglot persistence) на практике
- Держи **одну систему-источник истины** на сущность; любое другое хранилище — производное представление, перестраиваемое из неё (поисковый индекс из таблицы заказов, кэш из каталога). Это определяет, куда идёт исправление бага и что восстанавливать из бэкапа.
- Производные хранилища заполняются асинхронно: outbox/CDC → Kafka → индексатор ([[search-and-indexing-services]]). Смирись с пробелами в read-your-writes или направляй чтение сразу после записи на primary.
- Выбор хранилища для каждого строительного блока сведён в [[storage-choices]]; формулировка для собеседования «выбирай по шаблону доступа, затем по согласованности» — ответ на большинство вопросов «какую БД взять?».

## Пример
```sql
-- Типичный сервис заказов eSIM: реляционное ядро с jsonb как запасным выходом
-- вместо отдельного документного хранилища для полей, специфичных для оператора.
CREATE TABLE esim_orders (
    id            uuid PRIMARY KEY,
    subscriber_id bigint NOT NULL REFERENCES subscribers(id),
    status        text   NOT NULL CHECK (status IN ('NEW','RESERVED','ACTIVATED','FAILED')),
    operator_data jsonb  NOT NULL DEFAULT '{}',   -- зависит от MNO: iccid, eid, тип профиля
    created_at    timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX esim_orders_operator_data_gin ON esim_orders USING gin (operator_data jsonb_path_ops);

-- Гибкий фильтр, который всё равно использует индекс
SELECT id FROM esim_orders
WHERE operator_data @> '{"profileType": "prepaid"}' AND status = 'ACTIVATED';
```
Поиск по истории заказов по произвольному тексту или 50 тысяч событий телеметрии в секунду с устройств — вот момент, когда стоит добавить Elasticsearch или колоночное хранилище, наполняемое из этой таблицы.

## Подводные камни
- Выбрать MongoDB, «потому что схема будет меняться»: изменение схемы в Postgres — это файл миграции ([[schema-migrations-flyway-liquibase]]); дрейф схемы в документном хранилище — сюрприз во время выполнения через три года.
- Выбрать Cassandra, а потом понадобится запрос по столбцу, не входящему в ключ партиции; решение — вторая таблица под каждый запрос, которую пишет приложение, без транзакций между ними.
- Считать кэш или поисковый индекс источником истины, а потом потерять его при перезапуске или переиндексации.
- «NoSQL — это без схемы»: схема существует, просто живёт в коде приложения без принудительной проверки.
- Связанные заметки: [[storage-choices]] — взгляд с точки зрения system design, [[cap-and-pacelc]] — чего стоит «согласованность в конечном счёте», [[normalization-and-denormalization]] — сторона реляционного моделирования.
