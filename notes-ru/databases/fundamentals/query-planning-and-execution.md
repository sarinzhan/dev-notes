## Кратко
SQL-оператор проходит четыре стадии: **парсер** превращает текст в дерево, **переписчик (rewriter)** раскрывает представления и правила, **планировщик (planner, оптимизатор)** перебирает возможные планы выполнения и выбирает план с наименьшей оценочной стоимостью, а **исполнитель (executor)** протягивает строки через этот план узел за узлом. Чтобы принять решение, планировщик никогда не выполняет запрос; он опирается на **статистику** о данных (число строк, число различных значений, гистограммы) и на **модель стоимости** с фиксированными весами для чтения страниц и работы CPU. Почти каждая история «база выбрала плохой план» — это неверная статистика или параметр стоимости, не соответствующий железу. Как читать конкретный план Postgres — в [[explain-analyze]].

## Основное

### Конвейер
| Стадия | Вход → выход | Что может пойти не так |
|---|---|---|
| Парсер | текст SQL → дерево разбора; синтаксис и разрешение имён | синтаксическая ошибка, неизвестный столбец |
| Переписчик | встраиваются представления и `RULE`, присоединяются запросы `WITH`, добавляются предикаты row-level security | стопка представлений из 5 уровней превращается в нечитаемый join |
| Планировщик | дерево разбора → самое дешёвое дерево плана | неверные оценки, взрыв числа порядков join |
| Исполнитель | дерево плана → строки, отдаваемые клиенту потоком | ограничения памяти (`work_mem`) приводят к сбросу на диск |

- SQL **декларативен**: он говорит, *какие* строки нужны, а не *как* их получить. Один и тот же запрос может выполниться как последовательное сканирование плюс hash join или как index scan плюс nested loop; решает планировщик. Переписать запрос «ради производительности» на деле значит дать планировщику лучшие варианты.
- Подготовленные выражения (prepared statements) разделяют конвейер: разбор и планирование один раз, выполнение много раз (на стороне сервера после пяти выполнений в JDBC-драйвере Postgres). **Обобщённый план (generic plan)**, построенный без значений параметров, может быть хуже индивидуального; Postgres сравнивает оба и может переключиться (`plan_cache_mode`).

### Что выбирает планировщик
- **Метод доступа** для каждой таблицы: последовательное сканирование, index scan, index-only scan, bitmap scan. Выбор зависит от селективности и от того, покрывает ли индекс столбцы ([[database-indexes]], [[postgres-indexes]]).
- **Алгоритм join** для каждой пары входов (сторона SQL — в [[sql-joins-and-commands]]):
  | Алгоритм | Форма стоимости | Лучше всего, когда |
  |---|---|---|
  | Nested loop | строки внешней стороны × поиск во внутренней | внешняя сторона мала, а у внутренней есть индекс по ключу join |
  | Hash join | построить хеш меньшей стороны, проверять по нему большую | join по равенству на средних/больших наборах, которые помещаются в `work_mem` |
  | Merge join | отсортировать обе стороны и пройти их параллельно | оба входа уже отсортированы (порядок индекса) или наборы очень большие |
- **Порядок join**: для *n* таблиц существует примерно *n!* порядков. До `join_collapse_limit` (8 в Postgres) планировщик перебирает их полностью; дальше он переключается на генетический поиск (`geqo`), и качество плана становится недетерминированным. Join двенадцати таблиц от ORM сложны не просто так.
- **Где сортировать, агрегировать, убирать дубликаты**: узла `Sort` удаётся избежать, если индекс уже даёт нужный порядок; выбор между `HashAggregate` и `GroupAggregate` зависит от оценочного числа групп.

### Модель стоимости
- Стоимость — безразмерное число, построенное из параметров: `seq_page_cost = 1`, `random_page_cost = 4` (на SSD ставь 1.1, значение по умолчанию рассчитано на вращающиеся диски), `cpu_tuple_cost = 0.01`, `cpu_operator_cost = 0.0025`, `effective_cache_size` (какую часть данных планировщик может считать находящейся в кэше ОС).
- Каждый узел плана получает `startup cost` (до первой строки) и `total cost`. Запрос с `LIMIT 10` предпочитает планы с низкой стартовой стоимостью, даже если общая была бы хуже; поэтому `ORDER BY created_at LIMIT 10` так любит индекс по `created_at`.
- Стоимость никогда не измеряет миллисекунды; два плана со стоимостью 100 и 120 — «примерно одинаковые», а 100 000 против 100 — это уже другой путь доступа.

### Статистика
- `ANALYZE` делает выборку из таблицы (`default_statistics_target = 100` → 30 000 строк) и сохраняет для каждого столбца: `null_frac`, `n_distinct`, самые частые значения и их частоты, гистограмму остальных и `correlation` между порядком столбца и физическим порядком (от этого зависит, дёшев ли диапазонный index scan).
- Autovacuum запускает `ANALYZE` примерно после изменения 10 % строк (`autovacuum_analyze_scale_factor`). Массовая загрузка десяти миллионов строк с запросами до следующего analyze даёт планы, построенные для пустой таблицы: nested loop повсюду, минуты вместо миллисекунд. После массовых операций запускай `ANALYZE` явно ([[postgres-vacuum-and-bloat]]).
- Столбцы считаются **независимыми**: `WHERE city = 'Bishkek' AND country = 'KG'` перемножает две селективности и недооценивает число строк на порядки. Это исправляет `CREATE STATISTICS (dependencies, ndistinct) ON city, country FROM addresses` (Postgres 10+).
- У выражений (`date_trunc('day', ts)`) нет статистики, если не создать индекс по выражению или расширенную статистику по выражению (PG 14+).

### Модель исполнителя
- Модель Volcano / итераторов: каждый узел реализует `next()`, корень тянет строки из дочерних узлов. Строки проходят потоком без материализации, кроме **блокирующих** узлов: `Sort`, `HashAggregate`, сторона построения `Hash Join`, `Materialize`. Им нужна память, ограниченная `work_mem` на узел (не на запрос); при превышении данные сбрасываются во временные файлы (`Sort Method: external merge Disk:` в плане).
- Postgres 9.6+ запускает параллельные воркеры для сканирований, join и агрегаций, когда оценочная стоимость превышает `parallel_setup_cost`; в плане видно `Gather` с `Workers Planned/Launched`.
- JIT-компиляция выражений (PG 11+) включается для дорогих аналитических запросов; для OLTP она обычно отключается на уровне запроса порогами стоимости.

## Пример
```sql
-- Ошибка оценки планировщика из-за коррелированных столбцов и её исправление
EXPLAIN SELECT * FROM sim_profiles WHERE operator = 'beeline_kg' AND country = 'KG';
--  Seq Scan on sim_profiles  (cost=0.00..21500.00 rows=120 width=96)
--    Filter: ((operator = 'beeline_kg') AND (country = 'KG'))
-- rows=120 — неверно: каждый профиль beeline_kg находится в KG, реальное число — 400 000.

CREATE STATISTICS sim_profiles_op_country (dependencies)
  ON operator, country FROM sim_profiles;
ANALYZE sim_profiles;

EXPLAIN SELECT * FROM sim_profiles WHERE operator = 'beeline_kg' AND country = 'KG';
--  Seq Scan on sim_profiles  (cost=0.00..21500.00 rows=398500 width=96)
-- Теперь join с этой таблицей будет использовать hash join вместо 400 000 поисков в nested loop.
```

## Подводные камни
- Доверять `EXPLAIN` без `ANALYZE`: оценки — это мнение планировщика, фактические строки — реальность; разрыв между ними и есть баг.
- `random_page_cost = 4` на NVMe-накопителях подталкивает планировщик к последовательным сканированиям таблиц, которые индекс обслужил бы в десять раз быстрее.
- Глобальная настройка `work_mem`: значение действует на каждый узел сортировки/хеша в каждом backend, так что 200 соединений × 5 узлов × 256 MB могут уронить сервер. Вместо этого задавай его на уровне сессии для отчётных запросов ([[postgres-performance-checklist]]).
- Запросы от ORM с `IN (?, ?, ..., ?)` на 10 000 id обходят кэш планов и порождают отдельный план для каждого размера пачки ([[jpa-n-plus-one]]).
- Чтение реальных планов: [[explain-analyze]]; индексная сторона выбора планировщика: [[database-indexes]].
