## Кратко
Индекс — это дополнительная структура данных рядом с таблицей, которая позволяет СУБД находить строки по условию, не сканируя всю таблицу. Структура по умолчанию — B-tree: отсортированные ключи с указателями на строки, поиск за O(log n), поддерживает равенство, диапазоны и сортировку. Каждый индекс стоит времени на запись и места на диске и используется только тогда, когда условие достаточно селективно, чтобы чтение индекса плюс строк обходилось дешевле чтения всей таблицы. Типы, специфичные для Postgres (GIN, BRIN, частичные, `INCLUDE`), — в [[postgres-indexes]].

## Основное

### Как работает индекс
- Без индекса: **полное сканирование таблицы (full table scan)** (`Seq Scan`), O(n), читается каждая страница.
- С B-tree: корень → внутренние страницы → листовые страницы хранят `(key, row pointer)`, отсортированные по ключу; поиск спускается на 3–4 уровня для миллионов строк, а затем идёт по указателям к страницам таблицы (heap). В Postgres указатель — это `ctid` (страница, смещение); в MySQL InnoDB вторичный индекс хранит первичный ключ, и поиск идёт через кластерный индекс по PK.
- Листовые страницы связаны между собой, поэтому диапазон (`BETWEEN`, `>`, `LIKE 'abc%'`) и `ORDER BY` по ключу — это один проход по листьям; индекс также может выдавать отсортированный результат и избавить от сортировки.
- **Уникальный** индекс — физическая реализация ограничений `PRIMARY KEY` и `UNIQUE` ([[constraints-and-relationships]]).

### Типы индексов (в общем)
| Тип | Поддерживает | Примечания |
|---|---|---|
| **B-tree** | `=`, `<`, `>`, `BETWEEN`, `IN`, `IS NULL`, `ORDER BY`, префиксный `LIKE` | по умолчанию везде; подходит для 90 % столбцов |
| **Hash** | только `=` | чуть меньше/быстрее для равенства по длинным значениям; без диапазонов и сортировки; в Postgres устойчив к сбоям только с PG 10 |
| **Кластерный (clustered)** | сама таблица хранится в порядке ключа | первичный ключ InnoDB и кластерный индекс SQL Server; один на таблицу. В Postgres кластерного индекса нет; `CLUSTER` переупорядочивает один раз и порядок не поддерживает |
| **Некластерный / вторичный** | отдельная структура, указывающая на строки | сколько угодно на таблицу; все индексы Postgres |
| Bitmap, GIN, GiST, BRIN, полнотекстовые, пространственные | принадлежность множеству, вхождение, диапазоны, текст | зависят от движка, см. [[postgres-indexes]] |

### Составные (многоколоночные) индексы
- `(a, b, c)` отсортирован по `a`, затем по `b` внутри `a`, затем по `c`. Он обслуживает `WHERE a = ?`, `WHERE a = ? AND b = ?`, `a = ? AND b > ?`, но **не** обслуживает эффективно `WHERE b = ?` сам по себе (правило левого префикса, leftmost-prefix rule).
- Сначала столбцы с равенством, затем один столбец с диапазоном, затем столбцы для `ORDER BY`. `(status, created_at)` обслуживает `WHERE status = 'NEW' ORDER BY created_at`; `(created_at, status)` — нет.
- Для предиката по двум столбцам один составной индекс обычно лучше двух одноколоночных (планировщик может объединить их через bitmap scan, но это стоит ресурсов).

### Покрывающие индексы и index-only scan
- Если каждый нужный запросу столбец **есть в индексе**, движок вообще не обращается к таблице: это index-only scan. Дополнительные столбцы добавляются через `INCLUDE (...)` (Postgres 11+, SQL Server) или просто дописываются в ключ.
- В Postgres index-only scan всё равно должен проверять видимость строк по карте видимости (visibility map); на часто обновляемой таблице без недавнего `VACUUM` он скатывается к чтению heap.

### Селективность
- Селективность — доля строк, которую возвращает условие. Индекс по `status` с тремя значениями, возвращающий 40 % таблицы, бесполезен: читать 40 % строк по случайным указателям из индекса медленнее, чем последовательное сканирование, и планировщик знает это из статистики (`ANALYZE`).
- Эмпирическое правило: индекс окупается, когда предикат возвращает заметно меньше ~5–10 % строк или когда он даёт сортировку/limit (`ORDER BY created_at DESC LIMIT 20`).
- Столбцы с малой кардинальностью всё равно имеют смысл внутри составного или частичного индекса (`WHERE status = 'PENDING'` на таблице-очереди, где в ожидании 0,1 % строк).
- После массовых загрузок статистика устаревает; запускай `ANALYZE`, смотри в `EXPLAIN (ANALYZE, BUFFERS)` на расхождения «оценка строк vs факт».

### Когда индексы вредят
- **Запись**: каждый `INSERT`/`DELETE` обновляет каждый индекс; `UPDATE` индексированного столбца тоже (HOT-обновления в Postgres избегают этого, только если ни один индексированный столбец не изменился и на странице есть место). Десять индексов на горячей таблице могут вдвое снизить скорость вставки.
- **Диск и кэш**: индексы конкурируют со страницами таблиц за `shared_buffers`/кэш ОС; большой неиспользуемый индекс вытесняет полезные данные.
- **Раздувание (bloat)**: удалённые ключи оставляют мёртвые записи до vacuum; B-tree никогда не сжимаются; это исправляет `REINDEX CONCURRENTLY`.
- **Функции и приведения типов отключают индекс**: `WHERE lower(email) = ?`, `WHERE created_at::date = ?`, `WHERE id = '42'` (text против bigint) не используют обычный индекс; создай индекс по выражению или перепиши предикат как диапазон.
- Ведущий шаблон `LIKE '%abc%'` не может использовать B-tree.
- Неиспользуемые индексы нужно находить (`pg_stat_user_indexes.idx_scan`) и удалять.

## Пример
```sql
-- Таблица-очередь: воркеры забирают самые старые ожидающие строки для заданного шарда
CREATE TABLE esim_orders (
    id          bigint PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
    shard       smallint    NOT NULL,
    status      varchar(16) NOT NULL,
    created_at  timestamptz NOT NULL DEFAULT now(),
    payload     jsonb       NOT NULL
);

-- сначала столбцы с равенством, затем столбец диапазона/сортировки
CREATE INDEX esim_orders_pending_idx
    ON esim_orders (shard, created_at)
    WHERE status = 'PENDING';           -- частичный: крошечный, только нужные строки

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, payload FROM esim_orders
WHERE shard = 3 AND status = 'PENDING'
ORDER BY created_at
LIMIT 100 FOR UPDATE SKIP LOCKED;
-- Ожидаем: Index Scan using esim_orders_pending_idx, без узла Sort
```

## Подводные камни
- Индексы на каждом столбце «на всякий случай» замедляют запись, а полезные индексы вынуждены конкурировать за кэш.
- Индекс, который никогда не используется, потому что приложение приводит тип столбца или оборачивает его в функцию: сравни текст запроса в `pg_stat_statements` с определением индекса.
- Создание индекса в production без `CONCURRENTLY` блокирует запись на всё время построения (см. [[postgres-indexes]]).
- Забытые индексы на столбцах внешних ключей, которые Postgres не создаёт автоматически ([[constraints-and-relationships]]).
- Индекс не исправит запрос, выполняемый в цикле в приложении; про запросы на каждую строку, генерируемые ORM, см. [[jpa-n-plus-one]]; про алгоритмы join, которые используют индексы, см. [[sql-joins-and-commands]].
