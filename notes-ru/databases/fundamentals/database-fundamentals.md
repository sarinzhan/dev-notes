## Кратко
База данных — это организованное структурированное хранилище связанных данных; СУБД (Postgres, MySQL, Oracle) — программа, которая их хранит, следит за структурой и ограничениями, выполняет запросы и гарантирует транзакции. **Реляционная** база хранит данные в таблицах из строк и столбцов, связанных первичными и внешними ключами, имеет фиксированную схему, запрашивается на SQL и даёт ACID-транзакции. **NoSQL**-системы отказываются от одного или нескольких из этих свойств (таблицы, фиксированная схема, связи по внешним ключам, строгий ACID), чтобы масштабироваться горизонтально или подойти под определённую форму данных. **Представление (view)** — это сохранённый `SELECT`, который ведёт себя как таблица; **материализованное представление (materialized view)** хранит результат, и его нужно обновлять.

## Основное

### Что такое база данных
- Организованная структура для хранения, изменения и обработки больших объёмов взаимосвязанной информации. Хрестоматийный пример — телефонный справочник: записи (строки), поля (имя, номер), упорядочение (индекс).
- **СУБД** стоит между приложением и файлами: парсер и планировщик SQL, движок хранения (storage engine), буферный кэш, журнал предзаписи (write-ahead log), менеджер блокировок/MVCC, контроль доступа. Приложение обращается к ней через JDBC, пул ([[hikaricp-pool-sizing]]) и обычно ORM ([[jpa-entities-and-relationships]]).

### Реляционные базы данных
- Данные живут в **таблицах**; у каждой таблицы строгий набор типизированных столбцов (схема) и строки (записи).
- Таблицы связаны ключами: **первичный ключ** однозначно идентифицирует строку; **внешний ключ** — столбец, ссылающийся на первичный ключ в другой таблице, и именно это делает данные «реляционными» (см. [[constraints-and-relationships]]).
- Схема задаётся заранее и соблюдается: типы, `NOT NULL`, уникальность, проверки.
- Язык — **SQL**, который делится на DDL, DML, DCL, TCL (см. [[sql-joins-and-commands]]).
- Транзакции с гарантиями **ACID** (см. [[transactions-acid-and-isolation]]); стандартный способ сделать многошаговое изменение по принципу «всё или ничего».
- Схема проектируется через **нормализацию**, чтобы убрать избыточность, а затем выборочно денормализуется ради скорости чтения (см. [[normalization-and-denormalization]]).
- Чтение ускоряют **индексы** (см. [[database-indexes]], [[postgres-indexes]]).
- Примеры: PostgreSQL (выбор по умолчанию для новых сервисов), MySQL/MariaDB, Oracle, SQL Server, SQLite.

### NoSQL-базы данных
Их выбирают для очень больших объёмов, высокой пропускной способности записи, гибких или вложенных данных или горизонтального масштабирования на много узлов. Основные семейства:
| Тип | Пример | Модель данных | Типичное применение |
|---|---|---|---|
| Ключ-значение (key-value) | Redis, DynamoDB | ключ → непрозрачное значение или небольшая структура | кэши, сессии, счётчики, очереди ([[redis-data-structures]]) |
| Документная | MongoDB, Couchbase | JSON-подобные документы, вложенные, с гибкой схемой | каталоги товаров, профили пользователей, CMS |
| Графовая | Neo4j | узлы и рёбра со свойствами | социальные графы, мошеннические группы, рекомендации |
| Колоночная (wide-column) | Apache Cassandra, HBase, ScyllaDB | ключ партиции → отсортированные строки из столбцов | временные ряды, журналы событий, интенсивная запись в большом масштабе |
- Компромиссы: обычно более слабые транзакции (в пределах документа / партиции), согласованность в конечном счёте (eventual consistency) между репликами, нет join (данные денормализуют и дублируют), шаблоны запросов должны быть известны на этапе проектирования.
- Postgres покрывает многие документные сценарии с помощью `jsonb` + GIN-индексов, прежде чем понадобится вторая база.

### Представления
- **Представление (view)** — виртуальная таблица, заданная `SELECT` по одной или нескольким таблицам. Данных оно не хранит: каждый запрос к нему выполняет исходный `SELECT` в момент обращения (планировщик его встраивает).
- Зачем: **безопасность** (показать только часть столбцов/строк, выдать права на представление, а не на таблицы), **упрощение** (спрятать join пяти таблиц за одним именем), **стабильность** (приложение продолжает запрашивать `v_customer_summary`, пока под ним рефакторят таблицы).
- Простые представления (одна таблица, без агрегатов) в Postgres обновляемые; `INSERT`/`UPDATE` проходят в базовую таблицу. `WITH CHECK OPTION` запрещает записывать строки, которые представление не показало бы.
- **Материализованное представление** физически хранит результат; оно быстрое, как таблица, и его можно индексировать, но показывает данные на момент последнего `REFRESH MATERIALIZED VIEW` (используй `CONCURRENTLY` с уникальным индексом, чтобы обновлять, не блокируя читателей). Хорошо для дашбордов и тяжёлых агрегатов по расписанию; не подходит для всего, что должно быть актуальным.
- Представление можно отобразить в JPA как read-only `@Entity` (`@Immutable`).

### Масштабирование (в источнике этот раздел оставлен недописанным)
- **Вертикальное**: машина помощнее; проще всего, но есть потолок.
- **Репликация**: один primary принимает запись, реплики (потоковая передача WAL) обслуживают чтение; задержка репликации (replication lag) означает, что чтение сразу после записи с реплики может вернуть устаревшие данные. Spring направляет чтения через маршрутизирующий `DataSource` и `@Transactional(readOnly = true)`.
- **Шардирование (sharding)**: строки распределяются по независимым базам по ключу (id клиента, регион); каждый шард меньше и быстрее, но join и транзакции между шардами становятся проблемой приложения. Postgres: Citus или шардирование на уровне приложения.
- **Партиционирование (partitioning)**: одна логическая таблица разбита на дочерние таблицы внутри одного сервера (по диапазону дат, по хешу); индексы остаются маленькими, а удаление старых данных превращается в `DROP TABLE`.
- Хранимые **процедуры/функции** (PL/pgSQL) и **триггеры** выполняют логику внутри СУБД: быстро для работы рядом с данными (таблицы аудита, счётчики), но их трудно версионировать и тестировать. Лучше код приложения, если только логика не касается исключительно целостности данных.

## Пример
```sql
-- Представление, которое прячет join и показывает только нечувствительные столбцы
CREATE VIEW v_active_subscriptions AS
SELECT s.id, c.msisdn, t.code AS tariff, s.activated_at
FROM subscriptions s
JOIN customers c ON c.id = s.customer_id
JOIN tariffs   t ON t.id = s.tariff_id
WHERE s.status = 'ACTIVE';

GRANT SELECT ON v_active_subscriptions TO reporting;

-- Материализованное представление для дашборда, обновляется планировщиком
CREATE MATERIALIZED VIEW mv_daily_activations AS
SELECT date_trunc('day', activated_at) AS day, tariff_id, count(*) AS n
FROM subscriptions GROUP BY 1, 2;
CREATE UNIQUE INDEX ON mv_daily_activations (day, tariff_id);
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_daily_activations;
```

## Подводные камни
- Представление над представлением над представлением: планировщик их встраивает, но итоговый план никто не может прочитать; держи один уровень.
- `SELECT *` в определении представления фиксирует список столбцов в момент создания; новые столбцы таблицы не появятся, пока представление не пересоздадут.
- Материализованные представления не обновляются сами; если забыть про планировщик, навсегда будут видны цифры прошлого месяца.
- «Нам нужен NoSQL ради масштаба» до каких-либо замеров: хорошо проиндексированный Postgres на одной машине выдерживает десятки тысяч транзакций в секунду.
