## Кратко
`LIMIT 10 OFFSET 100000` не прыгает к строке 100 000: база читает и **выбрасывает** 100 000 строк, а потом возвращает 10. Каждая следующая страница медленнее, а строки, вставленные или удалённые между запросами, сдвигают окно, и пользователь видит дубли или пропускает строки. **Keyset-пагинация** (seek method, курсорная пагинация) запоминает последний ключ предыдущей страницы и запрашивает `WHERE id < :last_id ORDER BY id DESC LIMIT 10`: поиск по индексу прямо к началу страницы, одинаковая стоимость на странице 1 и на странице 10 000.

## Основное
### Почему OFFSET медленный
- `ORDER BY id DESC OFFSET 1000 LIMIT 10` = достать 1 010 строк через индекс (и обычно ещё из heap), первые 1 000 выбросить. Стоимость O(offset + limit).
- На большой таблице страница 1 занимает миллисекунды, страница 10 000 — секунды; при `ORDER BY` по неиндексированной колонке база сначала сортирует всё.
- `EXPLAIN ANALYZE` это показывает: дочерний узел Limit возвращает `offset + limit` строк ([[explain-analyze]]).

### Почему OFFSET неправильный
- Между страницей 1 и 2 сверху вставилась новая строка: все строки сдвигаются на одну вниз, страница 2 повторяет последнюю строку страницы 1.
- Строка удалена: одна строка пропускается и никогда не будет показана.
- Больше всего страдают бесконечные ленты и выгрузки данных.

### Keyset (seek) пагинация
- Клиент возвращает ключ сортировки последней увиденной строки; запрос начинается **после** него: `WHERE id < 5001 ORDER BY id DESC LIMIT 10`.
- При индексе по ключу сортировки база спускается по B+-дереву к 5001 и читает 10 записей ([[b-tree-vs-b-plus-tree]]). Стоимость O(log n + limit) для любой страницы.
- Вставки и удаления не сдвигают страницы: следующая страница всегда начинается строго после последнего увиденного ключа.
- Неуникальным ключам сортировки нужен разрешающий ключ: сортировать по `(created_at, id)` и сравнивать **значением строки** (row value): `WHERE (created_at, id) < (:ts, :id)`, с индексом по `(created_at, id)`.
- API возвращает непрозрачный **курсор** (например, base64 от `created_at|id`) вместо номера страницы ([[api-design-for-system-design]]).

### Компромиссы
| | OFFSET | Keyset |
|---|---|---|
| Стоимость страницы n | растёт с n | постоянная |
| Устойчивость к вставкам/удалениям | нет | да |
| Перейти на страницу 57 | да | нет (только следующая/предыдущая) |
| Общее число / номера страниц | легко (но `COUNT(*)` сам дорогой) | неестественно |
| Произвольная сортировка | по любой колонке | нужен индекс под сортировку + уникальный разрешающий ключ |

- OFFSET подходит для маленьких таблиц, админок и первых нескольких страниц. Для лент, API и выгрузок — keyset.
- Предыдущая страница: перевернуть сравнение и порядок (`WHERE id > :first_id ORDER BY id ASC LIMIT 10`), затем развернуть результат в приложении.
- Пакетная обработка (задачи по всем строкам) — keyset по своей природе: `WHERE id > :last ORDER BY id LIMIT 1000` в цикле, никогда OFFSET.

## Пример
```sql
CREATE INDEX ON news (created_at DESC, id DESC);

-- page 1
SELECT id, title, created_at FROM news
ORDER BY created_at DESC, id DESC LIMIT 20;

-- next page: client sent the last row's (created_at, id)
SELECT id, title, created_at FROM news
WHERE (created_at, id) < ('2026-10-30 09:15:00+06', 48213)
ORDER BY created_at DESC, id DESC LIMIT 20;
```

```java
// Spring Data JPA: keyset scrolling (Spring Data 3.1+)
Window<News> page = repo.findFirst20ByOrderByCreatedAtDescIdDesc(ScrollPosition.keyset());
Window<News> next = repo.findFirst20ByOrderByCreatedAtDescIdDesc(page.positionAt(page.size() - 1));
```

## Подводные камни
- Keyset по неуникальной колонке без разрешающего ключа: строки с одинаковым значением пропускаются или повторяются.
- Нет индекса, подходящего под `ORDER BY`: keyset всё равно сортирует всю таблицу.
- `Pageable` в Spring Data выполняет лишний запрос `COUNT(*)` на каждую страницу; используй `Slice` или `Window`, если итоги не нужны ([[postgres-performance-checklist]]).
- OFFSET в пакетных задачах по миллионам строк: квадратичная суммарная стоимость.
