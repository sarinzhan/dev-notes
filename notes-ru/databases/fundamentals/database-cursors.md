## Кратко
Запрос, возвращающий 10 млн строк, не стоит загружать в память целиком. **Серверный курсор** держит результат открытым на сервере базы и отдаёт его клиенту пачками (`FETCH 1000`), поэтому память клиента остаётся маленькой — ценой открытой транзакции и ресурсов сервера. **Клиентский курсор** (по умолчанию в большинстве драйверов) вытягивает весь результат по сети в память клиента и потом даёт его перебирать: просто и быстро для маленьких результатов, `OutOfMemoryError` для больших. В JDBC с Postgres серверный курсор получается только при `autoCommit=false` и `fetchSize > 0`.

## Основное
### Что такое курсор
- Курсор — именованный указатель в результат запроса. `DECLARE c CURSOR FOR SELECT ...` планирует и запускает запрос; `FETCH n FROM c` возвращает следующие n строк; `CLOSE c` освобождает его.
- База не материализует сначала все строки (для большинства планов): она выдаёт строки по мере выборки, поэтому первые строки приходят быстро.
- В Postgres курсор живёт внутри транзакции (если только не `WITH HOLD`, который материализует результат при коммите).

### Серверный курсор
- Плюсы: память клиента пропорциональна пачке, а не результату; можно остановиться раньше; потоковая обработка (выгрузки, ETL, миграции).
- Минусы: транзакция открыта, пока идёт перебор: она держит снимок, поэтому VACUUM не может убрать мёртвые строки, появившиеся за это время ([[postgres-vacuum-and-bloat]]); backend и его память заняты; больше круговых обменов (по одному на пачку); не работает через PgBouncer в режиме transaction между транзакциями.
- Когда использовать: большие чтения, которые последовательно обрабатывает один потребитель.

### Клиентский курсор
- Драйвер выполняет запрос и получает **все** строки, прежде чем вернуть первую. Перебор локальный.
- Плюсы: один круговой обмен (плюс потоковая передача TCP), сервер сразу освобождается, транзакцию можно закончить.
- Минусы: память = весь результат; время до первой строки = время до последней.
- Когда использовать: маленькие и средние результаты, то есть большинство OLTP-запросов.

| | Серверный | Клиентский |
|---|---|---|
| Память клиента | одна пачка | весь результат |
| Ресурсы сервера | заняты во время перебора | освобождаются после запроса |
| Транзакция | открыта во время перебора | можно закрыть |
| Круговые обмены | по одному на пачку | один |
| Задержка первой строки | маленькая | после прихода всех строк |

### Другие применения и типы курсоров
- `UPDATE ... WHERE CURRENT OF c`: обновить строку, на которой стоит курсор.
- Прокручиваемые курсоры (`SCROLL`) умеют двигаться назад; `INSENSITIVE` и `SENSITIVE`: видны ли изменения, сделанные после открытия.
- В SQL Server много типов серверных курсоров: **static** (копия результата в tempdb), **keyset** (фиксированный набор ключей, значения перечитываются), **dynamic** (видит все изменения) и **fast-forward** (только чтение и только вперёд, самый дешёвый). Построчные циклы T-SQL по курсорам — классический антипаттерн производительности; SQL над множествами обычно в 10–100 раз быстрее.
- Запросы MongoDB всегда возвращают курсор: первая пачка (101 документ или 16 МБ), затем `getMore` на каждую пачку; простаивающие курсоры закрываются через 10 минут ([[database-wire-protocols]]).
- Для постраничной выдачи в API используй keyset-пагинацию, а не курсор, удерживаемый между HTTP-запросами ([[pagination-offset-vs-keyset]]).

## Пример
```sql
BEGIN;
DECLARE big_orders CURSOR FOR
  SELECT id, customer_id, amount FROM orders WHERE created_at >= '2026-01-01';
FETCH 1000 FROM big_orders;   -- rows 1..1000
FETCH 1000 FROM big_orders;   -- rows 1001..2000
CLOSE big_orders;
COMMIT;
```

```java
// JDBC + Postgres: server-side cursor needs autoCommit=false and a fetch size
try (Connection conn = dataSource.getConnection()) {
    conn.setAutoCommit(false);
    try (PreparedStatement ps = conn.prepareStatement(
            "SELECT id, customer_id, amount FROM orders WHERE created_at >= ?")) {
        ps.setFetchSize(1_000);                       // without this the driver loads everything
        ps.setObject(1, LocalDate.of(2026, 1, 1));
        try (ResultSet rs = ps.executeQuery()) {
            while (rs.next()) exporter.write(rs.getLong(1), rs.getLong(2), rs.getBigDecimal(3));
        }
    }
    conn.commit();
}
// Spring Data JPA: Stream<Order> findAllBy...() with @QueryHints(HINT_FETCH_SIZE) inside @Transactional(readOnly = true)
```

## Подводные камни
- `setFetchSize` при `autoCommit=true` в Postgres: молча игнорируется, грузится весь результат.
- MySQL Connector/J стримит только при `fetchSize = Integer.MIN_VALUE` или `useCursorFetch=true`.
- Держать курсор (и транзакцию) открытым часами во время медленной выгрузки: раздувание и заблокированный VACUUM; лучше обрабатывать keyset-пачками с короткими транзакциями.
- Медленная обработка каждой строки внутри цикла держит backend; буферизуй в очередь или файл и заканчивай чтение быстро.
