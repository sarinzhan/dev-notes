## Кратко
Когда транзакции одновременно работают с одними и теми же данными, база должна сохранить правильный результат. Для этого она использует **блокировки**: **разделяемая** (shared) пускает много читателей, **исключительная** (exclusive) пускает одного писателя. Блокировки, удерживаемые до коммита (**двухфазная блокировка**), дают сериализуемое выполнение, но могут образовывать **взаимоблокировки** (deadlocks), которые база обнаруживает и разрывает, убивая одну транзакцию. Приложение выбирает между **пессимистичным** управлением (сначала блокировка: `SELECT ... FOR UPDATE`) и **оптимистичным** (без блокировки, проверка версии при записи и повтор). Классический пример — проблема **двойного бронирования**: два пользователя бронируют одно и то же место.

## Основное
### Разделяемые и исключительные блокировки
- **Разделяемая (S, на чтение)**: её одновременно могут держать многие транзакции на одном объекте; пока она удерживается, никто не может писать.
- **Исключительная (X, на запись)**: держатель один; блокирует и других писателей, и других желающих заблокировать. Нельзя получить X, пока кто-то держит S, и наоборот.
- Нужны для согласованности: например, сверка в банке читает все счета под S-блокировками, чтобы ни один перевод не изменил их посреди отчёта; обновление баланса берёт X на строку.
- MVCC-базы (Postgres, InnoDB, Oracle) в основном обходятся без блокировок на чтение: обычный `SELECT` читает снимок и никогда не блокирует писателей и не блокируется ими. Блокировки берут записи и явные `FOR SHARE` / `FOR UPDATE`. Режимы блокировок подробно: [[postgres-locks]].

### Взаимоблокировки
- T1 блокирует строку A и ждёт B; T2 блокирует B и ждёт A. Ни одна не может продолжить.
- Базы находят цикл в графе ожиданий (Postgres проверяет через `deadlock_timeout`, 1 с; InnoDB сразу) и прерывают одну жертву с ошибкой (`40P01` в Postgres, `1213` в MySQL). Приложение должно **повторить** всю транзакцию.
- Частые причины: обновление одних и тех же строк в разном порядке, проверки внешних ключей, берущие разделяемые блокировки на родителе, вставки в уникальный индекс с одинаковым ключом.
- Профилактика: блокировать в одинаковом порядке (например, сортировать id), держать транзакции короткими, блокировать всё нужное сразу. Теория: [[deadlocks-and-synchronization-primitives]].

### Двухфазная блокировка (2PL)
- **Фаза роста**: транзакция берёт блокировки и не отпускает. **Фаза сокращения**: как только она отпустила хоть одну, новых она не берёт.
- **Строгая 2PL** держит все блокировки записи до коммита/отката (так делают настоящие базы): никто не видит неподтверждённых данных, и выполнение сериализуемо.
- Цена: блокировки держатся долго, конкурентность падает, становятся возможны взаимоблокировки. `SERIALIZABLE` в SQL Server и MySQL основан на блокировках; `SERIALIZABLE` в Postgres вместо этого использует SSI (оптимистичный, см. [[postgres-isolation-levels]]).

### Проблема двойного бронирования
- Два пользователя видят место 13 свободным, и оба выполняют `UPDATE seats SET booked_by = ? WHERE id = 13`. На READ COMMITTED второе обновление просто перезаписывает первое: потерянное обновление. Оба получают «успех».
- **Решение 1, пессимистичная блокировка строки**: `SELECT ... WHERE id = 13 AND booked_by IS NULL FOR UPDATE` внутри транзакции. Вторая транзакция ждёт коммита первой, затем перечитывает строку (Postgres заново проверяет WHERE на новой версии) и видит, что место занято.
- **Решение 2, атомарное условное обновление**: `UPDATE seats SET booked_by = ? WHERE id = 13 AND booked_by IS NULL` и проверка числа затронутых строк (0 = место досталось другому). Одно выражение, без явной блокировки; блокировка строки, которую берёт UPDATE, упорядочивает две транзакции.
- **Решение 3, ограничение**: уникальный индекс по `(event_id, seat_no)` в таблице `bookings`; второй INSERT падает с нарушением уникальности. Работает даже без заранее существующей строки, которую можно было бы заблокировать.
- **Решение 4, SERIALIZABLE**: пусть база сама обнаружит конфликт, а приложение повторит на `40001`.
- Что **не** работает: проверка в приложении («SELECT, если свободно — UPDATE») без блокировки.

### Оптимистичное и пессимистичное
| | Пессимистичное | Оптимистичное |
|---|---|---|
| Как | блокировать до чтения (`FOR UPDATE`) | читать свободно, писать с `WHERE version = ?`; 0 строк = конфликт |
| Конфликты | ждать | обнаружить и повторить |
| Хорошо, когда | конфликты часты, повтор дорог, транзакции короткие | конфликты редки, преобладает чтение, долгое «время раздумий» (пользователь правит форму) |
| Риски | ожидания, взаимоблокировки, эскалация блокировок (SQL Server превращает много блокировок строк в блокировку таблицы) | лавина повторов при высокой конкуренции |
| В JPA | `@Lock(PESSIMISTIC_WRITE)` | `@Version` ([[jpa-locking]]) |

- Память под блокировки: InnoDB хранит блокировки строк битовой картой на страницу; SQL Server эскалирует тысячи блокировок строк в блокировку таблицы; Postgres хранит блокировки строк в заголовке кортежа (без лимита памяти), но `FOR SHARE` от многих транзакций использует MultiXact.

### Особенности InnoDB
- **Блокировки записей** (record locks) блокируют записи индекса, а не строки: UPDATE без подходящего индекса блокирует каждую запись, которую сканирует.
- **Блокировки промежутков** (gap locks) и **next-key** (запись + промежуток перед ней) на REPEATABLE READ предотвращают фантомы: `SELECT ... WHERE age BETWEEN 20 AND 30 FOR UPDATE` блокирует вставку `age = 25`. Они же вызывают неожиданные взаимоблокировки между вставками.
- **Блокировки намерения вставки** (insert intention) позволяют параллельным вставкам в один промежуток пройти, если позиции разные.
- Понизь уровень до READ COMMITTED, чтобы отключить большую часть блокировок промежутков, если защита от фантомов не нужна.

## Пример
```sql
-- pessimistic: lock the seat, then book it
BEGIN;
SELECT id FROM seats WHERE id = 13 AND booked_by IS NULL FOR UPDATE;  -- blocks a concurrent booker
-- 0 rows → already booked: ROLLBACK and report
UPDATE seats SET booked_by = 'alice' WHERE id = 13;
COMMIT;

-- optimistic / atomic: one statement, check the row count
UPDATE seats SET booked_by = 'bob' WHERE id = 13 AND booked_by IS NULL;   -- UPDATE 0 → lost the race

-- consistent lock order to avoid deadlocks in a transfer
SELECT id FROM accounts WHERE id IN (7, 3) ORDER BY id FOR UPDATE;
```

## Подводные камни
- Чтение, затем запись в коде приложения без блокировки или условия в UPDATE: потерянные обновления.
- Блокировка строк в разном порядке в разных ветках кода: взаимоблокировки под нагрузкой. Всегда повторяй на `40P01`/`40001`.
- Держать блокировку строки во время вызова внешнего сервиса: все остальные ждут сеть.
- UPDATE/DELETE в InnoDB по неиндексированной колонке блокирует намного больше, чем подходящие строки.
