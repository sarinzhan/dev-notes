## Кратко
Сборщик мусора находит объекты, которые больше не достижимы из **корней GC** (GC roots), и освобождает их память; HotSpot использует трассировку, а не подсчёт ссылок, поэтому циклы не проблема. Каждый сборщик выполняет пометку → очистку/копирование → (уплотнение), а различаются они тем, какая часть этой работы происходит при остановленном приложении (**stop-the-world**, STW), а какая — параллельно с ним. По умолчанию: Serial на крошечных машинах, G1 начиная с Java 9 во всех остальных случаях; ZGC и Shenandoah дают паузы меньше миллисекунды на больших кучах.

## Основное
### Поиск мусора
- **Подсчёт ссылок** (reference counting): каждый объект хранит число ссылок на себя; ноль означает мусор. Дёшево и инкрементально, но два объекта, ссылающиеся друг на друга, никогда не достигают нуля, а каждая запись указателя требует обновления счётчика. JVM его не использует (используют CPython, Swift).
- **Трассировка** (tracing): объект жив, если он достижим из корня — напрямую или через другие живые объекты; всё остальное — мусор. Четыре вида корней: локальные переменные и параметры на стеке каждого потока, сами живые потоки, статические поля загруженных классов и JNI-ссылки (нативный код, удерживающий Java-объекты). Также: захваченные мониторы, константы JIT-скомпилированного кода и классы системного загрузчика.
- `System.gc()` — это *просьба* о полной сборке; большинство сборщиков её выполняют (как полную STW-сборку), а с `-XX:+DisableExplicitGC` она игнорируется. Метод не устарел, но в коде приложения ему не место. Более слабые виды ссылок, взаимодействующие со сборщиком, описаны в [[reference-types]].

### Фазы
- **Пометка (mark)**: обход от корней, пометка живых объектов (бит пометки в заголовке или битовая карта).
- **Очистка (sweep)**: освобождение непомеченных, после чего остаются «дыры» (списки свободных блоков; фрагментация).
- **Уплотнение (compact)**: живые объекты сдвигаются вместе, чтобы убрать фрагментацию; для этого нужно обновить каждую ссылку на перемещённый объект, поэтому перемещающим сборщикам нужно либо остановить приложение, либо хитрые барьеры.
- **Копирование (copy)** (используется в молодом поколении): живые объекты копируются из одного пространства в пустое; старое пространство затем освобождается целиком. Стоимость пропорциональна объёму живых данных, а не мусора, что идеально, когда большинство объектов умирает молодыми.

### Куча с поколениями
- **Слабая гипотеза о поколениях** (weak generational hypothesis): большинство объектов умирает молодыми. Поэтому куча ([[jvm-memory-areas]]) разделена на **молодое поколение** (Eden плюс два пространства выживших S0/S1) и **старое поколение** (tenured). Метаданные классов находятся в Metaspace (до Java 8 — в PermGen), а не в куче.
- **Малая сборка (minor GC)**: Eden заполнен → STW → живые объекты из Eden и активного пространства выживших копируются в другое пространство выживших; всё остальное отбрасывается разом. Каждое копирование между пространствами выживших увеличивает возраст объекта; при достижении порога (по умолчанию 15, адаптивный) объект **продвигается** (promotion) в старое поколение. Большие объекты сразу попадают в старое.
- **Большая / полная сборка (major / full GC)**: старое поколение заполняется → mark-sweep-compact по всей куче, долгая STW-пауза. Цель каждого современного сборщика — избежать этого.
- Модель стоимости: малая сборка дешёвая, потому что касается только живых молодых объектов; ссылки из старого поколения в молодое отслеживаются через **таблицу карт** (card table), чтобы сборщику не приходилось сканировать всё старое поколение в поисках корней, ведущих в Eden.

### Как сравнивать сборщики
- **Максимальная пауза (задержка, latency)**: самая длинная STW-остановка. Важна для сервисов, обслуживающих запросы.
- **Пропускная способность (throughput)**: доля общего времени, проведённого в коде приложения, а не в GC. Важна для пакетных задач.
- **Занимаемые ресурсы / накладные расходы**: дополнительный CPU (параллельные потоки, барьеры) и память (remembered sets, окрашенные указатели), которые нужны сборщику.
Максимизировать все три нельзя; каждый сборщик выбирает свою точку.

### Сборщики
| Сборщик | Флаг | С версии | Молодое | Старое | Характер |
|---|---|---|---|---|---|
| Serial | `-XX:+UseSerialGC` | 1.3 | копирование, STW | mark-sweep-compact, STW | один поток; минимальные ресурсы; по умолчанию при < 2 CPU или < 1792 МБ RAM (маленькие контейнеры!) |
| Parallel (Throughput) | `-XX:+UseParallelGC` | 1.4 | копирование, STW, многопоточное | mark-compact, STW, многопоточное | лучшая пропускная способность, долгие паузы; хорош для пакетных задач |
| CMS | `-XX:+UseConcMarkSweepGC` | 1.4 | ParNew, STW | параллельная mark-sweep, без уплотнения | короткие паузы по меркам своего времени; удалён в Java 14 |
| **G1** | `-XX:+UseG1GC` | 7u4, по умолчанию с 9 | копирование по регионам, STW | параллельная пометка + инкрементальная эвакуация | баланс между паузами и пропускной способностью; целевая пауза `-XX:MaxGCPauseMillis=200` |
| **ZGC** | `-XX:+UseZGC` | 11 экспериментальный, 15 для продакшена, с поколениями по умолчанию с 23 | параллельно с приложением | параллельно с приложением | паузы < 1 мс независимо от размера кучи (до 16 ТБ); окрашенные указатели + барьеры чтения; ~10-15 % потери пропускной способности |
| Shenandoah | `-XX:+UseShenandoahGC` | 12 экспериментальный, 15 для продакшена (Red Hat; нет в сборках Oracle) | параллельно с приложением | параллельно с приложением | те же цели, что у ZGC, через forwarding-указатели Брукса; режим с поколениями в 24 |

- CMS был выбором для низких задержек, пока G1 не созрел (по умолчанию в Java 8 был Parallel, а не CMS). Его цикл для старого поколения: начальная пометка (короткая STW, только корни) → параллельная пометка → повторная пометка (STW) → параллельная очистка. Уплотнения не было, поэтому фрагментация в конце концов вынуждала полную STW-сборку («concurrent mode failure»).
- **G1** делит кучу на одинаковые регионы (1–32 МБ, около 2048 штук), каждый из которых в любой момент — Eden, выживший, старый или humongous (объекты больше половины региона). Сборки молодого поколения эвакуируют живые объекты в свежие регионы. Параллельная пометка начинается, когда заполненность старого поколения превышает 45 % (`InitiatingHeapOccupancyPercent`); затем **смешанные сборки** (mixed collections) эвакуируют в первую очередь старые регионы с наибольшим количеством мусора («garbage first») в пределах целевой паузы, так что уплотнение инкрементальное. Дополнительно: `-XX:+UseStringDeduplication`, возврат неиспользуемой памяти ОС (Java 12+).
- **ZGC** помечает, перемещает и переназначает ссылки параллельно с приложением; единственные остановки — сканирование корней. Барьер чтения исправляет устаревшие ссылки при обращении через таблицу перенаправления. В OpenJDK он всегда был бесплатным; история про «задумывался как коммерческий» относится к ранним планам Oracle. Shenandoah вместо битов метаданных в указателях хранит forwarding-указатель в каждом объекте.

### Выбор и настройка
- Сервисы на Java 17/21 с кучей 2–32 ГБ: G1 по умолчанию; в контейнерах задавай `-Xms` = `-Xmx` и оставляй место для metaspace, потоков и прямых буферов ([[docker-containers-and-resources]]). Сервисы, чувствительные к p99, со свободным CPU: ZGC с поколениями. Пакетные задачи: Parallel.
- Проверь, какой сборщик ты на самом деле получил (контейнер с одним CPU молча получает Serial): `jcmd <pid> VM.flags`.
- Диагностика через `-Xlog:gc*`, GCeasy или JFR; скорость выделения и продвижения важнее размера кучи. Утечка выглядит как старое поколение, которое никогда не уменьшается после полных сборок; сними дамп кучи (`-XX:+HeapDumpOnOutOfMemoryError`) и посмотри на доминаторы.

## Пример
```bash
# Типичный сервис на Spring Boot на Java 21 в контейнере на 2 ГБ, 2 CPU
java -XX:+UseG1GC -XX:MaxGCPauseMillis=100 \
     -Xms1200m -Xmx1200m \
     -XX:MaxMetaspaceSize=256m -XX:MaxDirectMemorySize=128m \
     -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps \
     -Xlog:gc*,gc+age=trace:file=/logs/gc.log:time,uptime:filecount=5,filesize=20m \
     -jar app.jar

# Тот же сервис, критичный к задержкам: ZGC с поколениями (по умолчанию с поколениями на 23+, на 21 нужен флаг)
java -XX:+UseZGC -XX:+ZGenerational -Xmx1200m -Xms1200m -jar app.jar

# Чтение лога: "Pause Young (Normal) (G1 Evacuation Pause) 412M->98M(1200M) 7.3ms"
# = малая сборка, занятая куча уменьшилась с 412 МБ до 98 МБ, 7.3 мс stop-the-world.
```

## Подводные камни
- Объекты, которые достижимы, но бесполезны (статические кеши, так и не удалённые слушатели, `ThreadLocal` в потоках из пула, внутренние классы, удерживающие внешний объект, [[nested-and-anonymous-classes]]), — это утечки, которые GC исправить не может; исправляй ссылку или используй слабые/мягкие ссылки ([[reference-types]]).
- `finalize` задерживает освобождение на целый цикл и может «воскрешать» объекты; используй `Cleaner` или `try-with-resources` ([[object-class-and-reflection]]).
- Огромные humongous-выделения (большие байтовые массивы, гигантские `ArrayList`) в G1 минуют молодое поколение и фрагментируют старые регионы; обрабатывай данные потоком, а не материализуй их целиком.
- Если задать `-Xmx` больше, чем лимит контейнера минус использование вне кучи, ядро убьёт процесс по OOM без какого-либо Java-стек-трейса.
- Связанные заметки: [[jvm-memory-areas]], [[reference-types]], [[java-memory-model]].
