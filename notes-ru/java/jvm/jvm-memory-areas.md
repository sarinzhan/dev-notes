## Кратко
JVM делит память на общую **кучу** (heap; все объекты, разделённые на молодое и старое поколения), по одному приватному **стеку** на поток (фреймы с локальными переменными и стеками операндов), **Metaspace** (метаданные классов, заменил PermGen в Java 8), **кеш кода** (code cache; результат JIT) и разнообразную **нативную память** (прямые буферы, стеки потоков, структуры GC). Java-процесс использует гораздо больше, чем `-Xmx`; чтобы задать размер контейнера, нужно сложить всё это.

## Основное
### Куча
- Создаётся при старте JVM, общая для всех потоков, в ней живут все объекты и массивы; пул строк находится здесь начиная с Java 7 ([[strings-and-string-pool]]). Ограничена `-Xms` (начальный размер) и `-Xmx` (максимальный); максимум по умолчанию — 25 % RAM контейнера/хоста.
- Раскладка по поколениям в G1/Parallel/Serial: **Eden** (новые объекты), два пространства **выживших** (survivor, S0/S1, одно всегда пустое), **старое** (old/tenured; пережившие несколько малых сборок). G1 использует регионы одинакового размера, помеченные одной из этих ролей; у ZGC нет фиксированных размеров поколений. Подробности и сборщики: [[garbage-collection]].
- Выделение памяти — это сдвиг указателя внутри потоколокального буфера выделения (**TLAB**), поэтому `new` дёшев; JIT также может разложить объект на скаляры или выделить его на стеке, если escape analysis доказывает, что объект локален.
- Исчерпание: `OutOfMemoryError: Java heap space`; `GC overhead limit exceeded`, когда > 98 % времени уходит на GC, освобождающий < 2 % кучи.

### Раскладка объекта
- Заголовок: **mark word** (identity hash, биты возраста, состояние блокировки; 8 байт) + **указатель на класс** (4 байта со сжатыми указателями на классы, по умолчанию) → 12 байт, дополненные до выравнивания на 8 байт. Пустой объект занимает 16 байт; `new Integer(1)` — 16 байт ради 4 байт полезных данных.
- Сжатые указатели (compressed oops): при куче меньше 32 ГБ ссылки занимают 4 байта вместо 8. В куче на 33 ГБ может поместиться *меньше* объектов, чем в куче на 31 ГБ.
- Поля переупорядочиваются для выравнивания; массивы хранят длину. Когда это важно, измеряй с помощью JOL (`jol-core`).

### Стек потока
- Каждый поток получает свой стек при создании (`-Xss`, по умолчанию 1 МБ на 64-битном Linux; конструктор `Thread` может переопределить). В нём лежит по одному **фрейму** на каждый активный вызов метода: локальные переменные (включая `this` и параметры), стек операндов для арифметики байткода и ссылка на пул констант. Здесь живут примитивы и ссылки; объекты, на которые они указывают, находятся в куче.
- Данные стека приватны для потока, поэтому синхронизация не нужна ([[java-memory-model]]); фреймы освобождаются при возврате без участия GC.
- Переполнение: `StackOverflowError`, почти всегда неограниченная рекурсия. Нужна более глубокая рекурсия → увеличь `-Xss` или сделай алгоритм итеративным ([[data-structures]]).
- Виртуальные потоки ([[virtual-threads]]) хранят свои стеки как объекты в куче (stack chunks) и копируют их на стек потока-носителя (carrier) при монтировании; именно это делает миллионы виртуальных потоков доступными по ресурсам.
- Стеки нативных методов: используются для JNI-кода; в HotSpot это тот же стек потока ОС.

### Metaspace (и PermGen до него)
- Метаданные классов: представление каждого загруженного класса во время выполнения (методы, байткод, пул констант, vtables, аннотации). Java ≤ 7 хранила это в **PermGen** — части кучи фиксированного размера, которая давала `OutOfMemoryError: PermGen space` при redeploy и при большом количестве классов. Java 8 перенесла это в **Metaspace** в нативной памяти, который растёт по требованию; ограничивается `-XX:MaxMetaspaceSize`. Одновременно интернированные строки и статические поля переехали в кучу.
- Память освобождается, только когда загрузчик классов и все его классы становятся недостижимыми ([[class-initialization-order]]). Утекающие загрузчики (горячий redeploy, динамические прокси/лямбды, генерируемые без ограничений, скрипты Groovy) раздувают Metaspace без предела.
- Пространство сжатых классов (compressed class space) — отдельный резерв на 1 ГБ для указателей на классы (`-XX:CompressedClassSpaceSize`).

### Пул констант времени выполнения и область методов
- Для каждого класса: литералы, символьные ссылки на поля/методы/классы, разрешаемые лениво; часть Metaspace. Спецификация называет логическую область «областью методов» (method area); Metaspace — её реализация в HotSpot.

### Кеш кода
- JIT-скомпилированный машинный код, заглушки интерпретатора, адаптеры. `-XX:ReservedCodeCacheSize` (240 МБ по умолчанию при многоуровневой компиляции). Когда он заполняется, JIT перестаёт компилировать, и приложение резко замедляется с предупреждением «CodeCache is full».

### Нативная память (вне кучи)
- Прямые `ByteBuffer` ([[java-nio]]), ограниченные `-XX:MaxDirectMemorySize` (по умолчанию равно `-Xmx`); их используют Netty, клиенты Kafka и драйверы JDBC.
- Стеки потоков (`threads × Xss`), рабочая память GC (remembered sets в G1 могут занимать 10 % кучи), арены JIT-компилятора, таблицы символов, файлы, отображённые в память, нативные библиотеки, арены Foreign Function & Memory API (Java 22).
- Смотреть через `-XX:NativeMemoryTracking=summary` + `jcmd <pid> VM.native_memory summary`.

### Размер контейнера
`RSS ≈ heap (Xmx) + Metaspace + code cache + threads × Xss + direct memory + GC overhead + JVM itself`. Сервису с `-Xmx` на 1 ГБ обычно нужен контейнер на 1.5–2 ГБ. Начиная с Java 10 (`UseContainerSupport`) JVM читает лимит cgroup и задаёт по нему размер кучи по умолчанию; `-XX:MaxRAMPercentage=75` — более надёжная настройка, чем жёсткий `-Xmx`, когда размер контейнера меняется ([[docker-containers-and-resources]]).

## Пример
```java
public class OrderService {
    private static final Map<String, Tariff> TARIFFS = new HashMap<>();   // ссылка в Metaspace (static),
                                                                          // объект HashMap и записи в куче
    private final PricingRules rules;                                      // поле: внутри объекта OrderService в куче

    public long price(String tariffCode, int units) {                     // фрейм на стеке вызывающего потока:
        Tariff t = TARIFFS.get(tariffCode);                                //   this, tariffCode, units, t (ссылка)
        long base = t.unitPriceMinor() * units;                            //   base (примитив, живёт во фрейме)
        return rules.apply(base);                                          // для apply() кладётся новый фрейм
    }                                                                      // фрейм снят; base исчез, объект t остаётся,
}                                                                          // пока GC не обнаружит, что он недостижим
```
```bash
# Сколько процесс реально использует по сравнению с настроенной кучей
jcmd <pid> GC.heap_info
jcmd <pid> VM.native_memory summary      # требует -XX:NativeMemoryTracking=summary
ps -o rss= -p <pid>                       # resident set size в КБ, сравни с -Xmx
```

## Подводные камни
- «Объекты в куче, примитивы на стеке» верно только для локальных переменных; примитивные *поля* и элементы массивов живут внутри своего объекта в куче.
- `-Xmx` — это не лимит памяти процесса; когда сумма превышает лимит cgroup, историю заканчивает OOM-killer ядра, а не JVM.
- Тысячи платформенных потоков × стеки по 1 МБ — это реальная память (резервируется, а выделяется при обращении); пулы потоков и виртуальные потоки существуют именно поэтому ([[executors-and-thread-pools]]).
- Рост Metaspace после каждого redeploy или при активной динамической генерации классов (Mockito, CGLIB-прокси в тестах, Groovy) — это утечка загрузчика классов, а не повод вечно поднимать лимит.
- Связанные заметки: [[garbage-collection]], [[jvm-jre-jdk]], [[java-memory-model]], [[reference-types]].
