## Кратко
`String` — неизменяемый `final`-класс, литералы которого живут в **пуле строк** (string pool) — управляемой JVM таблице уникальных строк в куче. Именно неизменяемость делает возможными пул, кеширование хеш-кода, потокобезопасность и безопасное использование строк как ключей и учётных данных. Для построения строк в циклах используй `StringBuilder`; `StringBuffer` — его синхронизированный, по большей части устаревший близнец.

## Основное
### Свойства String
- `final`-класс, неизменяемый: каждый «изменяющий» метод (`concat`, `replace`, `toUpperCase`, `strip`) возвращает новый объект.
- Начиная с Java 9 содержимое хранится как `byte[]` плюс байт кодировки (Latin-1 = 1 байт на символ, UTF-16 = 2) вместо `char[]` («компактные строки», compact strings), что вдвое сокращает память для ASCII-текста.
- Создаётся из литерала (`"abc"`), конкатенацией (`+`, начиная с Java 9 компилируется в `invokedynamic`/`StringConcatFactory`), через `String.valueOf`, `new String(...)`, текстовые блоки `"""..."""` (Java 15).
- Можно использовать в `switch` начиная с Java 7; `equals`/`hashCode` основаны на значении; `hashCode` кешируется в поле после первого вызова (неизменяемость делает это безопасным).
- Полезный свежий API: `strip`, `isBlank`, `lines`, `repeat` (11), `formatted`, `stripIndent` (15), `String.join`, `chars()`/`codePoints()`.

### Пул строк
- Хеш-таблица (`StringTable`) внутри JVM, хранящая один канонический экземпляр на каждое уникальное содержимое. В Java 6 она жила в PermGen; начиная с 7 — в основной куче ([[jvm-memory-areas]]), поэтому строки из пула обычным образом собираются GC, когда на них больше нет ссылок. Размер таблицы по умолчанию — 65 536 корзин (`-XX:StringTableSize`).
- Литерал в исходном коде интернируется при загрузке класса: `"abc" == "abc"` равно `true` даже между разными классами. Константные выражения времени компиляции (`"a" + "b"`, `final String x = "a"; x + "b"`) тоже сворачиваются и интернируются.
- `new String("abc")` всегда создаёт новый объект вне пула (сам литерал всё равно интернирован). `s.intern()` возвращает экземпляр из пула, добавляя его, если его там нет.
- Зачем: экономия памяти для повторяющихся строк (уровни логирования, имена колонок, ключи JSON) и дешёвое `==` внутри JVM. Пул — хрестоматийный пример паттерна **Flyweight** ([[structural-patterns]]).
- Цена: поиск при создании литерала; строки, полученные во время выполнения (из сокета или БД), не попадают в пул, если не вызвать `intern()`, что обычно плохая идея; дедупликацию лучше оставить G1 с `-XX:+UseStringDeduplication` ([[garbage-collection]]).

### Почему неизменяемость и final
- Пул корректен, только если никто не может изменить общий экземпляр.
- Безопасность: строки несут имена классов для загрузчика классов, пути к файлам, JDBC URL и учётные данные; изменяемую строку можно было бы поменять после проверки и до использования.
- Потокобезопасность без синхронизации; строки безопасно разделять и использовать как ключи в `HashMap`, `ConcurrentHashMap` ([[hashmap-internals]]).
- `final` не даёт подклассу сломать всё перечисленное, переопределив `equals` или `hashCode`.

### `char[]` для паролей
- Пароль в `String` остаётся в памяти (и, возможно, в пуле и в дампах кучи), пока его не уберёт GC, и очистить его нельзя. `char[]` можно перезаписать нулями (`Arrays.fill`) сразу после использования, поэтому `Console.readPassword()` и API `KeyStore` принимают `char[]`. Это смягчение, а не гарантия: JIT и ОС всё равно могут скопировать байты.

### String против StringBuilder против StringBuffer
| | `String` | `StringBuilder` (1.5) | `StringBuffer` (1.0) |
|---|---|---|---|
| Изменяемый | нет | да | да |
| Потокобезопасный | да (неизменяемый) | нет | да (каждый метод `synchronized`) |
| Применение | значения, ключи, константы | построение в цикле, один поток | наследие; почти никогда: билдеры редко разделяются между потоками |

- Начиная с Java 9 `a + b + c` в одном выражении компилируется в единственный вызов `invokedynamic`, который так же быстр, как билдер; билдер выигрывает только внутри циклов, где `+=` создаёт новую строку на каждой итерации.
- `String.join`, `Collectors.joining`, `StringJoiner` покрывают частый случай «соединить через разделитель».

## Пример
```java
String a = "esim-" + "kg";            // свёртка констант -> интернирована
String b = "esim-kg";
String c = new String("esim-kg");     // новый объект вне пула
System.out.println(a == b);           // true
System.out.println(b == c);           // false
System.out.println(b == c.intern());  // true
System.out.println(b.equals(c));      // true: всегда сравнивай содержимое через equals

// Построение отчёта в цикле: StringBuilder, а не +=
StringBuilder sb = new StringBuilder(256);
for (var line : lines) {
    sb.append(line.msisdn()).append(';').append(line.amountMinor()).append('\n');
}
String report = sb.toString();

// То же самое, более декларативно
String report2 = lines.stream()
        .map(l -> l.msisdn() + ";" + l.amountMinor())
        .collect(Collectors.joining("\n"));
```

## Подводные камни
- Сравнение строк через `==` работает для литералов и не работает для строк, полученных во время выполнения; это никогда не правильный выбор. `Objects.equals(a, b)` к тому же обрабатывает `null`.
- `substring` в Java 6 разделял `char[]` родительской строки и мог удерживать огромный массив; начиная с 7u6 он копирует. `split` с регулярным выражением на горячем пути медленный; заранее компилируй `Pattern` или используй циклы с `indexOf`.
- `toLowerCase()`/`toUpperCase()` зависят от локали (проблема турецкой i); для строк протоколов передавай `Locale.ROOT`.
- Логирование через `"..." + obj` строит строку, даже когда уровень отключён; используй параметризованное логирование `log.debug("id={}", id)`.
