## Кратко
Класс загружается, связывается (linking) и инициализируется лениво — при первом активном использовании. Статическая инициализация выполняется один раз на класс, сначала родитель, потом наследник, в текстовом порядке статических полей и статических блоков. Инициализация экземпляра выполняется при каждом `new`: для каждого класса от вершины иерархии вниз — инициализаторы полей экземпляра и блоки экземпляра в текстовом порядке, затем тело конструктора.

## Основное
### Фазы загрузки класса
1. **Загрузка (loading)**: загрузчик классов (class loader) находит байты `.class` (classpath, module path, jar, сеть) и создаёт объект `Class` в metaspace ([[jvm-memory-areas]]). Делегирование: загрузчик сначала спрашивает родителя (bootstrap → platform → application → пользовательский), поэтому `java.lang.String` никогда не может быть подменён пользовательским jar.
2. **Связывание (linking)**: верификация (байткод корректен и типобезопасен), подготовка (статические поля получают значения по умолчанию: `0`, `null`, `false`), разрешение (символьные ссылки превращаются в прямые, часто лениво).
3. **Инициализация**: выполняется статический инициализатор `<clinit>`: инициализаторы статических полей и блоки `static {}` в порядке исходного кода. JVM берёт блокировку на класс, так что это происходит ровно один раз, даже если несколько потоков соревнуются (именно эта блокировка делает идиому holder безопасным ленивым синглтоном, см. [[creational-patterns]]).

### Что запускает инициализацию
- `new`, вызов статического метода, чтение или запись неконстантного статического поля, `Class.forName(name)` (но не `loadClass`), рефлексия, инициализация подкласса, роль главного класса (main class).
- Не запускают: обращение к `static final` константе времени компиляции (она встраивается в место использования), создание массива этого типа, литерал `SomeClass.class`.

### Статический порядок (один раз на класс)
1. Сначала полностью завершается статическая инициализация суперкласса, по всей цепочке вверх до `Object`.
2. Затем подкласс: инициализаторы статических полей и статические блоки вперемешку, в текстовом порядке.
- Интерфейсы инициализируются, только когда читается одно из их неконстантных полей или нужен default-метод; инициализация реализующего класса не инициализирует его интерфейсы.

### Порядок для экземпляра (каждый `new`)
Для каждого класса от вершины иерархии вниз:
1. инициализаторы полей экземпляра и блоки инициализации экземпляра `{ ... }` в текстовом порядке;
2. тело конструктора (после того как неявный или явный вызов `super(...)` вернул управление).

Таким образом, для `new Child()` полная последовательность такая: статика `Parent` → статика `Child` (только в первый раз) → поля/блоки `Parent` → конструктор `Parent` → поля/блоки `Child` → конструктор `Child`. Краткая формулировка источника «поле, затем динамический блок, затем конструктор, попарно от родителя к наследнику» — ровно это.

### Один класс, два загрузчика
- Идентичность класса — это пара (загрузчик, полное имя). Одни и те же байты, загруженные двумя загрузчиками, — это два разных класса: `instanceof` не проходит, а приведение бросает `ClassCastException`. С этим сталкиваются в серверах приложений, плагинных системах и инструментах горячей перезагрузки.
- Класс выгружается, только когда его загрузчик становится недостижимым; поэтому metaspace растёт при повторных redeploy, которые оставляют утечку старого загрузчика.

## Пример
```java
class Parent {
    static { System.out.println("1 Parent static"); }
    { System.out.println("3 Parent instance block"); }
    Parent() { System.out.println("4 Parent ctor"); describe(); }
    void describe() { System.out.println("Parent.describe"); }
}

class Child extends Parent {
    private final String name = "child";
    static { System.out.println("2 Child static"); }
    { System.out.println("5 Child instance block"); }
    Child() { System.out.println("6 Child ctor"); }
    @Override void describe() { System.out.println("Child.describe name=" + name); }
}

// new Child(); печатает 1,2,3,4, затем "Child.describe name=null"  <-- вызов переопределяемого метода из конструктора
//              затем 5,6. Второй new Child() начинается с 3.
```

## Подводные камни
- Вызов переопределяемого метода из конструктора выполняет версию подкласса до того, как поля подкласса инициализированы (`name=null` выше). Помечай такие методы `final` или `private` либо выноси логику из конструктора ([[constructors-and-initialization]]).
- Статический инициализатор, бросивший исключение, приводит к `ExceptionInInitializerError`; каждое последующее использование класса бросает `NoClassDefFoundError`, а исходная причина к тому времени давно ушла из логов. Статические блоки должны быть тривиальными.
- Циклическая статическая инициализация (статическая инициализация A трогает B, а статическая инициализация B трогает A) видит наполовину инициализированное состояние (значения по умолчанию `null`/`0`) без всякой ошибки.
- Константы `static final` встраиваются при компиляции; если поменять константу в библиотеке и не перекомпилировать клиента, в байткоде клиента останется старое значение.
- Связанные заметки: [[modifiers-final-static-access]], [[jvm-jre-jdk]], [[constructors-and-initialization]].
