## Кратко
`HashMap` — это массив **корзин** (buckets, по умолчанию 16). Хеш ключа выбирает корзину; коллизии внутри корзины образуют связный список, который с Java 8 превращается в красно-чёрное дерево, как только в нём 8 или больше записей. Когда map заполнена на 75% (коэффициент загрузки, load factor), массив удваивается, и каждая запись перехешируется.

## Основное
### Структура
- `table[]` из `Node` (ключ, значение, закэшированный хеш, next). Корзина либо пуста, либо содержит цепочку `Node`, либо дерево `TreeNode` (parent, left, right, prev, флаг red): собственное красно-чёрное дерево HashMap, а не `TreeMap`.
- Значения по умолчанию: ёмкость 16, коэффициент загрузки 0,75, порог превращения в дерево 8, порог обратного превращения 6, минимальный размер таблицы для деревьев 64 (ниже вместо этого выполняется resize).

### put(key, value)
1. `hash = key.hashCode()`, перемешанный через `h ^ (h >>> 16)`, чтобы участвовали старшие биты.
2. `index = hash & (table.length - 1)` (длина всегда степень двойки, поэтому это и есть остаток от деления).
3. Пустая корзина → туда кладётся новый `Node`.
4. Непустая корзина = **коллизия**. Обходится цепочка или дерево: сначала сравниваются сохранённые хеши (дёшево; разные хеши могут попасть в одну корзину), затем при равных хешах вызывается `equals()`. Совпадение → значение перезаписывается. Нет совпадения → добавление в конец цепочки (или вставка в дерево).
5. Длина цепочки ≥ 8 → превращение в дерево (поиск падает с O(n) до O(log n)). При удалении дерево снова становится цепочкой при ≤ 6.
6. `size > capacity * loadFactor` → resize ×2 и перераспределение.

### Почему дерево работает без Comparable-ключей
Красно-чёрному дереву нужен порядок. HashMap сравнивает ключи в дереве в таком порядке: хеш; затем `compareTo`, если оба ключа реализуют `Comparable` одного класса; затем `tieBreakOrder()`, который сравнивает имена классов и в конце `System.identityHashCode()`. Поэтому подходит любой тип ключа, просто медленнее при коллизиях хешей.

### Родственники
- `Hashtable`: legacy, каждый метод `synchronized`, нет null-ключа и null-значений, `Enumeration` вместо fail-fast итератора. Используй `HashMap` или `ConcurrentHashMap`.
- `LinkedHashMap`: сохраняет порядок вставки (или доступа) с помощью дополнительного связного списка через записи.
- `IdentityHashMap`: сравнивает ключи через `==`, игнорируя `equals`/`hashCode`. Для кэшей по идентичности объектов и фреймворков сериализации.
- `WeakHashMap`: ключи хранятся через `WeakReference` ([[reference-types]]), так что запись исчезает, как только на ключ больше ничего не ссылается. Классическое применение: прикреплять дополнительные данные к объектам, которые нельзя изменить; запись умирает вместе с объектом.

## Пример
```java
// Всё это работает благодаря контракту equals/hashCode
record Point(int x, int y) {}      // records генерируют оба метода корректно

Map<Point, String> names = new HashMap<>();
names.put(new Point(1, 2), "A");
names.get(new Point(1, 2));        // "A": тот же хеш -> та же корзина -> equals() true
```

## Подводные камни
- Переопредели `equals` без `hashCode` — и равные ключи попадут в разные корзины: `get` вернёт null.
- Плохой `hashCode` (константа или мало различных значений) сваливает всё в одну корзину; до Java 8 это был вектор DoS за O(n) для строковых ключей.
- `HashMap` не потокобезопасен: конкурентные `put` могут терять записи; до Java 8 они могли даже создать цикл и бесконечный цикл. Используй [[concurrent-collections]].
- Порядок итерации не определён и меняется после resize; никогда на него не полагайся.
- Обзор остальных реализаций: [[collections-framework]].
