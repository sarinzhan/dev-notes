## Кратко
Маленький пул обычно быстрее. Эмпирическое правило Hikari: `connections = cores * 2 + effective_spindle_count`, то есть 10–20 для типичного сервера Postgres, и это на **все** экземпляры приложения вместе. Больше соединений в основном добавляет переключения контекста и конкуренцию за блокировки на стороне базы данных. Большинство инцидентов «пул исчерпан» — не проблема размера, а транзакция, которая держит соединение, пока ждёт сеть.

## Основное

### Почему большие пулы медленнее
- База данных может выполнять параллельно столько запросов, сколько у неё ядер. Лишние соединения стоят в очереди внутри Postgres (за CPU, за блокировками буферов, за блокировкой WAL), а не внутри Hikari, а очередь внутри БД обходится дороже.
- Формула считает ядра сервера **базы данных**, а не приложения. Шпиндели важны для нагрузок, упирающихся в диск; на SSD/NVMe это слагаемое примерно равно 1.
- Каждое соединение Postgres — это отдельный форкнутый backend-процесс со своей памятью (`work_mem` на каждую сортировку/хеш, несколько МБ базовых накладных расходов). 200 подов приложения × 50 соединений = 10 000 backend-процессов: у сервера закончится память раньше, чем запросы.
- `max_connections` в Postgres (по умолчанию 100) — жёсткий глобальный лимит. Размер пула на экземпляр × число экземпляров + миграции + мониторинг + административные сессии должны оставаться ниже него, с запасом на rolling deploy, когда старые и новые поды работают одновременно.
- Когда арифметика не сходится, ставь перед базой PgBouncer в режиме пулинга **transaction**: тысячи клиентских соединений отображаются на несколько десятков серверных. Цена: нет состояния сессии (нет `SET`, нет prepared statements, если не задан `max_prepared_statements` в PgBouncer 1.21+, нет advisory locks между транзакциями, нет `LISTEN`).

### Таймауты Hikari
| Свойство | По умолчанию | Смысл |
|---|---|---|
| `connectionTimeout` | 30 с | сколько `getConnection()` ждёт до `SQLTransientConnectionException`; снизь до 1–3 с, чтобы насыщенный пул быстро падал |
| `idleTimeout` | 10 мин | когда закрываются простаивающие соединения сверх `minimumIdle`; при фиксированном пуле не важен |
| `maxLifetime` | 30 мин | вывести соединение из оборота в любом случае; держи ниже порога, после которого БД/балансировщик убивает простаивающие соединения (Postgres `idle_session_timeout`, облачный NAT ~ 10–15 мин) |
| `keepaliveTime` | 0 | пинговать простаивающие соединения, чтобы файрволы их не обрывали |
| `validationTimeout` | 5 с | для проверки `isValid()` перед выдачей соединения |
| `leakDetectionThreshold` | 0 (выкл.) | логировать стек-трейс, когда соединение удерживается дольше этого времени |
- `maximumPoolSize = minimumIdle` (фиксированный пул) избегает постоянного открытия/закрытия при всплесках нагрузки; именно это рекомендуют авторы Hikari.

### Исчерпание пула
- Симптом: `HikariPool-1 - Connection is not available, request timed out after 30000ms`, всплески задержки ровно на `connectionTimeout`, `hikaricp.connections.pending` > 0 при `hikaricp.connections.active == maximumPoolSize`.
- Частая причина: метод с [[spring-transactional|@Transactional]], который вызывает HTTP API, Kafka или S3. Соединение удерживается на всё время вызова; при пуле из 10 соединений десять медленных вызовов к партнёру блокируют все остальные операции с БД в приложении, включая health check.
- Другие причины: Open Session In View, удерживающий соединение во время рендеринга ответа; `REQUIRES_NEW` внутри `REQUIRED` (два соединения на поток, взаимная блокировка, когда пул меньше числа потоков); забытый `close()` у «сырого» `DataSource.getConnection()`.
- С [[virtual-threads]] пул потоков больше не ограничивает, поэтому пул соединений становится первым узким местом; очередь просто переезжает в `getConnection()`.

### Метрики, за которыми стоит следить
- Micrometer публикует `hikaricp.connections.{active,idle,pending,timeout,usage,acquire,creation}`; `pending` и `timeout` — для алертов, `usage` (время удержания соединения) — для диагностики.
- На стороне Postgres: число записей в `pg_stat_activity` по `state`, сессии `idle in transaction` (приложение держит открытую транзакцию), использование `max_connections`.

## Пример
```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 16
      minimum-idle: 16
      connection-timeout: 3000          # быстро падать
      max-lifetime: 1500000             # 25 мин, ниже лимитов простоя PgBouncer/NAT
      keepalive-time: 300000            # 5 мин
      leak-detection-threshold: 20000   # логировать удержание > 20 с
      data-source-properties:
        ApplicationName: esim-provisioning   # видно в pg_stat_activity
  jpa:
    open-in-view: false
```
Прикидка по числам: 3 пода × 16 = 48 соединений к Postgres с `max_connections = 100` оставляют место для Flyway, Grafana и второго деплоя во время раскатки.

## Подводные камни
- `leak-detection-threshold` — самый быстрый способ найти забытый `close()` или транзакцию, вызывающую внешний API; он только логирует и не возвращает соединение в пул.
- `maximumPoolSize` = 100 «на всякий случай» ухудшает p99-задержку под нагрузкой и может вызвать `FATAL: too many connections` у задачи миграции.
- `maxLifetime` выше таймаута простоя инфраструктуры даёт спорадические ошибки `Connection reset` на первом запросе после периода тишины.
- Ретрансляторы на `@Scheduled` в Spring Boot ([[outbox-pattern]]) используют тот же пул; зависшая транзакция ретранслятора невидима со стороны HTTP, пока пул не опустеет.
- `validationTimeout` и `connection-test-query` не нужны для драйверов JDBC4; Postgres JDBC поддерживает `isValid()`.
- Связанные заметки: [[spring-boot-properties-and-profiles]] — переопределение для каждого окружения, [[postgres-isolation-levels]] — что блокируют сессии `idle in transaction`.
