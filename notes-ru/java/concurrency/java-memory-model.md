## Кратко
Модель памяти Java (Java Memory Model, JMM) — часть спецификации языка, которая говорит, какие записи поток гарантированно увидит. Она определяет *действия* (чтение/запись переменной, захват/освобождение монитора, чтение/запись `volatile`, запуск потока) и одно отношение между ними — **happens-before** («происходит до»): если A happens-before B, то всё, что сделал A, видно B. Без такого ребра JVM и процессор вольны кэшировать значения и переупорядочивать инструкции.

## Основное
- **Проблема видимости.** Поток может держать поле в регистре или кэше процессора вместо основной памяти, поэтому другой поток, читающий основную память, видит устаревшее значение, и наоборот. JMM описывает это как «у каждого потока есть рабочая копия переменных»; это модель, а не требование к железу.
- **Переупорядочивание.** Компилятор и процессор могут выполнять операции не в том порядке, в котором они написаны, если один поток не может заметить разницы. Другой поток *может* её заметить, поэтому флаг, записанный после каких-то данных, не гарантирует видимости этих данных, если флаг не `volatile`.
- Ключевые слова, создающие рёбра happens-before: `synchronized`, `volatile` и `final`.

### Правила happens-before, которые реально используются
- Порядок программы: внутри одного потока каждое действие happens-before следующего в порядке исходного кода.
- Монитор: освобождение монитора happens-before каждого последующего захвата **того же** монитора (выход из блока `synchronized` → вход в блок на том же объекте).
- Volatile: запись в `volatile`-поле happens-before каждого последующего чтения этого поля.
- Запуск потока: `Thread.start()` happens-before всего в `run()`; всё в потоке happens-before возврата из `join()` на нём.
- Транзитивность: если A → B и B → C, то A → C. Именно это позволяет volatile-флагу «опубликовать» обычные записи, сделанные до него.

### Что synchronized и volatile делают с памятью
- Вход в блок `synchronized` обновляет представление потока из основной памяти; выход из него сбрасывает записи потока. Гарантия действует только между потоками, использующими **один и тот же монитор**.
- Чтения и записи `volatile` идут прямо в основную память, и их нельзя переупорядочить с окружающими чтениями и записями других переменных. Поэтому volatile boolean работает как флаг завершения.

## Пример
```java
class Config {
    private int value;                 // обычное поле
    private volatile boolean ready;    // флаг

    void init() { value = 42; ready = true; }   // поток-писатель

    int read() {                                // поток-читатель
        if (ready) return value;   // гарантированно 42: write(value) -> write(ready) -> read(ready) -> read(value)
        return -1;
    }
}
```
Если бы `ready` не был `volatile`, читатель мог бы увидеть `ready == true` и `value == 0`.

## Куча и стек с точки зрения потока
- У каждого потока **свой стек**: локальные переменные, параметры методов, фреймы вызовов. Ничто в стеке одного потока не видно другому. Переполнение → `StackOverflowError`.
- **Куча** (heap) общая для всех потоков; там живёт каждый объект. Переполнение → `OutOfMemoryError: Java heap space`. Потоки кэшируют значения из кучи; `volatile` говорит им этого не делать.

## Подводные камни
- `volatile` даёт видимость и упорядочивание, **но не атомарность**: `counter++` на volatile — всё равно гонка. Используй `AtomicInteger` или блокировку.
- Синхронизация на разных объектах не даёт ребра happens-before между потоками.
- `synchronized` — это ещё и то, что делает `wait()`/`notify()` корректными; см. [[synchronization-and-monitors]]. Опасности, возникающие из-за отсутствующих рёбер, — в [[concurrency-hazards]].
