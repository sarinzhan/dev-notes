## Кратко
Четыре способа, которыми многопоточная программа идёт не так: **состояние гонки** (race condition) делает результат зависимым от порядка планирования; **взаимная блокировка** (deadlock) замораживает потоки, ждущие блокировок друг друга; **livelock** держит их занятыми без прогресса; **голодание** (starvation) не даёт одному потоку дождаться своей очереди.

## Основное
- **Состояние гонки**: два или более потока обращаются к общему ресурсу (переменной, файлу, структуре), и результат зависит от порядка, в котором их запускает планировщик. Более строгий термин — *недетерминированность параллелизма*. Классические случаи — «проверить, затем действовать» (check-then-act: `if (!map.containsKey(k)) map.put(k, v)`) и «прочитать-изменить-записать» (read-modify-write: `count++`). Исправление: сделать составное действие атомарным (блокировка, `putIfAbsent`, `AtomicInteger`).
- **Deadlock**: поток A держит блокировку 1 и ждёт блокировку 2, поток B держит блокировку 2 и ждёт блокировку 1. Ни один не может продолжить. Нужны четыре условия: взаимное исключение, удержание с ожиданием, отсутствие вытеснения, циклическое ожидание. Сломай любое из них, обычно циклическое ожидание, — всегда захватывай блокировки в одном глобальном порядке или используй `tryLock` с таймаутом.
- **Livelock**: потоки постоянно меняют состояние в ответ друг на друга (оба отступают, оба повторяют, оба отступают…) и никогда не продвигаются. Выглядит живым, ничего не делает. Исправление: отступ со случайной задержкой.
- **Голодание**: поток никогда не получает ресурс, потому что всегда выигрывают другие (нечестные блокировки, потоки с более высоким приоритетом, писатель, который никак не войдёт, потому что постоянно приходят читатели). Исправление: честные блокировки (`new ReentrantLock(true)`), ограниченное ожидание.

## Пример
```java
// Deadlock: порядок блокировок в двух методах различается
void transfer(Account from, Account to, long amount) {
    synchronized (from) {
        synchronized (to) { from.debit(amount); to.credit(amount); }
    }
}
// transfer(a, b) и transfer(b, a) параллельно могут зависнуть навсегда.

// Исправление: ввести глобальный порядок
void transferSafe(Account from, Account to, long amount) {
    Account first = from.id < to.id ? from : to;
    Account second = first == from ? to : from;
    synchronized (first) { synchronized (second) { from.debit(amount); to.credit(amount); } }
}
```

## Подводные камни
- Deadlock виден в thread dump как потоки в `BLOCKED` с «waiting to lock <X> ... locked <Y>»; `jstack` сообщает о нём явно. Анализируй дампы, а не гадай.
- Deadlock в базе данных — тот же паттерн, только со строками вместо мониторов; Postgres обнаруживает их и прерывает одну транзакцию. См. [[postgres-isolation-levels]].
- Гонки не исправляются одним `volatile`; он исправляет видимость, а не атомарность ([[java-memory-model]]).
- Инструменты для избежания этих проблем — в [[synchronization-and-monitors]] и [[locks-and-lock-free]].
