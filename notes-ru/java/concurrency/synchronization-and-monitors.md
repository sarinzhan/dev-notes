## Кратко
**Синхронизация** — это организация последовательного доступа к общему ресурсу (ограничение того, сколько потоков может одновременно находиться внутри участка кода), чтобы программа не сбоила из-за состояния гонки. В Java встроенный инструмент — монитор, стоящий за `synchronized`; альтернативы — блокировки и атомарные классы из `java.util.concurrent`.

## Основное
### Словарь
- **Критическая секция** (critical section): код, который обращается к общему ресурсу и не должен выполняться больше чем в одном потоке одновременно. Два потока внутри → состояние гонки.
- **Мьютекс** (mutex, mutual exclusion): блокировка, которая позволяет ровно одному потоку владеть ресурсом в каждый момент.
- **Монитор** (monitor): конструкция более высокого уровня, мьютекс плюс набор ожидания. Он есть у каждого объекта Java; `synchronized` его захватывает.
- **Потокобезопасность** (thread safety): свойство кода или объекта вести себя корректно независимо от того, сколько потоков используют его одновременно.
- **Неизменяемые объекты** потокобезопасны бесплатно: после создания ничего не может измениться, так что синхронизировать нечего. Предпочитай их (records, `final`-поля, защитные копии).

### Инструменты, от самых тяжёлых к самым лёгким
- Метод или блок `synchronized`: пессимистичная блокировка, превращает конкурентное выполнение в последовательное на этом мониторе.
- `java.util.concurrent.locks`: `ReentrantLock`, `ReadWriteLock`, `Semaphore` ([[locks-and-lock-free]]).
- Атомарные классы (`AtomicInteger`, `AtomicReference`): оптимистичные, неблокирующие, построены на **CAS** (compare-and-swap, «сравнить и заменить»), который процессор выполняет как одну неделимую инструкцию. Перед записью CAS проверяет, что значение всё ещё такое, каким поток его последний раз прочитал; если нет, обновление не проходит, и поток повторяет попытку. Именно это сделало возможным пакет конкурентности Java 5; до него «конкурентная» работа с одним ресурсом была возможна только через монитор.

### wait / notify / notifyAll
- `wait()` (у `Object`) освобождает монитор и усыпляет текущий поток в наборе ожидания объекта, пока другой поток не вызовет `notify()` / `notifyAll()` на том же объекте. Необязательно принимает таймаут. Бросает `InterruptedException`.
- `notify()` будит один ожидающий поток, `notifyAll()` — все. Разбуженный поток должен заново захватить монитор, прежде чем продолжить.
- Их нужно вызывать внутри `synchronized` на этом объекте: сами методы не синхронизированы, а проверка условия и ожидание должны быть атомарными, иначе notify может потеряться между проверкой и ожиданием.
- `sleep()` устроен иначе: он сохраняет все удерживаемые мониторы и не зависит от другого потока.

## Пример
```java
class BoundedBuffer<T> {
    private final Deque<T> items = new ArrayDeque<>();
    private final int capacity;

    synchronized void put(T item) throws InterruptedException {
        while (items.size() == capacity) wait();   // всегда 'while', никогда 'if'
        items.addLast(item);
        notifyAll();
    }
    synchronized T take() throws InterruptedException {
        while (items.isEmpty()) wait();
        T item = items.removeFirst();
        notifyAll();
        return item;
    }
}
```

## Подводные камни
- Ожидание с `if` вместо `while`: из-за ложных пробуждений (spurious wake-ups) и `notifyAll` условие может быть всё ещё ложным после возврата из `wait()`.
- Синхронизация на `this` или на публичном объекте позволяет внешнему коду тебя заблокировать; предпочитай приватный final-объект блокировки.
- `synchronized` на *методе* класса блокирует весь экземпляр; два несвязанных метода блокируют друг друга.
- Блокировка внутри `synchronized` прикрепляет (pinning) [[virtual-threads|виртуальный поток]] к его потоку-носителю (до JDK 24); там используй `ReentrantLock`.
- Сторона `synchronized`, связанная с видимостью памяти, объясняется в [[java-memory-model]].
